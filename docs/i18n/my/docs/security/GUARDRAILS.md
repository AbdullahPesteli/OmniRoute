> **အမှန်တရား၏ မူရင်းရင်းမြစ်:** `src/lib/guardrails/`
> **နောက်ဆုံးမွမ်းမံထားသည့်ရက်:** 2026-08-29 — v3.8.51 (Video Bridge transcript ၏ မူလရင်းမြစ်ကို ခေါ်ယူသူက ကြေညာသတ်မှတ်ထားခြင်းဖြစ်ပြီး၊
> server က အတည်ပြုစစ်ဆေးထားခြင်း မရှိသေးပါ — #11661 အရ ရှင်းလင်းထားသည်)

Guardrail များသည် OmniRoute နှင့် upstream provider များကြား နယ်နိမိတ်တွင်
ဘေးကင်းလုံခြုံမှု၊ မူဝါဒနှင့် အကြောင်းအရာပြောင်းလဲမှုများကို အတည်ပြုကျင့်သုံးစေသည်။ Guardrail တစ်ခုစီသည် request payload များကို (`preCall`) နှင့်
upstream response များကို (`postCall`) စစ်ဆေးနိုင်ပြီး (လိုအပ်ပါက
ငြင်းပယ်ခြင်း၊ ပြောင်းလဲခြင်း သို့မဟုတ် မှတ်ချက်ထည့်ခြင်းတို့ကို ပြုလုပ်နိုင်သည်)။

စနစ်သည် **fail-open** ဖြစ်သည်။ Guardrail တစ်ခုကို လုပ်ဆောင်နေစဉ် exception ဖြစ်ပေါ်ပါက registry သည်
error ကို မှတ်တမ်းတင်ပြီး request ကို ပျက်ကွက်စေမည့်အစား နောက် guardrail ဖြင့်
ဆက်လက်လုပ်ဆောင်သည်။ ပိတ်ဆို့ခြင်းသည် မတော်တဆဖြစ်ပေါ်ခြင်း မဟုတ်ဘဲ တိကျရှင်းလင်းသော ဆုံးဖြတ်ချက် (`block: true`) ဖြစ်သည်။

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

**မမြင်သော မော်ဒယ်များ** သို့ ရည်ညွှန်းထားသော ပုံရိပ်ပါသော တောင်းဆိုမှုများကို ဖမ်းဆီးပြီး
တောင်းဆိုမှုကို အပြုံးရည်မှတ်ထားသော မော်ဒယ်သို့ ပြန်လည်လှည့်ပတ်ရန် သို့မဟုတ်
ပုံရိပ်အပိုင်းများကို စီစဉ်နိုင်သော မော်ဒယ်မှ ထုတ်လုပ်ထားသော စာသားဖော်ပြချက်များဖြင့်
အစားထိုးသည်။ ဤသည်က စာသားသာဖြစ်သော ပံ့ပိုးသူများကို မျိုးစုံအမျိုးအစား
payload များကို ထိန်းချုပ်စွာ ကိုင်တွယ်နိုင်စေသည်။

စီးဆင်းမှု:

1. ရည်ညွှန်းထားသော မော်ဒယ်သည် မျက်မြင်မှုကို ထောက်ပံ့ထားပါက ကျော်လွှားပါ (သို့မဟုတ်
   အခွင့်အရေးထားသော မော်ဒယ်စာရင်း `isVisionBridgeForcedModel` တွင် ပါရှိပါက)။
2. ပုံရိပ်အပိုင်းများကို `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`) မှတဆင့် ထုတ်ယူပါ၊ ဤသည်သည် **ထပ်တူမီဒီယာ
   ရှာဖွေရန်** `detectMediaParts()` ကို `open-sse/utils/mediaParts.ts` တွင်
   လွှဲပြောင်းသည် — combo compatibility filter နှင့် မျှဝေထားသော တစ်ခုတည်းသော
   အချက်အလက်။ ထုတ်ယူမှုသည် `replaceImageParts` သို့ ပြန်လည်ထည့်သွင်းနိုင်သော
   အထက်ဆုံးအပိုင်းများအတွက် ခွင့်ပြုထားသည် (ထုတ်ယူ↔အစားထိုး စာချုပ်): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, နှင့် Responses API `input_image`။ အတွင်းပိုင်း
   ထိတွေ့မှုများနှင့် အညွှန်းသာရှိသော အမျိုးအစားများသည် combo-filter
   ပစ္စည်းဖြစ်ပြီး အမြဲတမ်း ထုတ်ယူမည်မဟုတ်ပါ။ မည်သည့်အရာမှ မတွေ့ပါက ကျော်လွှားပါ။
3. `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`) မှတဆင့် runtime config ကို
   ဖြေရှင်းပါ: အသစ်သော `modalityBridge*` သတ်မှတ်ချက်များသည် အနိုင်ရသည်; ရှေးဟောင်း
   `visionBridge*` သတ်မှတ်ချက်များသည် **တစ်လှည့်ကျော်လွှားမှု** (rollback window)
   အနေဖြင့် ကျန်ရှိသည်။ ကာကွယ်စောင့်ရှောက်မှု ပိတ်ထားသောအခါ မည်သည့်မီဒီယာ
   လှည့်ပတ်မှုမပြုလုပ်ပါ။
4. မော်ဒယ်ရွေးချယ်သူ (`modalityBridgeVisionMode`, အောက်တွင် ဇယားကို ကြည့်ပါ) သည်
   ပြန်လည်လှည့်ပတ်မှုနှင့် ဖော်ပြမှုကို ဆုံးဖြတ်သည်။ ပြန်လည်လှည့်ပတ်မှုသည်
   `modifiedPayload` ကို `model` ကိုသာ အစားထိုးပြီး meta `{ rerouted, fromModel, toModel, imagesKept }` ဖြင့် ပြန်လည်ပေးသည်။
5. ဖော်ပြမှုလမ်းကြောင်း: ပုံရိပ်များကို `maxImages` တွင် ကန့်သတ်ပြီး
   အလုပ်သိရှိသော prompt ကို ဖွဲ့စည်းပါ၊ ဖော်ပြမှု cache ကို စစ်ဆေးပါ၊
   မျက်မြင်မော်ဒယ်ကို **အချိန်အတူ** ခေါ်ပါ (`Promise.allSettled`), နှင့်
   `[Image N]: <description>` စာသားအပိုင်းများကို ၎င်းတို့၏နေရာတွင် ထည့်သွင်းပါ။
   ဖော်ပြမှုမအောင်မြင်ပါက `null` ဖြစ်ပြီး မူရင်းပုံရိပ်အပိုင်းကို
   **ထိန်းသိမ်းထားသည်** (#4012) — combo ဖော်ပြမှုလမ်းကြောင်းတွင်
   ဖော်ပြမှုများအားလုံး မအောင်မြင်ပါက အတည်ပြုမရသော မျက်မြင်မော်ဒယ်
   အထက်ပိုင်းသည် `(unavailable — no vision-capable provider connected)` stub
   ကို အစားထိုးရရှိသည် (#8430)။
6. `modifiedPayload` + meta (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) ကို ပြန်လည်ပေးပါ။

#### မော်ဒယ်ရွေးချယ်သူ (`modalityBridgeVisionMode`)

| မော်ဒယ်    | အခြေခံ | အပြုအမူ                                                                                                                                                                                                                                                                                                            |
| ---------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auto`     | ✔      | ရှေးဟောင်း heuristic, မထိခိုက် (#6640/#7204): non-combo/`auto/` မော်ဒယ်များသည် အကောင်းဆုံး မျက်မြင်မော်ဒယ်သို့ ပြန်လည်လှည့်ပတ်သည်၊ မူရင်းမော်ဒယ်တွင် အသုံးပြုနိုင်သော အထောက်အထားများ ရှိပါက (ထို့ကြောင့် ဖော်ပြသည်); combo ရည်ညွှန်းများသည် အမြဲဖော်ပြသည်။                                                         |
| `describe` |        | အမြဲဖော်ပြသည် — ပြန်လည်လှည့်ပတ်မှုအပိုင်းကို အပြုံးဖြင့် ကျော်လွှားသည်; အသုံးပြုသူ၏ ရွေးချယ်ထားသော မော်ဒယ်သည် အမြဲတုံ့ပြန်သည်။                                                                                                                                                                                     |
| `reroute`  |        | ပြန်လည်လှည့်ပတ်မှုကို အခွင့်အရေးပြုလုပ်သည်: အထောက်အထားရှိသော မော်ဒယ်ကို ကာကွယ်စောင့်ရှောက်မှုကို ကျော်လွှားသည်။ ပြန်လည်လှည့်ပတ်မှု-**ရည်ညွှန်း** အထောက်အထားက သက်ဆိုင်သည် — အသုံးပြုနိုင်သော မျက်မြင်ရည်ညွှန်းမရှိပါက တောင်းဆိုမှုသည် ဖော်ပြမှုသို့ ကျော်လွှားပြီး စာသားသာဖြစ်သော backend သို့ မရောက်ရှိပါ (#8430)။ |

အခွင့်အရေးပြုလုပ်ထားသော မော်ဒယ်များသည် **auto** heuristic လည်ပတ်မှုမပြုမီ
တိုက်ရိုက်ဖြတ်သန်းသည်; `auto` အပြုအမူသည် pre-PR-1 ကာကွယ်စောင့်ရှောက်မှုနှင့် byte-identical ဖြစ်သည်။

#### API-key scope (`visionBridgeKeyScope.ts`)

ခေါ်ဆိုသူ၏ API key သည် `allowedConnections`, quota pools
(`allowedQuotas`) သို့မဟုတ် မော်ဒယ်များ (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) ကို ကန့်သတ်ပါက
ကာကွယ်စောင့်ရှောက်မှုသည် key သုံးနိုင်သော ပြန်လည်လှည့်ပတ်မှုနှင့် ဖော်ပြမှု

#### Task-aware ဖော်ပြမှု prompt (`modalityBridgeVisionTaskAware`)

Default **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) သည် **နောက်ဆုံး အသုံးပြုသူ စာသား** (500 chars အထိ ကန့်သတ်ထားသည်) ကို အခြေခံ ဖျော်ဖြေရန် prompt တွင် ထည့်သွင်းပြီး အသုံးပြုသူက မေးမြန်းခဲ့သောအရာကို ဖျော်ဖြေရန် ဖျော်ဖြေရန် အကြောင်းအရာကို ဦးတည်စေပြီး မြင်သာသော စာသားကို ရေးသားရန် ဗီရှင် မော်ဒယ်ကို မေးမြန်းသည်။ Flag ကို ပိတ်ထားသောအခါ — သို့မဟုတ် အသုံးပြုသူ စာသားမရှိပါက အခြေခံ prompt ကို မပြောင်းလဲဘဲ အသုံးပြုသည်။

Describe self-loop ၏ OpenAI-compatible request (`callVisionModelSingle()` `visionBridgeHelpers.ts` တွင်) သည် အမြဲ `image_url.detail: "high"` ကို မည်သည့် caller/provider အတွက်မဆို အခြားသော client signal များအပေါ် မူတည်ဘဲ မပြောင်းလဲဘဲ မေးမြန်းသည်။ အနိမ့်-detail sampling သည် OCR အတိအကျကို လျော့နည်းစေပြီး ဤ prompt သည် စာသားရေးသားမှုအတွက် မေးမြန်းသည်၊ ထို့ကြောင့် describe call သည် အစောပိုင်း inbound request သည် မည်သည့် detail level ကို အသုံးပြုခဲ့သည်ကို မူတည်ဘဲ အမြဲ high detail ကို မေးမြန်းသည်။ ဤသည်သည် အတွင်းပိုင်း describe request body ကိုသာ သက်ရောက်သည်။ OmniRoute သည် caller ၏ `image_url.detail` ကို primary request တွင် မပြောင်းလဲဘဲ ပေးပို့သည် — အဆိုပါ default သည် အထူးသဖြင့် ရှာဖွေတွေ့ရှိထားသော OpenCode clients အတွက် သီးသန့်အသုံးပြုသည်၊ `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) တွင်။ Describe self-loop ၏ Anthropic wire-format branch သည် `detail` field မရှိဘဲ default များမှ မသက်ရောက်ပါ။

#### Describe output cap (`modalityBridgeVisionMaxChars`)

| Key                            | Default | Range                   |
| ------------------------------ | ------- | ----------------------- |
| `modalityBridgeVisionMaxChars` | `0`     | `0` သို့မဟုတ် 100–50000 |

`0` (default) သည် **ကန့်သတ်မရှိ** — `callVisionModel()` မှ ပြန်လည်ရရှိသော ဖျော်ဖြေရန်ကို မပြောင်းလဲဘဲ ဖြတ်သန်းပေးသည်၊ ရှိပြီးသား အပြုအမူကို ထိန်းသိမ်းထားသည်။ 100–50000 အတွင်းရှိ တန်ဖိုးတစ်ခုသည် ဖျော်ဖြေရန်ကို `…` suffix ဖြင့် ကန့်သတ်ပြီး `[Image N]: <description>` အဖြစ် ပြန်လည်ထည့်သွင်းသည် (`VisionBridgeGuardrail.preCall()` `src/lib/guardrails/visionBridge.ts` တွင်)။ အပြုံးအပြုံး OCR အလုပ်များအတွက် ဤကို မြှင့်တင်ပါ၊ အောက်ခြေမော်ဒယ်များတွင် token အသုံးပြုမှုကို ကန့်သတ်ရန် လျှော့ပါ။ Dashboard field သည် Vision tab ၏ Advanced panel တွင် ရှိပြီး (`modality-bridge-max-chars` `ModalityBridgeVisionTab.tsx` တွင်) 1 နှင့် 99 အတွင်းရှိ တန်ဖိုးကို 100 floor အထိ ကန့်သတ်သည်၊ အထူးသဖြင့် `0` ကို မထိခိုက်ဘဲ ထိန်းသိမ်းထားသည် — `0` သည် ၎င်း၏ ကိုယ်ပိုင် Zod တန်ဖိုးဖြစ်သည် (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), မျှော်လင့်ထားသော "unset" default မဟုတ်ပါ။

#### Describe cache (`modalityBridge/bridgeCache.ts`)

Describe outputs အတွက် in-memory LRU + TTL cache, shared process-wide။ Key = `sha256(imageRef + composedPrompt + configuredBridgeModel)` သည် length-prefix framing (field-boundary collisions မရှိ) ဖြင့် ရှိသည်။ Model component သည် **configured** bridge model ဖြစ်ပြီး အဖြေကို အမှန်တကယ် ဖြေဆိုခဲ့သော model မဟုတ်ပါ — `callVisionModel` သည် အတွင်းပိုင်းတွင် ပြန်လည်ကျော်ဖြတ်နိုင်ပြီး၊ ကြိုးစားမှုတိုင်းအတွက် keying သည် cache ကို ဖျက်စီးစေမည်။ မအောင်မြင်သော describe များကို အမြဲ cache မထားပါ။ ဆက်တင်များ:

| Key                             | Default | Range   |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### Remote image normalization (self-loop describe/base64 fetch)

Bridge သည် **remote** image ကို ကိုယ်တိုင် ရယူသောအခါ — Anthropic describe self-call နှင့် claude-wire-format base64 ပြောင်းလဲမှု (`ensureBase64ImagesForClaudeWire`), နှစ်ခုလုံးသည် `fetchRemoteImageAsDataUri()` `visionBridgeHelpers.ts` တွင် — ရရှိသော data URI သည် `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) မှတစ်ဆင့် ဖြတ်သန်းပြီး vision-model request တွင် ထည့်သွင်းသည်။ အရွယ်အစားကြီးသော images များကို **2048px long edge** သို့ ကျယ်ပြန့်စေပြီး (OpenAI/Anthropic သည် server-side တွင် အAlready apply လုပ်ထားသော resize cap နှင့် ကိုက်ညီသည်)၊ upload bytes/latency ကို လျော့နည်းစေပြီး vision model သည် မည်သည့်အရာကို မျက်စိထဲတွင် မပြောင်းလဲပါ။ Resizing သည် `sharp` ကို dynamic import ဖြင့် လုပ်ဆောင်သည်: ၎င်း၏ native binary သည် အလုပ်မလုပ်သော platform တစ်ခုတွင် `normalizeDataUri()` **မထုတ်ပစ်ပါ** — ၎င်းသည် မူရင်း bytes ကို passthrough သို့ ပြန်လည်ကျော်ဖြတ်သည်၊ ထို့ကြောင့် describe/base64-conversion လမ်းကြောင်းသည် အမြဲ အလုပ်လုပ်နေပါသည်။ Non-image bytes (decodable image မရရှိသော fetch) များကိုလည်း မထိခိုက်ဘဲ ဖြတ်သန်းသည်။ ဤ normalization သည် bridge သည် ၎င်း၏ ကိုယ်ပိုင် self-call အတွက် ရယူသော images များအတွက်သာ သက်ရောက်သည် — caller ၏ raw passthrough payload တွင် မပြောင်းလဲပါ၊ opt-in-only mutation principle (Hard Rule #20) နှင့် ကိုက်ညီသည်။

#### Settings schema + migration

အသစ်သော `modalityBridge*` keys များကို Zod-validated လုပ်ထားသည် `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCache*` trio, နှင့် Audio Bridge မှ အသုံးပြုသော `modalityBridgeAudio*` group။ Migration `141_modality_bridge_settings.sql` သည် ရှိပြီးသား legacy `visionBridge*` တန်ဖိုးများကို သက်ဆိုင်ရာ အသစ်သော keys သို့ ကူးပြောင်းသည် (idempotent, operator-set `modalityBridge*` တန်ဖိုးကို မဖျက်သိမ်းပါ); legacy keys များသည် တစ်ခုသော release cycle အတွက် ဖတ်ရန် fallback အဖြစ် လက်ခံထားသည်။

#### Transparency header + stats

Describe-transformed responses သည် `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` ကို ယူဆောင်သည် ( `buildModalityBridgeHeader()` `modalityBridge/bridgeStats.ts` တွင် ဖန်တီးပြီး `withModalityBridgeHeader()` `src/sse/handlers/chatHelpers.ts` တွင် stamp လုပ်သည်)။ Rerouted requests များသည် **header မရှိပါ** — payload သည် မထိခိုက်ခဲ့ပြီး model swap သည် response body ၏ `model` field တွင် အထင်ရှားစွာ ရှိသည်။

`GET /api/modality-bridge/stats` (စီမံခန့်ခွဲမှု အတည်ပြုချက်၊ `GET /api/settings` နှင့် တူညီသော အဆင့်) သည် `vision`, `audio`, နှင့် `video` အတွက် အမှတ်အသားများကို ပြန်လည်ထုတ်ပေးသည် `{
attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }`။ `averageLatencyMs` သည် `latencySamples` ကို အသုံးပြုသည်၊ အားလုံးသော ကြိုးစားမှုများကို မဟုတ်ပါ။ အချိန်မရှိသော လုပ်ဆောင်မှုသည် သုည မီလီစက္ကန့် အမှတ်အသားကို ဖန်တီးမည်မဟုတ်ပါ။ `bridged` သည် အောင်မြင်သော ပြောင်းလဲမှုများအတွက် နောက်ပြန်သက်ဆိုင်သော အမည်ဖြစ်ပြီး၊ အောင်မြင်မှုမရှိသော ကြိုးစားမှုများသည် ၎င်းကို တိုးမြှင့်မည်မဟုတ်ပါ။ အမှတ်အသားများသည် လုပ်ငန်းစတင်သောအခါ ပြန်လည်သတ်မှတ်သည် (telemetry, အကောင့်မဟုတ်)။

#### ဒက်ရှ်ဘုတ် ပြင်ဆင်မှု

သီးသန့် ဒက်ရှ်ဘုတ် စာမျက်နှာသည် `/dashboard/settings/modality-bridge` ဖြစ်သည်။ ၎င်း၏ URL-လိပ်စာရရှိနိုင်သော `Vision`, `Audio`, နှင့် `Video` တပ်များသည် `tab` တန်ဖိုးကို ပြောင်းလဲစဉ်တွင် မေးခွန်းအချက်အလက်များကို ထိန်းသိမ်းထားသည်။ Vision တပ်သည် အတည်ပြုခြင်း၊ မODE၊ မော်ဒယ် ရွေးချယ်မှု (အလိုအလျောက် အခြေခံ)၊ အလုပ်အကိုင်သိရှိသော အကြောင်းပြုခြင်း၊ အဆင့်မြင့် အချိန်အဆုံး/ပုံ/ဖော်ပြချက်-အရှည်/ကာကွယ်မှု အကန့်အသတ်များ၊ လုပ်ဆောင်မှု အမှတ်အသားများနှင့် ကာကွယ်ထားသော နမူနာ တောင်းဆိုမှုကို ဖျော်ဖြေရန် ဖွင့်လှစ်သည်။ Audio တပ်သည်လည်း တက်ကြွနေသည်: ၎င်းသည် အတည်ပြုခြင်း၊ STT-သာ မော်ဒယ် ရွေးချယ်မှုကို Auto, အချိန်အဆုံး/အများဆုံး-ကလစ် အကန့်အသတ်များ၊ အသံ အမှတ်အသားများနှင့် `input_audio` နမူနာ စမ်းသပ်မှုကို ဖျော်ဖြေရန် ဖွင့်လှစ်သည်။ Video တပ်သည် လုပ်ဆောင်နိုင်သည်: ၎င်းသည် FFmpeg/ffprobe လုပ်ဆောင်မှု အခြေအနေကို အစီအစဉ်ပြုသည် — UI အခြေအနေ ၄ ခုထဲမှ တစ်ခု (`unknown` သည် probe သည် လေ့လာနေစဉ် သို့မဟုတ် ပြီးမြောက်မထားပါက၊ `restricted` သည် non-loopback ဒက်ရှ်ဘုတ် ဟိုက်စ်တွင် probe ကို client-side တွင် ကျော်လွှားသည်၊ `unavailable` သည် probe လုပ်ပြီး အတည်ပြုမထားသော အခြေအနေ၊ သို့မဟုတ် `available` သည် FFmpeg/ffprobe ဗားရှင်းများဖြင့်) — enable/model/frame/video/timeout အကန့်အသတ်များကို ထိန်းသိမ်းထားသည်၊ မော်ဒယ် ရွေးချယ်မှုကို vision-capable မော်ဒယ်များအတွက် စစ်ဆေးပြီး၊ ဗီဒီယို အမှတ်အသားများကို ဖျော်ဖြေရန် ဖွင့်လှစ်သည်။

AI settings အောက်ရှိ ယခင် Vision Bridge ကတ်သည် အသစ်သော စာမျက်နှာအတွက် သက်ဆိုင်မှု လင့်ခ်ဖြစ်သည်; ၎င်းသည် ဖောင်၏ ဒုတိယ ကူးပေးမှုကို မပိုင်ပါ။ Media Providers သည် Image-to-Text နှင့် Speech-to-Text လုပ်ငန်းစဉ်များကို သက်ဆိုင်ရာ Modality Bridge တပ်များသို့ ချိတ်ဆက်ပြီး ရှိပြီးသား Speech-to-Text playground ကို ဖယ်ရှားမထားပါ။

**Self-loop admission bypass:** describe ခေါ်ဆိုမှုသည် OmniRoute ၏ `/v1` self-loop (စံမဟုတ်သော ပေးသွင်းသူ မော်ဒယ်) မှတဆင့် လမ်းကြောင်းပြောင်းလဲသောအခါ၊ အောက်ခံ-တောင်းဆိုမှုသည် `x-omniroute-admission-bypass: internal` ကို ပေးပို့ပြီး ဖြေရှင်းထားသော self-loop အတည်ပြုချက်ဖြင့် အတည်ပြုသည် — ဒေသတွင်း `sk_omniroute` sentinel ကို ဒေသတွင်း မODE တွင် သို့မဟုတ် လုပ်ငန်းခွင်အဆင့်သတ်မှတ်ထားသော `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env key (#1350) သို့မဟုတ် `REQUIRE_API_KEY=true` ဖြင့် တင်ထားသော လုပ်ငန်းများသည် describe ခေါ်ဆိုမှုကို ဆက်လက်လုပ်ဆောင်နိုင်သည်။ bypass သည် အထူး အတည်ပြုချက်များအတွက်သာ လက်ခံသည်၊ ထို့ကြောင့် အပြင်ဘက် ဖောက်သည်များသည် admission ကို ကျော်လွှားရန် header ကို အသုံးပြု၍ မရပါ။

Legacy defaults သည် `src/shared/constants/visionBridgeDefaults.ts` တွင် ရှိသည်; အသစ်သော mode/task-aware/cache defaults နှင့် settings resolver သည် `src/shared/constants/modalityBridgeDefaults.ts` တွင် ရှိသည်။ guardrail သည် `deps` constructor option ကို ဖျော်ဖြေရန် ဖွင့်လှစ်သည်၊ ထို့ကြောင့် စမ်းသပ်မှုများသည် fake `getSettings` နှင့် `callVisionModel` အကောင့်များကို ထည့်သွင်းနိုင်သည်။

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

အသံပါသော စကားပြော တောင်းဆိုမှုများကို ရည်ညွှန်းထားသော ရည်မှန်းချက်သို့ မရောက်မီ ဖမ်းဆီးသည်။ ၎င်းသည် စကားပြော တောင်းဆိုမှုကို ပြန်လည်လမ်းကြောင်းပြောင်းမည်မဟုတ်ပါ: အသံပိုင်းများကို ရှိပြီးသား OpenAI-သက်ဆိုင်သော multipart endpoint မှတဆင့် အထောက်အထားပြုသည်။ ရွေးချယ်ထားသော စကားပြော မော်ဒယ်သည် စာသား အထောက်အထားများနှင့် ဆက်လက်လုပ်ဆောင်သည်။

လုပ်ငန်းစဉ်:

1. `supportsAudio` ကို `getResolvedModelCapabilities()` မှတဆင့် ဖြေရှင်းပါ။ အထူးပေးသွင်းသူ-မှတ်တမ်း အချက်အလက်များသည် အနိုင်ရသည်၊ ထို့နောက် သက်ရောက်မှု မော်ဒယ် အချက်အလက်များ၊ ထို့နောက် sync လုပ်ထားသော `modalities_input`။ `audio` မပါသော ကြေညာထားသော အထွက်စာရင်းသည် `false` ဖြစ်သည်; အထောက်အထားရှိမှု သက်သေများသည် `null` ဖြစ်သည်။ `false` နှင့် `null` နှစ်ခုလုံးသည် သာမန် bridge ကို ဖွင့်လှစ်သည်၊ `true` သည် ၎င်းကို ကျော်လွှားသည်။
2. `modalityBridgeAudio*` ပြင်ဆင်မှုများကို ဖြေရှင်းပြီး၊ မက်ဆေ့ခ်ျတိုင်းမှ spliceable အထက်ဆုံး အသံပိုင်းများကို `detectMediaParts()` detector မှတဆင့် ထုတ်ယူပါ။ ထောက်ခံထားသော ကြိုးပုံများမှာ OpenAI `input_audio`, `audio_url`, နှင့် `source.media_type: "audio/*"` ဖြစ်သည်။ Nested အသံသည် လမ်းကြောင်းပြောင်းရန် ရှာဖွေသည်၊ သို့သော် splice လမ်းကြောင်းမှ ဖယ်ရှားမထားပါ။ အလုပ်သည် `modalityBridgeAudioMaxClips` ဖြင့် ကန့်သတ်ထားသည်; နောက်ပိုင်းပိုင်းများသည် မထိခိုက်ပါ။
3. သတ်မှတ်ထားသော `provider/model` ကို လက်ခံပါ၊ သို့မဟုတ် `selectAudioBridgeModel()` သည် `AUDIO_TRANSCRIPTION_PROVIDERS` ကို သေချာသော ကတ်လိုက်အရေအတွက်အလိုက် လမ်းကြောင်းပြောင်းပြီး အသုံးပြုနိုင်သော လက်ရှိ ပေးသွင်းသူ အတည်ပြုချက်ဖြင့် ပထမဆုံး မော်ဒယ်ကို ရွေးချယ်ပါ။
4. `callAudioTranscription()` သည် base64/data-URI အသံကို multipart `file` သို့ ပြောင်းလဲသည်၊ သို့မဟုတ် DNS pinning နှင့် 25 MB အကန့်အသတ်ဖြင့် အများပြည်သူသာ အသုံးပြုနိုင်သော အပြင်ဘက် ကာကွယ်မှုမှ တစ်ဆင့် remote `audio_url` ကို ဒေါင်းလုပ်လုပ်သည်။ ၎င်းသည် ဖိုင်နှင့် ရွေးချယ်ထားသော မော်ဒယ်ကို ဒေသတွင်း `/v1/audio/transcriptions` self-loop သို့ POST လုပ်ပြီး `resolveSelfLoopBearer()` ဖြင့် အတည်ပြုသည်။ ရှိပြီးသား transcription လမ်းကြောင်းသည် ပုံမှန် အတည်ပြုချက် ရှာဖွေရန်၊ အချိန်အနည်းငယ်/နှုန်း-ကန့်သတ်မှုကို ကိုင်တွယ်ရန်နှင့် ပေးသွင်းသူကို ပေးပို့ရန် လုပ်ဆောင်သည်။
5. အောင်မြင်သော ခေါ်ဆိုမှုများသည် ၎င်းတို့၏ အပိုင်းများကို `[Audio N]: <transcript>` ဖြင့် အစားထိုးသည်။ ခေါ်ဆိုမှုများသည် `Promise.allSettled` ဖြင့် လုပ်ဆောင်သည်: တစ်ဦးချင်းစီ အောင်မြင်မှုမရှိပါက မူရင်း အသံပိုင်းကို ထိန်းသိမ်းထားသည် (#4012 စာချုပ်)။ ခေါ်ဆိုမှုများအားလုံး မအောင်မြင်ပါက နှင့် ရည်မှန်းချက်သည် `supportsAudio === false` ဖြစ်ပါက၊ အပိုင်းများသည် `[Audio N]: (unavailable — no STT provider connected)` (#8430 စာချုပ်) ဖြစ်သည်။ မသိရသော ရည်မှန်းချက် (`null`) အတွက် အောင်မြင်မှုမရှိသော ရလဒ်သည် မထိခိုက်ပါ။ အသုံးပြုနိုင်သော STT အတည်ပြုချက်မရှိသော သက်သေခံစာသာ ရှိသော ရည်မှန်းချက်သည် အင်တာနက်ခေါ်ဆိုမှုမပြုလုပ်ဘဲ အထူး stub ကို ရရှိသည်။

အောင်မြင်သော အထောက်အထားများသည် လုပ်ငန်း-ကျယ် Modality Bridge LRU/TTL cache ကို အသုံးပြုသည်။ အချက်အလက်သည် အသံကို ရည်ညွှန်းထားသော အချက်အလက်၊ သက်ရောက်မှု `audio-transcription` လုပ်ငန်းအမှတ်အသားနှင့် ရွေးချယ်ထားသော STT မော်ဒယ်ကို ပေါင်းစပ်ထားသည်; အောင်မြင်မှုမရှိသော အမှုများသည် ဘဏ်စာရင်းမရှိပါ။ အသံကြိုးစားမှုများသည် မျှဝေထားသော `bridged`, `cacheHits`, `failures`, နှင့် `lastUsedAt` အမှတ်အသားများကို အပ်ဒိတ်လုပ်သည်။ ပြောင်းလဲထားသော တုံ့ပြန်မှုများသည် `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ကို သယ်ဆောင်သည်; မထိခိုက်သော တောင်းဆိုမှုများသည် Audio Bridge အပိုင်းကို မရရှိပါ။

လုပ်ဆောင်မှု ပြင်ဆင်မှုများသည် DB-backed နှင့် Zod-validated:

| Key                           | Default | Range          |
| ----------------------------- | ------- | -------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —              |
| `modalityBridgeAudioModel`    | `""`    | Auto or STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000    |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10           |

မျှဝေထားသော cache သည် `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, နှင့် `modalityBridgeCacheMaxEntries` ဖြင့် ထိန်းချုပ်ထားသည်။

### Video Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

Chat Completions `messages` နှင့် Responses API `input` တွင် အထက်ဆုံးအဆင့် video အစိတ်အပိုင်းများကို ရှာဖွေပြီး ရည်ညွှန်းထားသော native video အထောက်အကူမပြုသော အခန်းကဏ္ဍကို ခေါ်ဆိုမည်မဟုတ်ပါ။ ထောက်ခံထားသော ပုံစံများမှာ `input_video`, `video_url`, `video_source`, HTTPS URLs, နှင့် `data:video/*;base64,...` data URIs ဖြစ်သည်။ စာသားထဲတွင် ရိုးရိုး ဖိုင်နာမည်များကို video အဖြစ် မထောက်ခံပါ။

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) သည် request traversal, capability/policy စစ်ဆေးခြင်း, per-request aggregation, နှင့် response payload ကို ပိုင်ဆိုင်သည်။ Per-video အလုပ်များ — ရရှိခြင်း၊ အပြုံးရလဒ် cache, frame sequence ကို ဖော်ပြခြင်း (caller-declared audio transcript ကို ပေါင်းစပ်သည်) နှင့် per-attempt metrics/abort/cleanup — သည် `processVideoPart` အောက်တွင် ဖုံးအုပ်ထားပြီး `videoBridgePipeline.ts` တွင် `preCall` ၏ loop အတွင်း video အစိတ်အပိုင်းတစ်ခုစီကို ခေါ်ဆိုသည်။ ထို module သည် `VideoMediaBrokerPort` (bytes ကို ရရှိခြင်းနှင့် sampled frames ကို ထုတ်ယူခြင်း), `VideoAudioTranscriptionPort` (caller-declared audio transcript ကို sampled captions နှင့် ပေါင်းစပ်ခြင်း), နှင့် `VideoDrilldownPort` (legacy raw-store ပုံစံ) ကို သတ်မှတ်ထားသည်။ ထုတ်လုပ်မှု STT နှင့် frame retention သည် `createVideoSttAdapter` နှင့် `createVideoDrilldownAdapter` မှာ ဖော်ပြထားသော port အပေါ်တွင် ဖွဲ့စည်းထားသည်။ နောက်ဆုံးတွင် shared opaque-handle lifecycle ကို အသုံးပြုသည်။

ပွင့်လင်းသော `/v1` request လမ်းကြောင်းသည် subprocess ကို မသွင်းပါနှင့် မခေါ်ဆိုပါ။ Remote videos များကို 50 MiB အကန့်အသတ်အောက်တွင် ဒေါင်းလုပ်လုပ်သည်။ inline base64 videos များသည် 36 MiB decoded per-video cap ကို သုံးစွဲထားပြီး model/messages/framing envelope သည် public JSON request admission limit 50 MiB အတွင်းရှိနေစေရန် ဖြစ်သည်။ Inline length နှင့် decoded-size ခန့်မှန်းချက်များကို allocation မပြုမီ စစ်ဆေးသည်။ HTTPS သည် အစောပိုင်း remote URL နှင့် ပြန်လည်လှည့်ပြောင်းမှုတိုင်းတွင် လိုအပ်ပြီး ရှိပြီးသား public-only outbound guard နှင့် DNS pinning ကို အသုံးပြုသည်။ Bytes များသည် အတိအကျ internal `POST /api/modality-bridge/video/extract` broker အကန့်အသတ်ကို ကျော်ဖြတ်သည်။ ထိုလမ်းကြောင်းသည် `LOCAL_ONLY` နှင့် `SPAWN_CAPABLE` နှစ်ခုလုံးဖြစ်ပြီး per-process authenticated, trusted-loopback request ကိုသာ လက်ခံသည်၊ URL, filesystem path, executable, သို့မဟုတ် argument list ကို မလက်ခံပါ။ API body-size pipeline နှင့် handler ၏ incremental body reader သည် 50 MiB broker input cap ကို သီးသန့်စွာ အတည်ပြုသည်။ ၎င်း၏ bounded queue သည် တစ်ခါတစ်လေ extraction တစ်ခုကိုသာ လုပ်ဆောင်ပြီး လုပ်ငန်းလေးခုကို ခန့်ထားနိုင်ပြီး pending input ကို 100 MiB အထိ ကန့်သတ်ထားသည်။

Broker အတွင်းတွင် `ffprobe` သည် ကိုယ်ပိုင် ဒေတာဖိုင်ကို ဖတ်သည်။ သတ်မှတ်ထားသော format allowlist သည် playlist နှင့် manifest formats များကို ထုတ်ပစ်သည်။ ခွင့်ပြုထားသော MOV-family containers များအတွက် အပြင် MOV ဒေတာကို ရည်ညွှန်းခြင်းသည် မူလတန်းပုံစံဖြစ်ပြီး default အနေဖြင့် ပိတ်ထားသည်။ `ffprobe` နှင့် `ffmpeg` နှစ်ခုလုံးသည် `file`-သာ protocol whitelist, thread တစ်ခု, fixed argument arrays, shell မရှိဘဲ၊ `PATH` မှ ရှာဖွေထားသော executables ကို အသုံးပြုသည်။ Attached-picture cover streams များသည် playable candidates မဟုတ်ပါ။ Playable streams များသည် ကန့်သတ်ချက်များကို ဖြည့်ဆည်းရမည်၊ နှင့် explicit default stream သည် deterministic lowest-index fallback မတိုင်မီ ရွေးချယ်ရန် ဦးစားပေးသည်။ Videos များသည် 600 စက္ကန့်၊ 8,192 pixels တစ်ခုချင်းစီတွင်၊ နှင့် 33,554,432 source pixels အထိ ကန့်သတ်ထားသည်။ FFmpeg သည် 1–16 midpoint JPEG frames ကို sampling လုပ်ပြီး၊ long edge ကို 1,024 pixels အထိ ကျော်မရသောအထိ အနိမ့်အထိ လျှော့ချပြီး၊ အရွယ်အစားသေးသော inputs များကို upscale မလုပ်ပါ။ URL ကို မရရှိပါ။ Sampling သည် default အနေဖြင့် `uniform` ဖြစ်သည်။ Optional `scene_aware` နှင့် experimental `segment_aware` policies များသည် အတည်ပြုထားသော ဒေတာဖိုင်ကို အပေါ်တွင် တစ်ခုထပ်မံ fixed FFmpeg pass ကို လုပ်ဆောင်ပြီး၊ bounded `showinfo` scene timestamps များကို ရွေးချယ်ပြီး၊ detector failure, timeout, malformed output, သို့မဟုတ် အလွတ် candidate set များတွင် deterministic fallback အဖြစ် uniform midpoints အထိ ပြန်လည်သွားသည်။ Segment-aware mode သည် validated scene intervals များအတွက် midpoint samples များကို အချိုးကျ သတ်မှတ်သည်။ Segment-aware evidence နှင့် fallback behavior များကို အောက်တွင် ဖော်ပြထားသည်။ Hard 16-frame cap သည် မည်သည့် policy တွင်မဆို ရွေးချယ်မှုအပြီးတွင် အထူးသတ်မှတ်သည်။ Scene-aware request တစ်ခုတွင် frame တစ်ခုသာ ရှိပါက active full-video သို့မဟုတ် focus window ၏ uniform midpoint ကို အသုံးပြု၍ `policyEffective: uniform` ကို အစီအစဉ်ပြုသည်။ ရွေးချယ်ထားသော scene frame တစ်ခုသည် temporal ends နှစ်ခုကို ထိန်းသိမ်း၍ မရနိုင်ပါ။ Caller သည် အချိန်ကန့်သတ်ထားသော focus window (`start`/`end` seconds) ကို ရွေးချယ်နိုင်ပြီး၊ bounds များသည် media duration သို့ ကန့်သတ်ထားပြီး၊ ပြန်လည်လှည့်ပြောင်းမှု သို့မဟုတ် မဆုံးမသတ် windows များကို ပယ်ဖျက်ပြီး၊ sampling policies များသည် normalized interval အတွင်းသာ လုပ်ဆောင်သည်။ ရရှိသော window သည် sampling metadata နှင့် untrusted description prefix တွင် ပါဝင်ပြီး downstream models များသည် focused excerpt ကို full timeline မှ ခွဲခြားနိုင်စေရန် ဖြစ်သည်။

Semantic caption focus သည် အထူးသီးသန့် သတ်မှတ်ချက်တစ်ခုဖြစ်သည်။ Default `full` analysis mode သည် ရှိပြီးသား frame prompt ကို ထိန်းသိမ်းပြီး request text ကို caption model သို့ မပေးပို့ပါ။ `focused` mode တွင် bridge သည် အထက်ပါ Chat သို့မဟုတ် Responses container မှ နောက်ဆုံး non-empty user-authored `text`/`input_text` ကိုသာ ဖတ်ပြီး NFC သို့ normalize လုပ်ပြီး၊ control characters နှင့် whitespace များကို ပျောက်ကွက်စေပြီး၊ 500 Unicode code points အထိ ကန့်သတ်သည်။ အလွတ်ရလဒ်သည် တိကျသော `full` prompt သို့ ပြန်လည်သွားသည်။ အသုံးပြုနိုင်သော hint သည် JSON အဖြစ် dedicated untrusted-user-context block တွင် serialize လုပ်ပြီး observable details များကိုသာ ဦးစားပေးနိုင်သည်။ ၎င်းသည် media တွင် မြင်သာ သို့မဟုတ် အသံထွက် instructions များကို လိုက်နာရန် သီးခြား သတိပေးချက်ကို မဖျက်သိမ်းနိုင်ပါ။ Textual focus သည် `start`/`end` ကို မခန့်မှန်းနိုင်ပါ၊ သို့မဟုတ် temporal sampler ကို မပြောင်းလဲနိုင်ပါ။

#### FU-07 structural segment evidence

`segment_aware` သည် အရင်မှ အတည်ပြုထားသော ဒေသခံ ဗီဒီယိုစီးဆင်းမှုကို အခြေခံ၍ တစ်ခုတည်းသော ကန့်သတ်ထားသော ကြိုတင်စစ်ဆေးမှုကို အသုံးပြုသည်။ အတည်ပြုထားသော ဖျော်ဖြေရန် စက်ရုပ်များသည် အရင်ဆုံး 320 pixels အကျယ်အထိ အရွယ်အစားချိန်ညှိပြီး၊ ရှုခင်းပြောင်းလဲမှုများနှင့် ရပ်တည်မှုအချိန်များကို ရှာဖွေပြီး၊ 1 စက္ကန့်တစ်ခါစီ ဗီဒီယိုဖျော်ဖြေရန်၊ blur၊ average luma နှင့် spatial/temporal အချက်အလက်များကို sample လုပ်သည်။ ကြိုတင်စစ်ဆေးမှုသည် 600 structural samples အထိ ကန့်သတ်ထားပြီး၊ FFmpeg/filter thread တစ်ခု၊ အထူး `file`-သာ protocol နှင့် container allowlists၊ 1 MiB process-output bound နှင့် broker ၏ မျှဝေထားသော abort/deadline အတွင်း 30 စက္ကန့်အထိသာ ရှိသည်။ ၎င်းသည် အမိန့်၊ ဖျော်ဖြေရန်၊ လမ်းကြောင်း သို့မဟုတ် URL များကို တောင်းဆိုမှုမှ လက်ခံခြင်းမရှိပါ။

Structural values များသည် သတ်မှတ်ထားသော sampling အထောက်အထားများဖြစ်ပြီး၊ semantic video နားလည်မှုမဟုတ်ပါ။ ၎င်းတို့သည် အကြောင်းအရာများ၊ လှုပ်ရှားမှုများ၊ caption များ၊ စကားပြောခြင်း သို့မဟုတ် အသုံးပြုသူရဲ့ ရည်ရွယ်ချက်ကို မခန့်မှန်းပါ။ ရှုခင်းနှင့် ရပ်တည်မှုနယ်နိမိတ်များသည် segments များကို ဖွဲ့စည်းသည်။ ရပ်တည်မှု coverage၊ blur၊ exposure၊ spatial detail နှင့် temporal change များသည် ရှိပြီးသား 1–16 frame budget ကို ဘယ်လို ခွဲဝေမလဲဆိုတာကိုသာ သက်ရောက်သည်။ အပြုံးဖြစ်သော segment တစ်ခုသည် frame တစ်ခုအထိသာ ကန့်သတ်ထားပြီး၊ အပြုံးမဖြစ်သော segments များသည် ကျန်ရှိသော budget အတွက် ယှဉ်ပြိုင်သည်။ နယ်နိမိတ်များသည် frames များထက် ပိုများသောအခါ၊ uniform timeline coverage ကို ထိန်းသိမ်းထားပြီး၊ အမြန်စတင်ဖြတ်ခြင်းများသည် ရှည်လျားသော trailing segment ကို ဖုံးကွယ်၍ မရပါ။ 1-စက္ကန့် ကြိုတင်စစ်ဆေးမှု resolution အတွင်း ရပ်တည်မှုနယ်နိမိတ်များသည် ပေါင်းစည်းသည်။

Filters များပျောက်ဆုံးခြင်း၊ malformed/empty evidence များ၊ detector error တစ်ခု သို့မဟုတ် bounded pre-analysis timeout သည် အတိအကျ uniform midpoint policy သို့ ဖွင့်လှစ်သည်။ Caller abort သို့မဟုတ် broker deadline သည် ဖွင့်လှစ်ခြင်းမရှိပါ: ၎င်းသည် in-flight subprocess ကို သတ်မှတ်ပြီး၊ နောက်ပိုင်း frame extraction ကို ကာကွယ်ပြီး၊ private temporary tree ကို `finally` တွင် ဖျက်သိမ်းသည်။

`scripts/perf/video-bridge-fu07-eval.ts` သည် post-dedup caption-call savings, dense-motion budget allocation, blur/exposure/SI-TI evidence, rapid cuts with a long tail, နှင့် gradual-fade false positives များအတွက် သတ်မှတ်ထားသော အမှန် FFmpeg fixtures များကို ဖန်တီးသည်။ ၎င်းသည် ကြိုတင်စစ်ဆေးမှု wall time ကို မှတ်တမ်းတင်ပြီး၊ `/usr/bin/time` ရှိပါက ကလေး CPU နှင့် peak RSS ကို မှတ်တမ်းတင်သည်။ ၎င်း၏ အရည်အသွေးစစ်ဆေးမှုများသည် structural oracles သာဖြစ်သည်။ အမှန် caption-model အရည်အသွေးသည် `HOLD` အနေဖြင့် ရှိနေသည်၊ အကြောင်းမှာ ဤ harness သည် အတည်ပြုထားသော endpoint သို့မဟုတ် frozen judge မရှိပါ။ ငွေကြေးသိမ်းဆည်းမှုများသည် `HOLD` အနေဖြင့် ရှိနေသည်၊ `--caption-cost-per-call-usd` သည် အထူးသတ်မှတ်ထားသော အပေါင်းအဖျော်အတွက် အတိအကျ အပေါင်းအဖျော် အခွင့်အလမ်းကို ပေးပါကသာ ဖြစ်သည်။ script သည် အဆိုပါရလဒ်ကို မဖန်တီးပါ။

Frame တစ်ခုသည် 4 MiB အထိသာ ကန့်သတ်ထားပြီး၊ အားလုံးသော raw frames များသည် 23 MiB အထိ၊ serialized broker response သည် 32 MiB အထိသာ ရှိသည်။ private temporary directory သည် `finally` တွင် ဖျက်သိမ်းသည်။ OmniRoute သည် FFmpeg ကို bundle မလုပ်ပါ၊ သို့မဟုတ် အထူး executable path ကို လက်ခံမည်မဟုတ်ပါ။ Captioning မပြုမီ၊ bridge သည် သေချာသော visual deduplication pass ကို လုပ်ဆောင်သည်: JPEG တစ်ခုစီကို 16×16 grayscale buffer သို့ လျှော့ချပြီး၊ နောက်ဆုံး frame နှင့်သာ နှိုင်းယှဉ်သည်။ တစ် frame ထက် ပိုမိုသော caption budget တစ်ခုကို တောင်းဆိုပါက၊ extraction သည် အထက်ပါ budget ၏ နှစ်ဆအထိ bounded candidate pool ကို ပေးသည်၊ 16 frames ထက် မပိုပါ။ တောင်းဆိုထားသော cap သည် deduplication ပြုလုပ်ပြီးနောက်သာ လျှောက်ထားပြီး၊ ပထမနှင့် နောက်ဆုံး ရွေးချယ်ထားသော candidates များသည် budget သည် နှစ်ခုအထက်ရှိသောအခါ နောက်ဆုံး thinning အတွင်း ထိန်းသိမ်းထားသည်။ versioned `grayscale-16x16-mean-cells-v2` policy သည် mean luma delta ၏ အကြီးဆုံးနှင့် normalized delta သည် 0.05 အထက်ရှိသော thumbnail cells ၏ အချိုးကို အသုံးပြုသည်။ duplicate threshold သည် predictability အတွက် ရွေးချယ်ထားသော 0.04 ဖြစ်သည်၊ runtime setting အဖြစ် ဖျော်ဖြေရန် မဖော်ပြပါ။ ဤ ဒုတိယ high-contrast signal သည် mean-only နှိုင်းယှဉ်မှုမှ ဖုံးကွယ်နိုင်သော သေးငယ်သော လှုပ်ရှားမှုနှင့် မြင်သာသောစာသားပြောင်းလဲမှုများကို ထိန်းသိမ်းသည်။ Comparator သို့မဟုတ် decoder errors များသည် ဖွင့်လှစ်ပြီး coverage ကို ထိန်းသိမ်းသည်။ Output metadata သည် extracted candidates များ၊ အောင်မြင်စွာ အသုံးပြုထားသော frames များနှင့် visual duplicates များကို ခွဲခြားသည်။

ထုတ်လုပ်ထားသော ဗီဒီယိုအပိုင်းတစ်ခုသည် timestamped contact sheet တစ်ခုကို တောင်းဆိုနိုင်သည်။ bridge သည် အများဆုံး 4-column, 16-frame JPEG grid တစ်ခုကို တည်ဆောက်သည်။ 512-pixel cell တစ်ခုစီသည် ၎င်း၏ အရင်းအမြစ် timestamp ကို အမြင့်-ကွန်ထရိုက် အောက်ပိုင်း band တွင် ထိုးထွင်းပြီး၊ အတူတူ timestamp များသည် အောက်ပိုင်း metadata တွင် ရှိနေသည်။ JPEG အပြည့်အစုံသည် 32 MiB အထိသာ ကန့်သတ်ထားသည်။ `sharp` သည် grid ကို decode သို့မဟုတ် compose မရနိုင်ပါက bridge သည် တစ်ခုချင်း JPEG frames သို့ ပြန်လည်သွားသည်။ client abort သည် sheet operation မှတစ်ဆင့် ဆက်လက်ဖြစ်ပေါ်သည်။

Promotion evidence သည် synthetic composition microbenchmark မှ သေချာစွာ ခွဲခြားထားသည်။ `scripts/perf/video-bridge-contact-sheet-eval.ts` သည် အမှန် OpenAI-compatible vision models များအတွက် schema-versioned A/B harness တစ်ခုကို သတ်မှတ်သည်။ ၎င်းသည် provider-reported tokens, end-to-end wall latency (sheet composition ကို အပါအဝင်), model-call count, နှင့် manifest-defined fact retention ကို တိုင်းတာသည်။ Raw model responses များကို report သို့ ရေးသားမထားပါ; SHA-256 digests နှင့် matched fact IDs များသာ ထိန်းသိမ်းသည်။ ၎င်း၏ harness သည် network သို့မဟုတ် paid model call မလုပ်ပါ၊ `--execute-real` ကို ဖြည့်စွက်ပြီး `--model`, `OMNIROUTE_BASE_URL`, နှင့် `OMNIROUTE_API_KEY` များကို ကွန်ဖစ်လုပ်ထားပါကသာ ဖြစ်သည်။ အဆိုပါ အထူးသတ်မှတ်ထားသော အမှန် run မရှိပါက ၎င်း၏ machine-readable verdict သည် `HOLD` အနေဖြင့် ရှိနေသည်; synthetic payload/call-count measurements များသာ promotion evidence မဟုတ်ပါ။

ခွဲခြားထားသော `scripts/perf/video-bridge-promotion-eval.ts` သည် FU-07 သို့မဟုတ် FU-09 observations များကို သုံးစွဲသည်။ Promotion admission သည် အစဉ်အလာ ၈ ခုသော synthetic scenario အမျိုးအစားများနှင့် sanitized real clip တစ်ခု၊ အခန်းနှင့် အမှုအတွက် တစ်ခုချင်းစီ အနည်းဆုံး သုံးခုတိုင်းတာမှုများ၊ အထက်ပါ ၁၀ ခုသော metrics များ၊ frozen media/prompt/expected-fact/settings digests များ၊ unique observation IDs နှင့် အတည်ပြုထားသော seeded A/B အစဉ်ကို လိုအပ်သည်။ Execution receipt သည် corpus digest, exact candidate SHA နှင့် model revision ကို ချိတ်ဆက်သည်။ ပျောက်ဆုံးသော သို့မဟုတ် မမှန်ကန်သောတိုင်းတာမှုများသည် `HOLD` အနေဖြင့် ရှိနေသည်၊ CPU 30 s အထက်၊ peak RSS 512 MiB အထက် သို့မဟုတ် pre-analysis 30 s အထက်ပါ။ ၎င်းတို့သည် evidence-admission caps ဖြစ်ပြီး၊ runtime RSS enforcement guarantee အသစ်မဟုတ်ပါ။

FU-07 သည် အနည်းဆုံး 98% အရည်အသွေး ထိန်းသိမ်းမှုနှင့် p95 လက်ရှိအချိန်သည် အခြေခံအချိန်ထက် 1.2x မကျော်ရပါ။ ထို့အပြင် အလားအလာရှိသော အလျင်အမြန်ခေါ်ဆိုမှုများတွင် 0.05 အပြုံးအလျင်အမြန် အလျင်အမြန် တိုးတက်မှု သို့မဟုတ် အနည်းဆုံး 10% နည်းပါးသော အလျင်အမြန် အကြောင်းအရာများကို လိုအပ်သည်။ FU-09 သည် အနည်းဆုံး 0.85 အရည်အသွေး၊ 95% ထိန်းသိမ်းမှု၊ 20% p95 လက်ရှိအချိန် လျှော့ချမှုနှင့် 10% token လျှော့ချမှုကို လိုအပ်သည်။ အရေးကြီးအချက်များ ပျောက်ဆုံးခြင်း၊ ထည့်သွင်းမှုလိုက်နာမှု သို့မဟုတ် အသုံးပြုမှုပျောက်ဆုံးခြင်းသည် မြှင့်တင်မှုကို ကန့်သတ်သည်။ တစ်ခုတည်းသော အကောင်အထည်ဖော်မှုသည် အရာဝတ္ထုတစ်ခုကို မြှင့်တင်နိုင်ခြင်းမရှိပါ: `--previous-report` သည် အထူးသဖြင့် အထူးသဖြင့် မထပ်ဆင့်၊ မထပ်ဆင့်၊ အဆက်မပြတ် အရည်အချင်းရှိ အကောင်အထည်ဖော်မှုနှစ်ခုကို အတည်ပြုသည်။ နမူနာစမ်းသပ်မှုသည် ဆက်သွယ်မှုစာရွက်စမ်းသပ်မှုကို အတည်ပြုမထားပါ။

စုဆောင်းသူများသည် အဖြေများကို အမှတ်ပေးပြီး `responseDigest` နှင့် အချက်အလက်များနှင့် ကြည့်ရှုမှုချိတ်ဆက်မှုများကို သိမ်းဆည်းရမည်၊ အဖြေစာသားကို မသိမ်းဆည်းပါ။ အသုံးပြုသူသည် အဟောင်းအချက်အလက်များကို ဖတ်ရမည်၊ သို့သော် အဆိုပါစာသားကို ၎င်း၏ အစီရင်ခံစာများထဲသို့ မကူးယူပါ။ `responseDigest` သို့မဟုတ် `rawResponseText` တစ်ခုတည်းကို အစီရင်ခံစာတစ်ခုစီအတွက် လက်ခံသည်။ ဗားရှင်းထားသော ခွင့်ပြုစာရင်းသည် အလွတ်ရှိပြီး `hold` အခြေခံဖြစ်သည်။ အရည်အချင်းရှိ အချက်အလက်တစ်ခုသည် ၎င်း၏ အထောက်အထားကို လိုအပ်ပြီး၊ မူဝါဒ၊ မော်ဒယ် ပြင်ဆင်မှု၊ တိကျသော အမည် SHA၊ မန်နီဖက်စ်ဒိုက်ဂျက်နှင့် အထူးသဖြင့် အရည်အချင်းရှိ အရည်အချင်းနှစ်ခုကို လိုအပ်သည်။ ဆန့်ကျင်သော အကြောင်းအရာများကို ပယ်ဖျက်သည်။ ဤမီတာဒေတာများသည် စစ်ဆေးမှုစာချုပ်ဖြစ်ပြီး၊ အထောက်အထားထားသော ဖိုင်သည် အမှန်တကယ်တိုင်းတာမှုများပါရှိသည်ဟု အထောက်အထားမဟုတ်ပါ။ အချက်အလက်များထဲသို့ အချက်အလက်များထည့်မည်မဟုတ်ပါ။ စီမံခန့်ခွဲမှု စာရင်းအင်းအချက်အလက်များနှင့် ဗီဒီယို ဒashboard သည် သေချာသော ပြင်ဆင်မှုကို ဖျော်ဖြေရန် ဖွင့်လှစ်သည်။ ပြင်ဆင်ထားသော မော်ဒယ် အမည်တစ်ခုသာ ၎င်း၏ ပြင်ဆင်မှု သို့မဟုတ် လည်ပတ်နေသော အမည် SHA ကို သတ်မှတ်မထားပါ၊ ထို့ကြောင့် လက်ရှိ ဒashboard သည် အခြားအကောင်အထည်ဖော်မှုအခြေအနေမှ အရည်အချင်းကို ပြန်လည်အသုံးပြုရန် `HOLD` ကို အစီရင်ခံသည်။ ရှင်းလင်းသော စမ်းသပ်မှုရွေးချယ်မှုသည် မြှင့်တင်မှုမှ သီးခြားရှိသည်။ အလိုအလျောက် ပြင်ဆင်မှုမပြောင်းလဲပါ။

ခေါ်ဆိုသူများသည် အဆင့်မြင့်သော `transcript.cues` အစိတ်အပိုင်းကို အထောက်အထားထားသော ဗီဒီယို အစိတ်အပိုင်းတွင် ထည့်သွင်းနိုင်သည်၊ ၎င်းတို့သည် အဆင့်မြင့်သော စာသားကို ရှိသည်။ အစိတ်အပိုင်းတိုင်းသည် `text` ကို သယ်ဆောင်ရမည်၊ စမ်းသပ်ထားသော အချိန်အတွင်းတွင် အကန့်အသတ် `start`/`end` ကို သယ်ဆောင်ရမည်၊ နှင့် ခွင့်ပြုထားသော `source` (`client`, `embedded`, သို့မဟုတ် `audio-bridge`); `confidence` သည် `1` သို့မဟုတ် `0` နှင့် `1` အကြားရှိရမည်။ တိကျသော အထပ်ထပ်သော အစိတ်အပိုင်းများကို ပျောက်ကွယ်သည်။ OmniRoute သည် ဤမီတာဒေတာမှ စာသားရေးခြင်းကို မစတင်ပါ: အတည်ပြုထားသော အစိတ်အပိုင်းများကို အဆိုပါ ရလဒ်ထဲသို့ ကူးယူပြီး အရင်းအမြစ်၊ ယုံကြည်မှုနှင့် အကန့်အသတ်အဖြစ် ဖျော်ဖြေရန် ရှိသည်။ မမှန်ကန်သော၊ အကန့်အသတ်မရှိသော သို့မဟုတ် အရင်းအမြစ်မရှိသော စာသားများကို ပယ်ဖျက်သည်၊ အကြောင်းအရာများထဲသို့ မထည့်ပါ။ တစ်ခုချင်းစီသော တောင်းဆိုမှု-ခေါင်းစဉ် စာသားချန်နယ်များသည် ပေးအပ်ထားသော အရင်းအမြစ်ကို `client` သို့ ပြောင်းလဲသည်၊ ၎င်းတွင် ကိုယ်တိုင် အတည်ပြုထားသော `embedded` သို့မဟုတ် `audio-bridge` အမှတ်အသားများပါဝင်သည်။ ယုံကြည်ရသော အမှတ်အသားများကို ကုဒ်-သာ `trustedSource` အဆိုပါ အချက်အလက်ဖြင့် သတ်မှတ်နိုင်သည်; တောင်းဆိုမှု JSON အကွက်သည် အဆိုပါ အချက်အလက်ကို မရောက်ရှိနိုင်ပါ။ စာသားသည် ယုံကြည်မှုမရှိသော မီဒီယာ-ရရှိသော အကြောင်းအရာဖြစ်ပြီး၊ ၎င်း၏ အရင်းအမြစ်မူလတည်နေရာကို မသိမ်းဆည်းရပါ။

အဆင့်မြင့်သော ခေါ်ဆိုသူသည် အတူတူ ဗီဒီယိုအတွက် `audioTranscript` အထူးသဖြင့် ပေးနိုင်သည်; ၎င်းသည် client-ပေးအပ်ထားသော စာသားအဖြစ် သတ်မှတ်သည်၊ server စာသားရေးခြင်း၏ အထောက်အထားမဟုတ်ပါ။ ဖျူးရှင်း seam သည် ဗီဒီယိုနှင့် အသံအကြောင်းအရာများကို တစ်ခုတည်းသော အချိန်ကန့်သတ်နှင့် အပျက်အခွင့်အလမ်းအောက်တွင် လည်ပတ်ပြီး၊ ၎င်းတို့ကို ပုံမှန် အချိန်ဇယားပေါ်တွင် အစီအစဉ်တကျ စီစဉ်ပြီး၊ တိကျသော အထပ်ထပ်များကို ပျောက်ကွယ်စေပြီး၊ တစ်ဖက်တစ်လမ်းသာ အောင်မြင်သောအခါ အပိုင်းဆိုင်ရာရလဒ်ကို အစီရင်ခံသည်။ မမှန်ကန်သော `audioTranscript` သည် အပိုင်းဆိုင်ရာရလဒ်သို့ လျော့နည်းသည် - ဗီဒီယို ဖော်ပြချက်ကို ထိန်းသိမ်းထားပြီး အသံအပိုင်းသည် သန့်ရှင်းသော အောင်မြင်မှုကုဒ်ကို မှတ်တမ်းတင်သည် - ဗီဒီယိုအားလုံးကို မပျက်ကွက်ပါ။ အပိုင်းစီစဉ်မှု၊ အပိုင်းဆိုင်ရာ အလံနှင့် သန့်ရှင်းသော အောင်မြင်မှုကုဒ်များသည် ဖျော်ဖြေရန် ရလဒ်ထဲတွင် ထိန်းသိမ်းထားပြီး၊ guardrail metadata (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), ရလဒ်- cache metadata နှင့် bridge fusion counters တွင် ထိန်းသိမ်းထားသည်။ အခြေခံ ဗီဒီယို Bridge လမ်းကြောင်းသည် စကားပြောမှ စာသားရေးခြင်းကို မစတင်ပါ သို့မဟုတ် ဒုတိယ မီဒီယာကူးယူမှုကို မဒေါင်းလုပ်လုပ်ပါ; ထိုအထူးသဖြင့် အထောက်အထားမရှိပါက ဗီဒီယို-သာ ဖြစ်နေသည်။

**စာသားထိန်းသိမ်းမှု (#12150 P1).** ဤသည်သည် အလိုအလျောက် အလုပ်လုပ်သည်၊ ဗီဒီယို Bridge (၎င်းကို အလိုအလျောက် ရွေးချယ်ရမည်) သည် စာသားရေးခြင်းအချက်အလက်ကို ဖျော်ဖြေရန် - သီးခြား ထိန်းသိမ်းမှု အလံမရှိပါ။ တောင်းဆိုမှုသည် အကြောင်းအရာရေးခြင်းအချက်အလက် (ခေါ်ဆိုသူက ကြေညာထားသော `transcript` သို့မဟုတ် ဖျူးရှင်းထားသော `audioTranscript`) တစ်ခုခုကို ဖျော်ဖြေရန် guardrail သည် ၎င်းကို `videoBridgeObserved` ဟု သတ်မှတ်ပြီး ဗီဒီယိုဖော်ပြချက်၏ အရောင်ပြောင်းထားသော အရောင်ကို ထုတ်လုပ်သည် - အတူတူသော ဖျော်ဖြေရန် ၎င်း၏ အစိတ်အပိုင်းတိုင်း၏ အခွင့်အရေးစာသားကို `[redacted-video-transcript]` ဖြင့် အစားထိုးထားပြီး၊ အစိတ်အပိုင်းကို စာသားကို စုစည်းမီတာဒေတာကို အစီအစဉ်တကျ ပြုလုပ်သည် (ဖျော်ဖြေရန် စာသားကို ဖျက်သိမ်းခြင်းဖြင့် မပြုလုပ်ပါ၊ ထို့ကြောင့် အစိတ်အပိုင်းအကြောင်းအရာ - ဆန့်ကျင်မှု သို့မဟုတ် ပုံမှန်၊ `]` ပါဝင်သော အစိတ်အပိုင်းများကို အပါအဝင် `[` အကြောင်းအရာများ - မကျန်ရှိနိုင်ပါ)။ ထိန်းသိမ်းထားသော ခေါ်ဆိုမှု-မှတ်တမ်း တောင်းဆိုမှုကို ဗီဒီယို-ရရှိသော စာသားအပိုင်းကို အဆိုပါ ဖျော်ဖြေရန် အရောင်ပြောင်းထားသော အရောင်ဖြင့် အစားထိုးသည်၊ အကြောင်းအရာအညီ; `fullText` အင်္ကျီကို ပြီးဆုံးသော pre-call guardrail payload မှ ပြန်ဖတ်သည်၊ ထို့ကြောင့် အဆက်မပြတ်သော guardrails (PII နှင့် အထောက်အထား maskers၊ ဦးစားပေး 10/95) သည် ဖော်ပြချက်စာသားကို အပြောင်းအလဲပြုလုပ်ပြီး၊ စနစ်-အကြောင်းအရာ/လွှဲပြောင်းမှု/မှတ်ဉာဏ် ထည့်သွင်းမှုသည် စာသားအမျိုးအစားကို ပြောင်းလဲသည်။ မော်ဒယ်သို့ အထက်သို့ ပို့သော အကြောင်းအရာ မပြောင်းလဲပါ။ အစီရင်ခံထားသော တောင်းဆိုမှုသည် တည်ငြိမ်သော အမှတ်တမ်းကို မဖြစ်စေပါ (တောင်းဆိုမှုနှင့် အဖြေမှ ထုတ်ယူမှုကို ကျော်ဖြတ်သည်)၊ ထို့ကြောင့် မော်ဒယ်၏ ကိုယ်ပိုင် အဖြေသည် စာသားကို Memory ထဲသို့ မထည့်နိုင်ပါ။

**Raw video fields (#12430).** Bridge သည် ဖွင့်လှစ်ထားသောအခါနှင့် သဘာဝဗီဒီယို ထောက်ပံ့မှုကို မသိရသော်လည်း၊ သတ်မှတ်ထားသော `transcript`/`audioTranscript` အကွက်များသည် `videoBridgeObserved` ကိုလည်း ဖွင့်လှစ်သည်၊ ဖော်ပြချက် မအောင်မြင်သောအခါ သို့မဟုတ် `maxVideos` ကန့်သတ်ချက်ရှိသောအခါတွင်ပါ။ `null` နှင့် အလွတ်စာသားများကို အရေအတွက်ထည့်ပါ; မရှိသော အကွက်များနှင့် မဗီဒီယို metadata မပါဝင်ပါ။ ထိန်းသိမ်းထားသော ကူးယူမှုများသည် ဤအကွက်များကို ဖျက်သိမ်း သို့မဟုတ် တောင်းဆိုမှုကို မထည့်ပါ၊ caches/Memory များကို ကျော်ဖြတ်သည်။

ဒီ fallback လမ်းကြောင်းများတွင်၊ သက်ဆိုင်သော caller cues များသည် nonstandard provider fields မဟုတ်ပဲ supported `text`/`input_text` အစိတ်အပိုင်းများဖြစ်လာသည်။ request-supplied tracks နှစ်ခုလုံးသည် untrusted `client` အကြောင်းအရာများဖြစ်ပြီး၊ ဗီဒီယိုကို ဖျော်ဖြေရန် မဖော်ပြထားခြင်းနှင့် timestamps များကို မီဒီယာနှင့် တိုက်ဆိုင်စစ်ဆေးခြင်းမရှိကြောင်း အထောက်အထားပြုသော သတိပေးချက်တစ်ခုပါရှိသည်။ ရှိပြီးသား 256-cue/64-KiB စုစုပေါင်းနှင့် per-cue ဘတ်ဂျက်များသည် နှစ်ခုလုံးတွင် အတူတကွ သက်ဆိုင်သည်။ timestamps များသည် broker ၏ 600-စက္ကန့် အထိအမြင့်နှင့် ပေးအပ်ထားသော focus window ကို သင့်လျော်စွာ ထည့်သွင်းရမည်။ မသက်ဆိုင်သော tracks များကို ဖျက်ပစ်ပြီး၊ အလွတ်အစား text အဖြစ် မပေးပို့ပါ။ သက်ဆိုင်သော အစ်ကိုတစ်ဦးကို သုံးနိုင်သော်လည်း၊ သူတို့၏ ပေါင်းစပ် ဘတ်ဂျက်ကို ကျော်လွန်မည်မဟုတ်ပါ။ Null/empty fields များသည် text မထည့်သွင်းပါ။ ဒီ fallback မှာ မီဒီယာ ရယူခြင်း သို့မဟုတ် transcription မထည့်သွင်းပါ။ Transcript extension fields များကို fallback video carrier နှင့် ၎င်း၏ `video_url`/`source` objects များမှ ဖယ်ရှားသည်။ OpenAI wire allowlist သည် တင်းကြပ်နေသည်။ မသိသော native video carriers များသည် ရရှိနိုင်ပြီး၊ သိရှိထားသော text-only targets များသည် လုံခြုံသော အမှတ်များကို ထိန်းသိမ်းထားသည်။ Structured redaction shadows များသည် ထပ်ထည့်ထားသော transcript text ကို ကာကွယ်သည်၊ အစစ် caller-owned request သည် မပြောင်းလဲပါ။ Native-supported targets နှင့် disabled bridges များသည် ၎င်းတို့၏ ရှိပြီးသား bypass အပြုအမူကို ထိန်းသိမ်းထားသည်။

ထပ်မံထားရှိသော ကူးပြောင်းများသည် အတူတူသော observed-request signal ကို အသုံးပြုသည်။ raw pre-guardrail client-request snapshot, in-memory pending request, နှင့် early rejected-request log များသည် video parts တွင် transcript fields များကို ဖယ်ရှားစေသည်။ pipeline stages နှင့် context handoff မှ ဖန်တီးထားသော string prompts များကို persisted-request-body sink တွင် ဖယ်ရှားသည်။ persisted `video_content_removed` marker သည် `previous_response_id` ဆက်လက်မှုကို ပိတ်ပင်ပြီး၊ အထူးသဖြင့် ဖယ်ရှားထားသော text ကို ပြန်လည်ဖန်တီးခြင်းမရှိပါ။ အကယ်၍ observed request သည် logging မပြုမီ per-part redaction shadow ကို ဆုံးရှုံးပါက၊ သို့မဟုတ် အချို့သော video shadows များသည် နောက်ပိုင်း request mutations များအပြီးတွင် မကိုက်ညီပါက၊ retained request body ကို အပြုံးအပြုံး ဖယ်ရှားသည်။

observed request အတွက် model response သည် transcript ၏ မည်သည့်အပိုင်းကိုမဆို structured cue boundary မရှိဘဲ ကိုးကားနိုင်သည်။ ၎င်း၏ persisted call-log `responseBody` သည် ထို့ကြောင့် ဖယ်ရှားမှု marker ဖြင့် အစားထိုးသည်။ အသေးစိတ် pipeline artifact (upstream/client bodies နှင့် stream chunks များကို ပါဝင်နိုင်သည်) ကို မထိန်းသိမ်းပါ။ Semantic, idempotency, နှင့် reasoning-replay caches များသည် အဆိုပါ request အတွက် ဖတ်ခြင်းနှင့် ရေးခြင်းကို bypass လုပ်သည်။ provider request နှင့် client-visible response များသည် မပြောင်းလဲပါ။ အသေးစိတ် artifact ကို ဖယ်ရှားသောအခါ early keepalive bytes များကို အချိန်ပိုင်း buffer မှ ဖယ်ရှားသည်။ Kiro ၏ malformed EventStream သတိပေးချက်သည် payload byte count ကိုသာ အစီရင်ခံပြီး၊ ၎င်း၏ အကြောင်းအရာ သို့မဟုတ် JSON parser ၏ raw error ကို မဖော်ပြပါ။
ဒါသည် မည်သည့်ဆက်စပ်မဟုတ်သော provider/plugin diagnostic များကို စစ်ဆေးခဲ့သည်ဟု မဆိုလိုပါ။ ပိုမိုကျယ်ပြန့်သော retained-sink sweep ကို #11658 တွင် စောင့်ကြည့်ထားသည်။

အတွင်းပိုင်း `/api/modality-bridge/video/drilldown` lifecycle သည် အထူး၊ loopback/token-authenticated cache substrate ဖြစ်သည်။ လုပ်ဆောင်ချက်တိုင်းသည် canonical opaque principal ID ကို လိုအပ်သည်။ ထုတ်လုပ်မှု caller ကို ဖွင့်ရန်မပြုမီ၊ ၎င်းသည် authenticated tenant မှ ID ကို ထုတ်ယူရမည်နှင့် client-selected value ကို မပေးပို့ရပါ။ Cache keys များသည် ၎င်း principal ကို canonical session နှင့် video-reference IDs များနှင့် ချိတ်ဆက်ပြီး၊ ၎င်းတို့၏ SHA-256-derived keys များကိုသာ သိမ်းဆည်းပြီး၊ ဖတ်ခြင်းနှင့် ဖျက်ခြင်းကို အတူတကွ principal တစ်ခုအတွက်သာ သတ်မှတ်သည်။ Cache သည် entry တစ်ခုချင်းစီတွင် JPEG frames 16 ခုအထိ သိမ်းဆည်းပြီး၊ ၁၀ မိနစ်အတွင်း သက်တမ်းကုန်သည်၊ bounded `start`/`end` ဖတ်ခြင်း သို့မဟုတ် အထူး session ဖျက်ခြင်းကို ထောက်ပံ့သည်။

တိုင်း principal သည် 16 entries နှင့် 64 MiB ၏ canonical JPEG data အထိ ကန့်သတ်ထားသည်။ ၎င်းတို့၏ ကန့်သတ်ချက်များသည် ကမ္ဘာလုံးဆိုင်ရာ 64-entry/256 MiB အထိအမြင့်မှ လွတ်လပ်သည်။ principal quota pressure သည် global LRU eviction ကို စဉ်းစားမီ ၎င်း principal ၏ အနည်းဆုံး အသုံးပြုခဲ့သော entries များကို ဖျက်ပစ်သည်။ သက်တမ်းကုန်သော entries များကို cache activity တွင် principal နှင့် global accounting နှစ်ခုလုံးမှ ဖယ်ရှားသည်၊ cancellation နှင့် validation failure များသည် အပိုင်းအစ ပြောင်းလဲမှုကို မကျင့်သုံးပါ။

cache သည် non-canonical Base64, excess padding, non-JPEG media, malformed သို့မဟုတ် truncated JPEGs, နှင့် bounded full-image `sharp` decode အတွင်း သတိပေးချက်ကို ထုတ်လုပ်သော JPEGs များကို ပယ်ဖျက်သည်။ ၎င်းသည် လက်ခံထားသော image တစ်ခုချင်းစီကို canonical JPEG အဖြစ် ပြန်လည်ကုန်ကျစေပြီး၊ caller fields များကို ယုံကြည်မထားဘဲ decoded bytes များမှ အကျယ်နှင့် အမြင့်ကို ထုတ်ယူပြီး၊ trailing polyglot bytes များကို ထိန်းသိမ်းမထားဘဲ ဖယ်ရှားသည်။ bounded canonical compressed buffer သာ နှစ်ခုလုံး၏ quota များကို ချိုးဆွဲသည်။ JSON wire limit သည် 32 MiB decoded-input ceiling အတွက် Base64 overhead ကို ပါဝင်သည်။ သိမ်းဆည်းထားသော derivation တစ်ခုချင်းစီသည် ၎င်း၏ validated JPEG format/resolution, sampling policy, derivation version, creation time, server-computed content hash, နှင့် hashed parent reference အပြင် trusted caller ၏ parent-content hash ကို မှတ်တမ်းတင်သည်။ Cancellation သည် asynchronous decode/hash အဆင့်များအကြား စစ်ဆေးသည်၊ atomic cache commit မပြုမီ။

ထုတ်လုပ်မှု producer သည် visual analysis အောင်မြင်ပြီးနောက်သာ ရှိပြီးသား broker frames များကို အသုံးပြုသည်၊ ဒါမှမဟုတ် ဒုတိယဗီဒီယိုကို download/extraction မပြုပါ။ ၎င်းသည် operator `modalityBridgeVideoDrilldownEnabled=true`, strict per-part `drilldown: true`, နှင့် authenticated API-key record ID ကို လိုအပ်သည်။ Client-declared principal/session values များသည် ownership ကို ဖွဲ့စည်းခြင်းမရှိပါ။ သုံးခုလုံးသော အခြေအနေများမရှိပါက ၎င်းသည် hash, resize သို့မဟုတ် ထပ်မံ frames များကို ထိန်းသိမ်းမည်မဟုတ်ပါ။ Retention failure သည် အသုံးပြုနိုင်သော visual response ကို ထိန်းသိမ်းသည်။ Consent လုပ်ထားသော requests များသည် whole-video result cache ကို bypass လုပ်ပြီး၊ cached results များသည် handles မပြန်လည်ဖျော်ဖြေရန် မရှိပါ။

JSON နှင့် SSE တုံ့ပြန်မှုများသည် `x-omniroute-video-drilldown` ခေါင်းစဉ်တွင် အနည်းဆုံး လေးခုသော opaque handles များကို ဖျော်ဖြေရန် အောင်မြင်သည်။ အာဏာပိုင် browser origins များသည် CORS origin policy ကို ကျယ်ပြန့်စွာ တိုးချဲ့မထားဘဲ ထိုခေါင်းစဉ်ကို ဖတ်နိုင်သည်။ အသစ်သော handles များသည် `v1.<32-byte random base64url token>` ကို အသုံးပြုသည်၊ registry သည် ၎င်းတို့၏ SHA-256 hashes များကိုသာ ထိန်းသိမ်းထားသည်။ reader/header parser သည် legacy 64-hex tokens များကိုလည်း လက်ခံသည်။ အတည်ပြုထားသော ပြည်သူ့ အသုံးပြုသူသည် `GET /api/v1/video-bridge/drilldown?handle=...` ဖြစ်ပြီး `modalityBridgeVideoDrilldownRemoteEnabled=true` ဖြင့် လွတ်လပ်စွာ gate လုပ်ထားသည်။ အထောက်အထားထားသော false သည် legacy `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` env fallback သည် အလုပ်လုပ်နေစဉ်တွင်လည်း ဝင်ရောက်ခွင့်ကို ပယ်ဖျက်သည်။ ထုတ်လုပ်မှု retention သည် အလားတူ legacy `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED` fallback ကို ထိန်းသိမ်းထားသည်။ နှစ်ခုလုံး fallback များသည် အလိုအလျောက် ပိတ်ထားသည်။

အသုံးပြုသူသည် အတည်ပြုထားသော key မှ ပိုင်ဆိုင်မှုကို ထုတ်ယူပြီး key policy ကို လျှောက်ထားသည်၊ မသိ၊ သက်တမ်းကုန်ဆုံးပြီး အခြား key ၏ handles များအတွက် 404 တူညီသော အဖြေကို ပြန်လည်ပေးသည်။ ၎င်းသည် `variant=preview|standard|detail` (JPEG အမြင့်အနက် 320/640/1280, အမြဲမမြှင့်တင်)၊ `limit=1..8` (သို့မဟုတ် legacy `frames` alias, နှစ်ခုလုံးမဟုတ်)၊ zero-based `page` နှင့် optional `start`/`end` focus seconds ကို လက်ခံသည်။ အထပ်ထပ် query keys နှင့် ပြန်လည်အာရုံစိုက်မှု windows များကို ပယ်ဖျက်သည်။ ပြန်လည်ပေးသော variant တစ်ခုစီသည် ၎င်း၏ အမှန်တကယ် အကြောင်းအရာနှင့် အမှန်တကယ် resolution metadata ၏ hash ကို ထိန်းသိမ်းထားပြီး ထိန်းသိမ်းထားသော အရင်းအမြစ်နှင့် ဆက်စပ်သည်။ Variants များသည် ဖတ်ရန်အတွက် ထုတ်ယူပြီး ထိန်းသိမ်းထားသော ကူးပြောင်းမထားသော ကူးပြောင်းများအဖြစ် မသိမ်းဆည်းပါ။ JSON တုံ့ပြန်မှုသည် Base64/envelope အပါအဝင် 32 MiB အထိ ကန့်သတ်ထားသည်; အရွယ်အစားကြီးသော စာမျက်နှာသည် 413 ကို ပြန်လည်ပေးပြီး client သည် frames များကို နည်းနည်းသာ တောင်းဆိုရမည်။ ဖတ်ခြင်းသည် အရွယ်အစားပြောင်းလဲမှုနှင့် ပြန်လည်စစ်ဆေးမှုကို စစ်ဆေးပြီး handle validity ကို ပြန်လည်စစ်ဆေးသည်။ ပိုင်ရှင်မှ `DELETE` သည် idempotent ဖြစ်သည်; ဖျက်ခြင်း သို့မဟုတ် TTL ကုန်ဆုံးခြင်းသည် ထိန်းသိမ်းထားသော အရင်းအမြစ်နှင့် အသုံးပြုမှု အကောင့်ကို လွှတ်ပေးသည်။

မျှဝေထားသော စတိုးသည် process-local ဖြစ်သည်: handles များသည် ပြန်လည်စတင်သောအခါ သက်တမ်းကုန်ဆုံးပြီး လွတ်လပ်သော OmniRoute processes များအကြား လွှဲပြောင်းမရ။ စီမံခန့်ခွဲမှု စာရင်းများသည် ထိရောက်သော retention/remote policy နှင့် စုစုပေါင်း ထိန်းသိမ်းထားသော အချက်အလက်/bytes များကိုသာ ဖျော်ဖြေရန် ဖျော်ဖြေရန် မဟုတ်ပါ၊ မီဒီယာ၊ ကိုးကားချက်များ၊ အဓိပ္ပါယ် ID များ သို့မဟုတ် handles များကို မဖျော်ဖြေရန်။ Video settings panel သည် ထိုတန်ဖိုးများကို ပြသပြီး consent switches နှစ်ခုလုံးကို ထိန်းသိမ်းနိုင်သည်။ ဤအကောင့်ရေးသားမှုစာရွက်စာတမ်းသည် တိုက်ရိုက် အသုံးပြုမှု သို့မဟုတ် ကြော်ငြာ အထောက်အထား မဟုတ်ပါ; အမှန်တကယ် မော်ဒယ် လက်ခံမှုကို သီးခြားစီမံထားသည်။

Frames များကို စီစဉ်ထားသော Video မော်ဒယ်နှင့် အတူ အကြောင်းအရာများကို အစဉ်လိုက် အကြောင်းပြုသည်။ အလွတ် Video override သည် Vision setting ကို ဆက်ခံသည်; နှစ်ခုလုံး အလွတ်ဖြစ်ပါက Vision auto-router သည် ထိရောက်သော vision-capable model ကို ရွေးချယ်သည်။ အောင်မြင်သော အကြောင်းအရာများသည် အစောပိုင်း အပိုင်းကို တည်ငြိမ်သော `[Video description:` prefix ဖြင့် အစားထိုးပြီး အဆိုပါ စာသားကို မယုံကြည်ရသော မီဒီယာမှ ရရှိသော အကြောင်းအရာအဖြစ် သတ်မှတ်သည်။ Frame-caption cache keys များတွင် JPEG bytes, prompt, timestamp, နှင့် ထိရောက်သော model ပါဝင်သည်; အောင်မြင်သော အကြောင်းအရာများသာ cache လုပ်သည်။ Cache entries များသည် အမှန်တကယ် အောင်မြင်သော producer model ကို ထိန်းသိမ်းထားပြီး fallback model ကိုလည်း ထိန်းသိမ်းထားသည်; bridge သည် အမျိုးမျိုးသော frames များကို အမျိုးမျိုးသော models မှ ထုတ်လုပ်ခဲ့သောအခါ `mixed` ကို အစီရင်ခံသည်။ Cache hit သည် ထို producer identity ကို အသုံးပြု၍ မဟုတ်ဘဲ တောင်းဆိုထားသော routing plan အဖြစ် ပြန်လည်အမှတ်ပေးသည်။ အပြုံး-ဗီဒီယို ရလဒ် cache သည် output ကို ပြောင်းလဲသော အချက်အလက်တိုင်းအပေါ် အခြေခံထားသည် — prompt, ထိရောက်သော model, sampling policy, frame count, semantic analysis mode, normalized focus hint ၏ SHA-256 fingerprint, focus window, `transcript`, `audioTranscript`, နှင့် contact-sheet flag — ထို့ကြောင့် ထိုအတိုင်းအတာများကို ပြောင်းလဲခြင်းသည် cache miss ဖြစ်ပြီး အမြဲမဟုတ်သော အသုံးပြုမှုဖြစ်သည်။ Visual dedup policy version, threshold, နှင့် bounded candidate-frame count များသည် ရလဒ်-cache key နှင့် metadata တွင်လည်း ထင်ရှားသည်; policy ပြောင်းလဲမှုသည် သို့မဟုတ် အဟောင်း whole-video ဖော်ပြချက်ကို ပြန်လည်အသုံးပြု၍ မရပါ။ Result-cache v4 metadata သည် mode နှင့် fingerprint ကို ထိန်းသိမ်းထားပြီး raw user task ကို မထိန်းသိမ်းပါ။ Guardrail metadata သည် တောင်းဆိုထားသော နှင့် ထိရောက်သော analysis modes နှစ်ခုလုံးကို အစီရင်ခံသည်; အသုံးပြုသူစာသားကို အသုံးပြု၍ မရသော တောင်းဆိုထားသော `focused` mode သည် ထိရောက်သော `full` အဖြစ် အစီရင်ခံသည်။

Guardrail သည် ထောက်ပံ့ထားသော ဗီဒီယို အပိုင်းများကို အားလုံးထုတ်ယူသော်လည်း `modalityBridgeVideoMaxVideos` ထက် မပို၍ ဖော်ပြသည်။ `supportsVideo === false` ဖြစ်သည့် ရည်မှန်းချက်အတွက် မအောင်မြင်သော နှင့် အကန့်အသတ်ထက် များသော ဗီဒီယိုများသည် အထူးသဖြင့် လုံခြုံသော စာသား အမှတ်အသားများ ဖြစ်လာသည်၊ ထို့ကြောင့် မည်သည့် raw video များလည်း မကျန်ရှိပါ။ စွမ်းဆောင်ရည်ကို မသိပါက၊ ထိုအပိုင်းများသည် ၎င်းတို့၏ ဗီဒီယို carrier ကို ထိန်းသိမ်းထားသည်; မည်သည့် fallback transcript သည် အထက်ပါ bounded text conversion ကို 따르သည်။ `supportsVideo === true` ဖြစ်သော ရည်မှန်းချက်များသည် bridge ကို လွှတ်ပေးသည်။ client request abort signal သည် download, broker queue, subprocesses, နှင့် caption calls များအတွင်း ဖြန့်ဖြူးသည်; aborts များသည် ဗီဒီယိုများအကြား ရပ်တန့်ပြီး raw media သို့ မဖျက်သိမ်းပါ။

Runtime settings များသည် DB-backed ဖြစ်ပြီး Zod-validated ဖြစ်သည်:

| Key                                 | Default     | Range / behavior                                                                                                        |
| ----------------------------------- | ----------- | ----------------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | Optional runtime, opt-in                                                                                                |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` သည် generic captions များကို ထိန်းသိမ်းသည်; `focused` သည် bounded, untrusted latest-user context ကို အသုံးပြုသည် |
| `modalityBridgeVideoModel`          | `""`        | Vision Bridge model ကို ဆက်ခံသည်                                                                                        |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                                    |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, သို့မဟုတ် proportional `segment_aware`; detector failure သည် `uniform` သို့ ပြန်လည်သွားသည်    |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                                     |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                                          |

Legacy persisted Video timeout values above 120 seconds are clamped to the
broker deadline; new settings writes above that limit are rejected.
`GET /api/modality-bridge/video/runtime` requires trusted stamped loopback
locality before authentication or runtime probing, then requires management
auth. It returns only `available`, sanitized FFmpeg/ffprobe versions, and a fixed
reason when the runtime is unavailable. The internal extraction endpoint is not
a public upload API: queue saturation returns `503` plus `Retry-After`, a caller
disconnect returns `499`, and the fixed broker deadline returns `504`. Converted responses add
`video->text;model=<visionModel>;parts=<videos>` to the central
`x-omniroute-modality-bridge` header without removing Vision or Audio segments.

### PII Masker (`piiMasker.ts`)

**နှစ်ခုလုံး** အဆင့်တွင် လည်ပတ်သည်။

- **`preCall`** သည် payload ကို ကူးယူပြီး `system`, `messages`, `input`, နှင့်
  `prompt` (plain string items များပါဝင်သည်) ကို လမ်းလျှောက်ပြီး `processPII()` (from
  `@/shared/utils/inputSanitizer`) ကို string `content`/`text` fields တွင် လျှောက်ထားသည်။ `PII_REDACTION_ENABLED=true` ဖြစ်သောအခါ၊ ရှာဖွေတွေ့ရှိထားသော PII များကို outbound
  payload တွင် ဖျက်ပစ်သည်။ ၎င်းသည် `INPUT_SANITIZER_MODE` (prompt-injection policy ကိုသာ ထိန်းချုပ်သည်) နှင့် မဆက်နွယ်ပါ။ ဖျက်ပစ်မှု မရှိသောအခါ၊ call မှတ်တမ်းများသည် အကြောင်းအရာကို ပြန်ရေးမထားဘဲ ရှာဖွေမှု အရေအတွက်များကို မှတ်တမ်းတင်သည်။
- **`postCall`** သည် response ကို နက်ရှိုင်းစွာ ကူးယူပြီး `sanitizePIIResponse()` နှင့်
  Responses-API-shape masker (`maskResponsesOutput` — `output_text` နှင့် `output[].content[].text` ကို ဖုံးလွှမ်းသည်) ကို လည်ပတ်သည်။ ဖျက်ပစ်မှု တစ်ခုခု ဖြစ်ပါက၊ ပြင်ဆင်ထားသော response သည် မူရင်းကို အစားထိုးသည်။

Guardrail သည် ဘာမှ ပိတ်မထားပါ; ၎င်းသည် သာမန်မှတ်ချက်များ (`meta.detections`,
`meta.redacted`) သို့မဟုတ် ပြန်ရေးသည်။

### Prompt Injection (`promptInjection.ts`)

အသုံးပြုသူက ပေးပို့သော အကြောင်းအရာတွင် အန္တရာယ်ရှိသော ဖွဲ့စည်းမှုများကို ရှာဖွေပြီး
သတ်မှတ်ထားသော policy ကို အကောင်အထည်ဖော်သည်။ အပြုအမူသည် ပတ်ဝန်းကျင် အပြောင်းအလဲများနှင့် constructor
ရွေးချယ်မှုများမှ လမ်းညွှန်သည်:

| Setting         | Env var                                                                                               | Default | Effect                                                                                                                                                                                                             |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Enabled         | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | `false` ဖြစ်သောအခါ၊ guardrail သည် အတိုင်းအတာကို လျှော့ချသည်။                                                                                                                                                       |
| Mode            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | Injection policy: `block`, `warn`, သို့မဟုတ် `log`။ (`redact` သည် နောက်ပြန်-သက်ဆိုင်မှုအတွက် လက်ခံရရှိသော်လည်း injection text ကို ဖျက်ပစ်မထားပါ; request PII ပြန်ရေးသည် `PII_REDACTION_ENABLED` မှ ထိန်းချုပ်သည်။) |
| Block threshold | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | ပိတ်ရန် လိုအပ်သော အနည်းဆုံး အဆင့်။ Medium သည် အခြေအနေကိုသာ ကြည့်ရှုသည်။                                                                                                                                            |

**Mode precedence** (`getMode`): caller `options.mode` →
`INJECTION_GUARD_MODE` **DB feature-flag override** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`။ Dashboard override သည် အဆိုပါ env vars များထက် အနိုင်ရသည်၊ ထို့ကြောင့် Feature
Flags UI သည် လည်ပတ်နေသော guard ကို တိုက်ရိုက် ထိန်းချုပ်သည် (ပြန်လည်စတင်ရန် မလိုအပ်ပါ)။ DB ဖတ်ခြင်းသည် အန္တရာယ်ကင်းစေသည်:
၎င်းသည် အမှားဖြစ်ပါက guard သည် env-based behavior သို့ ပြန်လည်သွားပြီး override မရှိပါက အပြုအမူသည် env-only resolution နှင့် တူညီသည်။

Detection sources:

1. `sanitizeRequest()` from `@/shared/utils/inputSanitizer` (pipeline အတွင်း အခြားနေရာများတွင် အသုံးပြုသော မျှဝေသော detector set)။
2. Built-in `DEFAULT_GUARD_PATTERNS` (လက်ရှိ `system_override_inline` နှင့်
   `markdown_system_block`, နှစ်ခုလုံးသည် `high` severity)။
3. Constructor options မှတဆင့် ပေးပို့သော အထူး `customPatterns` (strings, regex,
   သို့မဟုတ် `{ name, pattern, severity }` မှတ်တမ်းများ)။

`mode === "block"` **နှင့်** ရှာဖွေမှု တစ်ခုခုသည် အဆင့် အဆင့်ကို ဖြည့်ဆည်းပါက `preCall` သည် `{ block: true, message: "Request rejected:
suspicious content detected" }` ကို ပြန်လည်ပေးပို့သည်။ `warn`/`log` modes တွင် guardrail သည် မှတ်တမ်းတင်သော်လည်း
call ကို ခွင့်ပြုသည်။ မျှဝေသော helper `evaluatePromptInjection()` သည် registry ကို မသွားဘဲ prompts များကို အကဲဖြတ်ရန် လိုအပ်သော callers များအတွက်လည်း ထုတ်လုပ်ထားသည်။

**Scan bound (v3.8.20):** detector သည် **ပထမ 16 KB** ကိုသာ စစ်ဆေးသည်
joined prompt text — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 bytes) in
`src/shared/utils/inputSanitizer.ts`။ `detectInjection()` နှင့်
`evaluatePromptInjection()` သည် `slice(0, MAX_INJECTION_SCAN_BYTES)` ကို pattern loop ကို လည်ပတ်ရန် မပြုလုပ်မီ။ Injection directives များသည် input ၏ အထက်ပိုင်းတွင် ရှိသည်၊ ထို့ကြောင့် ၎င်းသည် regex CPU/GC ကို multi-hundred-KB payloads တွင် ကန့်သတ်ပြီး detection ကို အားနည်းစေခြင်းမရှိပါ (cf.
#3932, #4041)။

### Credential Masker (`credentialMasker.ts`)

**နှစ်ခုလုံး** အဆင့်တွင် လည်ပတ်သည်၊ အခြေခံ chain တွင် နောက်ဆုံး (priority `95`)။
API-key / secret-token patterns များကို outbound payload (message
content, tool-call arguments, tool results) **နှင့်** provider response မှ ဖျက်ပစ်သည်၊ ထို့ကြောင့် prompt တွင် ကူးယူထားသော credential (သို့မဟုတ် tool result မှ ပြန်လည်ပြသခြင်း) သည် upstream provider သို့မဟုတ် client သို့ ပြန်လည်ထွက်ပေါက်မည်မဟုတ်ပါ။

- **Opt-in သာ**, PII redaction နှင့် အတူတူသော စည်းမျဉ်း (Hard Rule #20-adjacent):
  `settings.credentialRedactionEnabled === true` **သို့မဟုတ်**
  `CREDENTIAL_REDACTION_ENABLED=true` မရှိရင် ပိတ်ထားသည်။ အဲ့ဒါ ပိတ်ထားရင် guardrail က အလုပ်မလုပ်ပါ —
  အဲဒါက ဘာမှ မတားဆီးပါဘူး၊ ပြန်လည်ရေးသားလည်း မလုပ်ပါ။
- `redactCredentials()` က payload/response tree အပြည့်ကို လှမ်းသွားပြီး (`walkValue()`,
  prototype-pollution-safe, cycle-safe via `WeakSet`) နှင့် ကိုက်ညီမှုများကို
  `[REDACTED:<type>]` placeholder ဖြင့် အစားထိုးပြီး၊ အမှန်တကယ် ပြောင်းလဲခဲ့သော
  အရင်းအမြစ်များကိုသာ ကူးယူသည်။
- `CREDENTIAL_PATTERNS` က LLM provider keys (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS tokens (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), payment keys (Stripe, Square), cloud
  keys (AWS access key, Twilio, SendGrid, Mailgun), private keys / JWTs,
  credential-bearing connection strings (`mongodb://user:pass@...`, စသည်) နှင့်
  generic `Authorization`/`x-api-key`/`api-key`/`apikey` header-value
  pattern ကို ဖုံးလွှမ်းထားသည်။ Header-shaped keys (`authorization`, `x-api-key`, `api-key`,
  `apikey`) က structural အရ အစားထိုးသည် (တန်ဖိုးသာ၊ scheme prefix ကဲ့သို့
  `Bearer `/`Basic ` ကို ထိန်းသိမ်းထားသည်) generic text regex ဖြင့် မဟုတ်ပါ။
- Guardrail က ဘာမှ မတားဆီးပါ; ဒါက အပြောင်းအလဲများကိုသာ ပြန်လည်ရေးသားသည် (`modifiedPayload` /
  `modifiedResponse`) နှင့် မှတ်သားသည် (`meta.credentialsRedacted`, `meta.count`)။

Regression guard: `tests/unit/credential-masker-guardrail.test.ts`.

## အခြေခံ Contract (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ဖြစ်ပါက chain ကို ချက်ချင်းရပ်တန့်စေသည်
  message?: string; // ပိတ်ဆို့သည့်အခါ ဖော်ပြသည်
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // request ကို ပြန်လည်ရေးသားရန် preCall မှ ပြန်ပေးသည်
  modifiedResponse?: TValue; // response ကို ပြန်လည်ရေးသားရန် postCall မှ ပြန်ပေးသည်
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Guardrail တစ်ခုသည် `void`၊ `{}` သို့မဟုတ် `{ block: false }` တစ်ခုခုကို
ပြန်ပေးခြင်းဖြင့် "ပြောင်းလဲမှုမရှိ" ကြောင်း အချက်ပြသည်။ `modifiedPayload`/`modifiedResponse`
ကို ပြန်ပေးခြင်းသည် နောက်ဆက်တွဲ guardrail များသို့ chain တစ်လျှောက် စီးဆင်းနေသော
တန်ဖိုးကို အစားထိုးသည်။ `signal?: AbortSignal` သည် ခေါ်ဆိုသူ၏ lifecycle ကို
guardrail များသို့ သယ်ဆောင်ပေးသည်။ Request ကို ရပ်ဆိုင်းခြင်းသည် ရည်ရွယ်ထားသော
fail-open ခြွင်းချက်ဖြစ်သည်—media bridge များသည် အလုပ်လုပ်ခြင်းကို ရပ်တန့်ပြီး cleanup
ပြုလုပ်ကာ raw media ကို ပံ့ပိုးနိုင်ခြင်းမရှိကြောင်း သိထားသော target တစ်ခုသို့
ပြန်လည်မထည့်သွင်းပါ။

## Registry (`registry.ts`)

Singleton `guardrailRegistry` တွင် အောက်ပါတို့ ပါဝင်သည်-

- `register(guardrail)` — guardrail တစ်ခုကို ထည့်သွင်းပြီး (သို့မဟုတ် normalize လုပ်ထားသော
  name အလိုက် အစားထိုးပြီး) `priority` ငယ်ရာမှ ကြီးရာသို့ ပြန်လည်စီသည်။
- `clear()` / `list()` — စီမံခန့်ခွဲရေး အကူ method များ။
- `runPreCallHooks(payload, context)` — အသက်ဝင်နေသော guardrail များကို တစ်ခုပြီးတစ်ခု
  လုပ်ဆောင်ကာ payload ကို `modifiedPayload` မှတစ်ဆင့် လက်ဆင့်ကမ်းပြီး ပထမဆုံး
  `block: true` တွင် ရပ်တန့်သည်။
- `runPostCallHooks(response, context)` — response ဘက်တွင် အလားတူ flow ကို လုပ်ဆောင်သည်။
- `resetGuardrailsForTests({ registerDefaults })` — test တစ်ခုချင်းစီကို သီးခြားသန့်ရှင်းစွာ
  လုပ်ဆောင်နိုင်ရန် state ကို ရှင်းလင်းပြီး ရွေးချယ်မှုအလိုက် မူလ guardrail များကို
  ပြန်လည် register လုပ်သည်။

Runner နှစ်ခုစလုံးသည် `{ blocked, payload|response, results, guardrail?, message? }`
ကို ပြန်ပေးသည်။ ဤနေရာတွင် `results` သည် guardrail တစ်ခုချင်းစီ၏ `blocked`,
`skipped`, `modified`, `error` နှင့် `meta` field များ ပါဝင်သော
`GuardrailExecutionResult` record များ၏ array ဖြစ်ပြီး tracing အတွက် အသုံးဝင်သည်။

### Request တစ်ခုချင်းစီအလိုက် Guardrail များကို ပိတ်ခြင်း

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` သည် လက်ရှိ request အတွက်
ကျော်သွားသင့်သော guardrail name များကို ထပ်နေမှုမရှိအောင် စုစည်းပေးသည်။
ရင်းမြစ်များအားလုံးသည် မဖြစ်မနေ မဟုတ်ဘဲ ပေါင်းစည်းအသုံးပြုသည်-

- `apiKeyInfo.disabledGuardrails`
- Request body ၏ ထိပ်ဆုံးအဆင့်ရှိ `disabledGuardrails`
- Request body ၏ `metadata.disabledGuardrails`
- Header `x-omniroute-disabled-guardrails` (သို့မဟုတ် အဟောင်းဖြစ်သော
  `x-disabled-guardrails`)

တန်ဖိုးများသည် string array များ သို့မဟုတ် ကော်မာဖြင့် ခွဲထားသော string တစ်ခု
ဖြစ်နိုင်သည်။ Name များကို စာလုံးအသေး kebab-case အဖြစ် normalize လုပ်သည်
(`pii_masker` → `pii-masker`)။ ရလဒ်ကို `context.disabledGuardrails` မှတစ်ဆင့်
registry သို့ ပေးပို့ပြီး ၎င်း registry က ကိုက်ညီသော guardrail များကို ကျော်သွားသည်
(`results` ထဲတွင် `skipped: true`)။

## လုပ်ဆောင်မှု အစီအစဉ်

`src/sse/handlers/chat.ts` နှင့်
`open-sse/handlers/chatCore.ts` တို့မှတစ်ဆင့် ဖြတ်သန်းသည့် request တစ်ခုစီအတွက်-

1. `resolveDisabledGuardrails(...)` သည် API key၊ body နှင့် headers တို့မှ skip list ကို တည်ဆောက်သည်။
2. `guardrailRegistry.runPreCallHooks(body, ctx)` သည် guardrails များကို priority ငယ်စဉ်ကြီးလိုက်ဖြင့် လုပ်ဆောင်သည်-

   - Guardrail တစ်ခုစီ၏ `preCall` သည် `modifiedPayload` မှတစ်ဆင့် payload ကို ပြန်လည်ရေးသားနိုင်သည်။
   - ပထမဆုံး `block: true` သည် chain ကို ချက်ချင်းရပ်တန့်စေပြီး handler က guardrail ငြင်းပယ်မှု response ကို ပြန်ပေးသည်။
3. (ပြန်လည်ရေးသားထားနိုင်သည့်) payload သည် combo routing နှင့် upstream dispatch ထဲသို့ စီးဆင်းသွားသည်။
4. Response ကို စုစည်းပြီးနောက် `guardrailRegistry.runPostCallHooks(...)` သည် response ပေါ်တွင် တူညီသော chain ကို လုပ်ဆောင်သည်။ ဤနေရာရှိ `block: true` သည် upstream response ကို စွန့်ပစ်သည်။

Exception ပစ်သော guardrails များကို `error: <message>` ဖြင့် မှတ်တမ်းတင်ပြီး
`logger.warn` မှတစ်ဆင့် log ရေးသော်လည်း chain သည် ဆက်လက်လုပ်ဆောင်သည် — ဒီဇိုင်းအရ fail-open ဖြစ်သည်။

## စိတ်ကြိုက် Guardrail များ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

အဆင့်များ-

1. `BaseGuardrail` ကို တိုးချဲ့ထားသော `src/lib/guardrails/myGuardrail.ts` ကို ဖန်တီးပါ။
2. `preCall` နှင့်/သို့မဟုတ် `postCall` ကို အကောင်အထည်ဖော်ပါ။
3. Import ပြုလုပ်ချိန်တွင် register လုပ်ပါ (`registerDefaultGuardrails` မှ push လုပ်ခြင်း) သို့မဟုတ်
   runtime တွင် `guardrailRegistry.register(...)` ကို ခေါ်ပါ — registry သည် normalized name တူညီသည့်
   ယခင် guardrail တစ်ခုခုကို အစားထိုးပါမည်။
4. `tests/unit/` အောက်တွင် test များ ထည့်ပါ (ရှိပြီးသား နမူနာများ-
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)။

## Injection-guard route လွှမ်းခြုံမှုနှင့် red-team (Phase 8 · Block D)

Injection-guard (`createInjectionGuard` / `withInjectionGuard`) သည် user prompt များကို
လက်ခံသည့် route အားလုံးကို လွှမ်းခြုံသည်။ ၎င်းသည် `INJECTION_GUARD_MODE` ကို လိုက်နာသည် (မူလ `warn` = log သာရေးခြင်း၊
`block` = HTTP 400 `SECURITY_001` ကို ပြန်ပေးခြင်း)။

| အမျိုးအစား        | Route များ                                                                                                                                           | မူလ mode |

| Generative        | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn     |
| Data              | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn     |

စာသားထုတ်ယူမှု (`extractMessageContents`) သည် `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ကို လွှမ်းခြုံသည်။
