> **Ճշմարտության աղբյուր՝** `src/lib/guardrails/`
> **Վերջին թարմացումը՝** 2026-08-29 — v3.8.51 (Video Bridge-ի տրանսկրիպտի ծագումը հայտարարում է կանչողը,
> և այն դեռ չի ստուգվում սերվերի կողմից — հստակեցվել է ըստ #11661-ի)

Պաշտպանիչ սահմանափակումներն ապահովում են անվտանգությունը, քաղաքականությունների կիրառումը և բովանդակության փոխակերպումները
OmniRoute-ի ու վերին մակարդակի մատակարարների միջև ընկած սահմանագծում։ Յուրաքանչյուր պաշտպանիչ սահմանափակում կարող է ստուգել (և
ըստ անհրաժեշտության մերժել, փոխակերպել կամ ծանոթագրել) հարցման օգտակար բեռները (`preCall`) և
վերին մակարդակի պատասխանները (`postCall`)։

Համակարգը գործում է **fail-open** սկզբունքով․ եթե պաշտպանիչ սահմանափակման կատարման ընթացքում բացառություն է առաջանում, ռեեստրը
գրանցում է սխալը և հարցումը ձախողելու փոխարեն շարունակում է հաջորդ պաշտպանիչ սահմանափակմամբ։
Արգելափակումը միշտ բացահայտ որոշում է (`block: true`) և երբեք՝ պատահականություն։

### Vision Bridge (`visionBridge.ts`) — Մոդալիտետային կամուրջ PR-1

Բռնում է պատկերներ պարունակող հարցումները, որոնք ուղղված են **ոչ-տեսողական մոդելներին** և կամ
վերադարձնում է ամբողջ հարցումը տեսողական հնարավորություններով մոդելին կամ փոխում է պատկեր
մասերը տեքստային նկարագրություններով, որոնք ստեղծվում են կարգավորվող տեսողական մոդելի կողմից, մինչև
վերևի զանգը։ Սա թույլ է տալիս միայն տեքստային մատակարարներին թափանցիկ կերպով մշակել
մուլտիմոդալ բեռներ։

Հոսք:

1. Դադարեցնել, եթե նպատակային մոդելը արդեն աջակցում է տեսողությանը (բացառությամբ, եթե այն հայտնվում է
   պարտադիր կամուրջի ցուցակում `isVisionBridgeForcedModel`)։
2. Հանել պատկեր մասերը `extractImageParts(messages)` միջոցով
   (`visionBridgeHelpers.ts`), որը պատվիրում է **միավորված մեդիա
   հայտնաբերիչին** `detectMediaParts()`-ին `open-sse/utils/mediaParts.ts`-ում՝
   ճշգրիտ աղբյուր, որը կիսվում է կոմբինացված համատեղելիության ֆիլտրի հետ։
   Հանումը թույլատրվում է միայն ձևերի վերին մակարդակի մասերի համար, որոնք
   `replaceImageParts`-ը կարող է վերադարձնել (հանել↔փոխարինել պայմանագիր): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, և Responses API `input_image`։ Ներսում գտնվող հարվածները և
   միայն ցուցիչ ձևերը կոմբո-ֆիլտրի նյութ են և երբեք չեն հանվում։
   Դադարեցնել, եթե ոչինչ չի գտնվել։
3. Հարթակային կարգավորումը լուծել `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): նոր `modalityBridge*`
   կարգավորումների բանալիները հաղթում են; հին `visionBridge*` բանալիները մնում են
   **մեկ-ցիկլային վերադառնալու** (հետադարձ պատուհան)։ Դադարեցնել ցանկացած մեդիա անցումից առաջ, երբ
   կամուրջը անջատված է։
4. Մոդի ընտրիչը (`modalityBridgeVisionMode`, տես ստորև նշված աղյուսակը) որոշում է
   վերափոխել կամ նկարագրել։ Վերափոխումը վերադարձնում է `modifiedPayload` միայն `model`
   փոխված, plus meta `{ rerouted, fromModel, toModel, imagesKept }`։
5. Նկարագրելու ճանապարհը. սահմանափակել պատկերները `maxImages`-ով, կազմել խնդրի գիտակից հրահանգ,
   խորհրդակցել նկարագրության cache-ի հետ, զանգահարել տեսողական մոդելը **պարալել**
   (`Promise.allSettled`), և ներարկել `[Image N]: <description>` տեքստային մասերը իրենց տեղում։
   Նկարագրելու ձախողումը վերադարձնում է `null` և սկզբնական պատկեր մասը
   **պահպանվում է** (#4012) — բացառությամբ կոմբո նկարագրության ճանապարհի, երբ յուրաքանչյուր
   նկարագրություն ձախողվել է, որտեղ հաստատված ոչ-տեսողական վերևը ստանում է
   `(unavailable — no vision-capable provider connected)` կաղապար (#8430)։
6. Վերադարձնել `modifiedPayload` + meta (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`)։

#### Մոդի ընտրիչ (`modalityBridgeVisionMode`)

| Մոդ        | Դեֆոլտ | վարքագիծ                                                                                                                                                                                                                                                |
| ---------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔      | Հին հիպոթեզ, անփոփոխ (#6640/#7204): ոչ-կոմբո/`auto/` մոդելները վերափոխվում են լավագույն տեսողական մոդելին, եթե սկզբնական մոդելը արդեն ունի օգտագործելի հավատարմագրեր (այն ժամանակ նկարագրում); կոմբո նպատակները միշտ նկարագրում են։                     |
| `describe` |        | Always describe — the reroute block is skipped entirely; the user's chosen model always answers.                                                                                                                                                        |
| `reroute`  |        | Force reroute: the keep-credentialed-model guard is bypassed. The reroute-**target** credential guard still applies — when no usable vision target exists, the request falls through to describe so raw images never reach a text-only backend (#8430). |

Պարտադիր մոդերը կարճացնում են **առաջ** ավտո հիպոթեզը աշխատում է; `auto` վարքը
բայթ-հավասար է նախորդ PR-1 պաշտպանիչ միջոցին։

#### API-հիմնաբառի շրջանակ (`visionBridgeKeyScope.ts`)

Երբ զանգահարողի API հիմնաբառը սահմանափակում է `allowedConnections`, քվոտայի խմբեր
(`allowedQuotas`) կամ մոդելներ (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), կամուրջը միայն
ընտրում է վերափոխել և նկարագրել մոդելները, որոնք հիմնաբառը կարող է օգտագործել, այն կապերում, որոնք հիմնաբառը կարող է
օգտագործել։ Նկարագրելու զանգը ապա միշտ անցնում է OmniRoute ինքնամղման միջոցով
`x-omniroute-self-loop-key-id` գլխագրով, այնպես որ ստացող զրույցի հարցումը
կրկին պարտադրում է այդ հիմնաբառի կապի և մոդելի քաղաքականությունը։ `enforceApiKeyPolicy()`
հարգում է այդ գլխագիրը միայն ինքնամղման կրողի հետ միասին, այնպես որ այն կարող է միայն
սահմանափակել մուտքը, և լուծվող ID-ն մերժվում է։

Եթե տեսողական մոդելը թույլատրված չէ հիմնաբառի համար, նկարագրելու ճանապարհը կողմ է
անցնում և հարցումը անցնում է անփոփոխ, նույն ձախողման բաց վարքը, ինչպես անջատված
պաշտպանիչ միջոցը (meta `{ skipped: true, reason: "no_permitted_vision_model" }`)։
Հարցումները առանց հիմնաբառի, և հիմնաբառերը առանց այս սահմանափակումների, վարում են ճիշտ այնպես, ինչպես
նախկինում։

#### Պատասխանատու նկարագրության հրահանգ (`modalityBridgeVisionTaskAware`)

Անհրաժեշտ է **ճիշտ**։ `composeVisionPrompt()` (`visionBridgeHelpers.ts`) ավելացնում է
**վերջին օգտվողի հաղորդագրության** (կրճատված 500 նիշի) տեքստը հիմք
նկարագրելու հրահանգին, ուղղորդելով նկարագրությունը դեպի այն, ինչ օգտվողը իրականում հարցրել է
(codex-vision-proxy ձևաչափ) և հարցնելով տեսողական մոդելին տեսանելի
տեքստը տպագրելու համար։ Եթե դրոշակը անջատված է — կամ օգտվողի տեքստ չկա — հիմք
հրահանգը օգտագործվում է առանց փոփոխության։

Նկարագրելու ինքնապտույտի OpenAI-համատեղելի հարցումը (`callVisionModelSingle()`
`visionBridgeHelpers.ts`-ում) միշտ հարցնում է `image_url.detail: "high"` —
անհրաժեշտորեն, յուրաքանչյուր զանգահարողի/մատակարարի համար, առանց որևէ հաճախորդի ազդանշանի վրա
կանգ առնելու։ Նվազ մանրամասնության նմուշառումը նվազեցնում է OCR ճշգրտությունը հենց այն տեքստի-տպագրության
աշխատանքում, որը այս հրահանգը հարցնում է, այնպես որ նկարագրելու զանգը միշտ հարցնում է բարձր
մանրամասնություն, անկախ նրանից, թե ինչ մանրամասնության մակարդակ է օգտագործվել սկզբնական
մտնող հարցման մեջ։ Սա միայն ազդում է ներքին նկարագրության հարցման մարմնի վրա; դա չի փոխում, թե ինչպես
OmniRoute-ն փոխանցում է զանգահարողի սեփական `image_url.detail` հիմնական հարցման ժամանակ —
այս նախնական արժեքը կիրառվում է առանձին, և միայն հայտնաբերված OpenCode հաճախորդների համար,
`defaultImageDetail()`-ում (`open-sse/handlers/chatCore/upstreamBody.ts`)։ Anthropic-ի
լարային ձևաչափի նկարագրության ինքնապտույտը չունի `detail` դաշտ և չի ազդում
ոչ մի նախնական արժեքի վրա։

#### Նկարագրելու ելքային սահմանափակում (`modalityBridgeVisionMaxChars`)

| Կի                             | Նախնական | Տիրույթ           |
| ------------------------------ | -------- | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`      | `0` կամ 100–50000 |

`0` (նախնական) նշանակում է **ոչ սահմանափակում** — `callVisionModel()`-ի կողմից վերադարձված
նկարագրությունը փոխանցվում է առանց փոփոխության, պահպանելով առկա վարքագիծը։ 100–50000
տիրույթում ցանկացած արժեք կկրճատի նկարագրությունը `…` հավելվածով, նախքան այն
վերադարձնելը որպես `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` `src/lib/guardrails/visionBridge.ts`-ում)։
Ավելի բարձրացրեք սա մանրամասնության ծանր OCR աշխատանքների համար, որտեղ ներքևի մոդելը
պետք է ունենա ամբողջական տպագրություն; նվազեցրեք այն, որպեսզի սահմանափակեք նշանների օգտագործումը
խոսուն տեսողական մոդելների վրա։ Դաշտը գտնվում է Vision ներդիրի Advanced պանելում
(`modality-bridge-max-chars` `ModalityBridgeVisionTab.tsx`-ում) և սահմանափակում է ցանկացած
արժեք 1-ից 99 մինչև 100 հատակը, մինչդեռ թողնելով բացահայտ `0`-ը անփոփոխ — `0`-ը
իրենց իսկ իրավունքով վավեր Zod արժեք է
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), ոչ միայն
«չսահմանված» նախնական արժեք։

#### Նկարագրելու կոշտություն (`modalityBridge/bridgeCache.ts`)

Հիշողության մեջ LRU + TTL կոշտություն նկարագրության ելքերի համար, կիսված գործընթացի լայնությամբ։
Կի = `sha256(imageRef + composedPrompt + configuredBridgeModel)` երկարության-նախանշանի շրջանակով
(ոչ դաշտ-սահմանային բախումներ)։ Մոդելի բաղադրիչը **կոնֆիգուրացված** կամուրջի մոդելն է, ոչ թե
մոդելը, որը իրականում պատասխանեց — `callVisionModel` կարող է ներքին կերպով հետադարձվել,
և յուրաքանչյուր փորձի համար բանալին կկոտրի կոշտությունը։ Ապարդյուն նկարագրությունները երբեք չեն
կոշտացվում։ Կարգավորումներ.

| Կի                              | Նախնական | Տիրույթ |
| ------------------------------- | -------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`   | —       |
| `modalityBridgeCacheTtlMinutes` | `60`     | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`    | 10–5000 |

#### Remote image normalization (self-loop describe/base64 fetch)

Երբ կամուրջը ինքնուրույն **remote** պատկեր է բերում — Anthropic նկարագրության
ինքնահավաքը և claude-wire-format base64 փոխարկումը
(`ensureBase64ImagesForClaudeWire`), երկուսն էլ `fetchRemoteImageAsDataUri()`
`visionBridgeHelpers.ts`-ում — արդյունք հանդիսացող տվյալ URI-ն փոխանցվում է
`normalizeDataUri()`-ի միջոցով
(`open-sse/utils/imageNormalize.ts`) նախքան այն ներառվելը տեսողական մոդելի
հարցման մեջ։ Oversized պատկերները նվազեցվում են **2048px երկար եզր** (համապատասխանելով
OpenAI/Anthropic-ի կողմից արդեն կիրառվող վերափոխման սահմանափակմանը), ինչը կրճատում է
բեռնումը/լատենտությունը առանց փոխելու այն, ինչ տեսնում է տեսողական մոդելը։ Վերափոխումը
օգտագործում է `sharp`, որը բեռնվում է դինամիկ ներմուծմամբ։ Պլատֆորմում, որտեղ դրա բնիկ
բայթը չի բեռնվում, `normalizeDataUri()` **չի նետում** — այն վերադառնում է
առաջին բայթերի փոխանցմանը, այնպես որ նկարագրելու/base64-փոխարկման
ուղին միշտ շարունակում է աշխատել։ Ոչ-պատկերային բայթերը (մատակարարում, որը չի վերադարձրել
կարդացվող պատկեր) նույնպես փոխանցվում են առանց փոփոխության։ Այս նորմալացումը
սահմանափակվում է պատկերներին, որոնք կամուրջը բերում է իր սեփական ինքնահավաքի համար —
այն երբեք չի կիրառվում զանգահարողի خام փոխանցման բեռի վրա, համապատասխան
ընտրովի միայն մուտացիայի սկզբունքին (Hard Rule #20)։

#### Կարգավորումների սխեմա + միգրացիա

Նոր `modalityBridge*` բանալիները Zod-ով վավերացված են `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, `modalityBridgeCache*` եռյակը, և
`modalityBridgeAudio*` խումբը, որը օգտագործվում է Audio Bridge-ի կողմից։ Միգրացիա
`141_modality_bridge_settings.sql`-ը պատճենում է առկա ժառանգական
`visionBridge*` արժեքները համապատասխան նոր բանալիներին (իդեմպոտենտ, երբեք չի փոխում
օպերատորի սահմանած `modalityBridge*` արժեքը); ժառանգական բանալիները մնում են ընդունելի
որպես ընթերցմանFallback մեկ թողարկման ցիկլի համար։

#### Թափանցիկության գլխիկ + վիճակագրություն

Նկարագրության-փոխված պատասխանները կրում են
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(կառուցված `buildModalityBridgeHeader()`-ի միջոցով `modalityBridge/bridgeStats.ts`-ում,
նշված `withModalityBridgeHeader()`-ի միջոցով `src/sse/handlers/chatHelpers.ts`-ում)։
Վերափոխված հարցումները **չեն** կրում գլխիկ — բեռը անփոփոխ էր, և մոդելի
փոխարինումը արդեն տեսանելի է պատասխան մարմնի `model` դաշտում։

`GET /api/modality-bridge/stats` (կառավարման հեղինակություն, նույն մակարդակում ինչպես
`GET /api/settings`) վերադարձնում է հիշողության մեջ գտնվող յուրաքանչյուր մոդալիտետի հաշվիչները
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` `vision`, `audio`, և
`video` համար: `averageLatencyMs` օգտագործում է `latencySamples`, ոչ բոլոր փորձերը, որպես
այս բաժինը; ժամանակի բացակայությամբ գործողությունը չի ստեղծում զրո-միլիսեկունդի
օրինակ: `bridged` մնում է հետադարձ համատեղելի անուն հաջող
փոխարկումների համար; անհաջող փորձերը չեն ավելացնում այն:
Հաշվիչները վերականգնվում են գործընթացի վերագործարկման ժամանակ նախագծային
(հեռանկարային, ոչ հաշվապահական):

#### Դաշտի կարգավորում

Հատուկ դաշտի էջը
`/dashboard/settings/modality-bridge` է: Նրա URL-ով հասանելի `Vision`, `Audio`,
և `Video` թաբերը պահպանվում են հարցման պարամետրերը, երբ փոխվում է `tab` արժեքը:
Vision թաբը բացահայտում է ակտիվացումը, ռեժիմը, մոդելի ընտրությունը (ներառյալ ավտոմատ
հիմնականը), առաջադրանք-տեղեկացնող հարցումները, առաջադեմ ժամանակի/պատկեր/նկարագրության երկարության/կանխիկի
սահմանները, ընթացիկ
հաշվիչները, և պաշտպանված օրինակների հարցում: Audio թաբը նույնպես կենդանի է: այն բացահայտում է
ակտիվացումը, STT-մոդելի ընտրիչը Auto-ով, ժամանակի/մաքսիմալ-կլիպի սահմանները, աուդիո
հաշվիչները, և `input_audio` օրինակների փորձարկում: Video թաբը գործառնական է: այն հաղորդում է
FFmpeg/ffprobe ընթացիկ վիճակը — չորս հստակ UI վիճակներից մեկը (`unknown`, երբ
հետազոտությունը օդում է կամ չի կարող ավարտվել, `restricted` ոչ-լուպբեք
դաշտի հյուրընկալողում, որտեղ հետազոտությունը բաց է թողնվում հաճախորդի կողմից, `unavailable`, երբ հետազոտվել է
և հաստատվել է բացակայությունը, կամ `available` FFmpeg/ffprobe տարբերակներով) — պահպանվում է
ակտիվ/մոդել/ֆրեյմ/վիդեո/ժամանակի սահմանները, ֆիլտրում է մոդելի ընտրիչը տեսողական
կարողություններով մոդելների համար, և բացահայտում է վիդեո հաշվիչները:

AI կարգավորումներում նախկին Vision Bridge քարտը համատեղելիության հղում է
նոր էջին; այն այլևս չի տիրապետում ձևի երկրորդ պատճենին: Մեդիա մատակարարները նույնպես
հղում են տալիս Image-to-Text և Speech-to-Text աշխատանքային հոսքերին համապատասխան Modality
Bridge թաբերին, առանց գոյություն ունեցող Speech-to-Text խաղահրապարակը հեռացնելու:

**Self-loop ընդունման շրջանցում:** երբ նկարագրող զանգը անցնում է OmniRoute-ի
իր սեփական `/v1` self-loop (ոչ ստանդարտ մատակարարի մոդել), ենթահարցումը ուղարկում է
`x-omniroute-admission-bypass: internal` և հաստատվում է լուծված
self-loop հավատարմագրով — տեղական `sk_omniroute` պահապանով տեղական ռեժիմում, կամ
օպերատորի կողմից կարգավորված `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env բանալի (#1350), այնպես որ
`REQUIRE_API_KEY=true` տեղադրումները դեռ կարող են գործարկել նկարագրող զանգը: Շրջանցումը
ընդունվում է միայն այդ կոնկրետ հավատարմագրերի համար, այնպես որ արտաքին հաճախորդները չեն կարող օգտագործել
հաղորդագրությունը ընդունումը շրջանցելու համար:

Հին նախնական կարգավորումները գտնվում են `src/shared/constants/visionBridgeDefaults.ts`-ում; նոր
ռեժիմ/աշխատանք-տեղեկացնող/կանխիկ նախնական կարգավորումները և կարգավորման լուծիչը գտնվում են
`src/shared/constants/modalityBridgeDefaults.ts`-ում: Պաշտպանիչը բացահայտում է
`deps` կառուցողի տարբերակը, որպեսզի թեստերը կարողանան ներարկել կեղծ `getSettings` և
`callVisionModel` իրականացմանները:

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Խանգարում է աուդիո պարունակող զրույցի հարցումները, նախքան դրանք հասնում են նպատակին, որը հայտնի չէ
ընդունել աուդիո մուտք: Այն երբեք չի վերափոխում զրույցի հարցումը. աուդիո մասերը
գրանցվում են գոյություն ունեցող OpenAI-համատեղելի բազմամասային վերջնակետում, և
ընտրված զրույցի մոդելը շարունակվում է տեքստային գրառումների հետ:

Հոսք:

1. Լուծել `supportsAudio` `getResolvedModelCapabilities()`-ի միջոցով: Հստակ
   մատակարարի գրանցման մետադատան հաղթում է, ապա ստատիկ մոդելի մետադատան, ապա համաժամեցված
   `modalities_input`: `audio`-ի բացակայությամբ հայտարարված մուտքային ցուցակը `false` է; ոչ
   կարողության ապացույցը մնում է `null`: Որպես `false`, այնպես էլ `null` ակտիվացնում են
   պահպանողական կամուրջը, մինչդեռ `true` շրջանցում է այն:
2. Լուծել `modalityBridgeAudio*` կարգավորումները և յուրաքանչյուր հաղորդագրությունից դուրս բերել
   կտրվող բարձր մակարդակի աուդիո մասերը `detectMediaParts()` ընդհանուր
   հայտնաբերիչի միջոցով: Հsupported wire shapes-երը OpenAI `input_audio`, `audio_url`, և
   `source.media_type: "audio/*"`: Ներսում աուդիոն հայտնաբերվում է ուղղորդման համար, բայց
   չի հեռացվում կտրման ճանապարհով: Աշխատանքը սահմանափակվում է `modalityBridgeAudioMaxClips`-ով;
   հետագա մասերը մնում են անփոփոխ:
3. Հարգել կարգավորված `provider/model`, կամ թողնել `selectAudioBridgeModel()`-ը քայլել
   `AUDIO_TRANSCRIPTION_PROVIDERS` կայուն կատալոգի կարգով և ընտրել առաջին
   մոդելը, որը ունի օգտագործելի ակտիվ մատակարարի հավատարմագիր:
4. `callAudioTranscription()`-ը փոխարկում է base64/data-URI աուդիոն բազմամասային
   `file`-ի, կամ ներբեռնում է հեռավոր `audio_url` հանրային միայն դուրս գալու
   պաշտպանությամբ DNS-ով և 25 MB սահմանով: Այնուհետև POST-ով ուղարկում է ֆայլը և ընտրված
   մոդելը տեղական `/v1/audio/transcriptions` self-loop-ին, հաստատված `resolveSelfLoopBearer()`-ով: Գոյություն ունեցող
   գրանցման ուղին իրականացնում է սովորական հավատարմագրերի որոնում, սառեցման/տեմպի սահմանափակումների
   կառավարում և մատակարարի ուղարկում:
5. Հաջող զանգերը փոխում են իրենց մասերը `[Audio N]: <transcript>`. Զանգերը
   աշխատում են `Promise.allSettled`-ով. անհատական անհաջողությունը պահպանվում է այդ սկզբնական
   աուդիո մասի համար (#4012 պայմանագիր): Եթե յուրաքանչյուր զանգ անհաջող է, և նպատակն ապացուցվում է
   `supportsAudio === false`, մասերը դառնում են
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 պայմանագիր): Անհայտ նպատակների համար (`null`),
   բոլոր անհաջողությունների արդյունքը մնում է անփոփոխ: Ապացուցված տեքստային նպատակ, որը չունի օգտագործելի STT
   հավատարմագիր, ստանում է նույն հստակ
   stub-ը առանց ցանցային զանգ կատարելու:

Հաջող գրառումները օգտագործում են գործընթացի լայնությամբ Modality Bridge LRU/TTL կաշետը: Բանալիի
համակցումը աուդիո հղումը, կայուն `audio-transcription` գործողության
լեյբլը և ընտրված STT մոդելը; անհաջողությունները երբեք չեն պահվում: Աուդիո փորձերը թարմացնում են
համատեղ `bridged`, `cacheHits`, `failures`, և `lastUsedAt` հաշվիչները:
Փոխարկված պատասխանները կրում են
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; անփոփոխ
հարցումները չեն ստանում Audio Bridge հատված:

Ընթացիկ կարգավորումները DB-ով աջակցված են և Zod-ով վավերացված:

| Կոդ                           | Դեֆոլտ  | Տիրույթ         |
| ----------------------------- | ------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —               |
| `modalityBridgeAudioModel`    | `""`    | Auto կամ STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10            |

Կիսված կոշտ հիշողությունը մնում է վերահսկվող `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, և `modalityBridgeCacheMaxEntries` կողմից:

### Video Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

Բռնում է բարձր մակարդակի տեսանյութի մասերը Chat Completions `messages` և Responses
API `input`-ը, նախքան նպատակայինը, որի բնիկ տեսանյութի աջակցությունը հայտնի չէ, կոչվում է:
Աջակցվող ձևերը են `input_video`, `video_url`, `video_source`, HTTPS URLs,
և `data:video/*;base64,...` տվյալ URI-ները: Սովորական ֆայլի անունները տեքստում չեն դիտվում
որպես տեսանյութ:

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) պատկանում է հարցման անցմանը,
հնարավորության/քաղաքականության ստուգմանը, յուրաքանչյուր հարցման հավաքագրմանը, և պատասխանների բեռին:
Յուրաքանչյուր տեսանյութի աշխատանք — ձեռքբերում, ամբողջ արդյունքի կոշտ հիշողություն,
ֆրեյմի հաջորդականության նկարագրություն (որը միավորում է ցանկացած զանգահարողի կողմից հայտարարված
աուդիո տեքստը), և յուրաքանչյուր փորձի մետրիկներ/դադար/մաքրում — թաքնված է
`processVideoPart`-ի տակ `videoBridgePipeline.ts`-ում, որը կոչվում է մեկ անգամ
ամեն տեսանյութի մասի համար `preCall`-ի ցիկլի ներսում:
Այդ մոդուլը նաև սահմանում է հստակ պորտային սահմանները `VideoMediaBrokerPort`
(բեռնում է բայթեր և հանում նմուշված ֆրեյմեր), `VideoAudioTranscriptionPort`
(միավորում է զանգահարողի կողմից հայտարարված աուդիո տեքստը նմուշված ենթագրերի հետ), և
`VideoDrilldownPort` (հին خام-պահեստի ձևը): Արտադրական STT և ֆրեյմի պահպանում
կազմված են նկարագրող պորտի շուրջ `createVideoSttAdapter` և
`createVideoDrilldownAdapter`-ի միջոցով; վերջինս օգտագործում է կիսված անթափանց-հանդիպման կյանքի ցիկլը:

Հանրային `/v1` հարցման ուղին երբեք չի ներմուծում կամ չի հրավիրում ենթածրագրեր: Հեռավոր
տեսանյութերը ներբեռնվում են 50 MiB սահմանով; inline base64 տեսանյութերը ունեն
համեստ 36 MiB ապակոդավորված յուրաքանչյուր տեսանյութի սահման, որպեսզի մոդելը/հաղորդագրությունները/կ框ավորումը
կարողանան մնալ հանրային JSON հարցման ընդունման սահմանում 50 MiB: Inline
երկայնքի և ապակոդավորված չափերի գնահատումները ստուգվում են նախքան հատկացումը: HTTPS-ը
պահանջվում է սկզբնական հեռավոր URL-ում և յուրաքանչյուր վերափոխման ժամանակ, օգտագործելով
կայուն հանրային միայն outbound պաշտպանությունը DNS pinning-ով: Բայթերը ապա անցնում են
ճիշտ ներքին `POST /api/modality-bridge/video/extract` բրոքերի սահմանը: Այդ ուղին
ևս `LOCAL_ONLY` և `SPAWN_CAPABLE` է, ընդունում է միայն մեկ գործընթացի կողմից
հավաստագրված, վստահված-լուպի հարցում, և երբեք չի ընդունում URL, ֆայլային համակարգի
ուղի, executable, կամ արգումենտների ցանկ: API մարմնի չափի pipeline-ը և
հանդիպողի աճող մարմնի ընթերցողը անկախ կերպով պարտադրում են 50 MiB բրոքերի
մտածված սահման: Նրա սահմանափակ հերթը կատարում է մեկ extraction մեկ անգամ, թույլ

Բրոքերում, `ffprobe`-ը կարդում է մասնավոր տեղական ֆայլ; ֆիքսված ձևաչափի

`segment_aware` օգտագործում է մեկ սահմանափակ նախնական վերլուծության անցում արդեն հաստատված տեղական տեսահոսքի վրա: Կայուն ֆիլտրերի շղթան առաջինը չափում է առավելագույնը 320 պիքսել լայնությամբ, հայտնաբերում է տեսարանների փոփոխությունները և սառեցված միջակայքները, ապա նմուշավորում է 1 կադր մեկ վայրկյանում մթության, միջին լումայի և տարածական/ժամանակային տեղեկատվության համար: Անցումը սահմանափակվում է 600 կառուցվածքային նմուշներով, մեկ FFmpeg/ֆիլտրի թելով, նույն `file`-միայն պրոտոկոլով և կոնտեյների թույլտվություններով, 1 MiB գործընթացի-արտադրանքի սահմանով և առավելագույնը 30 վայրկյան բրոքերի ընդհանուր չեղարկման/ժամկետում: Այն երբեք չի ընդունում հրաման, ֆիլտր, ուղի կամ URL խնդրանքից:

Կորցված ֆիլտրերը, սխալ ձևավորված/ դատարկ ապացույցները, հայտնաբերման սխալը կամ սահմանափակ նախնական վերլուծության ժամկետը բաց են մնում ճշգրիտ միատեսակ միջին քաղաքականության համար: Հրահանգողի չեղարկումը կամ բրոքերի ժամկետը չեն բացվում. այն ավարտում է ընթացիկ ենթածրագրերը, կանխում հետագա կադրերի հանումը, և մասնավոր ժամանակավոր ծառը հեռացվում է `finally`-ում:

`scripts/perf/video-bridge-fu07-eval.ts` ստեղծում է որոշիչ իրական FFmpeg սարքեր հետագա կրկնօրինակման վերնագրերի խնայողությունների, խիտ-շարժման բյուջեի հատկացման, մթության/լուսավորության/SI-TI ապացույցների, արագ կտրվածքների երկար хвостով և աստիճանական-մարելու կեղծ դրականների համար: Այն գրանցում է նախնական վերլուծության պատի ժամանակը և, որտեղ `/usr/bin/time` հասանելի է, երեխայի CPU և գագաթային RSS: Նրա որակի ստուգումները միայն կառուցվածքային օրհնություններ են: Իրական վերնագրերի մոդելի որակը մնում է `HOLD`, քանի որ այս սարքը չունի թույլատրված վերջնակետ կամ սառեցված դատավոր: Դրամական խնայողությունները նույնպես մնում են `HOLD`, եթե `--caption-cost-per-call-usd` չի տրամադրում բացահայտ դրական յուրաքանչյուր զանգի գնահատում; սցենարը երբեք չի ստեղծում ոչ մի արդյունք:

Յուրաքանչյուր կադր սահմանափակվում է 4 MiB-ով, բոլոր خام կադրերը միասին 23 MiB-ով, և սերիալացված բրոքերի պատասխան 32 MiB-ով: Մասնավոր ժամանակավոր կատալոգը հեռացվում է `finally`-ում: OmniRoute-ը չի փաթեթավորում FFmpeg և չի ընդունում հարմարեցված executable ուղի: Վերնագրելուց առաջ, կամուրջը կիրառում է պահպանողական տեսողական կրկնօրինակման անցում. յուրաքանչյուր JPEG-ը նվազեցվում է 16×16 մոխրագույն բուֆերի և համեմատվում է միայն վերջին պահպանված կադրի հետ: ՄRequested վերնագրի բյուջեի համար, որը գերազանցում է մեկ կադր, հանումը տրամադրում է սահմանափակ թեկնածուների պուլ մինչև այդ բյուջեի կրկնակի և երբեք ավելի քան 16 կադր: ՄRequested սահմանը կիրառվում է միայն կրկնօրինակման հետո, առաջին և վերջնական ընտրված թեկնածուները պահպանվում են վերջնական նոսրացման ընթացքում, երբ բյուջեն առնվազն երկուսն է: Վարկանիշային `grayscale-16x16-mean-cells-v2` քաղաքականությունը օգտագործում է միջին լումայի դելտայի և մանրապատկերի բջիջների հարաբերությունը, որոնց նորմալացված դելտան առնվազն 0.05 է: Կրկնօրինակման շեմը 0.04 մշտական է, ընտրված կանխատեսելիության համար, այլ ոչ թե որպես գործառնական կարգավորում: Այս երկրորդական բարձր-հակապատկերային ազդանշանը պահպանվում է փոքր շարժման և տեսանելի-տեքստի փոփոխությունների, որոնք կարող են թաքցնել միայն միջին համեմատությունը: Համեմատիչի կամ դեկոդերի սխալները բաց են մնում և պահպանում են ծածկույթը: Արտադրանքի մետատվյալները բաժանում են հանված թեկնածուները, հաջողությամբ օգտագործված կադրերը և տեսողական կրկնօրինակները:

Բացահայտորեն նշված տեսանյութի մասը կարող է պահանջել ժամանակStamped կոնտակտային թերթիկ: Կամուրջը կառուցում է առավելագույնը 4-սյունակ, 16-կադր JPEG ցանց: Յուրաքանչյուր 512-պիքսել բջիջը այրում է իր աղբյուրի ժամանակը բարձր հակապատկերային ստորին գոտում, մինչդեռ նույն ժամանակները մնում են տեքստային մետատվյալներում հետագա ասոցիացիայի և աուդիտի համար: Completeness JPEG-ը մնում է սահմանափակված 32 MiB-ով: Եթե `sharp` չի կարող դեկոդել կամ կազմել ցանցը, կամուրջը վերադառնում է անհատական JPEG կադրերին; հաճախորդի չեղարկումը դեռ տարածվում է թերթիկի գործողության միջոցով:

Հրատապ ապացույցները դիտավորյալ առանձին են սինթետիկ կազմության միկրոքննարկումից: `scripts/perf/video-bridge-contact-sheet-eval.ts` սահմանում է սխեմայի տարբերակված A/B սարքավորում իրական OpenAI-համատեղելի տեսողական մոդելների համար: Այն չափում է մատակարարի հաղորդած նշանները, վերջից մինչև վերջ պատի ուշացումը (ներառյալ թերթիկի կազմությունը), մոդելի զանգերի քանակը և մանիֆեստի կողմից սահմանված փաստերի պահպանումը: خام մոդելի պատասխանները չեն գրանցվում հաշվետվությունում; միայն SHA-256 խտացումները և համապատասխան փաստերի ID-ները պահպանվում են: Սարքը չի կատարում ցանցային կամ վճարովի մոդելի զանգ, եթե `--execute-real` չի փոխանցվում և `--model`, `OMNIROUTE_BASE_URL`, և `OMNIROUTE_API_KEY` չեն կարգավորվում: Այդ բացահայտ իրական գործառույթից բացի, դրա մեքենայաբար ընթերցվող վճիռը մնում է `HOLD`; սինթետիկ բեռի/զանգերի քանակի չափումները միայն չեն հանդիսանում առաջխաղացման ապացույց:

Անհատական `scripts/perf/video-bridge-promotion-eval.ts` սպառում է FU-07 կամ FU-09 դիտարկումներ: Առաջխաղացման ընդունումը պահանջում է բոլոր ութ սինթետիկ սցենարի տեսակները, ինչպես նաև մաքրված իրական կլիպ, առնվազն երեք չափված կրկնություններ յուրաքանչյուր դերի և դեպքի համար, բոլոր տասը հայտարարված մետրիկաները, սառեցված մեդիա/խթան/սպասվող-փաստ/համակարգման խտացումները, եզակի դիտարկման ID-ները և ստուգված սերմավորված A/B կարգը: Գործողության ստացումն կապում է կորպուսի խտացումը, ճշգրիտ թեկնածու SHA-ն և մոդելի տարբերակը: Կորցված կամ անվավեր չափումները մնում են `HOLD`, ներառյալ CPU-ն 30 վայրկյանից բարձր, գագաթային RSS 512 MiB-ից բարձր կամ նախնական վերլուծությունը 30 վայրկյանից բարձր: Սա ապացույց-ընդունման սահմանափակումներ են, ոչ նոր գործառնական RSS-ի պարտադիր երաշխիք:

FU-07 պահանջում է առնվազն 98% որակի պահպանություն և p95 ուշացում ոչ ավելի, քան 1.2x
հիմնային, ինչպես նաև կամ 0.05 բացարձակ դեպքի հավասարակշռված միջին հիշողության բարելավում
համապատասխան միջին վերնագրերի զանգերի դեպքում, կամ առնվազն 10% ավելի քիչ միջին
հետադարձ-հեռացման վերնագրերի զանգեր: FU-09 պահանջում է առնվազն 0.85 որակ, 95% պահպանություն, 20% p95 ուշացման
կրճատում և 10% նշանների կրճատում: Կրիտիկական փաստերի կորուստը, ներարկման համապատասխանությունը կամ
կորած օգտագործումը կանխում են առաջխաղացումը: Մի կատարում չի կարող առաջխաղացնել ոչինչ:
`--previous-report` հաստատում է նույն քաղաքականության/մոդելի վերանայման/դիտարկման համար երկու տարբեր, չհամընկնող,
հաջորդականորեն իրավասու կատարումներ: Նմուշառման փորձարկումը չի կարող հաստատել
կոնտակտային-թերթիկի փորձարկումը:

Հավաքողները պետք է գնահատեն պատասխանները հիշողության մեջ և պահպանեն `responseDigest` և
մետրիկա և դիտարկման կապեր, երբեք պատասխանային տեքստը: Օգտագործողը նաև ընթերցում է
հին خام դիտարկումները, բայց երբեք չի պատճենում այդ տեքստը իր հաշվետվություններում: Ցանկացած դիտարկման համար ընդունվում է
միայն `responseDigest` կամ `rawResponseText`: Վարկանիշային թույլտվությունը մնում է դատարկ
անփոփոխ `hold` նախնական արժեքով: Իրավասու մուտքը պահանջում է իր ապացույցի հղումը, քաղաքականություն, մոդելի վերանայում, ճշգրիտ
դիտարկման SHA, մանիֆեստի դիգեստ և երկու տարբեր կատարումների ID-ներ; հակասական համատեքստերը
հրաժարվում են: Այս մետադատները աուդիտի պայմանագիր են, ոչ թե ապացույց, որ հղված
ֆայլը պարունակում է իսկական չափումներ: Ավելացնել ցանկացած մուտք, նախքան իրական
հաշվետվությունները: Կառավարման վիճակագրության վերջնակետը և Video վահանակը բացահայտում են պահպանողական
պատրաստականությունը: Միայն կոնֆիգուրացված մոդելի ալիասը չի հաստատում իր վերանայումը կամ

ԱյդFallback ուղիներում, վավեր զանգահարողի ազդակները դառնում են աջակցվող `text`/`input_text` մասեր, այլ ոչ թե ոչ ստանդարտ մատակարարի դաշտեր: Երկու պահանջով տրամադրված ուղիները մնում են անվստահ `client` դիտարկումներ, հստակ նախազգուշացումով, որ տեսանյութը չի նկարագրվել և ժամանակային նշումները չեն ստուգվել մեդիայի դեմ: Ակտիվ 256-ազդակ/64-KiB ընդհանուր և յուրաքանչյուր ազդակի բյուջեները կիրառվում են երկու ուղիների համար միասին; ժամանակային նշումները պետք է համապատասխանեն միջնորդի 600-վարկյան շեմին և ցանկացած տրամադրված կենտրոնացման պատուհանին: Անվավեր ուղիները մերժվում են, ոչ թե փոխանցվում որպես պատահական տեքստ; վավեր եղբայրը դեռ կարող է օգտագործվել, եթե նրանց համատեղ բյուջեն չի գերազանցվում: Null/ դատարկ դաշտերը չեն ավելացնում տեքստ: ԱյսFallback-ով չի ավելացվում որևէ մեդիա որոնում կամ տեքստագրություն: Տեքստագրության ընդլայնման դաշտերը հեռացվում ենFallback տեսանյութի կրողից և դրա `video_url`/`source` օբյեկտներից: OpenAI-ի մալուխի թույլտվությունը մնում է խիստ; անհայտ-բնական տեսանյութի կրողները մնում են հասանելի, իսկ հայտնի միայն տեքստային նպատակները պահպանում են անվտանգ նշաններ: Կառուցված կարմիրացումի ստվերները պաշտպանում են հավելված տեքստը, մինչդեռ սկզբնական զանգահարողի սեփական պահանջը մնում է անփոփոխ: Բնական աջակցվող նպատակները և անջատված կամուրջները պահպանում են իրենց գոյություն ունեցող շրջանցման վարքագիծը:

Ավելացված պահպանված պատճենները օգտագործում են նույն դիտարկված-պահանջի ազդակը: خام նախնական-պաշտպան client-request-ի պատկերումը, հիշողության մեջ սպասող պահանջը և վաղ մերժված-պահանջի օրագիրը կառուցվածքայինորեն փոխարինում են տեքստագրության դաշտերը տեսանյութի մասերում; տողային հրահանգները, որոնք սինթեզվում են խողովակաշարի փուլերով և համատեքստի փոխանցմամբ, կարմիրացվում են պահպանված-պահանջի մարմնի խողովակում: Պահպանված `video_content_removed` նշանը ստիպում է `previous_response_id` շարունակությունը փակվել, այլ ոչ թե վերակառուցել տեքստը, որը դիտավորյալ մերժվել է: Եթե դիտարկված պահանջը կորցնում է իր յուրաքանչյուր մասի կարմիրացման ստվերը նախքան գրանցումը, կամ նույնիսկ մի քանի տեսանյութի ստվերներից մեկը չի համապատասխանում հետագա պահանջի փոփոխություններից հետո, պահպանված պահանջի մարմինը ամբողջությամբ բացակայում է, այլ ոչ թե պահպանում է մասնակի կարմիրացված տեքստագրությունը:

Դիտարկված պահանջի համար մոդելի պատասխանն կարող է մեջբերել ցանկացած հատված տեքստագրությունից առանց կառուցվածքային ազդակային սահմանների: Նրա պահպանված զանգի-օրագիր `responseBody` հետևաբար փոխարինվում է բացակայության նշանով; մանրամասն խողովակաշարի արհեստական (որը կարող է ներառել վերին/client մարմիններ և հոսքի կտորներ) չի պահպանվում: Սեմանտիկ, իդեմպոտենտություն և տրամաբանության-վերադարձի caches-ն շրջանցում են ընթերցումները և գրառումները այդ պահանջի համար: Մատակարարի պահանջը և client-տեսանելի պատասխանն մնում են անփոփոխ: Վաղ keepalive բայթերը դուրս են հանվում ժամանակավոր բուֆերից, երբ մանրամասն արհեստականը բացակայում է: Kiro-ի սխալ ձևավորված EventStream նախազգուշացումը հաղորդում է միայն բեռի բայթերի քանակը, երբեք դրա պարունակությունը կամ JSON վերլուծիչի خام սխալը:
Այսը չի պնդում, որ յուրաքանչյուր անկապ մատակարարի/պլագինի ախտորոշում է ախտահանվել; ավելի լայն պահպանված-խողովակի մաքրումը հետևվում է #11658-ում:

Արտադրական `/api/modality-bridge/video/drilldown` կյանքի ցիկլը առանձին, շրջադարձային/թոքեն-հավաստագրված պահեստի ենթակառուցվածք է: Յուրաքանչյուր գործողություն նաև պահանջում է կանոնական անթափանց հիմնական ID: Նախքան արտադրական զանգահարողի ակտիվացումը, այն պետք է ստանա այդ ID-ն հավաստագրված վարձակալից և երբեք չպետք է փոխանցի client-ընտրած արժեքը: Պահեստի բանալիները կապում են այդ հիմնականը կանոնական նստաշրջանի և տեսանյութի-հղման ID-ների հետ, պահում են միայն նրանց SHA-256-ով ստացված բանալիները և սահմանափակում են ինչպես ընթերցումները, այնպես էլ ջնջումը նույն հիմնականին: Պահեստը պահում է առավելագույնը 16 ստացված JPEG շրջանակ յուրաքանչյուր գրառման համար, ավարտում է դրանք տասը րոպե հետո և աջակցում է սահմանափակ `start`/`end` ընթերցումներին կամ հստակ նստաշրջանի ջնջմանը:

Յուրաքանչյուր հիմնականը սահմանափակված է 16 գրառմամբ և 64 MiB կանոնական JPEG տվյալներով: Այդ սահմանափակումները անկախ են գլոբալ 64-գրառման/256 MiB շեմից. հիմնական քվոտայի ճնշումը դուրս է մղում միայն այդ հիմնականի ամենաքիչ-վերջին օգտագործված գրառումները, նախքան գլոբալ LRU դուրս մղումը դիտարկվի: Վավերացված գրառումները մաքրվում են ինչպես հիմնականի, այնպես էլ գլոբալ հաշվարկից պահեստի գործունեության ժամանակ, մինչդեռ չեղարկումը և վավերացման ձախողումը չեն կատարում մասնակի փոխարինում:

Պահեստը մերժում է ոչ կանոնական Base64, ավելորդ padding, ոչ JPEG մեդիա, սխալ ձևավորված կամ կրճատված JPEG-ներ, և JPEG-ներ, որոնք արտադրում են նախազգուշացում սահմանափակ լիարժեք-պատկեր `sharp` դեկոդավորման ժամանակ: Այն վերադառնում է յուրաքանչյուր ընդունված պատկեր որպես կանոնական JPEG, ստանում է լայնությունը և բարձրությունը դեկոդավորված բայթերից, այլ ոչ թե վստահելով զանգահարողի դաշտերին, և հեռացնում է ցանկացած հետևողական polyglot բայթեր, այլ ոչ թե պահում դրանք: Միայն սահմանափակ կանոնական սեղմված բուֆերը հաշվարկվում է երկու քվոտաների համար: JSON մալուխի սահմանը ներառում է Base64-ի ավելցուկը 32 MiB դեկոդավորված-մտածված շեմի համար: Յուրաքանչյուր
պահված ստացում գրանցում է իր վավերացված JPEG ձևաչափը/լուծումը, նմուշառման քաղաքականությունը, ստացման տարբերակը, ստեղծման ժամանակը, սերվերի կողմից հաշվարկված բովանդակության հեշը և հեշավորված ծնողական հղումը, ինչպես նաև վստահելի զանգահարողի ծնողական-բովանդակության հեշը: Չեղարկումը ստուգվում է ասինխրոն դեկոդավորման/հեշավորման փուլերի միջև, նախքան ատոմային պահեստի հանձնումը:

Արտադրական արտադրողը վերօգտագործում է արդեն ստացված միջնորդի շրջանակները միայն հաջող տեսողական վերլուծությունից հետո, առանց երկրորդ տեսանյութի ներբեռնում/հանելու: Այն պահանջում է օպերատորի `modalityBridgeVideoDrilldownEnabled=true`, խիստ յուրաքանչյուր մասի `drilldown: true`, և հավաստագրված API-հիմնված գրանցման ID: Client-հայտարարած հիմնական/նստաշրջանի արժեքները երբեք չեն հաստատում սեփականությունը: Բոլոր երեք պայմանները չունենալով, այն չի հեշավորում, չի չափում կամ չի պահում լրացուցիչ շրջանակներ: Պահպանման ձախողումը պահպանվում է օգտագործելի տեսողական պատասխան: Համաձայնեցված պահանջները շրջանցում են ամբողջ-տեսանյութի արդյունքի պահեստը, այնպես որ պահեստավորված արդյունքները երբեք չեն կրկնում ձեռքեր:

Հաջող JSON և SSE պատասխանները բացահայտում են առավելագույնը չորս անթափանց ձեռքեր `x-omniroute-video-drilldown` գլխում: Արդարացված բրաուզերի ծագումները կարող են կարդալ այդ գլխի պարունակությունը առանց CORS ծագման քաղաքականության ընդլայնման: Նոր ձեռքեր օգտագործում են `v1.<32-byte random base64url token>` ձևաչափը, իսկ գրանցամատյանը պահպանում է միայն դրանց SHA-256 հեշերը: Կարդացող/գլխի վերծանողը նաև ընդունում է հին 64-հեքս տոքենները: Ավտորիզացված հանրային սպառողը է `GET /api/v1/video-bridge/drilldown?handle=...`, անկախ կերպով վերահսկվում է `modalityBridgeVideoDrilldownRemoteEnabled=true` պարամետրով: Հստակ պահպանված կեղծը վերացնում է մուտքը նույնիսկ այն դեպքում, երբ հին `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` միջավայրի վերապահումը ակտիվ է: Արտադրության պահպանման համար կա համապատասխան հին `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED` վերապահում: Երկու վերապահումները նույնպես ըստ կանխորոշման անջատված են:

Սպառողը սեփականություն է ստանում հաստատված բանալիից, կիրառելով բանալիի քաղաքականությունը և վերադարձնում է նույն 404-ը անհայտ, ժամկետանց և այլ բանալիների ձեռքերի համար: Այն ընդունում է `variant=preview|standard|detail` (ամենաբարձր JPEG չափը 320/640/1280, երբեք չի մեծացվում), `limit=1..8` (կամ հին `frames` այլ անունը, երբեք երկուսն էլ), զրոյից սկսվող `page`, և ընտրովի `start`/`end` կենտրոնացման վայրկյաններ: Դuplicated հարցման բանալիները և հակառակ կենտրոնացման պատուհանները մերժվում են: Յուրաքանչյուր վերադարձված տարբերակը ունի իր իրական պարունակության և իրական լուծման մետադատա, կապված պահված աղբյուրի հետ: Տարբերակները ստացվում են ընթերցման ժամանակ, այլ ոչ թե պահվում որպես լրացուցիչ պահված օրինակներ: JSON պատասխանն, ներառյալ Base64/փաթեթը, սահմանափակվում է 32 MiB-ով; չափազանց մեծ էջը վերադարձնում է 413, և հաճախորդը պետք է խնդրի ավելի քիչ շրջանակներ: Ընթերցումները ստուգում են չեղարկումը յուրաքանչյուր չափափոխման շուրջ և կրկին ստուգում են ձեռքի վավերությունը վերադարձնելուց առաջ: `DELETE` սեփականատիրոջ կողմից է իդեմպոտենտ; ջնջումը կամ TTL-ի ժամկետանցը ազատում է պահված աղբյուրը և օգտագործման հաշվարկը:

Կիսված պահեստը գործընթացային տեղական է. ձեռքերն ավարտվում են վերագործարկման ժամանակ և չեն փոխանցվում անկախ OmniRoute գործընթացների միջև: Կառավարման վիճակագրությունները բացահայտում են արդյունավետ պահպանման/հեռավոր քաղաքականությունը և հավաքական պահված գրառումները/բայթերը միայն, երբեք մեդիա, հղումներ, հիմնական ID-ներ կամ ձեռքեր: Տեսանյութի կարգավորումների պանելն ցույց է տալիս այդ արժեքները և կարող է պահպանել երկու համաձայնության switches: Այս իրականացման փաստաթուղթը չի հանդիսանում կենդանի տեղադրում կամ առաջխաղացման ապացույց; իրական մոդելի ընդունումը հետևվում է առանձին:

Շրջանակները ենթագրերով նշվում են հերթականությամբ կարգավորված Տեսանյութի մոդելի հետ: դատարկ Տեսանյութի փոխարինումը ժառանգում է Տեսողության կարգավորումը; եթե երկուսն էլ դատարկ են, Տեսողության ավտո-ուղղիչը ընտրում է արդյունավետ տեսողության ունակ մոդելը: Հաջող ենթագրերը փոխարինում են սկզբնական մասի հետ կայուն `[Video description:` նախածանցով, որը նաև նշում է տեքստը որպես անվստահ մեդիա-առաջարկություն և ասում է ստորին մոդելներին, որ չպետք է հետևեն մեդիայում հայտնաբերված հրահանգներին: Շրջանակի-սուբտիտրի կոշտ բանալիները ներառում են JPEG բայթերը, հրահանգը, ժամանակի կնիքը և արդյունավետ մոդելը; միայն հաջող ենթագրերը պահվում են: Կոշտ գրառումները պահպանում են իրական հաջող արտադրողի մոդելը, ներառյալ վերապահված մոդելը; կամուրջը հաղորդում է `mixed`, երբ տարբեր շրջանակներ արտադրել են տարբեր մոդելներ: Կոշտ գրառման հարվածը վերօգտագործում է այդ արտադրողի ինքնությունը, այլ ոչ թե վերանվանում է այն որպես խնդրված ուղղորդման պլան: Ընդհանուր տեսանյութի արդյունքի կոշտ գրառումը հիմնված է յուրաքանչյուր մուտքի վրա, որը փոխում է ելքը — հրահանգ, արդյունավետ մոդել, նմուշավորման քաղաքականություն, շրջանակների քանակ, սեմանտիկ վերլուծության ռեժիմ, նորմալացված կենտրոնացման հուշի SHA-256 մատնահետքը, կենտրոնացման պատուհան, `transcript`, `audioTranscript`, և կոնտակտային թերթիկի դրոշը — այնպես որ, այդ չափանիշներից որևէ մեկի փոփոխությունը կոշտ գրառման բաց թողնում է, երբեք չի հանդիսանում հին վերօգտագործում: Տեսողական կրկնօրինակի քաղաքականության տարբերակը, շեմը և սահմանափակ թեկնածու-շրջանակների քանակը նույնպես հստակ են արդյունքի կոշտ գրառման բանալու և մետադատի մեջ; քաղաքականության փոփոխությունը, հետևաբար, չի կարող վերօգտագործել հին ընդհանուր տեսանյութի նկարագրությունը: Արդյունքի կոշտ գրառման v4 մետադատը պահպանում է ռեժիմը և մատնահետքը, երբեք ոչ خام օգտվողի առաջադրանքը: Պաշտպանիչ մետադատը հաղորդում է ինչպես խնդրված, այնպես էլ արդյունավետ վերլուծության ռեժիմները; խնդրված `focused` ռեժիմը առանց օգտագործողի օգտակար տեքստի հաղորդվում է որպես արդյունավետ `full`.

Պաշտպանիչը հանում է յուրաքանչյուր աջակցվող տեսանյութի մասը, բայց նկարագրում է ոչ ավել, քան `modalityBridgeVideoMaxVideos`. Նպատակ ունենալով, որը հաստատված է `supportsVideo === false`, ձախողված և սահմանափակ տեսանյութերը դառնում են հստակ անվտանգ տեքստային նշաններ, այնպես որ ոչ մի خام տեսանյութ չի մնում: Երբ կարողությունը հայտնի չէ, այդ մասերը պահպանում են իրենց տեսանյութի կրողը; ցանկացած վերապահված տեքստային թարգմանություն հետևում է վերևում սահմանափակ տեքստի վերափոխմանը: Նպատակները, որոնք ունեն `supportsVideo === true`, շրջանցում են կամուրջը: Հաճախորդի հարցման չեղարկման ազդանշանը տարածվում է ներբեռնում, բրոքերային հերթ, ենթամիջոցներ և ենթագրերի զանգեր; չեղարկումները կանգնում են տեսանյութերի միջև և երբեք չեն բաց թողնում خام մեդիա:

Ռենտայմի կարգավորումները DB-հենված են և Zod-վավերացված:

| Բանալին                             | Նախնական    | Տիրույթ / վարքագիծ                                                                                            |
| ----------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | Ընտրովի ռենտայմ, ընտրովի                                                                                      |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` պահպանում է ընդհանուր ենթագրերը; `focused` օգտագործում է սահմանափակ, անվստահ վերջին-օգտվողի համատեքստը |
| `modalityBridgeVideoModel`          | `""`        | ժառանգել Տեսողության կամրջի մոդելը                                                                            |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                          |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, կամ համաչափ `segment_aware`; հայտնաբերման ձախողումը վերադառնում է `uniform`         |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                           |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                                |

Legacy պահպանված Video timeout արժեքները, որոնք գերազանցում են 120 վայրկյանը, սահմանափակվում են
broker ժամկետով; նոր կարգավորումները, որոնք գերազանցում են այդ սահմանը, մերժվում են.
`GET /api/modality-bridge/video/runtime` պահանջում է վստահ stamped loopback
տեղակայություն նախքան վավերացումը կամ runtime փորձարկումը, ապա պահանջում է կառավարման
ավտորիզացիա: Այն վերադարձնում է միայն `available`, մաքրված FFmpeg/ffprobe տարբերակներ, և
մի ֆիքսված պատճառ, երբ runtime-ը մատչելի չէ: Ներքին հանման վերջնակետը չի
լինում հանրային ներբեռնում API. հերթի հագեցվածությունը վերադարձնում է `503` և `Retry-After`, զանգահարողի
կապը կտրվում է `499`, և ֆիքսված broker ժամկետը վերադարձնում է `504`. Փոխարկված պատասխանները ավելացնում են
`video->text;model=<visionModel>;parts=<videos>` կենտրոնական
`x-omniroute-modality-bridge` գլխում, առանց Vision կամ Audio հատվածների հեռացման:

### PII Masker (`piiMasker.ts`)

Աշխատում է **երկու** փուլերում:

- **`preCall`** կրկնօրինակում է բեռը, անցնում `system`, `messages`, `input`, և
  `prompt` (ներառյալ պարզ տողային տարրեր), և կիրառվում է `processPII()` (ից
  `@/shared/utils/inputSanitizer`) տող `content`/`text` դաշտերի վրա: Երբ
  `PII_REDACTION_ENABLED=true`, հայտնաբերված PII-ն հեռացվում է outbound
  բեռում: Սա անկախ է `INPUT_SANITIZER_MODE`-ից (որը միայն վերահսկում է
  prompt-injection քաղաքականությունը): Երբ հեռացումը անջատված է, զանգը գրանցում է հայտնաբերման
  քանակները առանց բովանդակության վերագրելու:
- **`postCall`** խորքային կրկնօրինակում է պատասխանն, աշխատում է `sanitizePIIResponse()`-ի հետ
  և Responses-API-ձևի masker-ի (`maskResponsesOutput` — ընդգրկում է
  `output_text` և `output[].content[].text`). Եթե որևէ հեռացում տեղի ունենա, ապա
  փոփոխված պատասխանն փոխարինում է սկզբնականին:

Պաշտպանիչ գիծը երբեք չի արգելափակում; այն միայն նշում է (`meta.detections`,
`meta.redacted`) կամ վերագրում:

### Prompt Injection (`promptInjection.ts`)

Հայտնաբերում է հակառակորդական կառուցվածքներ օգտվողի տրամադրած բովանդակության մեջ և պարտադրում
կարգավորված քաղաքականությունը: վարքը ղեկավարվում է միջավայրի փոփոխականներով և կոնստրուկտորի
ընտրանքներով:

| Կարգավորում      | Env var                                                                                                 | Դեֆոլտ | Արդյունք                                                                                                                                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------------------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ակտիվ            | `INPUT_SANITIZER_ENABLED`                                                                               | `true` | Երբ `false`, պաշտպանիչ գիծը կարճացնում է:                                                                                                                                                                       |
| Մոդ              | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                         | `warn` | Injection քաղաքականություն: `block`, `warn`, կամ `log`. (`redact`-ը ընդունվում է հետադարձ համատեղելիության համար, բայց չի հեռացնում injection տեքստը; PII վերագրումը վերահսկվում է `PII_REDACTION_ENABLED`-ով.) |
| արգելափակման շեմ | `blockThreshold` տարբերակ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high` | Արգելափակելու համար անհրաժեշտ նվազագույն ծանրություն: Միջինն դիտարկման միայն է ըստ դեֆոլտի:                                                                                                                     |

**Մոդի առաջնահերթություն** (`getMode`): զանգահարողի `options.mode` →
`INJECTION_GUARD_MODE` **DB ֆունկցիոնալության-flag վերագրում** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. Դashboard-ի վերագրումը, հետևաբար, հաղթում է միջավայրի փոփոխականներին, այնպես որ Feature
Flags UI-ն վերահսկում է գործող պաշտպանիչ գիծը կենդանի (առանց վերագործարկման): DB ընթերցումը անվտանգ է:
եթե այն սխալ է, պաշտպանիչ գիծը վերադառնում է միջավայրի վրա հիմնված վարքին, և երբ ոչ
վերագրում է սահմանված, վարքը նույնն է, ինչ միջավայրի վրա հիմնված լուծումը:

Հայտնաբերման աղբյուրներ:

1. `sanitizeRequest()`-ը `@/shared/utils/inputSanitizer`-ից (համատեղ հայտնաբերման
   հավաքածու, որը օգտագործվում է այլուր խողովակում):
2. Ներառյալ `DEFAULT_GUARD_PATTERNS` (ներկայում `system_override_inline` և
   `markdown_system_block`, երկուսն էլ `high` ծանրությամբ).
3. Ընտրովի `customPatterns`, որոնք փոխանցվում են կոնստրուկտորի ընտրանքներով (տողեր, regex,
   կամ `{ name, pattern, severity }` գրառումներ).

Երբ `mode === "block"` **և** առնվազն մեկ հայտնաբերում համապատասխանում է ծանրության
շեմին, `preCall` վերադարձնում է `{ block: true, message: "Request rejected:
suspicious content detected" }`. `warn`/`log` մոդերում պաշտպանիչ գիծը գրանցում է, բայց
թույլ է տալիս զանգը: Համատեղ օգնական `evaluatePromptInjection()`-ը նույնպես արտահանվում է
զանգահարողների համար, ովքեր պետք է գնահատեն prompts առանց գրանցման միջոցով անցնելու:

**Scan bound (v3.8.20):** հայտնաբերիչը միայն ստուգում է **առաջին 16 KB**-ը
հավաքված prompt տեքստից — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 բայթ)
`src/shared/utils/inputSanitizer.ts`-ում: Երկուսն էլ `detectInjection()` և
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` կատարում են նախքան
պատկերի ցիկլը: Injection ուղղորդումները գտնվում են մուտքի վերևում, այնպես որ սա
սահմանափակում է regex CPU/GC բազմահարյուր-KB բեռների վրա առանց հայտնաբերման թուլացման (cf.
#3932, #4041).

### Credential Masker (`credentialMasker.ts`)

Աշխատում է **երկու** փուլերում, վերջինը նախնական շղթայում (prioritet `95`). Հեռացնում է
լավ հայտնի API-կոդի / գաղտնի-թոքենի ձևաչափերը outbound բեռից (հաղորդագրության
բովանդակություն, գործիք-զանգի արգումենտներ, գործիքի արդյունքներ) **և** մատակարարի պատասխանից, այնպես որ
մատակարարված գաղտնաբառը, որը տեղադրվում է prompt-ում (կամ վերադարձվում է գործիքի արդյունքով), չի արտահոսում
վերևի մատակարարին կամ վերադարձվում հաճախորդին:

- **Միայն համաձայնություն**, նույն կանոնը, ինչ PII-ի մաքրման համար (Hard Rule #20-համապատասխան):
  անջատված, եթե `settings.credentialRedactionEnabled === true` **կամ**
  `CREDENTIAL_REDACTION_ENABLED=true` չէ: Երբ անջատված է, պաշտպանիչ սահմանը ոչ մի գործողություն չի կատարում —
  երբեք չի արգելափակում և երբեք չի վերագրում:
- `redactCredentials()` քայլում է ամբողջ բեռի/պատասխանի ծառով (`walkValue()`,
  պրոտոտիպի աղտոտման անվտանգ, ցիկլային անվտանգ `WeakSet`-ի միջոցով) և փոխարինում է համապատասխանությունները
  `[REDACTED:<type>]` տեղապահով, կրկնօրինակելով միայն այն ճյուղերը, որոնք իրականում
  փոխվել են:
- `CREDENTIAL_PATTERNS` ընդգրկում է LLM մատակարարի բանալիները (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS նշանները (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), վճարման բանալիները (Stripe, Square), ամպի
  բանալիները (AWS մուտքի բանալին, Twilio, SendGrid, Mailgun), մասնավոր բանալիները / JWT-ները,
  հավատարմագրման պարունակող կապի տողերը (`mongodb://user:pass@...`, և այլն), և
  ընդհանուր `Authorization`/`x-api-key`/`api-key`/`apikey` գլխի-արժեքի
  նախշը: Գլխի ձևի բանալիները (`authorization`, `x-api-key`, `api-key`,
  `apikey`) կառուցվածքային կերպով են մաքրվում (միայն արժեքը, սխեմայի նախածանցը, ինչպիսիք են
  `Bearer `/`Basic ` պահպանվում են) ոչ թե ընդհանուր տեքստի regex-ի միջոցով:
- Պաշտպանիչ սահմանը երբեք չի արգելափակում; այն միայն վերագրում է (`modifiedPayload` /
  `modifiedResponse`) և նշում է (`meta.credentialsRedacted`, `meta.count`):

Վերադարձի պաշտպանություն: `tests/unit/credential-masker-guardrail.test.ts`.

## Հիմնական պայմանագիր (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true-ը անմիջապես դադարեցնում է շղթայի կատարումը
  message?: string; // ցուցադրվում է արգելափակման ժամանակ
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // վերադարձվում է preCall-ի կողմից՝ հարցումը վերագրելու համար
  modifiedResponse?: TValue; // վերադարձվում է postCall-ի կողմից՝ պատասխանը վերագրելու համար
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Պաշտպանիչ սահմանափակումը ազդարարում է «փոփոխություն չկա»՝ վերադարձնելով կա՛մ `void`, կա՛մ `{}`, կա՛մ
`{ block: false }`։ `modifiedPayload`/`modifiedResponse` վերադարձնելը փոխարինում է
շղթայով դեպի հաջորդ պաշտպանիչ սահմանափակումներ փոխանցվող արժեքը։
`signal?: AbortSignal`-ը կանչողի կենսացիկլը փոխանցում է պաշտպանիչ սահմանափակումներին։ Հարցման ընդհատումը կանխամտածված fail-open բացառություն է․ մեդիա կամուրջները դադարեցնում են աշխատանքը և մաքրում ռեսուրսները՝ առանց չմշակված մեդիան վերականգնելու այն թիրախի համար, որը, ինչպես հայտնի է, չի աջակցում այն։

## Ռեեստր (`registry.ts`)

`guardrailRegistry` եզակի օրինակը տրամադրում է՝

- `register(guardrail)` — ավելացնում է պաշտպանիչ սահմանափակում (կամ փոխարինում է այն ըստ նորմալացված անվան) և
  վերադասավորում ըստ աճող `priority`-ի։
- `clear()` / `list()` — վարչական օժանդակ մեթոդներ։
- `runPreCallHooks(payload, context)` — հերթով մշակում է ակտիվ պաշտպանիչ սահմանափակումները, փոխանցում է
  payload-ը `modifiedPayload`-ի միջոցով և կանգ է առնում առաջին `block: true`-ի դեպքում։
- `runPostCallHooks(response, context)` — նույն հոսքը պատասխանի կողմում։
- `resetGuardrailsForTests({ registerDefaults })` — մաքրում է վիճակը և, ըստ անհրաժեշտության,
  վերագրանցում է լռելյայնները՝ թեստերի մաքուր մեկուսացման համար։

Երկու գործարկիչներն էլ վերադարձնում են `{ blocked, payload|response, results, guardrail?, message? }`,
որտեղ `results`-ը `GuardrailExecutionResult` գրառումների զանգված է, որոնք ներառում են
յուրաքանչյուր պաշտպանիչ սահմանափակման `blocked`, `skipped`, `modified`, `error` և `meta` դաշտերը,
որոնք օգտակար են հետագծման համար։

### Յուրաքանչյուր հարցման համար պաշտպանիչ սահմանափակումների անջատում

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })`-ը հավաքում է
պաշտպանիչ սահմանափակումների անունների կրկնազերծված ցանկ, որոնք պետք է բաց թողնվեն ընթացիկ
հարցման համար։ Աղբյուրները (բոլորն ընտրովի են, բոլորը միավորվում են)՝

- `apiKeyInfo.disabledGuardrails`
- Հարցման մարմնի `disabledGuardrails` (վերին մակարդակում)
- Հարցման մարմնի `metadata.disabledGuardrails`
- `x-omniroute-disabled-guardrails` վերնագիր (կամ հին
  `x-disabled-guardrails`)

Արժեքները կարող են լինել տողերի զանգվածներ կամ ստորակետերով բաժանված տող․ անունները
նորմալացվում են փոքրատառ kebab-case ձևաչափի (`pii_masker` → `pii-masker`)։ Արդյունքը
`context.disabledGuardrails`-ի միջոցով փոխանցվում է ռեեստրին, որը բաց է թողնում
համապատասխան պաշտպանիչ սահմանափակումները (`skipped: true`՝ `results`-ում)։

## Կատարման հերթականություն

`src/sse/handlers/chat.ts`-ով և
`open-sse/handlers/chatCore.ts`-ով անցնող յուրաքանչյուր հարցման համար՝

1. `resolveDisabledGuardrails(...)`-ը API բանալիից, հարցման մարմնից և
   վերնագրերից կազմում է բաց թողնման ցանկը։
2. `guardrailRegistry.runPreCallHooks(body, ctx)`-ը պաշտպանիչ սահմանափակումները գործարկում է
   առաջնահերթության աճման կարգով՝
   - Անջատված պաշտպանիչ սահմանափակումներն արձանագրվում են որպես `skipped`։
   - Յուրաքանչյուր պաշտպանիչ սահմանափակման `preCall`-ը կարող է վերագրել օգտակար բեռը՝ օգտագործելով `modifiedPayload`։
   - Առաջին `block: true`-ն անմիջապես ընդհատում է շղթան, և մշակիչը վերադարձնում է
     պաշտպանիչ սահմանափակման մերժման պատասխան։
3. Հնարավոր վերագրված օգտակար բեռը փոխանցվում է համակցված երթուղավորմանը և վերին հոսքի
   ուղարկմանը։
4. Պատասխանը կազմելուց հետո `guardrailRegistry.runPostCallHooks(...)`-ը
   պատասխանի վրա գործարկում է նույն շղթան։ Այստեղ `block: true`-ն հեռացնում է վերին հոսքի
   պատասխանը։

Սխալ արձակող պաշտպանիչ սահմանափակումներն արձանագրվում են `error: <message>`-ով և գրանցվում
`logger.warn`-ի միջոցով, սակայն շղթան շարունակվում է. նախագծմամբ կիրառվում է սխալի դեպքում թույլատրելու մոտեցումը։

## Կազմաձևում

Ներկառուցված պաշտպանիչ սահմանափակումների կողմից ընթերցվող միջավայրի փոփոխականները՝

| Փոփոխական                             | Օգտագործվում է             | Ազդեցություն                                                                                                                  |
| ------------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | Հայտնաբերումն ամբողջությամբ անջատելու համար սահմանեք `false`։                                                                 |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | Ներարկման քաղաքականությունը՝ `warn`, `block` կամ `log`։ Հնացած `redact` արժեքը չի վերագրում ներարկման տեքստը։                 |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | Ներարկման պաշտպանիչի ռեժիմը. նաև ՏԲ-ի գործառույթի դրոշակ է, որը **գերակայում է** միջավայրի փոփոխականների նկատմամբ (DB > ENV)։ |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | Նվազագույն խստությունը, որը մերժվում է `MODE=block`-ի դեպքում՝ `high` (լռելյայն), `medium` կամ `low`։                         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD`-ի հնացած այլանունը։                                                                         |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | Երբ `true` է, հարցման PII-ը քողարկվում է՝ անկախ ներարկման ռեժիմից։                                                            |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ներքևի հոսք) | Կառավարում է պատասխանի կողմում քողարկիչի վարքագիծը։                                                                           |

Մոդալության կամրջի պաշտպանիչ սահմանափակումները կատարման ժամանակի կազմաձևումն ընթերցում են ՏԲ-ով ապահովվող կարգավորումների
պահոցից (`getSettings()`), ոչ թե միջավայրի փոփոխականներից։ Պատկերի մշակման հիմնական բանալիներն են՝
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` և
`modalityBridgeCacheMaxEntries`։ Հնացած
`visionBridge*` բանալիներն ընդունվում են միայն որպես փաստաթղթավորված՝ մեկ ցիկլի ընթերցման
պահուստային տարբերակ. կառավարման վահանակից գրանցումները կիրառում են հիմնական բանալիները։ Լռելյայն արժեքները և պահուստային
լուծիչը գտնվում են `src/shared/constants/modalityBridgeDefaults.ts`-ում, իսկ հնացած
հաստատունները պահպանվում են `src/shared/constants/visionBridgeDefaults.ts`-ում։

Ձայնի մշակումն օգտագործում է `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` և `modalityBridgeAudioMaxClips`, ինչպես նաև ընդհանուր
`modalityBridgeCache*` կարգավորումները։ Ձայնի մշակման համար հնացած բանալիների պահուստային տարբերակ չկա, քանի որ այս
բանալիները ներդրվել են Մոդալության կամրջի սխեմայի հետ։

Տեսանյութի մշակումն օգտագործում է `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` և
`modalityBridgeVideoTimeout`, ինչպես նաև ընդհանուր `modalityBridgeCache*` կարգավորումները։
Այն լռելյայն անջատված է, քանի որ FFmpeg/ffprobe-ը ոչ պարտադիր գործառնական
կախվածություններ են, իսկ կադրերի նկարագրությունների ստեղծումն ավելացնում է ուշացումն ու մոդելի օգտագործման արժեքը։

## Հատուկ պաշտպանիչ կանոններ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Քայլեր՝

1. Ստեղծեք `src/lib/guardrails/myGuardrail.ts`՝ ընդլայնելով `BaseGuardrail`-ը։
2. Իրագործեք `preCall`-ը և/կամ `postCall`-ը։
3. Կամ գրանցեք ներմուծման պահին (`registerDefaultGuardrails`-ից ավելացնելով), կամ
   գործարկման ընթացքում կանչեք `guardrailRegistry.register(...)`-ը․ ռեեստրը փոխարինում է
   նույն նորմալացված անունն ունեցող ցանկացած նախորդ պաշտպանիչ կանոն։
4. Ավելացրեք թեստեր `tests/unit/`-ում (առկա օրինակներ՝
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)։

## Թեստավորում

Թեստերի միջև օգտագործեք `resetGuardrailsForTests()`՝ հայտնի վիճակից սկսելու համար։
Փոխանցեք `{ registerDefaults: false }`՝ դատարկ ռեեստրից սկսելու և
միայն թեստավորվող պաշտպանիչ կանոնները գրանցելու համար։ Vision Bridge-ն աջակցում է կախվածությունների
ներմուծմանը (`deps.getSettings`, `deps.callVisionModel`), իսկ Audio Bridge-ը տրամադրում է
համարժեք միջերեսներ՝ կարգավորումների, հնարավորությունների, STT մոդելի ընտրության, հավատարմագրերի
ստուգումների և տրանսկրիպցիայի համար։ Հետևաբար, թեստերը կարող են ստուգել երկու հոսքերն էլ՝ առանց DB-ի
կամ ցանցային հասանելիության։

## Ներարկման պաշտպանիչ կանոնով երթուղիների ծածկույթ և red-team թեստավորում (Փուլ 8 · Բլոկ D)

Ներարկման պաշտպանիչ կանոնը (`createInjectionGuard` / `withInjectionGuard`) ընդգրկում է օգտատիրոջ հուշումներ
ընդունող բոլոր երթուղիները։ Այն հաշվի է առնում `INJECTION_GUARD_MODE`-ը (լռելյայն՝ `warn` = միայն գրանցել մատյանում,
`block` = վերադարձնում է HTTP 400 `SECURITY_001`)։

| Տեսակ        | Երթուղիներ                                                                                                                                           | Լռելյայն ռեժիմ |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| Տեքստ (առկա) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn           |
| Գեներատիվ    | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn           |
| Տվյալներ     | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn           |

Տեքստի արտաբերումը (`extractMessageContents`) ներառում է `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`։

**Red-team (ամեն գիշեր, `nightly-llm-security.yml`)․** promptfoo-ն ստուգում է, որ յուրաքանչյուր երթուղի արգելափակում է
OWASP-LLM կորպուսը `INJECTION_GUARD_MODE=block` ռեժիմում, իսկ garak-ը կատարում է ստուգումներ (գաղտնիքի բացակայության դեպքում՝ բաց է թողնում)։
`moderations`-ը ներառված է հետևողականության համար․ արգելափակման ռեժիմն օգտագործող օպերատորները կարող են այն բացառել
`resolveDisabledGuardrails`-ի միջոցով։

Գիշերային աշխատանքային հոսքը (`.github/workflows/nightly-llm-security.yml`, cron + ձեռքով
գործարկում) ունի երկու առաջադրանք՝

- **`promptfoo-guard` (արգելափակող)** — գործարկում է `promptfoo eval -c promptfooconfig.yaml`-ը
  `INJECTION_GUARD_MODE=block`-ով։ Յուրաքանչյուր հակառակորդային դեպք (օրինակ՝ «անտեսիր բոլոր
  նախորդ հրահանգները…», DAN ոճի jailbreak-ներ) հաստատում է, որ պատասխանը պարունակում է
  `error.code === "SECURITY_001"`, այսինքն՝ պաշտպանիչ կանոնն իսկապես մերժել է հարցումը։
- **`garak` (խորհրդատվական)** — գործարկում է garak-ը `--probes promptinject,dan,leakreplay`-ով
  տեղային OmniRoute օրինակի (`http://localhost:20128/v1`) նկատմամբ։ Պայմանավորված է
  մատակարարի գաղտնիքի (`PROMPTFOO_PROVIDER_KEY`) առկայությամբ․ դրա բացակայության դեպքում առանց սխալի բաց է թողնվում և վերջում
  ունի `|| true`, ուստի այն հաշվետվություն է ներկայացնում՝ առանց CI-ն ձախողելու։

Պաշտպանիչ օգնականի (`createInjectionGuard` / `withInjectionGuard`)
ծածկույթը տարածվում է հուշում պարունակող յուրաքանչյուր `/v1` երթուղու վրա․ հուշման տեքստը վերցվում է
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` դաշտերից՝
`src/shared/utils/inputSanitizer.ts`-ի `extractMessageContents()`-ի միջոցով։
