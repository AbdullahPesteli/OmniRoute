Guardrails អនុវត្តសុវត្ថិភាព គោលការណ៍ និងការបំប្លែងខ្លឹមសារ នៅចំណុចប្រទាក់
រវាង OmniRoute និងអ្នកផ្តល់សេវាខាងដើម។ Guardrail នីមួយៗអាចត្រួតពិនិត្យ (និង
ជាជម្រើស អាចបដិសេធ បំប្លែង ឬបន្ថែមចំណារពន្យល់ទៅលើ) payload សំណើ (`preCall`) និង
ការឆ្លើយតបពីខាងដើម (`postCall`)។

ប្រព័ន្ធនេះមានលក្ខណៈ **fail-open**៖ ប្រសិនបើ guardrail មួយបោះ exception ខណៈពេលប្រតិបត្តិការ registry
នឹងកត់ត្រាកំហុស ហើយបន្តទៅ guardrail បន្ទាប់ ជំនួសឱ្យការធ្វើឱ្យសំណើ
បរាជ័យ។ ការទប់ស្កាត់គឺជាការសម្រេចចិត្តជាក់លាក់ (`block: true`) មិនមែនកើតឡើងដោយចៃដន្យឡើយ។

### ការតភ្ជាប់ទស្សនៈ (`visionBridge.ts`) — ការតភ្ជាប់ម៉ូដាល PR-1

ចាប់យកសំណើដែលមានរូបភាពដែលមានគោលបំណងទៅកាន់ **ម៉ូដែលដែលមិនមានទស្សនៈ** ហើយ
បញ្ជូនសំណើទាំងមូលទៅកាន់ម៉ូដែលដែលអាចទស្សនាបាន ឬជំនួសផ្នែករូបភាព
ជាមួយការពិពណ៌នាអត្ថបទដែលផលិតដោយម៉ូដែលទស្សនាដែលអាចកំណត់បានមុន
ការហៅទៅកាន់អ៊ុតស្ត្រី។ នេះអនុញ្ញាតឱ្យអ្នកផ្តល់អត្ថបទតែមានអាចដោះសោ
ផ្ទុកពហុម៉ូដ។

លំហូរ:

1. ធ្វើការបោះបង់ប្រសិនបើម៉ូដែលគោលដៅមានការគាំទ្រទស្សនៈរួចហើយ (លើកលែងតែវាបង្ហាញនៅក្នុង
   បញ្ជីបង្ខំ-តភ្ជាប់ `isVisionBridgeForcedModel`).
2. ដកផ្នែករូបភាពតាមរយៈ `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), ដែលផ្តល់អំណាចទៅកាន់ **ឧបករណ៍កំណត់មីឌា
   យ៉ាងសាមញ្ញ** `detectMediaParts()` នៅក្នុង `open-sse/utils/mediaParts.ts` — ជាដើមគន្លងតែមួយដែលចែករំលែកជាមួយតម្រងសមាសភាព។
   ការដកគឺអនុញ្ញាតឱ្យមានតែផ្នែកកំពូលនៃរាង
   `replaceImageParts` អាចបញ្ចូលវិញ (កិច្ចសន្យាដក↔ជំនួស): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, និង Responses API `input_image`. ការចាប់ផ្តើមដែលមានសំណុំជាប់គ្នានិង
   រាងតែសញ្ញាគឺជាសម្ភារៈតម្រងសមាសភាព ហើយមិនដែលត្រូវបានដកចេញទេ។
   ធ្វើការបោះបង់ប្រសិនបើមិនមានអ្វីដែលបានរកឃើញទេ។
3. ដោះស្រាយកំណត់រយៈពេលតាមរយៈ `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): កូនសោនៃការកំណត់ `modalityBridge*`
   ថ្មីឈ្នះ; កូនសោនៃការកំណត់ `visionBridge*` ចាស់នៅតែជាការប្រយុទ្ធ **មួយវគ្គ
   ការបង្វិល** (បង្អួតវិនដូ)។ ធ្វើការបោះបង់មុនពេលមានការស្វែងរកមីឌា
   នៅពេលដែលការតភ្ជាប់ត្រូវបានបិទ។
4. ជ្រើសរើសម៉ូដ (`modalityBridgeVisionMode`, មើលតារាងខាងក្រោម) កំណត់
   ការបញ្ជូនឬពិពណ៌នា។ ការបញ្ជូនត្រឡប់មកវិញ `modifiedPayload` ដែលមានតែ `model`
   ត្រូវបានប្តូរ, បូកជាមួយមេតា `{ rerouted, fromModel, toModel, imagesKept }`.
5. ផ្លូវពិពណ៌នា: កំណត់រូបភាពនៅ `maxImages`, រៀបចំការពិពណ៌នាដែលមានការយកចិត្តទុកដាក់,
   ពិនិត្យកាសពិពណ៌នា, ហៅម៉ូដែលទស្សនាអោយ **នៅក្នុងគ្នា**
   (`Promise.allSettled`), ហើយបញ្ចូល `[Image N]: <description>` ផ្នែកអត្ថបទនៅក្នុង
   ទីកន្លែងរបស់ពួកវា។ ការពិពណ៌នាដែលបរាជ័យនឹងផ្តល់នូវ `null` ហើយផ្នែករូបភាពដើមត្រូវបាន
   **រក្សាទុក** (#4012) — លើកលែងតែនៅលើផ្លូវពិពណ៌នាប្រសិនបើការពិពណ៌នាទាំងអស់
   បរាជ័យ, នៅពេលដែលអ៊ុតស្ត្រីដែលបានបញ្ជាក់មិនមានទស្សនៈទទួលបាន
   `(unavailable — no vision-capable provider connected)` stub ជំនួស (#8430).
6. ត្រឡប់មកវិញ `modifiedPayload` + មេតា (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

ោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រកបដោយភាពប្រក ប្រសិនបើវាមានកំហុស, ការពារនឹងត្រឡប់ទៅអាកប្បកិរិយាដែលមានមូលដ្ឋានលើអថេរ, ហើយនៅពេលដែលគ្មាន
ការបញ្ចូលត្រូវបានកំណត់អាកប្បកិរិយាគឺស្មើនឹងការដោះស្រាយតែអថេរបរិស្ថាន។

ប្រភពការរកឃើញ:

1. `sanitizeRequest()` ពី `@/shared/utils/inputSanitizer` (កំណត់អ្នករកឃើញដែលបានចែករំលែក
   ដែលប្រើនៅកន្លែងផ្សេងទៀតក្នុងបណ្តាញ)។
2. `DEFAULT_GUARD_PATTERNS` ដែលមានក្នុង (បច្ចុប្បន្ន `system_override_inline` និង
   `markdown_system_block`, ទាំងពីរមានកម្រិត `high`)។
3. `customPatterns` ជម្រើសដែលបានផ្តល់តាមជម្រើសកសាង (អត្ថបទ, regex,
   ឬ `{ name, pattern, severity }` កំណត់)។

នៅពេល `mode === "block"` **និង** មានការរកឃើញយ៉ាងហោចណាស់មួយដែលបំពេញកម្រិត
កម្រិត, `preCall` ត្រឡប់ `{ block: true, message: "Request rejected:
suspicious content detected" }`។ នៅក្នុងរបៀប `warn`/`log` guardrail ធ្វើការចុះបញ្ជីប៉ុន្តែ
អនុញ្ញាតឱ្យការហៅ។ ជំនួយដែលបានចែករំលែក `evaluatePromptInjection()` ក៏ត្រូវបាននាំចេញ
សម្រាប់អ្នកហៅដែលត្រូវការប៉ាន់ប្រមាណ prompts ដោយគ្មានការឆ្លងកាត់កំណត់ត្រា។

**Scan bound (v3.8.20):** អ្នករកឃើញតែពិនិត្យ **16 KB ដំបូង** នៃ
អត្ថបទ prompt ដែលបានភ្ជាប់ — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 bytes) នៅក្នុង
`src/shared/utils/inputSanitizer.ts`។ ទាំង `detectInjection()` និង
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` មុននឹងដំណើរការលូប។ ការបញ្ជូន
សេចក្តីណែនាំស្ថិតនៅជិតកំពូលនៃការបញ្ចូល, ដូច្នេះនេះកំណត់ CPU/GC regex នៅលើ payloads
ដែលមានមូលដ្ឋានជាងរយៈពេលមួយដោយគ្មានការធ្លាក់ចុះការរកឃើញ (cf.
#3932, #4041)។

### Credential Masker (`credentialMasker.ts`)

រត់នៅលើ **ទាំងពីរ** ជំហាន, ចុងក្រោយក្នុងខ្សែដើមលំនាំ (អាទិភាព `95`)។ លុប
គំរូ API-key / secret-token ដែលគេស្គាល់ពី payload ដែលចេញ (មាតិកាសារ,
អាគុយម៉ង់ការហៅឧបករណ៍, លទ្ធផលឧបករណ៍) **និង** ការឆ្លើយតបពីអ្នកផ្គត់ផ្គង់, ដូច្នេះ
អត្តសញ្ញាណដែលបានបញ្ចូលទៅក្នុង prompt (ឬត្រូវបានបញ្ចេញវិញដោយលទ្ធផលឧបករណ៍) មិនត្រូវបានបង្ហាញ
ទៅអ្នកផ្គត់ផ្គង់ខាងលើឬត្រឡប់ទៅអតិថិជន។

- **តែជ្រើសរើស**, ប្រព័ន្ធដូចគ្នាជាមួយការកាត់បន្ថយ PII (ច្បាប់ក固 #20-ជិត):
  បិទប្រើប្រាស់ទាំងអស់ លុះត្រាតែ `settings.credentialRedactionEnabled === true` **ឬ**
  `CREDENTIAL_REDACTION_ENABLED=true`. នៅពេលវាបិទ, ការពារនេះគឺជាការមិនអនុវត្ត —
  វាមិនដែលរារាំងនិងមិនដែលសរសេរឡើងវិញ។
- `redactCredentials()` ដើរតួជាដើមពេញលេញនៃ payload/response tree (`walkValue()`,
  មានសុវត្ថិភាពប្រភេទ prototype-pollution, មានសុវត្ថិភាពច្រកតាម `WeakSet`) ហើយជំនួសការប្រកួតជាមួយ
  កន្លែងកាន់តែ `[REDACTED:<type>]`, ក cloning តែសាឡាងដែលបានផ្លាស់ប្តូរពិតប្រាកដ។
- `CREDENTIAL_PATTERNS` គ្របដណ្តប់កូនសោ LLM provider (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS tokens (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), កូនសោបង់ប្រាក់ (Stripe, Square), កូនសោពពក
  (AWS access key, Twilio, SendGrid, Mailgun), កូនសោឯកជន / JWTs,
  ស្រទាប់ការតភ្ជាប់ដែលមានកំណត់សិទ្ធិ (`mongodb://user:pass@...`, ល។), និង
  គំរូកូនសោទូទៅ `Authorization`/`x-api-key`/`api-key`/`apikey`
  header-value. កូនសោដែលមានរាង header (`authorization`, `x-api-key`, `api-key`,
  `apikey`) ត្រូវបានកាត់បន្ថយយ៉ាងរឹងមាំ (តែតម្លៃ, ស្គីម prefix ដូចជា
  `Bearer `/`Basic ` ត្រូវបានរក្សាទុក) ជាងតាមរយៈ regex អត្ថបទទូទៅ។
- ការពារនេះមិនដែលរារាំង; វាតែសរសេរឡើងវិញ (`modifiedPayload` /
  `modifiedResponse`) និងបន្ថែមសម្គាល់ (`meta.credentialsRedacted`, `meta.count`)។

ការពារការប្រកួត: `tests/unit/credential-masker-guardrail.test.ts`.

## កិច្ចសន្យាមូលដ្ឋាន (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true បញ្ឈប់ដំណើរការខ្សែសង្វាក់ភ្លាមៗ
  message?: string; // បង្ហាញនៅពេលទប់ស្កាត់
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ត្រូវបានត្រឡប់ដោយ preCall ដើម្បីសរសេរសំណើឡើងវិញ
  modifiedResponse?: TValue; // ត្រូវបានត្រឡប់ដោយ postCall ដើម្បីសរសេរការឆ្លើយតបឡើងវិញ
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Guardrail ផ្តល់សញ្ញាថា «គ្មានការផ្លាស់ប្តូរ» ដោយត្រឡប់ `void`, `{}` ឬ
`{ block: false }`។ ការត្រឡប់ `modifiedPayload`/`modifiedResponse` នឹងជំនួស
តម្លៃដែលហូរឆ្លងកាត់ខ្សែសង្វាក់សម្រាប់ guardrail បន្ទាប់ៗ។
`signal?: AbortSignal` នាំយកវដ្តជីវិតរបស់អ្នកហៅចូលទៅក្នុង guardrail។ ការបោះបង់សំណើគឺជាករណីលើកលែង fail-open ដោយចេតនា៖ ស្ពានមេឌៀនឹងបញ្ឈប់ការងារ និងសម្អាតដោយមិនស្ដារមេឌៀដើមទៅកាន់គោលដៅដែលដឹងថាមិនគាំទ្រវាឡើយ។

## បញ្ជីចុះឈ្មោះ (`registry.ts`)

Singleton `guardrailRegistry` ផ្តល់ជូន៖

- `register(guardrail)` — បន្ថែម guardrail មួយ (ឬជំនួសតាមឈ្មោះដែលបានធ្វើឱ្យមានទម្រង់ស្តង់ដារ) ហើយ
  តម្រៀបឡើងវិញតាម `priority` ពីតូចទៅធំ។
- `clear()` / `list()` — មុខងារជំនួយផ្នែករដ្ឋបាល។
- `runPreCallHooks(payload, context)` — ធ្វើដំណើរឆ្លងកាត់ guardrail ដែលសកម្ម បញ្ជូន
  payload តាមរយៈ `modifiedPayload` ហើយបញ្ឈប់នៅពេលជួប `block: true` ដំបូង។
- `runPostCallHooks(response, context)` — ដំណើរការដូចគ្នានៅផ្នែក response។
- `resetGuardrailsForTests({ registerDefaults })` — សម្អាតស្ថានភាព និងអាច
  ចុះឈ្មោះតម្លៃលំនាំដើមឡើងវិញ ដើម្បីរក្សាភាពដាច់ដោយឡែកស្អាតសម្រាប់ការធ្វើតេស្ត។

Runner ទាំងពីរត្រឡប់ `{ blocked, payload|response, results, guardrail?, message? }`
ដែល `results` គឺជា array នៃ record `GuardrailExecutionResult` ដែលរួមមាន
field `blocked`, `skipped`, `modified`, `error` និង `meta` សម្រាប់ guardrail នីមួយៗ
ដែលមានប្រយោជន៍សម្រាប់ការតាមដាន។

### ការបិទ Guardrail សម្រាប់សំណើនីមួយៗ

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` ប្រមូលផ្ដុំបញ្ជី
ឈ្មោះ guardrail ដែលបានដកធាតុស្ទួន ហើយគួរត្រូវបានរំលងសម្រាប់សំណើ
បច្ចុប្បន្ន។ ប្រភព (ទាំងអស់ជាជម្រើស និងត្រូវបានបញ្ចូលគ្នាទាំងអស់)៖

- `apiKeyInfo.disabledGuardrails`
- `disabledGuardrails` ក្នុង body របស់សំណើ (កម្រិតកំពូល)
- `metadata.disabledGuardrails` ក្នុង body របស់សំណើ
- Header `x-omniroute-disabled-guardrails` (ឬឈ្មោះចាស់
  `x-disabled-guardrails`)

តម្លៃអាចជា array នៃ string ឬ string ដែលបំបែកដោយសញ្ញាក្បៀស; ឈ្មោះត្រូវបាន
បម្លែងឱ្យមានទម្រង់ស្តង់ដារជា kebab-case អក្សរតូច (`pii_masker` → `pii-masker`)។ លទ្ធផល
ត្រូវបានបញ្ជូនតាមរយៈ `context.disabledGuardrails` ទៅ registry ដែលនឹងរំលង
guardrail ដែលត្រូវគ្នា (`skipped: true` ក្នុង `results`)។

## លំដាប់ប្រតិបត្តិការ

សម្រាប់សំណើនីមួយៗដែលឆ្លងកាត់ `src/sse/handlers/chat.ts` និង
`open-sse/handlers/chatCore.ts`៖

1. `resolveDisabledGuardrails(...)` បង្កើតបញ្ជីរំលងពី API key, body
   និង headers។
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ដំណើរការ guardrails តាមលំដាប់
   priority ពីទាបទៅខ្ពស់៖
   - Guardrails ដែលត្រូវបានបិទនឹងត្រូវកត់ត្រាជា `skipped`។
   - `preCall` របស់ guardrail នីមួយៗអាចសរសេរ payload ឡើងវិញតាមរយៈ `modifiedPayload`។
   - `block: true` ដំបូងនឹងបញ្ឈប់ខ្សែដំណើរការភ្លាមៗ ហើយ handler នឹងត្រឡប់
     response បដិសេធពី guardrail។
3. Payload ដែលអាចត្រូវបានសរសេរឡើងវិញ នឹងបន្តទៅកាន់ combo routing និងការបញ្ជូន
   ទៅ upstream។
4. បន្ទាប់ពី response ត្រូវបានរៀបចំរួច `guardrailRegistry.runPostCallHooks(...)`
   នឹងដំណើរការខ្សែដដែលលើ response។ `block: true` នៅទីនេះនឹងបោះបង់
   response ពី upstream។

Guardrails ដែលបង្កើត exception នឹងត្រូវបានកត់ត្រាជាមួយ `error: <message>` និងកត់ត្រា log តាមរយៈ
`logger.warn` ប៉ុន្តែខ្សែដំណើរការនៅតែបន្ត — នេះជាការរចនាបែប fail-open។

## Guardrail ផ្ទាល់ខ្លួន

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ជំហាន៖

1. បង្កើត `src/lib/guardrails/myGuardrail.ts` ដែលពង្រីកពី `BaseGuardrail`។
2. អនុវត្ត `preCall` និង/ឬ `postCall`។
3. ចុះឈ្មោះនៅពេល import (បញ្ចូលពី `registerDefaultGuardrails`) ឬ
   ហៅ `guardrailRegistry.register(...)` នៅពេល runtime — registry នឹងជំនួស
   guardrail មុនណាមួយដែលមានឈ្មោះបានធ្វើ normalization ដូចគ្នា។
4. បន្ថែមតេស្តនៅក្រោម `tests/unit/` (ឧទាហរណ៍ដែលមានស្រាប់៖
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)។
