> **ბოლოს განახლდა:** 2026-08-29 — v3.8.51 (ვიდეო ხიდის ტრანსკრიპტის წარმომავლობა დეკლარირებულია გამომძახებლის მიერ, ჯერ არ არის სერვერის მიერ დამოწმებული — განმარტებულია #11661-ის მიხედვით)

Guardrails უზრუნველყოფენ უსაფრთხოებას, პოლიტიკას და კონტენტის ტრანსფორმაციებს OmniRoute-სა და upstream პროვაიდერებს შორის საზღვარზე. თითოეულ guardrail-ს შეუძლია შეამოწმოს (და სურვილისამებრ უარყოს, გარდაქმნას ან ანოტირება გაუკეთოს) მოთხოვნის payload-ები (`preCall`) და upstream პასუხები (`postCall`).

სისტემა არის **fail-open**: თუ guardrail-ის შესრულებისას შეცდომა მოხდა, რეგისტრატორი აღრიცხავს შეცდომას და აგრძელებს შემდეგ guardrail-ზე, ნაცვლად მოთხოვნის შეწყვეტისა. დაბლოკვა არის მკაფიო გადაწყვეტილება (`block: true`), არასდროს შემთხვევითობა.

### ვიზუალური ხიდი (`visionBridge.ts`) — მოდალობის ხიდი PR-1

შეაჩერებს სურათების შემცველ მოთხოვნებს, რომლებიც მიმართულია **არავიზუალური მოდელების**კენ და ან
გადამისამართებს მთელ მოთხოვნას ვიზუალურად შესაძლებლობების მქონე მოდელზე ან ცვლის სურათის
ნაწილებს ტექსტური აღწერებით, რომელიც წარმოიქმნება კონფიგურირებად ვიზუალურ მოდელზე, სანამ
ზემოთ აღნიშნულ ზარებზე. ეს საშუალებას აძლევს მხოლოდ ტექსტურ პროვაიდერებს გამჭვირვალედ
ხელმძღვანელობენ მრავალმოდალურ დატვირთვებზე.

მიმდინარე პროცესი:

1. გამოტოვეთ, თუ მიზნობრივი მოდელი უკვე მხარს უჭერს ვიზუალურ შესაძლებლობებს (თუ არ ჩანს
   იძულებითი ხიდების სიაში `isVisionBridgeForcedModel`).
2. გამოიტანეთ სურათის ნაწილები `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), რომელიც委托给 **ერთიანი მედია
   დეტექტორი** `detectMediaParts()` `open-sse/utils/mediaParts.ts` — სიმართლე
   ერთადერთი წყარო, რომელიც გაზიარებულია კომბინირებული თავსებადობის ფილტრთან.
   გამოტანა დაშვებულია მხოლოდ ზედა დონეზე ნაწილებზე, რომლებიც
   `replaceImageParts`-ს შეუძლია უკან დააბრუნოს (გამოტანა↔შეცვლა კონტრაქტი): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, და Responses API `input_image`. ჩ Nested hits და
   მხოლოდ ინდიკატორის ფორმები კომბინირებული ფილტრის მასალაა და არასოდეს გამოიტანება.
   გამოტოვეთ, თუ არაფერი მოიძებნა.
3. გადაწყვიტეთ runtime კონფიგურაცია `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): ახალი `modalityBridge*`
   პარამეტრების გასაღებები იგებს; ძველი `visionBridge*` გასაღებები რჩება **ერთი ციკლის
   Fallback** (უკან დაბრუნების ფანჯარა). გამოტოვეთ ნებისმიერი მედიის გავლა, როდესაც
   ხიდი გამორთულია.
4. რეჟიმის არჩევანი (`modalityBridgeVisionMode`, იხილეთ ქვემოთ მოცემული ცხრილი) გადაწყვეტს
   გადამისამართებას თუ აღწერას. გადამისამართება აბრუნებს `modifiedPayload` მხოლოდ `model`
   შეცვლილი, პლუს მეტა `{ rerouted, fromModel, toModel, imagesKept }`.
5. აღწერის გზა: შეზღუდეთ სურათები `maxImages`, შეადგინეთ დავალების ცნობიერი
   მოთხოვნა, კონსულტაციები აღწერის კაშხალთან, გამოიძახეთ ვიზუალური მოდელი **პარალელურად**
   (`Promise.allSettled`), და ჩადეთ `[Image N]: <description>` ტექსტური ნაწილები
   მათ ადგილას. წარუმატებელი აღწერა იძლევა `null` და ორიგინალი სურათის ნაწილი
   **შენარჩუნებულია** (#4012) — გარდა კომბინირებული აღწერის გზაზე, როდესაც ყველა
   აღწერა წარუმატებელია, სადაც დადასტურებული არავიზუალური ზემოთ აღნიშნული იღებს
   `(unavailable — no vision-capable provider connected)` stub-ის ნაცვლად (#8430).
6. დააბრუნეთ `modifiedPayload` + მეტა (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### API-კი სქემა (`visionBridgeKeyScope.ts`)

როდესაც გამიძახებლის API გასაღები ზღუდავს `allowedConnections`, კვოტის აუზებს
(`allowedQuotas`) ან მოდელებს (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), ხიდი მხოლოდ
არჩევს გადამისამართების და აღწერის მოდელებს, რომლებიც გასაღები შეიძლება გამოიყენოს, იმ
კავშირებზე, რომლებიც გასაღები შეიძლება გამოიყენოს. აღწერის ზარი მაშინ ყოველთვის გადის OmniRoute თვით-ციკლზე
`x-omniroute-self-loop-key-id` სათაურით, ასე რომ, მიღებული ჩათვის მოთხოვნა
მორიგებს იმ გასაღების კავშირს და მოდელის პოლიტიკას კვლავ. `enforceApiKeyPolicy()`
ამოწმებს ამ სათაურს მხოლოდ თვით-ციკლის მატარებელთან ერთად, ასე რომ, ის მხოლოდ
შეიძლება შეამციროს წვდომა, და id, რომელიც არ იძებნება, უარყოფილია.

თუ ვიზუალური მოდელი არ არის დაშვებული გასაღებისთვის, აღწერის გზა გვერდზე გადადის და
მოთხოვნა უცვლელად გადის, იგივე წარუმატებელი ღია ქცევა როგორც გამორთული
დაცვა (მეტა `{ skipped: true, reason: "no_permitted_vision_model" }`).
მოთხოვნები, რომლებიც არ აქვთ გასაღები, და გასაღებები, რომლებსაც არ აქვთ ეს შეზღუდვები, მოქმედებენ ზუსტად ისე, როგორც ადრე.

#### დავალების ცნობიერი აღწერის მოთხოვნა (`modalityBridgeVisionTaskAware`)

Default **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) ამატებს
**ბოლო მომხმარებლის შეტყობინების** ტექსტს (500 სიმბოლომდე შეზღუდული) ბაზის
აღწერის პრომტში, აღწერას მიმართავს იმაზე, რაც მომხმარებელმა რეალურად მოითხოვა
(codex-vision-proxy pattern) და ითხოვს ვიზუალური მოდელისგან ხილული
ტექსტის ტრანსკრიბირებას. დროშის გამორთვის შემთხვევაში — ან მომხმარებლის ტექსტის
არარსებობისას — ბაზის პრომტი უცვლელად გამოიყენება.

აღწერის თვითციკლის საკუთარი OpenAI-თან თავსებადი მოთხოვნა (`callVisionModelSingle()`
`visionBridgeHelpers.ts`-ში) ყოველთვის ითხოვს `image_url.detail: "high"` —
არასოდეს, ყველა გამწვდელის/მომწვდელისათვის, არ არის დამოკიდებული
მომხმარებლის სიგნალზე. დაბალი დეტალების ნიმუშის აღება ამცირებს OCR-ის
სიზუსტეს იმ ტექსტის ტრანსკრიბირების დავალებისათვის, რაც ამ პრომტში
ითხოვება, ამიტომ აღწერის ზარი ყოველთვის ითხოვს მაღალ დეტალს, მიუხედავად
ისეთის დეტალების დონე, რაც თავდაპირველ შემომავალი მოთხოვნაში გამოიყენებოდა.
ეს მხოლოდ გავლენას ახდენს შიდა აღწერის მოთხოვნის სხეულზე; ეს არ ცვლის
როგორ აგზავნის OmniRoute გამწვდელის საკუთარ `image_url.detail` პირველ
მოთხოვნაზე — ეს დეფოლტი ცალკე გამოიყენება და მხოლოდ აღმოჩენილი OpenCode
მომხმარებლებისათვის, `defaultImageDetail()`-ში (`open-sse/handlers/chatCore/upstreamBody.ts`).
Anthropic-ის ვაირ-ფორმატის შტო აღწერის თვითციკლში არ შეიცავს `detail`
ველს და არ ექვემდებარება არცერთ დეფოლტს.

#### აღწერის გამოსვლის ზღვარი (`modalityBridgeVisionMaxChars`)

| გასაღები                       | დეფოლტი | დიაპაზონი        |
| ------------------------------ | ------- | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`     | `0` ან 100–50000 |

`0` (დეფოლტი) ნიშნავს **არანაირ ზღვარს** — `callVisionModel()`-ის მიერ
დაბრუნებული აღწერა გადადის უცვლელად, არსებული ქცევის შენარჩუნებით. ნებისმიერი
მნიშვნელობა 100–50000 დიაპაზონში აღწერას შეზღუდავს `…` სუფიქსით, სანამ
ის კვლავ არ გაწვდება როგორც `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` `src/lib/guardrails/visionBridge.ts`-ში).
ამას უნდა გაზარდოთ დეტალებით დატვირთული OCR დავალებებისათვის, სადაც
ქვედა მოდელს სრული ტრანსკრიბირება სჭირდება; შეამცირეთ, რომ
ტოკენის გამოყენება შეზღუდოს საუბრული ვიზუალური მოდელებისათვის.
დაშბორდის ველი Vision-ის ჩანართის მოწინავე პანელში
(`modality-bridge-max-chars` `ModalityBridgeVisionTab.tsx`-ში) ცხოვრობს და
შეიზღუდება ნებისმიერი მნიშვნელობა 1 და 99 შორის 100-ის სართულზე, ხოლო
მიუხედავად ამისა, ექსპლიციტური `0` უცვლელად რჩება — `0` არის
ვალიდური Zod მნიშვნელობა თავისთავად
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), არა მხოლოდ
"არასრული" დეფოლტი.

#### აღწერის კეში (`modalityBridge/bridgeCache.ts`)

მეხსიერების LRU + TTL კეში აღწერის გამოსვლებისათვის, საერთო პროცესში.
გასაღები = `sha256(imageRef + composedPrompt + configuredBridgeModel)` სიგრძის
პრეფიქსით ჩარჩოებით (არანაირი ველის საზღვრის შეჯახება). მოდელის კომპონენტი არის
**კონფიგურირებული** ხიდის მოდელი, არა მოდელი, რომელიც რეალურად პასუხობს —
`callVisionModel` შეიძლება შიდა fallback-ით იმოქმედოს, და გასაღების
ყოველი მცდელობის მიხედვით ფრაგმენტირება მოახდინოს კეში. წარუმატებელი
აღწერები არასოდეს ინახება. პარამეტრები:

| გასაღები                        | დეფოლტი | დიაპაზონი |
| ------------------------------- | ------- | --------- |
| `modalityBridgeCacheEnabled`    | `true`  | —         |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440    |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000   |

#### შორეული გამოსახულების ნორმალიზაცია (თვითციკლური აღწერა/base64 გადმოწერა)

როდესაც ხიდი **შორეულ** გამოსახულებას თავად იღებს — Anthropic-ის აღწერის
თვითზარი და claude-wire-format base64 გარდაქმნა
(`ensureBase64ImagesForClaudeWire`), ორივე
`fetchRemoteImageAsDataUri()`-ის მეშვეობით `visionBridgeHelpers.ts`-ში —
შედეგი მონაცემთა URI გადადის `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`)-ში, სანამ ის ჩადებულია
ვიზუალური მოდელის მოთხოვნაში. გადაჭარბებული გამოსახულებები
**2048px გრძივი კიდეზე** (რომელიც ემთხვევა OpenAI/Anthropic-ის მიერ
მომსახურების მხარეს უკვე გამოყენებულ ზომის ზღვარს) შემცირდება, რაც
წყვეტს ატვირთვის ბაიტებს/ლატენტობას, ვიზუალური მოდელის ხედვის
შეცვლების გარეშე. ზომის შეცვლა იყენებს `sharp`, რომელიც დინამიურად
იმპორტირდება: პლატფორმაზე, სადაც მისი ადგილობრივი ბინარი ვერ იტვირთება,
`normalizeDataUri()` **არასოდეს ისვრის** — ის უკან დაბრუნდება
ორიგინალური ბაიტების გადაცემით, ასე რომ აღწერა/base64-გარდაქმნის
პატარა გზა ყოველთვის მუშაობს. არ გამოსახულების ბაიტები (გადმოწერა,
რომელიც არ დაბრუნდა დეკოდირებადი გამოსახულება) ასევე გადადის
უცვლელად. ეს ნორმალიზაცია შეზღუდულია იმ გამოსახულებებზე, რომლებიც ხიდი
იღებს საკუთარი თვითზარისათვის — ეს არასოდეს გამოიყენება
გამწვდელის ნედლი გადაცემული დატვირთვისათვის, რაც შეესაბამება
მხოლოდ ოპტ-ინ მუტაციის პრინციპს (Hard Rule #20).

#### გამჭვირვალობის სათაური + სტატისტიკა

აღწერის გარდაქმნილი პასუხები ატარებენ
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(`buildModalityBridgeHeader()`-ით `modalityBridge/bridgeStats.ts`-ში,
`withModalityBridgeHeader()`-ით `src/sse/handlers/chatHelpers.ts`-ში).
გადამისამართებული მოთხოვნები **არ** იღებენ სათაურს — დატვირთვა უცვლელია და
მოდელის შეცვლა უკვე ჩანს პასუხის სხეულის `model` ველში.

`GET /api/modality-bridge/stats` (მმართველობის ავტორიზაცია, იგივე დონეზე როგორც
`GET /api/settings`) აბრუნებს მეხსიერებაში არსებული თითოეული მოდალობის
კაუნტერებს `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` `vision`, `audio`, და
`video`-სთვის. `averageLatencyMs` იყენებს `latencySamples`, არა ყველა მცდელობას, როგორც
მის denominator; ოპერაცია, რომელიც დროის გარეშეა, არ ქმნის ნულ-მილიწამიან
ნიმუშს. `bridged` რჩება უკუკავშირით თავსებად ალტერნატივად წარმატებული
კონვერსიებისთვის; წარუმატებელი მცდელობები არ ზრდიან მას.
კაუნტერები პროცესის ხელახალი დაწყებისას ნაგულისხმევად
(ტელემეტრია, არა ანგარიშგება) ნულდება.

#### დაფის კონფიგურაცია

მიუღებელი დაფის გვერდი არის
`/dashboard/settings/modality-bridge`. მისი URL-მისამართით `Vision`, `Audio`,
და `Video` ტაბები ინარჩუნებენ შეკითხვის პარამეტრებს `tab` მნიშვნელობის
შეცვლისას. Vision ტაბი აჩვენებს აქტივაციას, რეჟიმს, მოდელის არჩევანს (მათ შორის
ავტომატურ ნაგულისხმევს), დავალების ცნობიერების პრომპტინგს, მოწინავე
დროის/სურათის/აღწერის სიგრძის/კეშის შეზღუდვებს, გაწვდილი
კაუნტერებს და დაცულ ნიმუშის მოთხოვნას. Audio ტაბი ასევე ცოცხალია: ის აჩვენებს
აქტივაციას, STT- მხოლოდ მოდელის არჩევანს Auto, დროის/მაქსიმალური კლიპის
შეზღუდვებს, აუდიო კაუნტერებს და `input_audio` ნიმუშის ტესტს. Video ტაბი
ფუნქციონირებს: ის იტყობინება FFmpeg/ffprobe გაწვდილი მდგომარეობის შესახებ — ოთხი
სპეციფიური UI მდგომარეობის ერთ-ერთი (`unknown`, როდესაც
პრობლემა ფრენაშია ან ვერ დასრულდა, `restricted` არ-ლუპბექ
დაფის მასპინძელზე, სადაც პრობლემა გამოტოვებულია კლიენტ-გვერდზე, `unavailable`
ერთხელ გამოკვლეული და დადასტურებული დაკარგულია, ან `available` FFmpeg/ffprobe
ვერსიებით) — ინარჩუნებს აქტივ/მოდელ/ფრეიმ/ვიდეო/დროის შეზღუდვებს, ფილტრავს
მოდელის არჩევანს ვიზუალური შესაძლებლობების მქონე მოდელებზე და აჩვენებს
ვიდეო კაუნტერებს.

ყოფილი Vision Bridge ბარათი AI პარამეტრებში არის თავსებადობის ბმული
ახალ გვერდზე; ის აღარ ფლობს ფორმის მეორე ასლს. მედია პროვაიდერები ასევე
ბმულობენ სურათიდან ტექსტში და სიტყვიდან ტექსტში სამუშაო პროცესებს
Corresponding Modality Bridge ტაბებზე, არსებული სიტყვიდან ტექსტში
თამაშის გარეშე.

**თვით-ციკლის მიღების გვერდის ავლა:** როდესაც აღწერის გამოძახება OmniRoute-ის

`sk_omniroute` სენტინელით ადგილობრივ რეჟიმში, ან ოპერატორის მიერ
კონფიგურირებული `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env გასაღებით (#1350),
ასე რომ `REQUIRE_API_KEY=true` განლაგებები კვლავ შეუძლიათ
აღწერის გამოძახების გაწვდვა. გვერდის ავლა მხოლოდ იმ ზუსტ სერტიფიკატებზე
იქნება პატივცემული, ამიტომ გარე კლიენტები ვერ გამოიყენებენ

### აუდიო ბრიჯი (`audioBridge.ts`) — მოდალობის ბრიჯი PR-3

შეაჩერებს აუდიო-შევსებულ ჩატ მოთხოვნებს სანამ ისინი მიაღწევენ
მიზანს, რომელიც არ არის ცნობილი აუდიო შესვლის მიღებაზე. ის არასდროს
გადამისამართებს ჩატ მოთხოვნას: აუდიო ნაწილები
გადაიწერება არსებული OpenAI-თან თავსებადი მრავალმხრივი
ბოლო წერტილზე და არჩეული ჩატ მოდელი აგრძელებს ტექსტური
ტრანსკრიპტებით.

მიმდინარე პროცესი:

1. გადაწყვიტეთ `supportsAudio` `getResolvedModelCapabilities()`-ის
   საშუალებით. ექსპლიციტური პროვაიდერის რეგისტრაციის მეტადატა
   იგებს, შემდეგ სტატიკური მოდელის მეტადატა, შემდეგ სინქრონიზებული
   `modalities_input`. დეკლარირებული შესვლის სია, რომელიც არ შეიცავს
   `audio`, არის `false`; არანაირი შესაძლებლობის მტკიცებულება რჩება
   `null`. როგორც `false`, ისე `null` აქტივირებს
   კონსერვატიულ ბრიჯს, ხოლო `true` გვერდს უვლის.
2. გადაწყვიტეთ `modalityBridgeAudio*` პარამეტრები და გამოიტანეთ
   გაწვდილი უმაღლესი აუდიო ნაწილები თითოეული შეტყობინებიდან
   საერთო `detectMediaParts()` დეტექტორის საშუალებით. მხარდაჭერილი
   მავთულოვანი ფორმები არიან OpenAI `input_audio`, `audio_url`, და
   `source.media_type: "audio/*"`. ნესტირებული აუდიო
   აღმოჩენილია მარშრუტისთვის, მაგრამ არ არის ამოღებული
   გაწვდილი გზით. სამუშაოს ზღვარი არის `modalityBridgeAudioMaxClips`;
   შემდგომი ნაწილები რჩება შეუცვლელი.
3. პატივისცემა კონფიგურირებული `provider/model`, ან
   დაუშვით `selectAudioBridgeModel()`-მა გაიაროს
   `AUDIO_TRANSCRIPTION_PROVIDERS` სტაბილური კატალოგის წესით და
   აირჩიოს პირველი მოდელი, რომელსაც აქვს გამოსაყენებელი აქტიური
   პროვაიდერის სერტიფიკატი.
4. `callAudioTranscription()` გარდაქმნის base64/data-URI აუდიოს
   მრავალმხრივ `file`-ად, ან ჩამოტვირთავს შორეულ `audio_url`
   საჯაროდ მხოლოდ გასვლის დაცვით DNS-ით და 25 MB-ის ზღვარით. შემდეგ
   ის POST-ით აგზავნის ფაილსა და არჩეულ მოდელს ადგილობრივ
   `/v1/audio/transcriptions` თვით-ციკლზე, ავტორიზებული
   `resolveSelfLoopBearer()`-ით. არსებული ტრანსკრიპციის მარშრუტი
   ასრულებს ჩვეულებრივ სერტიფიკატის ძიებას, გაგრილების/ტარიფის
   მართვას და პროვაიდერის გადაცემას.
5. წარმატებული გამოძახებები ცვლიან თავიანთ ნაწილებს `[Audio N]: <transcript>`. გამოძახებები
   მუშაობენ `Promise.allSettled`: ინდივიდუალური წარუმატებლობა
   ინარჩუნებს იმ ორიგინალურ აუდიო ნაწილს (#4012 კონტრაქტი). თუ
   ყოველი გამოძახება წარუმატებელია და მიზანი დადასტურებულია
   `supportsAudio === false`, ნაწილები ხდება
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 კონტრაქტი). უცნობ
   მიზანზე (`null`), ყველა წარუმატებელი შედეგი რჩება შეუცვლელი. დადასტურებული
   ტექსტური მიზანი, რომელსაც არ აქვს გამოსაყენებელი STT სერტიფიკატი,
   იღებს იმავე ექსპლიციტურ სტაბს, ქსელის გამოძახების გარეშე.

წარმატებული ტრანსკრიპტები იყენებენ პროცესის ფართო მოდალობის ბრიჯის LRU/TTL
კეშს. გასაღები აერთიანებს აუდიო მითითებას, სტაბილურ `audio-transcription`
ოპერაციის ლეიბლს და არჩეულ STT მოდელს; წარუმატებლობები არასდროს
კეშდება. აუდიო მცდელობები განაახლებენ საერთო `bridged`, `cacheHits`, `failures`, და
`lastUsedAt` კაუნტერებს. გარდაქმნილი პასუხები ატარებენ
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; შეუცვლელი
მოთხოვნები არ იღებენ აუდიო ბრიჯის სექციას.

გადამწყვეტი პარამეტრები არის DB-ით მხარდაჭერილი და Zod-ით
ვალიდირებული:

| გასაღები                      | ნაგულისხმები | დიაპაზონი            |
| ----------------------------- | ------------ | -------------------- |

| `modalityBridgeAudioModel`    | `""`         | ავტომატური ან STT ID |

გაზიარებული კეში კონტროლდება `modalityBridgeCacheEnabled`,

### ვიდეო ბრიჯი (`videoBridge.ts`, `videoBridgePipeline.ts`)

შეიჭრება უმაღლესი დონეების ვიდეო ნაწილებში ჩათვის დასრულებებში `messages` და პასუხების

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) ფლობს მოთხოვნის გავლას,

მეტრიკა/გაუქმება/წმენდა — დაფარულია `processVideoPart`-ში
`videoBridgePipeline.ts`, რომელიც იწვევება თითოეული ვიდეო ნაწილისთვის `preCall`-ის ციკლის შიგნით.

(ბაიტების შეძენა და ნიმუშების ჩარჩოების ამოღება), `VideoAudioTranscriptionPort`
(გამხმოვანებლის მიერ გამოცხადებული აუდიო ტრანსკრიპტის გაწვდვა ნიმუშური სათაურებისთან ერთად), და
`VideoDrilldownPort` (ძველი ნედლეულის ფორმატი). წარმოების STT და ჩარჩოს შენახვა

`createVideoDrilldownAdapter`-ის საშუალებით; უკანასკნელი იყენებს გაზიარებულ მუქი-ხელის სიცოცხლის ციკლს.

#### FU-07 სტრუქტურული სექციის მტკიცებულება

`segment_aware` იყენებს ერთ შეზღუდულ წინასწარ ანალიზის გადაცემას უკვე ვალიდირებული ადგილობრივი ვიდეო ნაკადის. ფიქსირებული ფილტრის ჯაჭვი პირველად ზომავს მაქსიმუმ 320 პიქსელს სიგანეში, აღმოაჩენს სცენის ცვლილებებს და გაყინულ ინტერვალებს, შემდეგ კი 1 კადრს წამში ნიმუშებს იღებს ბუნდოვანების, საშუალო ლუმას და სივრცული/დროითი ინფორმაციისთვის. გადაცემა შეზღუდულია 600 სტრუქტურული ნიმუშით, ერთი FFmpeg/filter ნაკადით, იმავე `file`-მხოლოდ პროტოკოლით და კონტეინერის ნებართვებით, 1 MiB პროცესის-გამოსვლის საზღვრით და მაქსიმუმ 30 წამით ბროკერის საერთო გაწყვეტის/დედლაინში. იგი არასდროს იღებს ბრძანებას, ფილტრს, გზას ან URL-ს მოთხოვნიდან.

სტრუქტურული მნიშვნელობები არის დეტერმინისტული ნიმუშების მტკიცებულება, არა სემანტიკური ვიდეო გაგება. ისინი არ განსაზღვრავენ სუბიექტებს, მოქმედებებს, წარწერებს, მეტყველებას ან მომხმარებლის ნებას. სცენის და გაყინული საზღვრები ქმნიან სექტორებს; გაყინული დაფარვა, ბუნდოვანება, ექსპოზიცია, სივრცული დეტალი და დროითი ცვლილება მხოლოდ გავლენას ახდენს იმაზე, როგორ არის გამოყოფილი არსებული 1–16 კადრის ბიუჯეტი. სრულად გაყინული სექტორი შეზღუდულია ერთ კადრამდე, ხოლო არაგაყინული სექტორები კონკურენციას უწევენ დარჩენილ ბიუჯეტზე. როდესაც საზღვრები კადრებს აღემატება, ერთგვაროვანი დროის ხაზის დაფარვა შენარჩუნებულია, რათა სწრაფი ადრეული გაწყვეტები ვერ დამალონ გრძელი კვალის სექტორი. სცენის საზღვრები 1-წამიანი ანალიზის რეზოლუციის ფარგლებში გაყინული საზღვრის ფარგლებში გაწვდილი არიან.

მოსული ფილტრები, ფორმატირებული/ცარიელი მტკიცებულებები, დეტექტორის შეცდომა ან შეზღუდული წინასწარი ანალიზის დროის გასვლის შემთხვევაში, იხსნება ზუსტად ერთგვაროვანი შუა პოლიტიკისთვის. გამიძახებელი გაწყვეტა ან ბროკერის დედლაინი არ იხსნება: იგი ასრულებს მიმდინარე სუბპროცესს, ხელს უშლის შემდგომ კადრების ამოღებას და კერძო დროებითი ხე იხსნება `finally`-ში.

`scripts/perf/video-bridge-fu07-eval.ts` გენერირებს დეტერმინისტულ რეალურ FFmpeg მოწყობილობებს პოსტ-დედუპლიკაციის წარწერების ხარჯების დაზოგვისთვის, მჭიდრო მოძრაობის ბიუჯეტის განაწილებისთვის, ბუნდოვანების/ექსპოზიციის/SI-TI მტკიცებულებების, სწრაფი გაწყვეტების გრძელი კვალით და ნელ-ნელა გაქრობის ყალბი დადებითი შედეგებისთვის. იგი აღრიცხავს წინასწარი ანალიზის კედლის დროს და, სადაც `/usr/bin/time` ხელმისაწვდომია, შვილობილი CPU და პიკი RSS. მისი ხარისხის შემოწმებები მხოლოდ სტრუქტურული ორკაკლებია. რეალური წარწერის მოდელის ხარისხი რჩება `HOLD`, რადგან ეს მოწყობილობა არ აქვს ავტორიზებული ბოლო წერტილი ან გაყინული მსაჯი. ფინანსური დაზოგვები ასევე რჩება `HOLD`, თუ `--caption-cost-per-call-usd` არ აწვდოს კონკრეტული დადებითი თითო-ზარის შეფასება; სკრიპტი არასდროს ქმნის არც ერთ შედეგს.

ყოველი კადრი შეზღუდულია 4 MiB-მდე, ყველა خام კადრი ერთად 23 MiB-მდე და სერიული ბროკერის პასუხი 32 MiB-მდე. კერძო დროებითი დირექტორია იხსნება `finally`-ში. **ნედლი ვიდეო ველები (#12430).** როდესაც ხიდი ჩართულია და ადგილობრივი ვიდეო მხარდაჭერა უცნობია ან არ არის,

ამFallback გზებზე, ვალიდური ზარის სიგნალები ხდება მხარდაჭერილი `text`/`input_text` ნაწილები, ნაცვლად არასტანდარტული პროვაიდერის ველების. ორივე მოთხოვნით მიწვდილი ტრეკი რჩება დაუმოწმებელი `client` დაკვირვებები, explicit გაფრთხილებით, რომ ვიდეო არ იყო აღწერილი და დროის ნიშნები არ იყო გადამოწმებული მედიის წინააღმდეგ. არსებული 256-სიგნალი/64-KiB საერთო და თითოეული სიგნალის ბიუჯეტები ვრცელდება ორივე ტრეკზე ერთად; დროის ნიშნები უნდა მოერგოს ბროკერის 600-წუთიან ჭერს და ნებისმიერ მიწვდილ ფოკუსის ფანჯარას. არвалидური ტრეკები გადაყრილია, არ გადაეცემა როგორც შემთხვევითი ტექსტი; ვალიდური ძმა შეიძლება კვლავ გამოყენებულ იქნას, თუ მათი გაწვდილი ბიუჯეტი არ არის გადაჭარბებული. ნულოვანი/ცარიელი ველები არ ამატებენ ტექსტს. ამFallback-ით არ ემატება მედიის გადმოწერა ან ტრანსკრიფცია. ტრანსკრიპტის გაფართოების ველები ამოიღებაFallback ვიდეო გადამზიდიდან და მისი `video_url`/`source` ობიექტებიდან. OpenAI-ის ქსელის ნებართვის სია რჩება მკაცრი; უცნობი-ნატურალური ვიდეო გადამზიდები რჩება ხელმისაწვდომი და ცნობილი ტექსტის მხოლოდ მიზნები ინარჩუნებენ უსაფრთხო მარკერებს. სტრუქტურირებული რედაქციის ჩრდილები იცავს დამატებულ ტრანსკრიპტის ტექსტს, ხოლო ორიგინალური ზარის საკუთრებაში არსებული მოთხოვნა უცვლელი რჩება. ნატურალურად მხარდაჭერილი მიზნები და გამორთული ხიდები ინარჩუნებენ თავიანთ არსებულ გვერდის გავლას.

დაკვირვებული მოთხოვნისთვის, მოდელის პასუხი შეიძლება ციტირებდეს ტრანსკრიპტის ნებისმიერ ნაწილს სტრუქტურული სიგნალის საზღვრის გარეშე. მისი შენახული ზარის-ლოგი `responseBody` ამიტომ იცვლება გამოტოვების მარკერით; დეტალური pipeline არტეფაქტი (რომელიც შეიძლება მოიცავდეს ზედა/კლიენტის სხეულებს და ნაკადების ნაწილებს) არ ინახება. სემანტიკური, იდემპოტენტობის და მიზეზების-გადმოწერის კეშები გვერდს უვლიან ამ მოთხოვნის წაკითხვას და წერის პროცესს. პროვაიდერის მოთხოვნა და კლიენტისთვის ხილული პასუხი უცვლელი რჩება. ადრეული keepalive ბაიტები იწოვება დროებით ბუფერში, როდესაც დეტალური არტეფაქტი გამოტოვებულია. დაცვა extracts ყველა მხარდაჭერილი ვიდეო ნაწილს, მაგრამ აღწერს არა მეტს, ვიდრე `modalityBridgeVideoMaxVideos`. მიზანზე, რომელიც დადასტურებულია, რომ აქვს `supportsVideo === false`, წარუმატებელი და ზედმეტი ვიდეოები ხდება ექსპლიციტური უსაფრთხო ტექსტური მარკერები, ასე რომ არანაირი ნედლი ვიდეო არ გადარჩება. როდესაც შესაძლებლობა უცნობია, ეს ნაწილები ინარჩუნებენ მათ ვიდეო გადამზიდს; ნებისმიერიFallback ტრანსკრიპტი მიჰყვება ზემოთ აღწერილ შეზღუდულ ტექსტურ კონვერტაციას. მიზნები, რომლებსაც აქვთ `supportsVideo === true`, გვერდს უვლიან ხიდს. კლიენტის მოთხოვნის გაწყვეტის სიგნალი ვრცელდება ჩამოტვირთვაში, ბროკერის რიგში, სუბპროცესებში და სათაურების გამოძახებებში; გაწყვეტები შეჩერდება ვიდეოებს შორის და არასოდეს გაიფუჭება ნედლ მედიისკენ.

რეგისტრაციის პარამეტრები DB-ით მხარდაჭერილი და Zod-ით ვალიდირებული:

| გასაღები                            | დეფოლტი     | დიაპაზონი / ქცევა                                                                                         |
| ----------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | სავალდებულო runtime, ოპტ-ინ                                                                               |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` ინარჩუნებს ზოგად სათაურებს; `focused` იყენებს შეზღუდულ, არამტკიცებულ ბოლო-გამოყენების კონტექსტს    |
| `modalityBridgeVideoModel`          | `""`        | მემკვიდრეობით იღებს ხედვის ხიდის მოდელს                                                                   |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                      |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, ან პროპორციული `segment_aware`; დეტექტორის წარუმატებლობა უკუქცდება `uniform`-ზე |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                       |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                            |

Legacy persisted Video timeout values above 120 seconds are clamped to the
broker deadline; new settings writes above that limit are rejected.
`GET /api/modality-bridge/video/runtime` requires trusted stamped loopback
locality before authentication or runtime probing, then requires management
auth. It returns only `available`, sanitized FFmpeg/ffprobe versions, and a fixed
reason when the runtime is unavailable. The internal extraction endpoint is not
a public upload API: queue saturation returns `503` plus `Retry-After`, a caller
disconnect returns `499`, and the fixed broker deadline returns `504`. Converted responses add
`video->text;model=<visionModel>;parts=<videos>` to the central
`x-omniroute-modality-bridge` header without removing Vision or Audio segments.

### PII Masker (`piiMasker.ts`)

მუშაობს **ორივე** ეტაპზე.

- **`preCall`** კლონავს დატვირთვას, გადის `system`, `messages`, `input`, და
  `prompt` (მათ შორის უბრალო სტრინგის ელემენტები), და იყენებს `processPII()` (განაცხადიდან
  `@/shared/utils/inputSanitizer`) სტრინგ `content`/`text` ველებზე. როდესაც
  `PII_REDACTION_ENABLED=true`, აღმოჩენილი PII წაიშლება გასულ
  დატვირთვაში. ეს დამოუკიდებელია `INPUT_SANITIZER_MODE`-დან (რომელიც მხოლოდ აკონტროლებს
  prompt-injection პოლიტიკას). როდესაც წაშლა გამორთულია, ზარი აღრიცხავს აღმოჩენის
  რაოდენობებს შინაარსის გარეშე.
- **`postCall`** ღრმად კლონავს პასუხს, ატარებს `sanitizePIIResponse()` და
  Responses-API-ს ფორმის მასკერს (`maskResponsesOutput` — მოიცავს
  `output_text` და `output[].content[].text`). თუ რაიმე წაშლა ხდება,
  შეცვლილი პასუხი ცვლის ორიგინალს.

დაცვა არასოდეს ბლოკავს; ის მხოლოდ ანოტირებს (`meta.detections`,
`meta.redacted`) ან ხელახლა წერს.

### Prompt Injection (`promptInjection.ts`)

აღმოაჩენს მტრულ სტრუქტურებს მომხმარებლის მიერ მიწვდილი შინაარსში და ახორციელებს
კონფიგურირებულ პოლიტიკას. ქცევა მართვადია გარემოს ცვლადებით და კონსტრუქტორის
ოპციებით:

| პარამეტრი          | გარემოს ცვლადი                                                                                                  | ნაგულისხმები | ეფექტი                                                                                                                                                                                                        |
| ------------------ | --------------------------------------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ჩართული            | `INPUT_SANITIZER_ENABLED`                                                                                       | `true`       | როდესაც `false`, დაცვა მოკლდება.                                                                                                                                                                              |
| რეჟიმი             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                                 | `warn`       | ინექციის პოლიტიკა: `block`, `warn`, ან `log`. (`redact` მიღებულია უკანასკნელი თავსებადობისთვის, მაგრამ არ წაშლის ინექციის ტექსტს; მოთხოვნა PII-ის ხელახალი წერისთვის კონტროლდება `PII_REDACTION_ENABLED`-ით.) |
| ბლოკირების ზღვრები | `blockThreshold` პარამეტრი / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ალტერნატიული `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | მინიმალური სერიოზულობა საჭირო ბლოკირებისთვის. საშუალო მხოლოდ დაკვირვების რეჟიმშია ნაგულისხმები.                                                                                                               |

**რეჟიმის პრიორიტეტი** (`getMode`): ზარის `options.mode` →
`INJECTION_GUARD_MODE` **DB ფუნქციის დროშის გადაფარვა** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` გარემო → `INPUT_SANITIZER_MODE` გარემო →
`warn`. შესაბამისად, Dashboard-ის გადაფარვა უფრო მაღლა დგას გარემოს ცვლადებზე, ამიტომ Feature
Flags UI მართავს მიმდინარე დაცვას პირდაპირ (არასაჭიროა გადატვირთვა). DB-ის წაკითხვა უსაფრთხოა:
თუ შეცდომა ხდება, დაცვა გადადის გარემოზე დაფუძნებულ ქცევაზე, და როდესაც არ არის
გადაფარვა, ქცევა იდენტურია მხოლოდ გარემოს გადაწყვეტასთან.

აღმოჩენის წყაროები:

1. `sanitizeRequest()`გან `@/shared/utils/inputSanitizer` (გაზიარებული დეტექტორი
   ნაკრები, რომელიც გამოიყენება სხვა ადგილებში).
2. ჩაშენებული `DEFAULT_GUARD_PATTERNS` (ამჟამად `system_override_inline` და
   `markdown_system_block`, ორივე `high` სერიოზულობა).
3. სავალდებულო `customPatterns`, რომლებიც გადაეცემა კონსტრუქტორის პარამეტრებით (სტრინგები, რეგულარული გამოხატულებები,
   ან `{ name, pattern, severity }` ჩანაწერები).

როდესაც `mode === "block"` **და** მინიმუმ ერთი აღმოჩენა აკმაყოფილებს სერიოზულობის
ზღვარს, `preCall` აბრუნებს `{ block: true, message: "მოთხოვნა უარყოფილია:
შეუმჩნეველი შინაარსი აღმოჩენილი" }`. `warn`/`log` რეჟიმებში დაცვა ლოგავს, მაგრამ
შეგიძლიათ ზარი. გაზიარებული დამხმარე `evaluatePromptInjection()` ასევე ექსპორტირდება
ზარებისათვის, რომლებსაც სჭირდებათ პრომპტების შეფასება რეგისტრაციის გავლით.

**Scan bound (v3.8.20):** დეტექტორი მხოლოდ ინსპექტირებს **პირველ 16 KB**-ს
ერთიან პრომპტ ტექსტში — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ბაიტი)
`src/shared/utils/inputSanitizer.ts`-ში. როგორც `detectInjection()` ასევე
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)`-ს იყენებს
პატერნის ციკლის გაშვების წინ. ინექციის დირექტივები მდებარეობს ინპუტის ზედა ნაწილში, ასე რომ ეს
შეზღუდავს რეგულარულ გამოხატულებებს CPU/GC-ზე მრავალ ასეულ KB დატვირთვებზე, რაც არ
აღიზიანებს აღმოჩენას (cf. #3932, #4041).

### Credential Masker (`credentialMasker.ts`)

მუშაობს **ორივე** ეტაპზე, ბოლო ნაგულისხმები ჯაჭვში (პრიორიტეტი `95`). წაშლის
კარგად ცნობილი API-კი / საიდუმლო-ტოკენის პატერნებს გასულ დატვირთვაში (მესიჯის
შინაარსი, ინსტრუმენტის ზარის არგუმენტები, ინსტრუმენტის შედეგები) **და** პროვაიდერის პასუხში, ასე რომ
საიდუმლო, რომელიც პრომპტში არის ჩასმული (ან ინსტრუმენტის შედეგით დაბრუნებული) არ გაჟონოს
ზემოთ პროვაიდერისთვის ან უკან კლიენტისთვის.

- **მხოლოდ არჩევითი**, იგივე კონვენცია როგორც PII რედაქცია (Hard Rule #20-adjacent):
  გამორთულია, თუ არა `settings.credentialRedactionEnabled === true` **ან**
  `CREDENTIAL_REDACTION_ENABLED=true`. როდესაც გამორთულია, დაცვის ბარიერი არ მოქმედებს —
  არასოდეს ბლოკავს და არასოდეს გადაწერს.
- `redactCredentials()` გადის სრული დატვირთვის/პასუხის ხეს (`walkValue()`,
  პროტოტიპის დაბინძურებისგან დაცული, ციკლისგან დაცული `WeakSet`-ით) და შეცვლის
  შესაბამისობებს `[REDACTED:<type>]` ადგილმდებარეობით, მხოლოდ იმ შტოებს
  კლონირებით, რომლებიც სინამდვილეში შეიცვალა.
- `CREDENTIAL_PATTERNS` მოიცავს LLM პროვაიდერების გასაღებებს (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ტოკენებს (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), გადახდის გასაღებებს (Stripe, Square),
  ღრუბლოვანი გასაღებები (AWS access key, Twilio, SendGrid, Mailgun), კერძო
  გასაღებები / JWT-ები,
  სერტიფიკატების შემცველი კავშირების სტრიქონები (`mongodb://user:pass@...`, და
  ა.შ.), და ზოგადი `Authorization`/`x-api-key`/`api-key`/`apikey` ჰედერ-ღირებულების
  ნიმუში. ჰედერ-ფორმის გასაღებები (`authorization`, `x-api-key`, `api-key`,
  `apikey`) სტრუქტურულად არის რედაქტირებული (მხოლოდ ღირებულება, სქემის პრეფიქსი
  როგორიცაა `Bearer `/`Basic ` შენარჩუნებულია) არა კი ზოგადი ტექსტური regex-ის
  საშუალებით.
- დაცვის ბარიერი არასოდეს ბლოკავს; ის მხოლოდ გადაწერს (`modifiedPayload` /
  `modifiedResponse`) და ანოტაციას აკეთებს (`meta.credentialsRedacted`, `meta.count`).

## ბაზის კონტრაქტი (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true მოკლედ აჩერებს ჯაჭვს
  message?: string; // გამოჩნდება როდესაც ბლოკირებულია
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // დაბრუნებულია preCall-ით მოთხოვნის გადაკეთებისთვის
  modifiedResponse?: TValue; // დაბრუნებულია postCall-ით პასუხის გადაკეთებისთვის
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

გარდრაილი "არანაირი ცვლილება" სიგნალს აძლევს `void`, `{}`, ან
`{ block: false }` დაბრუნებით. `modifiedPayload`/`modifiedResponse` დაბრუნება
ცვლილებას ახდენს ჯაჭვში მიმდინარე მნიშვნელობაზე ქვემოთ მდებარე გარდრაილებისთვის.
`signal?: AbortSignal` გადატანს გამიძახებლის სიცოცხლის ციკლს გარდრაილებში. მოთხოვნის გაწყვეტა არის განზრახი წარუმატებელი გამოტოვების გამონაკლისი: მედია ხიდები წყვეტენ მუშაობას და წმენდას, არ აღადგინებენ ნედლ მედია მიზანზე, რომელიც ცნობილია, რომ არ უჭერს მხარს.

## რეგისტრატორი (`registry.ts`)

სინგლტონი `guardrailRegistry` აჩვენებს:

- `register(guardrail)` — ამატებს (ან ცვლის ნორმალიზებული სახელით) გარდრეილს და
  ხელახლა ალაგებს ზრდადი `priority`-ის მიხედვით.
- `clear()` / `list()` — ადმინისტრაციული დამხმარეები.
- `runPreCallHooks(payload, context)` — ახდენს აქტიური გარდრეილების იტერაციას,
  გადასცემს `payload`-ს `modifiedPayload`-ის გავლით და ჩერდება პირველ `block: true`-ზე.
- `runPostCallHooks(response, context)` — იგივე ნაკადი პასუხის მხარეს.
- `resetGuardrailsForTests({ registerDefaults })` — ასუფთავებს მდგომარეობას და სურვილისამებრ
  ხელახლა არეგისტრირებს ნაგულისხმევ პარამეტრებს ტესტის სუფთა იზოლაციისთვის.

ორივე რანერი აბრუნებს `{ blocked, payload|response, results, guardrail?, message? }`-ს,
სადაც `results` არის `GuardrailExecutionResult` ჩანაწერების მასივი, რომელიც მოიცავს
თითოეული გარდრეილის `blocked`, `skipped`, `modified`, `error` და `meta` ველებს,
რაც სასარგებლოა ტრეისინგისთვის.

### გარდრეილების გამორთვა თითო მოთხოვნაზე

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` აგროვებს
გარდრეილების სახელების დედუპლიცირებულ სიას, რომლებიც უნდა გამოტოვებულ იქნას
მიმდინარე მოთხოვნისთვის. წყაროები (ყველა არასავალდებულო, ყველა გაერთიანებულია):

- `apiKeyInfo.disabledGuardrails`
- მოთხოვნის სხეული `disabledGuardrails` (ზედა დონის)
- მოთხოვნის სხეული `metadata.disabledGuardrails`
- ჰედერი `x-omniroute-disabled-guardrails` (ან მოძველებული
  `x-disabled-guardrails`)

მნიშვნელობები შეიძლება იყოს სტრიქონების მასივები ან მძიმით გამოყოფილი სტრიქონი;
სახელები ნორმალიზდება პატარა ასოებით kebab-case-ში (`pii_masker` → `pii-masker`).
შედეგი გადაეცემა `context.disabledGuardrails`-ის გავლით რეგისტრატორს,
რომელიც გამოტოვებს შესაბამის გარდრეილებს (`skipped: true` `results`-ში).

## შესრულების თანმიმდევრობა

ყოველი მოთხოვნისთვის, რომელიც გადის `src/sse/handlers/chat.ts`-სა და `open-sse/handlers/chatCore.ts`-ის გავლით:

1.  `resolveDisabledGuardrails(...)` აგებს გამოტოვების სიას API გასაღებიდან, სხეულიდან და სათაურებიდან.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` ასრულებს დამცავ მექანიზმებს პრიორიტეტის ზრდადი თანმიმდევრობით:
    - გამორთული დამცავი მექანიზმები აღირიცხება როგორც `skipped`.
    - თითოეული დამცავი მექანიზმის `preCall`-მა შეიძლება გადაწეროს მონაცემთა პაკეტი `modifiedPayload`-ის მეშვეობით.
    - პირველი `block: true` წყვეტს ჯაჭვს და დამმუშავებელი აბრუნებს დამცავი მექანიზმის უარყოფის პასუხს.
3.  (პოტენციურად გადაწერილი) მონაცემთა პაკეტი მიედინება კომბინირებულ მარშრუტიზაციასა და ზედა დინების გაგზავნაში.
4.  პასუხის აწყობის შემდეგ, `guardrailRegistry.runPostCallHooks(...)` აწარმოებს იმავე ჯაჭვს პასუხზე. `block: true` აქ აგდებს ზედა დინების პასუხს.

დამცავი მექანიზმები, რომლებიც შეცდომას აგდებენ, აღირიცხება `error: <message>`-ით და აღინიშნება `logger.warn`-ის მეშვეობით, მაგრამ ჯაჭვი გრძელდება — დიზაინით ღიაა წარუმატებლობისთვის.

## მორგებული Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ნაბიჯები:

1.  შექმენით `src/lib/guardrails/myGuardrail.ts`, რომელიც აფართოებს `BaseGuardrail`-ს.
2.  განახორციელეთ `preCall` და/ან `postCall`.
3.  ან დაარეგისტრირეთ იმპორტის დროს (`registerDefaultGuardrails`-დან დამატებით) ან გამოიძახეთ `guardrailRegistry.register(...)` გაშვების დროს — რეესტრი ჩაანაცვლებს ნებისმიერ წინა guardrail-ს იგივე ნორმალიზებული სახელით.
4.  დაამატეთ ტესტები `tests/unit/`-ში (არსებული მაგალითები: `tests/unit/guardrails-registry.test.ts`, `tests/unit/prompt-injection-guard.test.ts`, `tests/unit/guardrails/visionBridge.test.ts`).

გამოიყენეთ `resetGuardrailsForTests()` ტესტებს შორის, რათა დაიწყოთ ცნობილი მდგომარეობიდან. გადაეცით `{ registerDefaults: false }`, რათა დაიწყოთ ცარიელი რეესტრით და დაარეგისტრიროთ მხოლოდ ტესტირებადი guardrails. Vision Bridge იღებს დამოკიდებულების ინექციას (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge აჩვენებს ექვივალენტურ წერტილებს პარამეტრებისთვის, შესაძლებლობებისთვის, STT მოდელის არჩევისთვის, სერთიფიკატების შემოწმებისთვის და ტრანსკრიფციისთვის. ამიტომ, ტესტებს შეუძლიათ ორივე ნაკადის შემოწმება მონაცემთა ბაზის ან ქსელზე წვდომის გარეშე.

## ინექციისგან დამცავი მარშრუტების დაფარვა და წითელი გუნდი (ფაზა 8 · ბლოკი D)

ინექციისგან დამცავი მექანიზმი (`createInjectionGuard` / `withInjectionGuard`) მოიცავს ყველა მარშრუტს, რომელიც იღებს მომხმარებლის მოთხოვნებს. ის ითვალისწინებს `INJECTION_GUARD_MODE`-ს (ნაგულისხმევი `warn` = მხოლოდ ჟურნალი; `block` = აბრუნებს HTTP 400 `SECURITY_001`).

| ტიპი            | მარშრუტები                                                                                                                                           | ნაგულისხმევი რეჟიმი |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| Text (existing) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                |
| Generative      | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                |
| Data            | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                |

ტექსტის ამოღება (`extractMessageContents`) მოიცავს `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`-ს.

**წითელი გუნდი (ღამის, `nightly-llm-security.yml`):** promptfoo ამოწმებს, რომ თითოეული მარშრუტი ბლოკავს OWASP-LLM კორპუსს `INJECTION_GUARD_MODE=block` რეჟიმში; garak აწარმოებს ზონდებს (გამოტოვებს საიდუმლოს გარეშე). `moderations` შედის თანმიმდევრულობისთვის — ოპერატორებს ბლოკირების რეჟიმში შეუძლიათ მისი გათავისუფლება `resolveDisabledGuardrails`-ის მეშვეობით.

ღამის სამუშაო პროცესი (`.github/workflows/nightly-llm-security.yml`, cron + ხელით გაშვება) მოიცავს ორ დავალებას:

- **`promptfoo-guard` (ბლოკირება)** — აწარმოებს `promptfoo eval -c promptfooconfig.yaml`-ს `INJECTION_GUARD_MODE=block`-ით. თითოეული მტრული შემთხვევა (მაგ. „უგულებელყავით ყველა წინა ინსტრუქცია…“, DAN-ის სტილის jailbreaks) ადასტურებს, რომ პასუხი შეიცავს `error.code === "SECURITY_001"`, ანუ guard-მა რეალურად უარყო მოთხოვნა.
- **`garak` (საკონსულტაციო)** — აწარმოებს garak `--probes promptinject,dan,leakreplay`-ს ლოკალური OmniRoute ინსტანციის წინააღმდეგ (`http://localhost:20128/v1`). დაცულია პროვაიდერის საიდუმლო გასაღებით (`PROMPTFOO_PROVIDER_KEY`); გამოტოვებს შეცდომის გარეშე და დამატებულია `|| true`, ასე რომ, ის აფიქსირებს CI-ის ჩავარდნის გარეშე.

guard დამხმარის (`createInjectionGuard` / `withInjectionGuard`) დაფარვა მოიცავს ყველა მოთხოვნის შემცველ `/v1` მარშრუტს; მოთხოვნის ტექსტი ამოღებულია `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`-დან `extractMessageContents()` ფუნქციის მიერ `src/shared/utils/inputSanitizer.ts`-ში.
