> **ბოლოს განახლდა:** 2026-08-29 — v3.8.51 (ვიდეო ხიდის ტრანსკრიპტის წარმომავლობა დეკლარირებულია გამომძახებლის მიერ, ჯერ არ არის სერვერის მიერ დამოწმებული — განმარტებულია #11661-ის მიხედვით)

Guardrails უზრუნველყოფენ უსაფრთხოებას, პოლიტიკას და კონტენტის ტრანსფორმაციებს OmniRoute-სა და upstream პროვაიდერებს შორის საზღვარზე. თითოეულ guardrail-ს შეუძლია შეამოწმოს (და სურვილისამებრ უარყოს, გარდაქმნას ან ანოტირება გაუკეთოს) მოთხოვნის payload-ები (`preCall`) და upstream პასუხები (`postCall`).

სისტემა არის **fail-open**: თუ guardrail-ის შესრულებისას შეცდომა მოხდა, რეგისტრატორი აღრიცხავს შეცდომას და აგრძელებს შემდეგ guardrail-ზე, ნაცვლად მოთხოვნის შეწყვეტისა. დაბლოკვა არის მკაფიო გადაწყვეტილება (`block: true`), არასდროს შემთხვევითობა.

### ხედვის ხიდი (`visionBridge.ts`) — მოდალობის ხიდი PR-1

შეიცავს იმიჯების შემცველ მოთხოვნებს, რომლებიც მიმართულია **არახედვით მოდელებზე** და ან
გადამისამართებს მთელ მოთხოვნას ხედვის შესაძლებლობის მქონე მოდელზე ან ცვლის იმიჯის
ნაწილებს ტექსტური აღწერებით, რომლებიც წარმოიქმნება კონფიგურირებად ხედვის მოდელით, წინასწარ
ზემოთ აღნიშნულ ზარებზე. ეს საშუალებას აძლევს მხოლოდ ტექსტურ პროვაიდერებს გამჭვირვალედ
ხელმძღვანელობენ მრავალმოდალურ დატვირთვებზე.

მიმდინარე პროცესი:

1. გამოტოვეთ, თუ მიზნობრივი მოდელი უკვე მხარს უჭერს ხედვას (თუ არ ჩანს
   იძულებითი ხიდების სიაში `isVisionBridgeForcedModel`).
2. ამოიღეთ იმიჯის ნაწილები `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), რომელიც დელეგატებს **ერთიან მედია
   დეტექტორს** `detectMediaParts()` `open-sse/utils/mediaParts.ts`-ში —
   სიმართლესთან ერთად ერთადერთი წყარო, რომელიც გაზიარებულია კომბინირებული თავსებადობის ფილტრთან.
   ამოღება დაშვებულია მხოლოდ ზედა დონეზე ნაწილებზე, რომლებსაც
   `replaceImageParts` შეუძლია უკან დააბრუნოს (ამოღება↔შეცვლა კონტრაქტი): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, და Responses API `input_image`. ჩასმული_hits და
   მხოლოდ ინდიკატორის ფორმები კომბო-ფილტრის მასალაა და არასოდეს გამოითხოვება.
   გამოტოვეთ, თუ არაფერი მოიძებნა.
3. გადაწყვიტეთ runtime კონფიგურაცია `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): ახალი `modalityBridge*`
   პარამეტრების გასაღებები მოიგებს; ძველი `visionBridge*` გასაღებები რჩება
   **ერთი ციკლისFallback** (უკან დაბრუნების ფანჯარა). გამოტოვეთ ნებისმიერი მედიის
   გავლა, როდესაც ხიდი გამორთულია.
4. რეჟიმის არჩევანი (`modalityBridgeVisionMode`, იხილეთ ქვემოთ მოცემული ცხრილი)
   გადაწყვეტს გადამისამართებას თუ აღწერას. გადამისამართება აბრუნებს `modifiedPayload`
   მხოლოდ `model` შეცვლილი, პლუს მეტა `{ rerouted, fromModel, toModel, imagesKept }`.
5. აღწერის გზა: შეზღუდეთ იმიჯები `maxImages`-ზე, შეადგინეთ დავალების
   ცნობიერი პრომტი, კონსულტაცია გაუწიეთ აღწერის კეშს, გამოიძახეთ ხედვის მოდელი
   **პარალელურად** (`Promise.allSettled`), და ჩააწვდეთ `[Image N]: <description>`
   ტექსტური ნაწილები მათ ადგილას. წარუმატებელი აღწერა იძლევა `null` და
   ორიგინალური იმიჯის ნაწილი **შენარჩუნებულია** (#4012) — გარდა კომბო აღწერის
   გზის, როდესაც ყველა აღწერა წარუმატებელია, სადაც დადასტურებული არახედვით
   ზემოთ აღნიშნული იღებს `(unavailable — no vision-capable provider connected)`
   stub-ის ნაცვლად (#8430).
6. დააბრუნეთ `modifiedPayload` + მეტა (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### API-კი სქემა (`visionBridgeKeyScope.ts`)

როდესაც დამრიგებლის API გასაღები ზღუდავს `allowedConnections`, კვოტის აუზებს
(`allowedQuotas`) ან მოდელებს (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), ხიდი მხოლოდ
არჩევს გადამისამართების და აღწერის მოდელებს, რომლებიც გასაღები შეიძლება გამოიყენოს, იმ
კავშირებზე, რომლებიც გასაღები შეიძლება გამოიყენოს. აღწერის ზარი მაშინ ყოველთვის გადის
OmniRoute თვით-ციკლზე `x-omniroute-self-loop-key-id` სათაურით, ასე რომ მიღებული
ჩატ მოთხოვნა კვლავ ახორციელებს იმ გასაღების კავშირს და მოდელის პოლიტიკას. `enforceApiKeyPolicy()`
პატივს სცემს ამ სათაურს მხოლოდ თვით-ციკლის ბერერთან ერთად, ასე რომ იგი მხოლოდ
შეზღუდავს წვდომას, და id, რომელიც არ იწვდება, უარყოფილია.

თუ ხედვის მოდელი არ არის დაშვებული გასაღებისთვის, აღწერის გზა გვერდზე გადადის და
მოთხოვნა გადის უცვლელად, იგივე წარუმატებელი ღია ქცევა, როგორც გამორთული
დაცვა (მეტა `{ skipped: true, reason: "no_permitted_vision_model" }`).
მოთხოვნები, რომლებიც არ აქვთ გასაღები, და გასაღებები, რომლებსაც არ აქვთ ეს შეზღუდვები,
მუშაობენ ზუსტად ისე, როგორც ადრე.

#### დავალების ცნობიერი აღწერის პრომტი (`modalityBridgeVisionTaskAware`)

Default **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) ამატებს
**ბოლო მომხმარებლის შეტყობინების** ტექსტს (500 სიმბოლომდე შეზღუდული) ბაზის
აღწერის პრომტზე, რაც აღწერას მიმართავს იმაზე, რაც მომხმარებელმა სინამდვილეში მოითხოვა
(codex-vision-proxy pattern) და ითხოვს ვიზუალური მოდელისგან ხილული
ტექსტის ტრანსკრიფციას. როდესაც დროშა გამორთულია — ან მომხმარებლის ტექსტი არ არის — ბაზის
პრომტი უცვლელად გამოიყენება.

აღწერის თვით-ციკლის საკუთარი OpenAI-თან თავსებადი მოთხოვნა (`callVisionModelSingle()`
`visionBridgeHelpers.ts`-ში) ყოველთვის ითხოვს `image_url.detail: "high"` —
არასამუშაოდ, ყველა გამწვდელზე/მომწოდებელზე, არ არის დამოკიდებული რომელიმე
კლენტის სიგნალზე. დაბალი დეტალების ნიმუში ამცირებს OCR-ის სიზუსტეს იმ
ტექსტის ტრანსკრიფციის დავალებისთვის, რაც ამ პრომტზეა მოთხოვნილი, ამიტომ
აღწერის გამოძახება ყოველთვის ითხოვს მაღალ დეტალს, მიუხედავად იმისა, თუ
რა დეტალების დონე იყო გამოყენებული ორიგინალურ შემოსულ მოთხოვნაში. ეს
მხოლოდ გავლენას ახდენს შიდა აღწერის მოთხოვნის სხეულზე; ეს არ ცვლის
როგორ OmniRoute აგზავნის გამწვდელის საკუთარ `image_url.detail` პირველადი
მოთხოვნის დროს — ეს დეფოლტი ცალკე გამოიყენება და მხოლოდ აღმოჩენილი
OpenCode კლენტებისთვის, `defaultImageDetail()`-ში (`open-sse/handlers/chatCore/upstreamBody.ts`).
Anthropic-ის მავთულ-ფორმატის შტო აღწერის თვით-ციკლში არ აქვს `detail` ველი
და არ ექვემდებარება არცერთ დეფოლტს.

#### აღწერის გამომავალი კაპი (`modalityBridgeVisionMaxChars`)

| გასაღები                       | დეფოლტი | დიაპაზონი        |
| ------------------------------ | ------- | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`     | `0` ან 100–50000 |

`0` (დეფოლტი) ნიშნავს **არანაირ კაპს** — აღწერა, რომელიც
`callVisionModel()`-ით დაბრუნდება, გადადის უცვლელად, რაც ამჟამინდელ
ქცევას ინარჩუნებს. ნებისმიერი მნიშვნელობა 100–50000 დიაპაზონში
შეზღუდავს აღწერას `…` სუფიქსით, სანამ ის კვლავ არ გაწვდება როგორც
`[Image N]: <აღწერა>` (`VisionBridgeGuardrail.preCall()` `src/lib/guardrails/visionBridge.ts`-ში).
ამას უნდა გაზარდოთ დეტალებით დატვირთული OCR დავალებებისათვის, როდესაც
ქვედა მოდელს სჭირდება სრული ტრანსკრიფცია; შეამცირეთ, რომ
შეზღუდოთ ტოკენის გამოყენება საუბრობად ვიზუალური მოდელებისთვის.
დაშბორდის ველი მდებარეობს Vision-ის ტაბის მოწინავე პანელში
(`modality-bridge-max-chars` `ModalityBridgeVisionTab.tsx`-ში) და
შეზღუდავს ნებისმიერ მნიშვნელობას 1 და 99 შორის 100 სართულზე, ხოლო
მიუხედავად ამისა, აშკარა `0` არ ეხება — `0` არის ვალიდური Zod
მნიშვნელობა თავისთავად
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), არა მხოლოდ
"არასამუშაო" დეფოლტი.

#### აღწერის კეში (`modalityBridge/bridgeCache.ts`)

მეხსიერების LRU + TTL კეში აღწერის გამომავალებისთვის, გაზიარებული პროცესის მასშტაბით.
გასაღები = `sha256(imageRef + composedPrompt + configuredBridgeModel)` სიგრძის
პრეფიქსით ჩარჩო (არანაირი ველის საზღვრის შეჯახება). მოდელის კომპონენტი არის
**კონფიგურირებული** ხიდის მოდელი, არა მოდელი, რომელიც სინამდვილეში პასუხობს —
`callVisionModel` შეიძლება შიდა fallback-ით, და გასაღების თითოეული
ცდის მიხედვით კეში დაიშლება. წარუმატებელი აღწერები არასოდეს ინახება. პარამეტრები:

| გასაღები                        | დეფოლტი | დიაპაზონი |
| ------------------------------- | ------- | --------- |
| `modalityBridgeCacheEnabled`    | `true`  | —         |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440    |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000   |

#### შორეული გამოსახულების ნორმალიზაცია (თვით-ციკლი აღწერა/base64 მიღება)

როდესაც ხიდი იღებს **შორეულ** გამოსახულებას — Anthropic-ის აღწერის
თვით-გამოძახება და claude-wire-format base64 გარდაქმნა
(`ensureBase64ImagesForClaudeWire`), ორივე
`fetchRemoteImageAsDataUri()`-ით `visionBridgeHelpers.ts`-ში — შედეგი
მონაცემთა URI გადადის `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) სანამ ის ჩასმული იქნება ვიზუალური მოდელის
მოთხოვნაში. ზედმეტი ზომის გამოსახულებები შემცირდება **2048px გრძივი კიდეზე**
(რომელიც ემთხვევა OpenAI/Anthropic-ის მიერ უკვე გამოყენებულ
ზომის შემცირების კაპს), რაც ამცირებს
ატვირთვის ბაიტებს/ლატენტობას, რაც არ ცვლის იმაზე, რაც ვიზუალური მოდელი ხედავს.
ზომის შემცირება იყენებს `sharp`, რომელიც დაიტვირთება დინამიური იმპორტით: პლატფორმაზე,
სადაც მისი ნატივი ბინარი ვერ იტვირთება, `normalizeDataUri()` **არასოდეს
შეიძულებს** — ის გადადის ორიგინალური ბაიტების პას-through-ზე, ასე რომ
აღწერა/base64-გარდაქმნის გზა ყოველთვის მუშაობს. არ გამოსახულების ბაიტები
(მიღება, რომელიც არ დაბრუნდა დეკოდირებადი გამოსახულება) ასევე გადადის
უცვლელად. ეს ნორმალიზაცია შეზღუდულია იმ გამოსახულებებზე, რომლებიც ხიდი
იღებს საკუთარი თვით-გამოძახებისთვის — ეს არასოდეს გამოიყენება
გამწვდელის ნედლი პას-through დატვირთვისთვის, რაც შეესაბამება
მხოლოდ ოპტ-ინ მუტაციის პრინციპს (Hard Rule #20).

#### გამჭვირვალობის სათაური + სტატისტიკა

აღწერის გარდაქმნილი პასუხები ატარებენ
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(შექმნილია `buildModalityBridgeHeader()`-ით `modalityBridge/bridgeStats.ts`-ში,

გადამისამართებული მოთხოვნები **არ აქვთ** სათაურს — დატვირთვა უცვლელია და მოდელის
შეცვლა უკვე ჩანს პასუხის სხეულის `model` ველში.

`GET /api/modality-bridge/stats` (მმართველობის ავტორიზაცია, იგივე დონეზე როგორც
`GET /api/settings`) აბრუნებს მეხსიერებაში არსებულ თითოეული მოდალობის

latencySamples, averageLatencyMs, lastUsedAt }` `vision`, `audio`, და
`video`-სთვის. `averageLatencyMs` იყენებს `latencySamples`, არა ყველა
ცდას, როგორც მისი გამყოფი; ოპერაცია, რომელიც დროის გარეშეა, არ ქმნის
ნულოვანი მილიწამიანი ნიმუშს. `bridged` რჩება უკუკავშირების თავსებად
ალტერნატივად წარმატებული გარდაქმნებისთვის; წარუმატებელი ცდები არ
ამატებენ მას.
კაუნტერები პროცესის ხელახლა დაწყებისას ნაგულისხმევად
(ტელემეტრია, არა ანგარიშგება) აღდგება.

#### დაფის კონფიგურაცია

მიუწვდელი დაფის გვერდი არის
`/dashboard/settings/modality-bridge`. მისი URL-მისამართით `Vision`, `Audio`,
და `Video` ტაბები ინარჩუნებენ კითხვების პარამეტრებს `tab` მნიშვნელობის
შეცვლისას.
Vision ტაბი აჩვენებს ჩართვას, რეჟიმს, მოდელის არჩევანს (მათ შორის
ავტომატურ დეფოლტს), დავალების ცნობიერების პრომპტინგს, მოწინავე
დროის/სურათის/აღწერის სიგრძის/კეშის შეზღუდვებს, გაწვდილი
კაუნტერებს და დაცულ ნიმუშის მოთხოვნას. Audio ტაბი ასევე ცოცხალია: ის
აჩვენებს ჩართვას, STT-წარმოების მოდელის არჩევანს Auto-ით, დროის/მაქსიმალური
კლიპის შეზღუდვებს, აუდიო კაუნტერებს და `input_audio` ნიმუშის ტესტს. Video
ტაბი ფუნქციონირებს: ის იტყობინება FFmpeg/ffprobe-ის გაწვდილი მდგომარეობის
შესახებ — ოთხი აშკარა UI მდგომარეობიდან ერთ-ერთი (`unknown`, როდესაც
პრობლემა ფრენაშია ან ვერ დასრულდა, `restricted` არ-ლუპბექ დაფაზე, სადაც
პრობლემა გამოტოვებულია კლიენტ-გვერდზე, `unavailable`, როდესაც
პრობლემა გაწვდილი და დადასტურებულია, რომ არ არის, ან `available` FFmpeg/ffprobe
ვერსიებით) — ინარჩუნებს enable/model/frame/video/timeout შეზღუდვებს,
ფილტრავს მოდელის არჩევანს ვიზუალური შესაძლებლობების მქონე მოდელებზე და
აჩვენებს ვიდეო კაუნტერებს.

ყოფილი Vision Bridge ბარათი AI პარამეტრებში არის თავსებადობის ბმული
ახალ გვერდზე; ის აღარ ფლობს ფორმის მეორე ასალს. მედია პროვაიდერები ასევე
ბმულობენ სურათიდან ტექსტში და სიტყვიდან ტექსტში სამუშაო პროცესებს
Corresponding Modality Bridge ტაბებზე, არსებული სიტყვიდან ტექსტში
თამაშის გარეშე.

**თვით-ციკლის დაშვების გვერდის ავლა:** როდესაც აღწერის ზარი
OmniRoute-ის საკუთარ `/v1` თვით-ციკლში (არასტანდარტული პროვაიდერის მოდელი)

`sk_omniroute` სენტინელით ადგილობრივ რეჟიმში, ან ოპერატორის მიერ
კონფიგურირებული `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env გასაღებით (#1350),
ასე რომ `REQUIRE_API_KEY=true` განლაგებები კვლავ შეუძლიათ
აღწერის ზარის გაწვდვა. გვერდის ავლა მხოლოდ იმ ზუსტ სერთიფიკატებზე
იქნება გათვალისწინებული, ამიტომ გარე კლიენტები ვერ გამოიყენებენ
ბმულს დაშვების გამოტოვებისთვის.

რეჟიმი/დავალების ცნობიერების/კეშის დეფოლტები და პარამეტრების

### აუდიო ბრიჯი (`audioBridge.ts`) — მოდალობის ბრიჯი PR-3

შეაჩერებს აუდიომომცველ ჩათის მოთხოვნებს, სანამ ისინი მიაღწევენ
მიზანს, რომელიც ცნობილი არ არის აუდიო შესატყვისის მიღებაზე. ის არასდროს
გადამისამართებს ჩათის მოთხოვნას: აუდიო ნაწილები
გაწვდილი OpenAI-თან თავსებადი მრავალმხრივი ბოლო წერტილის საშუალებით
იქმნება და არჩეული ჩათის მოდელი აგრძელებს ტექსტური
ტრანსკრიპტებით.

მიმდინარე პროცესი:

1. გადაწყვიტეთ `supportsAudio` `getResolvedModelCapabilities()`-ის
   საშუალებით. აშკარა პროვაიდერის რეგისტრაციის მეტადატა გამარჯვებს, შემდეგ
   სტატიკური მოდელის მეტადატა, შემდეგ სინქრონული `modalities_input`.
   დეკლარირებული შესატყვისი სია, რომელიც არ შეიცავს `audio`, არის `false`;
   არანაირი შესაძლებლობის მტკიცებულება რჩება `null`. როგორც `false`, ასევე
   `null` აქტივირებს კონსერვატიულ ბრიჯს, ხოლო `true` გვერდს
   უგულებელყოფს.
2. გადაწყვიტეთ `modalityBridgeAudio*` პარამეტრები და გამოიტანეთ
   გაწვდილი უმაღლესი აუდიო ნაწილები თითოეული შეტყობინებიდან
   საერთო `detectMediaParts()` დეტექტორის საშუალებით. მხარდაჭერილი
   მავთულოვანი ფორმები არიან OpenAI `input_audio`, `audio_url`, და
   `source.media_type: "audio/*"`. ჩ Nested აუდიო
   აღმოჩენილია გადამისამართებისთვის, მაგრამ არ არის
   ამოღებული გაწვდილი გზით. სამუშაოს ზღვარი არის `modalityBridgeAudioMaxClips`;
   შემდგომი ნაწილები რჩება შეუცვლელი.
3. პატივი სცით კონფიგურირებულ `provider/model`, ან
   დაუშვით `selectAudioBridgeModel()`-ის გავლა `AUDIO_TRANSCRIPTION_PROVIDERS`
   სტაბილური კატალოგის წესით და აირჩიეთ პირველი მოდელი
   გამოყენებად აქტიური პროვაიდერის სერთიფიკატით.
4. `callAudioTranscription()` გარდაქმნის base64/data-URI აუდიოს
   მრავალმხრივ `file`-ში, ან ჩამოტვირთავს შორეულ `audio_url`
   საჯაროდ მხოლოდ გასვლის დაცვით DNS-ით და 25 MB-ის ზღვარით. შემდეგ
   ის POST-ით აგზავნის ფაილსა და არჩეულ მოდელს ადგილობრივ
   `/v1/audio/transcriptions` თვით-ციკლში, ავტორიზებული
   `resolveSelfLoopBearer()`-ით. არსებული ტრანსკრიპციის მარშრუტი
   ახორციელებს ჩვეულებრივ სერთიფიკატის ძიებას, გაგრილების/სიჩქარის
   შეზღუდვის მართვას და პროვაიდერის გადაცემას.
5. წარმატებული ზარები ცვლიან თავიანთ ნაწილებს `[Audio N]: <transcript>`.
   ზარები მუშაობენ `Promise.allSettled`: ინდივიდუალური წარუმატებლობა
   ინარჩუნებს იმ ორიგინალურ აუდიო ნაწილს (#4012 კონტრაქტი). თუ ყველა
   ზარი წარუმატებელია და მიზანი დადასტურებულია `supportsAudio === false`,
   ნაწილები ხდება `[Audio N]: (unavailable — no STT provider connected)`
   (#8430 კონტრაქტი). უცნობ მიზანზე (`null`), ყველა წარუმატებელი
   შედეგი რჩება შეუცვლელი. დადასტურებული ტექსტური მიზანი, რომელსაც არ აქვს
   გამოყენებად STT სერთიფიკატი, იღებს იმავე აშკარა
   stub-ს, ქსელის ზარის გარეშე.

წარმატებული ტრანსკრიპტები იყენებენ პროცესის მასშტაბით Modality Bridge LRU/TTL
კეშს. გასაღები აერთიანებს აუდიო რეფერენს, სტაბილურ `audio-transcription`
ოპერაციის ლეიბლს და არჩეულ STT მოდელს; წარუმატებლობები არასდროს
კეშდება. აუდიო ცდები განაახლებენ საერთო `bridged`, `cacheHits`, `failures`,
და `lastUsedAt` კაუნტერებს. გარდაქმნილი პასუხები ატარებენ
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`;
შეუცვლელი მოთხოვნები არ იღებენ აუდიო ბრიჯის სექციას.

მიმდინარე პარამეტრები DB-ით გაწვდილი და Zod-ით ვალიდირებული:

| ----------------------------- | ------------ | -------------------- |

გადაზიარებული კეში კონტროლდება `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, და `modalityBridgeCacheMaxEntries`.

### ვიდეო ხიდი (`videoBridge.ts`, `videoBridgePipeline.ts`)

შეიჭრება უმაღლესი დონეების ვიდეო ნაწილებში ჩათვის დასრულებებში `messages` და პასუხების

ვიდეოებად.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) ფლობს მოთხოვნის გავლას,

სკენების აღწერა (რომელიც აერთიანებს ნებისმიერ გამსწორებელ აუდიო ტრანსკრიპტს), და თითოეული მცდელობის

(ბაიტების შეძენა და ნიმუშების ჩარჩოების ამოღება), `VideoAudioTranscriptionPort`
(გამსწორებელი აუდიო ტრანსკრიპტის გაწვდვა ნიმუშების სექციებთან), და

შედგება აღწერილი პორტის გარშემო `createVideoSttAdapter` და

საჯარო `/v1` მოთხოვნის გზა არასდროს იმპორტირებს ან იწვევს სუბპროცესს. შორეული

ნდობით აღჭურვილ ლუპბექ მოთხოვნას, და არასდროს იღებს URL-ს, ფაილური გზას,Executable,
ან არგუმენტების სიას. API სხეულის ზომის pipeline და დამუშავების ინკრემენტული სხეულის

შეასრულებს ერთExtraction ერთდროულად, საშუალებას აძლევს ოთხი მოლოდინის სამუშაოს, და

ბროკერის შიგნით, `ffprobe` კითხულობს პირად ადგილობრივ ფაილს; ფიქსირებული ფორმატი

Fallback-ის წინ. ვიდეოები შეზღუდულია 600 წამით, 8,192 პიქსელით თითო განზომილებაში, და

`scene_aware` და ექსპერიმენტული `segment_aware` პოლიტიკები ასრულებენ ერთ დამატებით

#### FU-07 სტრუქტურული სექციის მტკიცებულება

`segment_aware` იყენებს ერთ შეზღუდულ წინასწარ ანალიზის გადაცემას უკვე ვალიდირებულ ადგილობრივ ვიდეო ნაკრებზე. ფიქსირებული ფილტრის ჯაჭვი პირველად ზომავს მაქსიმუმ 320 პიქსელს სიგანეში, აღმოაჩენს სცენის ცვლილებებს და გაყინულ ინტერვალებს, შემდეგ კი 1 ჩარჩოს სიხშირით ნიმუშებს იღებს ბუნდოვანების, საშუალო ლუმას და სივრცული/დროითი ინფორმაციისთვის. გადაცემა შეზღუდულია 600 სტრუქტურული ნიმუშით, ერთ FFmpeg/filter ნაკადით, იმავე `file`-მხოლოდ პროტოკოლით და კონტეინერის ნებართვებით, 1 MiB პროცესის-გამოსვლის საზღვრით და მაქსიმუმ 30 წამით ბროკერის საერთო გაწყვეტის/დროის ვადის ფარგლებში. იგი არასოდეს იღებს ბრძანებას, ფილტრს, გზას ან URL-ს მოთხოვნიდან.

სტრუქტურული მნიშვნელობები არის დეტერმინისტული ნიმუშების მტკიცებულება, არა სემანტიკური ვიდეო გაგება. ისინი არ განსაზღვრავენ სუბიექტებს, მოქმედებებს, წარწერებს, მეტყველებას ან მომხმარებლის ნებას. სცენის და გაყინული საზღვრები ქმნიან სექტორებს; გაყინული დაფარვა, ბუნდოვანება, ექსპოზიცია, სივრცული დეტალი და დროითი ცვლილება მხოლოდ გავლენას ახდენს იმაზე, როგორ არის გამოყოფილი არსებული 1–16 ჩარჩოს ბიუჯეტი. სრულად გაყინული სექტორი შეზღუდულია ერთ ჩარჩოზე, ხოლო არაგაყინული სექტორები კონკურენციას უწევენ დარჩენილ ბიუჯეტზე. როდესაც საზღვრები ჩარჩოებზე მეტია, ერთგვარი დროის დაფარვა შენარჩუნებულია, რათა სწრაფი ადრეული გაჭრილი არ დამალოს გრძელი კუდიანი სექტორი. სცენის საზღვრები 1-წამიანი ანალიზის რეზოლუციის ფარგლებში გაყინული საზღვრის ფარგლებში გაწვდილი არიან.

მოსაკლავი ფილტრები, არასწორი/ცარიელი მტკიცებულებები, დეტექტორის შეცდომა ან შეზღუდული წინასწარი ანალიზის დროის გასვლის შემთხვევაში, იხსნება ზუსტად ერთგვაროვანი შუა პოლიტიკისკენ. გამსCaller-ის გაწყვეტა ან ბროკერის ვადა არ იხსნება: იგი ამთავრებს მიმდინარე სუბპროცესს, ხელს უშლის შემდგომ ჩარჩოს ამოღებას და კერძო დროებითი ხე იხსნება `finally`-ში.

`scripts/perf/video-bridge-fu07-eval.ts` გენერირებს დეტერმინისტულ რეალურ FFmpeg-ის მოწყობილობებს პოსტ-დედუპის წარწერის-ზარალის, სქელი მოძრაობის ბიუჯეტის გამოყოფისთვის, ბუნდოვანების/ექსპოზიციის/SI-TI მტკიცებულებების, სწრაფი გაჭრილი გრძელი კუდით და ნელ-ნელა გაქცეული ცრუ დადებითი შედეგებისთვის. იგი აღრიცხავს წინასწარი ანალიზის კედლის დროს და, სადაც `/usr/bin/time` ხელმისაწვდომია, შვილობილი CPU და პიკი RSS. მისი ხარისხის შემოწმებები მხოლოდ სტრუქტურული ორკაკლებია. რეალური წარწერის მოდელის ხარისხი რჩება `HOLD`, რადგან ეს მოწყობილობა არ აქვს ავტორიზებული ბოლო წერტილი ან გაყინული მსაჯი. ფინანსური დაზოგვები ასევე რჩება `HOLD`, თუ `--caption-cost-per-call-usd` არ აწვდავს კონკრეტულ დადებით შეფასებას თითო ზარალზე; სკრიპტი არასოდეს ქმნის არც ერთ შედეგს.

ყოველი ჩარჩო შეზღუდულია 4 MiB-ზე, ყველა خام ჩარჩო ერთად 23 MiB-ზე, და სერიული ბროკერის პასუხი 32 MiB-ზე. კერძო დროებითი დირექტორია იხსნება `finally`-ში. OmniRoute არ აერთიანებს FFmpeg-ს და არ იღებს მორგებულExecutable-ის გზას. წარწერის წინ, ხიდი იყენებს კონსერვატიულ ვიზუალურ დედუპლიკაციის გადაცემას: თითო JPEG შემცირდება 16×16 გრayscale ბუფერში და შედარებულია მხოლოდ ბოლო ჩარჩოსთან. მოთხოვნილი წარწერის ბიუჯეტის შემთხვევაში, რომელიც ერთ ჩარჩოზე მეტია, ამოღება აწვდავს შეზღუდულ კანდიდატთა აუზს, რომელიც მაქსიმუმ ორჯერ იმ ბიუჯეტზეა და არასოდეს მეტია 16 ჩარჩოზე. მოთხოვნილი ზღვარი გამოიყენება მხოლოდ დედუპლიკაციის შემდეგ, პირველ და საბოლოო არჩეულ კანდიდატებს ინარჩუნებენ საბოლოო თხელების დროს, როდესაც ბიუჯეტი მინიმუმ ორი არის. ვერსიონირებული `grayscale-16x16-mean-cells-v2` პოლიტიკა იყენებს საშუალო ლუმას დელტას და იმ თუმბნეილების უჯრედების თანაფარდობას, რომლის ნორმალიზებული დელტა მინიმუმ 0.05-ია. დუბლიკატის ზღვარი არის მუდმივი 0.04, რომელიც აირჩიეს პროგნოზირებადობისთვის, ვიდრე როგორც runtime პარამეტრი. ეს მეორადი მაღალი-კონტრასტული სიგნალი ინარჩუნებს მცირე მოძრაობას და ხილულ-ტექსტურ ცვლილებებს, რომლებიც მხოლოდ საშუალო შედარებით შეიძლება დამალოს. შედარების ან დეკოდერის შეცდომები იხსნება და ინარჩუნებს დაფარვას. გამოსავალი მეტადატა ცალკე გამოყოფს ამოღებულ კანდიდატებს, წარმატებით გამოყენებულ ჩარჩოებს და ვიზუალურ დუბლიკატებს, რომლებიც ჩამოაგდეს.

### PII Masker (`piiMasker.ts`)

მუშაობს **ორივე** ეტაპზე.

- **`preCall`** ასახავს დატვირთვას, გადის `system`, `messages`, `input`, და `prompt` (მათ შორის უბრალო სტრინგის ელემენტები), და იყენებს `processPII()` (განყოფილებიდან `@/shared/utils/inputSanitizer`) სტრინგ `content`/`text` ველებზე. როდესაც `PII_REDACTION_ENABLED=true`, აღმოჩენილი PII არის წაშლილი გასვლის დატვირთვაში. ეს დამოუკიდებელია `INPUT_SANITIZER_MODE`-ისგან (რომელიც მხოლოდ აკონტროლებს პრომპტ-შეტყობინების პოლიტიკას). როდესაც წაშლა გამორთულია, ზარი აღრიცხავს აღმოჩენის რაოდენობებს, კონტენტის ხელახალი წერის გარეშე.
- **`postCall`** ღრმად ასახავს პასუხს, ატარებს `sanitizePIIResponse()`-ს და პასუხების API-ის ფორმის მარკერს (`maskResponsesOutput` — მოიცავს `output_text` და `output[].content[].text`). თუ რაიმე წაშლა ხდება, შეცვლილი პასუხი ცვლის ორიგინალს.

დაცვა არასოდეს ბლოკავს; იგი მხოლოდ ანოტირებს (`meta.detections`, `meta.redacted`) ან ხელახლა წერს.

### Prompt Injection (`promptInjection.ts`)

Detects adversarial structures in user-supplied content and enforces the
configured policy. Behavior is driven by environment variables and constructor
options:

| Setting         | Env var                                                                                               | Default | Effect                                                                                                                                                                                   |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Enabled         | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | When `false`, guardrail short-circuits.                                                                                                                                                  |
| Mode            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | Injection policy: `block`, `warn`, or `log`. (`redact` is accepted for back-compat but does **not** strip injection text; request PII rewrite is controlled by `PII_REDACTION_ENABLED`.) |
| Block threshold | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | Minimum severity required to block. Medium is observe-only at default.                                                                                                                   |

**Mode precedence** (`getMode`): caller `options.mode` →
`INJECTION_GUARD_MODE` **DB feature-flag override** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. A dashboard override therefore wins over the env vars, so the Feature
Flags UI controls the running guard live (no restart). The DB read is fail-safe:
if it errors, the guard falls back to the env-based behavior, and when no
override is set behavior is identical to env-only resolution.

Detection sources:

1. `sanitizeRequest()` from `@/shared/utils/inputSanitizer` (shared detector
   set used elsewhere in the pipeline).
2. Built-in `DEFAULT_GUARD_PATTERNS` (currently `system_override_inline` and
   `markdown_system_block`, both `high` severity).
3. Optional `customPatterns` passed via constructor options (strings, regex,
   or `{ name, pattern, severity }` records).

When `mode === "block"` **and** at least one detection meets the severity
threshold, `preCall` returns `{ block: true, message: "Request rejected:
suspicious content detected" }`. In `warn`/`log` modes the guardrail logs but
allows the call. The shared helper `evaluatePromptInjection()` is also exported
for callers that need to evaluate prompts without going through the registry.

**Scan bound (v3.8.20):** the detector only inspects the **first 16 KB** of
joined prompt text — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 bytes) in
`src/shared/utils/inputSanitizer.ts`. Both `detectInjection()` and
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` before running
the pattern loop. Injection directives sit near the top of an input, so this
caps regex CPU/GC on multi-hundred-KB payloads without weakening detection (cf.
#3932, #4041).

### Credential Masker (`credentialMasker.ts`)

Runs on **both** stages, last in the default chain (priority `95`). Redacts
well-known API-key / secret-token patterns from the outbound payload (message
content, tool-call arguments, tool results) **and** the provider response, so a
credential pasted into a prompt (or echoed back by a tool result) is not leaked
to the upstream provider or back to the client.

- **Opt-in only**, same convention as PII redaction (Hard Rule #20-adjacent):
  disabled unless `settings.credentialRedactionEnabled === true` **or**
  `CREDENTIAL_REDACTION_ENABLED=true`. With it off, the guardrail is a no-op —
  it never blocks and never rewrites.
- `redactCredentials()` walks the full payload/response tree (`walkValue()`,
  prototype-pollution-safe, cycle-safe via `WeakSet`) and replaces matches with
  a `[REDACTED:<type>]` placeholder, cloning only the branches that actually
  changed.
- `CREDENTIAL_PATTERNS` covers LLM provider keys (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS tokens (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), payment keys (Stripe, Square), cloud
  keys (AWS access key, Twilio, SendGrid, Mailgun), private keys / JWTs,
  credential-bearing connection strings (`mongodb://user:pass@...`, etc.), and
  a generic `Authorization`/`x-api-key`/`api-key`/`apikey` header-value
  pattern. Header-shaped keys (`authorization`, `x-api-key`, `api-key`,
  `apikey`) are redacted structurally (value only, scheme prefix like
  `Bearer `/`Basic ` preserved) rather than via the generic text regex.
- The guardrail never blocks; it only rewrites (`modifiedPayload` /
  `modifiedResponse`) and annotates (`meta.credentialsRedacted`, `meta.count`).

Regression guard: `tests/unit/credential-masker-guardrail.test.ts`.

```typescript
  message?: string; // გამოჩნდება როდესაც ბლოკირებულია
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // დაბრუნებულია preCall-ით მოთხოვნის გადაკეთებისთვის
  modifiedResponse?: TValue; // დაბრუნებულია postCall-ით პასუხის გადაკეთებისთვის
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

გარდრაილი "არანაირი ცვლილება" სიგნალს აძლევს `void`, `{}`, ან
`{ block: false }` დაბრუნებით. `modifiedPayload`/`modifiedResponse` დაბრუნება
ცვლილებას ახდენს ჯაჭვში მიმდინარე მნიშვნელობაზე ქვემოთ მდებარე გარდრაილებისთვის.
`signal?: AbortSignal` გადატანს გამიძახებლის სიცოცხლის ციკლს გარდრაილებში. მოთხოვნის გაწყვეტა არის განზრახი წარუმატებელი გამოტოვების გამონაკლისი: მედია ხიდები წყვეტენ მუშაობას და წმენდას, არ აღადგინებენ ნედლ მედია მიზანზე, რომელიც ცნობილია, რომ არ უჭერს მხარს.

## რეგისტრატორი (`registry.ts`)

სინგლტონი `guardrailRegistry` აჩვენებს:

- `register(guardrail)` — ამატებს (ან ცვლის ნორმალიზებული სახელით) გარდრეილს და
  ხელახლა ალაგებს ზრდადი `priority`-ის მიხედვით.
- `clear()` / `list()` — ადმინისტრაციული დამხმარეები.
- `runPreCallHooks(payload, context)` — ახდენს აქტიური გარდრეილების იტერაციას,
  გადასცემს `payload`-ს `modifiedPayload`-ის გავლით და ჩერდება პირველ `block: true`-ზე.
- `runPostCallHooks(response, context)` — იგივე ნაკადი პასუხის მხარეს.
- `resetGuardrailsForTests({ registerDefaults })` — ასუფთავებს მდგომარეობას და სურვილისამებრ
  ხელახლა არეგისტრირებს ნაგულისხმევ პარამეტრებს ტესტის სუფთა იზოლაციისთვის.

ორივე რანერი აბრუნებს `{ blocked, payload|response, results, guardrail?, message? }`-ს,
სადაც `results` არის `GuardrailExecutionResult` ჩანაწერების მასივი, რომელიც მოიცავს
თითოეული გარდრეილის `blocked`, `skipped`, `modified`, `error` და `meta` ველებს,
რაც სასარგებლოა ტრეისინგისთვის.

### გარდრეილების გამორთვა თითო მოთხოვნაზე

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` აგროვებს
გარდრეილების სახელების დედუპლიცირებულ სიას, რომლებიც უნდა გამოტოვებულ იქნას
მიმდინარე მოთხოვნისთვის. წყაროები (ყველა არასავალდებულო, ყველა გაერთიანებულია):

- `apiKeyInfo.disabledGuardrails`
- მოთხოვნის სხეული `disabledGuardrails` (ზედა დონის)
- მოთხოვნის სხეული `metadata.disabledGuardrails`
- ჰედერი `x-omniroute-disabled-guardrails` (ან მოძველებული
  `x-disabled-guardrails`)

მნიშვნელობები შეიძლება იყოს სტრიქონების მასივები ან მძიმით გამოყოფილი სტრიქონი;
სახელები ნორმალიზდება პატარა ასოებით kebab-case-ში (`pii_masker` → `pii-masker`).
შედეგი გადაეცემა `context.disabledGuardrails`-ის გავლით რეგისტრატორს,
რომელიც გამოტოვებს შესაბამის გარდრეილებს (`skipped: true` `results`-ში).

## შესრულების თანმიმდევრობა

ყოველი მოთხოვნისთვის, რომელიც გადის `src/sse/handlers/chat.ts`-სა და `open-sse/handlers/chatCore.ts`-ის გავლით:

1.  `resolveDisabledGuardrails(...)` აგებს გამოტოვების სიას API გასაღებიდან, სხეულიდან და სათაურებიდან.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` ასრულებს დამცავ მექანიზმებს პრიორიტეტის ზრდადი თანმიმდევრობით:
    - გამორთული დამცავი მექანიზმები აღირიცხება როგორც `skipped`.
    - თითოეული დამცავი მექანიზმის `preCall`-მა შეიძლება გადაწეროს მონაცემთა პაკეტი `modifiedPayload`-ის მეშვეობით.
    - პირველი `block: true` წყვეტს ჯაჭვს და დამმუშავებელი აბრუნებს დამცავი მექანიზმის უარყოფის პასუხს.
3.  (პოტენციურად გადაწერილი) მონაცემთა პაკეტი მიედინება კომბინირებულ მარშრუტიზაციასა და ზედა დინების გაგზავნაში.
4.  პასუხის აწყობის შემდეგ, `guardrailRegistry.runPostCallHooks(...)` აწარმოებს იმავე ჯაჭვს პასუხზე. `block: true` აქ აგდებს ზედა დინების პასუხს.

დამცავი მექანიზმები, რომლებიც შეცდომას აგდებენ, აღირიცხება `error: <message>`-ით და აღინიშნება `logger.warn`-ის მეშვეობით, მაგრამ ჯაჭვი გრძელდება — დიზაინით ღიაა წარუმატებლობისთვის.

## მორგებული Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ნაბიჯები:

1.  შექმენით `src/lib/guardrails/myGuardrail.ts`, რომელიც აფართოებს `BaseGuardrail`-ს.
2.  განახორციელეთ `preCall` და/ან `postCall`.
3.  ან დაარეგისტრირეთ იმპორტის დროს (`registerDefaultGuardrails`-დან დამატებით) ან გამოიძახეთ `guardrailRegistry.register(...)` გაშვების დროს — რეესტრი ჩაანაცვლებს ნებისმიერ წინა guardrail-ს იგივე ნორმალიზებული სახელით.
4.  დაამატეთ ტესტები `tests/unit/`-ში (არსებული მაგალითები: `tests/unit/guardrails-registry.test.ts`, `tests/unit/prompt-injection-guard.test.ts`, `tests/unit/guardrails/visionBridge.test.ts`).

## ტესტირება

გამოიყენეთ `resetGuardrailsForTests()` ტესტებს შორის, რათა დაიწყოთ ცნობილი მდგომარეობიდან. გადაეცით `{ registerDefaults: false }`, რათა დაიწყოთ ცარიელი რეესტრით და დაარეგისტრიროთ მხოლოდ ტესტირებადი guardrails. Vision Bridge იღებს დამოკიდებულების ინექციას (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge აჩვენებს ექვივალენტურ წერტილებს პარამეტრებისთვის, შესაძლებლობებისთვის, STT მოდელის არჩევისთვის, სერთიფიკატების შემოწმებისთვის და ტრანსკრიფციისთვის. ამიტომ, ტესტებს შეუძლიათ ორივე ნაკადის შემოწმება მონაცემთა ბაზის ან ქსელზე წვდომის გარეშე.

## ინექციისგან დამცავი მარშრუტების დაფარვა და წითელი გუნდი (ფაზა 8 · ბლოკი D)

ინექციისგან დამცავი მექანიზმი (`createInjectionGuard` / `withInjectionGuard`) მოიცავს ყველა მარშრუტს, რომელიც იღებს მომხმარებლის მოთხოვნებს. ის ითვალისწინებს `INJECTION_GUARD_MODE`-ს (ნაგულისხმევი `warn` = მხოლოდ ჟურნალი; `block` = აბრუნებს HTTP 400 `SECURITY_001`).

| ტიპი            | მარშრუტები                                                                                                                                           | ნაგულისხმევი რეჟიმი |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| Text (existing) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                |
| Generative      | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                |
| Data            | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                |

ტექსტის ამოღება (`extractMessageContents`) მოიცავს `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`-ს.

**წითელი გუნდი (ღამის, `nightly-llm-security.yml`):** promptfoo ამოწმებს, რომ თითოეული მარშრუტი ბლოკავს OWASP-LLM კორპუსს `INJECTION_GUARD_MODE=block` რეჟიმში; garak აწარმოებს ზონდებს (გამოტოვებს საიდუმლოს გარეშე). `moderations` შედის თანმიმდევრულობისთვის — ოპერატორებს ბლოკირების რეჟიმში შეუძლიათ მისი გათავისუფლება `resolveDisabledGuardrails`-ის მეშვეობით.

ღამის სამუშაო პროცესი (`.github/workflows/nightly-llm-security.yml`, cron + ხელით გაშვება) მოიცავს ორ დავალებას:

- **`promptfoo-guard` (ბლოკირება)** — აწარმოებს `promptfoo eval -c promptfooconfig.yaml`-ს `INJECTION_GUARD_MODE=block`-ით. თითოეული მტრული შემთხვევა (მაგ. „უგულებელყავით ყველა წინა ინსტრუქცია…“, DAN-ის სტილის jailbreaks) ადასტურებს, რომ პასუხი შეიცავს `error.code === "SECURITY_001"`, ანუ guard-მა რეალურად უარყო მოთხოვნა.
- **`garak` (საკონსულტაციო)** — აწარმოებს garak `--probes promptinject,dan,leakreplay`-ს ლოკალური OmniRoute ინსტანციის წინააღმდეგ (`http://localhost:20128/v1`). დაცულია პროვაიდერის საიდუმლო გასაღებით (`PROMPTFOO_PROVIDER_KEY`); გამოტოვებს შეცდომის გარეშე და დამატებულია `|| true`, ასე რომ, ის აფიქსირებს CI-ის ჩავარდნის გარეშე.

guard დამხმარის (`createInjectionGuard` / `withInjectionGuard`) დაფარვა მოიცავს ყველა მოთხოვნის შემცველ `/v1` მარშრუტს; მოთხოვნის ტექსტი ამოღებულია `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`-დან `extractMessageContents()` ფუნქციის მიერ `src/shared/utils/inputSanitizer.ts`-ში.
