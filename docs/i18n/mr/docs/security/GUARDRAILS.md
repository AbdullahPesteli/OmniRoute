> **सत्याचा अधिकृत स्रोत:** `src/lib/guardrails/`
> **शेवटचे अद्यतन:** 2026-08-29 — v3.8.51 (Video Bridge प्रतिलेखाचा उगम कॉलरद्वारे घोषित केला जातो,
> अद्याप सर्व्हरद्वारे सत्यापित केलेला नाही — #11661 नुसार स्पष्टीकरण दिले)

Guardrails, OmniRoute आणि अपस्ट्रीम प्रदात्यांच्या सीमेवर सुरक्षितता, धोरणे आणि आशय रूपांतरे लागू करतात. प्रत्येक guardrail विनंती payloads (`preCall`) आणि अपस्ट्रीम प्रतिसाद (`postCall`) तपासू शकतो (आणि पर्यायाने नाकारू, रूपांतरित करू किंवा त्यांवर भाष्य नोंदवू शकतो).

प्रणाली **fail-open** आहे: एखाद्या guardrail च्या अंमलबजावणीदरम्यान अपवाद निर्माण झाल्यास, विनंती अयशस्वी करण्याऐवजी registry त्रुटीची नोंद करून पुढील guardrail वर प्रक्रिया सुरू ठेवते. अवरोधित करणे हा नेहमी स्पष्ट निर्णय (`block: true`) असतो, अपघाताने ते कधीही होत नाही.

## अंतर्निहित गार्डरेल्स

नोंदणी आयातावर प्राधान्य क्रमाने सहा गार्डरेल्स स्वयंचलितपणे लोड करते
(पहा `registry.ts` → `registerDefaultGuardrails()`):

| प्राधान्य | नाव                 | स्टेज(स)       | फाइल                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`      | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`      | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

कमी प्राधान्य क्रमांक **प्रथम** चालवतात.

### व्हिजन ब्रिज (`visionBridge.ts`) — मोडालिटी ब्रिज PR-1

**नॉन-व्हिजन मॉडेल्स** वर लक्षित चित्र-धारक विनंत्या अडवते आणि संपूर्ण विनंती
एक व्हिजन-सक्षम मॉडेलकडे पुनर्निर्देशित करते किंवा चित्र भागांना
कॉन्फिगर करण्यायोग्य व्हिजन मॉडेलद्वारे तयार केलेल्या मजकूर वर्णनांसह बदलते.
हे मजकूर-फक्त प्रदात्यांना मल्टीमोडल पेलोड्स पारदर्शकपणे हाताळण्याची परवानगी देते.

प्रवाह:

1. लक्ष्य मॉडेल आधीच व्हिजनला समर्थन देत असल्यास वगळा (जर ते
   मजबूर-ब्रिज यादी `isVisionBridgeForcedModel` मध्ये दिसत नसेल तर).
2. `extractImageParts(messages)` द्वारे चित्र भाग काढा
   (`visionBridgeHelpers.ts`), जे **एकत्रित मीडिया
   डिटेक्टर** `detectMediaParts()` कडेDelegates करते `open-sse/utils/mediaParts.ts` मध्ये — एकच सत्य स्रोत जो
   कॉम्बो सुसंगतता फिल्टरसह सामायिक केला जातो.
   काढणे `replaceImageParts` परत जोडू शकणाऱ्या आकारांच्या टॉप-लेव्हल भागांपर्यंत
   परवानगी दिली जाते (काढा↔बदल करार): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, आणि Responses API `input_image`. नेस्टेड हिट्स आणि
   फक्त संकेतक आकार कॉम्बो-फिल्टर सामग्री आहेत आणि कधीही काढले जात नाहीत.
   काहीही सापडले नाही तर वगळा.
3. `resolveVisionBridgeRuntimeSettings()` द्वारे रनटाइम कॉन्फिगरेशन निश्चित करा
   (`src/shared/constants/modalityBridgeDefaults.ts`): नवीन `modalityBridge*`
   सेटिंग्ज कीज जिंकतात; वारसा `visionBridge*` कीज एक **एक-चक्र
   बॅकफॉल** (रोलबॅक विंडो) म्हणून राहतात. ब्रिज अक्षम असताना कोणत्याही मीडिया प्रवासापूर्वी वगळा.
4. मोड निवडक (`modalityBridgeVisionMode`, खालील तक्त्यात पहा) पुनर्निर्देशित करणे विरुद्ध वर्णन ठरवते. पुनर्निर्देशित `modifiedPayload` परत करते ज्यामध्ये फक्त `model`
   बदललेले असते, तसेच मेटा `{ rerouted, fromModel, toModel, imagesKept }`.
5. वर्णन मार्ग: `maxImages` वर चित्रे मर्यादित करा, कार्य-ज्ञान असलेला प्रॉम्प्ट तयार करा,
   वर्णन कॅशसाठी सल्ला घ्या, व्हिजन मॉडेलला **समांतर** कॉल करा
   (`Promise.allSettled`), आणि त्यांच्या जागी `[Image N]: <description>` मजकूर भाग इंजेक्ट करा. एक अयशस्वी वर्णन `null` देते आणि मूळ चित्र भाग **सुरक्षित** राहतो (#4012) — कॉम्बो वर्णन मार्गावर प्रत्येक
   वर्णन अयशस्वी झाल्यास, जिथे एक निश्चित नॉन-व्हिजन अपस्ट्रीम
   `(unavailable — no vision-capable provider connected)` स्टब मिळतो (#8430).
6. `modifiedPayload` + मेटा (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) परत करा.

#### मोड निवडक (`modalityBridgeVisionMode`)

| मोड        | डिफॉल्ट | वर्तन                                                                                                                                                                                                                                                                                                      |
| ---------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | वारसा ह्युरिस्टिक, निःशंक (#6640/#7204): नॉन-कॉम्बो/`auto/` मॉडेल्स सर्वोत्तम व्हिजन मॉडेलकडे पुनर्निर्देशित करतात जोपर्यंत मूळ मॉडेलकडे वापरण्यायोग्य क्रेडेन्शियल्स नाहीत (तेव्हा वर्णन); कॉम्बो लक्ष्य नेहमीच वर्णन करतात.                                                                              |
| `describe` |         | नेहमीच वर्णन करा — पुनर्निर्देशित ब्लॉक पूर्णपणे वगळला जातो; वापरकर्त्याने निवडलेले मॉडेल नेहमी उत्तर देते.                                                                                                                                                                                                |
| `reroute`  |         | मजबूर पुनर्निर्देशित करा: क्रेडेन्शियल-धारक मॉडेल गार्ड वगळला जातो. पुनर्निर्देशित-**लक्ष्य** क्रेडेन्शियल गार्ड अद्याप लागू होते — जेव्हा वापरण्यायोग्य व्हिजन लक्ष्य अस्तित्वात नाही, तेव्हा विनंती वर्णन करण्यासाठी खाली जाते जेणेकरून कच्ची चित्रे कधीही मजकूर-फक्त बॅकएंडपर्यंत पोहोचत नाहीत (#8430). |

मजबूर मोड **पूर्वी** स्वयंचलित ह्युरिस्टिक चालवतात; `auto` वर्तन
पूर्व-PR-1 गार्डरेलसारखेच आहे.

#### API-key स्कोप (`visionBridgeKeyScope.ts`)

जेव्हा कॉलरचा API की `allowedConnections`, कोटा पूल
(`allowedQuotas`) किंवा मॉडेल (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) वर निर्बंध घालते,
तेव्हा ब्रिज फक्त पुनर्निर्देशित आणि वर्णन मॉडेल निवडतो ज्याचा की वापर करू शकते,
ज्या कनेक्शनवर की वापरू शकते. वर्णन कॉल नंतर नेहमीच OmniRoute स्व-सर्कलद्वारे जातो
`x-omniroute-self-loop-key-id` हेडरसह, त्यामुळे प्राप्त करणारा चॅट विनंती
त्या कीच्या कनेक्शन आणि मॉडेल धोरणाची पुन्हा अंमलबजावणी करतो. `enforceApiKeyPolicy()`
त्या हेडरला फक्त स्व-सर्कल बिअररसोबत एकत्रितपणे मान्यता देते, त्यामुळे ते फक्त
अॅक्सेस कमी करू शकते, आणि एक आयडी जो निराकरण होत नाही तो नाकारला जातो.

जर कीसाठी कोणतेही व्हिजन मॉडेल परवानगी नसेल, तर वर्णन मार्ग बाजूला जातो आणि
विनंती अपरिवर्तित राहते, अक्षम गार्डरेलसारखेच फेल-ओपन वर्तन (मेटा `{ skipped: true, reason: "no_permitted_vision_model" }`).
कीशिवाय विनंत्या, आणि या निर्बंधांशिवाय कीज, अगदी पूर्वीप्रमाणेच वर्तन करतात.

#### कार्य-ज्ञान असलेला वर्णन प्रॉम्प्ट (`modalityBridgeVisionTaskAware`)

डिफॉल्ट **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) अंतिम
उपयोगकर्ता संदेशाचा मजकूर (500 अक्षरांपर्यंत कमी केलेला) बेस
वर्णन प्रॉम्प्टमध्ये जोडतो, वर्णनाला वापरकर्त्याने खरोखरच विचारलेले
काय आहे याकडे वळवितो (codex-vision-proxy पॅटर्न) आणि दृश्य मॉडेलला
दृश्यमान मजकूर ट्रान्सक्राइब करण्यास विचारतो. फ्लॅग बंद असताना — किंवा
कोणताही वापरकर्ता मजकूर नसताना — बेस प्रॉम्प्ट अपरिवर्तित वापरला जातो.

वर्णन स्वयं-लूपचा स्वतःचा OpenAI-संगत विनंती (`callVisionModelSingle()`
`visionBridgeHelpers.ts` मध्ये) नेहमी `image_url.detail: "high"` ची
विनंती करते — कोणत्याही ग्राहक सिग्नलवर गेट न करता, प्रत्येक कॉलर/प्रदात्यासाठी
अविरत. कमी-तपशील नमुना OCR अचूकतेला कमी करतो, विशेषतः त्या मजकूर-ट्रान्सक्रिप्शन
कार्यांसाठी ज्यासाठी हा प्रॉम्प्ट विचारतो, त्यामुळे वर्णन कॉल नेहमी उच्च
तपशीलासाठी विचारतो, मूळ इनबाउंड विनंतीने वापरलेल्या तपशील स्तरावर
असले तरीही. हे केवळ अंतर्गत वर्णन विनंती शरीरावर परिणाम करते; हे OmniRoute कसे
कॉलरच्या स्वतःच्या `image_url.detail` ला प्राथमिक विनंतीवर पुढे पाठवते
यामध्ये बदल करत नाही — तो डिफॉल्ट स्वतंत्रपणे लागू केला जातो, आणि फक्त
ओळखलेल्या OpenCode ग्राहकांसाठी, `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`)
मध्ये. वर्णन स्वयं-लूपचा Anthropic वायर-फॉर्मेट शाखेत `detail` क्षेत्र नाही
आणि दोन्ही डिफॉल्टवर परिणाम होत नाही.

#### वर्णन आउटपुट कॅप (`modalityBridgeVisionMaxChars`)

| की                             | डिफॉल्ट | श्रेणी              |
| ------------------------------ | ------- | ------------------- |
| `modalityBridgeVisionMaxChars` | `0`     | `0` किंवा 100–50000 |

`0` (डिफॉल्ट) म्हणजे **कॅप नाही** — `callVisionModel()` द्वारे परत केलेले
वर्णन अपरिवर्तितपणे पास केले जाते, विद्यमान वर्तन जतन करते. 100–50000
श्रेणीतील कोणतीही किंमत वर्णनाला `…` उपसर्गासह कमी करते, जेणेकरून ते
`[Image N]: <description>` म्हणून पुन्हा जोडले जाईल
(`VisionBridgeGuardrail.preCall()` `src/lib/guardrails/visionBridge.ts` मध्ये).
हे तपशील-गडद OCR कार्यांसाठी वाढवा जिथे डाउनस्ट्रीम मॉडेलला पूर्ण
ट्रान्सक्रिप्शनची आवश्यकता आहे; चाटी दृश्य मॉडेलवर टोकन वापर मर्यादित
करण्यासाठी कमी करा. डॅशबोर्ड क्षेत्र Vision टॅबच्या अॅडव्हान्स्ड पॅनेलवर
(`modality-bridge-max-chars` `ModalityBridgeVisionTab.tsx` मध्ये) आहे आणि
1 आणि 99 दरम्यान कोणतीही किंमत 100 मजल्यावर क्लीप करते, तर स्पष्ट `0`
अपरिवर्तित ठेवते — `0` स्वतःच एक वैध Zod मूल्य आहे
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), फक्त
"unset" डिफॉल्ट नाही.

#### वर्णन कॅशे (`modalityBridge/bridgeCache.ts`)

वर्णन आउटपुटसाठी इन-मेमरी LRU + TTL कॅशे, सामायिक प्रक्रिया-व्यापी.
की = `sha256(imageRef + composedPrompt + configuredBridgeModel)` लांबी-पूर्वसूचक
फ्रेमिंगसह (कोणतीही क्षेत्र-सीमा टकराव नाही). मॉडेल घटक
**कॉन्फिगर केलेला** ब्रिज मॉडेल आहे, जो प्रत्यक्षात उत्तर दिला —
`callVisionModel` अंतर्गत मागे जाऊ शकतो, आणि प्रत्येक प्रयत्नानुसार की
कॅशे तुकडे करेल. अयशस्वी वर्णने कधीही कॅश केले जात नाहीत. सेटिंग्ज:

| की                              | डिफॉल्ट | श्रेणी  |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### रिमोट इमेज नॉर्मलायझेशन (स्वयं-लूप वर्णन/base64 फेच)

जेव्हा ब्रिज एक **रिमोट** इमेज स्वतः फेच करतो — Anthropic वर्णन
स्वयं-कल आणि क्लॉड-वायर-फॉर्मेट बेस64 रूपांतरण
(`ensureBase64ImagesForClaudeWire`), दोन्ही `fetchRemoteImageAsDataUri()`
`visionBridgeHelpers.ts` मध्ये — परिणामी डेटा URI `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) द्वारे पास केला जातो
आणि दृश्य-मॉडेल विनंतीमध्ये समाविष्ट केला जातो. मोठ्या आकाराच्या
इमेजेस **2048px लांब काठ** पर्यंत कमी केल्या जातात (जे OpenAI/Anthropic
सर्व्हर-साइडवर आधीच लागू करतात), जे अपलोड बाइट्स/लेटन्सी कमी करते
दृश्य मॉडेल काय पाहते ते बदलले बिना. आकार बदलण्यासाठी `sharp` वापरले जाते,
डायनॅमिक इम्पोर्टद्वारे लोड केले जाते: ज्या प्लॅटफॉर्मवर त्याचा
मूळ बायनरी लोड होण्यात अयशस्वी होतो, `normalizeDataUri()` **कधीही
फेकत नाही** — हे मूळ बाइट्सच्या पास-थ्रूवर मागे जाते, त्यामुळे वर्णन/base64-रूपांतरण
मार्ग नेहमी कार्यरत राहतो. नॉन-इमेज बाइट्स (एक फेच जे डिकोडेबल
इमेज परत करत नाही) देखील अपरिवर्तित पास केले जातात. हे नॉर्मलायझेशन
ब्रिजने स्वतःच्या स्वयं-कलसाठी फेच केलेल्या इमेजेसवर मर्यादित आहे —
हे कधीही कॉलरच्या कच्च्या पास-थ्रू पेलोडवर लागू केले जात नाही, फक्त
ऑप्ट-इन-फक्त म्यूटेशन तत्त्वाशी सुसंगत (हार्ड नियम #20).

#### सेटिंग्ज स्कीमा + स्थलांतर

नवीन `modalityBridge*` की `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts` मध्ये) मध्ये Zod-प्रमाणित आहेत:
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCache*` त्रीक, आणि ऑडिओ ब्रिजद्वारे वापरलेला
`modalityBridgeAudio*` समूह. स्थलांतर `141_modality_bridge_settings.sql`
मौजूदा वारसा `visionBridge*` मूल्ये जुळणाऱ्या नवीन कींमध्ये कॉपी करते
(idempotent, कधीही ऑपरेटर-सेट `modalityBridge*` मूल्य ओव्हरराइट करत नाही);
वारसा की एक वाचन फॉलबॅक म्हणून एक रिलीज चक्रासाठी स्वीकारले जातात.

#### पारदर्शकता हेडर + आकडेवारी

वर्णन-परिवर्तित प्रतिसादांमध्ये `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
असते (जे `buildModalityBridgeHeader()` द्वारे तयार केले जाते
`modalityBridge/bridgeStats.ts` मध्ये, `withModalityBridgeHeader()`
`src/sse/handlers/chatHelpers.ts` मध्ये मुद्रित केले जाते). पुनर्निर्देशित
विनंत्या **कोणताही** हेडर घेत नाहीत — पेलोड अपरिवर्तित होता आणि
मॉडेल स्वॅप प्रतिसादाच्या शरीरातील `model` क्षेत्रात आधीच दिसत आहे.

`GET /api/modality-bridge/stats` (व्यवस्थापन प्रमाणीकरण, `GET /api/settings` च्या समान स्तरावर) `vision`, `audio`, आणि `video` साठी इन-मेमोरी प्रति-मोडालिटी काउंटर `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` परत करते. `averageLatencyMs` चा विभाजक म्हणून `latencySamples` वापरला जातो, सर्व प्रयत्न नाही; वेळ न घेणारी क्रिया शून्य-मिलिसेकंद नमुना तयार करत नाही. `bridged` यशस्वी रूपांतरणांसाठी मागील-सुसंगत उपनाम म्हणून राहतो; अपयशी प्रयत्न त्याला वाढवत नाहीत. काउंटर प्रक्रिया पुन्हा सुरू झाल्यावर डिझाइननुसार रीसेट होतात (टेलीमेट्री, लेखा नाही).

#### डॅशबोर्ड कॉन्फिगरेशन

विशिष्ट डॅशबोर्ड पृष्ठ आहे `/dashboard/settings/modality-bridge`. त्याचा URL-प्रवेशयोग्य `Vision`, `Audio`, आणि `Video` टॅब `tab` मूल्य बदलताना क्वेरी पॅरामीटर्स जतन करतात. Vision टॅब सक्षमतेचे, मोड, मॉडेल निवड (स्वयंचलित डिफॉल्टसह), कार्य-आधारित प्रॉम्प्टिंग, प्रगत टाइमआउट/प्रतिमा/वर्णन-लांबी/कॅश मर्यादा, रनटाइम काउंटर, आणि एक संरक्षित नमुना विनंती उघडतो. Audio टॅब देखील सक्रिय आहे: हे सक्षमतेचे, STT-फक्त मॉडेल पिकर ऑटो, टाइमआउट/कमाल-क्लिप मर्यादा, ऑडिओ काउंटर, आणि एक `input_audio` नमुना चाचणी उघडते. Video टॅब कार्यशील आहे: हे FFmpeg/ffprobe रनटाइम स्थितीची माहिती देते — चार स्पष्ट UI स्थितींपैकी एक (`unknown` जेव्हा प्रॉब उडत आहे किंवा पूर्ण होऊ शकत नाही, `restricted` एका नॉन-लूपबॅक डॅशबोर्ड होस्टवर जिथे प्रॉब क्लायंट-साइडवर वगळला जातो, `unavailable` एकदा प्रॉब केले आणि गायब असल्याचे पुष्टी केले, किंवा `available` FFmpeg/ffprobe आवृत्त्यांसह) — सक्षम/मॉडेल/फ्रेम/व्हिडिओ/टाइमआउट मर्यादा टिकवते, मॉडेल पिकरला व्हिजन-सक्षम मॉडेल्सवर फिल्टर करते, आणि व्हिडिओ काउंटर उघडते.

AI सेटिंग्ज अंतर्गत पूर्वीचा Vision Bridge कार्ड नवीन पृष्ठासाठी एक सुसंगतता लिंक आहे; याला फॉर्मची दुसरी प्रत नाही. मीडिया प्रदाते देखील इमेज-टू-टेक्स्ट आणि स्पीच-टू-टेक्स्ट कार्यप्रवाहांना संबंधित मोडालिटी ब्रिज टॅबवर लिंक करतात, विद्यमान स्पीच-टू-टेक्स्ट प्लेग्राउंड काढून टाकत नाहीत.

**स्वयं-लूप प्रवेश बायपास:** जेव्हा वर्णन कॉल OmniRoute च्या स्वतःच्या `/v1` स्वयं-लूप (असामान्य प्रदाता मॉडेल) द्वारे मार्गक्रमण करते, तेव्हा उप-प्रार्थना `x-omniroute-admission-bypass: internal` पाठवते आणि निश्चित केलेल्या स्वयं-लूप क्रेडेन्शियलसह प्रमाणित केले जाते — स्थानिक मोडमध्ये स्थानिक `sk_omniroute` सेंटिनल, किंवा ऑपरेटर-कॉन्फिगर केलेले `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env की (#1350) त्यामुळे `REQUIRE_API_KEY=true` तैनात केलेले वर्णन कॉल चालवू शकतात. बायपास फक्त त्या अचूक क्रेडेन्शियलसाठी मान्य आहे, त्यामुळे बाह्य क्लायंट हेडरचा वापर करून प्रवेश वगळू शकत नाहीत.

ऐतिहासिक डिफॉल्ट्स `src/shared/constants/visionBridgeDefaults.ts` मध्ये आहेत; नवीन मोड/कार्य-आधारित/कॅश डिफॉल्ट्स आणि सेटिंग्ज रिझॉल्व्हर `src/shared/constants/modalityBridgeDefaults.ts` मध्ये आहेत. गार्डरेल एक `deps` कन्स्ट्रक्टर पर्याय उघडतो जेणेकरून चाचण्या खोटी `getSettings` आणि `callVisionModel` अंमलबजावणी समाविष्ट करू शकतात.

### ऑडिओ ब्रिज (`audioBridge.ts`) — मोडालिटी ब्रिज PR-3

ऑडिओ असलेल्या चॅट विनंत्या लक्ष्यापर्यंत पोहोचण्यापूर्वी हस्तक्षेप करते जे ऑडिओ इनपुट स्वीकारण्यास ज्ञात नाही. हे कधीही चॅट विनंती पुनःमार्गित करत नाही: ऑडिओ भाग विद्यमान OpenAI-सुसंगत मल्टीपार्ट एंडपॉइंटद्वारे ट्रान्सक्राइब केले जातात आणि निवडलेला चॅट मॉडेल मजकूर ट्रान्सक्रिप्टसह पुढे जातो.

प्रवाह:

1. `getResolvedModelCapabilities()` द्वारे `supportsAudio` निश्चित करा. स्पष्ट प्रदाता-नोंदणी मेटाडेटा जिंकते, नंतर स्थिर मॉडेल मेटाडेटा, नंतर समन्वयित `modalities_input`. `audio` न असलेली घोषित इनपुट यादी `false` आहे; कोणतीही क्षमता पुरावा `null` राहते. दोन्ही `false` आणि `null` संवेदनशील ब्रिज सक्रिय करतात, तर `true` त्याला बायपास करते.
2. `modalityBridgeAudio*` सेटिंग्ज निश्चित करा आणि प्रत्येक संदेशातून सामायिक `detectMediaParts()` डिटेक्टरद्वारे स्प्लायस करण्यायोग्य टॉप-लेव्हल ऑडिओ भाग काढा. समर्थित वायर आकार OpenAI `input_audio`, `audio_url`, आणि `source.media_type: "audio/*"` आहेत. नेस्टेड ऑडिओ मार्गक्रमणासाठी शोधले जाते परंतु स्प्लायस पथाद्वारे काढले जात नाही. काम `modalityBridgeAudioMaxClips` द्वारे मर्यादित आहे; नंतरचे भाग अनछुई राहतात.
3. कॉन्फिगर केलेले `provider/model` मान्य करा, किंवा `selectAudioBridgeModel()` ला स्थिर कॅटलॉग क्रमाने `AUDIO_TRANSCRIPTION_PROVIDERS` चालवू द्या आणि वापरण्यायोग्य सक्रिय प्रदाता क्रेडेन्शियलसह पहिला मॉडेल निवडा.
4. `callAudioTranscription()` base64/data-URI ऑडिओला मल्टीपार्ट `file` मध्ये रूपांतरित करते, किंवा सार्वजनिक-फक्त बाह्य गार्डद्वारे DNS पिनिंग आणि 25 MB बंधनासह दूरस्थ `audio_url` डाउनलोड करते. नंतर ते फाइल आणि निवडलेला मॉडेल स्थानिक `/v1/audio/transcriptions` स्वयं-लूपवर POST करते, `resolveSelfLoopBearer()` सह प्रमाणित केले जाते. विद्यमान ट्रान्सक्रिप्शन मार्ग सामान्य क्रेडेन्शियल लुकअप, कूलडाऊन/रेट-लिमिट हाताळणी, आणि प्रदाता वितरण करते.
5. यशस्वी कॉल त्यांच्या भागांना `[Audio N]: <transcript>` सह बदलतात. कॉल `Promise.allSettled` सह चालवले जातात: एकटा अपयश त्या मूळ ऑडिओ भागाला जतन करतो (#4012 करार). जर प्रत्येक कॉल अपयशी झाला आणि लक्ष्य सिद्ध झाले `supportsAudio === false`, तर भाग बनतात `[Audio N]: (unavailable — no STT provider connected)` (#8430 करार). अज्ञात लक्ष्य (`null`) साठी, सर्व-अपयश परिणाम अनछुई राहतो. सिद्ध केलेले मजकूर-फक्त लक्ष्य ज्याला वापरण्यायोग्य STT क्रेडेन्शियल नाही, त्याला नेटवर्क कॉल न करता समान स्पष्ट स्टब प्राप्त होते.

यशस्वी ट्रान्सक्रिप्ट्स प्रक्रिया-व्यापी मोडालिटी ब्रिज LRU/TTL कॅश वापरतात. की ऑडिओ संदर्भ, स्थिर `audio-transcription` ऑपरेशन लेबल, आणि निवडलेला STT मॉडेल यांचे संयोजन करते; अपयश कधीही कॅश केले जात नाही. ऑडिओ प्रयत्न सामायिक `bridged`, `cacheHits`, `failures`, आणि `lastUsedAt` काउंटर अपडेट करतात. रूपांतरित प्रतिसादांमध्ये `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` असते; अनछुई विनंत्यांना ऑडिओ ब्रिज विभाग मिळत नाही.

रनटाइम सेटिंग्ज DB-समर्थित आणि Zod-मान्यताप्राप्त आहेत:

| की                            | डिफॉल्ट | श्रेणी           |
| ----------------------------- | ------- | ---------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —                |
| `modalityBridgeAudioModel`    | `""`    | ऑटो किंवा STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000      |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10             |

सामायिक कॅश `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, आणि `modalityBridgeCacheMaxEntries` द्वारे नियंत्रित राहतो.

### व्हिडिओ ब्रिज (`videoBridge.ts`, `videoBridgePipeline.ts`)

चॅट पूर्णता `messages` आणि प्रतिसाद
API `input` मध्ये टार्गेट कॉल करण्यापूर्वी टॉप-लेव्हल व्हिडिओ भागांना अडवतो ज्याला ज्ञात स्थानिक व्हिडिओ समर्थन नाही.
समर्थित आकार आहेत `input_video`, `video_url`, `video_source`, HTTPS URLs,
आणि `data:video/*;base64,...` डेटा URI. मजकूरामध्ये साधे फाइल नाव व्हिडिओ म्हणून मानले जात नाहीत.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) विनंती प्रवास, क्षमता/धोरण तपासणी, प्रति-विनंती एकत्रीकरण, आणि प्रतिसाद पेलोडची मालकी ठेवतो.
प्रति-व्हिडिओ काम — अधिग्रहण, संपूर्ण-परिणाम कॅश, फ्रेम अनुक्रमाचे वर्णन (जे कोणत्याही कॉलर-घोषित ऑडिओ ट्रान्सक्रिप्टला एकत्र करते), आणि प्रति-प्रयत्न मेट्रिक्स/अवरोध/स्वच्छता — `processVideoPart` च्या मागे लपलेले आहे
`videoBridgePipeline.ts` मध्ये, `preCall` च्या लूपमध्ये प्रत्येक व्हिडिओ भागासाठी एकदा कॉल केले जाते.
त्या मॉड्यूलने स्पष्ट पोर्ट सीमांचे परिभाषित केले आहे `VideoMediaBrokerPort`
(बाइट्स अधिग्रहण आणि नमुना फ्रेम्स काढणे), `VideoAudioTranscriptionPort`
(नमुना कॅप्शनसह कॉलर-घोषित ऑडिओ ट्रान्सक्रिप्ट एकत्र करणे), आणि
`VideoDrilldownPort` (लेगसी रॉ-स्टोअर आकार). उत्पादन STT आणि फ्रेम धारणा
`createVideoSttAdapter` आणि `createVideoDrilldownAdapter` च्या माध्यमातून वर्णन करणाऱ्या पोर्टच्या आसपास रचना केलेली आहे; नंतरचा सामायिक अपारदर्शक-हँडल जीवनचक्र वापरतो.

सार्वजनिक `/v1` विनंती मार्ग कधीही उपप्रक्रिया आयात किंवा कॉल करत नाही. दूरस्थ
व्हिडिओ 50 MiB मर्यादेखाली डाउनलोड केले जातात; इनलाइन बेस64 व्हिडिओंमध्ये
संरक्षित 36 MiB डिकोड केलेल्या प्रति-व्हिडिओ कॅप आहे जेणेकरून मॉडेल/messages/framing envelope
सार्वजनिक JSON विनंती प्रवेश मर्यादेत 50 MiB मध्ये राहू शकेल. इनलाइन
लांबी आणि डिकोड-आकार अंदाज आवंटनापूर्वी तपासले जातात. HTTPS
प्रारंभिक दूरस्थ URL आणि प्रत्येक पुनर्निर्देशनावर आवश्यक आहे, विद्यमान
सार्वजनिक-फक्त बाह्य गार्डसह DNS पिनिंग वापरून. बाइट्स नंतर अचूक अंतर्गत
`POST /api/modality-bridge/video/extract` ब्रोकर सीमेला पार करतात. त्या मार्गावर
`LOCAL_ONLY` आणि `SPAWN_CAPABLE` दोन्ही आहेत, फक्त प्रति-प्रक्रिया प्रमाणित,
विश्वासार्ह-लूपबॅक विनंती स्वीकारते, आणि कधीही URL, फाइल सिस्टम पथ, कार्यान्वित,
किंवा तर्क सूची स्वीकारत नाही. API बॉडी-आकार पाईपलाइन आणि हँडलरचा वाढता बॉडी
रेडर स्वतंत्रपणे 50 MiB ब्रोकर इनपुट कॅप लागू करतो. त्याची मर्यादित क्यू
एकाच वेळी एक काढण्यास चालवते, चार प्रलंबित नोकऱ्यांना परवानगी देते, आणि प्रलंबित इनपुट 100 MiB वर मर्यादित करते.

ब्रोकरच्या आत, `ffprobe` एक खासगी स्थानिक फाइल वाचतो; निश्चित स्वरूप
परवानगी यादी प्लेलिस्ट आणि मॅनिफेस्ट स्वरूपांना वगळते. परवान्याच्या MOV-कुटुंब
कॉन्टेनर साठी, बाह्य MOV डेटा संदर्भ डिफॉल्टने अक्षम राहतात, आणि निश्चित
आज्ञा त्यांच्यात सामील होत नाही. दोन्ही `ffprobe` आणि `ffmpeg` वापरतात
`file`-फक्त प्रोटोकॉल परवानगी यादी, एक थ्रेड, निश्चित तर्क अरे, कोणतीही शेल,
आणि `PATH` मधून निराकृत कार्यान्वित. संलग्न-चित्र कव्हर स्ट्रीम प्ले करण्यायोग्य उमेदवार नाहीत. सर्व प्ले करण्यायोग्य स्ट्रीम्स मर्यादांची पूर्तता करणे आवश्यक आहे, आणि एक स्पष्ट डिफॉल्ट स्ट्रीम निश्चित कमी-इंडेक्स फॉलबॅकच्या आधी प्राधान्य दिले जाते. व्हिडिओ 600 सेकंद, 8,192 पिक्सेल प्रति मिती, आणि
33,554,432 स्रोत पिक्सेलवर मर्यादित आहेत. FFmpeg 1–16 मध्यवर्ती JPEG फ्रेम्सचे नमुने घेतो, लांब कडेला 1,024 पिक्सेलपर्यंत कमी करतो, लहान इनपुट्सना अपस्केल न करता, आणि कधीही URL प्राप्त करत नाही. नमुना `uniform` डिफॉल्टने आहे. वैकल्पिक
`scene_aware` आणि प्रयोगात्मक `segment_aware` धोरणे आधीच मान्यताप्राप्त स्थानिक स्ट्रीमवर एक अतिरिक्त निश्चित FFmpeg पास पार करतात, मर्यादित `showinfo` दृश्य टाइमस्टॅम्प निवडतात, आणि डिटेक्टर अपयश, टाइमआउट, खराब आउटपुट, किंवा रिक्त उमेदवार सेटवर निश्चितपणे समान
युनिफॉर्म मध्यवर्ती बिंदूंवर फॉलबॅक करतात. सेगमेंट-वेअर मोड मान्यताप्राप्त दृश्य अंतरालानुसार मध्यवर्ती नमुन्यांचे प्रमाणित वितरण करते; सेगमेंट-वेअर पुरावे आणि फॉलबॅक वर्तन खाली तपशीलवार आहेत. कठोर 16-फ्रेम कॅप
प्रत्येक धोरणात निवडीच्या नंतर लागू केला जातो. जेव्हा दृश्य-वेअर विनंतीमध्ये फक्त एक-फ्रेम बजेट असते, तेव्हा ते सक्रिय पूर्ण-व्हिडिओ किंवा फोकस
विंडोचा युनिफॉर्म मध्यवर्ती बिंदू वापरते आणि `policyEffective: uniform` अहवाल देते: एकच निवडलेले दृश्य फ्रेम दोन्ही कालानुक्रमिक टोकांचे संरक्षण करू शकत नाही. एक कॉलर वैकल्पिकपणे एक
मर्यादित फोकस विंडो (`start`/`end` सेकंद) प्रदान करू शकतो; मर्यादा मीडिया
कालावधीवर क्लॅम्प केल्या जातात, उलट किंवा अनंत विंडो नाकारल्या जातात, आणि सर्व नमुना
धोरणे फक्त सामान्यीकृत अंतरात केली जातात. परिणामी
विंडो नमुना मेटाडेटामध्ये आणि अविश्वसनीय वर्णन
पूर्वसूचनेत समाविष्ट आहे जेणेकरून खालील मॉडेल पूर्ण
कालावधीपासून लक्ष केंद्रित केलेल्या उताऱ्याला वेगळे करू शकतील.

सामाजिक कॅप्शन फोकस एक स्वतंत्र, स्पष्ट सेटिंग आहे. डिफॉल्ट `full`
विश्लेषण मोड विद्यमान फ्रेम प्रॉम्प्ट जतन करतो आणि कधीही विनंती मजकूर कॅप्शन मॉडेलकडे पुढे करत नाही. `focused` मोडमध्ये, ब्रिज फक्त नवीनतम
रिक्त नसलेल्या वापरकर्ता-लेखित `text`/`input_text` वाचतो, त्यास NFC मध्ये सामान्यीकृत करतो, नियंत्रण वर्ण आणि पांढरे जागा कमी करतो,
आणि 500 युनिकोड कोड पॉइंट्सपर्यंत मर्यादित करतो. रिक्त परिणाम अचूक `full` प्रॉम्प्टवर फॉलबॅक करतो. एक वापरण्यायोग्य सूचक JSON मध्ये एक समर्पित
अविश्वसनीय-उपयोगकर्ता-परिस्थिती ब्लॉकमध्ये अनुक्रमित केला जातो आणि फक्त निरीक्षणयोग्य तपशीलांना प्राधान्य देऊ शकतो; हे मीडिया मध्ये दृश्यमान किंवा श्रव्य सूचनांचे पालन करण्याविरुद्ध असलेल्या स्वतंत्र चेतावणीला ओव्हरराइड करू शकत नाही. मजकूर फोकस कधीही `start`/`end` चा अर्थ लावत नाही किंवा
कालानुक्रमिक नमुना बदलत नाही.

#### FU-07 संरचनात्मक सेगमेंट पुरावा

`segment_aware` आधीच मान्यताप्राप्त स्थानिक व्हिडिओ प्रवाहावर एक मर्यादित पूर्व-विश्लेषण पास वापरतो. निश्चित फिल्टर चेन प्रथम 320 पिक्सेल रुंदीत स्केल करते, दृश्य बदल आणि थांबलेले अंतर शोधते, नंतर धुंद, सरासरी ल्यूमा, आणि स्थानिक/कालिक माहिती साठी प्रति सेकंद 1 फ्रेमवर नमुने घेतात. हा पास 600 संरचनात्मक नमुन्यांपर्यंत मर्यादित आहे, एक FFmpeg/filter थ्रेड, त्याच `file`-फक्त प्रोटोकॉल आणि कंटेनर अलॉवलिस्ट, 1 MiB प्रक्रिया-आउटपुट बाउंड, आणि ब्रोकरच्या सामायिक रद्द/अवधीत कमीत कमी 30 सेकंदांपर्यंत मर्यादित आहे. तो कधीही विनंतीमधून आदेश, फिल्टर, पथ, किंवा URL स्वीकारत नाही.

संरचनात्मक मूल्ये निश्चित नमुना पुरावे आहेत, अर्थपूर्ण व्हिडिओ समज नाहीत. ते विषय, क्रिया, कॅप्शन, भाषण, किंवा वापरकर्त्याच्या हेतूचा अर्थ लावत नाहीत. दृश्य आणि थांबण्याच्या सीमांनी विभाग तयार केले; थांबण्याचे कव्हरेज, धुंद, एक्सपोजर, स्थानिक तपशील, आणि कालिक बदल फक्त विद्यमान 1–16 फ्रेम बजेट कसे वाटले जाते यावर प्रभाव टाकतात. पूर्णपणे थांबलेला विभाग एका फ्रेमवर मर्यादित आहे, तर न थांबलेले विभाग उर्वरित बजेटसाठी स्पर्धा करतात. जेव्हा सीमांची संख्या फ्रेम्सपेक्षा जास्त असते, तेव्हा एकसारखी टाइमलाइन कव्हरेज राखली जाते जेणेकरून जलद प्रारंभिक कट एक लांब ट्रेलिंग विभाग लपवू शकत नाही. थांबण्याच्या सीमांच्या 1-सेकंद विश्लेषणाच्या ठरावात दृश्य सीमांना एकत्र केले जाते.

गहाळ फिल्टर्स, खराब/रिक्त पुरावे, एक डिटेक्टर त्रुटी, किंवा मर्यादित पूर्व-विश्लेषण टाइमआउट अचूक एकसारख्या मध्यवर्ती धोरणावर खुला असतो. एक कॉलर रद्द किंवा ब्रोकरची अंतिम मुदत खुली होत नाही: हे प्रवाहित उपप्रक्रिया समाप्त करते, नंतरच्या फ्रेमच्या काढण्यास प्रतिबंध करते, आणि खाजगी तात्पुरती झाड `finally` मध्ये काढली जाते.

`scripts/perf/video-bridge-fu07-eval.ts` पोस्ट-डेडुप कॅप्शन-कॉल बचतीसाठी निश्चित वास्तविक FFmpeg फिक्स्चर तयार करते, घन-गती बजेट वाटप, धुंद/एक्सपोजर/SI-TI पुरावे, लांब शेपटीसह जलद कट, आणि हळूहळू-फेड खोटी सकारात्मकता. हे पूर्व-विश्लेषण भिंत वेळ नोंदवते आणि, जिथे `/usr/bin/time` उपलब्ध आहे, तिथे चाइल्ड CPU आणि पीक RSS. त्याची गुणवत्ता तपासणी फक्त संरचनात्मक ओरॅकल आहे. वास्तविक कॅप्शन-मॉडेल गुणवत्ता `HOLD` राहते कारण या हार्नेसकडे अधिकृत एंडपॉइंट किंवा थांबलेला न्यायाधीश नाही. आर्थिक बचती देखील `HOLD` राहतात जोपर्यंत `--caption-cost-per-call-usd` एक स्पष्ट सकारात्मक प्रति-कॉल अंदाज प्रदान करत नाही; स्क्रिप्ट कधीही दोन्ही परिणाम तयार करत नाही.

प्रत्येक फ्रेम 4 MiB वर मर्यादित आहे, सर्व कच्च्या फ्रेम एकत्र 23 MiB पर्यंत, आणि अनुक्रमित ब्रोकर प्रतिसाद 32 MiB पर्यंत. एक खाजगी तात्पुरती निर्देशिका `finally` मध्ये काढली जाते. OmniRoute FFmpeg एकत्रित करत नाही आणि कस्टम कार्यान्वयन पथ स्वीकारत नाही. कॅप्शनिंगपूर्वी, ब्रिज एक संवेदनशील दृश्य डेडुप्लिकेशन पास लागू करतो: प्रत्येक JPEG 16×16 ग्रेस्केल बफरमध्ये कमी केला जातो आणि फक्त शेवटच्या फ्रेमसह तुलना केली जाते. एक फ्रेमपेक्षा जास्त कॅप्शन बजेट मागितल्यास, काढणे एक मर्यादित उमेदवार पूल प्रदान करते जो त्या बजेटच्या दुप्पटपर्यंत असतो आणि कधीही 16 फ्रेमपेक्षा जास्त नसतो. मागितलेला कॅप फक्त डेडुप्लिकेशननंतर लागू केला जातो, पहिल्या आणि अंतिम निवडक उमेदवार अंतिम पातळ करताना जतन केले जातात जेव्हा बजेट किमान दोन असते. आवृत्तीत `grayscale-16x16-mean-cells-v2` धोरण सरासरी ल्यूमा डेल्टा आणि थंबनेल सेल्सच्या प्रमाणाचा मोठा वापर करते ज्याचा सामान्यीकृत डेल्टा किमान 0.05 आहे. डुप्लिकेट थ्रेशोल्ड हा स्थिर 0.04 आहे, जो भविष्यवाणीसाठी निवडला गेला आहे, चालू सेटिंग म्हणून उघडला जात नाही. हा द्वितीयक उच्च-कोन्ट्रास्ट सिग्नल लहान गती आणि दृश्यमान-टेक्स्ट बदल जतन करतो जे एक साधी तुलना लपवू शकते. तुलना करणारे किंवा डिकोडर त्रुटी खुल्या राहतात आणि कव्हरेज राखतात. आउटपुट मेटाडेटा काढलेल्या उमेदवारांना, यशस्वीपणे वापरलेल्या फ्रेमना, आणि दृश्य डुप्लिकेटांना वेगळे करते.

एक स्पष्टपणे चिन्हांकित व्हिडिओ भाग एक टाइमस्टॅम्प केलेला संपर्क पत्रक मागू शकतो. ब्रिज कमीत कमी 4-कॉलम, 16-फ्रेम JPEG ग्रिड तयार करतो. प्रत्येक 512-पिक्सेल सेल त्याच्या स्रोत टाइमस्टॅम्पला उच्च-कोन्ट्रास्ट तळाच्या बँडमध्ये जाळतो, तर त्याच टाइमस्टॅम्प्स पाठपुरावा संघटन आणि ऑडिटसाठी मजकूर मेटाडेटामध्ये राहतात. संपूर्ण JPEG 32 MiB वर मर्यादित राहतो. जर `sharp` ग्रिड डिकोड किंवा संकलित करू शकत नसेल, तर ब्रिज वैयक्तिक JPEG फ्रेमवर परत जातो; एक क्लायंट रद्द अद्याप पत्रक ऑपरेशनद्वारे प्रसारित होते.

प्रमोशन पुरावे कृत्रिम रचना मायक्रोबेंचमार्फत स्पष्टपणे वेगळे आहेत. `scripts/perf/video-bridge-contact-sheet-eval.ts` वास्तविक OpenAI-संगत दृष्टि मॉडेलसाठी एक स्कीमा-आवृत्त A/B हार्नेस परिभाषित करते. हे प्रदाता-रिपोर्ट केलेले टोकन, अंत-ते-अंत भिंत विलंब (पत्रक रचना समाविष्ट), मॉडेल-कॉल संख्या, आणि मॅनिफेस्ट-परिभाषित तथ्य राखण मोजते. कच्च्या मॉडेल प्रतिसादांना अहवालात लिहिले जात नाही; फक्त SHA-256 डाइजेस्ट आणि जुळलेल्या तथ्य IDs राखल्या जातात. हार्नेस कोणतीही नेटवर्क किंवा सशुल्क मॉडेल कॉल करत नाही जोपर्यंत `--execute-real` पास केले जात नाही आणि `--model`, `OMNIROUTE_BASE_URL`, आणि `OMNIROUTE_API_KEY` कॉन्फिगर केलेले नाहीत. त्या स्पष्ट वास्तविक चालविण्याशिवाय, त्याचा मशीन-वाचनायोग्य निर्णय `HOLD` राहतो; कृत्रिम पेलोड/कॉल-गणना मोजमापे एकट्याने प्रमोशन पुरावा नाहीत.

वेगळा `scripts/perf/video-bridge-promotion-eval.ts` FU-07 किंवा FU-09 निरीक्षणांचा वापर करतो. प्रमोशन प्रवेशासाठी सर्व आठ कृत्रिम परिस्थितींच्या प्रकारांची आवश्यकता आहे आणि एक स्वच्छ वास्तविक क्लिप, प्रत्येक भूमिकेसाठी आणि प्रकरणासाठी किमान तीन मोजलेले पुनरावृत्त्या, सर्व दहा घोषित मेट्रिक्स, थांबलेली मीडिया/प्रॉम्प्ट/अपेक्षित-तथ्य/सेटिंग्ज डाइजेस्ट, अद्वितीय निरीक्षण IDs आणि सत्यापित बीजित A/B क्रम आवश्यक आहे. कार्यान्वयन पावती कॉर्पस डाइजेस्ट, अचूक उमेदवार SHA आणि मॉडेल आवृत्तीला बांधते. गहाळ किंवा अमान्य मोजमापे `HOLD` राहतात, ज्यात CPU 30 सेकंदांपेक्षा जास्त, पीक RSS 512 MiB पेक्षा जास्त किंवा पूर्व-विश्लेषण 30 सेकंदांपेक्षा जास्त आहे. हे पुरावा-प्रवेश मर्यादा आहेत, नवीन चालू RSS अंमलबजावणी हमी नाही.

FU-07 किमान 98% गुणवत्ता राखण्याची आणि p95 विलंब 1.2x पेक्षा जास्त नसावा, याची आवश्यकता आहे, तसेच समान सरासरी कॅप्शन कॉल्सवर 0.05 पूर्ण प्रकरण-समतोल सरासरी पुनःप्राप्ती सुधारणा किंवा किमान 10% कमी सरासरी पोस्ट-डेडुप कॅप्शन कॉल्स असाव्यात. FU-09 किमान 0.85 गुणवत्ता, 95% राखण, 20% p95 विलंब कमी करणे आणि 10% टोकन कमी करणे आवश्यक आहे. महत्त्वाच्या तथ्यांचा तोटा, इंजेक्शन अनुपालन किंवा गहाळ वापर पदोन्नतीला प्रतिबंध करतो. एक कार्यवाही काहीही पदोन्नत करू शकत नाही: `--previous-report` समान धोरण/मॉडेल पुनरावलोकन/उम्मीदवार/कॉर्पसच्या दोन भिन्न, नॉन-ओव्हरलॅपिंग, सलग पात्र कार्यवाहीची पुष्टी करते. एक नमुना प्रयोग संपर्क-शिट प्रयोगाची पुष्टी करू शकत नाही.

संग्रहकांनी प्रतिसादांना स्मरणात स्कोअर करणे आवश्यक आहे आणि `responseDigest` सह मेट्रिक्स आणि निरीक्षण बाइंडिंग्ज जतन करणे आवश्यक आहे, कधीही प्रतिसाद मजकूर नाही. उपभोक्ता देखील वारसा कच्च्या निरीक्षणांचे वाचन करतो, परंतु कधीही त्या मजकूराची नक्कल आपल्या अहवालात करत नाही. प्रत्येक निरीक्षणासाठी `responseDigest` किंवा `rawResponseText` पैकी एकच स्वीकारले जाते. आवृत्तीय मान्यता यादी रिकामी राहते ज्यामध्ये अपरिवर्तनीय `hold` डिफॉल्ट आहे. पात्र नोंदणीसाठी त्याच्या पुराव्याचा संदर्भ, धोरण, मॉडेल पुनरावलोकन, अचूक उम्मेदवार SHA, मॅनिफेस्ट डाइजेस्ट आणि दोन भिन्न चालवण्याच्या आयडींची आवश्यकता आहे; संघर्ष करणारे संदर्भ नाकारले जातात. हे मेटाडेटा एक ऑडिट करार आहे, संदर्भित फाइलमध्ये खरे मोजमाप आहेत याचे प्रमाण नाही. कोणतीही नोंद जोडण्यापूर्वी वास्तविक पावत्या पुनरावलोकन करा. व्यवस्थापन आकडेवारी अंतिम बिंदू आणि व्हिडिओ डॅशबोर्ड संवेदनशील तयारी दर्शवतात. एक कॉन्फिगर केलेला मॉडेल उपनाम एकटा त्याच्या पुनरावलोकन किंवा चालू उम्मेदवार SHA स्थापित करत नाही, त्यामुळे वर्तमान डॅशबोर्ड `HOLD` अहवाल करतो, दुसऱ्या कार्यवाही संदर्भातून पात्रता पुन्हा वापरण्याऐवजी. स्पष्ट प्रयोगात्मक निवड पदोन्नतीपासून वेगळी राहते; कोणताही डिफॉल्ट स्वयंचलितपणे बदलला जात नाही.

कॉलरने एक पर्यायी `transcript.cues` अ‍ॅरे समर्थित व्हिडिओ भागात जोडू शकतो जेव्हा त्यांच्याकडे आधीच संरेखित मजकूर असतो. प्रत्येक क्यूमध्ये `text`, प्रॉब केलेल्या कालावधीत एक निश्चित `start`/`end` अंतर आणि एक व्हाइटलिस्टेड `source` (`client`, `embedded`, किंवा `audio-bridge`) असावे; `confidence` डिफॉल्ट `1` आहे आणि `0` आणि `1` च्या दरम्यान राहावे लागते. अचूक डुप्लिकेट क्यू एकत्रित केले जातात. OmniRoute कधीही या मेटाडेटावरून ट्रान्सक्रिप्शन सुरू करत नाही: मान्यताप्राप्त क्यू वर्णन केलेल्या परिणामात स्रोत, विश्वास आणि अंतरासह कॉपी केले जातात, आणि फ्रेम कॅप्शनसह अविश्वसनीय निरीक्षण म्हणून दर्शविले जातात. अमान्य, श्रेणीबाह्य, किंवा उत्पत्ति-मुक्त मजकूर कॅप्शन प्रवाहात मिसळण्याऐवजी नाकारला जातो. दोन्ही विनंती-शरीर ट्रान्सक्रिप्ट चॅनेल पुरवलेले उत्पत्ति `client` मध्ये सामान्यीकृत करतात, स्व-संकेतित `embedded` किंवा `audio-bridge` लेबलसह. फक्त एक सर्व्हर-स्वामित्व असलेला अडॅप्टर त्या विश्वसनीय लेबल्सना कोड-फक्त `trustedSource` आर्ग्युमेंटद्वारे असाइन करू शकतो; विनंती JSON फील्ड त्या आर्ग्युमेंटपर्यंत पोहोचू शकत नाही. ट्रान्सक्रिप्ट मजकूर अविश्वसनीय मीडिया-व्युत्पन्न सामग्री राहतो, त्याच्या उत्पत्तीसाठी महत्त्वाचे नाही, आणि कधीही अधिकृतता ठरवू नये.

एक प्रगत कॉलर त्याच व्हिडिओसाठी `audioTranscript` ट्रॅक प्रदान करू शकतो; हे क्लायंट-प्रदान केलेल्या मजकूरासारखे मानले जाते, सर्व्हर ट्रान्सक्रिप्शनचे प्रमाण नाही. फ्यूजन सीम एकाच अंतिम मुदती आणि थांबविण्याच्या सिग्नल अंतर्गत दृश्य आणि ऑडिओ निरीक्षण चालवते, त्यांना सामान्य टाइमलाइनवर आदेश देते, अचूक डुप्लिकेट एकत्रित करते, आणि केवळ एक बाजू यशस्वी झाल्यास अंशतः परिणाम अहवाल करते. अमान्य `audioTranscript` त्या अंशतः परिणामात कमी होते - दृश्य वर्णन ठेवले जाते आणि ऑडिओ शाखा एक स्वच्छ असफलता कोड नोंदवते - संपूर्ण व्हिडिओ अपयशी होण्याऐवजी. प्रत्येक शाखेची उपलब्धता, अंशतः ध्वज, आणि स्वच्छ असफलता कोड वर्णन केलेल्या परिणामात, गार्डरेल मेटाडेटामध्ये (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), परिणाम-कॅश मेटाडेटामध्ये, आणि ब्रिज फ्यूजन काउंटरमध्ये जतन केले जातात. डिफॉल्ट व्हिडिओ ब्रिज पथ भाषण-टेक्स्टला सक्रिय करत नाही किंवा दुसऱ्या मीडिया कॉपीला डाउनलोड करत नाही; त्या स्पष्ट ट्रॅकशिवाय, ते फक्त व्हिडिओ राहते.

**ट्रान्सक्रिप्ट राखणे (#12150 P1).** हे स्वयंचलितपणे लागू होते जेव्हा व्हिडिओ ब्रिज (स्वतः ऑप्ट-इन) एक ट्रान्सक्रिप्ट क्यू तयार करतो - स्वतंत्र राखण ध्वज नाही. जेव्हा एक विनंती कोणतीही ट्रान्सक्रिप्ट क्यू (एक कॉलर-घोषित `transcript` किंवा एक फ्यूज केलेला `audioTranscript`) तयार करते, तेव्हा गार्डरेल ते `videoBridgeObserved` म्हणून चिन्हांकित करते आणि व्हिडिओ वर्णनाचा एक संपादित सावली तयार करते - एक समान रेंडरिंग ज्यामध्ये प्रत्येक क्यूच्या मुक्त-टेक्स्ट शरीराला `[redacted-video-transcript]` ने बदलले जाते, संरचित क्यू फील्डची जागा घेऊन स्ट्रिंग एकत्रित करण्यापूर्वी (कधीही फ्लॅट केलेल्या मजकूराचे पार्सिंग करून, त्यामुळे कोणताही क्यू सामग्री - शत्रुत्व किंवा सामान्य, `]` समाविष्ट करणारे शरीर जसे की `[inaudible]`/`[music]` - टिकत नाही). जतन केलेल्या कॉल-लॉग विनंती शरीर प्रत्येक व्हिडिओ-व्युत्पन्न मजकूर भागासाठी त्या संपादित सावलीसाठी स्वाप करते, सामग्री समानतेद्वारे जुळवले जाते; `fullText` अँकर पूर्ण केलेल्या प्री-कॉल गार्डरेल पेलोडमधून पुन्हा वाचले जाते, त्यामुळे जुळणी नंतरच्या चेन गार्डरेल (PII आणि क्रेडेन्शियल मास्कर्स, प्राधान्य 10/95) वर्णन मजकूर जागेवर पुन्हा लिहिताना अजूनही यशस्वी होते आणि प्रणाली-प्रॉम्प्ट/हँडऑफ/स्मृती इंजेक्शन संदेश अरेचे आकार बदलते. मॉडेलकडे पाठवलेले शरीर अपरिवर्तित राहते. एक निरीक्षित विनंती देखील कोणतीही टिकाऊ स्मृती भरत नाही (दोन्ही विनंती- आणि प्रतिसाद-व्युत्पन्न निष्कर्ष वगळले जातात), त्यामुळे मॉडेलच्या स्वतःच्या उत्तराने स्मृतीमध्ये ट्रान्सक्रिप्ट मजकूर प्रतिध्वनी करू शकत नाही.

**कच्चा व्हिडिओ फील्ड (#12430).** जेव्हा ब्रिज सक्षम आहे आणि स्थानिक व्हिडिओ समर्थन अनिश्चित किंवा अनुपस्थित आहे, तेव्हा परिभाषित `transcript`/`audioTranscript` फील्ड देखील `videoBridgeObserved` सक्रिय करतात, वर्णन अपयश किंवा `maxVideos` मर्यादेनंतर देखील. `null` आणि रिकामे स्ट्रिंग्स मोजले जातात; अनुपस्थित फील्ड आणि नॉन-व्हिडिओ मेटाडेटा मोजले जात नाहीत. राखलेले प्रतीक या फील्डना संपादित करतात किंवा विनंती वगळतात, आणि कॅश/स्मृती वगळले जातात. प्रदाता पेलोड अपरिवर्तित राहतो.

अतिरिक्त राखलेले प्रतीक समान निरीक्षित-प्रार्थना सिग्नल वापरतात. कच्चा प्री-गार्डरेल क्लायंट-प्रार्थना स्नॅपशॉट, मेमरीमध्ये प्रलंबित प्रार्थना, आणि लवकर नाकारलेली प्रार्थना लॉग संरचनात्मकदृष्ट्या व्हिडिओ भागांमधील ट्रान्सक्रिप्ट फील्ड्सची जागा घेतात; पाईपलाइन स्टेजेस आणि संदर्भ हस्तांतरणाद्वारे तयार केलेले स्ट्रिंग प्रॉम्प्ट्स कायम ठेवलेल्या प्रार्थना-शरीर सिंगकडे गुप्त केले जातात. कायम ठेवलेला `video_content_removed` मार्कर `previous_response_id` च्या निरंतरतेला बंद करण्यास कारणीभूत ठरतो, त्याऐवजी त्यातले टेक्स्ट पुन्हा तयार करण्याऐवजी जे उद्देशाने काढले गेले होते. जर निरीक्षित प्रार्थना लॉगिंगपूर्वी तिचा प्रत्येक भाग गुप्तता सावली गमावते, किंवा नंतरच्या प्रार्थना बदलांनंतर अनेक व्हिडिओ सावल्या जुळत नसल्यास, राखलेले प्रार्थना शरीर संपूर्णपणे वगळले जाते, अर्धवट गुप्त ट्रान्सक्रिप्ट राखण्याऐवजी.

एक निरीक्षित प्रार्थना साठी, मॉडेल प्रतिसाद ट्रान्सक्रिप्टच्या कोणत्याही भागाचे उद्धरण देऊ शकते, संरचित संकेत सीमांशिवाय. त्यामुळे, त्याचा कायम ठेवलेला कॉल-लॉग `responseBody` वगळण्याच्या मार्करने बदलला जातो; तपशीलवार पाईपलाइन आर्टिफॅक्ट (जो अपस्ट्रीम/क्लायंट शरीर आणि स्ट्रीम चंक्स समाविष्ट करू शकतो) राखला जात नाही. अर्थ, आयडेम्पोटेन्सी, आणि विचार-पुनरावृत्ती कॅशेस त्या प्रार्थनेसाठी वाचन आणि लेखन वगळतात. प्रदाता प्रार्थना आणि क्लायंट-दृश्यमान प्रतिसाद अपरिवर्तित राहतात. तपशीलवार आर्टिफॅक्ट वगळल्यावर तात्पुरत्या बफरमधून लवकरच्या कीपअलाईव्ह बाइट्स काढले जातात. किरोच्या खराब झालेल्या इव्हेंटस्ट्रीम चेतावणी फक्त पेलोड बाइट गणना रिपोर्ट करते, कधीही त्याच्या सामग्री किंवा JSON पार्सरच्या कच्च्या त्रुटीची माहिती देत नाही.
हे दावा करत नाही की प्रत्येक अप्रासंगिक प्रदाता/प्लगइन निदान तपासले गेले आहे; व्यापक राखलेले-सिंक स्वेप #11658 मध्ये ट्रॅक केले जाते.

आतील `/api/modality-bridge/video/drilldown` जीवनचक्र एक स्वतंत्र, लूपबॅक/टोकन-प्रमाणित कॅश सबस्ट्रेट आहे. प्रत्येक ऑपरेशनसाठी एक कॅनॉनिकल ओपेक प्रिन्सिपल ID आवश्यक आहे. उत्पादन कॉलर सक्षम करण्यापूर्वी, त्याला प्रमाणित भाडेकरू कडून ती ID व्युत्पन्न करावी लागते आणि कधीही क्लायंट-निवडक मूल्य पुढे पाठवू नये. कॅश कीज त्या प्रिन्सिपलला कॅनॉनिकल सत्र आणि व्हिडिओ-रेफरन्स IDs शी बांधतात, फक्त त्यांच्या SHA-256-व्युत्पन्न कीज संग्रहित करतात, आणि वाचन आणि हटविणे दोन्ही त्या प्रिन्सिपलसाठी सीमित करतात. कॅश प्रत्येक नोंदीसाठी कमीत कमी 16 व्युत्पन्न JPEG फ्रेम्स संग्रहित करते, दहा मिनिटांनंतर त्यांना कालबाह्य करते, आणि सीमित `start`/`end` वाचन किंवा स्पष्ट सत्र हटविण्याचे समर्थन करते.

प्रत्येक प्रिन्सिपल 16 नोंदींवर आणि 64 MiB कॅनॉनिकल JPEG डेटावर मर्यादित आहे. त्या मर्यादा जागतिक 64-नोंदी/256 MiB छतापासून स्वतंत्र आहेत: प्रिन्सिपल कोटा दाब फक्त त्या प्रिन्सिपलच्या कमी-उपयोग केलेल्या नोंदींना हद्दपार करते, जागतिक LRU हद्दपारीसाठी विचार केला जातो. कालबाह्य नोंदी कॅश क्रियाकलापावर प्रिन्सिपल आणि जागतिक लेखाकडे स्वेप केल्या जातात, तर रद्द करणे आणि प्रमाणीकरण अपयश अर्धवट बदलाची नोंद करत नाही.

कॅश गैर-कॅनॉनिकल बेस64, अतिरिक्त पॅडिंग, गैर-JPEG मीडिया, खराब किंवा कापलेले JPEG, आणि सीमित पूर्ण-प्रतिमा `sharp` डिकोड दरम्यान चेतावणी निर्माण करणारे JPEG नाकारते. हे प्रत्येक स्वीकारलेल्या प्रतिमेला कॅनॉनिकल JPEG म्हणून पुन्हा कोड करते, डिकोड केलेल्या बाइट्समधून रुंदी आणि उंची व्युत्पन्न करते, कॉलर फील्ड्सवर विश्वास ठेवण्याऐवजी, आणि कोणतेही ट्रेलिंग पॉलीग्लॉट बाइट्स काढून टाकते, त्यांना राखण्याऐवजी. फक्त सीमित कॅनॉनिकल संकुचित बफर दोन्ही कोट्यांवर चार्ज केला जातो. JSON वायर मर्यादा 32 MiB डिकोडेड-इनपुट छतासाठी बेस64 ओव्हरहेड समाविष्ट करते. प्रत्येक संग्रहित व्युत्पन्न त्याच्या प्रमाणित JPEG स्वरूप/रिझोल्यूशन, सॅम्पलिंग धोरण, व्युत्पन्न आवृत्ती, निर्मिती वेळ, सर्व्हर-गणित केलेला सामग्री हॅश, आणि हॅश केलेला पॅरेंट संदर्भ तसेच विश्वासार्ह कॉलरच्या पॅरेंट-कंटेंट हॅशची नोंद ठेवते. रद्द करणे असिंक्रोनस डिकोड/हॅश टप्प्यांदरम्यान तपासले जाते, अणु कॅश कमिट करण्यापूर्वी.

उत्पादन उत्पादक आधीच व्युत्पन्न केलेल्या ब्रोकर फ्रेम्सचा पुनर्वापर फक्त यशस्वी दृश्य विश्लेषणानंतर करतो, दुसऱ्या व्हिडिओ डाउनलोड/निर्गमनाशिवाय. याला ऑपरेटर `modalityBridgeVideoDrilldownEnabled=true`, कठोर प्रति-भाग `drilldown: true`, आणि प्रमाणित API-key नोंद ID आवश्यक आहे. क्लायंट-घोषित प्रिन्सिपल/सत्र मूल्ये कधीही मालकी स्थापित करत नाहीत. या तीन अटींपैकी कोणतीही एक नसल्यास, हे हॅश, आकार बदलत नाही किंवा अतिरिक्त फ्रेम्स राखत नाही. राखण्याची अपयश वापरायोग्य दृश्य प्रतिसाद जपते. सहमतीने केलेल्या प्रार्थना संपूर्ण-व्हिडिओ परिणाम कॅशला वगळतात, त्यामुळे कॅश केलेले परिणाम कधीही पुनरावृत्ती हाताळत नाहीत.

यशस्वी JSON आणि SSE प्रतिसाद कमीत कमी चार ओपेक हँडल्स `x-omniroute-video-drilldown` हेडरमध्ये उघडतात. अधिकृत ब्राउझर मूळ त्या हेडरला वाचन करू शकतात, CORS मूळ धोरण विस्तारित न करता. नवीन हँडल्स `v1.<32-byte random base64url token>` वापरतात, आणि नोंदणी फक्त त्यांच्या SHA-256 हॅशेस राखते. वाचक/हेडर पार्सर जुने 64-हेक्स टोकन देखील स्वीकारतो. प्रमाणित सार्वजनिक उपभोक्ता आहे `GET /api/v1/video-bridge/drilldown?handle=...`, स्वतंत्रपणे गेट केलेले `modalityBridgeVideoDrilldownRemoteEnabled=true`. स्पष्टपणे कायम ठेवलेले खोटे प्रवेश रद्द करते, अगदी जुने `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` env फॉलबॅक सक्षम असताना. उत्पादन राखण्याकडे समान जुने `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED` फॉलबॅक आहे. दोन्ही फॉलबॅक डिफॉल्टने बंद आहेत.

उपभोक्ता प्रमाणित की कडून मालकी व्युत्पन्न करतो, की धोरण लागू करतो, आणि अज्ञात, कालबाह्य आणि दुसऱ्या कीच्या हँडलसाठी समान 404 परत करतो. हे स्वीकारते `variant=preview|standard|detail` (कमाल JPEG आयाम 320/640/1280, कधीही अपस्केल केलेले नाही), `limit=1..8` (किंवा जुना `frames` उपनाम, कधीही दोन्ही नाही), शून्य-आधारित `page`, आणि वैकल्पिक `start`/`end` फोकस सेकंद. डुप्लिकेट क्वेरी कीज आणि उलट फोकस विंडो नाकारल्या जातात. प्रत्येक परत केलेला प्रकार त्याच्या वास्तविक सामग्री आणि वास्तविक रिझोल्यूशन मेटाडेटाचा हॅश असतो, राखलेल्या स्रोताशी जोडलेला. प्रकार वाचनावर व्युत्पन्न केले जातात, अतिरिक्त राखलेल्या प्रती म्हणून संग्रहित केले जात नाहीत. JSON प्रतिसाद, बेस64/एन्व्हेलपसह, 32 MiB वर मर्यादित आहे; एक मोठा पृष्ठ 413 परत करतो आणि क्लायंटने कमी फ्रेम्सची विनंती करावी लागते. वाचन प्रत्येक आकार बदलण्याच्या आसपास रद्द करणे तपासते आणि परत करण्यापूर्वी हँडल वैधता पुन्हा तपासते. `DELETE` मालकाद्वारे आयडेम्पोटेंट आहे; हटविणे किंवा TTL कालबाह्य होणे राखलेल्या स्रोत आणि वापर लेखा मुक्त करते.

सामायिक स्टोरेज प्रक्रिया-स्थानिक आहे: हँडल्स पुन्हा सुरू केल्यावर कालबाह्य होतात आणि स्वतंत्र OmniRoute प्रक्रियांमध्ये हस्तांतरित केले जात नाहीत. व्यवस्थापन आकडेवारी प्रभावी रिटेन्शन/दूरध्वनी धोरण आणि एकत्रित ठेवलेले नोंदी/बाइट्स फक्त उघड करते, कधीही मीडिया, संदर्भ, मुख्य आयडी किंवा हँडल्स नाहीत. व्हिडिओ सेटिंग्ज पॅनेल त्या मूल्ये दर्शवते आणि दोन्ही सहमती स्विचेस टिकवू शकते. ही अंमलबजावणी दस्तऐवज थेट तैनाती किंवा प्रचार पुरावा नाही; वास्तविक-मॉडेल स्वीकृती वेगळ्या पद्धतीने ट्रॅक केली जाते.

फ्रेम्स अनुक्रमे कॉन्फिगर केलेल्या व्हिडिओ मॉडेलसह कॅप्शन केले जातात. एक रिक्त व्हिडिओ ओव्हरराइड व्हिजन सेटिंगचा वारसा घेतो; जर दोन्ही रिक्त असतील, तर व्हिजन ऑटो-राउटर प्रभावी व्हिजन-सक्षम मॉडेल निवडतो. यशस्वी कॅप्शन्स मूळ भाग स्थिर `[Video description:` प्रीफिक्ससह बदलतात जो मजकूराला अविश्वसनीय मीडिया-व्युत्पन्न निरीक्षण म्हणून चिन्हांकित करतो आणि खालील मॉडेल्सना मीडिया मध्ये आढळलेल्या सूचनांचे पालन न करण्यास सांगतो. फ्रेम-कॅप्शन कॅश कीज JPEG बाइट्स, प्रॉम्प्ट, टाइमस्टॅम्प, आणि प्रभावी मॉडेल समाविष्ट करतात; फक्त यशस्वी कॅप्शन्स कॅश केल्या जातात. कॅश नोंदी वास्तविक यशस्वी उत्पादक मॉडेल ठेवतात, ज्यात एक फॉलबॅक मॉडेल समाविष्ट आहे; ब्रिज `mixed` रिपोर्ट करतो जेव्हा वेगवेगळ्या फ्रेम्स वेगवेगळ्या मॉडेल्सद्वारे उत्पादित केल्या जातात. कॅश हिट त्या उत्पादक ओळखीचा पुनर्वापर करतो त्याऐवजी त्याला मागणी केलेल्या राउटिंग योजनेप्रमाणे पुन्हा लेबल करतो. संपूर्ण-व्हिडिओ परिणाम कॅश प्रत्येक इनपुटवर की केले जाते जे आउटपुट बदलते — प्रॉम्प्ट, प्रभावी मॉडेल, सॅम्पलिंग धोरण, फ्रेम संख्या, सेमांटिक विश्लेषण मोड, सामान्यीकृत फोकस हिन्टचा SHA-256 फिंगरप्रिंट, फोकस विंडो, `transcript`, `audioTranscript`, आणि संपर्क-शिट ध्वज — त्यामुळे त्या कोणत्याही परिमाणांमध्ये बदल करणे म्हणजे कॅश मिस, कधीही जुनाट पुनर्वापर नाही. दृश्य डेडुप धोरण आवृत्ती, थ्रेशोल्ड, आणि बाउंडेड कॅंडिडेट-फ्रेम संख्या देखील परिणाम-कॅश की आणि मेटाडेटामध्ये स्पष्ट आहेत; त्यामुळे धोरण बदल जुनाट संपूर्ण-व्हिडिओ वर्णनाचा पुनर्वापर करू शकत नाही. परिणाम-कॅश v4 मेटाडेटा मोड आणि फिंगरप्रिंट ठेवते, कधीही कच्चा वापरकर्ता कार्य नाही. गार्डरेल मेटाडेटा मागणी केलेल्या आणि प्रभावी विश्लेषण मोड दोन्ही रिपोर्ट करते; वापरण्यायोग्य वापरकर्ता मजकूराशिवाय मागणी केलेला `focused` मोड प्रभावीपणे `full` म्हणून रिपोर्ट केला जातो.

गार्डरेल प्रत्येक समर्थित व्हिडिओ भाग काढतो पण `modalityBridgeVideoMaxVideos` पेक्षा अधिक वर्णन करत नाही. `supportsVideo === false` असलेल्या लक्ष्यांसाठी, अपयशी आणि ओव्हर-लिमिट व्हिडिओ स्पष्ट सुरक्षित मजकूर मार्कर बनतात त्यामुळे कोणताही कच्चा व्हिडिओ टिकत नाही. जेव्हा क्षमता अज्ञात असते, तेव्हा त्या भागांना हाताळले जात नाही. `supportsVideo === true` असलेल्या लक्ष्यांनी ब्रिज बायपास केला. क्लायंट विनंती रद्द सिग्नल डाउनलोड, ब्रोकर क्यू, उपप्रक्रिया, आणि कॅप्शन कॉल्समध्ये प्रसारित होतो; रद्द करणे व्हिडिओ दरम्यान थांबवते आणि कधीही कच्च्या मीडियाकडे उघडे होत नाही.

### PII मास्कर (`piiMasker.ts`)

**दोन्ही** स्टेजवर चालतो.

- **`preCall`** पेलोड क्लोन करतो, `system`, `messages`, `input`, आणि `prompt` (सामान्य स्ट्रिंग आयटम समाविष्ट) वर चालतो, आणि `processPII()` (मधून `@/shared/utils/inputSanitizer`) स्ट्रिंग `content`/`text` फील्डवर लागू करतो. जेव्हा `PII_REDACTION_ENABLED=true` असते, तेव्हा शोधलेले PII बाह्य पेलोडमध्ये काढले जाते. हे `INPUT_SANITIZER_MODE` पासून स्वतंत्र आहे (जे फक्त प्रॉम्प्ट-इंजेक्शन धोरण नियंत्रित करते). जेव्हा काढणे बंद असते, तेव्हा कॉल शोधलेले गणना नोंदवते सामग्री पुन्हा लिहित नाही.
- **`postCall`** प्रतिसादाची गहन क्लोन करतो, `sanitizePIIResponse()` चालवतो आणि प्रतिसाद-API-आकार मास्कर (`maskResponsesOutput` — `output_text` आणि `output[].content[].text` कव्हर करतो). जर कोणतेही काढणे झाले, तर सुधारित प्रतिसाद मूळ प्रतिसाद बदलतो.

गार्डरेल कधीही ब्लॉक करत नाही; ते फक्त टिप्पणी करते (`meta.detections`, `meta.redacted`) किंवा पुन्हा लिहिते.

`INJECTION_GUARD_MODE` **DB फिचर-फ्लॅग ओव्हरराइड** (डॅशबोर्ड → सेटिंग्ज →
फिचर फ्लॅग) → `INJECTION_GUARD_MODE` पर्यावरण → `INPUT_SANITIZER_MODE` पर्यावरण →
`warn`. त्यामुळे डॅशबोर्ड ओव्हरराइड पर्यावरणीय चलांवर विजय मिळवतो, त्यामुळे फिचर फ्लॅग UI चालू गार्ड नियंत्रित करते (पुनः प्रारंभ नाही). DB वाचन सुरक्षित आहे:
जर ते त्रुटी दिल्यास, गार्ड पर्यावरण-आधारित वर्तनावर परत येतो, आणि जेव्हा कोणतेही ओव्हरराइड सेट केलेले नाही तेव्हा वर्तन पर्यावरण-फक्त निराकरणासारखेच असते.

शोध स्रोत:

1. `sanitizeRequest()` `@/shared/utils/inputSanitizer` कडून (पाईपलाइनमध्ये इतरत्र वापरलेला सामायिक शोधक सेट).
2. अंतर्निहित `DEFAULT_GUARD_PATTERNS` (सध्या `system_override_inline` आणि
   `markdown_system_block`, दोन्ही `high` तीव्रता).
3. कन्स्ट्रक्टर पर्यायांद्वारे पास केलेले वैकल्पिक `customPatterns` (स्ट्रिंग्ज, regex,
   किंवा `{ name, pattern, severity }` रेकॉर्ड).

जेव्हा `mode === "block"` **आणि** किमान एक शोध तीव्रता थ्रेशोल्ड पूर्ण करतो, `preCall` `{ block: true, message: "विनंती नाकारली: शंकास्पद सामग्री शोधली गेली" }` परत करते. `warn`/`log` मोडमध्ये गार्डरेल लॉग करते पण कॉलला परवानगी देते. सामायिक सहाय्यक `evaluatePromptInjection()` देखील निर्यात केले जाते
ज्यांना रजिस्ट्रीतून न जाता प्रॉम्प्टचे मूल्यांकन करण्याची आवश्यकता आहे.

**स्कॅन बाउंड (v3.8.20):** शोधक फक्त **पहिल्या 16 KB** चा तपास करतो
जोडलेल्या प्रॉम्प्ट मजकूर — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 बाइट्स) मध्ये
`src/shared/utils/inputSanitizer.ts`. दोन्ही `detectInjection()` आणि
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` चालवण्यापूर्वी पॅटर्न लूप चालवतात. इंजेक्शन निर्देशांक इनपुटच्या शीर्षस्थानी असतात, त्यामुळे हे मल्टी-शंभर-KB पेल्यात regex CPU/GC वर मर्यादा घालते आणि शोध कमी करत नाही (cf.
#3932, #4041).

### क्रेडेन्शियल मास्कर (`credentialMasker.ts`)

**दोन्ही** टप्प्यांवर चालतो, डीफॉल्ट साखळीत शेवटचा (प्राधान्य `95`). बाह्य पेल्यातून (संदेश सामग्री, टूल-कॉल आर्ग्युमेंट्स, टूल परिणाम) चांगले ज्ञात API-key / secret-token पॅटर्न काढतो **आणि** प्रदाता प्रतिसाद, त्यामुळे प्रॉम्प्टमध्ये पेस्ट केलेले क्रेडेन्शियल (किंवा टूल परिणामाद्वारे परत केलेले) अपस्ट्रीम प्रदात्याकडे किंवा क्लायंटकडे लीक होत नाही.

- **फक्त ऑप्ट-इन**, PII पुनर्लेखनासारखीच पद्धत (हार्ड नियम #20-शेजारी):
  `settings.credentialRedactionEnabled === true` **किंवा**
  `CREDENTIAL_REDACTION_ENABLED=true` नसल्यास निष्क्रिय. हे बंद असताना, गार्डरेल एक नॉन-ऑप आहे —
  ते कधीही ब्लॉक करत नाही आणि कधीही पुनर्लेखन करत नाही.
- `redactCredentials()` संपूर्ण पेल्यात/प्रतिसाद वृक्षात फिरतो (`walkValue()`,
  प्रोटोटाइप-प्रदूषण-सुरक्षित, `WeakSet` द्वारे चक्र-सुरक्षित) आणि जुळणारे बदलते
  `[REDACTED:<type>]` प्लेसहोल्डर, फक्त त्या शाखांचे क्लोनिंग करणे जे प्रत्यक्षात
  बदलले आहेत.
- `CREDENTIAL_PATTERNS` LLM प्रदाता कींवर (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS टोकन (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), पेमेंट की (Stripe, Square), क्लाउड
  की (AWS access key, Twilio, SendGrid, Mailgun), खाजगी की / JWTs,
  क्रेडेन्शियल-धारक कनेक्शन स्ट्रिंग्ज (`mongodb://user:pass@...`, इ.) आणि
  एक सामान्य `Authorization`/`x-api-key`/`api-key`/`apikey` हेडर-मूल्य
  पॅटर्न. हेडर-आकाराच्या की (`authorization`, `x-api-key`, `api-key`,
  `apikey`) संरचनात्मकपणे काढल्या जातात (फक्त मूल्य, योजना प्रीफिक्स जसे की
  `Bearer `/`Basic ` जतन केले जाते) सामान्य मजकूर regex द्वारे नाही.
- गार्डरेल कधीही ब्लॉक करत नाही; ते फक्त पुनर्लेखन करते (`modifiedPayload` /
  `modifiedResponse`) आणि अ‍ॅनोटेट करते (`meta.credentialsRedacted`, `meta.count`).

पुनरागमन गार्ड: `tests/unit/credential-masker-guardrail.test.ts`.

## मूलभूत करार (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true असल्यास साखळीचे पुढील कार्य तत्काळ थांबते
  message?: string; // अवरोधित करताना दर्शविला जाणारा संदेश
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // विनंती पुन्हा लिहिण्यासाठी preCall कडून परत केला जातो
  modifiedResponse?: TValue; // प्रतिसाद पुन्हा लिहिण्यासाठी postCall कडून परत केला जातो
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

`void`, `{}`, किंवा `{ block: false }` यांपैकी काहीही परत करून guardrail "कोणताही बदल नाही" असे सूचित करते. `modifiedPayload`/`modifiedResponse` परत केल्यास, साखळीमधून पुढील guardrails कडे जाणारे मूल्य बदलले जाते.
`signal?: AbortSignal` कॉलरचे जीवनचक्र guardrails पर्यंत पोहोचवते. विनंती रद्द करणे हा मुद्दाम ठेवलेला fail-open अपवाद आहे: ज्याला raw media समर्थित नसल्याचे माहीत आहे अशा target मध्ये ते पुनर्स्थापित न करता, media bridges काम थांबवतात आणि cleanup करतात.

## रजिस्ट्री (`registry.ts`)

singleton `guardrailRegistry` पुढील गोष्टी उपलब्ध करून देते:

- `register(guardrail)` — guardrail जोडते (किंवा normalized name नुसार बदलते) आणि चढत्या `priority` क्रमाने पुन्हा क्रमवारी लावते.
- `clear()` / `list()` — प्रशासकीय सहाय्यक.
- `runPreCallHooks(payload, context)` — सक्रिय guardrails वर पुनरावृत्ती करते, `modifiedPayload` द्वारे payload पुढे पाठवते आणि पहिल्या `block: true` वर थांबते.
- `runPostCallHooks(response, context)` — प्रतिसादाच्या बाजूने समान प्रवाह.
- `resetGuardrailsForTests({ registerDefaults })` — स्वच्छ चाचणी विलगीकरणासाठी स्थिती साफ करते आणि पर्यायाने defaults पुन्हा नोंदवते.

दोन्ही runners `{ blocked, payload|response, results, guardrail?, message? }` परत करतात, ज्यामध्ये `results` हा `GuardrailExecutionResult` नोंदींचा array असतो. या नोंदींमध्ये प्रत्येक guardrail साठी `blocked`, `skipped`, `modified`, `error`, आणि `meta` fields समाविष्ट असतात आणि त्या tracing साठी उपयुक्त असतात.

### प्रत्येक विनंतीनुसार Guardrails अक्षम करणे

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` सध्याच्या विनंतीसाठी वगळल्या जाणाऱ्या guardrail names ची पुनरावृत्ती-विरहित यादी एकत्रित करते. स्रोत (सर्व पर्यायी, सर्व एकत्रित केले जातात):

- `apiKeyInfo.disabledGuardrails`
- विनंती body मधील `disabledGuardrails` (top-level)
- विनंती body मधील `metadata.disabledGuardrails`
- Header `x-omniroute-disabled-guardrails` (किंवा जुना
  `x-disabled-guardrails`)

मूल्ये strings चे arrays किंवा स्वल्पविरामाने विभक्त केलेली string असू शकतात; names lowercase kebab-case मध्ये normalize केली जातात (`pii_masker` → `pii-masker`). परिणाम `context.disabledGuardrails` द्वारे registry कडे पाठवला जातो, जी जुळणारे guardrails वगळते (`results` मध्ये `skipped: true`).

## अंमलबजावणीचा क्रम

`src/sse/handlers/chat.ts` आणि
`open-sse/handlers/chatCore.ts` मधून जाणाऱ्या प्रत्येक विनंतीसाठी:

1. `resolveDisabledGuardrails(...)` API की, बॉडी आणि हेडर्सवरून वगळण्याची यादी तयार करते.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` चढत्या प्राधान्यक्रमाने गार्डरेल्स चालवते:
   - अक्षम केलेल्या गार्डरेल्सची `skipped` म्हणून नोंद केली जाते.
   - प्रत्येक गार्डरेलचे `preCall`, `modifiedPayload` द्वारे पेलोड पुन्हा लिहू शकते.
   - पहिले `block: true` आल्यावर साखळी त्वरित थांबते आणि हँडलर गार्डरेल नकार प्रतिसाद परत करतो.
3. (संभाव्यतः पुन्हा लिहिलेला) पेलोड कॉम्बो राउटिंग आणि अपस्ट्रीम डिस्पॅचकडे जातो.
4. प्रतिसाद तयार झाल्यानंतर, `guardrailRegistry.runPostCallHooks(...)` प्रतिसादावर तीच साखळी चालवते. येथे `block: true` असल्यास अपस्ट्रीम प्रतिसाद वगळला जातो.

अपवाद निर्माण करणाऱ्या गार्डरेल्सची `error: <message>` सह नोंद केली जाते आणि `logger.warn` द्वारे लॉग केले जाते, मात्र साखळी सुरूच राहते — रचनेनुसार फेल-ओपन.

## संरचना

अंगभूत गार्डरेल्सद्वारे वाचली जाणारी पर्यावरण चल:

| चल                                    | यामध्ये वापरले जाते        | परिणाम                                                                                             |
| ------------------------------------- | -------------------------- | -------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | शोध पूर्णपणे अक्षम करण्यासाठी `false` सेट करा.                                                     |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | इंजेक्शन धोरण: `warn`, `block`, किंवा `log`. जुने मूल्य `redact` इंजेक्शन मजकूर पुन्हा लिहीत नाही. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | इंजेक्शन गार्डसाठी मोड; तसेच पर्यावरण चलांना **अधिलिखित** करणारा DB फीचर फ्लॅग (DB > ENV).         |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | `MODE=block` द्वारे नाकारली जाणारी किमान तीव्रता: `high` (डीफॉल्ट), `medium`, किंवा `low`.         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD` साठी जुने पर्यायी नाव.                                           |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | `true` असताना, विनंतीमधील PII झाकले जाते (इंजेक्शन मोडपासून स्वतंत्र).                             |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (डाउनस्ट्रीम) | प्रतिसादाच्या बाजूच्या मास्करचे वर्तन नियंत्रित करते.                                              |

Modality Bridge गार्डरेल्स पर्यावरण चलांऐवजी DB-समर्थित सेटिंग्ज स्टोअरमधून (`getSettings()`) रनटाइम संरचना वाचतात. Vision च्या प्राथमिक की
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, आणि
`modalityBridgeCacheMaxEntries` आहेत. जुन्या
`visionBridge*` की केवळ दस्तऐवजीकृत एक-चक्र वाचन फॉलबॅक म्हणून स्वीकारल्या जातात; डॅशबोर्डमधून होणाऱ्या लेखनांसाठी प्राथमिक की वापरल्या जातात. डीफॉल्ट्स आणि फॉलबॅक रिझॉल्व्हर `src/shared/constants/modalityBridgeDefaults.ts` मध्ये आहेत, तर जुन्या कॉन्स्टंट्स `src/shared/constants/visionBridgeDefaults.ts` मध्ये कायम ठेवलेल्या आहेत.

Audio हे `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout`, आणि `modalityBridgeAudioMaxClips`, तसेच सामायिक
`modalityBridgeCache*` सेटिंग्ज वापरते. Audio साठी जुन्या कींचा फॉलबॅक नाही, कारण या की Modality Bridge स्कीमासोबत सादर करण्यात आल्या होत्या.

Video हे `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos`, आणि
`modalityBridgeVideoTimeout`, तसेच सामायिक `modalityBridgeCache*` सेटिंग्ज वापरते.
ते डीफॉल्टनुसार अक्षम असते, कारण FFmpeg/ffprobe या पर्यायी कार्यान्वयन अवलंबिता आहेत आणि फ्रेम कॅप्शनिंगमुळे विलंब व मॉडेल खर्च वाढतो.

## सानुकूल Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

पायऱ्या:

1. `BaseGuardrail` विस्तारित करणारी `src/lib/guardrails/myGuardrail.ts` तयार करा.
2. `preCall` आणि/किंवा `postCall` लागू करा.
3. एकतर आयात करताना नोंदणी करा (`registerDefaultGuardrails` मधून पुश करा) किंवा
   रनटाइममध्ये `guardrailRegistry.register(...)` कॉल करा — रजिस्ट्री समान सामान्यीकृत
   नाव असलेली कोणतीही आधीची guardrail बदलते.
4. `tests/unit/` अंतर्गत चाचण्या जोडा (विद्यमान उदाहरणे:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## चाचणी

ज्ञात स्थितीपासून सुरुवात करण्यासाठी चाचण्यांदरम्यान `resetGuardrailsForTests()` वापरा.
रिकाम्या रजिस्ट्रीपासून सुरुवात करण्यासाठी `{ registerDefaults: false }` पास करा आणि

इंजेक्शन (`deps.getSettings`, `deps.callVisionModel`) स्वीकारते; Audio Bridge सेटिंग्ज,

## Injection-guard मार्ग कव्हरेज आणि रेड-टीम (टप्पा 8 · ब्लॉक D)

injection-guard (`createInjectionGuard` / `withInjectionGuard`) वापरकर्त्याचे प्रॉम्प्ट स्वीकारणारे सर्व मार्ग
व्यापते. ते `INJECTION_GUARD_MODE` चे पालन करते (डीफॉल्ट `warn` = फक्त लॉग;
`block` = HTTP 400 `SECURITY_001` परत करते).

| प्रकार           | मार्ग                                                                                                                                                | डीफॉल्ट मोड |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| मजकूर (विद्यमान) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| जनरेटिव्ह        | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| डेटा             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

मजकूर निष्कर्षण (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` व्यापते.

**रेड-टीम (दररोज रात्री, `nightly-llm-security.yml`):** promptfoo हे सत्यापित करते की प्रत्येक मार्ग
`INJECTION_GUARD_MODE=block` मध्ये OWASP-LLM कॉर्पस ब्लॉक करतो; garak प्रोब्स चालवते (secret नसल्यास वगळते).
सुसंगततेसाठी `moderations` समाविष्ट केले आहे — ब्लॉक-मोडमधील ऑपरेटर `resolveDisabledGuardrails` द्वारे
त्याला सूट देऊ शकतात.

रात्रीचे वर्कफ्लो (`.github/workflows/nightly-llm-security.yml`, cron + मॅन्युअल
डिस्पॅच) दोन जॉब्सचे आहे:

- **`promptfoo-guard` (ब्लॉकिंग)** — `INJECTION_GUARD_MODE=block` सह
  `promptfoo eval -c promptfooconfig.yaml` चालवते. प्रत्येक प्रतिकूल प्रकरण (उदा. "मागील सर्व
  सूचना दुर्लक्षित करा…", DAN-शैलीतील जेलब्रेक्स) प्रतिसादात
  `error.code === "SECURITY_001"` असल्याचे निश्चित करते, म्हणजेच guard ने विनंती प्रत्यक्षात नाकारली.
- **`garak` (सल्लात्मक)** — स्थानिक OmniRoute इन्स्टन्सवर (`http://localhost:20128/v1`)
  garak `--probes promptinject,dan,leakreplay` चालवते. हे provider secret
  (`PROMPTFOO_PROVIDER_KEY`) वर अवलंबून असते; secret नसल्यास व्यवस्थितपणे वगळते आणि त्याला
  `|| true` प्रत्यय जोडलेला असतो, त्यामुळे ते CI अयशस्वी न करता अहवाल देते.

guard helper (`createInjectionGuard` / `withInjectionGuard`) चे कव्हरेज
प्रॉम्प्ट असलेल्या प्रत्येक `/v1` मार्गावर पसरलेले आहे; प्रॉम्प्ट मजकूर
`src/shared/utils/inputSanitizer.ts` मधील `extractMessageContents()` द्वारे
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` मधून घेतला जातो.
