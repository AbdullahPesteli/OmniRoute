> **อัปเดตล่าสุด:** 2026-08-29 — v3.8.51 (ที่มาของทรานสคริปต์ Video Bridge ถูกประกาศโดยผู้เรียก
> และยังไม่ได้รับการตรวจสอบโดยเซิร์ฟเวอร์ — ชี้แจงตาม #11661)

Guardrails บังคับใช้มาตรการด้านความปลอดภัย นโยบาย และการแปลงเนื้อหาที่ขอบเขต
ระหว่าง OmniRoute กับผู้ให้บริการต้นทาง Guardrail แต่ละตัวสามารถตรวจสอบ (และ
เลือกที่จะปฏิเสธ แปลง หรือใส่คำอธิบายประกอบ) เพย์โหลดคำขอ (`preCall`) และ
การตอบกลับจากต้นทาง (`postCall`)

ระบบนี้เป็นแบบ **fail-open**: หาก Guardrail เกิดข้อผิดพลาดขณะทำงาน รีจิสทรี
จะบันทึกข้อผิดพลาดและดำเนินการต่อด้วย Guardrail ตัวถัดไป แทนที่จะทำให้
คำขอล้มเหลว การบล็อกต้องเกิดจากการตัดสินใจอย่างชัดเจน (`block: true`) ไม่ใช่เหตุบังเอิญ

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

ดักจับคำขอที่มีภาพซึ่งมุ่งเป้าไปที่ **โมเดลที่ไม่ใช่ภาพ** และ
เปลี่ยนเส้นทางคำขอทั้งหมดไปยังโมเดลที่รองรับภาพหรือแทนที่ส่วนของภาพ
ด้วยคำอธิบายข้อความที่สร้างโดยโมเดลภาพที่สามารถกำหนดค่าได้ก่อน
การเรียกขึ้นต้น นี่ช่วยให้ผู้ให้บริการที่มีเฉพาะข้อความสามารถจัดการ
กับข้อมูลหลายรูปแบบได้อย่างโปร่งใส

การไหล:

1. ข้ามหากโมเดลเป้าหมายรองรับภาพอยู่แล้ว (เว้นแต่จะปรากฏใน
   รายการบังคับ `isVisionBridgeForcedModel`).
2. ดึงส่วนของภาพผ่าน `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), ซึ่งมอบหมายให้กับ **ตัวตรวจจับสื่อ
   ที่รวมกัน** `detectMediaParts()` ใน `open-sse/utils/mediaParts.ts` — แหล่งข้อมูลเดียวที่แชร์กับตัวกรองความเข้ากันได้แบบรวม
   การดึงจะอนุญาตเฉพาะส่วนระดับสูงสุดของรูปร่าง
   `replaceImageParts` ที่สามารถนำกลับมาใช้ใหม่ได้ (สัญญา extract↔replace): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, และ Responses API `input_image`. การตีที่ซ้อนกันและ
   รูปร่างที่มีเฉพาะตัวบ่งชี้เป็นวัสดุสำหรับการกรองแบบรวมและจะไม่ถูกดึงออก
   ข้ามหากไม่พบ.
3. แก้ไขการตั้งค่ารันไทม์ผ่าน `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): คีย์การตั้งค่าใหม่ `modalityBridge*`
   จะชนะ; คีย์ `visionBridge*` แบบเก่ายังคงเป็น **การสำรองข้อมูลรอบเดียว**
   (หน้าต่างการย้อนกลับ). ข้ามก่อนการเดินทางสื่อใด ๆ เมื่อ
   สะพานถูกปิดใช้งาน.
4. ตัวเลือกโหมด (`modalityBridgeVisionMode`, ดูตารางด้านล่าง) ตัดสินใจ
   ว่าจะเปลี่ยนเส้นทางหรืออธิบาย. การเปลี่ยนเส้นทางจะส่งคืน `modifiedPayload` โดยมีเพียง `model`
   ที่ถูกสลับ, พร้อมเมตา `{ rerouted, fromModel, toModel, imagesKept }`.
5. เส้นทางการอธิบาย: จำกัดภาพที่ `maxImages`, รวบรวมคำสั่งที่ตระหนักถึงงาน,
   ปรึกษาคำอธิบายแคช, เรียกโมเดลภาพ **พร้อมกัน**
   (`Promise.allSettled`), และฉีดส่วนข้อความ `[Image N]: <description>` แทนที่ใน
   ที่ของพวกเขา. การอธิบายที่ล้มเหลวจะให้ `null` และส่วนภาพต้นฉบับจะ
   **ถูกเก็บรักษา** (#4012) — ยกเว้นในเส้นทางการอธิบายแบบรวมเมื่อการ
   อธิบายทั้งหมดล้มเหลว, ซึ่งจะได้รับการยืนยันว่าไม่มีการเชื่อมต่อที่รองรับภาพ
   ขึ้นต้นจะได้รับ stub `(unavailable — no vision-capable provider connected)` แทน (#8430).
6. ส่งคืน `modifiedPayload` + เมตา (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### ตัวเลือกโหมด (`modalityBridgeVisionMode`)

| โหมด       | ค่าเริ่มต้น | พฤติกรรม                                                                                                                                                                                                                                    |
| ---------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔           | อัลกอริธึมแบบเก่า, ไม่ถูกแตะต้อง (#6640/#7204): โมเดลที่ไม่ใช่แบบรวม/`auto/` จะเปลี่ยนเส้นทางไปยังโมเดลภาพที่ดีที่สุด เว้นแต่โมเดลต้นฉบับจะมีข้อมูลรับรองที่ใช้งานได้ (จากนั้นจะอธิบาย); เป้าหมายแบบรวมจะอธิบายเสมอ.                        |
| `describe` |             | อธิบายเสมอ — บล็อกการเปลี่ยนเส้นทางจะถูกข้ามโดยสิ้นเชิง; โมเดลที่ผู้ใช้เลือกจะตอบเสมอ.                                                                                                                                                      |
| `reroute`  |             | บังคับเปลี่ยนเส้นทาง: การป้องกันโมเดลที่มีข้อมูลรับรองจะถูกข้าม. การป้องกันข้อมูลรับรองเป้าหมายการเปลี่ยนเส้นทางยังคงมีผล — เมื่อไม่มีเป้าหมายภาพที่ใช้งานได้ คำขอจะตกไปที่การอธิบายเพื่อให้ภาพดิบไม่ถึงแบ็กเอนด์ที่มีเฉพาะข้อความ (#8430). |

โหมดที่บังคับจะทำงาน **ก่อน** ที่อัลกอริธึมอัตโนมัติจะทำงาน; พฤติกรรม `auto`
เหมือนกันกับการป้องกันก่อน PR-1.

#### ขอบเขต API-key (`visionBridgeKeyScope.ts`)

เมื่อคีย์ API ของผู้เรียกจำกัด `allowedConnections`, กลุ่มโควตา
(`allowedQuotas`) หรือโมเดล (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), สะพานจะเลือกเฉพาะโมเดลการเปลี่ยนเส้นทางและการอธิบายที่คีย์สามารถใช้ได้, บนการเชื่อมต่อที่คีย์สามารถใช้ได้. การเรียกอธิบายจะต้องผ่าน OmniRoute self-loop เสมอด้วย
หัวข้อ `x-omniroute-self-loop-key-id`, ดังนั้นคำขอแชทที่ได้รับจะบังคับใช้การเชื่อมต่อและนโยบายโมเดลของคีย์นั้นอีกครั้ง. `enforceApiKeyPolicy()`
จะให้เกียรติกับหัวข้อนั้นเฉพาะเมื่อรวมกับ bearer self-loop, ดังนั้นจึงสามารถ
จำกัดการเข้าถึงได้เท่านั้น, และ ID ที่ไม่สามารถแก้ไขได้จะถูกปฏิเสธ.

หากไม่มีโมเดลภาพที่อนุญาตสำหรับคีย์, เส้นทางการอธิบายจะหลีกทางและ
คำขอจะผ่านไปโดยไม่เปลี่ยนแปลง, พฤติกรรมการเปิดล้มเหลวเดียวกันกับการป้องกันที่ถูกปิดใช้งาน (เมตา `{ skipped: true, reason: "no_permitted_vision_model" }`).
คำขอที่ไม่มีคีย์, และคีย์ที่ไม่มีข้อจำกัดเหล่านี้, จะทำงานเหมือนเดิม.

#### คำสั่งอธิบายที่ตระหนักถึงงาน (`modalityBridgeVisionTaskAware`)

ค่าเริ่มต้น **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) จะเพิ่ม
ข้อความของ **ข้อความผู้ใช้ล่าสุด** (ตัดให้เหลือ 500 ตัวอักษร) ไปยังพื้นฐาน
prompt อธิบาย ซึ่งจะนำการอธิบายไปสู่สิ่งที่ผู้ใช้ถามจริง ๆ
(รูปแบบ codex-vision-proxy) และขอให้โมเดลวิสัยทัศน์ถอดความ
ข้อความที่มองเห็นได้ หากปิดธง — หรือไม่มีข้อความผู้ใช้ — จะใช้ prompt พื้นฐาน
โดยไม่มีการเปลี่ยนแปลง

คำขอ OpenAI ที่เข้ากันได้ของ self-loop อธิบาย (`callVisionModelSingle()`
ใน `visionBridgeHelpers.ts`) จะขอ `image_url.detail: "high"` เสมอ —
โดยไม่มีเงื่อนไข สำหรับผู้โทร/ผู้ให้บริการทุกคน ไม่ถูกควบคุมโดยสัญญาณจากลูกค้า
การสุ่มตัวอย่างรายละเอียดต่ำจะลดความแม่นยำของ OCR สำหรับงานถอดความข้อความ
ที่ prompt นี้ขอ ดังนั้นการเรียกอธิบายจึงขอรายละเอียดสูงเสมอโดยไม่คำนึงถึงระดับ
รายละเอียดที่คำขอเข้ามาใช้ นี่มีผลต่อเนื้อหาคำขออธิบายภายในเท่านั้น; ไม่เปลี่ยนแปลงวิธีที่
OmniRoute ส่งต่อ `image_url.detail` ของผู้โทรในคำขอหลัก —
ค่านั้นจะถูกนำไปใช้แยกต่างหาก และเฉพาะสำหรับลูกค้า OpenCode ที่ตรวจพบใน
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). สาขา
รูปแบบสายของ Anthropic ของ self-loop อธิบายไม่มีฟิลด์ `detail` และไม่ได้รับผลกระทบจากค่าเริ่มต้นใด ๆ

#### ขีดจำกัดผลลัพธ์การอธิบาย (`modalityBridgeVisionMaxChars`)

| คีย์                           | ค่าเริ่มต้น | ช่วง               |
| ------------------------------ | ----------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`         | `0` หรือ 100–50000 |

`0` (ค่าเริ่มต้น) หมายถึง **ไม่มีขีดจำกัด** — คำอธิบายที่ส่งคืนโดย
`callVisionModel()` จะถูกส่งผ่านโดยไม่เปลี่ยนแปลง รักษาพฤติกรรมที่มีอยู่
ค่าใด ๆ ในช่วง 100–50000 จะตัดคำอธิบายด้วย `…` ต่อท้ายก่อนที่จะถูกนำกลับมาเป็น
`[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` ใน `src/lib/guardrails/visionBridge.ts`).
เพิ่มค่านี้สำหรับงาน OCR ที่มีรายละเอียดมากซึ่งโมเดลด้านล่างต้องการการถอดความทั้งหมด;
ลดมันเพื่อจำกัดการใช้โทเค็นในโมเดลวิสัยทัศน์ที่พูดคุยมากเกินไป
ฟิลด์แดชบอร์ดอยู่ในแผงขั้นสูงของแท็บวิสัยทัศน์
(`modality-bridge-max-chars` ใน `ModalityBridgeVisionTab.tsx`) และจำกัดค่าใด ๆ
ระหว่าง 1 และ 99 ขึ้นไปที่ 100 ขณะที่ปล่อยให้ `0` ที่ชัดเจนไม่ถูกแตะต้อง — `0` เป็นค่า Zod ที่ถูกต้องในตัวมันเอง
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), ไม่ใช่เพียง
ค่าเริ่มต้น "ไม่ได้ตั้งค่า"

#### แคชการอธิบาย (`modalityBridge/bridgeCache.ts`)

แคช LRU + TTL ในหน่วยความจำสำหรับผลลัพธ์การอธิบาย แบ่งปันทั่วทั้งกระบวนการ
คีย์ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` โดยมีการจัดกรอบความยาว
(ไม่มีการชนกันของขอบเขตฟิลด์) ส่วนประกอบโมเดลคือ
โมเดลสะพานที่ **กำหนดค่า** ไม่ใช่โมเดลที่ตอบจริง —
`callVisionModel` อาจสำรองภายใน และการกำหนดคีย์ต่อความพยายามจะทำให้แคชแตก
การอธิบายที่ล้มเหลวจะไม่ถูกเก็บไว้ในแคช การตั้งค่า:

| คีย์                            | ค่าเริ่มต้น | ช่วง    |
| ------------------------------- | ----------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`      | —       |
| `modalityBridgeCacheTtlMinutes` | `60`        | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`       | 10–5000 |

#### การทำให้ภาพระยะไกลเป็นมาตรฐาน (self-loop describe/base64 fetch)

เมื่อสะพานดึง **ภาพระยะไกล** เอง — การเรียกตนเองของ Anthropic อธิบายและการแปลง base64
รูปแบบ claude-wire
(`ensureBase64ImagesForClaudeWire`), ทั้งสองผ่าน
`fetchRemoteImageAsDataUri()` ใน `visionBridgeHelpers.ts` — URI ข้อมูลที่ได้จะถูกส่งผ่าน
`normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) ก่อนที่จะถูกฝังในคำขอโมเดลวิสัยทัศน์
ภาพที่มีขนาดใหญ่เกินไปจะถูกปรับขนาดให้มี **ขอบยาว 2048px** (ตรงกับ
ขีดจำกัดการปรับขนาดที่ OpenAI/Anthropic ใช้แล้วที่ฝั่งเซิร์ฟเวอร์) ซึ่งลด
จำนวนไบต์ที่อัปโหลด/ความล่าช้าโดยไม่เปลี่ยนสิ่งที่โมเดลวิสัยทัศน์เห็น การปรับขนาด
ใช้ `sharp` ซึ่งโหลดผ่านการนำเข้าแบบไดนามิก: บนแพลตฟอร์มที่ไบนารี
ดั้งเดิมไม่สามารถโหลดได้ `normalizeDataUri()` **ไม่เคยโยนข้อผิดพลาด** — มันจะสำรอง
ไปยังการส่งผ่านของไบต์ต้นฉบับ ดังนั้นเส้นทางการอธิบาย/การแปลง base64
จึงทำงานได้เสมอ ไบต์ที่ไม่ใช่ภาพ (การดึงข้อมูลที่ไม่คืนค่าภาพที่ถอดรหัสได้) ก็จะถูกส่งผ่านโดยไม่เปลี่ยนแปลงเช่นกัน การทำให้เป็นมาตรฐานนี้
จำกัดเฉพาะภาพที่สะพานดึงสำหรับการเรียกตนเอง — จะไม่ถูกนำไปใช้กับ
ข้อมูลดิบที่ส่งผ่านของผู้โทร ซึ่งสอดคล้องกับหลักการการเปลี่ยนแปลงที่เลือกใช้เท่านั้น (กฎที่เข้มงวด #20)

#### โครงสร้างการตั้งค่า + การโยกย้าย

คีย์ใหม่ `modalityBridge*` จะถูกตรวจสอบโดย Zod ใน `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, กลุ่ม `modalityBridgeCache*` สามกลุ่ม และกลุ่ม
`modalityBridgeAudio*` ที่ใช้โดย Audio Bridge การโยกย้าย
`141_modality_bridge_settings.sql` จะคัดลอกค่า `visionBridge*` ที่มีอยู่ไปยังคีย์ใหม่ที่ตรงกัน (ไม่เปลี่ยนแปลง, ไม่เคยเขียนทับค่า `modalityBridge*` ที่ตั้งค่าโดยผู้ดำเนินการ); คีย์เก่าจะยังคงถูกยอมรับเป็นการสำรองข้อมูลอ่านสำหรับหนึ่งรอบการปล่อย

#### ส่วนหัวความโปร่งใส + สถิติ

การตอบสนองที่ถูกแปลงโดยการอธิบายจะมี
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(สร้างโดย `buildModalityBridgeHeader()` ใน `modalityBridge/bridgeStats.ts`,
ประทับโดย `withModalityBridgeHeader()` ใน `src/sse/handlers/chatHelpers.ts`).
คำขอที่ถูกเปลี่ยนเส้นทางจะไม่มีส่วนหัว — เนื้อหายังไม่ได้รับการเปลี่ยนแปลงและการเปลี่ยนโมเดล
ก็เห็นได้ชัดในฟิลด์ `model` ของเนื้อหาการตอบสนอง

`GET /api/modality-bridge/stats` (การตรวจสอบการจัดการ, ระดับเดียวกับ
`GET /api/settings`) จะส่งคืนตัวนับต่อโมดัลในหน่วยความจำ
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` สำหรับ `vision`, `audio`, และ
`video`. `averageLatencyMs` ใช้ `latencySamples`, ไม่ใช่ทุกความพยายาม, เป็น
ตัวหาร; การดำเนินการที่ไม่มีการวัดเวลาไม่สร้างตัวอย่างที่มีค่าเป็นศูนย์มิลลิวินาที.
`bridged` ยังคงเป็นชื่อที่เข้ากันได้ย้อนหลังสำหรับการแปลงที่ประสบความสำเร็จ;
ความพยายามที่ล้มเหลวจะไม่เพิ่มมัน.
ตัวนับจะรีเซ็ตเมื่อเริ่มกระบวนการใหม่ตามการออกแบบ
(การวัดผล, ไม่ใช่การบัญชี).

#### การกำหนดค่าดashboard

หน้าดashboard ที่เฉพาะเจาะจงคือ
`/dashboard/settings/modality-bridge`. แท็บ `Vision`, `Audio`,
และ `Video` ที่สามารถเข้าถึงได้ผ่าน URL จะรักษาพารามิเตอร์การค้นหาในขณะที่เปลี่ยนค่า `tab`.
แท็บ Vision จะแสดงการเปิดใช้งาน, โหมด, การเลือกโมเดล (รวมถึงค่าเริ่มต้นอัตโนมัติ),
การกระตุ้นที่รู้จักงาน, ขีดจำกัดเวลา/ภาพ/ความยาวคำอธิบาย/แคชที่สูงขึ้น, ตัวนับ
การทำงาน, และคำขอตัวอย่างที่มีการป้องกัน. แท็บ Audio ก็ใช้งานได้เช่นกัน: มันแสดง
การเปิดใช้งาน, ตัวเลือกโมเดลเฉพาะ STT ที่มี Auto, ขีดจำกัดเวลา/คลิปสูงสุด, ตัวนับเสียง,
และการทดสอบตัวอย่าง `input_audio`. แท็บ Video ทำงานได้: มันรายงาน
สถานะการทำงานของ FFmpeg/ffprobe — หนึ่งในสี่สถานะ UI ที่ชัดเจน (`unknown` ขณะที่
การตรวจสอบอยู่ในระหว่างการบินหรือไม่สามารถทำได้, `restricted` บนโฮสต์แดชบอร์ดที่ไม่ใช่
loopback ซึ่งการตรวจสอบถูกข้ามที่ฝั่งลูกค้า, `unavailable` เมื่อถูกตรวจสอบแล้ว
และยืนยันว่าขาดหายไป, หรือ `available` พร้อมกับเวอร์ชัน FFmpeg/ffprobe) — ยังคง
รักษาขีดจำกัดการเปิดใช้งาน/โมเดล/เฟรม/วิดีโอ/เวลา, กรองตัวเลือกโมเดลให้เป็น
โมเดลที่สามารถมองเห็นได้, และแสดงตัวนับวิดีโอ.

การ์ด Vision Bridge ก่อนหน้านี้ภายใต้การตั้งค่า AI เป็นลิงก์ความเข้ากันได้กับ
หน้าที่ใหม่; มันไม่เป็นเจ้าของสำเนาที่สองของฟอร์มอีกต่อไป. ผู้ให้บริการสื่อยัง
เชื่อมโยงการทำงาน Image-to-Text และ Speech-to-Text กับแท็บ Modality
Bridge ที่เกี่ยวข้องโดยไม่ลบสนามเด็กเล่น Speech-to-Text ที่มีอยู่.

**การข้ามการอนุญาตการวนซ้ำตัวเอง:** เมื่อการเรียกคำอธิบายถูกส่งผ่าน
self-loop `/v1` ของ OmniRoute (โมเดลผู้ให้บริการที่ไม่เป็นมาตรฐาน), การร้องขอย่อยจะส่ง
`x-omniroute-admission-bypass: internal` และได้รับการตรวจสอบด้วย
ข้อมูลประจำตัว self-loop ที่แก้ไขแล้ว — sentinel `sk_omniroute` ในโหมดท้องถิ่น, หรือ
คีย์ env ที่กำหนดโดยผู้ดำเนินการ `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350) ดังนั้น
การปรับใช้ `REQUIRE_API_KEY=true` ยังคงสามารถเรียกคำอธิบายได้. การข้ามนี้
จะได้รับการเคารพเฉพาะสำหรับข้อมูลประจำตัวที่แน่นอนเหล่านั้น, ดังนั้นลูกค้าภายนอกไม่สามารถใช้
header เพื่อข้ามการอนุญาต.

ค่าเริ่มต้นเก่าจะอยู่ใน `src/shared/constants/visionBridgeDefaults.ts`; ค่าเริ่มต้น
ใหม่ที่รู้จักโหมด/งาน/แคชและตัวแก้ไขการตั้งอยู่ใน
`src/shared/constants/modalityBridgeDefaults.ts`. การป้องกันแสดงตัวเลือก
`deps` ในตัวสร้างเพื่อให้การทดสอบสามารถฉีด `getSettings` และ
`callVisionModel` ที่ปลอมได้.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ดักจับคำขอแชทที่มีเสียงก่อนที่จะถึงเป้าหมายที่ไม่รู้จักว่า
ยอมรับการป้อนข้อมูลเสียง. มันไม่เปลี่ยนเส้นทางคำขอแชท: ส่วนเสียงจะถูก
ถอดความผ่านจุดสิ้นสุด multipart ที่เข้ากันได้กับ OpenAI ที่มีอยู่และโมเดลแชทที่เลือกจะดำเนินการต่อด้วย
การถอดความเป็นข้อความ.

การไหล:

1. แก้ไข `supportsAudio` ผ่าน `getResolvedModelCapabilities()`. เมตาดาต้าของ
   การลงทะเบียนผู้ให้บริการที่ชัดเจนจะชนะ, จากนั้นเมตาดาต้าของโมเดลแบบสถิติ, จากนั้น
   `modalities_input` ที่ซิงค์. รายการป้อนที่ประกาศโดยไม่มี `audio` จะเป็น `false`; ไม่มี
   หลักฐานความสามารถจะยังคงเป็น `null`. ทั้ง `false` และ `null` จะเปิดใช้งาน
   สะพานที่อนุรักษ์นิยม, ในขณะที่ `true` จะข้ามมัน.
2. แก้ไขการตั้งค่า `modalityBridgeAudio*` และดึงส่วนเสียงระดับสูงที่สามารถตัดต่อได้
   จากทุกข้อความผ่านตัวตรวจจับ `detectMediaParts()` ที่แชร์. รูปร่างสายที่รองรับคือ
   OpenAI `input_audio`, `audio_url`, และ `source.media_type: "audio/*"`. เสียงที่ซ้อนกันจะถูกตรวจจับ
   สำหรับการส่งต่อแต่ไม่ถูกลบโดยเส้นทางการตัดต่อ. งานจะถูกจำกัดโดย
   `modalityBridgeAudioMaxClips`; ส่วนที่ตามมาจะไม่ถูกแตะต้อง.
3. เคารพ `provider/model` ที่กำหนด, หรือให้ `selectAudioBridgeModel()` เดิน
   `AUDIO_TRANSCRIPTION_PROVIDERS` ในลำดับแคตตาล็อกที่เสถียรและเลือกโมเดลแรกที่มี
   ข้อมูลประจำตัวผู้ให้บริการที่ใช้งานได้.
4. `callAudioTranscription()` แปลงเสียง base64/data-URI เป็น multipart
   `file`, หรือดาวน์โหลด `audio_url` ระยะไกลผ่านการป้องกันที่ออกไปสาธารณะเท่านั้น
   พร้อมการปักหมุด DNS และขีดจำกัด 25 MB. จากนั้นจะ POST ไฟล์และโมเดลที่เลือกไปยัง
   self-loop `/v1/audio/transcriptions` ในท้องถิ่น, ได้รับการตรวจสอบด้วย
   `resolveSelfLoopBearer()`. เส้นทางการถอดความที่มีอยู่จะทำการค้นหาข้อมูลประจำตัวตามปกติ,
   การจัดการการระบาย/การจำกัดอัตรา, และการส่งมอบผู้ให้บริการ.
5. การเรียกที่ประสบความสำเร็จจะเปลี่ยนส่วนของพวกเขาเป็น `[Audio N]: <transcript>`. การเรียกจะ
   ทำงานด้วย `Promise.allSettled`: ความล้มเหลวแต่ละรายการจะรักษาส่วนเสียงเดิม (#4012 สัญญา).
   หากการเรียกทั้งหมดล้มเหลวและเป้าหมายได้รับการพิสูจน์ว่า `supportsAudio === false`,
   ส่วนจะกลายเป็น
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 สัญญา). สำหรับ
   เป้าหมายที่ไม่รู้จัก (`null`), ผลลัพธ์ที่ล้มเหลวทั้งหมดจะยังคงไม่ถูกแตะต้อง. เป้าหมายที่พิสูจน์แล้วว่า
   เป็นข้อความเท่านั้นที่ไม่มีข้อมูลประจำตัว STT ที่ใช้งานได้จะได้รับ stub ที่ชัดเจนเดียวกันโดยไม่ต้อง
   ส่งคำขอเครือข่าย.

การถอดความที่ประสบความสำเร็จจะใช้แคช Modality Bridge LRU/TTL ทั่วทั้งกระบวนการ.
กุญแจจะรวมการอ้างอิงเสียง, ป้ายการดำเนินการ `audio-transcription` ที่เสถียร,
และโมเดล STT ที่เลือก; ความล้มเหลวจะไม่ถูกเก็บไว้ในแคช. ความพยายามเสียงจะอัปเดต
ตัวนับ `bridged`, `cacheHits`, `failures`, และ `lastUsedAt` ที่แชร์.
การตอบสนองที่แปลงแล้วจะมี
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; คำขอที่ไม่ถูกแตะต้องจะไม่
ได้รับส่วน Audio Bridge.

การตั้งค่าในระยะเวลาจะถูกสนับสนุนโดย DB และตรวจสอบโดย Zod:

| คีย์                          | ค่าเริ่มต้น | ช่วง                  |
| ----------------------------- | ----------- | --------------------- |
| `modalityBridgeAudioEnabled`  | `true`      | —                     |
| `modalityBridgeAudioModel`    | `""`        | อัตโนมัติ หรือ STT ID |
| `modalityBridgeAudioTimeout`  | `60000`     | 1000–300000           |
| `modalityBridgeAudioMaxClips` | `3`         | 1–10                  |

แคชที่แชร์จะถูกควบคุมโดย `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` และ `modalityBridgeCacheMaxEntries`。

### วิดีโอบริดจ์ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ดักจับส่วนวิดีโอระดับสูงใน Chat Completions `messages` และ Responses
API `input` ก่อนที่เป้าหมายที่ไม่มีการสนับสนุนวิดีโอพื้นเมืองที่รู้จักจะถูกเรียก
รูปแบบที่รองรับคือ `input_video`, `video_url`, `video_source`, HTTPS URLs,
และ `data:video/*;base64,...` data URIs ชื่อไฟล์ธรรมดาในข้อความจะไม่ถูกจัดการ
เป็นวิดีโอ。

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) เป็นเจ้าของการเดินทางของคำขอ,
การตรวจสอบความสามารถ/นโยบาย, การรวมข้อมูลต่อคำขอ, และข้อมูลการตอบกลับ
การทำงานต่อวิดีโอ — การเข้าซื้อ, แคชผลลัพธ์ทั้งหมด, การอธิบายลำดับเฟรม
(ซึ่งรวมการถอดเสียงเสียงที่ประกาศโดยผู้เรียก), และเมตริก/การยกเลิก/การทำความสะอาดต่อการพยายาม
— ถูกซ่อนอยู่หลัง `processVideoPart` ใน
`videoBridgePipeline.ts`, ถูกเรียกครั้งเดียวต่อส่วนวิดีโอภายในลูปของ `preCall`
โมดูลนั้นยังนิยามขอบเขตพอร์ตที่ชัดเจน `VideoMediaBrokerPort`
(การเข้าซื้อไบต์และการดึงเฟรมที่สุ่มตัวอย่าง), `VideoAudioTranscriptionPort`
(การรวมการถอดเสียงเสียงที่ประกาศโดยผู้เรียกกับคำบรรยายที่สุ่มตัวอย่าง), และ
`VideoDrilldownPort` (รูปแบบการจัดเก็บดิบแบบเก่า) การผลิต STT และการเก็บเฟรม
ถูกสร้างขึ้นรอบพอร์ตที่อธิบายผ่าน `createVideoSttAdapter` และ
`createVideoDrilldownAdapter`; ตัวหลังใช้วงจรชีวิตที่แชร์แบบ opaque-handle。

เส้นทางคำขอสาธารณะ `/v1` จะไม่นำเข้าหรือเรียกใช้กระบวนการย่อย ระยะไกล
วิดีโอจะถูกดาวน์โหลดภายใต้ขอบเขต 50 MiB; วิดีโอ base64 แบบในบรรทัดมี
ขีดจำกัดการถอดรหัสที่อนุรักษ์นิยม 36 MiB ต่อวิดีโอเพื่อให้โมเดล/ข้อความ/กรอบ
สามารถอยู่ภายในขีดจำกัดการอนุญาตคำขอ JSON สาธารณะ 50 MiB ความยาวในบรรทัดและการประมาณขนาดที่ถอดรหัสจะถูกตรวจสอบก่อนการจัดสรร HTTPS เป็น
สิ่งจำเป็นใน URL ระยะไกลเริ่มต้นและการเปลี่ยนเส้นทางทุกครั้ง โดยใช้การป้องกันที่มีอยู่
เฉพาะสาธารณะกับการปักหมุด DNS ไบต์จะข้ามพรมแดนของนายหน้า `POST /api/modality-bridge/video/extract` ที่แน่นอน เส้นทางนั้นเป็นทั้ง
`LOCAL_ONLY` และ `SPAWN_CAPABLE`, ยอมรับเฉพาะคำขอที่ผ่านการตรวจสอบแล้ว,
trusted-loopback ต่อกระบวนการ, และไม่เคยยอมรับ URL, เส้นทางระบบไฟล์, ไฟล์ที่สามารถเรียกใช้,
หรือรายการอาร์กิวเมนต์ เนื้อหาของ API ขนาดท่อและตัวอ่านเนื้อหาที่เพิ่มขึ้นของตัวจัดการจะบังคับใช้ขีดจำกัดการป้อนข้อมูลนายหน้า 50 MiB คิวที่มีขอบเขตทำงาน
การดึงข้อมูลครั้งละหนึ่งครั้ง, อนุญาตให้มีงานที่รอดำเนินการสี่งาน, และจำกัดการป้อนข้อมูลที่รอดำเนินการที่
100 MiB。

ภายในนายหน้า `ffprobe` อ่านไฟล์ท้องถิ่นส่วนตัว; รายการอนุญาตรูปแบบที่แน่นอนจะไม่รวมรูปแบบเพลย์ลิสต์และแมนิเฟสต์ สำหรับคอนเทนเนอร์ MOV-family ที่อนุญาต การอ้างอิงข้อมูล MOV ภายนอกจะถูกปิดใช้งานตามค่าเริ่มต้น และคำสั่งที่แน่นอนจะไม่เลือกใช้พวกเขา ทั้ง `ffprobe` และ `ffmpeg` ใช้
รายการอนุญาตโปรโตคอล `file` เท่านั้น, เธรดเดียว, อาร์กิวเมนต์ที่แน่นอน, ไม่มีเชลล์,
และไฟล์ที่สามารถเรียกใช้ที่แก้ไขจาก `PATH` สตรีมภาพที่แนบมาจะไม่ใช่ผู้สมัครที่สามารถเล่นได้ สตรีมที่สามารถเล่นได้ทั้งหมดต้องเป็นไปตามขีดจำกัด และสตรีมเริ่มต้นที่ชัดเจนจะถูกเลือกก่อนการสำรองข้อมูลที่มีดัชนีต่ำสุดที่กำหนด วิดีโอมีขีดจำกัดที่ 600 วินาที, 8,192 พิกเซลต่อมิติ, และ
33,554,432 พิกเซลต้นทาง FFmpeg จะสุ่มตัวอย่างเฟรม JPEG จุดกึ่งกลาง 1–16, ลดขนาดขอบยาวลงเหลือสูงสุด 1,024 พิกเซลโดยไม่ทำการขยายขนาดข้อมูลขนาดเล็กกว่า และ
ไม่เคยได้รับ URL การสุ่มตัวอย่างจะเป็น `uniform` ตามค่าเริ่มต้น นโยบาย `scene_aware` และ `segment_aware` ที่เลือกใช้จะทำการผ่าน FFmpeg ที่แน่นอนเพิ่มเติมหนึ่งครั้งเหนือสตรีมท้องถิ่นที่ได้รับการตรวจสอบแล้ว, เลือกขีดจำกัด `showinfo` เวลาตำแหน่งฉาก, และสำรองข้อมูลอย่างแน่นอนไปยังจุดกึ่งกลางที่เป็นสากลเดียวกันเมื่อการตรวจจับล้มเหลว, หมดเวลา, ผลลัพธ์ที่ไม่ถูกต้อง, หรือชุดผู้สมัครว่าง โหมดที่ตระหนักถึงส่วนจะจัดสรรตัวอย่างจุดกึ่งกลางตามสัดส่วนกับช่วงเวลาฉากที่ได้รับการตรวจสอบแล้ว; หลักฐานที่ตระหนักถึงส่วนและพฤติกรรมการสำรองข้อมูลจะถูกอธิบายด้านล่าง ขีดจำกัด 16 เฟรมที่เข้มงวดจะถูกนำไปใช้หลังจากการเลือกในนโยบายทุกครั้ง เมื่อคำขอที่ตระหนักถึงฉากมีงบประมาณเพียงเฟรมเดียว มันจะใช้จุดกึ่งกลางที่เป็นสากลของวิดีโอเต็มหรือหน้าต่างโฟกัสที่ใช้งานอยู่และรายงาน `policyEffective: uniform`: เฟรมฉากที่เลือกเพียงเฟรมเดียวไม่สามารถรักษาทั้งสองด้านเวลาได้ ผู้เรียกสามารถเลือกที่จะให้หน้าต่างโฟกัสที่จำกัด (`start`/`end` วินาที); ขอบเขตจะถูกจำกัดให้ตรงกับระยะเวลาของสื่อ, หน้าต่างที่กลับด้านหรือไม่สิ้นสุดจะถูกปฏิเสธ, และนโยบายการสุ่มตัวอย่างทั้งหมดจะดำเนินการเฉพาะภายในช่วงเวลาที่เป็นมาตรฐาน หน้าต่างที่เกิดขึ้นจะรวมอยู่ในข้อมูลเมตาของการสุ่มตัวอย่างและในคำอธิบายที่ไม่เชื่อถือได้เพื่อให้โมเดลที่อยู่ด้านล่างสามารถแยกแยะระหว่างการตัดตอนที่มุ่งเน้นจากไทม์ไลน์ทั้งหมด。

การมุ่งเน้นคำบรรยายเชิงความหมายเป็นการตั้งค่าที่แยกต่างหากและชัดเจน โหมดการวิเคราะห์ค่าเริ่มต้น `full`
จะรักษาคำกระตุ้นเฟรมที่มีอยู่และไม่เคยส่งต่อข้อความคำขอไปยังโมเดลคำบรรยาย ในโหมด `focused` บริดจ์จะอ่านเฉพาะ `text`/`input_text` ที่ผู้ใช้เขียนขึ้นล่าสุดที่ไม่ว่างจากคอนเทนเนอร์ Chat หรือ Responses เดียวกัน, ทำให้เป็น NFC, รวบรวมอักขระควบคุมและช่องว่าง, และจำกัดไว้ที่ 500 จุดรหัส Unicode ผลลัพธ์ที่ว่างเปล่าจะสำรองข้อมูลไปยังคำกระตุ้น `full` ที่แน่นอน ข้อบ่งชี้ที่ใช้งานได้จะถูกจัดเรียงเป็น JSON ในบล็อกบริบทผู้ใช้ที่ไม่เชื่อถือได้ที่กำหนดไว้และอาจให้ความสำคัญกับรายละเอียดที่สังเกตได้เท่านั้น; มันไม่สามารถแทนที่คำเตือนแยกต่างหากเกี่ยวกับการปฏิบัติตามคำแนะนำที่มองเห็นหรือได้ยินในสื่อ การมุ่งเน้นข้อความจะไม่อนุมาน `start`/`end` หรือเปลี่ยน
ตัวสุ่มตัวอย่างตามเวลา。

#### หลักฐานส่วนโครงสร้าง FU-07

`segment_aware` ใช้การวิเคราะห์ล่วงหน้าที่มีขอบเขตหนึ่งครั้งบนสตรีมวิดีโอท้องถิ่นที่ได้รับการตรวจสอบแล้ว โซ่กรองที่กำหนดไว้จะปรับขนาดให้กว้างไม่เกิน 320 พิกเซล ตรวจจับการเปลี่ยนแปลงของฉากและช่วงเวลาที่หยุดนิ่ง จากนั้นทำการสุ่มตัวอย่างที่ 1 เฟรมต่อวินาทีสำหรับเบลอ ค่าเฉลี่ยลูม่า และข้อมูลเชิงพื้นที่/เชิงเวลา การวิเคราะห์นี้ถูกจำกัดไว้ที่ 600 ตัวอย่างเชิงโครงสร้าง หนึ่งเธรด FFmpeg/filter โปรโตคอลและรายการอนุญาตของคอนเทนเนอร์ที่เป็น `file` เท่านั้น ขอบเขตการประมวลผลที่ 1 MiB และไม่เกิน 30 วินาทีภายในการยกเลิก/กำหนดเวลาที่แชร์ของโบรกเกอร์ มันไม่เคยรับคำสั่ง กรอง เส้นทาง หรือ URL จากคำขอ

ค่าทางโครงสร้างเป็นหลักฐานการสุ่มตัวอย่างที่กำหนดได้ ไม่ใช่การเข้าใจวิดีโอเชิงความหมาย พวกเขาไม่อนุมานหัวข้อ การกระทำ คำบรรยาย การพูด หรือเจตนาของผู้ใช้ ขอบเขตของฉากและการหยุดนิ่งจะก่อให้เกิดส่วนต่าง ๆ การครอบคลุมการหยุดนิ่ง เบลอ การเปิดรับ แสงรายละเอียดเชิงพื้นที่ และการเปลี่ยนแปลงเชิงเวลาเพียงแค่มีอิทธิพลต่อการจัดสรรงบประมาณเฟรมที่มีอยู่ 1–16 เฟรม ส่วนที่หยุดนิ่งทั้งหมดจะถูกจำกัดที่หนึ่งเฟรม ในขณะที่ส่วนที่ไม่หยุดนิ่งจะแข่งขันกันเพื่อขอบเขตงบประมาณที่เหลือ เมื่อขอบเขตมีจำนวนมากกว่าผลลัพธ์ เฟรมจะถูกเก็บรักษาไว้ในช่วงเวลาเดียวกันเพื่อไม่ให้การตัดที่รวดเร็วในช่วงต้นสามารถซ่อนส่วนที่ยาวนานได้ ขอบเขตของฉากภายในความละเอียดการวิเคราะห์ 1 วินาทีของขอบเขตการหยุดนิ่งจะถูกรวมกัน

การขาดกรอง หลักฐานที่มีรูปแบบไม่ถูกต้อง/ว่างเปล่า ข้อผิดพลาดของตัวตรวจจับ หรือการหมดเวลาในการวิเคราะห์ล่วงหน้าที่มีขอบเขตจะล้มเหลวเปิดไปยังนโยบายจุดกึ่งกลางที่เป็นเอกลักษณ์ที่แน่นอน การยกเลิกจากผู้เรียกหรือกำหนดเวลาของโบรกเกอร์จะไม่ล้มเหลวเปิด: มันจะยุติการทำงานของกระบวนการย่อยที่กำลังดำเนินอยู่ ป้องกันการดึงเฟรมในภายหลัง และต้นไม้ชั่วคราวส่วนตัวจะถูกลบใน `finally`

`scripts/perf/video-bridge-fu07-eval.ts` สร้างการติดตั้ง FFmpeg ที่กำหนดได้จริงสำหรับการประหยัดการเรียกคำบรรยายหลังการลบซ้ำ การจัดสรรงบประมาณการเคลื่อนไหวหนา หลักฐานเบลอ/การเปิดรับ/ข้อมูล SI-TI การตัดที่รวดเร็วพร้อมหางยาว และผลบวกเท็จที่ค่อยเป็นค่อยไป มันบันทึกเวลาที่ใช้ในการวิเคราะห์ล่วงหน้า และเมื่อ `/usr/bin/time` มีให้ใช้งาน จะบันทึก CPU ของลูกและ RSS สูงสุด การตรวจสอบคุณภาพของมันเป็นเพียงออราเคิลเชิงโครงสร้าง คุณภาพของโมเดลคำบรรยายจริงยังคงอยู่ที่ `HOLD` เนื่องจากอุปกรณ์นี้ไม่มีจุดสิ้นสุดที่ได้รับอนุญาตหรือผู้ตัดสินที่หยุดนิ่ง การประหยัดเงินยังคงอยู่ที่ `HOLD` เว้นแต่ `--caption-cost-per-call-usd` จะให้การประมาณการเชิงบวกต่อการเรียกอย่างชัดเจน; สคริปต์จะไม่สร้างผลลัพธ์ใด ๆ

แต่ละเฟรมถูกจำกัดที่ 4 MiB เฟรมดิบทั้งหมดรวมกันไม่เกิน 23 MiB และการตอบสนองของโบรกเกอร์ที่ถูกจัดเรียงไม่เกิน 32 MiB ไดเรกทอรีชั่วคราวส่วนตัวจะถูกลบใน `finally` OmniRoute ไม่รวม FFmpeg และไม่รับเส้นทางที่สามารถเรียกใช้ได้แบบกำหนดเอง ก่อนการบรรยาย สะพานจะใช้การวิเคราะห์การลบซ้ำทางสายตาที่ระมัดระวัง: JPEG แต่ละไฟล์จะถูกลดขนาดลงเป็นบัฟเฟอร์สีเทาขนาด 16×16 และจะถูกเปรียบเทียบเฉพาะกับเฟรมสุดท้ายที่เก็บรักษาไว้ สำหรับงบประมาณคำบรรยายที่ร้องขอเกินหนึ่งเฟรม การดึงข้อมูลจะจัดเตรียมกลุ่มผู้สมัครที่มีขอบเขตไม่เกินสองเท่าของงบประมาณนั้นและไม่เกิน 16 เฟรม งบประมาณที่ร้องขอจะถูกนำไปใช้เฉพาะหลังจากการลบซ้ำ โดยผู้สมัครที่เลือกครั้งแรกและสุดท้ายจะถูกเก็บรักษาไว้ในระหว่างการลดขนาดขั้นสุดท้ายเมื่อมีงบประมาณอย่างน้อยสอง นโยบายที่มีเวอร์ชัน `grayscale-16x16-mean-cells-v2` จะใช้ค่าเฉลี่ยของค่าเฉลี่ยลูม่าและอัตราส่วนของเซลล์ภาพขนาดย่อที่มีค่าเบี่ยงเบนที่ปรับมาตรฐานอย่างน้อย 0.05 ขีดจำกัดการซ้ำจะเป็นค่าคงที่ 0.04 ซึ่งเลือกเพื่อความคาดเดาได้มากกว่าที่จะเปิดเผยเป็นการตั้งค่าเวลาทำงาน สัญญาณที่มีความคอนทราสต์สูงนี้จะรักษาการเคลื่อนไหวเล็กน้อยและการเปลี่ยนแปลงข้อความที่มองเห็นได้ซึ่งการเปรียบเทียบเฉพาะค่าเฉลี่ยอาจซ่อนอยู่ ข้อผิดพลาดของตัวเปรียบเทียบหรือตัวถอดรหัสจะล้มเหลวเปิดและรักษาการครอบคลุม เมตาดาต้าขาออกจะแยกผู้สมัครที่ถูกดึงออก เฟรมที่ใช้สำเร็จ และการซ้ำซ้อนทางสายตาที่ถูกทิ้ง

ส่วนวิดีโอที่ถูกทำเครื่องหมายอย่างชัดเจนอาจขอแผ่นติดต่อที่มีการระบุเวลา สะพานจะสร้างกริด JPEG ที่มีคอลัมน์สูงสุด 4 คอลัมน์และ 16 เฟรม เซลล์ขนาด 512 พิกเซลแต่ละเซลล์จะบันทึกเวลาแหล่งที่มาลงในแถบด้านล่างที่มีความคอนทราสต์สูง ในขณะที่เวลาเดียวกันจะยังคงอยู่ในเมตาดาต้าข้อความสำหรับการเชื่อมโยงและการตรวจสอบในภายหลัง JPEG ที่สมบูรณ์จะถูกจำกัดที่ 32 MiB หาก `sharp` ไม่สามารถถอดรหัสหรือประกอบกริดได้ สะพานจะกลับไปที่เฟรม JPEG ทีละเฟรม การยกเลิกจากลูกค้าจะยังคงส่งผ่านการดำเนินการแผ่น

หลักฐานการส่งเสริมถูกแยกออกอย่างตั้งใจจากไมโครเบนช์มาร์คการประกอบสังเคราะห์ `scripts/perf/video-bridge-contact-sheet-eval.ts` กำหนด A/B harness ที่มีเวอร์ชันสคีมาสำหรับโมเดลวิสัยทัศน์ที่เข้ากันได้กับ OpenAI จริง มันวัดจำนวนโทเค็นที่รายงานโดยผู้ให้บริการ ความล่าช้าของกำแพงแบบ end-to-end (รวมถึงการประกอบแผ่น) จำนวนการเรียกโมเดล และการเก็บรักษาข้อเท็จจริงที่กำหนดโดยแผนผัง การตอบสนองของโมเดลดิบจะไม่ถูกเขียนลงในรายงาน; จะเก็บเฉพาะ SHA-256 และ ID ข้อเท็จจริงที่ตรงกัน อุปกรณ์นี้จะไม่ทำการเรียกโมเดลที่มีเครือข่ายหรือจ่ายเงินเว้นแต่ `--execute-real` จะถูกส่งผ่านและ `--model`, `OMNIROUTE_BASE_URL`, และ `OMNIROUTE_API_KEY` ถูกกำหนดค่า โดยไม่มีการเรียกใช้งานจริงอย่างชัดเจน คำตัดสินที่อ่านได้ของมันจะยังคงอยู่ที่ `HOLD`; การวัดเฉพาะการเรียก/โหลดสังเคราะห์เพียงอย่างเดียวไม่ถือเป็นหลักฐานการส่งเสริม

`scripts/perf/video-bridge-promotion-eval.ts` แยกต่างหากจะใช้การสังเกต FU-07 หรือ FU-09 การเข้ารับการส่งเสริมต้องการประเภทสถานการณ์สังเคราะห์ทั้งแปดประเภทบวกกับคลิปจริงที่ผ่านการทำความสะอาดอย่างน้อยสามครั้งที่วัดได้ต่อบทบาทและกรณี เมตริกที่ประกาศทั้งสิบ ข้อมูลการสื่อสาร/การตั้งค่า/ข้อเท็จจริงที่คาดหวังที่หยุดนิ่ง ID การสังเกตที่ไม่ซ้ำกันและลำดับ A/B ที่ได้รับการตรวจสอบ การรับรองการดำเนินการจะผูกพันกับการย่อยของคอร์ปัส SHA ที่แน่นอนและการแก้ไขโมเดล การวัดที่ขาดหายไปหรือไม่ถูกต้องจะยังคงอยู่ที่ `HOLD` รวมถึง CPU ที่เกิน 30 วินาที RSS สูงสุดที่เกิน 512 MiB หรือการวิเคราะห์ล่วงหน้าที่เกิน 30 วินาที นี่คือขีดจำกัดการเข้ารับหลักฐาน ไม่ใช่การรับประกันการบังคับใช้ RSS ใหม่ในระยะเวลาการทำงาน

FU-07 ต้องการการเก็บรักษาคุณภาพอย่างน้อย 98% และความล่าช้า p95 ไม่เกิน 1.2 เท่าของค่ามาตรฐาน พร้อมกับการปรับปรุงค่าเฉลี่ยการเรียกคืนที่สมดุลในกรณีที่แน่นอน 0.05 ที่การเรียกคำบรรยายเฉลี่ยเท่ากัน หรือมีการเรียกคำบรรยายหลังการลบซ้ำเฉลี่ยน้อยกว่า 10% FU-09 ต้องการคุณภาพอย่างน้อย 0.85 การเก็บรักษา 95% การลดความล่าช้า p95 20% และการลดโทเค็น 10% การสูญเสียข้อเท็จจริงที่สำคัญ การปฏิบัติตามการฉีด หรือการใช้งานที่ขาดหายไปจะป้องกันการเลื่อนระดับ การดำเนินการหนึ่งไม่สามารถเลื่อนระดับอะไรได้: `--previous-report` ยืนยันการดำเนินการที่แตกต่างกันสองรายการที่ไม่ทับซ้อนกันซึ่งมีสิทธิ์ต่อเนื่องกันของนโยบาย/รุ่นโมเดล/ผู้สมัคร/คอร์ปัสเดียวกัน การทดลองสุ่มไม่สามารถยืนยันการทดลองแผ่นติดต่อได้

ผู้รวบรวมควรให้คะแนนการตอบสนองในหน่วยความจำและบันทึก `responseDigest` พร้อมกับเมตริกและการผูกสังเกต ไม่เคยบันทึกข้อความการตอบสนอง ผู้บริโภคยังอ่านการสังเกตดิบแบบเก่า แต่ไม่เคยคัดลอกข้อความนั้นไปยังรายงานของตน โดยต้องมีเพียงหนึ่งใน `responseDigest` หรือ `rawResponseText` ที่ได้รับการยอมรับสำหรับแต่ละการสังเกต รายการที่มีสิทธิ์ต้องการการอ้างอิงหลักฐาน นโยบาย รุ่นโมเดล SHA ของผู้สมัครที่แน่นอน digest ของแผนผัง และรหัสการทำงานที่แตกต่างกันสองรายการ; บริบทที่ขัดแย้งจะถูกปฏิเสธ เมตาดาต้าเหล่านี้เป็นสัญญาการตรวจสอบ ไม่ใช่หลักฐานว่ามีไฟล์ที่อ้างอิงมีการวัดที่แท้จริง ตรวจสอบใบเสร็จจริงก่อนที่จะเพิ่มรายการใด ๆ จุดสิ้นสุดสถิติการจัดการและแดชบอร์ดวิดีโอเปิดเผยความพร้อมใช้งานที่อนุรักษ์นิยม ชื่อเล่นโมเดลที่กำหนดไว้เพียงอย่างเดียวไม่สามารถกำหนดรุ่นหรือ SHA ของผู้สมัครที่กำลังทำงานได้ ดังนั้นแดชบอร์ดปัจจุบันจึงรายงาน `HOLD` แทนที่จะใช้สิทธิ์จากบริบทการดำเนินการอื่น การเลือกทดลองที่ชัดเจนยังคงแยกจากการเลื่อนระดับ; ไม่มีค่าเริ่มต้นใดที่เปลี่ยนแปลงโดยอัตโนมัติ

ผู้โทรสามารถแนบอาร์เรย์ `transcript.cues` ที่เป็นทางเลือกไปยังส่วนวิดีโอที่รองรับเมื่อพวกเขามีข้อความที่จัดเรียงแล้ว ทุกการชี้ต้องมี `text` ช่วงเวลา `start`/`end` ที่จำกัดภายในระยะเวลาที่ตรวจสอบ และ `source` ที่อยู่ในรายการที่อนุญาต (`client`, `embedded`, หรือ `audio-bridge`); `confidence` จะตั้งค่าเป็น `1` โดยค่าเริ่มต้นและต้องอยู่ระหว่าง `0` และ `1` การชี้ที่ซ้ำกันจะถูกยุบรวม OmniRoute จะไม่เริ่มการถอดเสียงจากเมตาดาต้านี้: การชี้ที่ได้รับการตรวจสอบจะถูกคัดลอกไปยังผลลัพธ์ที่อธิบายพร้อมกับแหล่งที่มา ความมั่นใจ และช่วงเวลา และจะถูกแสดงเป็นการสังเกตที่ไม่น่าเชื่อถือควบคู่ไปกับคำบรรยายของเฟรม ข้อความที่ไม่ถูกต้อง นอกช่วง หรือไม่มีแหล่งที่มาจะถูกปฏิเสธแทนที่จะถูกผสมเข้าไปในสตรีมคำบรรยาย ช่องทางถอดเสียงของคำขอทั้งสองจะทำให้แหล่งที่มาที่จัดเตรียมไว้เป็น `client` รวมถึงการระบุ `embedded` หรือ `audio-bridge` ที่อ้างสิทธิ์ด้วยตนเองเท่านั้น อะแดปเตอร์ที่เป็นเจ้าของเซิร์ฟเวอร์เท่านั้นที่สามารถกำหนดป้ายชื่อที่เชื่อถือได้เหล่านั้นผ่านอาร์กิวเมนต์ `trustedSource` ที่เป็นโค้ดเท่านั้น; ฟิลด์ JSON ของคำขอไม่สามารถเข้าถึงอาร์กิวเมนต์นั้นได้ ข้อความถอดเสียงยังคงเป็นเนื้อหาที่ได้มาจากสื่อที่ไม่น่าเชื่อถือ ไม่ว่าจะมีแหล่งที่มาหรือไม่ และต้องไม่กำหนดการอนุญาต

ผู้โทรขั้นสูงสามารถจัดเตรียมแทร็ก `audioTranscript` สำหรับวิดีโอเดียวกัน; จะถูกจัดการเป็นข้อความที่จัดเตรียมโดยลูกค้า ไม่ใช่หลักฐานการถอดเสียงของเซิร์ฟเวอร์ รอยต่อการรวมจะดำเนินการสังเกตภาพและเสียงภายใต้เส้นตายและสัญญาณยกเลิก สั่งให้พวกเขาในไทม์ไลน์ทั่วไป ยุบรวมการซ้ำกันที่แน่นอน และรายงานผลลัพธ์บางส่วนเมื่อด้านใดด้านหนึ่งประสบความสำเร็จเท่านั้น `audioTranscript` ที่ไม่ถูกต้องจะลดลงเป็นผลลัพธ์บางส่วน — คำอธิบายภาพจะถูกเก็บไว้และสาขาเสียงจะบันทึกโค้ดความล้มเหลวที่ทำความสะอาด — แทนที่จะทำให้วิดีโอทั้งหมดล้มเหลว ความพร้อมใช้งานต่อสาขา ธงบางส่วน และรหัสความล้มเหลวที่ทำความสะอาดจะถูกเก็บรักษาไว้ในผลลัพธ์ที่อธิบาย ในเมตาดาต้า guardrail (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`) ในเมตาดาต้าผลลัพธ์ และในเคาน์เตอร์การรวมสะพาน เส้นทาง Video Bridge เริ่มต้นจะไม่เรียกใช้การพูดเป็นข้อความหรือดาวน์โหลดสำเนาสื่อที่สอง; หากไม่มีแทร็กที่ชัดเจน จะยังคงเป็นวิดีโอเท่านั้น

**การเก็บรักษาถอดเสียง (#12150 P1).** สิ่งนี้จะถูกนำไปใช้โดยอัตโนมัติเมื่อใดก็ตามที่ Video Bridge (ซึ่งเป็นการเลือกเข้าร่วม) สร้างการชี้ถอดเสียง — ไม่มีธงการเก็บรักษาแยกต่างหาก เมื่อคำขอสร้างการชี้ถอดเสียงใด ๆ (การประกาศโดยผู้โทร `transcript` หรือ `audioTranscript` ที่รวมกัน) guardrail จะทำเครื่องหมายว่า `videoBridgeObserved` และสร้างเงาของคำอธิบายวิดีโอที่ถูกแก้ไข — การสร้างที่เหมือนกันซึ่งเนื้อหาฟรีของการชี้แต่ละรายการจะถูกแทนที่ด้วย `[redacted-video-transcript]` ซึ่งสร้างขึ้นโดยการแทนที่ฟิลด์การชี้ที่มีโครงสร้างก่อนที่สตริงจะถูกประกอบ (ไม่เคยโดยการวิเคราะห์ข้อความที่แบนราบ ดังนั้นเนื้อหาการชี้ — ไม่ว่าจะเป็นการต่อต้านหรือปกติ รวมถึงเนื้อหาที่มี `]` เช่น `[inaudible]`/`[music]` — ไม่สามารถอยู่รอดได้) ร่างคำขอในบันทึกการโทรที่เก็บรักษาไว้จะสลับแต่ละส่วนของข้อความที่ได้จากวิดีโอเป็นเงาที่ถูกแก้ไข โดยตรงตามความเท่าเทียมกันของเนื้อหา; แท็ก `fullText` จะถูกอ่านใหม่จากข้อมูล guardrail ก่อนการโทรที่เสร็จสิ้น ดังนั้นการจับคู่ยังคงสำเร็จหลังจาก guardrails ของสายโซ่ในภายหลัง (PII และตัวปิดบังข้อมูลประจำตัว ลำดับความสำคัญ 10/95) เขียนข้อความคำอธิบายใหม่ในที่และหลังจากการกระตุ้นระบบ/การส่งต่อ/การฉีดหน่วยความจำเปลี่ยนรูปอาร์เรย์ข้อความ ร่างที่ส่งไปยังโมเดลจะไม่เปลี่ยนแปลง คำขอที่สังเกตยังไม่เติมหน่วยความจำถาวร (การสกัดที่ได้จากคำขอและการตอบสนองจะถูกข้าม) ดังนั้นการตอบสนองของโมเดลเองจึงไม่สามารถสะท้อนข้อความถอดเสียงในหน่วยความจำได้

**ฟิลด์วิดีโอดิบ (#12430).** เมื่อสะพานถูกเปิดใช้งานและการสนับสนุนวิดีโอพื้นฐานไม่เป็นที่รู้จักหรือไม่มีอยู่ ฟิลด์ `transcript`/`audioTranscript` ที่กำหนดจะเปิดใช้งาน `videoBridgeObserved` แม้หลังจากความล้มเหลวในการอธิบายหรือขีดจำกัด `maxVideos` `null` และสตริงว่างจะนับ; ฟิลด์ที่ขาดหายไปและข้อมูลเมตาดาต้าที่ไม่ใช่วิดีโอจะไม่นับ การสำเนาที่เก็บรักษาไว้จะลบฟิลด์เหล่านี้หรือข้ามคำขอ และแคช/หน่วยความจำจะถูกข้าม

ในเส้นทางสำรองเหล่านั้น คิวผู้โทรที่ถูกต้องจะกลายเป็นส่วนที่รองรับ `text`/`input_text` แทนที่จะเป็นฟิลด์ผู้ให้บริการที่ไม่เป็นมาตรฐาน ทั้งสองแทร็กที่จัดเตรียมโดยคำขอจะยังคงเป็นการสังเกต `client` ที่ไม่เชื่อถือได้ โดยมีการเตือนอย่างชัดเจนว่าวิดีโอไม่ได้ถูกอธิบายและเวลาไม่ได้รับการตรวจสอบกับสื่อ งบประมาณที่มีอยู่ 256 คิว/64-KiB รวมและต่อคิวจะใช้ร่วมกันในสองแทร็ก; เวลาต้องอยู่ในขีดจำกัด 600 วินาทีของนายหน้าและหน้าต่างโฟกัสที่จัดเตรียมไว้ใดๆ แทร็กที่ไม่ถูกต้องจะถูกทิ้ง ไม่ถูกส่งต่อเป็นข้อความตามอำเภอใจ; พี่น้องที่ถูกต้องอาจยังคงถูกใช้ได้ เว้นแต่จะเกินงบประมาณรวม ฟิลด์ที่ว่างเปล่าหรือเป็นศูนย์จะไม่เพิ่มข้อความใดๆ ไม่มีการดึงสื่อหรือการถอดความที่เพิ่มโดยการสำรองนี้ ฟิลด์การขยายการถอดความจะถูกลบออกจากตัวพาหะวิดีโอสำรองและวัตถุ `video_url`/`source` ของมัน รายการอนุญาตของ OpenAI ยังคงเข้มงวด; ตัวพาหะวิดีโอที่ไม่รู้จักยังคงมีอยู่และเป้าหมายที่รู้จักเฉพาะข้อความจะมีเครื่องหมายที่ปลอดภัย การปกป้องการลบที่มีโครงสร้างจะปกป้องข้อความการถอดความที่แนบมา ในขณะที่คำขอที่เป็นเจ้าของโดยผู้โทรเดิมยังคงไม่เปลี่ยนแปลง เป้าหมายที่รองรับโดยเนทีฟและสะพานที่ถูกปิดใช้งานจะรักษาพฤติกรรมการข้ามที่มีอยู่

สำเนาที่เก็บรักษาเพิ่มเติมใช้สัญญาณคำขอที่สังเกตเห็นเดียวกัน สแนปช็อตคำขอของลูกค้าแบบดิบก่อนการป้องกัน, คำขอที่รอดำเนินการในหน่วยความจำ และบันทึกคำขอที่ถูกปฏิเสธในระยะต้นจะเปลี่ยนฟิลด์การถอดความในส่วนวิดีโอ; สตริงพรอมต์ที่สังเคราะห์โดยขั้นตอนของท่อและการส่งต่อบริบทจะถูกลบออกที่ซิงค์ร่างคำขอที่เก็บรักษาไว้ เครื่องหมาย `video_content_removed` ที่เก็บรักษาไว้ทำให้การต่อเนื่องของ `previous_response_id` ล้มเหลวโดยปิดแทนที่จะสร้างข้อความที่ถูกทิ้ง intentionally หากคำขอที่สังเกตเห็นสูญเสียเงาของการลบต่อส่วนก่อนที่จะบันทึก หรือแม้แต่เงาวิดีโอหนึ่งในหลายๆ เงาล้มเหลวในการจับคู่หลังจากการเปลี่ยนแปลงคำขอในภายหลัง ร่างคำขอที่เก็บรักษาไว้จะถูกละเว้นโดยสิ้นเชิงแทนที่จะรักษาการถอดความที่ถูกลบบางส่วน

สำหรับคำขอที่สังเกตเห็น การตอบสนองของโมเดลอาจอ้างอิงส่วนใดๆ ของการถอดความโดยไม่มีขอบเขตคิวที่มีโครงสร้าง ดังนั้น `responseBody` ของบันทึกการโทรที่เก็บรักษาไว้จึงถูกแทนที่ด้วยเครื่องหมายการละเว้น; ผลิตภัณฑ์ท่อที่ละเอียด (ซึ่งอาจรวมถึงร่างของลูกค้า/ต้นทางและชิ้นส่วนสตรีม) จะไม่ถูกเก็บรักษาไว้ แคชเซมานติก, idempotency, และ reasoning-replay จะข้ามการอ่านและการเขียนสำหรับคำขอนั้น คำขอของผู้ให้บริการและการตอบสนองที่มองเห็นได้จากลูกค้ายังคงไม่เปลี่ยนแปลง ไบต์ keepalive ในระยะต้นจะถูกระบายออกจากบัฟเฟอร์ชั่วคราวเมื่อผลิตภัณฑ์ที่ละเอียดถูกละเว้น คำเตือน EventStream ที่ผิดรูปแบบของ Kiro รายงานเฉพาะจำนวนไบต์ของเพย์โหลด ไม่เคยเป็นเนื้อหาหรือข้อผิดพลาดดิบของ JSON parser
นี่ไม่ได้อ้างว่าได้มีการตรวจสอบการวินิจฉัยของผู้ให้บริการ/ปลั๊กอินที่ไม่เกี่ยวข้องทุกตัว; การตรวจสอบการเก็บรักษาที่กว้างขึ้นจะถูกติดตามใน #11658

วงจรชีวิต `/api/modality-bridge/video/drilldown` ภายในเป็นฐานข้อมูลแคชที่แยกต่างหาก ซึ่งใช้การวนซ้ำ/การตรวจสอบโทเค็น ทุกการดำเนินการยังต้องการ ID หลักที่ทึบแสงตามมาตรฐาน ก่อนที่ผู้โทรในผลิตภัณฑ์จะถูกเปิดใช้งาน จะต้องสร้าง ID นั้นจากผู้เช่าที่ได้รับการตรวจสอบและต้องไม่ส่งต่อค่าที่เลือกโดยลูกค้า คีย์แคชจะผูก ID หลักนั้นกับเซสชันมาตรฐานและ ID อ้างอิงวิดีโอ เก็บเฉพาะคีย์ที่ได้จาก SHA-256 ของพวกเขา และกำหนดขอบเขตการอ่านและการลบให้กับหลักเดียวกัน แคชเก็บเฟรม JPEG ที่ได้มาไม่เกิน 16 เฟรมต่อรายการ หมดอายุหลังจากสิบนาที และสนับสนุนการอ่านที่มีขอบเขต `start`/`end` หรือการลบเซสชันที่ชัดเจน

แต่ละหลักถูกจำกัดไว้ที่ 16 รายการและ 64 MiB ของข้อมูล JPEG มาตรฐาน ขีดจำกัดเหล่านั้นเป็นอิสระจากขีดจำกัดทั่วโลก 64 รายการ/256 MiB: ความกดดันจากโควต้าหลักจะไล่ที่ใช้ล่าสุดของหลักนั้นออกก่อนที่จะพิจารณาการไล่ระดับ LRU ทั่วโลก รายการที่หมดอายุจะถูกลบออกจากการบัญชีของทั้งหลักและทั่วโลกเมื่อมีกิจกรรมแคช ในขณะที่การยกเลิกและการตรวจสอบความถูกต้องล้มเหลวจะไม่ทำการเปลี่ยนแปลงบางส่วน

แคชจะปฏิเสธ Base64 ที่ไม่เป็นมาตรฐาน, การเติมที่เกิน, สื่อที่ไม่ใช่ JPEG, JPEG ที่ผิดรูปแบบหรือถูกตัดทอน, และ JPEG ที่สร้างคำเตือนระหว่างการถอดรหัสภาพเต็มที่มีขอบเขต `sharp` มันจะทำการเข้ารหัสใหม่แต่ละภาพที่ยอมรับเป็น JPEG มาตรฐาน ดึงความกว้างและความสูงจากไบต์ที่ถอดรหัสแทนที่จะเชื่อฟิลด์ของผู้โทร และทิ้งไบต์ polyglot ที่ตามมาทั้งหมดแทนที่จะเก็บรักษาไว้ เฉพาะบัฟเฟอร์ที่บีบอัดมาตรฐานที่มีขอบเขตเท่านั้นที่จะถูกคิดค่าธรรมเนียมต่อโควต้า ทั้งหมด ขีดจำกัดของ JSON wire รวมถึงค่าใช้จ่าย Base64 สำหรับขีดจำกัดการป้อนข้อมูลที่ถอดรหัส 32 MiB ทุกการสร้างที่เก็บรักษาจะบันทึกฟอร์แมต/ความละเอียด JPEG ที่ได้รับการตรวจสอบ, นโยบายการสุ่มตัวอย่าง, เวอร์ชันการสร้าง, เวลาในการสร้าง, แฮชเนื้อหาที่คำนวณโดยเซิร์ฟเวอร์, และแฮชอ้างอิงของผู้ปกครองที่เชื่อถือได้รวมถึงแฮชเนื้อหาของผู้โทรที่เชื่อถือได้ การยกเลิกจะถูกตรวจสอบระหว่างขั้นตอนการถอดรหัส/แฮชแบบอะซิงโครนัสก่อนที่จะมีการคอมมิตแคชแบบอะตอมิก

ผู้ผลิตในผลิตภัณฑ์จะนำเฟรมของนายหน้าที่ได้มาแล้วมาใช้ใหม่เฉพาะหลังจากการวิเคราะห์ภาพที่ประสบความสำเร็จ โดยไม่ต้องดาวน์โหลด/ดึงวิดีโอครั้งที่สอง มันต้องการ `modalityBridgeVideoDrilldownEnabled=true` ของผู้ดำเนินการ, `drilldown: true` ต่อส่วนที่เข้มงวด, และ ID บันทึก API-key ที่ได้รับการตรวจสอบ ค่าเซสชัน/หลักที่ประกาศโดยลูกค้าไม่เคยสร้างความเป็นเจ้าของ โดยไม่มีเงื่อนไขทั้งสามนี้จะไม่ทำการแฮช, เปลี่ยนขนาดหรือเก็บเฟรมเพิ่มเติม การล้มเหลวในการเก็บรักษาจะรักษาการตอบสนองภาพที่ใช้งานได้ คำขอที่ได้รับความยินยอมจะข้ามแคชผลลัพธ์วิดีโอทั้งหมด ดังนั้นผลลัพธ์ที่เก็บรักษาไว้จะไม่เล่นซ้ำการจัดการ

การตอบสนอง JSON และ SSE ที่ประสบความสำเร็จจะเปิดเผยที่จับที่ไม่โปร่งใสสูงสุดสี่ตัวในส่วนหัว `x-omniroute-video-drilldown` ที่มีขอบเขต ต้นทางเบราว์เซอร์ที่ได้รับอนุญาตสามารถอ่านส่วนหัวนั้นได้โดยไม่ต้องขยายนโยบาย CORS origin ที่มีอยู่ ที่จับใหม่ใช้ `v1.<32-byte random base64url token>` และทะเบียนจะเก็บเฉพาะ SHA-256 hashes ของพวกเขา ตัวอ่าน/พาร์เซอร์ส่วนหัวยังยอมรับโทเค็น 64-hex แบบเก่า ผู้บริโภคสาธารณะที่ได้รับการตรวจสอบแล้วคือ `GET /api/v1/video-bridge/drilldown?handle=...` ซึ่งถูกควบคุมโดยอิสระโดย `modalityBridgeVideoDrilldownRemoteEnabled=true` การตั้งค่าเป็นเท็จที่เก็บถาวรอย่างชัดเจนจะเพิกถอนการเข้าถึงแม้ว่าจะเปิดใช้งานการสำรองข้อมูล `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` แบบเก่า การเก็บรักษาผลิตภัณฑ์มีการสำรองข้อมูลแบบเก่า `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED` ทั้งสองการสำรองข้อมูลจะปิดโดยค่าเริ่มต้น

ผู้บริโภคจะได้มาซึ่งความเป็นเจ้าของจากกุญแจที่ได้รับการตรวจสอบแล้ว ใช้นโยบายกุญแจ และส่งคืน 404 เดียวกันสำหรับที่จับที่ไม่รู้จัก หมดอายุ และของกุญแจอื่น มันยอมรับ `variant=preview|standard|detail` (ขนาด JPEG สูงสุด 320/640/1280 ไม่เคยขยายขนาด) `limit=1..8` (หรือชื่อเล่น `frames` แบบเก่า ไม่เคยทั้งสอง) `page` ที่เริ่มต้นจากศูนย์ และวินาทีที่โฟกัส `start`/`end` ที่เลือกได้ คีย์การค้นหาที่ซ้ำกันและหน้าต่างโฟกัสที่กลับด้านจะถูกปฏิเสธ ตัวแปรที่ส่งคืนแต่ละตัวมีแฮชของเนื้อหาจริงและข้อมูลเมตาของความละเอียดจริงที่เชื่อมโยงกับแหล่งที่เก็บไว้ ตัวแปรจะถูกสร้างขึ้นเมื่ออ่านแทนที่จะถูกเก็บเป็นสำเนาที่เก็บไว้เพิ่มเติม การตอบสนอง JSON รวมถึง Base64/envelope จะถูกจำกัดที่ 32 MiB; หน้าขนาดใหญ่จะส่งคืน 413 และไคลเอนต์ต้องขอเฟรมที่น้อยลง การอ่านจะตรวจสอบการยกเลิกรอบๆ การปรับขนาดแต่ละครั้งและตรวจสอบความถูกต้องของที่จับก่อนที่จะส่งคืน `DELETE` โดยเจ้าของเป็นอิดempotent; การลบหรือการหมดอายุ TTL จะปล่อยแหล่งที่เก็บและการบัญชีการใช้งาน

ร้านค้าที่แชร์เป็นระดับกระบวนการ: ที่จับจะหมดอายุเมื่อเริ่มต้นใหม่และไม่สามารถโอนย้ายระหว่างกระบวนการ OmniRoute ที่เป็นอิสระ สถิติการจัดการจะแสดงนโยบายการเก็บรักษา/ระยะไกลที่มีประสิทธิภาพและจำนวนรายการ/ไบต์ที่เก็บไว้รวมเท่านั้น ไม่เคยมีสื่อ อ้างอิง ID หลัก หรือที่จับ แผงการตั้งค่าวิดีโอจะแสดงค่าดังกล่าวและสามารถเก็บสวิตช์การยินยอมทั้งสองได้ เอกสารการใช้งานนี้ไม่ใช่หลักฐานการปรับใช้หรือการส่งเสริมที่มีชีวิต; การยอมรับโมเดลจริงจะถูกติดตามแยกต่างหาก

เฟรมจะถูกบรรยายตามลำดับด้วยโมเดลวิดีโอที่กำหนดไว้ การแทนที่วิดีโอที่ว่างเปล่าจะสืบทอดการตั้งค่ามุมมอง; หากทั้งสองว่างเปล่า ตัวเลือกอัตโนมัติของมุมมองจะเลือกโมเดลที่มีความสามารถด้านวิสัยทัศน์ที่มีประสิทธิภาพ บรรยายที่ประสบความสำเร็จจะเปลี่ยนส่วนต้นฉบับด้วยคำนำ `[Video description:` ที่เสถียรซึ่งยังทำเครื่องหมายข้อความว่าเป็นการสังเกตที่ได้มาจากสื่อที่ไม่น่าเชื่อถือและบอกโมเดลที่อยู่ด้านล่างว่าไม่ให้ทำตามคำแนะนำที่พบในสื่อ คีย์แคชการบรรยายเฟรมรวมถึงไบต์ JPEG คำกระตุ้น เวลา และโมเดลที่มีประสิทธิภาพ; จะมีการแคชเฉพาะการบรรยายที่ประสบความสำเร็จเท่านั้น รายการแคชจะเก็บโมเดลผู้ผลิตที่ประสบความสำเร็จจริง รวมถึงโมเดลสำรอง; สะพานจะรายงานว่า `mixed` เมื่อเฟรมที่แตกต่างกันถูกผลิตโดยโมเดลที่แตกต่างกัน การเข้าชมแคชจะใช้ตัวตนของผู้ผลิตนั้นแทนที่จะเปลี่ยนชื่อเป็นแผนการจัดเส้นทางที่ร้องขอ แคชผลลัพธ์ทั้งวิดีโอจะถูกกำหนดคีย์จากทุกการป้อนข้อมูลที่เปลี่ยนผลลัพธ์ — คำกระตุ้น โมเดลที่มีประสิทธิภาพ นโยบายการสุ่มตัวอย่าง จำนวนเฟรม โหมดการวิเคราะห์เชิงความหมาย SHA-256 ลายนิ้วมือของคำแนะนำที่ปรับให้เป็นมาตรฐาน หน้าต่างโฟกัส `transcript` `audioTranscript` และธง contact-sheet — ดังนั้นการเปลี่ยนแปลงมิติใด ๆ เหล่านั้นจะเป็นการพลาดแคช ไม่เคยเป็นการใช้ซ้ำที่ล้าสมัย เวอร์ชันนโยบายการลดภาพที่มองเห็นได้ ขีดจำกัด และจำนวนเฟรมที่มีขอบเขตจะถูกระบุอย่างชัดเจนในคีย์แคชผลลัพธ์และข้อมูลเมตา; การเปลี่ยนแปลงนโยบายจึงไม่สามารถใช้คำอธิบายวิดีโอทั้งหมดที่ล้าสมัยได้ ข้อมูลเมตาแคชผลลัพธ์ v4 จะเก็บโหมดและลายนิ้วมือ ไม่เคยเป็นงานผู้ใช้ดิบ ข้อมูลเมตา guardrail รายงานทั้งโหมดการวิเคราะห์ที่ร้องขอและมีประสิทธิภาพ; โหมด `focused` ที่ร้องขอโดยไม่มีข้อความผู้ใช้ที่ใช้งานได้จะถูกรายงานว่าเป็น `full` ที่มีประสิทธิภาพ

การควบคุมจะดึงทุกส่วนวิดีโอที่รองรับ แต่จะไม่อธิบายมากกว่า `modalityBridgeVideoMaxVideos` สำหรับเป้าหมายที่พิสูจน์แล้วว่ามี `supportsVideo === false` วิดีโอที่ล้มเหลวและเกินขีดจำกัดจะกลายเป็นเครื่องหมายข้อความที่ปลอดภัยอย่างชัดเจน ดังนั้นจึงไม่มีวิดีโอดิบที่รอดชีวิต เมื่อความสามารถไม่เป็นที่รู้จัก ส่วนเหล่านั้นจะเก็บผู้ให้บริการวิดีโอของพวกเขาไว้; การถอดความสำรองใด ๆ จะตามการแปลงข้อความที่มีขอบเขตข้างต้น เป้าหมายที่มี `supportsVideo === true` จะข้ามสะพาน สัญญาณการยกเลิกคำขอของไคลเอนต์จะส่งผ่านการดาวน์โหลด คิวตัวกลาง กระบวนการย่อย และการเรียกบรรยาย; การยกเลิกจะหยุดระหว่างวิดีโอและไม่เคยล้มเหลวในการเปิดสู่สื่อดิบ

การตั้งค่าเวลาทำงานจะถูกสนับสนุนโดยฐานข้อมูลและตรวจสอบโดย Zod:

broker deadline; new settings writes above that limit are rejected.
`GET /api/modality-bridge/video/runtime` requires trusted stamped loopback
locality before authentication or runtime probing, then requires management
auth. It returns only `available`, sanitized FFmpeg/ffprobe versions, and a fixed
reason when the runtime is unavailable. The internal extraction endpoint is not
a public upload API: queue saturation returns `503` plus `Retry-After`, a caller
disconnect returns `499`, and the fixed broker deadline returns `504`. Converted responses add
`video->text;model=<visionModel>;parts=<videos>` to the central
`x-omniroute-modality-bridge` header without removing Vision or Audio segments.

### PII Masker (`piiMasker.ts`)

ทำงานใน **ทั้งสอง** ระยะ

- **`preCall`** ทำการโคลน payload, เดินผ่าน `system`, `messages`, `input`, และ
  `prompt` (รวมถึงรายการสตริงธรรมดา) และใช้ `processPII()` (จาก
  `@/shared/utils/inputSanitizer`) กับฟิลด์สตริง `content`/`text` เมื่อ
  `PII_REDACTION_ENABLED=true`, PII ที่ตรวจพบจะถูกลบออกใน payload ที่ส่งออก นี่เป็นอิสระจาก `INPUT_SANITIZER_MODE` (ซึ่งควบคุม
  นโยบายการฉีด prompt เท่านั้น) เมื่อการลบออกปิดอยู่ การบันทึกการโทรจะนับจำนวนการตรวจจับโดยไม่เขียนเนื้อหาใหม่
- **`postCall`** ทำการโคลนลึกของการตอบกลับ, รัน `sanitizePIIResponse()` บวก
  ตัวป้องกันรูปแบบ Responses-API (`maskResponsesOutput` — ครอบคลุม
  `output_text` และ `output[].content[].text`) หากมีการลบออกเกิดขึ้น การตอบกลับที่แก้ไขจะแทนที่ต้นฉบับ

การป้องกันจะไม่บล็อก; มันเพียงแค่ทำการบันทึก (`meta.detections`,
`meta.redacted`) หรือเขียนใหม่

### Prompt Injection (`promptInjection.ts`)

ตรวจจับโครงสร้างที่เป็นอันตรายในเนื้อหาที่ผู้ใช้จัดหาและบังคับใช้นโยบายที่กำหนดไว้ การทำงานถูกขับเคลื่อนโดยตัวแปรสภาพแวดล้อมและตัวเลือกของผู้สร้าง:

| การตั้งค่า | ตัวแปรสภาพแวดล้อม                                                                                        | ค่าเริ่มต้น | ผลกระทบ                                                                                                                                                                            |
| ---------- | -------------------------------------------------------------------------------------------------------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| เปิดใช้งาน | `INPUT_SANITIZER_ENABLED`                                                                                | `true`      | เมื่อ `false`, การป้องกันจะทำงานแบบสั้น.                                                                                                                                           |
| โหมด       | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                          | `warn`      | นโยบายการฉีด: `block`, `warn`, หรือ `log`. (`redact` ยอมรับสำหรับความเข้ากันได้ย้อนหลังแต่จะ **ไม่** ลบข้อความการฉีด; การขอการเขียนใหม่ PII ถูกควบคุมโดย `PII_REDACTION_ENABLED`.) |
| เกณฑ์บล็อก | ตัวเลือก `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (นามแฝง `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`      | ความรุนแรงขั้นต่ำที่ต้องการเพื่อบล็อก ระดับกลางจะสังเกตเฉพาะที่ค่าเริ่มต้น.                                                                                                        |

**ลำดับความสำคัญของโหมด** (`getMode`): ตัวเลือก `options.mode` ของผู้เรียก →
`INJECTION_GUARD_MODE` **การตั้งค่า DB feature-flag override** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. การ override บนแดชบอร์ดจึงชนะตัวแปรสภาพแวดล้อม ดังนั้น UI ของ Feature
Flags ควบคุมการทำงานของการป้องกันแบบสด (ไม่ต้องรีสตาร์ท). การอ่าน DB เป็นแบบ fail-safe:
หากเกิดข้อผิดพลาด การป้องกันจะกลับไปใช้พฤติกรรมตามตัวแปรสภาพแวดล้อม และเมื่อไม่มี
การตั้งค่า override พฤติกรรมจะเหมือนกับการแก้ไขเฉพาะตัวแปรสภาพแวดล้อม.

แหล่งที่มาของการตรวจจับ:

1. `sanitizeRequest()` จาก `@/shared/utils/inputSanitizer` (ชุดตัวตรวจจับที่ใช้ร่วมกัน
   ใช้ในที่อื่นในสายการผลิต).
2. รูปแบบ `DEFAULT_GUARD_PATTERNS` ที่สร้างขึ้น (ปัจจุบัน `system_override_inline` และ
   `markdown_system_block`, ทั้งสองมีความรุนแรง `high`).
3. `customPatterns` ที่เลือกได้ซึ่งส่งผ่านตัวเลือกของผู้สร้าง (สตริง, regex,
   หรือ `{ name, pattern, severity }` records).

เมื่อ `mode === "block"` **และ** การตรวจจับอย่างน้อยหนึ่งรายการตรงตามเกณฑ์ความรุนแรง
`preCall` จะส่งคืน `{ block: true, message: "Request rejected:
suspicious content detected" }`. ในโหมด `warn`/`log` การป้องกันจะบันทึกแต่
อนุญาตให้การโทรดำเนินต่อไป. ตัวช่วยที่ใช้ร่วมกัน `evaluatePromptInjection()` ยังถูกส่งออก
สำหรับผู้เรียกที่ต้องการประเมิน prompt โดยไม่ต้องผ่านการลงทะเบียน.

**ขอบเขตการสแกน (v3.8.20):** ตัวตรวจจับจะตรวจสอบเฉพาะ **16 KB แรก** ของ
ข้อความ prompt ที่รวมกัน — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ไบต์) ใน
`src/shared/utils/inputSanitizer.ts`. ทั้ง `detectInjection()` และ
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` ก่อนที่จะรัน
ลูปแบบ. คำสั่งการฉีดจะอยู่ใกล้ด้านบนของข้อมูลนำเข้า ดังนั้นนี่จึงจำกัด CPU/GC regex ใน payload ขนาดหลายร้อย KB โดยไม่ลดทอนการตรวจจับ (ดู #3932, #4041).

### Credential Masker (`credentialMasker.ts`)

ทำงานใน **ทั้งสอง** ระยะ, เป็นลำดับสุดท้ายในสายการทำงานเริ่มต้น (ลำดับความสำคัญ `95`). ลบ
รูปแบบ API-key / secret-token ที่รู้จักจาก payload ที่ส่งออก (เนื้อหาข้อความ,
อาร์กิวเมนต์การเรียกเครื่องมือ, ผลลัพธ์เครื่องมือ) **และ** การตอบกลับของผู้ให้บริการ เพื่อไม่ให้
ข้อมูลประจำตัวที่วางลงใน prompt (หรือสะท้อนกลับโดยผลลัพธ์ของเครื่องมือ) ถูกเปิดเผย
ไปยังผู้ให้บริการต้นน้ำหรือกลับไปยังลูกค้า.

- **เฉพาะการเลือกเข้าร่วมเท่านั้น** ตามแนวทางเดียวกับการลบข้อมูล PII (กฎที่เข้มงวด #20-adjacent):
  จะถูกปิดใช้งานเว้นแต่ `settings.credentialRedactionEnabled === true` **หรือ**
  `CREDENTIAL_REDACTION_ENABLED=true` เมื่อปิดอยู่ การควบคุมจะไม่มีผล —
  มันจะไม่บล็อกและไม่เขียนใหม่เลย
- `redactCredentials()` จะเดินผ่านโครงสร้างข้อมูลทั้งหมดของ payload/response (`walkValue()`,
  ปลอดภัยจากการทำให้ prototype เสียหาย, ปลอดภัยจากวงจรผ่าน `WeakSet`) และแทนที่การจับคู่ด้วย
  ตัวแทน `[REDACTED:<type>]` โดยการทำสำเนาเฉพาะสาขาที่เปลี่ยนแปลงจริงๆ
- `CREDENTIAL_PATTERNS` ครอบคลุมคีย์ของผู้ให้บริการ LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), โทเค็น VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), คีย์การชำระเงิน (Stripe, Square), คีย์คลาวด์
  (AWS access key, Twilio, SendGrid, Mailgun), คีย์ส่วนตัว / JWTs,
  สตริงการเชื่อมต่อที่มีข้อมูลรับรอง (`mongodb://user:pass@...`, ฯลฯ) และ
  รูปแบบ header-value ทั่วไป `Authorization`/`x-api-key`/`api-key`/`apikey`
  คีย์ที่มีรูปแบบ header (`authorization`, `x-api-key`, `api-key`,
  `apikey`) จะถูกลบออกในเชิงโครงสร้าง (เฉพาะค่า, คำนำหน้า scheme เช่น
  `Bearer `/`Basic ` จะถูกเก็บรักษาไว้) แทนที่จะใช้ regex ข้อความทั่วไป
- การควบคุมจะไม่บล็อก; มันจะเขียนใหม่เท่านั้น (`modifiedPayload` /
  `modifiedResponse`) และทำการบันทึก (`meta.credentialsRedacted`, `meta.count`)

การป้องกันการถดถอย: `tests/unit/credential-masker-guardrail.test.ts`

## สัญญาพื้นฐาน (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // ค่า true จะลัดวงจรของเชน
  message?: string; // แสดงเมื่อมีการบล็อก
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ส่งคืนโดย preCall เพื่อเขียนคำขอใหม่
  modifiedResponse?: TValue; // ส่งคืนโดย postCall เพื่อเขียนการตอบกลับใหม่
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

การ์ดเรลระบุว่า "ไม่มีการเปลี่ยนแปลง" ด้วยการส่งคืน `void`, `{}` หรือ
`{ block: false }` อย่างใดอย่างหนึ่ง การส่งคืน `modifiedPayload`/`modifiedResponse`
จะแทนที่ค่าที่ไหลผ่านเชนสำหรับการ์ดเรลลำดับถัดไป
`signal?: AbortSignal` ส่งต่อวงจรชีวิตของผู้เรียกไปยังการ์ดเรล การยกเลิกคำขอเป็นข้อยกเว้นแบบยอมให้ทำงานต่อโดยเจตนา: บริดจ์สื่อจะหยุดการทำงานและล้างทรัพยากร โดยไม่กู้คืนสื่อดิบไปยังปลายทางที่ทราบว่าไม่รองรับสื่อนั้น

## รีจิสทรี (`registry.ts`)

ซิงเกิลตัน `guardrailRegistry` เปิดเผยเมธอดต่อไปนี้:

- `register(guardrail)` — เพิ่มการ์ดเรล (หรือแทนที่ตามชื่อที่ผ่านการทำให้เป็นมาตรฐาน)
  และเรียงลำดับใหม่ตาม `priority` จากน้อยไปมาก
- `clear()` / `list()` — ตัวช่วยสำหรับการดูแลระบบ
- `runPreCallHooks(payload, context)` — วนซ้ำการ์ดเรลที่ทำงานอยู่ ส่งต่อ
  เพย์โหลดผ่าน `modifiedPayload` และหยุดเมื่อพบ `block: true` ครั้งแรก
- `runPostCallHooks(response, context)` — ใช้โฟลว์เดียวกันกับฝั่งการตอบกลับ
- `resetGuardrailsForTests({ registerDefaults })` — ล้างสถานะและเลือก
  ลงทะเบียนค่าเริ่มต้นใหม่เพื่อแยกการทดสอบอย่างสะอาด

รันเนอร์ทั้งสองส่งคืน `{ blocked, payload|response, results, guardrail?, message? }`
โดย `results` เป็นอาร์เรย์ของเรคคอร์ด `GuardrailExecutionResult` ซึ่งประกอบด้วย
ฟิลด์ `blocked`, `skipped`, `modified`, `error` และ `meta` ของแต่ละการ์ดเรล
ซึ่งมีประโยชน์สำหรับการติดตาม

### การปิดใช้งานการ์ดเรลสำหรับแต่ละคำขอ

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` รวบรวมรายการ
ชื่อการ์ดเรลที่ตัดรายการซ้ำแล้ว ซึ่งควรข้ามสำหรับคำขอปัจจุบัน
แหล่งที่มา (ทั้งหมดเป็นตัวเลือกและนำมารวมกันทั้งหมด):

- `apiKeyInfo.disabledGuardrails`
- `disabledGuardrails` ในเนื้อหาคำขอ (ระดับบนสุด)
- `metadata.disabledGuardrails` ในเนื้อหาคำขอ
- เฮดเดอร์ `x-omniroute-disabled-guardrails` (หรือชื่อเดิม
  `x-disabled-guardrails`)

ค่าอาจเป็นอาร์เรย์ของสตริงหรือสตริงที่คั่นด้วยจุลภาค ชื่อจะถูก
ทำให้เป็นอักษรพิมพ์เล็กในรูปแบบ kebab-case (`pii_masker` → `pii-masker`) ผลลัพธ์
จะถูกส่งผ่าน `context.disabledGuardrails` ไปยังรีจิสทรี ซึ่งจะข้าม
การ์ดเรลที่ตรงกัน (`skipped: true` ใน `results`)

## ลำดับการดำเนินการ

สำหรับแต่ละคำขอที่ไหลผ่าน `src/sse/handlers/chat.ts` และ
`open-sse/handlers/chatCore.ts`:

1. `resolveDisabledGuardrails(...)` สร้างรายการที่ต้องข้ามจาก API key, body
   และ headers
2. `guardrailRegistry.runPreCallHooks(body, ctx)` เรียกใช้ guardrails ตามลำดับ
   priority จากน้อยไปมาก:
   - Guardrails ที่ปิดใช้งานจะถูกบันทึกเป็น `skipped`
   - `preCall` ของแต่ละ guardrail อาจเขียน payload ใหม่ผ่าน `modifiedPayload`
   - รายการแรกที่มี `block: true` จะยุติลำดับการทำงานทันที และ handler จะส่งคืน
     การตอบกลับที่ระบุว่า guardrail ปฏิเสธคำขอ
3. Payload ที่อาจถูกเขียนใหม่จะถูกส่งต่อไปยัง combo routing และการส่งคำขอ
   ไปยัง upstream
4. หลังจากประกอบการตอบกลับแล้ว `guardrailRegistry.runPostCallHooks(...)`
   จะเรียกใช้ลำดับเดิมกับการตอบกลับ หากพบ `block: true` ในขั้นตอนนี้ การตอบกลับ
   จาก upstream จะถูกละทิ้ง

Guardrails ที่ throw ข้อผิดพลาดจะถูกบันทึกด้วย `error: <message>` และเขียน log ผ่าน
`logger.warn` แต่ลำดับการทำงานจะดำเนินต่อไป ซึ่งเป็นการออกแบบแบบ fail-open

## การกำหนดค่า

ตัวแปรสภาพแวดล้อมที่ guardrails ในตัวอ่าน:

| ตัวแปร                                | ใช้โดย                    | ผลกระทบ                                                                                                  |
| ------------------------------------- | ------------------------- | -------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | ตั้งค่าเป็น `false` เพื่อปิดใช้งานการตรวจจับทั้งหมด                                                      |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`        | นโยบายการตรวจจับ injection: `warn`, `block` หรือ `log` ค่าเดิม `redact` จะไม่เขียนข้อความ injection ใหม่ |
| `INJECTION_GUARD_MODE`                | `prompt-injection`        | โหมดสำหรับ injection guard และยังเป็น DB feature flag ที่ **มีผลเหนือกว่า** env vars (DB > ENV)          |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`        | ระดับความรุนแรงขั้นต่ำที่ `MODE=block` จะปฏิเสธ: `high` (ค่าเริ่มต้น), `medium` หรือ `low`               |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`        | Alias แบบเดิมสำหรับ `INPUT_SANITIZER_BLOCK_THRESHOLD`                                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`              | เมื่อเป็น `true` ข้อมูล PII ในคำขอจะถูกปกปิด (ไม่ขึ้นกับโหมด injection)                                  |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (downstream) | ควบคุมลักษณะการทำงานของ masker ฝั่งการตอบกลับ                                                            |

Guardrails ของ Modality Bridge อ่านการกำหนดค่าขณะรันไทม์จาก settings
store ที่มี DB รองรับ (`getSettings()`) ไม่ใช่จาก env vars โดย primary keys ของ Vision คือ
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` และ
`modalityBridgeCacheMaxEntries` ส่วน keys แบบเดิม
`visionBridge*` จะได้รับการยอมรับเฉพาะในฐานะกลไกสำรองสำหรับการอ่านหนึ่งรอบตามที่ระบุไว้
ในเอกสารเท่านั้น การเขียนค่าจาก dashboard จะใช้ primary keys ค่าเริ่มต้นและตัวแก้ไข
fallback อยู่ใน `src/shared/constants/modalityBridgeDefaults.ts` ขณะที่ constants
แบบเดิมยังคงอยู่ใน `src/shared/constants/visionBridgeDefaults.ts`

Audio ใช้ `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` และ `modalityBridgeAudioMaxClips` ร่วมกับ settings
`modalityBridgeCache*` ที่ใช้ร่วมกัน Audio ไม่มีกลไก fallback ไปยัง keys แบบเดิม เนื่องจาก
keys เหล่านี้ถูกนำมาใช้พร้อมกับ schema ของ Modality Bridge

Video ใช้ `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` และ
`modalityBridgeVideoTimeout` ร่วมกับ settings `modalityBridgeCache*` ที่ใช้ร่วมกัน
โดยค่าเริ่มต้นจะปิดใช้งาน เนื่องจาก FFmpeg/ffprobe เป็น operational dependencies
ที่ไม่บังคับ และการสร้างคำบรรยายให้แต่ละ frame จะเพิ่มเวลาแฝงและต้นทุนของโมเดล

## การ์ดเรลแบบกำหนดเอง

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ขั้นตอน:

1. สร้าง `src/lib/guardrails/myGuardrail.ts` โดยสืบทอดจาก `BaseGuardrail`
2. อิมพลีเมนต์ `preCall` และ/หรือ `postCall`
3. ลงทะเบียนขณะนำเข้า (เพิ่มจาก `registerDefaultGuardrails`) หรือ
   เรียก `guardrailRegistry.register(...)` ขณะรันไทม์ — รีจิสทรีจะแทนที่
   การ์ดเรลก่อนหน้าที่มีชื่อหลังการปรับรูปแบบเหมือนกัน
4. เพิ่มการทดสอบภายใต้ `tests/unit/` (ตัวอย่างที่มีอยู่:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)

## การทดสอบ

ใช้ `resetGuardrailsForTests()` ระหว่างการทดสอบแต่ละรายการเพื่อเริ่มต้นจากสถานะที่ทราบแน่ชัด
ส่ง `{ registerDefaults: false }` เพื่อเริ่มต้นด้วยรีจิสทรีว่างและ
ลงทะเบียนเฉพาะการ์ดเรลที่กำลังทดสอบ Vision Bridge รองรับการฉีดการพึ่งพา
(`deps.getSettings`, `deps.callVisionModel`); Audio Bridge มีจุดเชื่อมต่อ
ที่เทียบเท่ากันสำหรับการตั้งค่า ความสามารถ การเลือกโมเดล STT การตรวจสอบข้อมูลรับรอง
และการถอดเสียง ดังนั้นการทดสอบจึงสามารถตรวจสอบโฟลว์ทั้งสองได้โดยไม่ต้องเข้าถึง DB
หรือเครือข่าย

## ความครอบคลุมของเส้นทางและการทดสอบแบบเรดทีมสำหรับการป้องกันการแทรกคำสั่ง (Phase 8 · Block D)

การป้องกันการแทรกคำสั่ง (`createInjectionGuard` / `withInjectionGuard`) ครอบคลุมทุกเส้นทาง
ที่รับพรอมต์จากผู้ใช้ โดยจะเคารพ `INJECTION_GUARD_MODE` (ค่าเริ่มต้น `warn` = บันทึกล็อกเท่านั้น;
`block` = ส่งคืน HTTP 400 `SECURITY_001`)

| ประเภท         | เส้นทาง                                                                                                                                              | โหมดเริ่มต้น |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| ข้อความ (เดิม) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn         |
| เชิงสร้างสรรค์ | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn         |
| ข้อมูล         | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn         |

การแยกข้อความ (`extractMessageContents`) ครอบคลุม `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`

**เรดทีม (ทุกคืน, `nightly-llm-security.yml`):** promptfoo ตรวจสอบว่าแต่ละเส้นทางบล็อก
คลัง OWASP-LLM ใน `INJECTION_GUARD_MODE=block`; garak เรียกใช้โพรบ (ข้ามหากไม่มีข้อมูลลับ)
`moderations` ถูกรวมไว้เพื่อความสอดคล้อง — ผู้ดูแลระบบที่ใช้โหมดบล็อกสามารถยกเว้นเส้นทางนี้ผ่าน
`resolveDisabledGuardrails`

เวิร์กโฟลว์รายคืน (`.github/workflows/nightly-llm-security.yml`, cron + การสั่งงาน
ด้วยตนเอง) มีสองงาน:

- **`promptfoo-guard` (บล็อกเมื่อไม่ผ่าน)** — เรียกใช้ `promptfoo eval -c promptfooconfig.yaml`
  โดยใช้ `INJECTION_GUARD_MODE=block` กรณีโจมตีแต่ละกรณี (เช่น "เพิกเฉยต่อ
  คำสั่งก่อนหน้าทั้งหมด…", การเจลเบรกแบบ DAN) จะยืนยันว่าการตอบกลับมี
  `error.code === "SECURITY_001"` กล่าวคือ การ์ดได้ปฏิเสธคำขอจริง
- **`garak` (ให้คำแนะนำ)** — เรียกใช้ garak `--probes promptinject,dan,leakreplay`
  กับอินสแตนซ์ OmniRoute ภายในเครื่อง (`http://localhost:20128/v1`) โดยขึ้นอยู่กับ
  ข้อมูลลับของผู้ให้บริการ (`PROMPTFOO_PROVIDER_KEY`); จะข้ามอย่างราบรื่นหากไม่มีข้อมูลดังกล่าว และต่อท้ายด้วย
  `|| true` จึงรายงานผลโดยไม่ทำให้ CI ล้มเหลว

ความครอบคลุมของตัวช่วยการ์ด (`createInjectionGuard` / `withInjectionGuard`)
ครอบคลุมทุกเส้นทาง `/v1` ที่มีพรอมต์; ข้อความพรอมต์จะถูกดึงจาก
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` โดย
`extractMessageContents()` ใน `src/shared/utils/inputSanitizer.ts`
