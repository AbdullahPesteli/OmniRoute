> **מקור האמת:** `src/lib/guardrails/`
> **עדכון אחרון:** 2026-08-29 — v3.8.51 (מקור התמליל של Video Bridge מוצהר על ידי הקורא,
> ועדיין אינו מאומת על ידי השרת — הובהר בהתאם ל-#11661)

מנגנוני הגנה אוכפים בטיחות, מדיניות והתמרות תוכן בגבול
שבין OmniRoute לספקים במעלה הזרם. כל מנגנון הגנה יכול לבדוק (ובאופן
אופציונלי לדחות, להתמיר או להוסיף הערות אל) מטעני בקשות (`preCall`) ותגובות
במעלה הזרם (`postCall`).

המערכת פועלת בגישת **fail-open**: אם מנגנון הגנה זורק חריגה במהלך הביצוע, הרישום
מתעד את השגיאה וממשיך למנגנון ההגנה הבא במקום להכשיל את
הבקשה. חסימה היא החלטה מפורשת (`block: true`), ולעולם אינה מתרחשת בטעות.

## מגני ברירת מחדל

הרשימה טוענת אוטומטית שישה מגנים בסדר עדיפויות בעת ייבוא
(ראה `registry.ts` → `registerDefaultGuardrails()`):

| עדיפות | שם                  | שלב(ים)        | קובץ                  |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

מספרי עדיפות נמוכים יותר פועלים **ראשונים**.

### גשר הראייה (`visionBridge.ts`) — גשר מודליות PR-1

חוסם בקשות נושאות תמונות המיועדות ל**מודלים שאינם ראייה** ומפנה
את הבקשה כולה למודל תומך ראייה או מחליף את חלקי התמונה בתיאורי טקסט המיוצרים על ידי מודל ראייה שניתן להגדיר לפני הקריאה העליונה. זה מאפשר לספקי טקסט בלבד לטפל בצורה שקופה
במטענים מרובי מודלים.

זרימה:

1. דלג אם המודל המיועד כבר תומך בראייה (אלא אם הוא מופיע ברשימת הגשרים הכפויים `isVisionBridgeForcedModel`).
2. חילץ חלקי תמונה באמצעות `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), שמאציל ל**מגלה מדיה מאוחד**
   `detectMediaParts()` ב`open-sse/utils/mediaParts.ts` — מקור האמת היחיד המשותף עם מסנן תאימות קומבו.
   החילוץ מותנה בחלקים ברמה העליונה של הצורות
   ש`replaceImageParts` יכול לחבר חזרה (החוזה extract↔replace): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, ו-Responses API `input_image`. פגיעות מקוננות וצורות רק אינדיקטור הן חומר למסנן קומבו ואינן נחלצות לעולם.
   דלג אם לא נמצא דבר.
3. פתח את הגדרות הריצה באמצעות `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): מפתחות הגדרות `modalityBridge*`
   החדשות מנצחות; מפתחות `visionBridge*` הישנים נשארים **גיבוי של מחזור אחד**
   (חלון חזרה). דלג לפני כל מעבר מדיה כאשר הגשר מושבת.
4. בורר מצב (`modalityBridgeVisionMode`, ראה טבלה למטה) מחליט
   אם להפנות או לתאר. הפנייה מחזירה `modifiedPayload` עם רק `model`
   מוחלף, בנוסף למטה `{ rerouted, fromModel, toModel, imagesKept }`.
5. מסלול תיאור: הגבל תמונות ל`maxImages`, הרכב את ההנחיה המודעת למשימה,
   התייעץ עם מטמון התיאור, קרא למודל הראייה **במקביל**
   (`Promise.allSettled`), והכנס חלקי טקסט `[Image N]: <description>` במקומם. תיאור שנכשל מחזיר `null` וחלק התמונה המקורי **שמור** (#4012) — למעט במסלול התיאור הקומבו כאשר כל תיאור נכשל, שם מקור לא תומך בראייה מאושר מקבל
   `(unavailable — no vision-capable provider connected)` במקום (#8430).
6. החזר `modifiedPayload` + מטה (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### בורר מצב (`modalityBridgeVisionMode`)

| מצב        | ברירת מחדל | התנהגות                                                                                                                                                                                           |
| ---------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔          | היסק ישן, לא נוגע (#6640/#7204): מודלים שאינם קומבו/`auto/` מפנים למודל הראייה הטוב ביותר אלא אם המודל המקורי כבר יש לו אישורים שימושיים (אז מתאר); מטרות קומבו תמיד מתארות.                      |
| `describe` |            | תמיד מתאר — בלוק ההפנייה מדולג לחלוטין; המודל הנבחר של המשתמש תמיד עונה.                                                                                                                          |
| `reroute`  |            | הפנייה כפויה: שומר המודל עם אישורים נשמר מדולג. שומר האישור של יעד ההפנייה עדיין חל — כאשר אין יעד ראייה שימושי, הבקשה נופלת לתיאור כך שהתמונות הגולמיות לעולם לא מגיעות לאחור טקסט בלבד (#8430). |

מצבים כפויים מקצרים **לפני** שההיסק האוטומטי פועל; התנהגות `auto`
זהה בייט-לבי למגן לפני PR-1.

#### טווח מפתח API (`visionBridgeKeyScope.ts`)

כאשר מפתח ה-API של הקורא מגביל `allowedConnections`, בריכות מכסה
(`allowedQuotas`) או מודלים (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), הגשר בוחר רק
מודלים להפנייה ולתיאור שהמפתח יכול להשתמש בהם, על חיבורים שהמפתח יכול
להשתמש בהם. הקריאה לתיאור אז תמיד עוברת דרך הלולאה העצמית של OmniRoute עם
הכותרת `x-omniroute-self-loop-key-id`, כך שבקשת הצ'אט המתקבלת
אוכפת שוב את מדיניות החיבור והמודל של המפתח הזה. `enforceApiKeyPolicy()`
מכבדת את הכותרת הזו רק יחד עם נושא הלולאה העצמית, כך שהיא יכולה רק
להצמצם גישה, ומזהה שאינה נפתרת נדחית.

אם אין מודל ראייה מותר עבור המפתח, מסלול התיאור מתרחק והבקשה עוברת
ללא שינוי, אותה התנהגות פתוחה כמו מגן מושבת (מטה `{ skipped: true, reason: "no_permitted_vision_model" }`).
בקשות ללא מפתח, ומפתחות ללא הגבלות אלו, מתנהגות בדיוק כמו קודם.

#### הנחיית תיאור מודעת למשימה (`modalityBridgeVisionTaskAware`)

ברירת מחדל **נכון**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) מוסיף
את הטקסט של **ההודעה האחרונה של המשתמש** (מקוצר ל-500 תווים) לבסיס
ההנחיה לתיאור, מכוון את התיאור למה שהמשתמש באמת שאל
(דפוס codex-vision-proxy) ושואל את מודל הוויז'ן לתמלל טקסט גלוי. כאשר הדגל כבוי — או שאין טקסט מהמשתמש — ההנחיה הבסיסית משמשת ללא שינוי.

הבקשה של הלולאת תיאור עצמית תואמת OpenAI (`callVisionModelSingle()`
ב-`visionBridgeHelpers.ts`) תמיד מבקשת `image_url.detail: "high"` —
ללא תנאים, עבור כל קורא/ספק, לא תלוי באות סיגנל מהלקוח.
דגימה ברזולוציה נמוכה מפחיתה את דיוק ה-OCR בדיוק עבור משימת תמלול הטקסט
שבה ההנחיה הזו עוסקת, כך שהקריאה לתיאור עצמה תמיד מבקשת רזולוציה גבוהה
ללא קשר לרמת הרזולוציה שבה השתמשה הבקשה המקורית. זה משפיע רק על גוף הבקשה הפנימית לתיאור; זה לא משנה איך
OmniRoute מעביר את `image_url.detail` של הקורא בבקשה הראשית —
ברירת המחדל מוחלת בנפרד, ורק עבור לקוחות OpenCode שזוהו, ב-`defaultImageDetail()`
(`open-sse/handlers/chatCore/upstreamBody.ts`). הסניף של פורמט החוט של Anthropic של הלולאת תיאור עצמית אין לו שדה `detail`
ואינו מושפע מאף ברירת מחדל.

#### מגבלת פלט תיאור (`modalityBridgeVisionMaxChars`)

| מפתח                           | ברירת מחדל | טווח             |
| ------------------------------ | ---------- | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`        | `0` או 100–50000 |

`0` (ברירת מחדל) פירושו **אין מגבלה** — התיאור המוחזר על ידי
`callVisionModel()` מועבר ללא שינוי, שומר על ההתנהגות הקיימת. כל ערך בטווח 100–50000 מקצר את התיאור עם סיומת `…` לפני שהוא מחובר חזרה כ-`[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` ב-`src/lib/guardrails/visionBridge.ts`).
הגדל זאת עבור משימות OCR עשירות בפרטים שבהן המודל downstream זקוק לתמלול המלא; הקטן זאת כדי להגביל את השימוש בטוקנים במודלי ויז'ן מדברים.
שדה הלוח נמצא בלשונית הוויז'ן בלוח המתקדם
(`modality-bridge-max-chars` ב-`ModalityBridgeVisionTab.tsx`) ומגביל כל
ערך בין 1 ל-99 עד לרצפה של 100 תוך השארת `0` מפורש ללא שינוי — `0` הוא ערך Zod תקף בפני עצמו
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), לא רק
ברירת המחדל "לא הוגדרה".

#### מטמון תיאור (`modalityBridge/bridgeCache.ts`)

מטמון LRU + TTL בזיכרון עבור פלטי תיאור, משותף בכל התהליך.
מפתח = `sha256(imageRef + composedPrompt + configuredBridgeModel)` עם
מסגרת באורך-קידומת (ללא התנגשויות גבול שדה). רכיב המודל הוא
המודל **המוגדר** של הגשר, לא המודל שענה בפועל —
`callVisionModel` עשוי ליפול חזרה פנימית, ומפתח לפי ניסיון היה
שובר את המטמון. תיאורים שנכשלו לעולם אינם נשמרים. הגדרות:

| מפתח                            | ברירת מחדל | טווח    |
| ------------------------------- | ---------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`     | —       |
| `modalityBridgeCacheTtlMinutes` | `60`       | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`      | 10–5000 |

#### נורמליזציה של תמונות מרוחקות (לולאת תיאור/משיכת base64)

כאשר הגשר מושך תמונה **מרוחקת** בעצמו — הקריאה העצמית של תיאור של Anthropic
והמרת base64 של פורמט claude-wire
(`ensureBase64ImagesForClaudeWire`), שניהם דרך
`fetchRemoteImageAsDataUri()` ב-`visionBridgeHelpers.ts` — ה-URI הנתונים الناتן מועבר דרך `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) לפני שהוא מוטמע בבקשת מודל הוויז'ן. תמונות גדולות מדי מצומצמות לגובה **2048 פיקסלים** (תואם
למגבלת השינוי ש-OpenAI/Anthropic כבר מיישמים בצד השרת), מה שמפחית
בייטים/שהייה של העלאה מבלי לשנות מה שמודל הוויז'ן רואה. שינוי גודל
משתמש ב-`sharp`, שנמצא דרך ייבוא דינמי: על פלטפורמה שבה הבינארי המקורי שלו נכשל לטעון, `normalizeDataUri()` **לא זורק** — הוא נופל חזרה
למעבר של הבייטים המקוריים, כך שהמסלול לתיאור/המרת base64
תמיד נשאר פעיל. בייטים שאינם תמונה (משיכה שלא החזירה תמונה שניתן לפענח) מועברים גם הם ללא שינוי. נורמליזציה זו
מוגבלת לתמונות שהגשר מושך עבור הקריאה העצמית שלו — היא לעולם לא
מוחלת על העומס הגולמי של הקורא, בהתאם לעקרון המוטציה רק באופציה (כלל קשה #20).

#### סכמת הגדרות + הגירה

המפתחות החדשים `modalityBridge*` מאומתים על ידי Zod ב-`updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, שלישיית `modalityBridgeCache*`, וקבוצת
`modalityBridgeAudio*` שמשתמשת על ידי Audio Bridge. ההגירה
`141_modality_bridge_settings.sql` מעתיקה ערכים ישנים קיימים
`visionBridge*` למפתחות החדשים המתאימים (אידמפוטנטי, לעולם לא מוחק
ערך `modalityBridge*` שנקבע על ידי מפעיל); המפתחות הישנים נשארים מקובלים כהחזרה לקריאה במשך מחזור שחרור אחד.

#### כותרת שקיפות + סטטיסטיקות

תגובות שהוסבו על ידי תיאור נושאות
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(נבנה על ידי `buildModalityBridgeHeader()` ב-`modalityBridge/bridgeStats.ts`,
נחתם על ידי `withModalityBridgeHeader()` ב-`src/sse/handlers/chatHelpers.ts`).
בקשות שהופנו מקבלות **לא** כותרת — העומס לא הושפע והחלפת המודל
כבר נראית בשדה `model` של גוף התגובה.

`GET /api/modality-bridge/stats` (אימות ניהול, באותו רמה כמו
`GET /api/settings`) מחזיר את המונים לפי מודל בזיכרון
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` עבור `vision`, `audio`, ו
`video`. `averageLatencyMs` משתמש ב`latencySamples`, ולא בכל הניסיונות, כ
מכנה; פעולה ללא תזמון אינה מייצרת דגימה של אפס מילישניות. `bridged` נשאר
הכינוי התואם לאחור עבור המרות מוצלחות; ניסיונות כושלים אינם מגדילים אותו.
המונים מתאפסים עם הפסקת התהליך בעיצוב
(טלמטריה, לא חשבונאות).

#### הגדרת לוח מחוונים

דף הלוח מחוונים המוקדש הוא
`/dashboard/settings/modality-bridge`. הכתובת URL שלו `Vision`, `Audio`,
ו`Video` שומרת על פרמטרי השאילתה בזמן החלפת ערך ה`tab`.
הכרטיסייה Vision חושפת הפעלה, מצב, בחירת מודל (כולל ברירת המחדל האוטומטית),
הנחיות מודעות למשימות, מגבלות מתקדמות על זמן/תמונה/אורך תיאור/מטמון,
מונים בזמן ריצה, ובקשה לדוגמה מוגנת. הכרטיסייה Audio גם פעילה: היא חושפת
הפעלה, בורר מודל STT בלבד עם Auto, מגבלות זמן/מקסימום קליפ, מונים של אודיו,
ובדיקת דוגמה של `input_audio`. הכרטיסייה Video פעילה: היא מדווחת על
מצב הריצה של FFmpeg/ffprobe — אחד מארבעה מצבי UI מפורשים (`unknown` בזמן
שהחיפוש באוויר או לא הצליח להסתיים, `restricted` על מארח לוח מחוונים שאינו
לולאת חזרה שבו החיפוש מדולל בצד הלקוח, `unavailable` לאחר חיפוש ואישור
חסר, או `available` עם גרסאות FFmpeg/ffprobe) — שומרת על מגבלות enable/model/frame/video/timeout,
מסננת את בורר המודל למודלים בעלי יכולת ראייה, וחושפת מונים של וידאו.

הכרטיס הקודם של Vision Bridge תחת הגדרות AI הוא קישור תאימות לדף החדש;
כעת אין לו עותק שני של הטופס. ספקי מדיה גם מקשרים את זרימות העבודה של
Image-to-Text וSpeech-to-Text לכרטיסיות Modality Bridge המתאימות מבלי להסיר את
משחק ה-Speech-to-Text הקיים.

**עקיפת קבלת לולאת עצמי:** כאשר קריאת התיאור מנותבת דרך הלולאה העצמית
של OmniRoute `/v1` (מודל ספק לא סטנדרטי), הבקשה המשנית שולחת
`x-omniroute-admission-bypass: internal` ומאומתת עם האישור של הלולאה העצמית
המפוענחת — ה`sk_omniroute` המקומי במצב מקומי, או המפתח `OMNIROUTE_API_KEY` / `ROUTER_API_KEY`
המוגדר על ידי המפעיל (#1350) כך שפריסות עם `REQUIRE_API_KEY=true` יכולות
עדיין להריץ את קריאת התיאור. העקיפה מכובדת רק עבור אותם אישורים מדויקים,
כך שלקוחות חיצוניים אינם יכולים להשתמש בכותרת כדי לדלג על קבלה.

ברירות המחדל הישנות נמצאות ב`src/shared/constants/visionBridgeDefaults.ts`;
ברירות המחדל החדשות המודעות למשימות/מטמון והפותר הגדרות נמצאות ב
`src/shared/constants/modalityBridgeDefaults.ts`. המדריך חושף אפשרות קונסטרוקטור
`deps` כך שהבדיקות יכולות להזריק יישומים מזויפים של `getSettings` ו
`callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

מ intercepts בקשות צ'אט נושאות אודיו לפני שהן מגיעות ליעד שאינו
ידוע כמקבל קלט אודיו. היא אף פעם לא מנתבת מחדש את בקשת הצ'אט: חלקי האודיו
מועתקים דרך נקודת הקצה הקיימת התואמת ל-OpenAI ומודל הצ'אט הנבחר ממשיך עם
העתקות טקסט.

זרימה:

1. פותר `supportsAudio` דרך `getResolvedModelCapabilities()`. מטא-נתוני רישום
   ספק מפורשים מנצחים, ואז מטא-נתוני מודל סטטי, ואז `modalities_input` מסונכרנים.
   רשימת קלט שהוכרזה ללא `audio` היא `false`; אין ראיות יכולת נשארות `null`.
   גם `false` וגם `null` מפעילים את הגשר השמרני, בעוד ש`true` עוקף אותו.
2. פותר הגדרות `modalityBridgeAudio*` ומוציא חלקי אודיו ברמה עליונה שניתן לחתוך
   מכל הודעה דרך המגלה המשותף `detectMediaParts()`. צורות חוט נתמכות הן
   `input_audio`, `audio_url`, ו`source.media_type: "audio/*"`. אודיו מקונן
   מזוהה לצורך ניתוב אך לא מוסר על ידי מסלול החיתוך. העבודה מוגבלת על ידי
   `modalityBridgeAudioMaxClips`; חלקים מאוחרים נשארים ללא שינוי.
3. מכבד `provider/model` שהוגדר, או נותן ל`selectAudioBridgeModel()` לעבור
   על `AUDIO_TRANSCRIPTION_PROVIDERS` בסדר קטלוג יציב ולבחור את המודל הראשון
   עם אישור ספק פעיל שניתן להשתמש בו.
4. `callAudioTranscription()` ממיר אודיו ב-base64/data-URI לקובץ multipart,
   או מוריד `audio_url` מרוחק דרך השומר החיצוני בלבד עם נעילת DNS ומגבלה של 25 MB.
   לאחר מכן הוא POST את הקובץ ואת המודל הנבחר ללולאת ה`/v1/audio/transcriptions`
   המקומית, מאומת עם `resolveSelfLoopBearer()`. מסלול ההעתקה הקיים מבצע חיפוש
   רגיל של אישורים, טיפול בקירור/מגבלת קצב, והפצת ספקים.
5. קריאות מוצלחות מחליפות את חלקיהן ב`[Audio N]: <transcript>`. קריאות
   רצות עם `Promise.allSettled`: כישלון בודד שומר על חלק האודיו המקורי (#4012
   חוזה). אם כל קריאה נכשלת והיעד הוכח כ`supportsAudio === false`, החלקים
   הופכים ל`[Audio N]: (unavailable — no STT provider connected)` (#8430 חוזה).
   עבור יעד לא ידוע (`null`), תוצאה של כישלון מוחלט נשארת ללא שינוי. יעד
   שהוכח כטקסט בלבד ללא אישור STT שניתן להשתמש בו מקבל את אותו דחליל מפורש
   מבלי להוציא קריאת רשת.

העתקות מוצלחות משתמשות במטמון LRU/TTL של Modality Bridge ברמת התהליך. המפתח
משלב את הפניה לאודיו, את תווית הפעולה היציבה `audio-transcription`, ואת מודל ה-STT הנבחר;
כישלונות לעולם אינם נשמרים במטמון. ניסיונות אודיו מעדכנים את המונים המשותפים
`bridged`, `cacheHits`, `failures`, ו`lastUsedAt`.
תגובות שהוסבו נושאות
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; בקשות שלא
נגעו לא מקבלות קטע Audio Bridge.

הגדרות בזמן ריצה מגובות DB ומאומתות על ידי Zod:

| מפתח                          | ברירת מחדל | טווח           |
| ----------------------------- | ---------- | -------------- |
| `modalityBridgeAudioEnabled`  | `true`     | —              |
| `modalityBridgeAudioModel`    | `""`       | Auto או STT ID |
| `modalityBridgeAudioTimeout`  | `60000`    | 1000–300000    |
| `modalityBridgeAudioMaxClips` | `3`        | 1–10           |

המטמון המשותף נשאר תחת שליטה של `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, ו-`modalityBridgeCacheMaxEntries`.

### גשר וידאו (`videoBridge.ts`, `videoBridgePipeline.ts`)

חוטף חלקי וידאו ברמה העליונה ב-Chat Completions `messages` וב-Responses
API `input` לפני שמתקשרים ליעד ללא תמיכה בוידאו מקורי ידועה.
צורות נתמכות הן `input_video`, `video_url`, `video_source`, URLs של HTTPS,
ו-`data:video/*;base64,...` URI נתונים. שמות קבצים פשוטים בטקסט לא מטופלים
כוידאו.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) אחראי על מעבר הבקשה,
בדיקת היכולת/מדיניות, אגרגציה לפי בקשה, וטעינת התגובה.
עבודה לפי וידאו — רכישה, מטמון התוצאה המלאה, תיאור רצף פריימים
(שמאחד כל תמלול אודיו שהוכרז על ידי המתקשר), ומדדים/ביטול/ניקוי לפי ניסיון
— מוסתרת מאחורי `processVideoPart` ב-`videoBridgePipeline.ts`, הנקראת פעם אחת לכל חלק וידאו בתוך הלולאה של `preCall`.
מודול זה גם מגדיר את גבולות הפורט המפורשים `VideoMediaBrokerPort`
(רכישת בתים והפקת פריימים מדוגמים), `VideoAudioTranscriptionPort`
(איחוד תמלול אודיו שהוכרז על ידי המתקשר עם הכיתובים המדוגמים), ו-`VideoDrilldownPort`
(צורת האחסון הגולמית הישנה). STT בייצור ושימור פריימים
מורכבים סביב הפורט המתאר דרך `createVideoSttAdapter` ו-`createVideoDrilldownAdapter`; האחרון משתמש בלוח מחזור ידני משותף.

נתיב הבקשה הציבורי `/v1` אף פעם לא מייבא או מפעיל תהליך משנה.
וידאו מרוחק מורד תחת מגבלה של 50 MiB; וידאו בסיס64 אינליין יש לו
מגבלה שמרנית של 36 MiB מפוענח לכל וידאו כך שהמודל/הודעות/עטיפת המסגרת
יכולים להישאר בתוך מגבלת קבלת הבקשה JSON הציבורית של 50 MiB. אורך אינליין
ואומדני גודל מפוענח נבדקים לפני הקצאה. HTTPS
נדרש על ה-URL המרוחק הראשוני וכל הפניה מחדש, תוך שימוש בשמירה קיימת
רק לציבור עם נעילת DNS. הבתים אז חוצים את הגבול המדויק של
`POST /api/modality-bridge/video/extract` של הברוקר. הנתיב הזה הוא גם
`LOCAL_ONLY` וגם `SPAWN_CAPABLE`, מקבל רק בקשה מאומתת,
מהימנה-חוזרת, ואינו מקבל אף פעם URL, נתיב מערכת קבצים, קובץ הרצה,
או רשימת ארגומנטים. צינור גודל גוף ה-API וקורא גוף ההדרן
הולכים באופן עצמאי לאכוף מגבלת קלט של 50 MiB. התור המוגבל שלו פועל
על הוצאת אחת בכל פעם, מאפשר ארבעה עבודות ממתינות, ומגביל קלט ממתין ל-100 MiB.

בתוך הברוקר, `ffprobe` קורא קובץ מקומי פרטי; רשימת הפורמטים
המותרת קובעת כי פורמטים של רשימות השמעה ומניפסטים אינם מותרים. עבור קונטיינרים
ממשפחת MOV המותרים, הפניות לנתוני MOV חיצוניים נשארות מושבתות כברירת מחדל, והפקודה הקבועה אינה בוחרת בהם. גם `ffprobe` וגם `ffmpeg` משתמשים
ברשימת הלבנה של פרוטוקול `file`-בלבד, חוט אחד, מערכי ארגומנטים קבועים, ללא שורת פקודה,
וקבצים ניתנים לפתרון מ-`PATH`. זרמי כיסוי של תמונות מצורפות אינם
מועמדים ניתנים לניגון. כל הזרמים הניתנים לניגון חייבים לעמוד במגבלות, וזרם ברירת מחדל מפורש מועדף לפני הנפילה הנמוכה ביותר הקבועה.
וידאו מוגבל ל-600 שניות, 8,192 פיקסלים לכל מימד, ו-33,554,432 פיקסלים מקוריים. FFmpeg מדגם 1–16 פריימים JPEG באמצע, מקטין את הקצה הארוך ל-1,024 פיקסלים לכל היותר מבלי להגדיל קלטים קטנים יותר, ואינו מקבל אף פעם URL.
הדגימה היא `uniform` כברירת מחדל. המדיניות האופציונלית
`scene_aware` והניסי `segment_aware` מבצעות מעבר FFmpeg קבוע נוסף על הזרם המקומי שכבר אומת, בוחרות חותמות זמן של סצנות `showinfo` מוגבלות, ונופלות באופן דטרמיניסטי לאותם
אמצעים אחידים במקרה של כישלון של המגלה, פסק זמן, פלט לא תקין, או קבוצת מועמדים ריקה. מצב מודע לסגמנטים מקצה דגימות אמצע באופן פרופורציונלי לאינטרוולים של סצנות מאומתות; ראיות מודעות לסגמנטים והתנהגות נפילה מפורטות למטה. מגבלת 16 הפריימים הקשה
מוחלת לאחר הבחירה בכל מדיניות. כאשר בקשה מודעת לסצנה יש רק תקציב של פריים אחד, היא משתמשת באמצע האחיד של הווידאו המלא הפעיל או חלון הפוקוס ומדווחת `policyEffective: uniform`: פריים סצנה אחד שנבחר אינו יכול לשמור על שני הקצוות הזמניים. מתקשר יכול לספק אופציונלית חלון פוקוס סופי (`start`/`end` שניות); גבולות ננעלים על משך המדיה, חלונות הפוכים או לא סופיים נדחים, וכל מדיניות דגימה מתבצעת רק בתוך האינטרוול הנורמליזי. החלון الناتן
כלול במטא-נתוני הדגימה ובתיאור הלא מהימן כך שמודלים downstream יכולים להבחין בין קטע ממוקד לבין ציר הזמן המלא.

מיקוד בכיתוב סמנטי הוא הגדרה נפרדת ומפורשת. מצב הניתוח ברירת המחדל `full`
שומר על ההנחיה הקיימת של הפריים ואינו מעביר אף פעם טקסט בקשה למודל הכיתוב. במצב `focused`, הגשר קורא רק את ה-`text`/`input_text` האחרון שאינו ריק שנכתב על ידי המשתמש מאותו מיכל של Chat או Responses, מנרמל אותו ל-NFC, מתמוטט על תווי שליטה ורווחים, ומגביל אותו ל-500 נקודות קוד Unicode. תוצאה ריקה נופלת חזרה להנחיה המדויקת `full`. רמז שימושי מסודר כ-JSON בחסימה ייחודית של הקשר משתמש לא מהימן ויכול להעדיף רק פרטים נראים; הוא אינו יכול להחליף את האזהרה הנפרדת נגד ביצוע הוראות הנראות או הנשמעות במדיה. מיקוד טקסטואלי אינו מסיק אף פעם `start`/`end` או משנה
את הדגימה הזמנית.

#### FU-07 ראיות סגמנט מבניות

`segment_aware` משתמש במעבר ניתוח מקדים מוגבל על זרם הווידאו המקומי שכבר אומת. שרשרת המסננים הקבועה קודם כל מקטינה לרוחב של עד 320 פיקסלים, מזהה שינויים בסצנה ובזמנים קפואים, ולאחר מכן מדגימה בקצב של פריים אחד בשנייה עבור טשטוש, ממוצע לומה, ומידע מרחבי/זמני. המעבר מוגבל ל-600 דגימות מבניות, חוט FFmpeg/filter אחד, אותו פרוטוקול וקונטיינר המאפשרים קבצים בלבד, גבול פלט תהליך של 1 MiB, ובמקסימום 30 שניות בתוך הזמן המשותף של הברוקר לביטול/דדליין. הוא אף פעם לא מקבל פקודה, מסנן, נתיב או URL מהבקשה.

הערכים המבניים הם ראיות דגימה דטרמיניסטיות, לא הבנה סמנטית של ווידאו. הם לא מסיקים נושאים, פעולות, כיתובים, דיבור או כוונת משתמש. גבולות הסצנה והקפיאה יוצרים קטעים; כיסוי הקפאה, טשטוש, חשיפה, פרטים מרחביים ושינויים זמניים משפיעים רק על איך שהתקציב הקיים של 1–16 פריימים מוקצה. קטע קפוא לחלוטין מוגבל לפריים אחד, בעוד שקטעים לא קפואים מתחרים על התקציב הנותר. כאשר הגבולות עולים על הפריימים, נשמר כיסוי אחיד של ציר הזמן כך שחתיכות מהירות לא יכולות להסתיר קטע ארוך מאחור. גבולות סצנה בתוך רזולוציית הניתוח של שנייה אחת של גבול קפיאה מתמזגים.

מסננים חסרים, ראיות מעוותות/ריקות, שגיאת גלאי, או זמן ההמתנה המוגבל של הניתוח המוקדם נכשלות לפתיחה לפי מדיניות האמצע האחיד המדויק. ביטול של Caller או דדליין של ברוקר לא נכשלות לפתיחה: זה מסיים את תהליך המשנה המתקדם, מונע הוצאת פריימים מאוחרים, והעץ הזמני הפרטי מוסר ב-`finally`.

`scripts/perf/video-bridge-fu07-eval.ts` מייצר מתקנים דטרמיניסטיים אמיתיים של FFmpeg לחיסכון בכיתובים לאחר דדופליקציה, הקצאת תקציב תנועה צפופה, ראיות טשטוש/חשיפה/SI-TI, חתיכות מהירות עם זנב ארוך, וחיוב שגוי של פוזיטיביים. הוא רושם את זמן הקיר של הניתוח המוקדם ובמקום שבו `/usr/bin/time` זמין, את ה-CPU של הילד ואת ה-RSS המקסימלי. בדיקות האיכות שלו הן אורקל מבני בלבד. איכות מודל הכיתוב האמיתית נשארת `HOLD` כי לרתמה הזו אין נקודת קצה מאושרת או שופט קפוא. חיסכון כספי גם נשאר `HOLD` אלא אם `--caption-cost-per-call-usd` מספק הערכה חיובית מפורשת לכל שיחה; הסקריפט אף פעם לא ממציא אף תוצאה.

כל פריים מוגבל ל-4 MiB, כל הפריימים הגולמיים יחד ל-23 MiB, ותגובה של הברוקר המוסרת ל-32 MiB. תיקייה זמנית פרטית מוסרת ב-`finally`. OmniRoute לא כוללת את FFmpeg ולא מקבלת נתיב קובץ מותאם אישית. לפני הכיתוב, הגשר מבצע מעבר דדופליקציה חזותית שמרנית: כל JPEG מצטמצם לבופר של 16×16 בגווני אפור ומושווה רק עם הפריים האחרון שנשמר. עבור תקציב כיתוב המבוקש מעל פריים אחד, ההוצאה מספקת בריכת מועמדים מוגבלת של עד פי שניים מהתקציב הזה ולא יותר מ-16 פריימים. הגבול המבוקש מוחל רק לאחר דדופליקציה, עם המועמדים הנבחרים הראשונים והאחרונים נשמרים במהלך הצמצום הסופי כאשר התקציב הוא לפחות שניים. המדיניות המהדורה `grayscale-16x16-mean-cells-v2` משתמשת בממוצע של דלתת הלומה הגדולה יותר וביחס של תאי התמונה הממוזערים שהדלתא הנורמלית שלהם היא לפחות 0.05. סף השכפול הוא הקבוע 0.04, שנבחר לניבוי ולא נחשף כהגדרת זמן ריצה. האות השני הזה בעל הניגודיות הגבוהה שומר על תנועה קטנה ושינויים בטקסט הנראה שיכולים להסתיר השוואה רק ממוצעת. שגיאות של משווה או מפענח נכשלות לפתיחה ושומרות על הכיסוי. מטא-דאטה של פלט מפריד בין מועמדים שהוצאו, פריימים שהשתמשו בהצלחה, ושכפולים חזותיים שנזרקו.

חלק וידאו שמסומן במפורש יכול לבקש גיליון קשר עם חותמת זמן. הגשר בונה לכל היותר רשת JPEG של 4 עמודות ו-16 פריימים. כל תא של 512 פיקסלים שורף את חותמת הזמן שלו לרצועת תחתית בעלת ניגודיות גבוהה, בעוד שהחותמות זמן זהות נשארות במטא-דאטה טקסטואלית עבור אסוציאציה וביקורת בהמשך. ה-JPEG המלא נשאר מוגבל ל-32 MiB. אם `sharp` לא יכול לפענח או להרכיב את הרשת, הגשר חוזר לפריימים JPEG האישיים; ביטול של לקוח עדיין מתפשט דרך פעולת הגיליון.

ראיות קידום מופרדות במכוון מההרכב הסינתטי של המיקרו-בנצ'מרק. `scripts/perf/video-bridge-contact-sheet-eval.ts` מגדיר רתמת A/B עם גרסת סכימה עבור מודלים אמיתיים תואמי OpenAI. הוא מודד טוקנים מדווחים על ידי ספק, השהיית קיר קצה לקצה (כולל הרכבת גיליון), מספר קריאות מודל, ושימור עובדות המוגדרות במניפסט. תגובות מודל גולמיות לא נכתבות לדו"ח; רק דיגסטים SHA-256 וזיהוי עובדות תואמות נשמרים. הרתמה לא מבצעת קריאה לרשת או מודל בתשלום אלא אם `--execute-real` מועבר ו-`--model`, `OMNIROUTE_BASE_URL`, ו-`OMNIROUTE_API_KEY` מוגדרים. ללא הריצה האמיתית המפורשת הזו, פסק הדין הקריא של המכונה נשאר `HOLD`; מדידות של משקל סינתטי/מספר קריאות בלבד אינן ראיות קידום.

הסקריפט הנפרד `scripts/perf/video-bridge-promotion-eval.ts` צורך תצפיות FU-07 או FU-09. קבלת קידום דורשת את כל שמונת סוגי התרחישים הסינתטיים בנוסף לקליפ אמיתי מסונן, לפחות שלוש חזרות מדודות לכל תפקיד ומקרה, כל עשרה מדדים המוצהרים, דיגסטים של מדיה קפואה/הנחיה/עובדות צפויות/הגדרות, מזהי תצפיות ייחודיים וסדר A/B מאומת. קבלת הביצוע קושרת את דיגסט הקורפוס, SHA המדויק של המועמד וגרסת המודל. מדידות חסרות או לא תקפות נשארות `HOLD`, כולל CPU מעל 30 שניות, RSS מקסימלי מעל 512 MiB או ניתוח מוקדם מעל 30 שניות. אלה הם גבולות קבלת ראיות, לא הבטחת אכיפת RSS חדשה בזמן ריצה.

FU-07 דורש לפחות 98% שמירה על איכות ו- p95 השהיה לא יותר מ- 1.2x
בסיס, בנוסף לשיפור מוחלט של 0.05 בשיעור זיכרון מאוזן במקרים
שווים בשיחות כיתוב ממוצעות, או לפחות 10% פחות בשיחות כיתוב לאחר דדופליקציה ממוצעות. FU-09 דורש לפחות 0.85 איכות, 95% שמירה, הפחתה של 20% ב- p95 השהיה והפחתה של 10% בטוקנים. אובדן של עובדות קריטיות, עמידה בהזרקה או חוסר שימוש מונעים קידום. ביצוע אחד לא יכול לקדם דבר: `--previous-report` מאשר שני ביצועים נפרדים, לא חופפים, זכאים ברצף של אותה מדיניות/גרסה/מועמד/קובץ. ניסוי דגימה לא יכול לאשר ניסוי גיליון קשר.

אוספים צריכים לדרג תגובות בזיכרון ולשמור `responseDigest` בנוסף
למדדים והקשרים של תצפיות, לעולם לא טקסט תגובה. הצרכן גם קורא
תצפיות גולמיות ישנות אך לעולם לא מעתיק את הטקסט הזה לדו"ח שלו. בדיוק
אחד מ- `responseDigest` או `rawResponseText` מתקבל עבור כל תצפית.
הרשימה המותרת בגרסה נשארת ריקה עם ברירת מחדל בלתי ניתנת לשינוי `hold`. רשומה זכאית דורשת את הפניה שלה, מדיניות, גרסת מודל, SHA מדויק של המועמד, דיגסט המניפסט ושני מזהי ריצה נפרדים; הקשרים סותרים נדחים. מטא-דאטה אלה הם חוזה ביקורת, לא הוכחה שקובץ המוזכר מכיל מדידות אמיתיות. עיין בקבלות האמיתיות לפני הוספת
כל רשומה. נקודת הקצה של סטטיסטיקות הניהול ולוח המחוונים של הווידאו חושפים
מוכנות שמרנית. כינוי מודל מוגדר בלבד לא קובע את הגרסה שלו או
את ה-SHA של המועמד הפועל, כך שלוח המחוונים הנוכחי מדווח `HOLD` במקום
לנצל זכאות מקונטקסט ביצוע אחר. בחירת ניסוי מפורשת נשארת נפרדת מקידום; לא ברירת מחדל משתנה אוטומטית.

קוראים יכולים לצרף מערך אופציונלי של `transcript.cues` לחלק וידאו נתמך
כאשר הם כבר מחזיקים טקסט מיושר. כל רמז חייב לשאת `text`, טווח סופי של `start`/`end` בתוך משך הזמן הנבדק, ו- `source` ברשימה המותרת (`client`, `embedded`, או `audio-bridge`); `confidence` ברירת המחדל היא `1` וחייבת להישאר בין `0` ל- `1`. רמזים מדויקים כפולים מתמזגים.
OmniRoute לעולם לא מתחיל תמלול מהמטא-דאטה הזו: רמזים מאומתים מועתקים לתוצאה המתוארת עם מקור, ביטחון וטווח, ומוצגים כתצפיות לא מהימנות לצד כיתובי המסגרת. טקסט לא תקף, מחוץ לטווח, או חסר מקור נדחה במקום להיכנס לזרם הכיתוב. שני ערוצי תמלול של גוף הבקשה מנרמלים את המקור שסופק ל- `client`, כולל תוויות `embedded` או `audio-bridge` שהוצהרו על ידי עצמם. רק מתאם בבעלות השרת יכול להקצות את התוויות המהימנות הללו דרך הארגומנט `trustedSource` בלבד; שדה JSON בבקשה לא יכול להגיע
לארגומנט הזה. טקסט התמלול נשאר תוכן נגזר ממדיה לא מהימנה,
בלא קשר למקורה, ולעולם לא יכול לקבוע אישור.

קורא מתקדם יכול לספק מסלול `audioTranscript` עבור אותו וידאו;
הוא מתייחס כטקסט שסופק על ידי הלקוח, לא הוכחה לתמלול של השרת.
תפרחת הפיוז'ן מריצה תצפיות חזותיות וקוליות תחת
מועד אחרון אחד ואות ביטול, מסדרת אותן על ציר זמן משותף, מתמזגת
כפולים מדויקים, ומדווחת על תוצאה חלקית כאשר צד אחד בלבד מצליח.
`audioTranscript` לא תקף מתדרדר לתוצאה החלקית הזו — התיאור החזותי נשמר והענף הקולי רושם קוד כישלון מסונן —
במקום להיכשל על כל הווידאו. זמינות לפי ענף, הדגל החלקי,
וקודי הכישלון המסוננים נשמרים בתוצאה המתוארת, במטא-דאטה של
הגדרות הגנה (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), במטא-דאטה של מטמון התוצאה, ובספירות פיוז'ן של הגשר. הנתיב המוגדר כברירת מחדל של גשר הווידאו לא מפעיל דיבור לטקסט
או מוריד עותק מדיה שני; ללא המסלול המפורש הזה, הוא נשאר
רק ווידאו.

**שמירה על תמלול (#12150 P1).** זה חל אוטומטית בכל פעם ש
גשר הווידאו (עצמו אופציה) מציג רמז תמלול — אין דגל שמירה נפרד. כאשר בקשה מציגה כל רמז תמלול (תמלול שהוכרז על ידי הקורא או `audioTranscript` ממוזג), הגדרות ההגנה מסמנות אותו
`videoBridgeObserved` ומייצרות צל אדום של התיאור הווידאו —
הצגה זהה שבה גוף הטקסט החופשי של כל רמז מוחלף ב- `[redacted-video-transcript]`, שנבנה על ידי החלפת שדה הרמז המובנה לפני שהמחרוזת מורכבת (לעולם לא על ידי ניתוח הטקסט המפושט, כך שאין תוכן רמז — עוין או רגיל, כולל גופים המכילים `]` כמו
`[inaudible]`/`[music]` — יכול לשרוד). גוף בקשת יומן השיחות שנשמר מחליף
כל חלק טקסט נגזר ווידאו באותו צל אדום, תואם לפי שוויון תוכן; העוגן `fullText` נקרא מחדש מהמטען של הגדרות ההגנה לפני השיחה, כך שההתאמה עדיין מצליחה לאחר שהגדרות הגנה מאוחרות (מסנני PII ואישורים, עדיפויות 10/95) כותבות מחדש את טקסט התיאור במקום ואחרי שהזרקת מערכת/העברה/זיכרון מעצבת את מערך ההודעה. הגוף שנשלח למעלה למודל נשאר ללא שינוי. בקשה שנצפתה גם לא ממלאת
זיכרון עמיד (גם הוצאת תגובה וגם הוצאת בקשה מדלגות),
כך שהתשובה של המודל לא יכולה להדהד טקסט תמלול לזיכרון.

**שדות וידאו גולמיים (#12430).** כאשר הגשר מופעל ותמיכה בווידאו מקומית אינה ידועה או חסרה, שדות `transcript`/`audioTranscript` המוגדרים מפעילים גם את `videoBridgeObserved`, גם לאחר כישלון תיאור או גבול `maxVideos`. `null` ומחרוזות ריקות נחשבות; שדות חסרים ומטא-דאטה לא וידאו לא נחשבים. עותקים שנשמרים מסננים את השדות הללו או משאירים את הבקשה, ומטמונים/זיכרון מדולגים. המטען של הספק נשאר ללא שינוי.

עותקים נוספים שנשמרים משתמשים באותן אותות בקשה שנצפו. תמונת הלקוח הגולמית לפני הגדרות הגדרות, בקשה ממתינה בזיכרון, ורשומת הבקשות שנדחו מוקדם מחליפים מבנית את שדות הטרנסקריפט בחלקי הווידאו; הנחיות מחרוזת שנוצרו על ידי שלבי צינור והעברת הקשר נמחקות ביעד גוף הבקשה שנשמר. הסמן `video_content_removed` שנשמר גורם לכך שהמשך `previous_response_id` נכשל בסגירה במקום לשחזר טקסט שנזרק בכוונה. אם בקשה שנצפתה מאבדת את צללית ההסרה שלה לפני ההקלטה, או אפילו אחת מכמה צלליות וידאו נכשלת בהתאמה לאחר שינויים מאוחרים בבקשה, גוף הבקשה שנשמר נמנע לחלוטין במקום לשמור על טרנסקריפט חלקי שנמחק.

לגבי בקשה שנצפתה, תגובת מודל עשויה לצטט כל חלק מהטרנסקריפט ללא גבול תמרור מובנה. לכן, `responseBody` של יומן השיחות שנשמר מוחלף בסמן השמטה; הארטיפקט המפורט של הצינור (שיכול לכלול גופי עליון/לקוח וחתיכות זרם) לא נשמר. מטמוני סמנטיקה, אידמפוטנציה וחזרה על הסקת מסקנות עוקפים קריאות וכתיבות עבור בקשה זו. בקשת הספק ותגובה נראית ללקוח נשארות ללא שינוי. בתים מוקדמים לשמירה נמשכים מהזיכרון הזמני כאשר הארטיפקט המפורט נמנע. אזהרת ה-EventStream המוטעית של קירו מדווחת רק על מספר הבתים של העומס, אף פעם לא על התוכן או על השגיאה הגולמית של מפענח ה-JSON.
זה לא טוען שכל אבחון לא קשור של ספק/תוסף נבדק; הסSweep של היעד שנשמר נעקב ב-#11658.

מחזור החיים של `/api/modality-bridge/video/drilldown` הוא תשתית קאש נפרדת, מאומתת בלולאה/טוקן. כל פעולה דורשת גם מזהה עיקרי אטום קנוני. לפני שמפעיל ייצור מופעל, עליו להפיק את המזהה הזה מהשוכר המאומת ולא להעביר ערך שנבחר על ידי הלקוח. מפתחות הקאש קושרים את העיקרי הזה למזהי מושב קנוניים ומזהי הפניה לווידאו, מאחסנים רק את המפתחות המופקים שלהם SHA-256, ומגבילים גם קריאות וגם מחיקות לאותו עיקרי. הקאש מאחסן לכל היותר 16 מסגרות JPEG שהופקו לכל רשומה, פג תוקפן לאחר עשר דקות, ותומך בקריאות `start`/`end` מוגבלות או מחיקת מושב מפורשת.

כל עיקרי מוגבל ל-16 רשומות ו-64 MiB של נתוני JPEG קנוניים. מגבלות אלו אינן תלויות בתקרת 64 הרשומות/256 MiB הגלובלית: לחץ מכסה על העיקרי מפנה רק את הרשומות שהיו בשימוש הכי פחות לאחרונה של אותו עיקרי לפני שמחשבים על פינוי LRU גלובלי. רשומות שפג תוקפן נמחקות גם מהעיקרי וגם מהחשבונאות הגלובלית על פעילות קאש, בעוד שביטול וכישלון אימות אינם מחייבים החלפה חלקית.

הקאש דוחה Base64 לא קנוני, ריפוד יתר, מדיה לא JPEG, JPEGs מעוותים או מקוצרים, ו-JPEGs שמפיקים אזהרה במהלך פענוח מלא של תמונה מוגבלת `sharp`. הוא מקודד מחדש כל תמונה שהתקבלה כ-JPEG קנוני, מפיק רוחב וגובה מהבתים המפוענחים במקום לסמוך על שדות המתקשר, ומסלק כל בתים פוליגלוטיים אחרונים במקום לשמור עליהם. רק הבופר הקנוני המכווץ המוגבל מחויב לשני מכסות. מגבלת חוט ה-JSON כוללת את העומס של Base64 עבור תקרת הקלט המפוענח של 32 MiB. כל הפקת שמורה מתעדת את פורמט/רזולוציית ה-JPEG המאומתת שלה, מדיניות דגימה, גרסת הפקה, זמן יצירה, גזירת תוכן מחושבת על ידי השרת, וההפניה ההורית המגוללת של המתקשר המהימן. ביטול נבדק בין שלבי פענוח/גזירה אסינכרוניים לפני ההתחייבות האטומית של הקאש.

המפיק בייצור עושה שימוש חוזר במסגרת הברוקר שהופקה כבר רק לאחר ניתוח חזותי מוצלח, ללא הורדה/חילוץ וידאו שני. הוא דורש `modalityBridgeVideoDrilldownEnabled=true` של מפעיל, `drilldown: true` מחמיר לכל חלק, ורשומת מזהה מפתח API מאומת. ערכי עיקרי/מושב שהוכרזו על ידי הלקוח אינם מקנים בעלות. ללא שלושת התנאים הללו הוא לא מגזים, משנה גודל או שומר על מסגרות נוספות. כישלון בשמירה שומר על התגובה החזותית השימושית. בקשות שהוסכמו עוקפות את קאש התוצאה של כל הווידאו כך שהתוצאות המאוחסנות לא משחזרות ידיות.

תגובות JSON ו-SSE מוצלחות חושפות לכל היותר ארבע ידיות אטומות בהגדרת הכותרת המוגבלת `x-omniroute-video-drilldown`. מקורות דפדפן מורשים יכולים לקרוא את הכותרת מבלי להרחיב את מדיניות מקור CORS. ידיות חדשות משתמשות ב- `v1.<32-byte random base64url token>`, והרישום שומר רק את ה-SHA-256 שלהן. הקורא/מפרש הכותרת מקבל גם טוקנים ישנים של 64-hex. הצרכן הציבורי המאומת הוא `GET /api/v1/video-bridge/drilldown?handle=...`, שנחסם באופן עצמאי על ידי `modalityBridgeVideoDrilldownRemoteEnabled=true`. ביטול מפורש שנשמר מבטל גישה גם כאשר הגיבוי הישן `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` מופעל. שמירה בייצור יש לה גיבוי ישן דומה `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED`. שני הגיבויים כבויים כברירת מחדל.

הצרכן מפיק בעלות מהמפתח המאומת, מיישם מדיניות מפתח, ומחזיר את אותו 404 עבור ידיות לא ידועות, פג תוקף וידיות של מפתח אחר. הוא מקבל `variant=preview|standard|detail` (ממדי JPEG מקסימליים 320/640/1280, אף פעם לא מוגדלים), `limit=1..8` (או את הכינוי הישן `frames`, אף פעם לא שניהם), `page` מבוסס אפס, ושניות מיקוד אופציונליות `start`/`end`. מפתחות שאילתות כפולים וחלונות מיקוד הפוכים נדחים. כל וריאנט שהוחזר יש לו גזירה של התוכן האמיתי שלו ומטא-נתוני הרזולוציה האמיתית, מקושרים למקור שנשמר. וריאנטים נגזרים בקריאה במקום להיות מאוחסנים כהעתקות נוספות שנשמרות. התגובה JSON, כולל Base64/envelope, מוגבלת ל-32 MiB; דף גדול מדי מחזיר 413 והלקוח חייב לבקש פחות מסגרות. קריאות בודקות ביטול סביב כל שינוי גודל ומוודאות את תוקף הידית לפני החזרה. `DELETE` על ידי בעל הוא אידמפוטנטי; מחיקה או פקיעת TTL משחררת את המקור שנשמר ואת חשבונאות השימוש.

החנות המשותפת היא מקומית לתהליך: הידיות פוקעות בהפעלה מחדש ואינן ניתנות להעברה בין תהליכי OmniRoute עצמאיים. הסטטיסטיקות של הניהול חושפות מדיניות שמירה/מרוחקת אפקטיבית ומסכמות רשומות/בייטים שנשמרו בלבד, לעולם לא מדיה, הפניות, מזהי עיקר או ידיות. לוח ההגדרות של הווידאו מציג ערכים אלה ויכול לשמור את שני מתגי ההסכמה. תיעוד ההטמעה הזה אינו ראיה לפריסה חיה או לקידום; קבלת מודל אמיתי נעקבת בנפרד.

הכותרות מתווספות ברצף עם מודל הווידאו המוגדר. ע override וידאו ריק יורש את הגדרת הוויז'ן; אם שניהם ריקים, המפנה האוטומטי של הוויז'ן בוחר במודל הוויז'ן היעיל. כותרות מוצלחות מחליפות את החלק המקורי עם קידומת `[Video description:` יציבה שמסמנת גם את הטקסט כהערה נגזרת מדיה לא מהימנה ואומרת למודלים downstream לא לעקוב אחרי הוראות שנמצאות במדיה. מפתחות מטמון כותרות המסגרת כוללים את בייטי ה-JPEG, הפקודה, חותמת הזמן, והמודל היעיל; רק כותרות מוצלחות נשמרות במטמון. רשומות המטמון שומרות את המודל המפיק המוצלח בפועל, כולל מודל גיבוי; הגשר מדווח על `mixed` כאשר מסגרות שונות הופקו על ידי מודלים שונים. פגיעה במטמון עושה שימוש בזהות המפיק במקום לשנות את השם שלה לתוכנית ההפניה המבוקשת. מטמון התוצאה של הווידאו כולו מקודד על כל קלט שמשנה את הפלט — הפקודה, המודל היעיל, מדיניות הדגימה, מספר המסגרות, מצב ניתוח סמנטי, חותמת ה-SHA-256 של רמז המיקוד הנורמליזי, חלון המיקוד, `transcript`, `audioTranscript`, ודגל גיליון הקשר — כך ששינוי באחת מהמידות הללו הוא פגיעה במטמון, לעולם לא שימוש ישן. גרסת מדיניות ההסרה הוויזואלית, הסף, ומספר מסגרות המועמדות המוגבלות גם הם מפורטים במפתח המטמון ובמטא-דאטה; שינוי מדיניות לכן אינו יכול לעשות שימוש בתיאור הווידאו כולו ישן. מטא-דאטה של מטמון התוצאה v4 שומרת את המצב ואת החותמת, לעולם לא את משימת המשתמש הגולמית. מטא-דאטה של מסילות הגנה מדווחת על שני מצבי הניתוח המבוקשים והאפקטיביים; מצב `focused` המבוקש ללא טקסט משתמש שימושי מדווח כיעיל `full`.

המסילה שולפת כל חלק וידאו נתמך אך מתארת לא יותר מ-`modalityBridgeVideoMaxVideos`. עבור יעד שהוכח שיש לו `supportsVideo === false`, וידאוים שנכשלו ומעל למגבלה הופכים לסימני טקסט בטוחים מפורשים כך שאין וידאו גולמי שורד. כאשר היכולת אינה ידועה, חלקים אלה נשארים ללא שינוי. יעדים עם `supportsVideo === true` עוקפים את הגשר. אות הביטול של בקשת הלקוח מתפשט דרך ההורדה, תור הברוקרים, תהליכים משנה, ושיחות כותרות; ביטולים עוצרים בין וידאוים ולעולם לא נכשלות פתוחות למדיה גולמית.

ערכי זמן ההמתנה של הווידאו הישנים שנשמרו מעל 120 שניות מגודלים למועד הסיום של הברוקר; כתיבות הגדרות חדשות מעל למגבלה זו נדחות. `GET /api/modality-bridge/video/runtime` דורש מקומית מהימנה עם חותמת לפני אימות או חקירת זמן ריצה, ואז דורש אימות ניהול. זה מחזיר רק גרסאות FFmpeg/ffprobe זמינות ומסוננות, וסיבה קבועה כאשר זמן הריצה אינו זמין. נקודת הקצה הפנימית להפקה אינה API להעלאת ציבורית: רוויה בתור מחזירה `503` בנוסף ל-`Retry-After`, ניתוק של המתקשר מחזיר `499`, ומועד הסיום הקבוע של הברוקר מחזיר `504`. תגובות מומרות מוסיפות `video->text;model=<visionModel>;parts=<videos>` לכותרת המרכזית `x-omniroute-modality-bridge` מבלי להסיר את קטעי הוויז'ן או האודיו.

### מסנן PII (`piiMasker.ts`)

פועל על **שני** השלבים.

- **`preCall`** משכפל את העומס, עובר על `system`, `messages`, `input`, ו-`prompt` (כולל פריטי מיתר טקסט פשוטים), ומיישם `processPII()` (מ-`@/shared/utils/inputSanitizer`) על שדות הטקסט/תוכן. כאשר `PII_REDACTION_ENABLED=true`, PII שזוהה נמחק בעומס היוצא. זה עצמאי מ-`INPUT_SANITIZER_MODE` (ששולט רק במדיניות הזרקת הפקודה). כאשר ההסרה כבויה, השיחה רושמת ספירות זיהוי מבלי לכתוב מחדש את התוכן.
- **`postCall`** משכפל את התגובה לעמק, מפעיל `sanitizePIIResponse()` בנוסף למסנן צורת ה-Responses-API (`maskResponsesOutput` — מכסה את `output_text` ו-`output[].content[].text`). אם מתרחשת כל הסרה, התגובה המותאמת מחליפה את המקורית.

המסילה לעולם לא חוסמת; היא רק מסמנת (`meta.detections`, `meta.redacted`) או כותבת מחדש.

### הזרקת פקודות (`promptInjection.ts`)

מגלה מבנים עוינים בתוכן שסופק על ידי המשתמש ומאכף את המדיניות המוגדרת. ההתנהגות מונעת על ידי משתני סביבה ואופציות קונסטרוקטור:

| הגדרה    | משתנה סביבה                                                                                           | ברירת מחדל | השפעה                                                                                                                                                                |
| -------- | ----------------------------------------------------------------------------------------------------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| מופעל    | `INPUT_SANITIZER_ENABLED`                                                                             | `true`     | כאשר `false`, הגדרות השמירה מקצרות את התהליך.                                                                                                                        |
| מצב      | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`     | מדיניות הזרקה: `block`, `warn`, או `log`. (`redact` מתקבל עבור תאימות לאחור אך **לא** מסיר טקסט הזרקה; בקשת כתיבה מחדש של PII נשלטת על ידי `PII_REDACTION_ENABLED`.) |
| סף חסימה | אפשרות `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (כינוי `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`     | מינימום החומרה הנדרשת לחסימה. חומרה בינונית היא רק לצפייה כברירת מחדל.                                                                                               |

`INJECTION_GUARD_MODE` **החלפת דגל תכונה** (לוח בקרה → הגדרות →
דגלי תכונה) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. לכן, החלפה בלוח הבקרה מנצחת על פני משתני הסביבה, כך ש-UI דגלי התכונה שולטת על השמירה בזמן אמת (ללא הפסקה). קריאת ה-DB היא בטוחה: אם היא נכשלת, השמירה חוזרת להתנהגות מבוססת סביבה, וכאשר אין החלפה, ההתנהגות זהה לפתרון מבוסס סביבה בלבד.

מקורות זיהוי:

1. `sanitizeRequest()` מ- `@/shared/utils/inputSanitizer` (סט מגלה משותף
   שמשמש במקומות אחרים בצינור).
2. `DEFAULT_GUARD_PATTERNS` המובנה (נוכחי `system_override_inline` ו
   `markdown_system_block`, שניהם ברמת חומרה `high`).
3. `customPatterns` אופציונליים המועברים דרך אפשרויות הקונסטרוקטור (מחרוזות, regex,
   או `{ name, pattern, severity }` רשומות).

כאשר `mode === "block"` **וגם** לפחות זיהוי אחד עומד בסף החומרה,
`preCall` מחזיר `{ block: true, message: "Request rejected:
suspicious content detected" }`. במצבי `warn`/`log` השמירה רושמת אך
מאפשרת את הקריאה. העוזר המשותף `evaluatePromptInjection()` גם מיוצא
לקרואים שצריכים להעריך פקודות מבלי לעבור דרך הרישום.

**סורק גבול (v3.8.20):** המגלה בודק רק את **16 KB הראשונים** של
טקסט הפקודה המאוחד — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 בתים) ב
`src/shared/utils/inputSanitizer.ts`. גם `detectInjection()` וגם
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` לפני הרצת
לולאת התבנית. הנחיות הזרקה נמצאות קרוב לחלק העליון של קלט, כך שזה
מגביל את ה-CPU/GC של regex על משקלים של מאות קילובייט מבלי להחליש את הזיהוי (השווה ל
#3932, #4041).

### מסנן אישורים (`credentialMasker.ts`)

פועל על **שני** השלבים, אחרון בשרשרת ברירת המחדל (עדיפות `95`). מסיר
תבניות מפתח API / סוד מוכרות מהמשקל החיצוני (תוכן ההודעה, ארגומנטים של קריאות כלים, תוצאות כלים) **וגם** את תגובת הספק, כך שאישור שהודבק לפקודה (או הושלך חזרה על ידי תוצאת כלי) לא דולף
לספק העל או חזרה ללקוח.

- **רק בהסכמה**, אותה קונבנציה כמו הסרת PII (כלל קשה #20-סמוך):
  מושבת אלא אם `settings.credentialRedactionEnabled === true` **או**
  `CREDENTIAL_REDACTION_ENABLED=true`. כאשר זה כבוי, השמירה היא לא-פעולה —
  היא אף פעם לא חוסמת ואינה כותבת מחדש.
- `redactCredentials()` עובר על כל עץ המשקל/תגובה (`walkValue()`,
  בטוח מפני זיהום פרוטוטיפ, בטוח ממעגלים דרך `WeakSet`) ומחליף התאמות עם
  מקום מחזיק `[REDACTED:<type>]`, משכפל רק את הענפים ששונו בפועל.
- `CREDENTIAL_PATTERNS` מכסה מפתחות ספק LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), טוקנים של VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), מפתחות תשלום (Stripe, Square), מפתחות ענן (מפתח גישה AWS, Twilio, SendGrid, Mailgun), מפתחות פרטיים / JWTs,
  מחרוזות חיבור נושאות אישורים (`mongodb://user:pass@...`, וכו'), ודפוס ערך כותרת גנרי `Authorization`/`x-api-key`/`api-key`/`apikey`.
  מפתחות בצורת כותרת (`authorization`, `x-api-key`, `api-key`,
  `apikey`) מוסרים באופן מבני (רק ערך, קידומת סכימה כמו
  `Bearer `/`Basic ` נשמרת) ולא דרך regex טקסט גנרי.
- השמירה אף פעם לא חוסמת; היא רק כותבת מחדש (`modifiedPayload` /
  `modifiedResponse`) ומסמנת (`meta.credentialsRedacted`, `meta.count`).

שמירת רגרסיה: `tests/unit/credential-masker-guardrail.test.ts`.

## חוזה בסיס (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true עוצר מיד את השרשרת
  message?: string; // מוצג בעת חסימה
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // מוחזר על ידי preCall כדי לשכתב את הבקשה
  modifiedResponse?: TValue; // מוחזר על ידי postCall כדי לשכתב את התגובה
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

מנגנון הגנה מסמן "ללא שינוי" באמצעות החזרת `void`, `{}`, או
`{ block: false }`. החזרת `modifiedPayload`/`modifiedResponse` מחליפה
את הערך שזורם בשרשרת עבור מנגנוני ההגנה שבהמשך.
`signal?: AbortSignal` מעביר אל מנגנוני ההגנה את מחזור החיים של הקורא. ביטול בקשה הוא החרגת fail-open מכוונת: גשרי מדיה מפסיקים את העבודה ומבצעים ניקוי מבלי לשחזר מדיה גולמית ליעד שידוע כי אינו תומך בה.

## מרשם (`registry.ts`)

היחידון `guardrailRegistry` חושף:

- `register(guardrail)` — מוסיף מנגנון הגנה (או מחליף לפי שם מנורמל) וממיין
  מחדש לפי `priority` בסדר עולה.
- `clear()` / `list()` — כלי עזר ניהוליים.
- `runPreCallHooks(payload, context)` — עובר על מנגנוני ההגנה הפעילים, מעביר את
  המטען דרך `modifiedPayload`, ועוצר ב-`block: true` הראשון.
- `runPostCallHooks(response, context)` — אותה זרימה בצד התגובה.
- `resetGuardrailsForTests({ registerDefaults })` — מנקה את המצב, ולפי הצורך
  רושם מחדש את ברירות המחדל לצורך בידוד נקי של בדיקות.

שני המריצים מחזירים `{ blocked, payload|response, results, guardrail?, message? }`
כאשר `results` הוא מערך של רשומות `GuardrailExecutionResult` הכוללות
את השדות `blocked`, `skipped`, `modified`, `error` ו-`meta` לכל מנגנון הגנה,
ושימושיות למעקב.

### השבתת מנגנוני הגנה לכל בקשה

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` אוסף רשימה
ללא כפילויות של שמות מנגנוני הגנה שיש לדלג עליהם עבור הבקשה הנוכחית.
המקורות (כולם אופציונליים וכולם ממוזגים):

- `apiKeyInfo.disabledGuardrails`
- `disabledGuardrails` בגוף הבקשה (ברמה העליונה)
- `metadata.disabledGuardrails` בגוף הבקשה
- הכותרת `x-omniroute-disabled-guardrails` (או הכותרת הישנה
  `x-disabled-guardrails`)

הערכים יכולים להיות מערכי מחרוזות או מחרוזת מופרדת בפסיקים; השמות
מנורמלים ל-kebab-case באותיות קטנות (`pii_masker` → `pii-masker`). התוצאה
מועברת דרך `context.disabledGuardrails` אל המרשם, שמדלג על
מנגנוני הגנה תואמים (`skipped: true` בתוך `results`).

## סדר הביצוע

עבור כל בקשה שעוברת דרך `src/sse/handlers/chat.ts` ודרך
`open-sse/handlers/chatCore.ts`:

1. `resolveDisabledGuardrails(...)` בונה את רשימת הדילוג ממפתח ה-API, מגוף הבקשה
   ומהכותרות.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` מפעיל את מנגנוני ההגנה לפי סדר
   עדיפויות עולה:
   - מנגנוני הגנה מושבתים מתועדים כ-`skipped`.
   - ה-`preCall` של כל מנגנון הגנה עשוי לשכתב את המטען באמצעות `modifiedPayload`.
   - המופע הראשון של `block: true` עוצר את השרשרת, וה-handler מחזיר
     תגובת דחייה של מנגנון ההגנה.
3. המטען (שייתכן ששוכתב) מועבר לניתוב משולב ולשליחה לשירות שבמעלה הזרם.
4. לאחר הרכבת התגובה, `guardrailRegistry.runPostCallHooks(...)`
   מפעיל את אותה שרשרת על התגובה. `block: true` בשלב זה מבטל את התגובה
   משירות מעלה הזרם.

מנגנוני הגנה שזורקים חריגה מתועדים עם `error: <message>` ונרשמים ביומן באמצעות
`logger.warn`, אך השרשרת ממשיכה — זהו תכנון מסוג fail-open.

## תצורה

משתני סביבה שנקראים על ידי מנגנוני ההגנה המובנים:

| משתנה                                 | בשימוש על ידי             | השפעה                                                                                    |
| ------------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | יש להגדיר `false` כדי להשבית לחלוטין את הזיהוי.                                          |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`        | מדיניות הזרקה: `warn`,‏ `block` או `log`. הערך הישן `redact` אינו משכתב טקסט של הזרקה.   |
| `INJECTION_GUARD_MODE`                | `prompt-injection`        | מצב מגן ההזרקה; משמש גם כדגל תכונה במסד הנתונים אשר **דורס** את משתני הסביבה (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`        | רמת החומרה המזערית שאותה `MODE=block` דוחה: `high` (ברירת המחדל), `medium` או `low`.     |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`        | כינוי ישן עבור `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                        |
| `PII_REDACTION_ENABLED`               | `pii-masker`              | כאשר הערך הוא `true`, מידע אישי מזהה בבקשה מושחר (ללא תלות במצב ההזרקה).                 |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (במורד הזרם) | שולט בהתנהגות המיסוך בצד התגובה.                                                         |

מנגנוני ההגנה של Modality Bridge קוראים את תצורת זמן הריצה ממאגר ההגדרות
המגובה במסד הנתונים (`getSettings()`), ולא ממשתני סביבה. המפתחות הראשיים של Vision הם
`modalityBridgeVisionEnabled`,‏ `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`,‏ `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`,‏ `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`,‏ `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`,‏ `modalityBridgeCacheTtlMinutes` ו-
`modalityBridgeCacheMaxEntries`. המפתחות הישנים
`visionBridge*` מתקבלים רק כמנגנון הגיבוי המתועד לקריאה במחזור אחד;
כתיבות מלוח הבקרה משתמשות במפתחות הראשיים. ברירות המחדל ופותר מנגנון הגיבוי
נמצאים ב-`src/shared/constants/modalityBridgeDefaults.ts`, בעוד שהקבועים הישנים
נשמרים ב-`src/shared/constants/visionBridgeDefaults.ts`.

אודיו משתמש ב-`modalityBridgeAudioEnabled`,‏ `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` וב-`modalityBridgeAudioMaxClips`, יחד עם הגדרות
`modalityBridgeCache*` המשותפות. לאודיו אין מנגנון גיבוי למפתחות ישנים, משום
שמפתחות אלה הוצגו יחד עם הסכימה של Modality Bridge.

וידאו משתמש ב-`modalityBridgeVideoEnabled`,‏ `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`,‏ `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` וב-
`modalityBridgeVideoTimeout`, יחד עם הגדרות `modalityBridgeCache*` המשותפות.
הוא מושבת כברירת מחדל משום ש-FFmpeg/ffprobe הם תלויות תפעוליות אופציונליות,
והוספת כיתובים לפריימים מגדילה את זמן ההשהיה ואת עלות המודל.

## מנגנוני הגנה מותאמים אישית

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

שלבים:

1. צרו את `src/lib/guardrails/myGuardrail.ts` כך שירחיב את `BaseGuardrail`.
2. ממשו את `preCall` ו/או את `postCall`.
3. בצעו רישום בזמן הייבוא (הוספה מתוך `registerDefaultGuardrails`) או
   קראו ל-`guardrailRegistry.register(...)` בזמן ריצה — הרישום מחליף
   כל מנגנון הגנה קודם בעל אותו שם מנורמל.
4. הוסיפו בדיקות תחת `tests/unit/` (דוגמאות קיימות:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## בדיקות

השתמשו ב-`resetGuardrailsForTests()` בין הבדיקות כדי להתחיל ממצב ידוע.

## כיסוי נתיבים ובדיקות צוות אדום למנגנון ההגנה מפני הזרקה (שלב 8 · בלוק D)

מנגנון ההגנה מפני הזרקה (`createInjectionGuard` / `withInjectionGuard`) מכסה את כל הנתיבים
שמקבלים הנחיות משתמש. הוא מכבד את `INJECTION_GUARD_MODE` (ברירת המחדל `warn` = רישום בלבד;
`block` = החזרת HTTP 400 עם `SECURITY_001`).

| סוג         | נתיבים                                                                                                                                               | מצב ברירת מחדל |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| טקסט (קיים) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn           |
| יצירתי      | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn           |
| נתונים      | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn           |

חילוץ טקסט (`extractMessageContents`) מכסה את `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**צוות אדום (מדי לילה, `nightly-llm-security.yml`):** ‏promptfoo מאמת שכל נתיב חוסם
את קורפוס OWASP-LLM כאשר `INJECTION_GUARD_MODE=block`; ‏garak מריץ בדיקות חדירה (ומדלג ללא סוד).
`moderations` נכלל למען העקביות — מפעילים במצב חסימה יכולים להחריג אותו באמצעות
`resolveDisabledGuardrails`.

תהליך העבודה הלילי (`.github/workflows/nightly-llm-security.yml`, ‏cron + הפעלה ידנית)
כולל שתי משימות:

- **`promptfoo-guard` (חוסמת)** — מריצה את `promptfoo eval -c promptfooconfig.yaml`
  עם `INJECTION_GUARD_MODE=block`. כל מקרה עוין (למשל "התעלם מכל
  ההוראות הקודמות…", פריצות בסגנון DAN) מוודא שהתשובה מכילה
  `error.code === "SECURITY_001"`, כלומר שמנגנון ההגנה אכן דחה את הבקשה.
- **`garak` (מייעצת)** — מריצה את garak עם `--probes promptinject,dan,leakreplay`
  מול מופע OmniRoute מקומי (`http://localhost:20128/v1`). ההרצה מותנית בסוד
  של ספק (`PROMPTFOO_PROVIDER_KEY`); היא מדלגת בצורה תקינה בהיעדרו ומסתיימת בסיומת
  `|| true`, כך שהיא מדווחת מבלי להכשיל את CI.

הכיסוי של פונקציית העזר של מנגנון ההגנה (`createInjectionGuard` / `withInjectionGuard`)
