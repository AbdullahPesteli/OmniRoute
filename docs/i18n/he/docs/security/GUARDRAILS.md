> **מקור האמת:** `src/lib/guardrails/`
> **עדכון אחרון:** 2026-08-29 — v3.8.51 (מקור התמליל של Video Bridge מוצהר על ידי הקורא,
> ועדיין אינו מאומת על ידי השרת — הובהר בהתאם ל-#11661)

מנגנוני הגנה אוכפים בטיחות, מדיניות והתמרות תוכן בגבול
שבין OmniRoute לספקים במעלה הזרם. כל מנגנון הגנה יכול לבדוק (ובאופן
אופציונלי לדחות, להתמיר או להוסיף הערות אל) מטעני בקשות (`preCall`) ותגובות
במעלה הזרם (`postCall`).

המערכת פועלת בגישת **fail-open**: אם מנגנון הגנה זורק חריגה במהלך הביצוע, הרישום
מתעד את השגיאה וממשיך למנגנון ההגנה הבא במקום להכשיל את
הבקשה. חסימה היא החלטה מפורשת (`block: true`), ולעולם אינה מתרחשת בטעות.

## מגני הגנה מובנים

הרשימה טוענת אוטומטית שישה מגני הגנה בסדר עדיפויות בעת ייבוא
(ראה `registry.ts` → `registerDefaultGuardrails()`):

| עדיפות | שם                  | שלב(ים)        | קובץ                  |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

מספרי עדיפות נמוכים יותר פועלים **ראשונים**.

### גשר הראייה (`visionBridge.ts`) — גשר מודל PR-1

מנטרל בקשות נושאות תמונה המיועדות ל**מודלים שאינם ראייה** ומבצע
אחת משתי פעולות: מפנה את הבקשה כולה למודל תומך ראייה או מחליף את חלקי התמונה
בתיאורי טקסט המיוצרים על ידי מודל ראייה שניתן להגדיר לפני הקריאה העליונה. זה מאפשר לספקי טקסט בלבד לטפל בצורה שקופה
במטענים רב-מודליים.

זרימה:

1. דלג אם המודל המיועד כבר תומך בראייה (אלא אם הוא מופיע ברשימת הגשרים הכפויים `isVisionBridgeForcedModel`).
2. חילוץ חלקי תמונה באמצעות `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), המפנה ל**מגלה מדיה מאוחד**
   `detectMediaParts()` ב`open-sse/utils/mediaParts.ts` — המקור האחד והיחיד של אמת המשותף עם מסנן התאמה משולב.
   החילוץ מותנה בחלקים ברמה עליונה של הצורות
   `replaceImageParts` יכול לחבר חזרה (החוזה extract↔replace): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, ו-Responses API `input_image`. פגיעות מקוננות וצורות רק אינדיקטור הן חומר למסנן משולב ואינן נחלצות לעולם.
   דלג אם לא נמצא דבר.
3. פותר הגדרות בזמן ריצה באמצעות `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): מפתחות הגדרות חדשים `modalityBridge*`
   מנצחים; מפתחות ישנים `visionBridge*` נשארים **גיבוי של מחזור אחד**
   (חלון חזרה). דלג לפני כל מעבר מדיה כאשר הגשר מושבת.
4. בורר מצב (`modalityBridgeVisionMode`, ראה טבלה למטה) מחליט
   אם להפנות או לתאר. הפניה מחזירה `modifiedPayload` עם רק `model`
   מוחלף, בנוסף למטה `{ rerouted, fromModel, toModel, imagesKept }`.
5. מסלול תיאור: מגביל תמונות ל`maxImages`, מרכיב את ההנחיה המודעת למשימה,
   מתייעץ עם מטמון התיאור, קורא למודל הראייה **במקביל**
   (`Promise.allSettled`), ומזריק חלקי טקסט `[Image N]: <description>` במקומם. תיאור שנכשל מחזיר `null` וחלק התמונה המקורי
   **שמור** (#4012) — למעט במסלול התיאור המשולב כאשר כל
   התיאורים נכשלו, שם מקור עליון שאינו תומך בראייה מקבל
   `(unavailable — no vision-capable provider connected)` במקום (#8430).
6. מחזיר `modifiedPayload` + מטה (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### בורר מצב (`modalityBridgeVisionMode`)

| מצב        | ברירת מחדל | התנהגות                                                                                                                                                                                   |
| ---------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔          | היסק ישן, לא נגעו (#6640/#7204): מודלים שאינם משולבים/`auto/` מפנים למודל הראייה הטוב ביותר אלא אם המודל המקורי כבר יש לו אישורים שימושיים (אז מתאר); מטרות משולבות תמיד מתארות.          |
| `describe` |            | תמיד מתאר — בלוק ההפניה מדולג לחלוטין; המודל הנבחר של המשתמש תמיד עונה.                                                                                                                   |
| `reroute`  |            | הפניה כפויה: שומר המודל עם אישורים נשמר. שומר האישור של יעד ההפניה עדיין חל — כאשר אין יעד ראייה שימושי, הבקשה נופלת לתיאור כך שהתמונות הגולמיות לעולם לא מגיעות לאחור טקסט בלבד (#8430). |

מצבים כפויים מקצרים **לפני** שההיסק האוטומטי פועל; התנהגות `auto`
זהה בתכלית למגן ההגנה לפני PR-1.

#### טווח מפתח API (`visionBridgeKeyScope.ts`)

כאשר מפתח ה-API של המתקשר מגביל `allowedConnections`, בריכות מכסה
(`allowedQuotas`) או מודלים (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), הגשר בוחר רק
מודלים להפניה ולתיאור שהמפתח יכול להשתמש בהם, על חיבורים שהמפתח יכול
להשתמש בהם. הקריאה לתיאור אז תמיד עוברת דרך הלולאת עצמית של OmniRoute עם
הכותרת `x-omniroute-self-loop-key-id`, כך שבקשת הצ'אט המתקבלת
אוכפת שוב את מדיניות החיבור והמודל של המפתח הזה. `enforceApiKeyPolicy()`
מכבדת את הכותרת הזו רק יחד עם נושאת הלולאה העצמית, כך שהיא יכולה רק
להצמצם גישה, ומזהה שאינה נפתרת נדחית.

אם אין מודל ראייה מותר עבור המפתח, מסלול התיאור מתרחק
והבקשה עוברת ללא שינוי, אותה התנהגות פתוחה כמו מגן הגנה מושבת (מטה `{ skipped: true, reason: "no_permitted_vision_model" }`).
בקשות ללא מפתח, ומפתחות ללא הגבלות אלו, מתנהגות בדיוק כמו קודם.

#### הנחיית תיאור מודעת למשימה (`modalityBridgeVisionTaskAware`)

ברירת מחדל **נכון**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) מוסיף
את הטקסט של **הודעת המשתמש האחרונה** (מקוצרת ל-500 תווים) לבסיס
ההנחיה לתיאור, מכוון את התיאור למה שהמשתמש באמת שאל
(דפוס codex-vision-proxy) ושואל את מודל הוויז'ן לתמלל טקסטים נראים. עם הדגל כבוי — או ללא טקסט משתמש — ההנחיה הבסיסית משמשת ללא שינוי.

הבקשה של הלולאת תיאור עצמית תואמת OpenAI (`callVisionModelSingle()`
ב-`visionBridgeHelpers.ts`) תמיד מבקשת `image_url.detail: "high"` —
ללא תנאים, עבור כל קורא/ספק, לא מוגבלת על ידי שום אות לקוח.
דגימה ברזולוציה נמוכה פוגעת בדיוק ה-OCR למשימת תמלול הטקסט בדיוק
שלה הנחיה זו מבקשת, כך שהקריאה לתיאור עצמה תמיד מבקשת רזולוציה גבוהה
בלא קשר לרמת הרזולוציה שהבקשה המקורית השתמשה בה. זה משפיע רק על גוף הבקשה הפנימית לתיאור; זה לא משנה איך
OmniRoute מעביר את `image_url.detail` של הקורא בבקשה הראשית —
ברירת המחדל מוחלת בנפרד, ורק עבור לקוחות OpenCode מזוהים, ב-
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`).
הסניף של פורמט החוט של Anthropic של הלולאת תיאור עצמית אין לו שדה `detail`
ואינו מושפע מאף ברירת מחדל.

#### מגבלת פלט תיאור (`modalityBridgeVisionMaxChars`)

| מפתח                           | ברירת מחדל | טווח             |
| ------------------------------ | ---------- | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`        | `0` או 100–50000 |

`0` (ברירת מחדל) פירושו **אין מגבלה** — התיאור המוחזר על ידי
`callVisionModel()` מועבר ללא שינוי, שומר על ההתנהגות הקיימת. כל ערך בטווח 100–50000 מקצר את התיאור עם סיומת
`…` לפני שהוא מחובר מחדש כ-`[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` ב-`src/lib/guardrails/visionBridge.ts`).
הגדל זאת עבור משימות OCR כבדות בפרטים שבהן המודל downstream זקוק
לתמלול המלא; הקטן זאת כדי להגביל את השימוש בטוקנים על מודלים ויזואליים מדברים.
שדה הלוח נמצא בלשונית Vision בלוח מתקדם
(`modality-bridge-max-chars` ב-`ModalityBridgeVisionTab.tsx`) ומגביל כל
ערך בין 1 ל-99 עד לרצפה של 100 תוך השארת `0` מפורש ללא שינוי — `0` הוא ערך Zod תקף בזכות עצמו
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), לא רק
ברירת המחדל "לא הוגדרה".

#### מטמון תיאור (`modalityBridge/bridgeCache.ts`)

מטמון LRU + TTL בזיכרון עבור פלטי תיאור, משותף על פני התהליך.
מפתח = `sha256(imageRef + composedPrompt + configuredBridgeModel)` עם
מסגרת באורך-קידומת (ללא התנגשויות גבול שדה). רכיב המודל הוא
המודל **המוגדר** של הגשר, לא המודל שענה בפועל —
`callVisionModel` עשוי ליפול חזרה פנימית, ומפתח לפי ניסיון היה
שובר את המטמון. תיאורים שנכשלו אינם נשמרים במטמון. הגדרות:

| מפתח                            | ברירת מחדל | טווח    |
| ------------------------------- | ---------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`     | —       |
| `modalityBridgeCacheTtlMinutes` | `60`       | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`      | 10–5000 |

#### נורמליזציה של תמונות מרוחקות (לולאת תיאור/משיכת base64)

כאשר הגשר מושך תמונה **מרוחקת** בעצמו — הקריאה העצמית של תיאור
Anthropic והמרת base64 בפורמט claude-wire
(`ensureBase64ImagesForClaudeWire`), שניהם דרך
`fetchRemoteImageAsDataUri()` ב-`visionBridgeHelpers.ts` — ה-URI הנתונים
המתקבל מועבר דרך `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) לפני שהוא מוטמע בבקשת מודל הוויז'ן. תמונות גדולות מדי מצומצמות לגובה **2048px** (תואם
למגבלת השינוי ש-OpenAI/Anthropic כבר מיישמים בצד השרת), מה שמפחית
בייטים/שהות העלאה מבלי לשנות מה שמודל הוויז'ן רואה. שינוי גודל
משתמש ב-`sharp`, שנמצא דרך ייבוא דינמי: על פלטפורמה שבה הבינארי
המקורי שלו נכשל לטעון, `normalizeDataUri()` **אף פעם לא זורק** — הוא נופל חזרה
למעבר של הבייטים המקוריים, כך שהמסלול לתיאור/המרת base64
תמיד נשאר פועל. בייטים שאינם תמונה (משיכה שלא החזירה תמונה
ניתנת לפענוח) מועברים גם הם ללא שינוי. נורמליזציה זו מוגבלת לתמונות שהגשר מושך עבור הקריאה העצמית שלו — היא אף פעם לא
מוחלת על העברת הגולמית של הקורא, בהתאם לעקרון המוטציה רק באופציה (כלל קשה #20).

#### סכמת הגדרות + הגירה

המפתחות החדשים `modalityBridge*` מאומתים על ידי Zod ב-`updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, השלישייה של `modalityBridgeCache*`, והקבוצה
`modalityBridgeAudio*` שמשתמשת בגשר האודיו. ההגירה
`141_modality_bridge_settings.sql` מעתיקה ערכים קיימים של `visionBridge*` למפתחות החדשים המתאימים (אידמפוטנטי, אף פעם לא מוחק
ערך `modalityBridge*` שהוגדר על ידי מפעיל); המפתחות הישנים נשארים מקובלים כהחזרה לקריאה במשך מחזור שחרור אחד.

#### כותרת שקיפות + סטטיסטיקות

תגובות שהוסבו על ידי תיאור נושאות
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(נבנה על ידי `buildModalityBridgeHeader()` ב-`modalityBridge/bridgeStats.ts`,
נחתם על ידי `withModalityBridgeHeader()` ב-`src/sse/handlers/chatHelpers.ts`).
בקשות שהופנו מחדש אינן מקבלות **כותרת** — העברת הנתונים לא השתנתה והחלפת המודל
כבר נראית בשדה `model` של גוף התגובה.

`GET /api/modality-bridge/stats` (אימות ניהול, באותו רמה כמו
`GET /api/settings`) מחזיר את המונים בזיכרון לפי מודל
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` עבור `vision`, `audio`, ו
`video`. `averageLatencyMs` משתמש ב`latencySamples`, ולא בכל הניסיונות, כ
מחלק; פעולה ללא תזמון אינה מייצרת דגימה של אפס מילישניות. `bridged` נשאר
הכינוי התואם לאחור עבור המרות מוצלחות; ניסיונות כושלים אינם מגדילים אותו.
המונים מתאפסים עם אתחול התהליך בעיצוב
(טלמטריה, לא חשבונאות).

#### הגדרת לוח מחוונים

דף הלוח מחוונים המוקדש הוא
`/dashboard/settings/modality-bridge`. הכתובת URL שלו `Vision`, `Audio`,
ו`Video` שומרת על פרמטרי השאילתה בזמן החלפת ערך ה`tab`.
הלשונית Vision חושפת הפעלה, מצב, בחירת מודל (כולל ברירת המחדל האוטומטית),
הנחיות מודעות למשימות, מגבלות מתקדמות על זמן/תמונה/אורך תיאור/מטמון,
מונים בזמן ריצה, ובקשת דגימה מוגנת. הלשונית Audio גם חיה: היא חושפת
הפעלה, בורר מודל STT בלבד עם Auto, מגבלות זמן/מקסימום קליפ, מונים
אודיו, ובדיקת דגימה `input_audio`. הלשונית Video פעילה: היא מדווחת
על מצב הריצה של FFmpeg/ffprobe — אחד מארבעה מצבי UI מפורשים (`unknown` בזמן
שהחיפוש באוויר או לא הצליח להושלם, `restricted` על מארח לוח מחוונים שאינו
לולאת חזרה שבו החיפוש מדלג בצד הלקוח, `unavailable` לאחר חיפוש ואישור
שחסר, או `available` עם גרסאות FFmpeg/ffprobe) — שומרת על מגבלות enable/model/frame/video/timeout,
מסננת את בורר המודל למודלים בעלי יכולת ראייה, ומחפשת מונים של וידאו.

הכרטיס הקודם של Vision Bridge תחת הגדרות AI הוא קישור תאימות לדף החדש;
כבר אין לו עותק שני של הטופס. ספקי מדיה גם מקשרים את זרימות העבודה
Image-to-Text וSpeech-to-Text ללשוניות Modality Bridge המתאימות מבלי להסיר
את מגרש המשחקים הקיים Speech-to-Text.

**עקיפת קבלת לולאת עצמית:** כאשר קריאת התיאור מנותבת דרך הלולאת
העצמית של OmniRoute `/v1` (מודל ספק לא סטנדרטי), הבקשה המשנית שולחת
`x-omniroute-admission-bypass: internal` ומאומתת עם האישור שנפתר
של הלולאה העצמית — ה`sk_omniroute` המקומי במצב מקומי, או המפתח
המאומת `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350) כך
שפריסות `REQUIRE_API_KEY=true` יכולות עדיין להריץ את קריאת התיאור. העקיפה
מכובדת רק עבור אותם אישורים מדויקים, כך שלקוחות חיצוניים אינם יכולים
להשתמש בכותרת כדי לדלג על קבלה.

ברירות המחדל הישנות נמצאות ב`src/shared/constants/visionBridgeDefaults.ts`;
ברירות המחדל החדשות המודעות למשימות/מטמון והפתרון הגדרות נמצאות ב
`src/shared/constants/modalityBridgeDefaults.ts`. המדריך חושף אפשרות
`deps` בבנאי כך שהבדיקות יכולות להזריק יישומים מזויפים של `getSettings` ו
`callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

חוסם בקשות צ'אט נושאות אודיו לפני שהן מגיעות ליעד שאינו ידוע
כמקבל קלט אודיו. הוא אף פעם לא מנתב מחדש את בקשת הצ'אט: חלקי האודיו
מועתקים דרך נקודת הקצה הקיימת התואמת ל-OpenAI ומודל הצ'אט הנבחר
ממשיך עם תמלילים טקסטואליים.

זרימה:

1. פותר `supportsAudio` דרך `getResolvedModelCapabilities()`. מטא-נתונים
   של רישום ספק מפורש מנצחים, ואז מטא-נתונים של מודל סטטי, ואז
   `modalities_input` מסונכרנים. רשימת קלט שהוכרזה ללא `audio` היא `false`;
   אין ראיות יכולת נשארות `null`. גם `false` וגם `null` מפעילים את
   הגשר השמרני, בעוד ש`true` עוקף אותו.
2. פותר הגדרות `modalityBridgeAudio*` ומוציא חלקי אודיו ברמה עליונה
   שניתן לחתוך מכל הודעה דרך המגלה המשותף `detectMediaParts()`.
   צורות חוט נתמכות הן OpenAI `input_audio`, `audio_url`, ו
   `source.media_type: "audio/*"`. אודיו מקונן מזוהה לניתוב אך לא
   מוסר על ידי מסלול החיתוך. העבודה מוגבלת על ידי `modalityBridgeAudioMaxClips`;
   חלקים מאוחרים נשארים ללא שינוי.
3. מכבד `provider/model` שהוגדר, או נותן ל`selectAudioBridgeModel()`
   לעבור על `AUDIO_TRANSCRIPTION_PROVIDERS` בסדר קטלוג יציב ולבחור את המודל
   הראשון עם אישור ספק פעיל שניתן להשתמש בו.
4. `callAudioTranscription()` ממיר אודיו ב-base64/data-URI לקובץ
   multipart, או מוריד `audio_url` מרוחק דרך המגן החיצוני בלבד עם
   נעילת DNS ומגבלה של 25 MB. לאחר מכן הוא POST את הקובץ ואת המודל הנבחר
   ללולאת `/v1/audio/transcriptions` המקומית, מאומת עם
   `resolveSelfLoopBearer()`. מסלול התמלול הקיים מבצע חיפוש רגיל
   של אישורים, טיפול בקירור/מגבלת קצב, והפצת ספקים.
5. קריאות מוצלחות מחליפות את חלקיהן ב`[Audio N]: <transcript>`. קריאות
   רצות עם `Promise.allSettled`: כישלון בודד שומר על חלק האודיו המקורי
   (#4012 contract). אם כל קריאה נכשלת והיעד הוכח כ`supportsAudio === false`,
   החלקים הופכים ל
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 contract). עבור
   יעד לא ידוע (`null`), תוצאה של כישלון מוחלט נשארת ללא שינוי. יעד
   שהוכח כטקסט בלבד ללא אישור STT שניתן להשתמש בו מקבל את אותו
   דגם מפורש מבלי להוציא קריאת רשת.

תמלולים מוצלחים משתמשים במטמון LRU/TTL של Modality Bridge ברמת התהליך. המפתח
משלב את הפניה לאודיו, את תווית הפעולה היציבה `audio-transcription`, ואת מודל ה-STT הנבחר;
כישלונות לעולם אינם נשמרים במטמון. ניסיונות אודיו מעדכנים את המונים המשותפים
`bridged`, `cacheHits`, `failures`, ו`lastUsedAt`.
תגובות שהומרו נושאות
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; בקשות שלא
נגעו לא מקבלות קטע Audio Bridge.

הגדרות בזמן ריצה מגובות DB ומאומתות על ידי Zod:

| מפתח                          | ברירת מחדל | טווח           |
| ----------------------------- | ---------- | -------------- |
| `modalityBridgeAudioEnabled`  | `true`     | —              |
| `modalityBridgeAudioModel`    | `""`       | Auto או STT ID |
| `modalityBridgeAudioTimeout`  | `60000`    | 1000–300000    |
| `modalityBridgeAudioMaxClips` | `3`        | 1–10           |

המטמון המשותף נשאר תחת שליטה של `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, ו-`modalityBridgeCacheMaxEntries`.

### גשר וידאו (`videoBridge.ts`, `videoBridgePipeline.ts`)

חוסם חלקי וידאו ברמה העליונה בהשלמות צ'אט `messages` וב-API תגובות `input`
לפני שנקרא יעד ללא תמיכה בוידאו מקורי ידוע.
צורות נתמכות הן `input_video`, `video_url`, `video_source`, URLs של HTTPS,
ו-`data:video/*;base64,...` URI נתונים. שמות קבצים פשוטים בטקסט אינם מטופלים
כוידאו.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) אחראי על מעבר הבקשה,
בדיקת היכולת/מדיניות, אגרגציה לפי בקשה, וטעינת התגובה.
עבודה לפי וידאו — רכישה, מטמון התוצאה המלאה, תיאור רצף פריימים
(שמאחד כל תמלול אודיו שהוכרז על ידי המתקשר), ומדדים/ביטול/ניקוי לפי ניסיון —
מוסתרת מאחורי `processVideoPart` ב-`videoBridgePipeline.ts`, הנקראת פעם אחת לכל חלק וידאו בתוך הלולאה של `preCall`.
מודול זה גם מגדיר את גבולות הפורט המפורשים `VideoMediaBrokerPort`
(רכישת בתים והפקת פריימים מדוגמים), `VideoAudioTranscriptionPort`
(איחוד תמלול אודיו שהוכרז על ידי המתקשר עם הכיתובים המדוגמים), ו-`VideoDrilldownPort`
(צורת אחסון גולמית ישנה). STT ייצור ושימור פריימים
מורכבים סביב הפורט המתאר דרך `createVideoSttAdapter` ו-`createVideoDrilldownAdapter`; האחרון משתמש בלוח מחזור ידני משותף.

נתיב הבקשה הציבורי `/v1` אף פעם לא מייבא או מפעיל תהליך משנה.
וידאו מרוחק מורד תחת מגבלה של 50 MiB; וידאו inline ב-base64 יש לו
מגבלה שמרנית של 36 MiB מפוענח לכל וידאו כך שהמודל/הודעות/עטיפת המסגרת
יכולים להישאר בתוך מגבלת קבלת הבקשה JSON הציבורית של 50 MiB.
אורך inline והערכות גודל מפוענח נבדקות לפני הקצאה. HTTPS
נדרש על ה-URL המרוחק הראשוני וכל הפניה מחדש, תוך שימוש בשמירה קיימת
רק לציבור עם נעילת DNS. הבתים אז חוצים את הגבול המדויק של
`POST /api/modality-bridge/video/extract`. נתיב זה הוא גם
`LOCAL_ONLY` וגם `SPAWN_CAPABLE`, מקבל רק בקשה מאומתת,
מהימנה, בלולאת חזרה, ואינו מקבל אף פעם URL, נתיב מערכת קבצים,
קובץ הרצה, או רשימת ארגומנטים. צינור גודל גוף ה-API וקורא גוף
ההדרגתית של המטפל אוכפים באופן עצמאי מגבלת קלט של 50 MiB.
התור המוגבל שלו פועל על הוצאת אחת בכל פעם, מאפשר ארבעה עבודות ממתינות, ומגביל קלט ממתין ל-100 MiB.

בתוך הברוקר, `ffprobe` קורא קובץ מקומי פרטי; רשימת הפורמטים המותרת
מחריגה פורמטים של רשימות השמעה ומניפסטים. עבור קונטיינרים מותרי MOV,
הפניות נתוני MOV חיצוניות נשארות מושבתות כברירת מחדל, והפקודה הקבועה
לא מצטרפת אליהם. גם `ffprobe` וגם `ffmpeg` משתמשים ברשימת הלבנה
של פרוטוקול `file` בלבד, חוט אחד, מערכי ארגומנטים קבועים, ללא שורת פקודה,
וקבצים נפתרים מ-`PATH`. זרמי כיסוי של תמונות מצורפות אינם
מועמדים ניתנים לניגון. כל הזרמים הניתנים לניגון חייבים לעמוד במגבלות,
ודרך ברירת המחדל המפורשת מועדפת לפני הנפילה הקטנה ביותר הקבועה.
וידאו מוגבלים ל-600 שניות, 8,192 פיקסלים לכל מימד, ו-33,554,432 פיקסלים מקוריים.
FFmpeg מדגם 1–16 פריימים JPEG באמצע, מקטין את הקצה הארוך ל-1,024 פיקסלים לכל היותר
ללא הגדלת קלטים קטנים יותר, ואינו מקבל אף פעם URL.
הדגימה היא `uniform` כברירת מחדל. המדיניות האופציונלית
`scene_aware` והניסי `segment_aware` מבצעות מעבר FFmpeg קבוע נוסף
על הזרם המקומי שכבר אומת, בוחרות חותמות זמן של סצנות `showinfo` מוגבלות,
ונופלות באופן דטרמיניסטי לאותם פריימים אחידים באמצע במקרה של כישלון של הגלאי,
פסק זמן, פלט לא תקין, או קבוצת מועמדים ריקה. מצב מודע לסגמנט מקצה דגימות
אמצע באופן פרופורציונלי לאינטרוולים של סצנה מאומתים; ראיות מודעות לסגמנט
ודפוסי נפילה מפורטים למטה. מגבלת 16 הפריימים הקשה מוחלת
אחרי הבחירה בכל מדיניות. כאשר בקשה מודעת לסצנה יש רק תקציב של פריים אחד,
היא משתמשת בנקודת האמצע האחידה של הוידאו המלא הפעיל או חלון הפוקוס
ומדווחת `policyEffective: uniform`: פריים סצנה אחד שנבחר אינו יכול לשמור
על שני הקצוות הזמניים. מתקשר יכול לספק אופציונלית חלון פוקוס סופי
(`start`/`end` שניות); גבולות מגודרים לאורך משך המדיה, חלונות הפוכים או לא סופיים נדחים,
וכל מדיניות הדגימה מתבצעת רק בתוך האינטרוול המנורמל.
חלון התוצאה כלול במטא-נתוני הדגימה ובתחילת התיאור הלא מהימן
כך שמודלים בהמשך יכולים להבחין בין קטע ממוקד לבין ציר הזמן המלא.

מיקוד בכיתוב סמנטי הוא הגדרה נפרדת ומפורשת. מצב הניתוח
ברירת המחדל `full` שומר על ההנחיה הקיימת של הפריים ואינו מעביר
טקסט בקשה למודל הכיתוב. במצב `focused`, הגשר קורא רק את
`text`/`input_text` האחרון שאינו ריק שנכתב על ידי המשתמש מאותו
מיכל צ'אט או תגובות, מנרמל אותו ל-NFC, קורס תווי בקרה ורווחים,
ומגביל אותו ל-500 נקודות קוד Unicode. תוצאה ריקה נופלת חזרה להנחיה
המדויקת `full`. רמז שניתן להשתמש בו מסודר כ-JSON בחסימה ייחודית
של הקשר משתמש לא מהימן ויכול להעדיף רק פרטים נראים; הוא
אינו יכול לבטל את האזהרה הנפרדת נגד ביצוע הוראות נראות
או נשמעות במדיה. מיקוד טקסטואלי אינו מסיק אף פעם `start`/`end`
או משנה את המדגם הזמני.

#### FU-07 ראיות סגמנט מבניות

`segment_aware` משתמש במעבר ניתוח מקדים מוגבל על זרם הווידאו המקומי שכבר אומת. שרשרת המסננים הקבועה קודם כל מקטינה לרוחב של עד 320 פיקסלים, מזהה שינויים בסצנה ובזמנים קפואים, ואז מדגימה בקצב של פריים אחד בשנייה עבור טשטוש, ממוצע לומה, ומידע מרחבי/זמני. המעבר מוגבל ל-600 דגימות מבניות, חוט FFmpeg/filter אחד, אותו פרוטוקול וקונטיינר המאפשרים קבצים בלבד, גבול פלט תהליך של 1 MiB, ובסך הכל 30 שניות בתוך הזמן המשותף של הברוקר לביטול/דדליין. הוא אף פעם לא מקבל פקודה, מסנן, נתיב או URL מהבקשה.

הערכים המבניים הם ראיות דגימה דטרמיניסטיות, לא הבנה סמנטית של ווידאו. הם לא מסיקים נושאים, פעולות, כיתובים, דיבור או כוונת משתמש. גבולות הסצנה והקפיאה יוצרים קטעים; כיסוי הקפאה, טשטוש, חשיפה, פרטים מרחביים ושינויים זמניים משפיעים רק על איך שהתקציב הקיים של 1–16 פריימים מוקצה. קטע קפוא לחלוטין מוגבל לפריים אחד, בעוד קטעים לא קפואים מתחרים על התקציב הנותר. כאשר הגבולות עולים על הפריימים, נשמר כיסוי אחיד של ציר הזמן כך שחתכים מהירים לא יכולים להסתיר קטע ארוך. גבולות סצנה בתוך רזולוציית הניתוח של שנייה אחת של גבול קפיאה מתמזגים.

מסננים חסרים, ראיות מעוותות/ריקות, שגיאת גלאי, או טיימאוט ניתוח מקדים מוגבל נכשלות לפתיחה לפי מדיניות האמצע האחיד המדויק. ביטול של מתקשר או דדליין של ברוקר לא נכשל לפתיחה: הוא מסיים את תהליך המשנה המתקדם, מונע חילוץ פריימים מאוחרים, והעץ הזמני הפרטי מוסר ב-`finally`.

`scripts/perf/video-bridge-fu07-eval.ts` מייצר מתקנים דטרמיניסטיים אמיתיים של FFmpeg לחיסכון בכיתובים לאחר דדופליקציה, הקצאת תקציב תנועה צפופה, ראיות טשטוש/חשיפה/SI-TI, חתכים מהירים עם זנב ארוך, ופולשנות שגויה בהדרגה. הוא רושם את זמן הקיר של ניתוח מקדים ובמקום שבו `/usr/bin/time` זמין, את ה-CPU של הילד ואת ה-RSS המקסימלי. בדיקות האיכות שלו הן אורקל מבני בלבד. איכות מודל הכיתוב האמיתית נשארת `HOLD` כי לחגורה הזו אין נקודת קצה מאושרת או שופט קפוא. חיסכון כספי גם נשאר `HOLD` אלא אם `--caption-cost-per-call-usd` מספק הערכה חיובית מפורשת לכל שיחה; הסקריפט אף פעם לא ממציא אף תוצאה.

כל פריים מוגבל ל-4 MiB, כל הפריימים הגולמיים יחד ל-23 MiB, ותשובת הברוקר המוסרת ל-32 MiB. תיקיה זמנית פרטית מוסרת ב-`finally`. OmniRoute לא כוללת את FFmpeg ולא מקבלת נתיב הפעלה מותאם אישית. לפני הכיתוב, הגשר מבצע מעבר דדופליקציה חזותית שמרנית: כל JPEG מצטמצם לבופר גריסקייל בגודל 16×16 ומושווה רק עם הפריים האחרון שנשמר. עבור תקציב כיתוב המבוקש מעל פריים אחד, החילוץ מספק מאגר מועמדים מוגבל של עד פי שניים מהתקציב הזה ולא יותר מ-16 פריימים. הגבול המבוקש מוחל רק לאחר דדופליקציה, עם המועמדים הנבחרים הראשונים והאחרונים שנשמרים במהלך הצמצום הסופי כאשר התקציב הוא לפחות שניים. המדיניות המהודרת `grayscale-16x16-mean-cells-v2` משתמשת בממוצע של דלתא לומה וביחס של תאי תמונה ממוזערים שהדלתא המנורמלת שלהם היא לפחות 0.05. סף השכפול הוא הקבוע 0.04, שנבחר עבור ניבוי ולא נחשף כהגדרת זמן ריצה. האות השני הזה בעל הניגודיות הגבוהה שומר על תנועה קטנה ושינויים בטקסט הנראה שיכולים להסתיר השוואה רק ממוצעת. שגיאות של משווה או מפענח נכשלות לפתיחה ושומרות על הכיסוי. מטא-דאטה של פלט מפריד בין מועמדים שנחצבו, פריימים שהשתמשו בהצלחה, ושכפולים חזותיים שנזרקו.

חלק וידאו מסומן במפורש עשוי לבקש גיליון קשר עם חותמת זמן. הגשר בונה לכל היותר רשת JPEG של 4 עמודות ו-16 פריימים. כל תא בגודל 512 פיקסלים שורף את חותמת הזמן שלו לרצועת תחתית בעלת ניגודיות גבוהה, בעוד שחותמות הזמן נשארות במטא-דאטה טקסטואלית עבור אסוציאציה וביקורת מאוחרת. ה-JPEG המלא נשאר מוגבל ל-32 MiB. אם `sharp` לא יכול לפענח או להרכיב את הרשת, הגשר חוזר לפריימים JPEG האישיים; ביטול של לקוח עדיין מתפשט דרך פעולת הגיליון.

ראיות קידום מופרדות במכוון מההרכב הסינתטי של המיקרו-בנצ'מרק. `scripts/perf/video-bridge-contact-sheet-eval.ts` מגדיר חגורת A/B עם גרסה של סכימה עבור מודלים אמיתיים תואמי OpenAI. הוא מודד את מספר הטוקנים המדווחים על ידי הספק, את השיהוי הכולל (כולל הרכבת הגיליון), את מספר הקריאות למודל, ואת שמירת העובדות המוגדרת במניפסט. תגובות המודל הגולמיות לא נכתבות לדו"ח; רק דיגסטים SHA-256 וזיהויי עובדות תואמים נשמרים. החגורה לא מבצעת קריאה לרשת או למודל בתשלום אלא אם `--execute-real` מועבר ו-`--model`, `OMNIROUTE_BASE_URL`, ו-`OMNIROUTE_API_KEY` מוגדרים. ללא הריצה האמיתית המפורשת הזו, פסק הדין הקריא של המחשב נשאר `HOLD`; מדידות של משקל/מספר קריאות סינתטיות בלבד אינן ראיות לקידום.

הסקריפט הנפרד `scripts/perf/video-bridge-promotion-eval.ts` צורך תצפיות FU-07 או FU-09. קבלת קידום דורשת את כל שמונת סוגי התרחישים הסינתטיים בנוסף לקליפ אמיתי מחוטא, לפחות שלוש חזרות מדודות לכל תפקיד ומקרה, את כל עשרת המדדים המוצהרים, דיגסטים של מדיה קפואה/הנחיה/עובדות צפויות/הגדרות, זיהויי תצפיות ייחודיים וסדר A/B מאומת. קבלת הביצוע קושרת את דיגסט הקורפוס, את SHA המדויק של המועמד ואת גרסת המודל. מדידות חסרות או לא תקפות נשארות `HOLD`, כולל CPU מעל 30 שניות, RSS מקסימלי מעל 512 MiB או ניתוח מקדים מעל 30 שניות. אלו הם גבולות קבלת ראיות, לא הבטחת אכיפת RSS חדשה בזמן ריצה.

FU-07 דורש לפחות 98% שמירה על איכות ו- p95 השהיה לא יותר מ- 1.2x
בסיס, בנוסף לשיפור מוחלט של 0.05 בממוצע זיכרון מאוזן במקרה בשיחות כיתוב שוות ערך, או לפחות 10% פחות בשיחות כיתוב לאחר דדופליקציה. FU-09 דורש לפחות 0.85 איכות, 95% שמירה, הפחתה של 20% ב- p95 השהיה והפחתה של 10% בטוקנים. אובדן של עובדות קריטיות, עמידה בהזרקה או שימוש חסר מונעים קידום. ביצוע אחד לא יכול לקדם דבר: `--previous-report` מאשר שני ביצועים נפרדים, לא חופפים, זכאים ברצף של אותה מדיניות/גרסה/מועמד/קורס. ניסוי דגימה לא יכול לאשר ניסוי גיליון קשר.

אוספים צריכים לדרג תגובות בזיכרון ולשמור `responseDigest` בנוסף למטריקות וקשרי תצפית, לעולם לא טקסט תגובה. הצרכן גם קורא תצפיות גולמיות ישנות אך לעולם לא מעתיק את הטקסט הזה לדו"ח שלו. בדיוק אחד מ- `responseDigest` או `rawResponseText` מתקבל עבור כל תצפית. הרשימה המותרת בגרסה נשארת ריקה עם ברירת מחדל בלתי ניתנת לשינוי `hold`. כניסה זכאית דורשת את הפניה שלה, מדיניות, גרסת מודל, SHA מדויק של מועמד, דיגסט מניפסט ושני מזהי ריצה נפרדים; הקשרים הסותרים נדחים. מטאדאטה אלה הם חוזה ביקורת, לא הוכחה שהקובץ המופנה מכיל מדידות אמיתיות. בדוק את הקבלות האמיתיות לפני הוספת כל כניסה. נקודת הקצה של הסטטיסטיקות לניהול ולוח הווידאו חושפים מוכנות שמרנית. כינוי מודל מוגדר בלבד לא קובע את הגרסה שלו או את ה-SHA של המועמד הפועל, כך שהדו"ח הנוכחי מדווח `HOLD` במקום לעשות שימוש בזכאות מקונטקסט ביצוע אחר. בחירת ניסוי מפורשת נשארת נפרדת מקידום; לא ברירת מחדל משתנה אוטומטית.

קוראים יכולים לצרף מערך אופציונלי של `transcript.cues` לחלק ווידאו נתמך כאשר הם כבר מחזיקים טקסט מיושר. כל רמז חייב לשאת `text`, טווח `start`/`end` סופי בתוך משך הזמן הנחקר, ו- `source` ברשימה המותרת (`client`, `embedded`, או `audio-bridge`); `confidence` ברירת המחדל היא `1` וחייבת להישאר בין `0` ל- `1`. רמזים כפולים מדויקים מתמזגים. OmniRoute לעולם לא מתחיל תמלול מהמטאדאטה הזו: רמזים מאומתים מועתקים לתוצאה המתוארת עם מקור, ביטחון וטווח, ומוצגים כתצפיות לא מהימנות לצד כיתובי המסגרת. טקסט לא חוקי, מחוץ לטווח, או חסר מקור נדחה במקום להתערבב בזרם הכיתוב. שני ערוצי תמלול גוף הבקשה מנרמלים את המקור המסופק ל- `client`, כולל תוויות `embedded` או `audio-bridge` שהוצהרו על ידי עצמם. רק מתאם בבעלות השרת יכול להקצות את התוויות המהימנות הללו דרך הפרמטר `trustedSource` בלבד; שדה JSON בבקשה לא יכול להגיע לארגומנט הזה. טקסט התמלול נשאר תוכן נגזר ממדיה לא מהימנה, ללא קשר למקורה, ולעולם לא יכול לקבוע הרשאה.

קורא מתקדם עשוי לספק מסלול `audioTranscript` עבור אותו ווידאו; הוא מתייחס כטקסט שסופק על ידי הלקוח, לא כהוכחה לתמלול של השרת. תפרחת הפיוז'ן מריצה תצפיות חזותיות ואודיו תחת
מועד אחרון אחד ואות ביטול, מסדרת אותן על ציר זמן משותף, מתמזגת
כפולים מדויקים, ומדווחת על תוצאה חלקית כאשר רק צד אחד מצליח.
`audioTranscript` לא חוקי מתדרדר לתוצאה חלקית — התיאור החזותי נשמר והענף האודיו רושם קוד כישלון מחוטא —
במקום להיכשל על כל הווידאו. זמינות לפי ענף, הדגל החלקי,
וקודי הכישלון המחוטאים נשמרים בתוצאה המתוארת, במטאדאטה של הגדרות הגנה (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), במטאדאטה של מטמון התוצאה, ובספירות פיוז'ן של הגשר. הנתיב המוגדר כברירת מחדל של גשר הווידאו לא מפעיל דיבור לטקסט
או מוריד עותק מדיה שני; ללא המסלול המפורש הזה, הוא נשאר
רק ווידאו.

**שימור תמלול (#12150 P1).** זה חל אוטומטית בכל פעם שגשר הווידאו (שגם הוא אופציה) מציג רמז תמלול — אין דגל שימור נפרד. כאשר בקשה מציגה כל רמז תמלול (תמלול שהוכרז על ידי הקורא או `audioTranscript` ממוזג), הגדרות ההגנה מסמנות אותו
`videoBridgeObserved` ומייצרות צל אדום של התיאור הווידאו —
הצגה זהה שבה גוף הטקסט החופשי של כל רמז מוחלף ב- `[redacted-video-transcript]`, שנבנה על ידי החלפת שדה הרמז המובנה לפני שהמחרוזת מורכבת (לעולם לא על ידי ניתוח הטקסט המפושט, כך שאין תוכן רמז — עוין או רגיל, כולל גופים המכילים `]` כמו
`[inaudible]`/`[music]` — יכול לשרוד). גוף הבקשה שנשמר ביומן החלפות
כל חלק טקסט נגזר ווידאו באותו צל מחוק, תואם על פי שוויון תוכן; העוגן `fullText` נקרא מחדש מהמטען של הגדרות ההגנה לפני השיחה, כך שההתאמה עדיין מצליחה לאחר שהגדרות הגנה מאוחרות (מסכות PII ואמינות, עדיפויות 10/95) משכתב את טקסט התיאור במקום ואחרי שהזרקת מערכת/העברה/זיכרון מעצבת את מערך ההודעה. הגוף שנשלח למעלה למודל אינו משתנה. בקשה שנצפתה גם לא ממלאת
זיכרון עמיד (גם חילוץ נגזר מבקשה וגם תגובה מדלגים),
כך שהתשובה של המודל לא יכולה להדהד טקסט תמלול לזיכרון.

**שדות ווידאו גולמיים (#12430).** כאשר הגשר מופעל ותמיכה בווידאו מקומית אינה ידועה או חסרה, שדות `transcript`/`audioTranscript` המוגדרים מפעילים גם את `videoBridgeObserved`, גם לאחר כישלון תיאור או מגבלת `maxVideos`. `null` ומחרוזות ריקות נחשבות; שדות חסרים ומטאדאטה לא ווידאו לא נחשבים. עותקים שנשמרים מחקים את השדות הללו או משאירים את הבקשה, ומטמונים/זיכרון מדולגים.

בדרכי הגיבוי הללו, תורים חוקיים של מתקשרים הופכים לחלקים נתמכים `text`/`input_text` במקום שדות ספק לא סטנדרטיים. שני המסלולים המסופקים על ידי הבקשה נשארים תצפיות `client` לא מהימנות, עם אזהרה מפורשת שהוידאו לא תואר והזמנים לא אומתו מול המדיה. התקציבים הקיימים של 256 תורים/64-KiB בסך הכל ובכל תור חלים על שני המסלולים יחד; הזמנים חייבים להתאים לתקרת ה-600 שניות של הברוקר וכל חלון מיקוד שסופק. מסלולים לא חוקיים נזרקים, ולא מועברים כטקסט שרירותי; אח נוסף חוקי עשוי עדיין לשמש אלא אם התקציב המשולב שלהם חורג. שדות ריקים/נול לא מוסיפים טקסט. אין חיפוש מדיה או תמלול נוסף על ידי גיבוי זה. שדות הרחבת תמלול מוסרים מהנשא הווידאו של הגיבוי ומהאובייקטים `video_url`/`source`. רשימת ההיתרים של OpenAI נשארת מחמירה; נשאים של וידאו לא ידועים נשארים זמינים ומטרות טקסט בלבד ידועות שומרות על סימנים בטוחים. צללים של מחיקה מובנית מגנים על טקסט התמלול המוסף, בעוד הבקשה המקורית בבעלות המתקשר נשארת ללא שינוי. מטרות נתמכות מקומית וגשרים מושבתים שומרים על התנהגות העקיפה הקיימת שלהם.

עותקים נוספים שנשמרים משתמשים באותו אות בקשה שנצפתה. תצלום הבקשה של הלקוח לפני הגדרות, הבקשה הממתינה בזיכרון, ורשומת הבקשה שנדחתה מוקדם מחליפים מבנית את שדות התמלול בחלקי הווידאו; פקודות מיתר שנוצרו על ידי שלבי צינור ומסירת הקשר נמחקות בבריכת גוף הבקשה שנשמרה. הסימן `video_content_removed` גורם לכך שהמשך `previous_response_id` נכשל בסגירה במקום לשחזר טקסט שנזרק בכוונה. אם בקשה שנצפתה מאבדת את צלל המחיקה שלה לפני הרישום, או אפילו אחד מכמה צללים של וידאו נכשל להתאים לאחר שינויים מאוחרים בבקשה, גוף הבקשה שנשמר מוחרג לחלוטין במקום לשמור על תמלול חלקי שנמחק.

לגבי בקשה שנצפתה, תגובה של מודל עשויה לצטט כל חלק מהתמלול ללא גבול תור מובנה. לכן, `responseBody` של יומן השיחות שנשמר מוחלף בסימן השמטה; האובייקט המפורט של הצינור (שיכול לכלול גופי עליון/לקוח וחלקי זרם) לא נשמר. מטמוני סמנטיקה, אידמפוטנציה, ומחשבות-חזרה על היגיון עוקפים קריאות וכתיבות עבור בקשה זו. הבקשה לספק ותגובה הנראית ללקוח נשארות ללא שינוי. בתים מוקדמים של שמירה נגרעים מהזיכרון הזמני כאשר האובייקט המפורט מוחרג. אזהרת ה-EventStream המעוותת של Kiro מדווחת רק על מספר הבתים של המטען, אף פעם לא על התוכן או השגיאה הגולמית של מפענח ה-JSON.
זה לא טוען שכל אבחון של ספק/תוסף שאינו קשור נבדק; הסSweep של בריכת השמירה הרחבה יותר מתועדת ב-#11658.

מחזור החיים של `/api/modality-bridge/video/drilldown` הוא תשתית קאש נפרדת, מאומתת בלולאה/טוקן. כל פעולה דורשת גם מזהה עיקרי אטום קנוני. לפני שמתקשר בייצור מופעל, עליו להפיק את המזהה הזה מהשוכר המאומת ולא להעביר ערך שנבחר על ידי הלקוח. מפתחות הקאש קושרים את העיקרי הזה למזהי מושב קנוני ומזהי הפניה לוידאו, מאחסנים רק את המפתחות המופקים שלהם SHA-256, ומגבילים גם קריאות וגם מחיקות לאותו עיקרי. הקאש מאחסן לכל היותר 16 מסגרות JPEG מופקות לכל רשומה, פג תוקף לאחר עשר דקות, ותומך בקריאות מוגבלות `start`/`end` או מחיקת מושב מפורשת.

כל עיקרי מוגבל ל-16 רשומות ו-64 MiB של נתוני JPEG קנוניים. מגבלות אלו אינן תלויות בתקרת 64 רשומות/256 MiB הגלובלית: לחץ מכסה עיקרי מפנה רק את הרשומות הפחות בשימוש של אותו עיקרי לפני שמחשבים על פינוי LRU גלובלי. רשומות שפג תוקפן נגרעות הן מהעיקרי והן מהחשבונאות הגלובלית על פעילות קאש, בעוד ביטול וכישלון אימות אינם מחייבים החלפה חלקית.

הקאש דוחה Base64 לא קנוני, ריפוד יתר, מדיה לא JPEG, JPEGs מעוותים או מקוצרים, ו-JPEGs שמפיקים אזהרה במהלך פענוח מלא של `sharp` מוגבל. הוא מקודד מחדש כל תמונה שהתקבלה כ-JPEG קנוני, מפיק רוחב וגובה מהבתים המפוענחים במקום לסמוך על שדות המתקשר, ומסלק כל בתים פוליגלוטיים אחרונים במקום לשמור עליהם. רק הבופר המכווץ הקנוני המוגבל מחויב לשני מכסות. מגבלת ה-JSON כוללת את העומס של Base64 עבור תקרת הקלט המפוענח של 32 MiB. כל
הפקת שמירה מתעדת את פורמט/רזולוציית JPEG המאומתת שלה, מדיניות דגימה, גרסת הפקה, זמן יצירה, גזירת תוכן מחושבת על ידי השרת, ומזהה הורה מחושבת יחד עם גזירת תוכן ההורה של המתקשר המהימן. ביטול נבדק בין שלבי פענוח/גזירה אסינכרוניים לפני המחויבות האטומית של הקאש.

המפיק בייצור עושה שימוש מחדש במסגרת הברוקר המופקת רק לאחר ניתוח חזותי מוצלח, ללא הורדה/חילוץ של וידאו שני. הוא דורש `modalityBridgeVideoDrilldownEnabled=true` של מפעיל, `drilldown: true` מחמיר לכל חלק, ורשומת מזהה מפתח API מאומת. ערכי עיקרי/מושב המוצהרים על ידי הלקוח לא מקנים בעלות. ללא שלושת התנאים הללו הוא לא מגזים, משנה גודל או שומר על מסגרות נוספות. כישלון בשמירה שומר על התגובה החזותית הניתנת לשימוש. בקשות שהוסכמו עוקפות את קאש התוצאה של כל הווידאו כך שהתוצאות המאוחסנות לא משחזרות ידיות.

תשובות JSON ו-SSE מוצלחות חושפות לכל היותר ארבעה ידיות אטומים בכותרת המוגבלת `x-omniroute-video-drilldown`. מקורות דפדפן מורשים יכולים לקרוא כותרת זו מבלי להרחיב את מדיניות מקור CORS. ידיות חדשות משתמשות ב-`v1.<32-byte random base64url token>`, והרישום שומר רק את ה-hashes SHA-256 שלהן. הקורא/מנתח הכותרת מקבל גם טוקנים ישנים באורך 64-hex. הצרכן הציבורי המאומת הוא `GET /api/v1/video-bridge/drilldown?handle=...`, שנשלט באופן עצמאי על ידי `modalityBridgeVideoDrilldownRemoteEnabled=true`. הפסקה מפורשת של גישה לא מתמשכת מבטלת גישה גם כאשר הגיבוי הישן `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` מופעל. שמירת ייצור כוללת את הגיבוי הישן האנלוגי `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED`. שני הגיבויים כבויים כברירת מחדל.

הצרכן נובע מהמפתח המאומת, מיישם מדיניות מפתח, ומחזיר את אותו 404 עבור ידיות לא ידועות, פג תוקף וידיות של מפתח אחר. הוא מקבל `variant=preview|standard|detail` (ממדי JPEG מקסימליים 320/640/1280, אף פעם לא מוגדלים), `limit=1..8` (או את הכינוי הישן `frames`, אף פעם לא שניהם), `page` מבוסס אפס, ושניות מיקוד אופציונליות `start`/`end`. מפתחות שאילתא כפולים וחלונות מיקוד הפוכים נדחים. כל וריאנט מוחזר כולל hash של התוכן האמיתי שלו ומטא-נתוני הרזולוציה האמיתית, מקושר למקור השמור. וריאנטים נגזרים בקריאה ולא נשמרים כהעתקים נוספים. תשובת JSON, כולל Base64/envelope, מוגבלת ל-32 MiB; עמוד גדול מדי מחזיר 413 והלקוח חייב לבקש פחות פריימים. קריאות בודקות ביטול סביב כל שינוי גודל ומוודאות את תוקף הידית לפני החזרה. `DELETE` על ידי בעלים הוא אידמפוטנטי; מחיקה או פקיעת TTL משחררת את המקור השמור ואת חישוב השימוש.

החנות המשותפת היא מקומית לתהליך: ידיות פגות תוקף עם אתחול ואינן ניתנות להעברה בין תהליכי OmniRoute עצמאיים. סטטיסטיקות ניהול חושפות מדיניות שמירה/מרוחקת אפקטיבית ומספר רשומות/בתים שמורים בלבד, אף פעם לא מדיה, הפניות, מזהי עיקריים או ידיות. לוח הגדרות הווידאו מציג ערכים אלה ויכול לשמור את שני מתגי ההסכמה. תיעוד ההטמעה הזה אינו ראיה לפריסה חיה או לקידום; קבלת מודל אמיתי נעקבת בנפרד.

פריימים מתוייגים ברצף עם מודל הווידאו המוגדר. ע override וידאו ריק יורש את הגדרת הוויזיה; אם שניהם ריקים, המפנה האוטומטי של הוויזיה בוחר את המודל היעיל בעל היכולת הוויזואלית. כותרות מוצלחות מחליפות את החלק המקורי עם קידומת יציבה `[Video description:` שמסמנת גם את הטקסט כהערה נגזרת מדיה לא מהימנה ואומרת למודלים downstream לא לעקוב אחרי הוראות שנמצאות במדיה. מפתחות מטמון כותרות פריימים כוללים את בתים JPEG, הנחיה, חותמת זמן, ומודל אפקטיבי; רק כותרות מוצלחות נשמרות במטמון. רשומות מטמון שומרות את מודל המפיק המוצלח האמיתי, כולל מודל גיבוי; המפנה מדווח על `mixed` כאשר פריימים שונים הופקו על ידי מודלים שונים. פגיעה במטמון עושה שימוש באותה זהות מפיק במקום לשנות את השם שלה לתוכנית המיקוד המבוקשת. מטמון התוצאה של הווידאו כולו מקודד על כל קלט שמשנה את הפלט — הנחיה, מודל אפקטיבי, מדיניות דגימה, מספר פריימים, מצב ניתוח סמנטי, חותמת SHA-256 של רמז המיקוד הנורמליזי, חלון מיקוד, `transcript`, `audioTranscript`, ודגל גיליון הקשר — כך ששינוי כל אחת מהמידות הללו הוא פגיעה במטמון, אף פעם לא שימוש ישן. גרסת מדיניות ההסרה הוויזואלית, סף, ומספר פריימים מועמדים מוגבלים גם הם מפורטים במפתח ובמטא-נתוני מטמון התוצאה; שינוי מדיניות לכן לא יכול לעשות שימוש בתיאור וידאו ישן. מטא-נתוני מטמון התוצאה v4 שומרים את המצב והחותמת, אף פעם לא את משימת המשתמש הגולמית. מטא-נתוני הגדרות מגן מדווחים על שני מצבי הניתוח המבוקשים והאפקטיביים; מצב `focused` המבוקש ללא טקסט שימושי מדווח כיעיל `full`.

המגן שולף כל חלק וידאו נתמך אך מתאר לא יותר מ-`modalityBridgeVideoMaxVideos`. עבור יעד שהוכח שיש לו `supportsVideo === false`, וידאו שנכשל ומעבר למגבלה הופך לסימני טקסט בטוחים מפורשים כך שאין וידאו גולמי שורד. כאשר היכולת אינה ידועה, חלקים אלה שומרים את נושא הווידאו שלהם; כל תמלול גיבוי עוקב אחרי המרת הטקסט המוגבלת למעלה. יעדים עם `supportsVideo === true` עוקפים את המפנה. אות הביטול של בקשת הלקוח מתפשט דרך ההורדה, תור הברוקרים, תהליכים משנה, ושיחות כותרות; ביטולים נעצרים בין וידאוים ואינם נכשלות פתוחות למדיה גולמית.

הגדרות בזמן ריצה מגובות ב-DB ומאומתות על ידי Zod:

| מפתח                                | ברירת מחדל  | טווח / התנהגות                                                                         |
| ----------------------------------- | ----------- | -------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | ריצה אופציונלית, הצטרפות                                                               |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` שומר על כותרות כלליות; `focused` משתמש בהקשר לא מהימן של המשתמש האחרון המוגבל   |
| `modalityBridgeVideoModel`          | `""`        | יורש את מודל גשר הוויזיה                                                               |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                   |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, או `segment_aware` פרופורציונלי; כישלון מגלה חוזר ל`uniform` |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                    |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                         |

ערכי זמן פסק זמן של וידאו שהוחזקו בעבר מעל 120 שניות מוגבלים למועד הסופי של הברוקר; כתיבות הגדרות חדשות מעל מגבלה זו נדחות. `GET /api/modality-bridge/video/runtime` דורש מקומית לולאת חזרה מהימנה לפני אימות או חקירת זמן ריצה, ואז דורש אימות ניהול. הוא מחזיר רק גרסאות FFmpeg/ffprobe זמינות ומסוננות, וסיבה קבועה כאשר זמן הריצה אינו זמין. נקודת הקצה הפנימית להפקה אינה API להעלאת ציבורית: רוויה בתור מחזירה `503` בנוסף ל`Retry-After`, ניתוק של הקורא מחזיר `499`, והמועד הסופי הקבוע של הברוקר מחזיר `504`. תגובות שהומרו מוסיפות `video->text;model=<visionModel>;parts=<videos>` לכותרת המרכזית `x-omniroute-modality-bridge` מבלי להסיר את קטעי הוויז'ן או האודיו.

### מסנן PII (`piiMasker.ts`)

פועל בשני השלבים.

- **`preCall`** משכפל את המטען, עובר על `system`, `messages`, `input`, ו`prompt` (כולל פריטי מיתר פשוטים), ומיישם `processPII()` (מ`@/shared/utils/inputSanitizer`) על שדות `content`/`text` מסוג מיתר. כאשר `PII_REDACTION_ENABLED=true`, PII שזוהה נמחק במטען היוצא. זה עצמאי מ`INPUT_SANITIZER_MODE` (ששולט רק במדיניות הזרקת פרומפט). כאשר מחיקת PII כבויה, השיחה רושמת את ספירות הזיהוי מבלי לכתוב מחדש את התוכן.
- **`postCall`** משכפל עמוק את התגובה, מפעיל `sanitizePIIResponse()` בנוסף למסנן צורת Responses-API (`maskResponsesOutput` — מכסה את `output_text` ו`output[].content[].text`). אם מתרחשת מחיקה כלשהי, התגובה המותאמת מחליפה את המקורית.

הגדרות הבטיחות אף פעם לא חוסמות; היא רק מסמנת (`meta.detections`, `meta.redacted`) או כותבת מחדש.

### הזרקת פרומפט (`promptInjection.ts`)

מגלה מבנים עוינים בתוכן שסופק על ידי המשתמש ומאכפת על המדיניות המוגדרת. ההתנהגות מונעת על ידי משתני סביבה ואופציות קונסטרוקטור:

| הגדרה    | משתנה סביבה                                                                                           | ברירת מחדל | השפעה                                                                                                                                                          |
| -------- | ----------------------------------------------------------------------------------------------------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| מופעל    | `INPUT_SANITIZER_ENABLED`                                                                             | `true`     | כאשר `false`, הגדרות הבטיחות מקצרות את התהליך.                                                                                                                 |
| מצב      | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`     | מדיניות הזרקה: `block`, `warn`, או `log`. (`redact` מתקבל עבור תאימות לאחור אך אינו מסיר את טקסט ההזרקה; בקשת מחיקת PII נשלטת על ידי `PII_REDACTION_ENABLED`.) |
| סף חסימה | אפשרות `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (כינוי `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`     | החומרה המינימלית הנדרשת לחסימה. חומרה בינונית היא רק לצפייה כברירת מחדל.                                                                                       |

**עדיפות מצב** (`getMode`): `options.mode` של הקורא → `INJECTION_GUARD_MODE` **דגל תכונה DB** (לוח מחוונים → הגדרות → דגלי תכונה) → משתנה סביבה `INJECTION_GUARD_MODE` → משתנה סביבה `INPUT_SANITIZER_MODE` → `warn`. לכן, דגל תכונה בלוח המחוונים מנצח על משתני הסביבה, כך ש-UI של דגלי התכונה שולט על הגדרות הבטיחות בזמן אמת (ללא הפסקה). קריאת ה-DB היא בטוחה: אם יש שגיאה, הגדרות הבטיחות חוזרות להתנהגות מבוססת סביבה, וכאשר אין דגל חורג, ההתנהגות זהה לפתרון מבוסס סביבה בלבד.

מקורות זיהוי:

1. `sanitizeRequest()` מ`@/shared/utils/inputSanitizer` (סט מגלה משותף בשימוש במקומות אחרים בצינור).
2. דפוסי הגנה מובנים `DEFAULT_GUARD_PATTERNS` (נוכחית `system_override_inline` ו`markdown_system_block`, שניהם ברמת חומרה `high`).
3. דפוסים מותאמים אישית אופציונליים המועברים דרך אפשרויות קונסטרוקטור (מחרוזות, regex, או `{ name, pattern, severity }` רשומות).

כאשר `mode === "block"` **וגם** לפחות זיהוי אחד עומד בסף החומרה, `preCall` מחזיר `{ block: true, message: "Request rejected: suspicious content detected" }`. במצבי `warn`/`log` הגדרות הבטיחות רושמות אך מאפשרות את השיחה. העוזר המשותף `evaluatePromptInjection()` גם מיוצא עבור קוראים שצריכים להעריך פרומפטים מבלי לעבור דרך הרישום.

**סורק מוגבל (v3.8.20):** המגלה בודק רק את **16 KB הראשונים** של טקסט הפרומפט המאוחד — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 בתים) ב`src/shared/utils/inputSanitizer.ts`. גם `detectInjection()` וגם `evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` לפני הפעלת לולאת הדפוס. הנחיות הזרקה יושבות קרוב לחלק העליון של קלט, כך שזה מגביל את ה-CPU/GC של regex על מטענים של מאות קילובייט מבלי להחליש את הזיהוי (השווה ל#3932, #4041).

### מסנן אישורים (`credentialMasker.ts`)

פועל בשני השלבים, האחרון בשרשרת ברירת המחדל (עדיפות `95`). מוחק דפוסים ידועים של מפתחי API / טוקן סודיים מהמטען היוצא (תוכן הודעה, ארגומנטים של קריאות כלים, תוצאות כלים) **וגם** את תגובת הספק, כך שאישור שהודבק בפרומפט (או הושמע חזרה על ידי תוצאת כלי) לא דולף לספק העליון או חזרה ללקוח.

- **רק בהסכמה**, אותה קונבנציה כמו הסתרת PII (כלל קשה #20-סמוך):
  מושבת אלא אם `settings.credentialRedactionEnabled === true` **או**
  `CREDENTIAL_REDACTION_ENABLED=true`. כאשר זה כבוי, המגבלה היא לא-פעילה —
  היא אף פעם לא חוסמת ואף פעם לא מחדש.
- `redactCredentials()` עובר על כל עץ ה-payload/response (`walkValue()`,
  בטוח מפני זיהום פרוטוטיפ, בטוח מפני לולאות באמצעות `WeakSet`) ומחליף התאמות עם
  מקום שמירה `[REDACTED:<type>]`, משכפל רק את הענפים שבאמת
  השתנו.
- `CREDENTIAL_PATTERNS` מכסה מפתחות ספקי LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), טוקנים של VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), מפתחות תשלום (Stripe, Square), מפתחות ענן
  (מפתח גישה של AWS, Twilio, SendGrid, Mailgun), מפתחות פרטיים / JWTs,
  מיתרי חיבור הנושאים credentials (`mongodb://user:pass@...`, וכו'), ודפוס כללי של
  `Authorization`/`x-api-key`/`api-key`/`apikey` כותרת-ערך.
  מפתחות בצורת כותרת (`authorization`, `x-api-key`, `api-key`,
  `apikey`) מוסרים בצורה מבנית (רק ערך, קידומת סכימה כמו
  `Bearer `/`Basic ` נשמרת) ולא באמצעות רגקס טקסט כללי.
- המגבלה אף פעם לא חוסמת; היא רק מחדש (`modifiedPayload` /
  `modifiedResponse`) ומסמנת (`meta.credentialsRedacted`, `meta.count`).

מגן רגרסיה: `tests/unit/credential-masker-guardrail.test.ts`.

## חוזה בסיס (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true עוצר מיד את השרשרת
  message?: string; // מוצג בעת חסימה
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // מוחזר על ידי preCall כדי לשכתב את הבקשה
  modifiedResponse?: TValue; // מוחזר על ידי postCall כדי לשכתב את התגובה
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

מנגנון הגנה מסמן "ללא שינוי" באמצעות החזרת `void`, `{}`, או
`{ block: false }`. החזרת `modifiedPayload`/`modifiedResponse` מחליפה
את הערך שזורם בשרשרת עבור מנגנוני ההגנה שבהמשך.
`signal?: AbortSignal` מעביר אל מנגנוני ההגנה את מחזור החיים של הקורא. ביטול בקשה הוא החרגת fail-open מכוונת: גשרי מדיה מפסיקים את העבודה ומבצעים ניקוי מבלי לשחזר מדיה גולמית ליעד שידוע כי אינו תומך בה.

## מרשם (`registry.ts`)

היחידון `guardrailRegistry` חושף:

- `register(guardrail)` — מוסיף מנגנון הגנה (או מחליף לפי שם מנורמל) וממיין
  מחדש לפי `priority` בסדר עולה.
- `clear()` / `list()` — כלי עזר ניהוליים.
- `runPreCallHooks(payload, context)` — עובר על מנגנוני ההגנה הפעילים, מעביר את
  המטען דרך `modifiedPayload`, ועוצר ב-`block: true` הראשון.
- `runPostCallHooks(response, context)` — אותה זרימה בצד התגובה.
- `resetGuardrailsForTests({ registerDefaults })` — מנקה את המצב, ולפי הצורך
  רושם מחדש את ברירות המחדל לצורך בידוד נקי של בדיקות.

שני המריצים מחזירים `{ blocked, payload|response, results, guardrail?, message? }`
כאשר `results` הוא מערך של רשומות `GuardrailExecutionResult` הכוללות
את השדות `blocked`, `skipped`, `modified`, `error` ו-`meta` לכל מנגנון הגנה,
ושימושיות למעקב.

### השבתת מנגנוני הגנה לכל בקשה

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` אוסף רשימה
ללא כפילויות של שמות מנגנוני הגנה שיש לדלג עליהם עבור הבקשה הנוכחית.
המקורות (כולם אופציונליים וכולם ממוזגים):

- `apiKeyInfo.disabledGuardrails`
- `disabledGuardrails` בגוף הבקשה (ברמה העליונה)
- `metadata.disabledGuardrails` בגוף הבקשה
- הכותרת `x-omniroute-disabled-guardrails` (או הכותרת הישנה
  `x-disabled-guardrails`)

הערכים יכולים להיות מערכי מחרוזות או מחרוזת מופרדת בפסיקים; השמות
מנורמלים ל-kebab-case באותיות קטנות (`pii_masker` → `pii-masker`). התוצאה
מועברת דרך `context.disabledGuardrails` אל המרשם, שמדלג על
מנגנוני הגנה תואמים (`skipped: true` בתוך `results`).

## סדר הביצוע

עבור כל בקשה שעוברת דרך `src/sse/handlers/chat.ts` ודרך
`open-sse/handlers/chatCore.ts`:

1. `resolveDisabledGuardrails(...)` בונה את רשימת הדילוג ממפתח ה-API, מגוף הבקשה
   ומהכותרות.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` מפעיל את מנגנוני ההגנה לפי סדר
   עדיפויות עולה:
   - מנגנוני הגנה מושבתים מתועדים כ-`skipped`.
   - ה-`preCall` של כל מנגנון הגנה עשוי לשכתב את המטען באמצעות `modifiedPayload`.
   - המופע הראשון של `block: true` עוצר את השרשרת, וה-handler מחזיר
     תגובת דחייה של מנגנון ההגנה.
3. המטען (שייתכן ששוכתב) מועבר לניתוב משולב ולשליחה לשירות שבמעלה הזרם.
4. לאחר הרכבת התגובה, `guardrailRegistry.runPostCallHooks(...)`
   מפעיל את אותה שרשרת על התגובה. `block: true` בשלב זה מבטל את התגובה
   משירות מעלה הזרם.

מנגנוני הגנה שזורקים חריגה מתועדים עם `error: <message>` ונרשמים ביומן באמצעות
`logger.warn`, אך השרשרת ממשיכה — זהו תכנון מסוג fail-open.

## תצורה

משתני סביבה שנקראים על ידי מנגנוני ההגנה המובנים:

| משתנה                                 | בשימוש על ידי             | השפעה                                                                                    |
| ------------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | יש להגדיר `false` כדי להשבית לחלוטין את הזיהוי.                                          |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`        | מדיניות הזרקה: `warn`,‏ `block` או `log`. הערך הישן `redact` אינו משכתב טקסט של הזרקה.   |
| `INJECTION_GUARD_MODE`                | `prompt-injection`        | מצב מגן ההזרקה; משמש גם כדגל תכונה במסד הנתונים אשר **דורס** את משתני הסביבה (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`        | רמת החומרה המזערית שאותה `MODE=block` דוחה: `high` (ברירת המחדל), `medium` או `low`.     |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`        | כינוי ישן עבור `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                        |
| `PII_REDACTION_ENABLED`               | `pii-masker`              | כאשר הערך הוא `true`, מידע אישי מזהה בבקשה מושחר (ללא תלות במצב ההזרקה).                 |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (במורד הזרם) | שולט בהתנהגות המיסוך בצד התגובה.                                                         |

מנגנוני ההגנה של Modality Bridge קוראים את תצורת זמן הריצה ממאגר ההגדרות
המגובה במסד הנתונים (`getSettings()`), ולא ממשתני סביבה. המפתחות הראשיים של Vision הם
`modalityBridgeVisionEnabled`,‏ `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`,‏ `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`,‏ `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`,‏ `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`,‏ `modalityBridgeCacheTtlMinutes` ו-
`modalityBridgeCacheMaxEntries`. המפתחות הישנים
`visionBridge*` מתקבלים רק כמנגנון הגיבוי המתועד לקריאה במחזור אחד;
כתיבות מלוח הבקרה משתמשות במפתחות הראשיים. ברירות המחדל ופותר מנגנון הגיבוי
נמצאים ב-`src/shared/constants/modalityBridgeDefaults.ts`, בעוד שהקבועים הישנים
נשמרים ב-`src/shared/constants/visionBridgeDefaults.ts`.

אודיו משתמש ב-`modalityBridgeAudioEnabled`,‏ `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` וב-`modalityBridgeAudioMaxClips`, יחד עם הגדרות
`modalityBridgeCache*` המשותפות. לאודיו אין מנגנון גיבוי למפתחות ישנים, משום
שמפתחות אלה הוצגו יחד עם הסכימה של Modality Bridge.

וידאו משתמש ב-`modalityBridgeVideoEnabled`,‏ `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`,‏ `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` וב-
`modalityBridgeVideoTimeout`, יחד עם הגדרות `modalityBridgeCache*` המשותפות.
הוא מושבת כברירת מחדל משום ש-FFmpeg/ffprobe הם תלויות תפעוליות אופציונליות,
והוספת כיתובים לפריימים מגדילה את זמן ההשהיה ואת עלות המודל.

## מנגנוני הגנה מותאמים אישית

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

שלבים:

1. צרו את `src/lib/guardrails/myGuardrail.ts` כך שירחיב את `BaseGuardrail`.
2. ממשו את `preCall` ו/או את `postCall`.
3. בצעו רישום בזמן הייבוא (הוספה מתוך `registerDefaultGuardrails`) או
   קראו ל-`guardrailRegistry.register(...)` בזמן ריצה — הרישום מחליף
   כל מנגנון הגנה קודם בעל אותו שם מנורמל.
4. הוסיפו בדיקות תחת `tests/unit/` (דוגמאות קיימות:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## בדיקות

השתמשו ב-`resetGuardrailsForTests()` בין הבדיקות כדי להתחיל ממצב ידוע.
העבירו `{ registerDefaults: false }` כדי להתחיל עם רישום ריק ולרשום
רק את מנגנוני ההגנה הנבדקים. Vision Bridge תומך בהזרקת תלויות
(`deps.getSettings`, `deps.callVisionModel`); ‏Audio Bridge חושף נקודות חיבור
מקבילות עבור הגדרות, יכולות, בחירת מודל STT, בדיקות פרטי גישה ותמלול.
לכן הבדיקות יכולות להפעיל את שני התהליכים ללא גישה למסד נתונים
או לרשת.

## כיסוי נתיבים ובדיקות צוות אדום למנגנון ההגנה מפני הזרקה (שלב 8 · בלוק D)

מנגנון ההגנה מפני הזרקה (`createInjectionGuard` / `withInjectionGuard`) מכסה את כל הנתיבים
שמקבלים הנחיות משתמש. הוא מכבד את `INJECTION_GUARD_MODE` (ברירת המחדל `warn` = רישום בלבד;
`block` = החזרת HTTP 400 עם `SECURITY_001`).

| סוג         | נתיבים                                                                                                                                               | מצב ברירת מחדל |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| טקסט (קיים) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn           |
| יצירתי      | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn           |
| נתונים      | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn           |

חילוץ טקסט (`extractMessageContents`) מכסה את `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**צוות אדום (מדי לילה, `nightly-llm-security.yml`):** ‏promptfoo מאמת שכל נתיב חוסם
את קורפוס OWASP-LLM כאשר `INJECTION_GUARD_MODE=block`; ‏garak מריץ בדיקות חדירה (ומדלג ללא סוד).
`moderations` נכלל למען העקביות — מפעילים במצב חסימה יכולים להחריג אותו באמצעות
`resolveDisabledGuardrails`.

תהליך העבודה הלילי (`.github/workflows/nightly-llm-security.yml`, ‏cron + הפעלה ידנית)
כולל שתי משימות:

- **`promptfoo-guard` (חוסמת)** — מריצה את `promptfoo eval -c promptfooconfig.yaml`
  עם `INJECTION_GUARD_MODE=block`. כל מקרה עוין (למשל "התעלם מכל
  ההוראות הקודמות…", פריצות בסגנון DAN) מוודא שהתשובה מכילה
  `error.code === "SECURITY_001"`, כלומר שמנגנון ההגנה אכן דחה את הבקשה.
- **`garak` (מייעצת)** — מריצה את garak עם `--probes promptinject,dan,leakreplay`
  מול מופע OmniRoute מקומי (`http://localhost:20128/v1`). ההרצה מותנית בסוד
  של ספק (`PROMPTFOO_PROVIDER_KEY`); היא מדלגת בצורה תקינה בהיעדרו ומסתיימת בסיומת
  `|| true`, כך שהיא מדווחת מבלי להכשיל את CI.

הכיסוי של פונקציית העזר של מנגנון ההגנה (`createInjectionGuard` / `withInjectionGuard`)
משתרע על כל נתיב `/v1` שמכיל הנחיה; טקסט ההנחיה נשלף מתוך
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` באמצעות
`extractMessageContents()` שב-`src/shared/utils/inputSanitizer.ts`.
