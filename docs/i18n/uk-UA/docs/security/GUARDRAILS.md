> **Джерело істини:** `src/lib/guardrails/`
> **Останнє оновлення:** 2026-08-29 — v3.8.51 (Походження стенограми Video Bridge оголошується абонентом,
> ще не перевірено сервером — уточнено згідно з #11661)

Захисні механізми забезпечують безпеку, політику та трансформації вмісту на межі між OmniRoute та вищестоящими провайдерами. Кожен захисний механізм може перевіряти (та за бажанням відхиляти, трансформувати або анотувати) корисні навантаження запитів (`preCall`) та відповіді вищестоящих систем (`postCall`).

Система є **відкритою при збої**: якщо захисний механізм видає помилку під час виконання, реєстр записує помилку та продовжує роботу з наступним захисним механізмом, замість того, щоб відхиляти запит. Блокування є явним рішенням (`block: true`), а не випадковістю.

## Вбудовані захисні механізми

Реєстр автоматично завантажує шість захисних механізмів у порядку пріоритету під час імпорту
(див. `registry.ts` → `registerDefaultGuardrails()`):

| Пріоритет | Назва               | Стадія(ї)      | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`      | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`      | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

Механізми з нижчими номерами пріоритету виконуються **першими**.

### Vision Bridge (`visionBridge.ts`) — Міст модальностей PR-1

Перехоплює запити з зображеннями, спрямовані на **немодель зору**, і або
перенаправляє весь запит на модель, що підтримує зір, або замінює частини зображення
текстовими описами, створеними налаштовуваною моделлю зору, перед
викликом вгору. Це дозволяє постачальникам, що працюють лише з текстом, прозоро обробляти
мультимодальні навантаження.

Процес:

1. Пропустити, якщо цільова модель вже підтримує зір (якщо вона не входить до
   списку примусових мостів `isVisionBridgeForcedModel`).
2. Витягти частини зображення за допомогою `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), яка делегує до **уніфікованого медіа
   детектора** `detectMediaParts()` у `open-sse/utils/mediaParts.ts` — єдиного джерела
   істини, спільного з фільтром сумісності комбінацій.
   Витягнення дозволено лише для верхніх частин форм, які
   `replaceImageParts` може вставити назад (контракт витягнення↔заміни): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, та Responses API `input_image`. Вкладені попадання та
   форми лише з індикаторами є матеріалом для фільтра комбінацій і ніколи не витягуються.
   Пропустити, якщо нічого не знайдено.
3. Визначити налаштування часу виконання за допомогою `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): нові ключі налаштувань `modalityBridge*`
   виграють; застарілі ключі `visionBridge*` залишаються **однократним
   резервним варіантом** (вікно скасування). Пропустити перед будь-яким медіа-перетворенням, коли
   міст вимкнено.
4. Вибір режиму (`modalityBridgeVisionMode`, див. таблицю нижче) вирішує
   перенаправлення або опис. Перенаправлення повертає `modifiedPayload` лише з
   заміненим `model`, плюс мета `{ rerouted, fromModel, toModel, imagesKept }`.
5. Шлях опису: обмежити зображення до `maxImages`, скласти завдання-обізнаний запит,
   проконсультуватися з кешем описів, викликати модель зору **паралельно**
   (`Promise.allSettled`), і вставити текстові частини `[Image N]: <description>` на
   їх місце. Неуспішний опис повертає `null`, і оригінальна частина зображення
   **зберігається** (#4012) — за винятком шляху опису комбінацій, коли кожен
   опис не вдався, де підтверджена немодель зору отримує
   `(недоступно — жоден постачальник, що підтримує зір, не підключений)` замість (#8430).
6. Повернути `modifiedPayload` + мета (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Вибір режиму (`modalityBridgeVisionMode`)

| Режим      | За замовчуванням | Поведінка                                                                                                                                                                                                                                                                                          |
| ---------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔                | Спадкова евристика, не змінена (#6640/#7204): немоделі/`auto/` перенаправляються на найкращу модель зору, якщо оригінальна модель вже має використовувані облікові дані (тоді опис); цілі комбінацій завжди описуються.                                                                            |
| `describe` |                  | Завжди описувати — блок перенаправлення повністю пропускається; обрана користувачем модель завжди відповідає.                                                                                                                                                                                      |
| `reroute`  |                  | Примусове перенаправлення: захист збереження облікових даних моделі обминається. Захист облікових даних **цілі** перенаправлення все ще застосовується — коли не існує використовуваної цілі зору, запит переходить до опису, тому сирі зображення ніколи не досягають текстового бекенду (#8430). |

Примусові режими короткозамикають **перед** запуском автоевристики; поведінка `auto`
є байтово ідентичною до захисного механізму до PR-1.

#### Область дії API-ключа (`visionBridgeKeyScope.ts`)

Коли API-ключ виклику обмежує `allowedConnections`, квотні пулі
(`allowedQuotas`) або моделі (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), міст вибирає лише
перенаправлення та моделі опису, які ключ може використовувати, на з'єднання, які ключ може
використовувати. Виклик опису завжди проходить через самопетлю OmniRoute з
заголовком `x-omniroute-self-loop-key-id`, тому отриманий запит чату
знову застосовує політику з'єднання та моделі цього ключа. `enforceApiKeyPolicy()`
поважає цей заголовок лише разом з носієм самопетлі, тому він може лише
звузити доступ, а ідентифікатор, який не розв'язується, відхиляється.

Якщо жодна модель зору не дозволена для ключа, шлях опису відступає, і
запит проходить без змін, таке ж поведінка fail-open, як у вимкненого
захисного механізму (мета `{ skipped: true, reason: "no_permitted_vision_model" }`).
Запити без ключа та ключі без цих обмежень поводяться точно так само, як і раніше.

#### Завдання-обізнаний опис запиту (`modalityBridgeVisionTaskAware`)

За замовчуванням **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) додає
текст **останнього повідомлення користувача** (обрізаного до 500 символів) до базового
підказки опису, направляючи опис на те, що насправді запитав користувач
(шаблон codex-vision-proxy) і запитуючи модель зору транскрибувати видимий
текст. Якщо прапор вимкнено — або немає тексту користувача — базова підказка використовується без змін.

Запит OpenAI-сумісного запиту самого циклу опису (`callVisionModelSingle()`
в `visionBridgeHelpers.ts`) завжди запитує `image_url.detail: "high"` —
безумовно, для кожного виклику/постачальника, не залежачи від будь-якого сигналу клієнта.
Зразки з низькою деталізацією погіршують точність OCR для саме тієї задачі транскрипції тексту, на яку запитує цей підказка, тому виклик опису завжди запитує високу
деталізацію, незалежно від того, який рівень деталізації використовувався в оригінальному вхідному запиті. Це
впливає лише на внутрішнє тіло запиту опису; це не змінює, як
OmniRoute пересилає власний `image_url.detail` виклику на первинний запит —
цей за замовчуванням застосовується окремо, і лише для виявлених клієнтів OpenCode, в
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Гілка формату проводів Anthropic для самого циклу опису не має поля `detail`
і не підлягає жодному з цих за замовчуванням.

#### Обмеження виходу опису (`modalityBridgeVisionMaxChars`)

| Ключ                           | За замовчуванням | Діапазон          |
| ------------------------------ | ---------------- | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`              | `0` або 100–50000 |

`0` (за замовчуванням) означає **без обмежень** — опис, повернутий
`callVisionModel()`, передається без змін, зберігаючи існуючу
поведінку. Будь-яке значення в діапазоні 100–50000 обрізає опис з
суфіксом `…` перед тим, як його знову вставити як `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` в `src/lib/guardrails/visionBridge.ts`).
Підвищте це для завдань OCR з великою деталізацією, де наступна модель потребує
повної транскрипції; зменште його, щоб обмежити використання токенів на балакучих моделях зору.
Поле панелі приладів знаходиться на вкладці Візуалізація в розширеній панелі
(`modality-bridge-max-chars` в `ModalityBridgeVisionTab.tsx`) і обмежує будь-яке
значення між 1 і 99 до 100, залишаючи явне `0`
незмінним — `0` є дійсним значенням Zod саме по собі
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто
"незадане" за замовчуванням.

#### Кеш опису (`modalityBridge/bridgeCache.ts`)

Кеш LRU + TTL в пам'яті для виходів опису, спільний для всього процесу.
Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` з
форматуванням з довжиною префікса (без зіткнень межі полів). Компонент моделі є
**налаштованою** моделлю моста, а не моделлю, яка насправді відповіла —
`callVisionModel` може внутрішньо повертатися, і ключування за спробою фрагментувало б кеш. Невдалі описи ніколи не кешуються. Налаштування:

| Ключ                            | За замовчуванням | Діапазон |
| ------------------------------- | ---------------- | -------- |
| `modalityBridgeCacheEnabled`    | `true`           | —        |
| `modalityBridgeCacheTtlMinutes` | `60`             | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`            | 10–5000  |

#### Нормалізація віддалених зображень (самоциклічний опис/base64 отримання)

Коли міст отримує **віддалене** зображення самостійно — само-виклик опису Anthropic
та конверсія base64 формату claude-wire
(`ensureBase64ImagesForClaudeWire`), обидва через
`fetchRemoteImageAsDataUri()` в `visionBridgeHelpers.ts` — отримане дані
URI проходить через `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) перед тим, як бути вбудованим у запит моделі зору. Занадто великі зображення зменшуються до **2048px довгої сторони** (відповідає
обмеженню зміни розміру, яке OpenAI/Anthropic вже застосовують на сервері), що зменшує
байти/затримку завантаження, не змінюючи те, що бачить модель зору. Зміна розміру
використовує `sharp`, завантажений через динамічний імпорт: на платформі, де її рідний
бінарний файл не вдається завантажити, `normalizeDataUri()` **ніколи не викидає** — він повертається
до проходження оригінальних байтів, тому шлях опису/конверсії base64
завжди залишається працездатним. Небайтові дані (отримання, яке не повернуло
декодоване зображення) також проходять без змін. Ця нормалізація
обмежена зображеннями, які міст отримує для свого власного само-виклику — вона ніколи
не застосовується до сирого навантаження виклику, відповідно до принципу мутації лише за згодою (Жорстке правило #20).

#### Схема налаштувань + міграція

Нові ключі `modalityBridge*` перевіряються Zod у `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, тріо `modalityBridgeCache*`, і група
`modalityBridgeAudio*`, що використовується Мостом Аудіо. Міграція
`141_modality_bridge_settings.sql` копіює існуючі значення
`visionBridge*` до відповідних нових ключів (ідемпотентна, ніколи не перезаписує
значення `modalityBridge*`, встановлене оператором); старі ключі залишаються прийнятими як
резервне читання на один цикл випуску.

#### Заголовок прозорості + статистика

Відповіді, перетворені описом, містять
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(створений `buildModalityBridgeHeader()` в `modalityBridge/bridgeStats.ts`,
позначений `withModalityBridgeHeader()` в `src/sse/handlers/chatHelpers.ts`).
Перенаправлені запити не отримують **жодного** заголовка — навантаження залишалося незмінним, і зміна моделі вже видно в полі `model` тіла відповіді.

`GET /api/modality-bridge/stats` (управлінська авторизація, той же рівень, що й
`GET /api/settings`) повертає в пам'яті лічильники за модальностями
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` та
`video`. `averageLatencyMs` використовує `latencySamples`, а не всі спроби, як
своєму знаменнику; операція без вимірювання не створює зразок нульової
мілісекунди. `bridged` залишається зворотно сумісним псевдонімом для успішних
конверсій; невдалі спроби не збільшують його.
Лічильники скидаються при перезапуску процесу за дизайном
(телеметрія, не облік).

#### Налаштування панелі приладів

Спеціальна сторінка панелі приладів знаходиться за адресою
`/dashboard/settings/modality-bridge`. Її URL-адресні вкладки `Vision`, `Audio`
та `Video` зберігають параметри запиту під час зміни значення `tab`.
Вкладка Vision відкриває можливості активації, режим, вибір моделі (включаючи
автоматичну за замовчуванням), підказки, що враховують завдання, розширені
обмеження на таймаути/зображення/довжину опису/кеш, лічильники
виконання та захищений запит зразка. Вкладка Audio також активна: вона відкриває
можливості активації, вибір моделі лише для STT з Auto, обмеження таймауту/максимальної
тривалості, аудіо лічильники та тест зразка `input_audio`. Вкладка Video є функціональною: вона
повідомляє про стан виконання FFmpeg/ffprobe — один з чотирьох явних станів UI
(`unknown`, поки зразок в обробці або не зміг завершитися, `restricted` на
не-циклозворотному хості панелі приладів, де зразок пропускається на стороні
клієнта, `unavailable`, як тільки зразок перевіряється і підтверджується як відсутній,
або `available` з версіями FFmpeg/ffprobe) — зберігає
обмеження enable/model/frame/video/timeout, фільтрує вибір моделі до моделей,
які підтримують зір, і відкриває аудіо лічильники.

Колишня картка Vision Bridge в налаштуваннях AI є сумісним посиланням на
нову сторінку; вона більше не має другої копії форми. Постачальники медіа також
посилають робочі процеси Image-to-Text та Speech-to-Text до відповідних вкладок
Modality Bridge, не видаляючи існуючий майданчик Speech-to-Text.

**Обхід допуску самопетлі:** коли виклик опису маршрутизується через
власну самопетлю OmniRoute `/v1` (нестандартна модель постачальника), підзапит
надсилає `x-omniroute-admission-bypass: internal` і автентифікується з
вирішеною обліковою інформацією самопетлі — локальним `sk_omniroute` у локальному
режимі або налаштованим оператором ключем `OMNIROUTE_API_KEY` / `ROUTER_API_KEY`
(#1350), щоб розгортання з `REQUIRE_API_KEY=true` все ще могли виконувати виклик
опису. Обхід
вшановується лише для цих точних облікових даних, тому зовнішні клієнти не можуть
використовувати заголовок для обходу допуску.

Спадкові значення живуть у `src/shared/constants/visionBridgeDefaults.ts`; нові
значення за замовчуванням для режиму/завдання/кешу та резолвер налаштувань
знаходяться в `src/shared/constants/modalityBridgeDefaults.ts`. Захисна
система відкриває параметр конструктора `deps`, щоб тести могли впроваджувати
підроблені реалізації `getSettings` та `callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехоплює запити чату з аудіо до того, як вони досягнуть цілі, яка не
відомо приймати аудіо-вхід. Він ніколи не перенаправляє запит чату: аудіо частини
транскрибуються через існуючу точку кінцевого OpenAI, що підтримує мультимодальність,
і вибрана модель чату продовжує з текстовими транскрипціями.

Процес:

1. Визначте `supportsAudio` через `getResolvedModelCapabilities()`. Явні
   метадані реєстру постачальників переважають, потім статичні метадані моделі,
   потім синхронізовані `modalities_input`. Оголошений список вхідних даних без
   `audio` є `false`; жодних доказів можливостей залишається `null`. Як `false`, так і
   `null` активують консервативний міст, тоді як `true` обходить його.
2. Визначте налаштування `modalityBridgeAudio*` та витягніть сплітовані
   верхні аудіо частини з кожного повідомлення через спільний детектор
   `detectMediaParts()`. Підтримувані форми проводів — це OpenAI `input_audio`,
   `audio_url` та `source.media_type: "audio/*"`. Вкладене аудіо виявляється для
   маршрутизації, але не видаляється спліт-путем. Робота обмежена `modalityBridgeAudioMaxClips`;
   пізні частини залишаються незайманими.
3. Вшануйте налаштований `provider/model`, або дозвольте `selectAudioBridgeModel()`
   пройти через `AUDIO_TRANSCRIPTION_PROVIDERS` у стабільному порядку каталогу та
   вибрати першу модель з використаною активною обліковою інформацією постачальника.
4. `callAudioTranscription()` перетворює аудіо base64/data-URI в мультимодальний
   `file`, або завантажує віддалений `audio_url` через публічно доступний вихідний
   захист з прив'язкою DNS та обмеженням у 25 МБ. Потім він POST-ить файл і
   вибрану модель до локальної самопетлі `/v1/audio/transcriptions`, автентифікованої
   з `resolveSelfLoopBearer()`. Існуючий маршрут транскрипції виконує нормальний
   пошук облікових даних, обробку охолодження/обмеження швидкості та відправку
   постачальника.
5. Успішні виклики замінюють свої частини на `[Audio N]: <transcript>`. Виклики
   виконуються з `Promise.allSettled`: індивідуальна помилка зберігає ту оригінальну
   аудіо частину (#4012 контракт). Якщо кожен виклик зазнає невдачі, а ціль
   доведено `supportsAudio === false`, частини стають
   `[Audio N]: (недоступно — жодного STT постачальника не підключено)` (#8430 контракт). Для
   невідомої цілі (`null`) результат з усіма невдачами залишається незайманим. Доведена
   ціль лише для тексту без використаної облікової інформації STT отримує той же
   явний шаблон без виконання мережевого виклику.

Успішні транскрипції використовують кеш LRU/TTL Modality Bridge на рівні процесу. Ключ
поєднує аудіо посилання, стабільну мітку операції `audio-transcription` та вибрану
модель STT; невдачі ніколи не кешуються. Аудіо спроби оновлюють спільні
лічильники `bridged`, `cacheHits`, `failures` та `lastUsedAt`.
Перетворені відповіді несуть
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; незаймані
запити не отримують сегмент Audio Bridge.

Налаштування виконання підтримуються базою даних і перевіряються Zod:

| Ключ                          | Значення за замовчуванням | Діапазон        |
| ----------------------------- | ------------------------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`                    | —               |
| `modalityBridgeAudioModel`    | `""`                      | Auto або STT ID |
| `modalityBridgeAudioTimeout`  | `60000`                   | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`                       | 1–10            |

Спільний кеш залишається під контролем `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` та `modalityBridgeCacheMaxEntries`.

### Відео міст (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехоплює верхні частини відео в Chat Completions `messages` та Responses
API `input` перед викликом цільового об'єкта без відомої нативної підтримки відео.
Підтримувані формати: `input_video`, `video_url`, `video_source`, HTTPS URL,
та `data:video/*;base64,...` data URI. Звичайні імена файлів у тексті не розглядаються
як відео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) відповідає за проходження запиту,
перевірку можливостей/політики, агрегацію за запитом та корисне навантаження відповіді.
Робота з відео — отримання, кешування всього результату, опис послідовності кадрів
(яка об'єднує будь-який аудіо транскрипт, оголошений викликачем), та метрики/скасування/очищення
за спробами — прихована за `processVideoPart` у `videoBridgePipeline.ts`,
яка викликається один раз для кожної частини відео всередині циклу `preCall`.
Цей модуль також визначає явні портові межі `VideoMediaBrokerPort`
(отримання байтів та витягування зразків кадрів), `VideoAudioTranscriptionPort`
(об'єднання аудіо транскрипту, оголошеного викликачем, з зразковими підписами), та
`VideoDrilldownPort` (спадковий формат сирого зберігання). Продукційний STT та зберігання кадрів
складаються навколо описового порту через `createVideoSttAdapter` та
`createVideoDrilldownAdapter`; останній використовує спільний непрозорий цикл життя.

Публічний шлях запиту `/v1` ніколи не імпортує і не викликає підпроцес. Віддалені
відео завантажуються в межах 50 МіБ; вбудовані base64 відео мають
консервативний ліміт у 36 МіБ декодованого розміру на відео, щоб модель/повідомлення/обгортка
могли залишатися в межах публічного ліміту прийому JSON запитів у 50 МіБ. Довжина вбудованого
та оцінки декодованого розміру перевіряються перед виділенням. HTTPS
вимагається на початковому віддаленому URL та кожному перенаправленні, використовуючи існуючий
публічно-тільки вихідний захист з прив'язкою DNS. Байти потім перетинають точну внутрішню
межу `POST /api/modality-bridge/video/extract`. Цей маршрут є як
`LOCAL_ONLY`, так і `SPAWN_CAPABLE`, приймає лише аутентифікований запит
довереного циклу зворотного зв'язку на процес, і ніколи не приймає URL, шлях до файлової системи,
виконуваний файл або список аргументів. Конвеєр розміру тіла API та інкрементальний читач тіла
обробника незалежно забезпечують ліміт вхідних байтів у 50 МіБ. Його обмежена черга виконує
одне витягнення за раз, дозволяє чотири очікуючі завдання та обмежує очікуючий вхід до
100 МіБ.

Всередині брокера `ffprobe` читає приватний локальний файл; фіксований формат
дозволів виключає плейлисти та формати маніфестів. Для дозволених контейнерів сімейства MOV
зовнішні посилання на дані MOV залишаються вимкненими за замовчуванням, і фіксована команда не
погоджується на них. Як `ffprobe`, так і `ffmpeg` використовують
дозволений протокол лише `file`, один потік, фіксовані масиви аргументів, без оболонки,
та виконувані файли, які вирішуються з `PATH`. Потоки з прикріпленими зображеннями не є
ігровими кандидатами. Усі ігрові потоки повинні відповідати обмеженням, і явний
потік за замовчуванням віддається перевагу перед детермінованим найнижчим індексом
резерву. Відео обмежені 600 секундами, 8192 пікселями на вимір, та
33,554,432 пікселями джерела. FFmpeg зразковує 1–16 середніх JPEG кадрів, зменшує довгу
сторону до максимуму 1024 пікселів без збільшення менших вхідних даних, і
ніколи не отримує URL. Вибірка є `uniform` за замовчуванням. Додаткові
політики `scene_aware` та експериментальна `segment_aware` виконують один додатковий
фіксований прохід FFmpeg над вже перевіреним локальним потоком, вибирають обмежені
часові мітки сцен `showinfo`, та детерміновано повертаються до тих же
однорідних середніх значень при збоях детектора, тайм-аутах, неправильно сформованому виходу
або порожньому набору кандидатів. Режим, обізнаний про сегменти, виділяє зразки середніх значень пропорційно
перевіреним інтервалам сцен; докази, обізнані про сегменти, та поведінка резерву
деталізовані нижче. Жорсткий ліміт у 16 кадрів застосовується
після вибору в кожній політиці. Коли запит, обізнаний про сцену, має лише
один кадр бюджету, він використовує однорідне середнє значення активного повного відео або фокусного
вікна та повідомляє `policyEffective: uniform`: один вибраний кадр сцени
не може зберегти обидва тимчасові кінці. Викликач може за бажанням надати
кінцеве фокусне вікно (`start`/`end` секунди); межі обмежуються тривалістю медіа,
реверсовані або нескінченні вікна відхиляються, і всі політики вибірки виконуються лише
всередині нормалізованого інтервалу. Отримане
вікно включається в метадані вибірки та в неперевірений префікс опису,
щоб подальші моделі могли відрізнити фокусований уривок від повної
хронології.

Семантичний фокус підпису є окремим, явним налаштуванням. Режим аналізу за замовчуванням `full`
зберігає існуючий запит кадру та ніколи не пересилає текст запиту до моделі підпису. У режимі `focused`
міст читає лише останній непорожній текст/вхідний текст, написаний користувачем, з того ж контейнера Chat або Responses,
нормалізує його до NFC, зменшує контрольні символи та пробіли,
та обмежує його до 500 кодових точок Unicode. Порожній результат повертається до
точного запиту `full`. Використовуваний підказка серіалізується як JSON у спеціальному
блоці неперевіреного користувача та може лише пріоритизувати спостережувані деталі; вона
не може переважити окреме попередження проти слідування інструкціям, видимим
або чутним у медіа. Текстовий фокус ніколи не виводить `start`/`end` або змінює
тимчасовий зразок.

#### FU-07 структурні сегменти доказів

`segment_aware` використовує один обмежений попередній аналіз вже перевіреного
місцевого відеопотоку. Фіксований фільтровий ланцюг спочатку масштабує до максимуму 320 пікселів
в ширину, виявляє зміни сцени та заморожені інтервали, а потім вибірково зразки на 1 кадр на
секунду для розмиття, середньої яскравості та просторової/тимчасової інформації. Прохід
обмежений 600 структурними зразками, одним потоком FFmpeg/filter, тим самим
протоколом лише для `file` та контейнерними дозволами, обмеженням виходу процесу в 1 МіБ,
і максимум 30 секундами всередині спільного аборту/термінації брокера. Він ніколи
не приймає команду, фільтр, шлях або URL з запиту.

Структурні значення є детермінованими доказами вибірки, а не семантичним
розумінням відео. Вони не виводять суб'єкти, дії, підписи, мову чи наміри користувача. Межі сцени та замороження формують сегменти; покриття замороження, розмиття,
експозиція, просторові деталі та тимчасові зміни лише впливають на те, як існуючий
бюджет у 1–16 кадрів розподіляється. Повністю заморожений сегмент обмежений одним кадром,
в той час як незаморожені сегменти конкурують за залишковий бюджет. Коли межі
перевищують кількість кадрів, зберігається рівномірне покриття хронології, щоб швидкі ранні
вирізи не могли приховати довгий сегмент. Межі сцени в межах 1-секундної
аналітичної роздільної здатності межі замороження об'єднуються.

Відсутні фільтри, неправильно сформовані/порожні докази, помилка детектора або обмежений
тайм-аут попереднього аналізу відкриваються до точної рівномірної політики середини. Аборт
виклику або термін брокера не відкривається: він завершує процес, що виконується,
запобігає подальшому вилученню кадрів, а приватне тимчасове дерево
видаляється в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` генерує детерміновані реальні FFmpeg
фікстури для заощаджень на підписах після дедуплікації, розподілу бюджету щільного руху,
доказів розмиття/експозиції/SI-TI, швидких вирізів з довгим хвостом та помилок
поступового зникнення. Він записує час стіни попереднього аналізу і, де доступно `/usr/bin/time`,
дочірній CPU та пікову RSS. Його перевірки якості є лише структурними оракулами.
Якість реальної моделі підписів залишається `HOLD`, оскільки цей механізм не має
авторизованої кінцевої точки або замороженого судді. Грошові заощадження також залишаються `HOLD`
якщо `--caption-cost-per-call-usd` не надає явну позитивну оцінку за виклик; скрипт ніколи не
фабрикує жоден з результатів.

Кожен кадр обмежений 4 МіБ, всі сирі кадри разом до 23 МіБ, а
серіалізована відповідь брокера до 32 МіБ. Приватний тимчасовий каталог видаляється
в `finally`. OmniRoute не пакує FFmpeg і не приймає власний
шлях до виконуваного файлу. Перед підписуванням місток застосовує консервативний
попередній аналіз візуальної дедуплікації: кожен JPEG зменшується до 16×16 градацій сірого
і порівнюється лише з останнім збереженим кадром. Для запитуваного бюджету підпису
вище одного кадру, вилучення постачає
обмежений пул кандидатів до двох бюджетів і ніколи більше 16 кадрів.
Запитуване обмеження застосовується лише після дедуплікації, з першим і фінальним
обраними кандидатами, збереженими під час остаточного звуження, коли бюджет становить щонайменше
два. Версійна
`grayscale-16x16-mean-cells-v2` політика використовує більше з середнього дельти яскравості та
співвідношення клітинок ескізу, чия нормалізована дельта становить щонайменше 0.05. Поріг
дублювання є сталою 0.04, обраною для передбачуваності, а не виставленою як налаштування
виконання. Цей вторинний
висококонтрастний сигнал зберігає невеликий рух і видимі зміни тексту, які можуть бути приховані
порівнянням лише середнього. Помилки компаратора або декодера відкриваються і зберігають
покриття. Вихідні метадані розділяють вилучених кандидатів, успішно використані
кадри та візуальні дублікати, які були відкинуті.

Явно позначена частина відео може запитувати таймстампований контактний лист. Місток
будує максимум 4-колонну, 16-кадрову сітку JPEG. Кожна клітинка розміром 512 пікселів
вписує свій вихідний таймстамп у висококонтрастну нижню смугу, в той час як ті ж таймстампи
залишаються в текстових метаданих для подальшої асоціації та аудиту. Повний
JPEG залишається обмеженим до 32 МіБ. Якщо `sharp` не може декодувати або скласти сітку, місток
повертається до окремих кадрів JPEG; аборт клієнта все ще поширюється
через операцію листа.

Докази просування навмисно відокремлені від синтетичного складання
мікробенчмарку. `scripts/perf/video-bridge-contact-sheet-eval.ts` визначає
схему-версію A/B для реальних моделей зору, сумісних з OpenAI. Він вимірює
звіти постачальника токенів, затримку стіни від початку до кінця (включаючи складання листа),
кількість викликів моделі та збереження фактів, визначених маніфестом. Сирі відповіді моделі не
записуються у звіт; лише SHA-256 дайджести та відповідні ID фактів зберігаються. Механізм не
здійснює жодних мережевих або платних викликів моделі, якщо не передано `--execute-real` і
не налаштовано `--model`, `OMNIROUTE_BASE_URL` та `OMNIROUTE_API_KEY`. Без
цього явного реального запуску його машинозчитуваний вердикт залишається `HOLD`; вимірювання
синтетичних навантажень/кількості викликів самі по собі не є доказами просування.

Окремий `scripts/perf/video-bridge-promotion-eval.ts` споживає спостереження FU-07 або
FU-09. Для прийняття просування потрібні всі вісім синтетичних сценаріїв плюс
санітизований реальний кліп, щонайменше три виміряні повторення для кожної ролі
та випадку, всі десять оголошених метрик, дайджести заморожених медіа/підказок/очікуваних-фактів/налаштувань,
унікальні ID спостережень та перевірений послідовний порядок A/B. Квиток виконання
прив'язує дайджест корпусу, точний кандидат SHA та ревізію моделі. Відсутні
або недійсні вимірювання залишаються `HOLD`, включаючи CPU понад 30 с, пікову RSS понад
512 МіБ або попередній аналіз понад 30 с. Це обмеження для прийняття доказів, а не нова
гарантія виконання RSS.

FU-07 вимагає принаймні 98% збереження якості та p95 затримки не більше 1.2x базового рівня, плюс або 0.05 абсолютне покращення середнього відгуку з урахуванням випадків, або принаймні 10% менше середніх викликів пост-дедуплікації. FU-09 вимагає принаймні 0.85 якості, 95% збереження, 20% зменшення p95 затримки та 10% зменшення токенів. Втрата критичних фактів, відповідність ін'єкцій або відсутнє використання заважають підвищенню. Один виконання не може підвищити нічого: `--previous-report` підтверджує два різні, неперекриваючі, послідовно придатні виконання однієї політики/моделі/кандидата/корпусу. Експеримент вибірки не може підтвердити експеримент контактного листа.

Збирачі повинні оцінювати відповіді в пам'яті та зберігати `responseDigest` плюс метрики та зв'язки спостережень, ніколи текст відповіді. Споживач також читає старі сирі спостереження, але ніколи не копіює цей текст у свої звіти. Приймається точно один з `responseDigest` або `rawResponseText` для кожного спостереження. Версійний дозволений список залишається порожнім з незмінним значенням за замовчуванням `hold`. Придатний запис вимагає посилання на його докази, політику, ревізію моделі, точний SHA кандидата, дайджест маніфесту та два різні ідентифікатори запуску; конфліктуючі контексти відхиляються. Ці метадані є контрактом аудиту, а не доказом того, що згадуваний файл містить справжні вимірювання. Перегляньте фактичні квитанції перед додаванням будь-якого запису. Кінцевий статистичний ендпоінт та панель управління відео відкривають консервативну готовність. Конфігурований псевдонім моделі сам по собі не встановлює її ревізію або SHA працюючого кандидата, тому поточна панель управління повідомляє `HOLD`, а не повторно використовує придатність з іншого контексту виконання. Явний експериментальний вибір залишається окремим від підвищення; жоден параметр за замовчуванням автоматично не змінюється.

Викликачі можуть прикріпити необов'язковий масив `transcript.cues` до підтримуваної частини відео, коли вони вже мають узгоджений текст. Кожен сигнал повинен містити `text`, скінченний інтервал `start`/`end` всередині перевіреної тривалості та дозволене `source` (`client`, `embedded` або `audio-bridge`); `confidence` за замовчуванням дорівнює `1` і повинен залишатися між `0` та `1`. Точно дубльовані сигнали об'єднуються. OmniRoute ніколи не починає транскрипцію з цих метаданих: перевірені сигнали копіюються в описаний результат з джерелом, впевненістю та інтервалом, і відображаються як ненадійні спостереження поряд з підписами кадрів. Неправильний, поза межами або без походження текст відхиляється, а не змішується в потік підписів. Обидва канали транскрипції тіла запиту нормалізують надане походження до `client`, включаючи самостверджені мітки `embedded` або `audio-bridge`. Тільки адаптер, що належить серверу, може призначити ці надійні мітки через аргумент `trustedSource`, що містить лише код; поле JSON запиту не може досягти цього аргументу. Текст транскрипції залишається ненадійним медіа-деривативним контентом, незалежно від його походження, і ніколи не повинен визначати авторизацію.

Розширений викликач може надати трек `audioTranscript` для того ж відео; він розглядається як текст, наданий клієнтом, а не доказ транскрипції сервера. Шов злиття запускає візуальні та аудіоспостереження під одним терміном і сигналом скасування, розташовує їх на спільній часовій шкалі, об'єднує точні дублікати та повідомляє частковий результат, коли лише одна сторона успішна. Неправильний `audioTranscript` знижується до цього часткового результату — візуальний опис зберігається, а аудіогілка записує очищений код помилки — замість того, щоб провалити все відео. Доступність за гілками, частковий прапор та очищені коди помилок зберігаються в описаному результаті, в метаданих захисних бар'єрів (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), в метаданих кешу результатів та в лічильниках злиття мосту. Шлях за замовчуванням Video Bridge не викликає перетворення мови в текст або не завантажує другу копію медіа; без цього явного треку він залишається лише відео.

**Збереження транскрипції (#12150 P1).** Це застосовується автоматично щоразу, коли Video Bridge (сам по собі за вибором) відображає сигнал транскрипції — немає окремого прапора збереження. Коли запит відображає будь-який сигнал транскрипції (оголошений викликачем `transcript` або злитий `audioTranscript`), захисний бар'єр позначає його як `videoBridgeObserved` і створює редаговану тінь відеоопису — ідентичне відображення, в якому кожне тіло вільного тексту сигналу замінюється на `[redacted-video-transcript]`, створене шляхом заміни структурованого поля сигналу перед складанням рядка (ніколи не шляхом парсингу сплющеного тексту, тому жоден вміст сигналу — ворожий чи звичайний, включаючи тіла, що містять `]`, такі як `[inaudible]`/`[music]` — не може вижити). Збережене тіло запиту журналу викликів замінює кожну частину тексту, отриману з відео, на цю редаговану тінь, відповідно до рівності вмісту; якорь `fullText` знову читається з завершеного вантажу захисного бар'єра перед викликом, тому збіг все ще успішний після пізніших захисних бар'єрів (маски для PII та облікових даних, пріоритети 10/95) переписують текст опису на місці та після системного запиту/передачі/ін'єкції пам'яті перетворюють масив повідомлень. Тіло, надіслане вгору до моделі, залишається незмінним. Спостережуваний запит також не заповнює жодну тривалу пам'ять (обидва витяги, отримані з запиту та відповіді, пропускаються), тому відповідь моделі не може повторити текст транскрипції в пам'яті.

**Сирі відеополя (#12430).** Коли місток увімкнено, а підтримка рідного відео невідома або відсутня, визначені поля `transcript`/`audioTranscript` також активують `videoBridgeObserved`, навіть після невдачі опису або обмеження `maxVideos`. `null` та порожні рядки враховуються; відсутні поля та невідеометадані не враховуються. Збережені копії редагують ці поля або пропускають запит, а кеші/пам'ять обходяться. Вантаж постачальника залишається незмінним.

Додаткові збережені копії використовують той же сигнал спостережуваного запиту. Сирий знімок запиту клієнта до охоронних бар'єрів, очікуючий запит в пам'яті та журнал раніше відхилених запитів структурно замінюють поля транскрипту у відеочастинах; рядкові підказки, синтезовані етапами конвеєра та передачею контексту, редагуються на місці збереженого тіла запиту. Збережений маркер `video_content_removed` змушує продовження `previous_response_id` завершуватися невдачею, а не відновлювати текст, який був навмисно відкинутий. Якщо спостережуваний запит втрачає свою тінь редагування перед записом, або навіть одна з кількох тіней відео не відповідає після пізніших мутацій запиту, збережене тіло запиту повністю опускається замість того, щоб зберігати частково відредагований транскрипт.

Для спостережуваного запиту відповідь моделі може цитувати будь-яку частину транскрипту без структурної межі підказки. Тому його збережений журнал викликів `responseBody` замінюється маркером пропуску; детальний артефакт конвеєра (який може включати тіла upstream/клієнта та частини потоку) не зберігається. Семантичні, ідемпотентні та кеші повторного розуміння обходять читання та запис для цього запиту. Запит постачальника та видима клієнтом відповідь залишаються незмінними. Ранні байти підтримки видаляються з тимчасового буфера, коли детальний артефакт опускається. Попередження Kiro про неправильно сформований EventStream повідомляє лише про кількість байтів корисного навантаження, ніколи про його вміст або сирий помилку парсера JSON. Це не стверджує, що кожна не пов'язана діагностика постачальника/плагіна була перевірена; ширший моніторинг збереженого зливу відстежується в #11658.

Внутрішній життєвий цикл `/api/modality-bridge/video/drilldown` є окремим кешем зворотного зв'язку/автентифікації токенів. Кожна операція також вимагає канонічного непрозорого ідентифікатора принципала. Перед тим, як виклик виробництва буде активовано, він повинен отримати цей ідентифікатор з автентифікованого орендаря і ніколи не повинен пересилати значення, вибране клієнтом. Ключі кешу пов'язують цього принципала з канонічними ідентифікаторами сесії та відео, зберігають лише їх ключі, отримані з SHA-256, і обмежують як читання, так і видалення до одного й того ж принципала. Кеш зберігає не більше 16 отриманих JPEG кадрів на запис, термін дії яких закінчується через десять хвилин, і підтримує обмежені читання `start`/`end` або явне видалення сесії.

Кожен принципал обмежений 16 записами та 64 MiB канонічних JPEG даних. Ці обмеження незалежні від глобального ліміту 64 записи/256 MiB: тиск квоти принципала видаляє лише найменш нещодавно використані записи цього принципала перед тим, як розглядати глобальне видалення LRU. Прострочені записи видаляються як з обліку принципала, так і з глобального обліку під час активності кешу, тоді як скасування та невдача валідації не фіксують часткову заміну.

Кеш відхиляє неконанічний Base64, надмірне заповнення, не-JPEG медіа, неправильно сформовані або обрізані JPEG, та JPEG, які викликають попередження під час обмеженого повного зображення `sharp` декодування. Він повторно кодує кожне прийняте зображення як канонічний JPEG, отримує ширину та висоту з декодованих байтів замість того, щоб довіряти полям виклику, і відкидає будь-які залишкові байти поліглотів, замість того, щоб зберігати їх. Лише обмежений канонічний стиснутий буфер зараховується до обох квот. Ліміт JSON по передачі включає накладні витрати Base64 для стелі 32 MiB декодованого вводу. Кожне збережене похідне значення записує свій перевірений формат/роздільну здатність JPEG, політику вибірки, версію похідного, час створення, хеш вмісту, обчислений сервером, та хеш батьківського посилання плюс хеш батьківського вмісту довіреного виклику. Скасування перевіряється між асинхронними фазами декодування/хешування перед атомарним комітом кешу.

Виробник продукції повторно використовує вже отримані кадри брокера лише після успішного візуального аналізу, без повторного завантаження/екстракції відео. Він вимагає оператора `modalityBridgeVideoDrilldownEnabled=true`, суворого перчастинного `drilldown: true` та автентифікованого ідентифікатора запису API-ключа. Значення принципала/сесії, оголошені клієнтом, ніколи не встановлюють право власності. Без усіх трьох умов він не хешує, не змінює розмір або не зберігає додаткові кадри. Невдача збереження зберігає придатну візуальну відповідь. Запити з дозволом обходять кеш результатів всього відео, тому кешовані результати ніколи не повторюють обробники.

Успішні відповіді JSON та SSE відкривають не більше чотирьох непрозорих обробників у обмеженому заголовку `x-omniroute-video-drilldown`. Авторизовані браузерні джерела можуть читати цей заголовок без розширення політики CORS. Нові обробники використовують `v1.<32-byte random base64url token>`, а реєстр зберігає лише їх SHA-256 хеші. Парсер читача/заголовка також приймає застарілі 64-шістнадцяткові токени. Автентифікований публічний споживач є `GET /api/v1/video-bridge/drilldown?handle=...`, незалежно контролюється `modalityBridgeVideoDrilldownRemoteEnabled=true`. Явне збережене значення false відкликає доступ, навіть коли застаріле значення `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` для середовища ввімкнено. Збереження продукції має аналогічне застаріле значення `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED`. Обидва застарілі значення за замовчуванням вимкнені.

Споживач отримує право власності з автентифікованого ключа, застосовує політику ключа та повертає той же 404 для невідомих, прострочених та обробників іншого ключа. Він приймає `variant=preview|standard|detail` (максимальний розмір JPEG 320/640/1280, ніколи не збільшений), `limit=1..8` (або застарілий псевдонім `frames`, ніколи обидва), нульовий `page` та необов'язкові `start`/`end` секунди фокусу. Дублікати ключів запиту та перевернуті вікна фокусу відхиляються. Кожен повернутий варіант має хеш свого фактичного вмісту та метадані фактичної роздільної здатності, пов'язані з збереженим джерелом. Варіанти отримуються під час читання, а не зберігаються як додаткові збережені копії. Відповідь JSON, включаючи Base64/конверт, обмежена 32 MiB; надмірна сторінка повертає 413, і клієнт повинен запитати менше кадрів. Читання перевіряють скасування навколо кожного зміни розміру та повторно перевіряють дійсність обробника перед поверненням. `DELETE` власником є ідемпотентним; видалення або закінчення терміну дії звільняє збережене джерело та облік використання.

Спільний магазин є локальним для процесу: дескриптори втрачають дійсність після перезапуску і не можуть бути передані між незалежними процесами OmniRoute. Статистика управління демонструє ефективну політику утримання/віддаленості та агрегує лише збережені записи/байти, ніколи медіа, посилання, ідентифікатори основних користувачів або дескриптори. Панель налаштувань відео показує ці значення і може зберігати обидва перемикачі згоди. Ця документація з реалізації не є доказом живого розгортання або просування; прийняття реальної моделі відстежується окремо.

Кадри підписуються послідовно з налаштованою моделлю відео. Порожнє перевизначення відео успадковує налаштування зору; якщо обидва порожні, автоматичний маршрутизатор зору вибирає ефективну модель, здатну до зору. Успішні підписи замінюють оригінальну частину зі стабільним префіксом `[Video description:` , який також позначає текст як ненадійне спостереження, отримане з медіа, і вказує подальшим моделям не слідувати інструкціям, знайденим у медіа. Ключі кешу підписів кадрів включають байти JPEG, запит, мітку часу та ефективну модель; лише успішні підписи кешуються. Записи кешу зберігають фактичну успішну модель виробника, включаючи резервну модель; місток повідомляє `mixed`, коли різні кадри були вироблені різними моделями. Успішний кеш використовує цю ідентичність виробника замість того, щоб переназивати її як запланований маршрут. Кеш результатів для всього відео ключується на кожному вході, що змінює вихід — запит, ефективну модель, політику вибірки, кількість кадрів, режим семантичного аналізу, SHA-256 відбиток нормалізованого підказки фокусу, вікно фокусу, `transcript`, `audioTranscript` та прапорець контактної таблиці — тому зміна будь-якого з цих вимірів є промахом кешу, ніколи застарілим повторним використанням. Версія політики візуальної дедуплікації, поріг та обмежена кількість кандидатних кадрів також є явними в ключі кешу результатів та метаданих; зміна політики, отже, не може повторно використовувати застарілий опис всього відео. Метадані кешу результатів v4 зберігають режим та відбиток, ніколи сире завдання користувача. Метадані захисних бар'єрів повідомляють про обидва запитувані та ефективні режими аналізу; запитуваний режим `focused` без придатного тексту користувача повідомляється як ефективно `full`.

Захисний бар'єр витягує кожну підтримувану частину відео, але не описує більше ніж `modalityBridgeVideoMaxVideos`. Для цілі, доведеної до `supportsVideo === false`, невдалі та перевищені відео стають явними безпечними текстовими маркерами, тому жодне сире відео не зберігається. Коли можливість невідома, ці частини залишаються недоторканими. Цілі з `supportsVideo === true` обходять місток. Сигнал скасування запиту клієнта поширюється через завантаження, чергу брокера, підпроцеси та виклики підписів; скасування зупиняються між відео і ніколи не відкриваються для сирого медіа.

Налаштування часу виконання підтримуються базою даних і перевіряються Zod:

| Ключ                                | Значення за замовчуванням | Діапазон / поведінка                                                                                           |
| ----------------------------------- | ------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`                   | Додатковий час виконання, за бажанням                                                                          |
| `modalityBridgeVideoAnalysisMode`   | `"full"`                  | `full` зберігає загальні підписи; `focused` використовує обмежений, ненадійний контекст останнього користувача |
| `modalityBridgeVideoModel`          | `""`                      | Успадковує модель мосту зору                                                                                   |
| `modalityBridgeVideoFrameCount`     | `8`                       | 1–16                                                                                                           |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`               | `uniform`, `scene_aware` або пропорційний `segment_aware`; збій детектора повертається до `uniform`            |
| `modalityBridgeVideoMaxVideos`      | `1`                       | 1–4                                                                                                            |
| `modalityBridgeVideoTimeout`        | `120000`                  | 1000–120000 мс                                                                                                 |

Значення тайм-ауту відео, що зберігаються в спадщині, вище 120 секунд обмежуються терміном брокера; нові записи налаштувань вище цього ліміту відхиляються. `GET /api/modality-bridge/video/runtime` вимагає довіреного штампованого локального зворотного зв'язку перед автентифікацією або перевіркою часу виконання, а потім вимагає управлінської автентифікації. Він повертає лише `available`, очищені версії FFmpeg/ffprobe та фіксовану причину, коли час виконання недоступний. Внутрішня точка витягання не є публічним API для завантаження: насичення черги повертає `503` плюс `Retry-After`, відключення виклику повертає `499`, а фіксований термін брокера повертає `504`. Перетворені відповіді додають `video->text;model=<visionModel>;parts=<videos>` до центрального заголовка `x-omniroute-modality-bridge`, не видаляючи сегменти зору або аудіо.

### Маска PII (`piiMasker.ts`)

Запускається на **обох** етапах.

- **`preCall`** клонує навантаження, проходить через `system`, `messages`, `input` та `prompt` (включаючи прості рядкові елементи) і застосовує `processPII()` (з `@/shared/utils/inputSanitizer`) до полів рядкового `content`/`text`. Коли `PII_REDACTION_ENABLED=true`, виявлені PII редагуються у вихідному навантаженні. Це незалежно від `INPUT_SANITIZER_MODE` (який лише контролює політику ін'єкції запиту). Коли редагування вимкнено, виклик фіксує кількість виявлень без переписування вмісту.
- **`postCall`** глибоко клонує відповідь, запускає `sanitizePIIResponse()` плюс маскувальник форми API Відповідей (`maskResponsesOutput` — охоплює `output_text` та `output[].content[].text`). Якщо відбувається будь-яке редагування, змінена відповідь замінює оригінал.

Захисний бар'єр ніколи не блокує; він лише анотує (`meta.detections`, `meta.redacted`) або переписує.

### Ін'єкція запиту (`promptInjection.ts`)

Виявляє ворожі структури в контенті, наданому користувачем, і забезпечує виконання
налаштованої політики. Поведінка керується змінними середовища та параметрами конструктора:

| Налаштування     | Змінна середовища                                                                                        | За замовчуванням | Ефект                                                                                                                                                                                               |
| ---------------- | -------------------------------------------------------------------------------------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Увімкнено        | `INPUT_SANITIZER_ENABLED`                                                                                | `true`           | Коли `false`, охоронна система короткочасно відключається.                                                                                                                                          |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                          | `warn`           | Політика ін'єкцій: `block`, `warn` або `log`. (`redact` приймається для зворотної сумісності, але **не** видаляє текст ін'єкції; запит на переписування PII контролюється `PII_REDACTION_ENABLED`.) |
| Поріг блокування | `blockThreshold` опція / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдонім `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`           | Мінімальна серйозність, необхідна для блокування. Середня серйозність за замовчуванням є лише для спостереження.                                                                                    |

**Пріоритет режиму** (`getMode`): параметри виклику `options.mode` →
`INJECTION_GUARD_MODE` **перекриття функціонального прапора** (Панель управління → Налаштування →
Функціональні прапори) → `INJECTION_GUARD_MODE` змінна середовища → `INPUT_SANITIZER_MODE` змінна середовища →
`warn`. Отже, перекриття панелі управління переважає над змінними середовища, тому UI функціональних прапорів контролює роботу охоронної системи в реальному часі (без перезапуску). Читання з бази даних є безпечним:
якщо виникає помилка, охоронна система повертається до поведінки на основі змінних середовища, а коли жодне
перекриття не встановлено, поведінка ідентична лише розв'язанню на основі змінних середовища.

Джерела виявлення:

1. `sanitizeRequest()` з `@/shared/utils/inputSanitizer` (спільний детектор,
   що використовується в інших частинах конвеєра).
2. Вбудовані `DEFAULT_GUARD_PATTERNS` (в даний час `system_override_inline` та
   `markdown_system_block`, обидва з серйозністю `high`).
3. Додаткові `customPatterns`, передані через параметри конструктора (рядки, регулярні вирази,
   або `{ name, pattern, severity }` записи).

Коли `mode === "block"` **і** принаймні одне виявлення відповідає порогу
серйозності, `preCall` повертає `{ block: true, message: "Запит відхилено:
виявлено підозрілий контент" }`. У режимах `warn`/`log` охоронна система веде журнал, але
дозволяє виклик. Спільний допоміжний метод `evaluatePromptInjection()` також експортується
для викликів, які потребують оцінки запитів без проходження через реєстр.

**Обмеження сканування (v3.8.20):** детектор перевіряє лише **перші 16 КБ**
об'єднаного тексту запиту — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байти) в
`src/shared/utils/inputSanitizer.ts`. Як `detectInjection()`, так і
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` перед виконанням
циклу шаблонів. Директиви ін'єкції розташовані ближче до початку введення, тому це
обмежує використання процесора/GC для вантажів розміром у кілька сотень КБ без послаблення виявлення (порівняйте
#3932, #4041).

### Маскувальник облікових даних (`credentialMasker.ts`)

Працює на **обох** етапах, останній у стандартному ланцюзі (пріоритет `95`). Видаляє
відомі шаблони API-ключів / секретних токенів з вихідного вантажу (вміст повідомлення,
аргументи виклику інструменту, результати інструменту) **і** відповіді постачальника, тому
облікові дані, вставлені в запит (або повернуті результатом інструменту), не витікають
до постачальника або назад до клієнта.

- **Тільки за бажанням**, та ж сама конвенція, що й для видалення PII (Жорстке правило #20-сусіднє):
  вимкнено, якщо `settings.credentialRedactionEnabled === true` **або**
  `CREDENTIAL_REDACTION_ENABLED=true`. Коли це вимкнено, охоронна система не виконує жодних дій —
  вона ніколи не блокує і ніколи не переписує.
- `redactCredentials()` обходить повне дерево вантажу/відповіді (`walkValue()`,
  безпечно для забруднення прототипу, безпечно для циклів через `WeakSet`) і замінює збіги на
  заповнювач `[REDACTED:<type>]`, клонує лише ті гілки, які насправді
  змінилися.
- `CREDENTIAL_PATTERNS` охоплює ключі постачальників LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токени VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платіжні ключі (Stripe, Square), ключі хмари
  (ключ доступу AWS, Twilio, SendGrid, Mailgun), приватні ключі / JWT,
  рядки з'єднання з обліковими даними (`mongodb://user:pass@...` тощо) та
  загальний шаблон заголовка `Authorization`/`x-api-key`/`api-key`/`apikey`.
  Ключі у формі заголовка (`authorization`, `x-api-key`, `api-key`,
  `apikey`) маскуються структурно (тільки значення, префікс схеми, такий як
  `Bearer `/`Basic ` зберігається) замість використання загального текстового регулярного виразу.
- Охоронна система ніколи не блокує; вона лише переписує (`modifiedPayload` /
  `modifiedResponse`) і анотує (`meta.credentialsRedacted`, `meta.count`).

Охорона регресії: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовий контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true коротко перериває ланцюг
  message?: string; // з'являється при блокуванні
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // повертається preCall для переписування запиту
  modifiedResponse?: TValue; // повертається postCall для переписування відповіді
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Гардурал сигналізує "без змін", повертаючи або `void`, `{}`, або
`{ block: false }`. Повернення `modifiedPayload`/`modifiedResponse` замінює
значення, що проходить через ланцюг для наступних гардуралів.
`signal?: AbortSignal` переносить життєвий цикл виклику в гардурали. Відміна запиту є навмисним винятком fail-open: медіа мости припиняють роботу та очищуються без відновлення сирого медіа до цілі, яка відома як така, що не підтримує його.

## Реєстр (`registry.ts`)

Синглтон `guardrailRegistry` надає:

- `register(guardrail)` — додає (або замінює за нормалізованим ім'ям) захисний механізм та пересортовує за зростанням `priority`.
- `clear()` / `list()` — допоміжні функції адміністрування.
- `runPreCallHooks(payload, context)` — ітерує активні захисні механізми, пропускає `payload` через `modifiedPayload` і зупиняється на першому `block: true`.
- `runPostCallHooks(response, context)` — той самий потік на стороні відповіді.
- `resetGuardrailsForTests({ registerDefaults })` — очищає стан та, за бажанням, повторно реєструє значення за замовчуванням для чистої ізоляції тестів.

Обидва виконавці повертають `{ blocked, payload|response, results, guardrail?, message? }`, де `results` — це масив записів `GuardrailExecutionResult`, що містять поля `blocked`, `skipped`, `modified`, `error` та `meta` для кожного захисного механізму, корисні для трасування.

### Вимкнення захисних механізмів для кожного запиту

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегує дедуплікований список імен захисних механізмів, які слід пропустити для поточного запиту. Джерела (всі необов'язкові, всі об'єднані):

- `apiKeyInfo.disabledGuardrails`
- Тіло запиту `disabledGuardrails` (верхнього рівня)
- Тіло запиту `metadata.disabledGuardrails`
- Заголовок `x-omniroute-disabled-guardrails` (або застарілий `x-disabled-guardrails`)

Значення можуть бути масивами рядків або рядком, розділеним комами; імена нормалізуються до нижнього регістру в kebab-case (`pii_masker` → `pii-masker`). Результат передається через `context.disabledGuardrails` до реєстру, який пропускає відповідні захисні механізми (`skipped: true` у `results`).

## Порядок виконання

Для кожного запиту, що проходить через `src/sse/handlers/chat.ts` та
`open-sse/handlers/chatCore.ts`:

1.  `resolveDisabledGuardrails(...)` створює список винятків з ключа API, тіла запиту
    та заголовків.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` запускає захисні механізми у порядку
    зростання пріоритету:
    - Вимкнені захисні механізми записуються як `skipped`.
    - `preCall` кожного захисного механізму може переписати корисне навантаження
      через `modifiedPayload`.
    - Перший `block: true` перериває ланцюжок, і обробник повертає
      відповідь про відхилення захисним механізмом.
3.  (Потенційно переписане) корисне навантаження надходить до комбінованої маршрутизації
    та вихідної диспетчеризації.
4.  Після формування відповіді `guardrailRegistry.runPostCallHooks(...)`
    запускає той самий ланцюжок на відповіді. `block: true` тут відкидає
    вихідну відповідь.

Захисні механізми, які викликають помилку, записуються з `error: <message>` та
реєструються через `logger.warn`, але ланцюжок продовжується — за задумом,
система працює за принципом "відмова-відкриття".

## Конфігурація

Змінні середовища, які читаються вбудованими захисними механізмами:

| Змінна                                | Використовується               | Ефект                                                                                                          |
| :------------------------------------ | :----------------------------- | :------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`             | Встановіть `false`, щоб повністю вимкнути виявлення.                                                           |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`             | Політика ін'єкцій: `warn`, `block` або `log`. Застаріле значення `redact` не переписує текст ін'єкції.         |
| `INJECTION_GUARD_MODE`                | `prompt-injection`             | Режим для захисту від ін'єкцій; також прапорець функції БД, який **перевизначає** змінні середовища (БД > ЗМ). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`             | Мінімальна серйозність, при якій `MODE=block` відхиляє: `high` (за замовчуванням), `medium` або `low`.         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`             | Застарілий псевдонім для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`                   | Якщо `true`, PII запиту редагується (незалежно від режиму ін'єкції).                                           |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (нижче за течією) | Контролює поведінку маскувальника на стороні відповіді.                                                        |

Захисні механізми Modality Bridge читають конфігурацію часу виконання зі сховища
налаштувань на основі БД (`getSettings()`), а не зі змінних середовища.
Основними ключами Vision є `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` та `modalityBridgeCacheMaxEntries`.
Застарілі ключі `visionBridge*` приймаються лише як задокументований
одноцикловий резервний варіант читання; записи на панелі керування
використовують основні ключі. Значення за замовчуванням та резервний
розв'язувач знаходяться в `src/shared/constants/modalityBridgeDefaults.ts`,
а застарілі константи зберігаються в
`src/shared/constants/visionBridgeDefaults.ts`.

Аудіо використовує `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` та `modalityBridgeAudioMaxClips`, а також спільні
налаштування `modalityBridgeCache*`. Аудіо не має резервного варіанту
застарілих ключів, оскільки ці ключі були введені зі схемою Modality Bridge.

Відео використовує `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`,
`modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos` та
`modalityBridgeVideoTimeout`, а також спільні налаштування `modalityBridgeCache*`.
Він вимкнений за замовчуванням, оскільки FFmpeg/ffprobe є необов'язковими
операційними залежностями, а створення субтитрів кадрів додає затримку та
витрати на модель.

## Користувацькі обмежувачі (Guardrails)

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Кроки:

1.  Створіть `src/lib/guardrails/myGuardrail.ts`, розширюючи `BaseGuardrail`.
2.  Реалізуйте `preCall` та/або `postCall`.
3.  Зареєструйте під час імпорту (виштовхніть з `registerDefaultGuardrails`) або
    викличте `guardrailRegistry.register(...)` під час виконання — реєстр замінює
    будь-який попередній обмежувач з тим самим нормалізованим ім'ям.
4.  Додайте тести до `tests/unit/` (існуючі приклади:
    `tests/unit/guardrails-registry.test.ts`,
    `tests/unit/prompt-injection-guard.test.ts`,
    `tests/unit/guardrails/visionBridge.test.ts`).

## Тестування

Використовуйте `resetGuardrailsForTests()` між тестами, щоб почати з відомого стану.
Передайте `{ registerDefaults: false }`, щоб почати з порожнього реєстру та
зареєструвати лише обмежувачі, що тестуються. Vision Bridge приймає впровадження
залежностей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge надає
еквівалентні точки для налаштувань, можливостей, вибору моделі STT, перевірок
облікових даних та транскрипції. Таким чином, тести можуть перевіряти обидва
потоки без доступу до БД або мережі.

## Покриття маршрутів захисту від ін'єкцій та червона команда (Фаза 8 · Блок D)

Захист від ін'єкцій (`createInjectionGuard` / `withInjectionGuard`) охоплює всі маршрути,
які приймають підказки користувача. Він враховує `INJECTION_GUARD_MODE` (за замовчуванням `warn` = лише логування;
`block` = повертає HTTP 400 `SECURITY_001`).

| Тип              | Маршрути                                                                                                                                             | Режим за замовчуванням |
| :--------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------- |
| Текст (існуючий) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                   |
| Генеративний     | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                   |
| Дані             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                   |

Вилучення тексту (`extractMessageContents`) охоплює `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Червона команда (нічна, `nightly-llm-security.yml`):** promptfoo перевіряє, що кожен маршрут блокує
корпус OWASP-LLM у режимі `INJECTION_GUARD_MODE=block`; garak запускає зонди (пропускає без секрету).
`moderations` включено для послідовності — оператори в режимі блокування можуть виключити його через
`resolveDisabledGuardrails`.

Нічний робочий процес (`.github/workflows/nightly-llm-security.yml`, cron + ручний
запуск) має два завдання:

- **`promptfoo-guard` (блокування)** — запускає `promptfoo eval -c promptfooconfig.yaml`
  з `INJECTION_GUARD_MODE=block`. Кожен ворожий випадок (наприклад, "ігнорувати всі
  попередні інструкції...", "jailbreaks" у стилі DAN) стверджує, що відповідь містить
  `error.code === "SECURITY_001"`, тобто обмежувач фактично відхилив запит.
- **`garak` (консультативний)** — запускає garak `--probes promptinject,dan,leakreplay`
  проти локального екземпляра OmniRoute (`http://localhost:20128/v1`). Залежить від
  секрету провайдера (`PROMPTFOO_PROVIDER_KEY`); пропускається без помилок і має суфікс
  `|| true`, тому він звітує без збою CI.

Покриття допоміжного обмежувача (`createInjectionGuard` / `withInjectionGuard`)
охоплює кожен маршрут `/v1`, що містить підказки; текст підказки витягується з
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` за допомогою
`extractMessageContents()` у `src/shared/utils/inputSanitizer.ts`.
