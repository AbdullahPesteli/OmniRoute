> **છેલ્લે અપડેટ કરેલું:** 2026-08-29 — v3.8.51 (Video Bridge ટ્રાન્સક્રિપ્ટનું મૂળ કૉલર દ્વારા જાહેર કરવામાં આવે છે,
> હજી સર્વર દ્વારા ચકાસાયેલું નથી — #11661 અનુસાર સ્પષ્ટ કરવામાં આવ્યું)

Guardrails, OmniRoute અને અપસ્ટ્રીમ પ્રદાતાઓ વચ્ચેની સીમા પર સુરક્ષા, નીતિ અને કન્ટેન્ટ રૂપાંતરણો લાગુ કરે છે. દરેક guardrail વિનંતીના payloads (`preCall`) અને અપસ્ટ્રીમ પ્રતિસાદો (`postCall`)નું નિરીક્ષણ કરી શકે છે (અને વૈકલ્પિક રીતે તેમને નકારી, રૂપાંતરિત અથવા ઍનોટેટ કરી શકે છે).

સિસ્ટમ **fail-open** છે: જો કોઈ guardrail કાર્યરત હોય ત્યારે અપવાદ ફેંકે, તો registry ભૂલ નોંધે છે અને વિનંતીને નિષ્ફળ કરવાને બદલે આગામી guardrail સાથે ચાલુ રહે છે. બ્લૉક કરવું હંમેશાં સ્પષ્ટ નિર્ણય (`block: true`) હોય છે, ક્યારેય આકસ્મિક ઘટના નહીં.

(જુઓ `registry.ts` → `registerDefaultGuardrails()`):

| ---------- | ------------------- | -------------- | --------------------- |
| `5`        | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`        | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |

### વિઝન બ્રિજ (`visionBridge.ts`) — મોડાલિટી બ્રિજ PR-1

**ગેર-વિઝન મોડેલ્સ** માટેના છબી ધરાવતી વિનંતીઓને અટકાવે છે અને અથવા તો
વિઝન-ક્ષમ મોડેલ તરફ સમગ્ર વિનંતીને ફરીથી માર્ગદર્શન આપે છે અથવા છબીના
ભાગોને ટેક્સ્ટ વર્ણન સાથે બદલવા માટે એક કન્ફિગરેબલ વિઝન મોડેલનો ઉપયોગ કરે છે
અપસ્ટ્રીમ કોલ પહેલાં. આ ટેક્સ્ટ-માત્ર પ્રદાતાઓને મલ્ટીમોડલ પેલોડ્સને પારદર્શક રીતે સંભાળવા દે છે.

પ્રવાહ:

1. જો લક્ષ્ય મોડેલ પહેલેથી જ વિઝનને સપોર્ટ કરે છે તો છોડી દો (જ્યારે તે
   ફરજિયાત-બ્રિજ યાદીમાં દેખાય છે `isVisionBridgeForcedModel`).
2. છબીના ભાગોને કાઢી નાખો `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), જે **એકીકૃત મીડિયા
   ડિટેક્ટર** `detectMediaParts()` ને委托 કરે છે `open-sse/utils/mediaParts.ts` — એક જ સત્યનો સ્ત્રોત જે કોમ્બો સુસંગતતા ફિલ્ટર સાથે શેર કરવામાં આવે છે.
   કાઢી નાખવું ટોચના સ્તરના ભાગો સુધી મર્યાદિત છે જે આકારો
   `replaceImageParts` પાછા સ્પ્લાઇસ કરી શકે છે (કાઢી નાખવું↔બદલવું કરાર): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, અને Responses API `input_image`. નેસ્ટેડ હિટ્સ અને
   સૂચક-માત્ર આકારો કોમ્બો-ફિલ્ટર સામગ્રી છે અને ક્યારેય કાઢી લેવામાં આવતી નથી.
   જો કશું મળતું નથી તો છોડી દો.
3. રનટાઇમ કન્ફિગરેશનને ઉકેલવા માટે `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): નવા `modalityBridge*`
   સેટિંગ્સ કી જીતે છે; વારસાગત `visionBridge*` કી એક **એક-ચક્ર
   પાછા ફરવું** (રોલબેક વિન્ડો) રહે છે. બ્રિજ અક્ષમ છે ત્યારે કોઈ મીડિયા ટ્રાવર્સલ પહેલાં છોડી દો.
4. મોડ પસંદકર્તા (`modalityBridgeVisionMode`, નીચેની કોષ્ટક જુઓ) નક્કી કરે છે
   ફરીથી માર્ગદર્શન આપવું કે વર્ણન કરવું. ફરીથી માર્ગદર્શન આપે છે `modifiedPayload` સાથે ફક્ત `model`
   બદલાયું, ઉપરાંત મેટા `{ rerouted, fromModel, toModel, imagesKept }`.
5. વર્ણન માર્ગ: છબીઓને `maxImages` પર મર્યાદિત કરો, કાર્ય-જાણકાર પ્રોમ્પ્ટ બનાવો,
   વર્ણન કેશને સલાહ લો, વિઝન મોડેલને **સાથે** બોલાવો
   (`Promise.allSettled`), અને `[Image N]: <description>` ટેક્સ્ટ ભાગોને
   તેમના સ્થાનમાં દાખલ કરો. એક નિષ્ફળ વર્ણન `null` આપે છે અને મૂળ છબીનો ભાગ **સંરક્ષિત** છે (#4012) — સિવાય કોમ્બો વર્ણન માર્ગે જ્યારે દરેક
   વર્ણન નિષ્ફળ જાય છે, જ્યાં એક પુષ્ટિ કરેલ ગેર-વિઝન અપસ્ટ્રીમને
   `(unavailable — no vision-capable provider connected)` સ્ટબ મળે છે (#8430).
6. પાછું આપો `modifiedPayload` + મેટા (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### મોડ પસંદકર્તા (`modalityBridgeVisionMode`)

| મોડ        | ડિફોલ્ટ | વર્તન                                                                                                                                                                                                                                                                                    |
| ---------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | વારસાગત હ્યુરિસ્ટિક, અસ્પષ્ટ (#6640/#7204): ગેર-કોમ્બો/`auto/` મોડેલો શ્રેષ્ઠ વિઝન મોડેલ તરફ ફરીથી માર્ગદર્શન આપે છે જો કે મૂળ મોડેલ પાસે ઉપયોગી પ્રમાણપત્રો હોય (ત્યારે વર્ણન); કોમ્બો લક્ષ્યો હંમેશા વર્ણન કરે છે.                                                                     |
| `describe` |         | હંમેશા વર્ણન કરો — ફરીથી માર્ગદર્શન બ્લોક સંપૂર્ણપણે છોડી દેવામાં આવે છે; વપરાશકર્તાનો પસંદ કરેલો મોડેલ હંમેશા જવાબ આપે છે.                                                                                                                                                              |
| `reroute`  |         | ફરજિયાત ફરીથી માર્ગદર્શન: કીપ-પ્રમાણિત-મોડેલ ગાર્ડને બાયપાસ કરવામાં આવે છે. ફરીથી માર્ગદર્શન-**લક્ષ્ય** પ્રમાણપત્ર ગાર્ડ હજુ પણ લાગુ પડે છે — જ્યારે કોઈ ઉપયોગી વિઝન લક્ષ્ય નથી, ત્યારે વિનંતી વર્ણન તરફ પસાર થાય છે જેથી કાચી છબીઓ ક્યારેય ટેક્સ્ટ-માત્ર બેકએન્ડ સુધી ન પહોંચે (#8430). |

ફરજિયાત મોડ્સ **પહેલાં** ઓટો હ્યુરિસ્ટિક ચાલે છે; `auto` વર્તન
પ્રિ-PR-1 ગાર્ડરેલ સાથે બાઇટ-આઇડેન્ટિકલ છે.

#### API-કી વ્યાપકતા (`visionBridgeKeyScope.ts`)

જ્યારે કોલરનું API કી `allowedConnections`, ક્વોટા પૂલ
(`allowedQuotas`) અથવા મોડેલો (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`)ને મર્યાદિત કરે છે, ત્યારે બ્રિજ ફક્ત
ફરીથી માર્ગદર્શન અને વર્ણન મોડેલોને પસંદ કરે છે જે કીનો ઉપયોગ કરી શકે છે, કનેક્શન પર જે કીનો ઉપયોગ કરી શકે છે. વર્ણન કૉલ પછી હંમેશા ઓમ્નીરૂટ સ્વયં-લૂપમાં જાય છે
`x-omniroute-self-loop-key-id` હેડર સાથે, તેથી પ્રાપ્ત થતી ચેટ વિનંતી
તે કીનું કનેક્શન અને મોડેલ નીતિ ફરીથી લાગુ કરે છે. `enforceApiKeyPolicy()`
તે હેડરને માત્ર સ્વયં-લૂપ બેરર સાથે માન્ય રાખે છે, તેથી તે ફક્ત
ઍક્સેસને સંકોચી શકે છે, અને એક આઈડી જે ઉકેલાતું નથી તે નકારી દેવામાં આવે છે.

જો કી માટે કોઈ વિઝન મોડેલ મંજૂર નથી, તો વર્ણન માર્ગ બાજુએ જ જાય છે અને
વિનંતી બદલાય વગર પસાર થાય છે, તે જ નિષ્ફળ-ઓપન વર્તન જે એક અક્ષમ
ગાર્ડરેલ (મેટા `{ skipped: true, reason: "no_permitted_vision_model" }`) છે.
કોઈ કી વગરની વિનંતીઓ, અને આ મર્યાદાઓ વગરની કીઓ, અગાઉની જેમ જ વર્તે છે.

#### કાર્ય-જાણકાર વર્ણન પ્રોમ્પ્ટ (`modalityBridgeVisionTaskAware`)

ડિફોલ્ટ **સાચું**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) **છેલ્લા યુઝર સંદેશા** (500 અક્ષરો સુધી કાપી) ના લખાણને આધાર વર્ણન પ્રોમ્પ્ટમાં ઉમેરે છે, વર્ણનને યુઝરે ખરેખર પૂછ્યું તે તરફ દોરી જાય છે (codex-vision-proxy પેટર્ન) અને દ્રષ્ટિ મોડેલને દૃશ્યમાન લખાણને લખવા માટે પૂછે છે. ફ્લેગ બંધ હોય ત્યારે — અથવા કોઈ યુઝર લખાણ ન હોય — આધાર પ્રોમ્પ્ટને અપરિવર્તિત રીતે ઉપયોગમાં લેવામાં આવે છે.

વર્ણન સ્વ-લૂપની પોતાની OpenAI-સંગત વિનંતી (`callVisionModelSingle()` `visionBridgeHelpers.ts` માં) હંમેશા `image_url.detail: "high"` માટે વિનંતી કરે છે — કોઈ શરત વિના, દરેક caller/provider માટે, કોઈ ક્લાયન્ટ સંકેત પર આધારિત નથી. નીચા-વિગતના નમૂનાઓ OCR ચોકસાઈને ખરાબ કરે છે તે ચોક્કસ લખાણ-લેખન કાર્ય માટે જે આ પ્રોમ્પ્ટ પૂછે છે, તેથી વર્ણન કોલ હંમેશા ઉચ્ચ વિગતો માટે પૂછે છે ભલે મૂળ inbound વિનંતી કઈ વિગતોના સ્તરનો ઉપયોગ કરે છે. આ માત્ર આંતરિક વર્ણન વિનંતી શરીરને અસર કરે છે; તે OmniRoute કેવી રીતે caller ની પોતાની `image_url.detail` ને મુખ્ય વિનંતી પર આગળ વધારવા બદલ બદલતું નથી — તે ડિફોલ્ટ અલગ રીતે લાગુ થાય છે, અને માત્ર શોધાયેલા OpenCode ક્લાયન્ટો માટે, `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) માં. વર્ણન સ્વ-લૂપનો Anthropic વાયર-ફોર્મેટ શાખામાં કોઈ `detail` ક્ષેત્ર નથી અને તે બંને ડિફોલ્ટથી અસંવેદનશીલ છે.

#### વર્ણન આઉટપુટ કૅપ (`modalityBridgeVisionMaxChars`)

| કી                             | ડિફોલ્ટ | શ્રેણી             |
| ------------------------------ | ------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`     | `0` અથવા 100–50000 |

`0` (ડિફોલ્ટ) નો અર્થ છે **કોઈ કૅપ નથી** — `callVisionModel()` દ્વારા પાછું મળતું વર્ણન અપરિવર્તિત રીતે પસાર થાય છે, વર્તમાન વર્તન જાળવી રાખે છે. 100–50000 શ્રેણીમાં કોઈપણ મૂલ્ય વર્ણનને `…` સોફિક્સ સાથે કાપે છે તે પહેલાં તે `[Image N]: <description>` તરીકે ફરીથી જોડાય છે (`VisionBridgeGuardrail.preCall()` `src/lib/guardrails/visionBridge.ts` માં). આને ઊંચી વિગતોવાળા OCR કાર્ય માટે વધારવું જ્યાં નીચેના મોડેલને સંપૂર્ણ લખાણની જરૂર છે; તેને ચેટી દ્રષ્ટિ મોડેલ પર ટોકન ઉપયોગને મર્યાદિત કરવા માટે ઘટાડવું. ડેશબોર્ડ ક્ષેત્ર Vision ટેબના એડવાન્સ્ડ પેનલ પર રહે છે (`modality-bridge-max-chars` `ModalityBridgeVisionTab.tsx` માં) અને 1 અને 99 વચ્ચેના કોઈપણ મૂલ્યને 100 ની જમીન સુધી મર્યાદિત કરે છે જ્યારે સ્પષ્ટ `0` ને અપરિવર્તિત રાખે છે — `0` પોતે જ માન્ય Zod મૂલ્ય છે (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), માત્ર "unset" ડિફોલ્ટ નથી.

#### વર્ણન કેશ (`modalityBridge/bridgeCache.ts`)

વર્ણન આઉટપુટ માટે મેમરીમાં LRU + TTL કેશ, શેર કરેલ પ્રક્રિયા-વિસ્તૃત. કી = `sha256(imageRef + composedPrompt + configuredBridgeModel)` સાથે લંબાઈ-પ્રિફિક્સ ફ્રેમિંગ (કોઈ ક્ષેત્ર-સીમા ટકરાવા નથી). મોડેલ ઘટક એ **કન્ફિગર કરેલ** બ્રિજ મોડેલ છે, જે મોડેલ ખરેખર જવાબ આપ્યો — `callVisionModel` આંતરિક રીતે પાછા પડી શકે છે, અને પ્રતિષ્ઠાન મુજબ કીંગ કરવાથી કેશને તૂટે છે. નિષ્ફળ વર્ણનો કેશમાં ક્યારેય નથી. સેટિંગ્સ:

| કી                              | ડિફોલ્ટ | શ્રેણી  |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### રીમોટ ઇમેજ નોર્મલાઇઝેશન (સ્વ-લૂપ વર્ણન/base64 ફેચ)

જ્યારે બ્રિજ **રીમોટ** ઇમેજને પોતે લાવે છે — Anthropic વર્ણન સ્વ-કોલ અને claude-wire-format base64 રૂપાંતરણ (`ensureBase64ImagesForClaudeWire`), બંને `fetchRemoteImageAsDataUri()` માં `visionBridgeHelpers.ts` દ્વારા — પરિણામે મળતું ડેટા URI `normalizeDataUri()` મારફતે પસાર થાય છે (`open-sse/utils/imageNormalize.ts`) પહેલાં દ્રષ્ટિ-મોડેલ વિનંતીમાં એમ્બેડ કરવામાં આવે છે. મોટા ઇમેજો **2048px લાંબા કિનારે** (જે OpenAI/Anthropic પહેલેથી જ સર્વર-સાઇડ પર લાગુ કરે છે) સુધી ઘટાડવામાં આવે છે, જે અપલોડ બાઇટ્સ/લેટન્સીને કાપે છે જ્યારે દ્રષ્ટિ મોડેલ શું જોવે છે તે બદલતું નથી. પુનઃઆકાર આપવું `sharp` નો ઉપયોગ કરે છે, જે ડાયનામિક આયાત દ્વારા લોડ થાય છે: એક પ્લેટફોર્મ પર જ્યાં તેની નેટિવ બાયનરી લોડ થવામાં નિષ્ફળ રહે છે, `normalizeDataUri()` **ક્યારેય ફેંકતું નથી** — તે મૂળ બાઇટ્સના પાસથ્રૂમાં પાછું પડે છે, તેથી વર્ણન/base64-રૂપાંતરણ માર્ગ હંમેશા કાર્યરત રહે છે. નોન-ઇમેજ બાઇટ્સ (એક ફેચ જે ડીકોડ કરી શકાય તેવી ઇમેજ પાછું આપતું નથી) પણ અપરિવર્તિત રીતે પસાર થાય છે. આ નોર્મલાઇઝેશન તે ઇમેજો માટે મર્યાદિત છે જે બ્રિજ તેના પોતાના સ્વ-કોલ માટે લાવે છે — તે ક Caller ના કાચા પાસથ્રૂ પેઇલોડ પર ક્યારેય લાગુ નથી થતું, ઓપ્ટ-ઇન-માત્ર મ્યુટેશન સિદ્ધાંત (Hard Rule #20) સાથે સુસંગત છે.

#### સેટિંગ્સ સ્કીમા + માઇગ્રેશન

નવી `modalityBridge*` કીઓ `updateSettingsSchema` માં Zod-પ્રમાણિત છે (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCache*` ત્રિકોણ, અને `modalityBridgeAudio*` જૂથ જે ઓડિયો બ્રિજ દ્વારા ઉપયોગમાં લેવાય છે. માઇગ્રેશન `141_modality_bridge_settings.sql` મૌજુદા વારસાગત `visionBridge*` મૂલ્યોને મેળ ખાતા નવા કીઓમાં નકલ કરે છે (ઇડેમ્પોટન્ટ, ક્યારેય ઓપરેટર-સેટ `modalityBridge*` મૂલ્યને ઓવરરાઇટ નથી કરે); વારસાગત કીઓ એક વાંચન ફોલબેક તરીકે એક રિલીઝ ચક્ર માટે સ્વીકારવામાં રહે છે.

#### પારદર્શિતા હેડર + આંકડા

વર્ણન-પરિવર્તિત પ્રતિસાદો ધરાવે છે `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` (જે `buildModalityBridgeHeader()` માં બનાવવામાં આવે છે `modalityBridge/bridgeStats.ts`, `withModalityBridgeHeader()` દ્વારા `src/sse/handlers/chatHelpers.ts` માં સ્ટેમ્પ કરવામાં આવે છે). ફરીથી માર્ગદર્શિત વિનંતીઓ **કોઈ** હેડર નથી — પેઇલોડ અપરિવર્તિત હતું અને મોડેલ સ્વાપ પહેલેથી જ પ્રતિસાદના શરીરના `model` ક્ષેત્રમાં સ્પષ્ટ છે.

`GET /api/modality-bridge/stats` (વ્યવસ્થાપન પ્રાધિકરણ, `GET /api/settings` સાથે સમાન સ્તર) મેમરીમાં પ્રત્યેક મોડાલિટી કાઉન્ટર્સ પાછા આપે છે `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` માટે `vision`, `audio`, અને `video`. `averageLatencyMs` તેના ગુણાંક તરીકે `latencySamples` નો ઉપયોગ કરે છે, બધા પ્રયાસો નહીં; સમય વિના એક ઓપરેશન શૂન્ય-મિલિસેકન્ડ નમૂનો બનાવતું નથી. `bridged` સફળ રૂપાંતરણો માટે પાછળની સાથે સુસંગત ઉપનામ તરીકે રહે છે; નિષ્ફળ પ્રયાસો તેને વધારતા નથી. કાઉન્ટર્સ પ્રક્રિયા પુનઃપ્રારંભ પર ડિઝાઇન દ્વારા પુનઃસેટ થાય છે (ટેલેમેટ્રી, ખાતાકીય નથી).

#### ડેશબોર્ડ રૂપરેખાંકન

વિશિષ્ટ ડેશબોર્ડ પૃષ્ઠ છે `/dashboard/settings/modality-bridge`. તેની URL-સરનામે `Vision`, `Audio`, અને `Video` ટેબ્સ `tab` મૂલ્ય બદલતા સમયે ક્વેરી પેરામીટર્સ જાળવે છે. Vision ટેબ સક્રિયતા, મોડ, મોડેલ પસંદગી (સ્વચાલિત ડિફોલ્ટ સહિત), કાર્ય-જાણકાર પ્રોમ્પ્ટિંગ, અદ્યતન ટાઈમઆઉટ/છબી/વર્ણન-લંબાઈ/કેશ મર્યાદાઓ, રનટાઇમ કાઉન્ટર્સ, અને એક સુરક્ષિત નમૂના વિનંતી પ્રદર્શિત કરે છે. Audio ટેબ પણ જીવંત છે: તે સક્રિયતા, STT-માત્ર મોડલ પિકર સાથે Auto, ટાઈમઆઉટ/મહત્તમ-ક્લિપ મર્યાદાઓ, ઓડિયો કાઉન્ટર્સ, અને એક `input_audio` નમૂના પરીક્ષણ પ્રદર્શિત કરે છે. Video ટેબ કાર્યાત્મક છે: તે FFmpeg/ffprobe રનટાઇમ રાજ્યને રિપોર્ટ કરે છે — ચાર સ્પષ્ટ UI રાજ્યોમાંથી એક (`unknown` જ્યારે પ્રોબ ઉડાનમાં હોય અથવા પૂર્ણ થઈ શકતું નથી, `restricted` એક નોન-લૂપબેક ડેશબોર્ડ હોસ્ટ પર જ્યાં પ્રોબ ક્લાયન્ટ-પક્ષે છોડી દેવામાં આવે છે, `unavailable` એકવાર પ્રોબ કરવામાં આવે છે અને ખોટું હોવાનું પુષ્ટિ કરવામાં આવે છે, અથવા `available` FFmpeg/ffprobe સંસ્કરણો સાથે) — સક્રિય/મોડલ/ફ્રેમ/વિડિયો/ટાઈમઆઉટ મર્યાદાઓ જાળવે છે, મોડલ પિકરને દ્રષ્ટિ-ક્ષમ મોડલ્સ સુધી મર્યાદિત કરે છે, અને વિડિયો કાઉન્ટર્સને પ્રદર્શિત કરે છે.

AI સેટિંગ્સ હેઠળનો પૂર્વવર્તી Vision Bridge કાર્ડ નવી પૃષ્ઠ માટે એક સુસંગતતા લિંક છે; તે ફોર્મની બીજી નકલ ધરાવતું નથી. મીડિયા પ્રદાતાઓ પણ છબી-થી-ટેક્સ્ટ અને ભાષણ-થી-ટેક્સ્ટ વર્કફ્લોને સંબંધિત મોડાલિટી બ્રિજ ટેબ્સ સાથે લિંક કરે છે, જે હાલના ભાષણ-થી-ટેક્સ્ટ પ્લેગ્રાઉન્ડને દૂર કર્યા વિના.

**સ્વ-લૂપ પ્રવેશ બાયપાસ:** જ્યારે વર્ણન કૉલ ઓમ્નીરૂટના પોતાના `/v1` સ્વ-લૂપ (અસામાન્ય પ્રદાતા મોડલ) મારફતે માર્ગદર્શિત થાય છે, ત્યારે ઉપ-વિનંતી `x-omniroute-admission-bypass: internal` મોકલે છે અને ઉકેલાયેલ સ્વ-લૂપ પ્રમાણપત્ર સાથે માન્યતા પ્રાપ્ત થાય છે — સ્થાનિક મોડમાં સ્થાનિક `sk_omniroute` સેન્ટિનલ, અથવા ઓપરેટર-કન્ફિગર કરેલ `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env કી (#1350) જેથી `REQUIRE_API_KEY=true` ડિપ્લોયમેન્ટ્સ વર્ણન કૉલ ચલાવી શકે. બાયપાસ માત્ર તે ચોક્કસ પ્રમાણપત્રો માટે માન્ય છે, તેથી બાહ્ય ક્લાયન્ટ header નો ઉપયોગ કરીને પ્રવેશને બાયપાસ કરી શકતા નથી.

વૈશ્વિક ડિફોલ્ટ્સ `src/shared/constants/visionBridgeDefaults.ts` માં રહે છે; નવા મોડ/કાર્ય-જાણકાર/કેશ ડિફોલ્ટ્સ અને સેટિંગ્સ રિઝોલ્વર `src/shared/constants/modalityBridgeDefaults.ts` માં રહે છે. ગાર્ડરેલ એક `deps` કન્સ્ટ્રક્ટર વિકલ્પ પ્રદર્શિત કરે છે જેથી પરીક્ષણો નકલી `getSettings` અને `callVisionModel` અમલને ઇન્જેક્ટ કરી શકે.

### ઓડિયો બ્રિજ (`audioBridge.ts`) — મોડાલિટી બ્રિજ PR-3

ઓડિયો ધરાવતી ચેટ વિનંતીઓને લક્ષ્ય સુધી પહોંચતા પહેલા અટકાવે છે જે ઓડિયો ઇનપુટ સ્વીકારવા માટે જાણીતી નથી. તે ક્યારેય ચેટ વિનંતીને ફરીથી માર્ગદર્શિત નથી કરતી: ઓડિયો ભાગો મૌજુદ OpenAI-સંગત મલ્ટિપાર્ટ અંતિમ બિંદુ મારફતે લખવામાં આવે છે અને પસંદ કરેલ ચેટ મોડલ લખાણના ટ્રાન્સક્રિપ્ટ સાથે ચાલુ રહે છે.

પ્રવાહ:

1. `supportsAudio` ને `getResolvedModelCapabilities()` મારફતે ઉકેલવું. સ્પષ્ટ પ્રદાતા-રજિસ્ટ્રી મેટાડેટા જીતે છે, પછી સ્થિર મોડલ મેટાડેટા, પછી સમન્વયિત `modalities_input`. `audio` વિના જાહેર કરેલ ઇનપુટ યાદી `false` છે; કોઈ ક્ષમતા પુરાવો `null` રહે છે. બંને `false` અને `null` સંરક્ષણાત્મક બ્રિજને સક્રિય કરે છે, જ્યારે `true` તેને બાયપાસ કરે છે.
2. `modalityBridgeAudio*` સેટિંગ્સને ઉકેલવું અને દરેક સંદેશામાંથી સ્પ્લાઇસેબલ ટોપ-લેવલ ઓડિયો ભાગો કાઢવા માટે શેર કરેલ `detectMediaParts()` ડિટેક્ટરનો ઉપયોગ કરવો. સમર્થિત વાયર આકારો OpenAI `input_audio`, `audio_url`, અને `source.media_type: "audio/*"` છે. નેસ્ટેડ ઓડિયો માર્ગદર્શિત કરવા માટે શોધવામાં આવે છે પરંતુ સ્પ્લાઇસ પાથ દ્વારા દૂર કરવામાં આવતું નથી. કાર્ય `modalityBridgeAudioMaxClips` દ્વારા મર્યાદિત છે; પછીના ભાગો અવિનાશિત રહે છે.
3. એક કન્ફિગર કરેલ `provider/model`ને માન્યતા આપો, અથવા `selectAudioBridgeModel()` ને સ્થિર કૅટલોગ ક્રમમાં `AUDIO_TRANSCRIPTION_PROVIDERS` ને ચલાવવા દો અને ઉપયોગી સક્રિય પ્રદાતા પ્રમાણપત્ર સાથે પ્રથમ મોડલ પસંદ કરો.
4. `callAudioTranscription()` base64/data-URI ઓડિયોને મલ્ટિપાર્ટ `ફાઇલ` માં રૂપાંતરિત કરે છે, અથવા જાહેર-માત્ર બહારના ગાર્ડ મારફતે 25 MB મર્યાદા સાથે એક દૂરના `audio_url` ને ડાઉનલોડ કરે છે. તે પછી ફાઇલ અને પસંદ કરેલ મોડલને સ્થાનિક `/v1/audio/transcriptions` સ્વ-લૂપમાં પોસ્ટ કરે છે, જે `resolveSelfLoopBearer()` સાથે માન્યતા પ્રાપ્ત છે. મૌજુદ ટ્રાન્સક્રિપ્શન માર્ગ સામાન્ય પ્રમાણપત્ર શોધ, કૂલડાઉન/દર-મર્યાદા હેન્ડલિંગ, અને પ્રદાતા વિતરણ કરે છે.
5. સફળ કૉલ્સ તેમના ભાગોને `[Audio N]: <transcript>` સાથે બદલે છે. કૉલ્સ `Promise.allSettled` સાથે ચલાવવામાં આવે છે: એક વ્યક્તિગત નિષ્ફળતા મૂળ ઓડિયો ભાગને જાળવે છે (#4012 કરાર). જો દરેક કૉલ નિષ્ફળ જાય અને લક્ષ્યને સાબિત કરવામાં આવે `supportsAudio === false`, તો ભાગો બની જાય છે `[Audio N]: (unavailable — no STT provider connected)` (#8430 કરાર). અજ્ઞાત લક્ષ્ય (`null`) માટે, એક તમામ-નિષ્ફળ પરિણામ અવિનાશિત રહે છે. એક સાબિત ટેક્સ્ટ-માત્ર લક્ષ્ય જે કોઈ ઉપયોગી STT પ્રમાણપત્ર ધરાવતું નથી તે નેટવર્ક કૉલ કર્યા વિના સમાન સ્પષ્ટ સ્ટબ પ્રાપ્ત કરે છે.

સફળ ટ્રાન્સક્રિપ્ટ્સ પ્રક્રિયા-વિસ્તૃત મોડાલિટી બ્રિજ LRU/TTL કેશનો ઉપયોગ કરે છે. કી ઓડિયો સંદર્ભ, સ્થિર `audio-transcription` ઓપરેશન લેબલ, અને પસંદ કરેલ STT મોડલને જોડે છે; નિષ્ફળતાઓ ક્યારેય કેશ કરવામાં આવતી નથી. ઓડિયો પ્રયાસો શેર કરેલ `bridged`, `cacheHits`, `failures`, અને `lastUsedAt` કાઉન્ટર્સને અપડેટ કરે છે. રૂપાંતરિત પ્રતિસાદો સાથે આવે છે `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; અવિનાશિત વિનંતીઓને ઓડિયો બ્રિજ વિભાગ પ્રાપ્ત નથી થતો.

રનટાઇમ સેટિંગ્સ DB-આધારિત અને Zod-માન્યતાપૂર્વક છે:

| કી                            | ડિફોલ્ટ | શ્રેણી           |
| ----------------------------- | ------- | ---------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —                |
| `modalityBridgeAudioModel`    | `""`    | Auto અથવા STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000      |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10             |

સાંજેદાર કેશ `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, અને `modalityBridgeCacheMaxEntries` દ્વારા નિયંત્રિત રહે છે.

### વિડિયો બ્રિજ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ચેટ પૂર્ણતાઓ `messages` અને પ્રતિસાદો API `input` માં ટોચના સ્તરના વિડિયો ભાગોને અવરોધિત કરે છે
જ્યારે કોઈ લક્ષ્યને ઓળખાયેલ સ્થાનિક વિડિયો સપોર્ટ વિના બોલાવવામાં આવે છે.
સમર્થિત આકારો છે `input_video`, `video_url`, `video_source`, HTTPS URLs,
અને `data:video/*;base64,...` ડેટા URI. ટેક્સ્ટમાં સાદા ફાઇલના નામોને વિડિયો તરીકે ગણવામાં આવતું નથી.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) વિનંતી પસાર કરવા, ક્ષમતા/નીતિની તપાસ, પ્રતિ-વિનંતી સંકલન, અને પ્રતિસાદ પેઢીનું માલિકી ધરાવે છે.
પ્રતિ-વિડિયો કાર્ય — પ્રાપ્ત કરવું, સમગ્ર-પરિણામ કેશ, ફ્રેમ ક્રમનું વર્ણન (જે કોઈ પણ caller-ઘોષિત ઓડિયો ટ્રાન્સ્ક્રિપ્ટને મિશ્રિત કરે છે), અને પ્રતિ-પ્રયત્ન મેટ્રિક્સ/રદ/સફાઈ — `processVideoPart` પાછળ છુપાયેલું છે
`videoBridgePipeline.ts` માં, જે `preCall` ના લૂપમાં દરેક વિડિયો ભાગ માટે એકવાર બોલાવવામાં આવે છે.
તે મોડ્યુલ સ્પષ્ટ પોર્ટ સીમાઓને પણ વ્યાખ્યાયિત કરે છે `VideoMediaBrokerPort`
(બાઇટ્સ મેળવવું અને નમૂનાકૃત ફ્રેમ્સ કાઢવું), `VideoAudioTranscriptionPort`
(નમૂનાકૃત શીર્ષકો સાથે caller-ઘોષિત ઓડિયો ટ્રાન્સ્ક્રિપ્ટને મિશ્રિત કરવું), અને
`VideoDrilldownPort` (પરંપરાગત કાચા-સ્ટોર આકાર). ઉત્પાદન STT અને ફ્રેમ જાળવણી
`createVideoSttAdapter` અને `createVideoDrilldownAdapter` દ્વારા વર્ણન કરેલ પોર્ટની આસપાસ રચાયેલ છે; છેલ્લું શેર કરેલ ઓપેક-હેન્ડલ જીવનચક્રનો ઉપયોગ કરે છે.

#### FU-07 બંધારણ સેગમેન્ટ પુરાવો

`segment_aware` પહેલેથી માન્ય સ્થાનિક વિડિઓ સ્ટ્રીમ પર એક બાઉન્ડેડ પ્રી-એનલિસિસ પાસનો ઉપયોગ કરે છે. નિશ્ચિત ફિલ્ટર ચેઇન પહેલા 320 પિક્સલ પહોળા સુધી સ્કેલ કરે છે, દૃશ્ય પરિવર્તનો અને જમતા અંતરાલોને ઓળખે છે, પછી ધૂંધળા, સરેરાશ લ્યુમા, અને સ્થળ/કાલિક માહિતી માટે પ્રતિ સેકન્ડ 1 ફ્રેમ નમૂના લે છે. પાસ 600 ઢાંચાકીય નમૂનાઓ, એક FFmpeg/filter થ્રેડ, સમાન `file`-માત્ર પ્રોટોકોલ અને કન્ટેનર અલોઇસ્ટ્સ, 1 MiB પ્રક્રિયા-આઉટપુટ બાઉન્ડ, અને બ્રોકરના શેર કરેલાabort/deadlineમાં વધુમાં વધુ 30 સેકન્ડ સુધી મર્યાદિત છે. તે ક્યારેય વિનંતીમાંથી આદેશ, ફિલ્ટર, માર્ગ, અથવા URL સ્વીકારતું નથી.

ઢાંચાકીય મૂલ્યો નિશ્ચિત નમૂનાકારક પુરાવા છે, નહીંતર અર્થપૂર્ણ વિડિઓ સમજણ. તેઓ વિષયો, ક્રિયાઓ, શીર્ષકો, ભાષણ, અથવા વપરાશકર્તા ઇરાદાને અનુમાનિત નથી. દૃશ્ય અને જમતા સીમાઓ વિભાગો બનાવે છે; જમતા આવરણ, ધૂંધળા, પ્રકાશન, સ્થળીય વિગતો, અને કાલિક પરિવર્તન માત્ર તે કેવી રીતે વર્તમાન 1–16 ફ્રેમ બજેટ ફાળવવામાં આવે છે તે પર અસર કરે છે. સંપૂર્ણ રીતે જમતા વિભાગ એક ફ્રેમ પર મર્યાદિત છે, જ્યારે ન જમતા વિભાગો બાકી બજેટ માટે સ્પર્ધા કરે છે. જ્યારે સીમાઓ ફ્રેમ્સની સંખ્યાને વધુ કરે છે, ત્યારે સમાન સમયરેખા આવરણ જાળવવામાં આવે છે જેથી ઝડપી પ્રારંભિક કટ્સ લાંબા પછાત વિભાગને છુપાવી ન શકે. 1-સેકન્ડના વિશ્લેષણના ઉકેલમાં જમતા સીમાઓને એકત્રિત કરવામાં આવે છે.

ગાયબ ફિલ્ટર્સ, ખોટા/ખાલી પુરાવા, ડિટેક્ટર ભૂલ, અથવા બાઉન્ડેડ પ્રી-એનલિસિસ ટાઇમઆઉટ ચોક્કસ સમાન મધ્યબિંદુ નીતિ તરફ ખુલ્લા રહે છે. કૉલરabort અથવા બ્રોકર ડેડલાઇન ખુલ્લા રહેતા નથી: તે ફ્લાઇટમાં રહેલા ઉપપ્રક્રિયાને સમાપ્ત કરે છે, પછીના ફ્રેમ નિષ્કર્ષણને રોકે છે, અને ખાનગી તાત્કાલિક વૃક્ષ `finally` માં દૂર કરવામાં આવે છે.

`scripts/perf/video-bridge-fu07-eval.ts` પોસ્ટ-ડેડુપ શીર્ષક-કૉલ બચત, ઘન-ચલન બજેટ ફાળવણી, ધૂંધળા/પ્રકાશન/SI-TI પુરાવા, લાંબા પછાત સાથે ઝડપી કટ્સ, અને ધીમે ધીમે ફેડ ખોટા પોઝિટિવ્સ માટે નિશ્ચિત વાસ્તવિક FFmpeg ફિક્સચર્સ બનાવે છે. તે પ્રી-એનલિસિસ વોલ ટાઇમને નોંધે છે અને જ્યાં `/usr/bin/time` ઉપલબ્ધ છે, ત્યાં બાળક CPU અને પીક RSS. તેની ગુણવત્તા ચકાસણીઓ માત્ર ઢાંચાકીય ઓરેકલ છે. વાસ્તવિક શીર્ષક-મોડલની ગુણવત્તા `HOLD` પર રહે છે કારણ કે આ હાર્નેસ પાસે કોઈ અધિકૃત અંતિમ બિંદુ અથવા જમતા જજ નથી. નાણાકીય બચત પણ `HOLD` પર રહે છે જો કે `--caption-cost-per-call-usd` સ્પષ્ટ સકારાત્મક પ્રતિ-કૉલ અંદાજ પૂરો પાડે છે; સ્ક્રિપ્ટ ક્યારેય બંને પરિણામો બનાવતી નથી.

દરેક ફ્રેમ 4 MiB સુધી મર્યાદિત છે, તમામ કાચા ફ્રેમ્સ સાથે 23 MiB સુધી, અને સીરિયલાઇઝ્ડ બ્રોકર પ્રતિસાદ 32 MiB સુધી. એક ખાનગી તાત્કાલિક ડિરેક્ટરી `finally` માં દૂર કરવામાં આવે છે. OmniRoute FFmpegને બંડલ નથી કરતી અને કસ્ટમ એક્ઝિક્યુટેબલ માર્ગ સ્વીકારતી નથી. શીર્ષક આપતા પહેલા, બ્રિજ એક સંરક્ષણાત્મક દૃશ્ય ડેડુપ્લિકેશન પાસ લાગુ કરે છે: દરેક JPEGને 16×16 ગ્રેસ્કેલ બફરમાં ઘટાડવામાં આવે છે અને તે માત્ર છેલ્લી ફ્રેમ સાથે સરખાવવામાં આવે છે. એક ફ્રેમથી વધુની વિનંતી કરેલી શીર્ષક બજેટ માટે, નિષ્કર્ષણ 16 ફ્રેમ્સથી વધુ ક્યારેય નહીં, તે બજેટના બે ગણાના મર્યાદિત ઉમેદવારો પૂરા પાડે છે. વિનંતી કરેલ મર્યાદા ડેડુપ્લિકેશન પછી જ લાગુ થાય છે, પ્રથમ અને અંતિમ પસંદ કરેલ ઉમેદવારોને અંતિમ પાતળા દરમિયાન જાળવવામાં આવે છે જ્યારે બજેટ ઓછામાં ઓછા બે હોય. સંસ્કરણિત `grayscale-16x16-mean-cells-v2` નીતિ સરેરાશ લ્યુમા ડેલ્ટા અને થંબનેલ સેલ્સના પ્રમાણનો મોટો ઉપયોગ કરે છે જેનું સામાન્ય ડેલ્ટા ઓછામાં ઓછું 0.05 છે. ડુપ્લિકેટ થ્રેશોલ્ડ સ્થિર 0.04 છે, જે આગાહી માટે પસંદ કરવામાં આવી છે, નહીંતર રનટાઇમ સેટિંગ તરીકે પ્રદર્શિત કરવામાં આવી છે. આ દ્વિતીય ઉચ્ચ-વિશિષ્ટતા સંકેત નાની ચળવળ અને દૃશ્ય-ટેક્સ્ટ પરિવર્તનોને જાળવે છે જે માત્ર સરેરાશની સરખામણી છુપાવી શકે છે. તુલનાકાર અથવા ડિકોડર ભૂલો ખુલ્લા રહે છે અને આવરણ જાળવે છે. આઉટપુટ મેટાડેટા કાઢવામાં આવેલા ઉમેદવારો, સફળતાપૂર્વક ઉપયોગમાં લેવાયેલા ફ્રેમ્સ, અને દૃશ્ય ડુપ્લિકેટ્સને અલગ કરે છે.

એક સ્પષ્ટ રીતે ચિહ્નિત વિડિઓ ભાગ સમયચિહ્નિત સંપર્ક શીટની વિનંતી કરી શકે છે. બ્રિજ વધુમાં વધુ 4-કોલમ, 16-ફ્રેમ JPEG ગ્રિડ બનાવે છે. દરેક 512-પિક્સલ સેલ તેની સ્ત્રોત સમયચિહ્નને ઉચ્ચ-વિશિષ્ટતા નીચલા બૅન્ડમાં બર્ન કરે છે, જ્યારે તે જ સમયચિહ્નો ટેક્સ્ટ મેટાડેટામાં નીચેના સંઘટન અને ઓડિટ માટે રહે છે. સંપૂર્ણ JPEG 32 MiB પર મર્યાદિત રહે છે. જો `sharp` ગ્રિડને ડિકોડ અથવા રચવા માટે અસમર્થ હોય, તો બ્રિજ વ્યક્તિગત JPEG ફ્રેમ્સ પર પાછું જાય છે; ક્લાયન્ટabort હજુ પણ શીટ ઓપરેશનમાં પ્રસારિત થાય છે.

પ્રમોશન પુરાવો故意 રીતે સંશ્લેષણ રચનાત્મક માઇક્રોબેન્ચમાર્કથી અલગ છે. `scripts/perf/video-bridge-contact-sheet-eval.ts` વાસ્તવિક OpenAI-સંગત દૃષ્ટિ મોડલ માટે એક સ્કીમા-સંસ્કરણિત A/B હાર્નેસ વ્યાખ્યાયિત કરે છે. તે પ્રદાતા-અહેવાલિત ટોકન્સ, અંત-થી-અંત વોલ લેટન્સી (શીટ રચનાને સમાવેશ કરીને), મોડલ-કૉલ ગણતરી, અને મેનિફેસ્ટ-વ્યાખ્યાયિત તથ્ય જાળવણીને માપે છે. કાચા મોડલ પ્રતિસાદો અહેવાલમાં લખવામાં આવતી નથી; માત્ર SHA-256 ડિજેસ્ટ અને મેળ ખાતા તથ્ય ID જાળવવામાં આવે છે. હાર્નેસ કોઈ નેટવર્ક અથવા ચૂકવેલ મોડલ કૉલ નથી કરતી જો સુધી `--execute-real` પસાર કરવામાં ન આવે અને `--model`, `OMNIROUTE_BASE_URL`, અને `OMNIROUTE_API_KEY` કન્ફિગર કરવામાં ન આવે. તે સ્પષ્ટ વાસ્તવિક ચલણ વિના, તેની મશીન-વાંચનીય ચુકાદો `HOLD` પર રહે છે; સંશ્લેષણ પેળવણ/કૉલ-ગણતરીના માપ માત્ર પ્રમોશન પુરાવો નથી.

અલગ `scripts/perf/video-bridge-promotion-eval.ts` FU-07 અથવા FU-09 અવલોકનોનો ઉપયોગ કરે છે. પ્રમોશન પ્રવેશ માટે તમામ આઠ સંશ્લેષણ દૃશ્ય પરિસ્થિતિઓની જરૂર છે તેમજ એક સાફ કરેલ વાસ્તવિક ક્લિપ, દરેક ભૂમિકા અને કેસ માટે ઓછામાં ઓછા ત્રણ માપવામાં આવેલા પુનરાવર્તનો, તમામ દસ જાહેર કરેલ મેટ્રિક્સ, જમતા મીડિયા/પ્રોમ્પ્ટ/અપેક્ષિત-તથ્ય/સેટિંગ્સ ડિજેસ્ટ, અનન્ય અવલોકન ID અને માન્ય બીજિત A/B ક્રમ. અમલની રસીદ કોર્પસ ડિજેસ્ટ, ચોક્કસ ઉમેદવાર SHA અને મોડલ સંસ્કરણને બાંધે છે. ગાયબ અથવા અમાન્ય માપ `HOLD` પર રહે છે, જેમાં CPU 30 સેકન્ડથી વધુ, પીક RSS 512 MiBથી વધુ અથવા પ્રી-એનલિસિસ 30 સેકન્ડથી વધુ છે. આ પુરાવા-પ્રવેશ મર્યાદાઓ છે, નવી રનટાઇમ RSS અમલમાં લાવવા માટેની ખાતરી નથી.

FU-07 ને ઓછામાં ઓછા 98% ગુણવત્તા જાળવણી અને p95 વિલંબ 1.2x બેઝલાઇન કરતાં વધુ ન હોવું જોઈએ, ઉપરાંત સમાન સરેરાશ કૅપ્શન કૉલ્સ પર 0.05 સંપૂર્ણ કેસ-સંતુલિત સરેરાશ પુનઃપ્રાપ્તિ સુધારણા અથવા ઓછામાં ઓછા 10% ઓછા સરેરાશ પોસ્ટ-ડેડુપ કૅપ્શન કૉલ્સ હોવા જોઈએ. FU-09 ને ઓછામાં ઓછા 0.85 ગુણવત્તા, 95% જાળવણી, 20% p95 વિલંબ ઘટાડો અને 10% ટોકન ઘટાડો જોઈએ. મહત્વપૂર્ણ તથ્ય નુકશાન, ઇન્જેક્શન અનુરૂપતા અથવા ખોટા ઉપયોગને પ્રમોશન અટકાવે છે. એક કાર્યન્વયન કંઈપણ પ્રમોટ કરી શકતું નથી: `--previous-report` સમાન નીતિ/મોડલ સુધારણા/ઉમેદવાર/કોર્પસના બે અલગ, નોન-ઓવરલેપિંગ, અનુક્રમણિકા લાયક કાર્યન્વયનોને પુષ્ટિ કરે છે. એક નમૂના પ્રયોગ સંપર્ક-શીટ પ્રયોગને પુષ્ટિ કરી શકતું નથી.

કલેક્શન કરનારોએ યાદીમાં પ્રતિસાદોને સ્કોર કરવું જોઈએ અને `responseDigest` સાથે મેટ્રિક્સ અને અવલોકન બાઇન્ડિંગ્સ સાચવવા જોઈએ, ક્યારેય પ્રતિસાદ ટેક્સ્ટ નહીં. ગ્રાહક પણ વારસાગત કાચા અવલોકનો વાંચે છે પરંતુ ક્યારેય તે ટેક્સ્ટને તેની અહેવાલોમાં નકલ નથી કરે. દરેક અવલોકન માટે ચોક્કસપણે `responseDigest` અથવા `rawResponseText` માંથી એક જ સ્વીકારવામાં આવે છે. સંસ્કરણિત મંજૂરી યાદી ખાલી રહે છે જેમાં એક અપરિવર્તનશીલ `hold` ડિફોલ્ટ છે. લાયક પ્રવેશ માટે તેની પુરાવા સંદર્ભ, નીતિ, મોડલ સુધારણા, ચોક્કસ ઉમેદવાર SHA, મેનિફેસ્ટ ડાઇજેસ્ટ અને બે અલગ રન ID ની જરૂર છે; વિરુદ્ધ સંદર્ભો નકારી દેવામાં આવે છે. આ મેટાડેટા એક ઓડિટ કરાર છે, જે એ પુરાવો નથી કે સંદર્ભિત ફાઇલમાં સાચી માપદંડો છે. કોઈપણ પ્રવેશ ઉમેરવા પહેલાં વાસ્તવિક રસીદો સમીક્ષા કરો. મેનેજમેન્ટ આંકડા અંતિમ બિંદુ અને વિડિઓ ડેશબોર્ડ સંરક્ષણાત્મક તૈયારીને પ્રદર્શિત કરે છે. એક કન્ફિગર કરેલ મોડલ ઉપનામ જ તેની સુધારણા અથવા ચાલતા ઉમેદવાર SHA ની સ્થાપના નથી કરતી, તેથી વર્તમાન ડેશબોર્ડ `HOLD` રિપોર્ટ કરે છે, બીજું કાર્યન્વયન સંદર્ભમાંથી લાયકાત ફરીથી ઉપયોગમાં લેતા નથી. સ્પષ્ટ પ્રયોગાત્મક પસંદગી પ્રમોશનથી અલગ રહે છે; કોઈ ડિફોલ્ટ આપોઆપ બદલાતું નથી.

કૉલર્સે સમર્થિત વિડિઓ ભાગ સાથે વૈકલ્પિક `transcript.cues` એરે જોડવા માટે જ્યારે તેઓ પહેલેથી જ સંકલિત ટેક્સ્ટ ધરાવે છે ત્યારે તેઓ કરી શકે છે. દરેક ક્યૂમાં `text`, એક મર્યાદિત `start`/`end` અંતર હોવું જોઈએ જે તપાસવામાં આવેલી અવધિની અંદર હોય, અને એક વ્હાઇટલિસ્ટેડ `source` (`client`, `embedded`, અથવા `audio-bridge`); `confidence` ડિફોલ્ટ રૂપે `1` છે અને `0` અને `1` વચ્ચે રહેવું જોઈએ. ચોક્કસ નકલ ક્યૂઝને સમકક્ષ કરવામાં આવે છે. ઓમ્નીરૂટ આ મેટાડેટા પરથી ટ્રાન્સ્ક્રિપ્શન શરૂ કરતું નથી: માન્ય ક્યૂઝને વર્ણવેલ પરિણામમાં સ્ત્રોત, વિશ્વસનીયતા, અને અંતર સાથે નકલ કરવામાં આવે છે, અને ફ્રેમ કૅપ્શન સાથે અવિશ્વસનીય અવલોકનો તરીકે રજૂ કરવામાં આવે છે. અમાન્ય, રેન્જની બહાર, અથવા પુરાવા-મુક્ત ટેક્સ્ટને કૅપ્શન સ્ટ્રીમમાં મિશ્રિત કરવામાં બદલે નકારી દેવામાં આવે છે. બંને વિનંતી-શરીર ટ્રાન્સ્ક્રિપ્ટ ચેનલ્સ પૂરી પાડેલ પુરાવાને `client` તરીકે સામાન્ય બનાવે છે, જેમાં સ્વ-દાવો કરેલ `embedded` અથવા `audio-bridge` લેબલ્સનો સમાવેશ થાય છે. ફક્ત સર્વર-માલિક એડેપ્ટર જ આ વિશ્વસનીય લેબલ્સને કોડ-માત્ર `trustedSource` દલીલ દ્વારા સોંપી શકે છે; વિનંતી JSON ક્ષેત્ર તે દલીલ સુધી પહોંચી શકતું નથી. ટ્રાન્સ્ક્રિપ્ટ ટેક્સ્ટ અવિશ્વસનીય મીડિયા-ઉત્પન્ન સામગ્રી રહે છે, તેની પુરાવા છતાં, અને ક્યારેય અધિકૃતતા નક્કી કરવી જોઈએ.

એક અદ્યતન કૉલર સમાન વિડિઓ માટે `audioTranscript` ટ્રેક પ્રદાન કરી શકે છે; તેને ક્લાયન્ટ-પ્રદાન કરેલ ટેક્સ્ટ તરીકે માનવામાં આવે છે, સર્વર ટ્રાન્સ્ક્રિપ્શનનો પુરાવો નહીં. ફ્યુઝન સીમ એક ડેડલાઇન અનેabort સંકેત હેઠળ દૃશ્ય અને ઓડિયો અવલોકનો ચલાવે છે, તેમને સામાન્ય સમયરેખા પર ઓર્ડર કરે છે, ચોક્કસ નકલને સમકક્ષ કરે છે, અને જ્યારે ફક્ત એક બાજુ સફળ થાય ત્યારે અંશિક પરિણામને રિપોર્ટ કરે છે. અમાન્ય `audioTranscript` તે અંશિક પરિણામમાં ઘટાડે છે - દૃશ્ય વર્ણન રાખવામાં આવે છે અને ઓડિયો શાખા એક સાફ કરવામાં આવેલ નિષ્ફળતા કોડને નોંધે છે - સમગ્ર વિડિઓને નિષ્ફળ બનાવવાની બદલે. પ્રતિ-શાખા ઉપલબ્ધતા, અંશિક ધ્વજ, અને સાફ કરવામાં આવેલ નિષ્ફળતા કોડ વર્ણવેલ પરિણામમાં, ગાર્ડરેલ મેટાડેટા (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), પરિણામ-કેશ મેટાડેટા, અને બ્રિજ ફ્યુઝન કાઉન્ટર્સમાં જાળવવામાં આવે છે. ડિફોલ્ટ વિડિઓ બ્રિજ પાથ બોલી-ટુ-ટેક્સ્ટને આમંત્રણ નથી આપતું અથવા બીજા મીડિયા નકલને ડાઉનલોડ નથી કરતી; તે સ્પષ્ટ ટ્રેક વિના, તે માત્ર વિડિઓ જ રહે છે.

**ટ્રાન્સ્ક્રિપ્ટ જાળવણી (#12150 P1).** જ્યારે વિડિઓ બ્રિજ (તે પોતે ઓપ્ટ-ઇન) ટ્રાન્સ્ક્રિપ્ટ ક્યૂને રજૂ કરે છે ત્યારે આ આપોઆપ લાગુ પડે છે - કોઈ અલગ જાળવણી ધ્વજ નથી. જ્યારે એક વિનંતી કોઈપણ ટ્રાન્સ્ક્રિપ્ટ ક્યૂ (એક કૉલર-જાહેરાત `transcript` અથવા એક ફ્યુઝ્ડ `audioTranscript`)ને રજૂ કરે છે, ત્યારે ગાર્ડરેલ તેને `videoBridgeObserved` તરીકે ચિહ્નિત કરે છે અને વિડિઓ વર્ણનનો એક રેડેક્ટેડ શેડો ઉત્પન્ન કરે છે - એક સમાન રેન્ડરિંગ જેમાં દરેક ક્યૂના મુક્ત-ટેક્સ્ટ શરીરને `[redacted-video-transcript]` દ્વારા બદલી દેવામાં આવે છે, જે સ્ટ્રક્ચર્ડ ક્યૂ ફીલ્ડને સ્ટ્રિંગ એકત્રિત કરવામાં પહેલાં બદલવા દ્વારા બનાવવામાં આવે છે (ક્યારેય સમકક્ષ ટેક્સ્ટને પાર્સ કરીને, તેથી કોઈ ક્યૂ સામગ્રી - વિરોધી અથવા સામાન્ય, જેમાં `]` ધરાવતી બોડી જેવી કે `[inaudible]`/`[music]` - જીવંત રહી શકતી નથી). જાળવેલ કૉલ-લોગ વિનંતી શરીર દરેક વિડિઓ-ઉત્પન્ન ટેક્સ્ટ ભાગને તે રેડેક્ટેડ શેડો માટે બદલાવે છે, સામગ્રી સમાનતાના આધારે; `fullText` એન્કર પૂર્ણ થયેલ પૂર્વ-કૉલ ગાર્ડરેલ પેઇલોડમાંથી ફરીથી વાંચવામાં આવે છે, તેથી મેચ પછીના ચેઇન ગાર્ડરેલ્સ (PII અને પ્રમાણપત્ર માસ્કર્સ, પ્રાથમિકતાઓ 10/95) વર્ણન ટેક્સ્ટને સ્થાનમાં ફરીથી લખે છે અને પછી સિસ્ટમ-પ્રોમ્પ્ટ/હેન્ડઓફ/મેમરી ઇન્જેક્શન સંદેશા એરેને પુનઃઆકાર આપે છે. મોડલને ઉપર મોકલવામાં આવેલ શરીર અપરિવર્તિત રહે છે. એક અવલોકિત વિનંતી પણ કોઈ ટકાઉ મેમરીને ભરતી નથી (વિનંતી અને પ્રતિસાદ-ઉત્પન્ન ઉત્કર્ષ બંનેને છોડી દેવામાં આવે છે), તેથી મોડલની પોતાની જવાબદારી મેમરીમાં ટ્રાન્સ્ક્રિપ્ટ ટેક્સ્ટને પ્રતિબિંબિત કરી શકતી નથી.

**કાચા વિડિઓ ક્ષેત્રો (#12430).** જ્યારે બ્રિજ સક્રિય હોય છે અને સ્થાનિક વિડિઓ સપોર્ટ અજ્ઞાત અથવા ગેરહાજર હોય છે, ત્યારે વ્યાખ્યાયિત `transcript`/`audioTranscript` ક્ષેત્રો પણ `videoBridgeObserved`ને સક્રિય કરે છે, વર્ણન નિષ્ફળતા અથવા `maxVideos` મર્યાદા પછી પણ. `null` અને ખાલી સ્ટ્રિંગ્સ ગણવામાં આવે છે; ગેરહાજર ક્ષેત્રો અને નોન-વિડિઓ મેટાડેટા ગણવામાં આવતી નથી. જાળવેલ નકલ આ ક્ષેત્રોને રેડેક્ટ કરે છે અથવા વિનંતી છોડી દે છે, અને કેશ/મેમરીને બાયપાસ કરવામાં આવે છે. પ્રદાતા પેઇલોડ અપરિવર્તિત રહે છે.

અન્ય રાખેલા નકલોએ સમાન અવલોકિત-વિનંતી સંકેતનો ઉપયોગ કર્યો છે. કાચા પ્રી-ગાર્ડરેલ ક્લાયન્ટ-વિનંતી સ્નેપશોટ, મેમરીમાં પેન્ડિંગ વિનંતી, અને વહેલી નકારી લેવામાં આવેલી વિનંતી લોગ રચનાત્મક રીતે વિડિઓ ભાગોમાં ટ્રાન્સક્રિપ્ટ ફીલ્ડ્સને બદલે છે; પાઇપલાઇન તબક્કાઓ અને સંદર્ભ હેન્ડઓફ દ્વારા સંશ્લેષિત સ્ટ્રિંગ પ્રોમ્પ્ટ્સને રાખેલા વિનંતી-શરીરના સિંક પર રેડેક્ટ કરવામાં આવે છે. રાખેલા `video_content_removed` માર્કર `previous_response_id` ચાલુ રાખવા માટે બંધ થાય છે, ટેક્સ્ટને પુનઃનિર્માણ કરવા માટે નહીં જે ઇરાદાપૂર્વક નિકાલ કરવામાં આવ્યું હતું. જો અવલોકિત વિનંતી તેના ભાગ-પ્રતિબંધ છાયાને લોગિંગ પહેલાં ગુમાવે છે, અથવા પછીની વિનંતી પરિવર્તનો પછી ઘણા વિડિઓ છાયાઓમાંથી એક પણ મેળ ખાતા નથી, તો રાખેલી વિનંતી શરીર સંપૂર્ણપણે છોડી દેવામાં આવે છે, ભાગિક રીતે રેડેક્ટ કરેલ ટ્રાન્સક્રિપ્ટને રાખવા બદલે.

અવલોકિત વિનંતી માટે, મોડેલ પ્રતિસાદ ટ્રાન્સક્રિપ્ટના કોઈપણ ભાગને રચનાત્મક સંકેતની સીમા વિના ઉલ્લેખ કરી શકે છે. તેથી, તેની રાખેલી કોલ-લોગ `responseBody`ને એક છોડી દેવા માટેના માર્કર દ્વારા બદલી દેવામાં આવે છે; વિગતવાર પાઇપલાઇન આર્ટિફેક્ટ (જેમાં અપસ્ટ્રીમ/ક્લાયન્ટ બોડી અને સ્ટ્રીમ ચંક્સનો સમાવેશ થઈ શકે છે) રાખવામાં આવતું નથી. અર્થશાસ્ત્ર, આઈડેમ્પોટન્સી, અને તર્ક-પુનરાવૃત્તિ કેશો તે વિનંતી માટે વાંચન અને લખાણને બાયપાસ કરે છે. પ્રદાતા વિનંતી અને ક્લાયન્ટ-દૃશ્ય પ્રતિસાદ અપરિવર્તિત રહે છે. વિગતવાર આર્ટિફેક્ટ છોડી દેવામાં આવે ત્યારે અર્લી કીપઅલાઇવ બાઇટ્સ તાત્કાલિક બફરમાંથી કાઢી લેવામાં આવે છે. કિરોના ખોટા ઇવેન્ટસ્ટ્રીમ ચેતવણી Payload બાઇટ ગણતરીને જ અહેવાલ આપે છે, ક્યારેય તેની સામગ્રી અથવા JSON પાર્સરની કાચી ભૂલને નહીં.
આ દાવો નથી કરતો કે દરેક અસંબંધિત પ્રદાતા/પ્લગિન નિદાનનું ઓડિટ કરવામાં આવ્યું છે; વ્યાપક રાખેલા-સિંક સ્વીપ #11658 માં ટ્રેક કરવામાં આવે છે.

આંતરિક `/api/modality-bridge/video/drilldown` જીવનચક્ર એક અલગ, લૂપબેક/ટોકન-પ્રમાણિત કેશ આધારભૂત છે. દરેક ઓપરેશનને એક કૅનોનિકલ ઓpaque પ્રિન્સિપલ IDની જરૂર છે. ઉત્પાદન કોલર સક્રિય થવા પહેલાં, તેને પ્રમાણિત ટેનન્ટમાંથી તે ID મેળવવું જોઈએ અને ક્યારેય ક્લાયન્ટ-ચૂંટેલ મૂલ્યને આગળ ન વધારવું જોઈએ. કેશ કી તે પ્રિન્સિપલને કૅનોનિકલ સત્ર અને વિડિઓ-સંદર્ભ ID સાથે બાંધે છે, ફક્ત તેમના SHA-256-ઉત્પન્ન કી જ રાખે છે, અને વાંચન અને કાઢી નાખવા બંનેને સમાન પ્રિન્સિપલ માટે મર્યાદિત કરે છે. કેશમાં દરેક એન્ટ્રી માટે મહત્તમ 16 ઉત્પન્ન JPEG ફ્રેમ્સ હોય છે, દસ મિનિટ પછી તેમને સમાપ્ત કરે છે, અને મર્યાદિત `start`/`end` વાંચન અથવા સ્પષ્ટ સત્ર કાઢી નાખવા માટે સમર્થન આપે છે.

દરેક પ્રિન્સિપલ 16 એન્ટ્રીઓ અને 64 MiB કૅનોનિકલ JPEG ડેટા સુધી મર્યાદિત છે. આ મર્યાદાઓ વૈશ્વિક 64-એન્ટ્રી/256 MiB છતથી સ્વતંત્ર છે: પ્રિન્સિપલ કોટા દબાણ માત્ર તે પ્રિન્સિપલના સૌથી-છેલ્લા-ઉપયોગમાં આવેલા એન્ટ્રીઓને દૂર કરે છે, પહેલાં વૈશ્વિક LRU ખસેડવા પર વિચાર કરવામાં આવે છે. સમાપ્ત થયેલ એન્ટ્રીઓ કેશ પ્રવૃત્તિ પર બંને પ્રિન્સિપલ અને વૈશ્વિક હિસાબમાંથી દૂર કરવામાં આવે છે, જ્યારે રદ કરવું અને માન્યતા નિષ્ફળતા અર્ધ-બદલાવને પ્રતિબદ્ધ નથી કરે.

કેશ નોન-કૅનોનિકલ બેસ64, વધારાના પેડિંગ, નોન-JPEG મીડિયા, ખોટા અથવા ટુકડાઓ JPEGને નકારી નાખે છે, અને JPEG જે મર્યાદિત સંપૂર્ણ-છબી `sharp` ડિકોડ દરમિયાન ચેતવણી આપે છે. તે દરેક સ્વીકૃત છબીને કૅનોનિકલ JPEG તરીકે પુનઃકોડ કરે છે, ડિકોડ કરેલ બાઇટ્સમાંથી પહોળાઈ અને ઊંચાઈ મેળવવા માટે કોલર ફીલ્ડ્સ પર વિશ્વાસ ન રાખે, અને કોઈપણ ટ્રેઇલિંગ પોલીગ્લોટ બાઇટ્સને રાખવા બદલે નિકાલ કરે છે. ફક્ત મર્યાદિત કૅનોનિકલ સંકોચિત બફર બંને કોટાઓને ચાર્જ કરવામાં આવે છે. JSON વાયર મર્યાદા 32 MiB ડિકોડ-ઇનપુટ છત માટે બેસ64 ઓવરહેડને સમાવેશ કરે છે. દરેક
રાખેલ ઉત્પન્ન તેની માન્ય JPEG ફોર્મેટ/રિઝોલ્યુશન, નમૂના નીતિ, ઉત્પન્ન સંસ્કરણ, સર્જન સમય, સર્વર-ગણિત સામગ્રી હેશ, અને હેશ કરેલ પેરેન્ટ સંદર્ભ સાથે સાથે વિશ્વસનીય કોલરના પેરેન્ટ-સામગ્રી હેશને નોંધાવે છે. રદ કરવું અસંબંધિત ડિકોડ/હેશ તબક્કાઓ વચ્ચે ચકાસવામાં આવે છે પહેલાં અણુ કેશ પ્રતિબદ્ધ થાય છે.

ઉત્પાદન ઉત્પાદક પહેલાથી જ ઉત્પન્ન થયેલ બ્રોકર ફ્રેમ્સને માત્ર સફળ દૃશ્ય વિશ્લેષણ પછી પુનઃઉપયોગ કરે છે, બીજું વિડિઓ ડાઉનલોડ/ઉત્પાદન વિના. તે ઓપરેટર `modalityBridgeVideoDrilldownEnabled=true`, કડક પ્રતિ-ભાગ `drilldown: true`, અને એક પ્રમાણિત API-કી રેકોર્ડ IDની જરૂર છે. ક્લાયન્ટ-જાહેરાત કરેલ પ્રિન્સિપલ/સત્ર મૂલ્યો ક્યારેય માલિકી સ્થાપિત નથી કરતા. આ ત્રણ શરતો વિના તે હેશ, પુનઃમાપે અથવા વધારાના ફ્રેમ્સને રાખતું નથી. રાખવાની નિષ્ફળતા ઉપયોગી દૃશ્ય પ્રતિસાદને જાળવે છે. સંમતિ આપેલ વિનંતીઓ સમગ્ર-વિડિઓ પરિણામ કેશને બાયપાસ કરે છે જેથી કેશ કરેલ પરિણામો ક્યારેય પુનરાવૃત્તિ હેન્ડલ ન કરે.

સફળ JSON અને SSE પ્રતિસાદ મર્યાદિત `x-omniroute-video-drilldown` હેડરમાં મહત્તમ ચાર ઓpaque હેન્ડલ્સને પ્રદર્શિત કરે છે. અધિકૃત બ્રાઉઝર મૂળો તે હેડરને વાંચી શકે છે વિના CORS મૂળ નીતિનું વિસ્તરણ કર્યા વિના. નવા હેન્ડલ્સ `v1.<32-byte random base64url token>` નો ઉપયોગ કરે છે, અને રજિસ્ટ્રી ફક્ત તેમના SHA-256 હેશને જ રાખે છે. રીડર/હેડર પાર્સર પણ વારસાગત 64-હેક્સ હેન્ડલ્સને સ્વીકારે છે. પ્રમાણિત જાહેર ગ્રાહક છે `GET /api/v1/video-bridge/drilldown?handle=...`, સ્વતંત્ર રીતે ગેટેડ દ્વારા `modalityBridgeVideoDrilldownRemoteEnabled=true`. સ્પષ્ટ રાખેલ ખોટું પ્રવેશને રદ કરે છે જ્યારે વારસાગત `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` env ફોલબેક સક્રિય હોય છે. ઉત્પાદન રાખવા માટે સમાન વારસાગત `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED` ફોલબેક છે. બંને ફોલબેક ડિફોલ્ટ બંધ છે.

ગ્રાહક પ્રમાણિત કીમાંથી માલિકી મેળવશે, કી નીતિ લાગુ કરશે, અને અજ્ઞાત, સમાપ્ત અને અન્ય કી હેન્ડલ્સ માટે સમાન 404 પાછું આપે છે. તે સ્વીકારે છે `variant=preview|standard|detail` (મહત્તમ JPEG પરિમાણ 320/640/1280, ક્યારેય અપસ્કેલ ન થાય), `limit=1..8` (અથવા વારસાગત `frames` ઉપનામ, ક્યારેય બંને નહીં), શૂન્ય આધારિત `page`, અને વૈકલ્પિક `start`/`end` ફોકસ સેકન્ડ. નકલી
ક્વેરી કી અને વળાંક ફોકસ વિન્ડોઝને નકારી દેવામાં આવે છે. દરેક પાછા મળેલ વૈવિધ્યમાં તેની વાસ્તવિક સામગ્રી અને વાસ્તવિક રિઝોલ્યુશન મેટાડેટાનો હેશ હોય છે, જે રાખેલ સ્ત્રોત સાથે જોડાયેલ છે. વૈવિધ્ય વાંચન પર ઉત્પન્ન થાય છે, વધારાના રાખેલા નકલ તરીકે નહીં. JSON પ્રતિસાદ, બેસ64/એન્વેલોપ સહિત, 32 MiB પર મર્યાદિત છે; એક વધુ મોટા પાનું 413 પાછું આપે છે અને ક્લાયન્ટને ઓછા ફ્રેમ્સની વિનંતી કરવી જોઈએ. વાંચનો દરેક પુનઃમાપની આસપાસ રદ કરવાનું ચકાસે છે અને પાછા ફરતા પહેલાં હેન્ડલ માન્યતાને ફરીથી ચકાસે છે. માલિક દ્વારા `DELETE` આઈડેમ્પોટન્ટ છે; કાઢી નાખવું અથવા TTL સમાપ્ત થવું રાખેલ સ્ત્રોત અને ઉપયોગ હિસાબને મુક્ત કરે છે.

શેર કરેલ સ્ટોર પ્રક્રિયા-સ્થાનિક છે: હેન્ડલ્સ પુનઃપ્રારંભ પર સમાપ્ત થાય છે અને સ્વતંત્ર OmniRoute પ્રક્રિયાઓ વચ્ચે પરિવહન કરી શકાતી નથી. વ્યવસ્થાપન આંકડાઓ અસરકારક રાખવા/દૂરની નીતિ અને માત્ર સંકલિત રાખેલ એન્ટ્રીઓ/બાઇટ્સને પ્રદર્શિત કરે છે, ક્યારેય મીડિયા, સંદર્ભો, મુખ્ય ID અથવા હેન્ડલ્સને નહીં. વિડિઓ સેટિંગ્સ પેનલ તે મૂલ્યો દર્શાવે છે અને બંને સંમતિ સ્વિચોને જાળવી શકે છે. આ અમલ દસ્તાવેજ જીવંત ડિપ્લોયમેન્ટ અથવા પ્રમોશન પુરાવા નથી; વાસ્તવિક મોડલ સ્વીકૃતિ અલગથી ટ્રેક કરવામાં આવે છે.

ફ્રેમો સેટ કરેલ વિડિઓ મોડલ સાથે અનુક્રમણિકા મુજબ કેપ્શન કરવામાં આવે છે. ખાલી વિડિઓ ઓવરરાઇડ વિઝન સેટિંગને વારસામાં લે છે; જો બંને ખાલી હોય, તો વિઝન ઓટો-રાઉટર અસરકારક વિઝન-ક્ષમ મોડલ પસંદ કરે છે. સફળ કેપ્શન મૂળ ભાગને સ્થિર `[Video description:` પૂર્વપ્રતિષ્ઠા સાથે બદલે છે જે ટેક્સ્ટને અવિશ્વસનીય મીડિયા-ઉત્પાદિત અવલોકન તરીકે પણ ચિહ્નિત કરે છે અને નીચેના મોડલને મીડિયા માં મળેલ સૂચનાઓને અનુસરણ ન કરવા કહે છે. ફ્રેમ-કેપ્શન કેશ કી JPEG બાઇટ્સ, પ્રોમ્પ્ટ, ટાઈમસ્ટેમ્પ, અને અસરકારક મોડલને સમાવેશ કરે છે; માત્ર સફળ કેપ્શન જ કેશ કરવામાં આવે છે. કેશ એન્ટ્રીઓ વાસ્તવિક સફળ ઉત્પાદક મોડલને જાળવે છે, જેમાં એક ફોલબેક મોડલ પણ હોય છે; બ્રિજ `mixed` રિપોર્ટ કરે છે જ્યારે અલગ મોડલ દ્વારા અલગ ફ્રેમો ઉત્પન્ન કરવામાં આવ્યા હતા. કેશ હિટ તે ઉત્પાદક ઓળખને પુનઃઉપયોગ કરે છે તેના બદલે તેને વિનંતી કરેલ રૂટિંગ યોજના તરીકે પુનઃલેબલ કરે છે. સમગ્ર-વિડિઓ પરિણામ કેશ દરેક ઇનપુટ પર કી કરવામાં આવે છે જે આઉટપુટને બદલે છે — પ્રોમ્પ્ટ, અસરકારક મોડલ, નમૂના નીતિ, ફ્રેમ ગણતરી, અર્થશાસ્ત્ર વિશ્લેષણ મોડ, નોર્મલાઇઝ્ડ ફોકસ હિન્ટનો SHA-256 ફિંગરપ્રિન્ટ, ફોકસ વિન્ડો, `transcript`, `audioTranscript`, અને સંપર્ક-શીટ ધ્વજ — તેથી આમાંથી કોઈપણ પરિમાણ બદલવું કેશ મિસ છે, ક્યારેય જૂના પુનઃઉપયોગ નથી. દૃશ્ય ડેડુપ નીતિ સંસ્કરણ, થ્રેશોલ્ડ, અને બાઉન્ડેડ કૅન્ડિડેટ-ફ્રેમ ગણતરી પણ પરિણામ-કેશ કી અને મેટાડેટામાં સ્પષ્ટ છે; તેથી, નીતિમાં ફેરફાર જૂના સમગ્ર-વિડિઓ વર્ણનને પુનઃઉપયોગ કરી શકતું નથી. પરિણામ-કેશ v4 મેટાડેટા મોડ અને ફિંગરપ્રિન્ટને જાળવે છે, ક્યારેય કાચા વપરાશકર્તા કાર્યને નહીં. ગાર્ડરેલ મેટાડેટા વિનંતી કરેલ અને અસરકારક વિશ્લેષણ મોડ બંનેને રિપોર્ટ કરે છે; ઉપયોગી વપરાશકર્તા ટેક્સ્ટ વિના વિનંતી કરેલ `focused` મોડને અસરકારક રીતે `full` તરીકે રિપોર્ટ કરવામાં આવે છે.

ગાર્ડરેલ દરેક સમર્થિત વિડિઓ ભાગને કાઢે છે પરંતુ `modalityBridgeVideoMaxVideos` કરતાં વધુ વર્ણવતું નથી. એક લક્ષ્ય જે સાબિત છે કે `supportsVideo === false`, નિષ્ફળ અને ઓવર-લિમિટ વિડિઓઓ સ્પષ્ટ સુરક્ષિત ટેક્સ્ટ માર્કર્સ બની જાય છે જેથી કોઈ કાચા વિડિઓ જીવંત રહેતા નથી. જ્યારે ક્ષમતા અજાણ હોય, ત્યારે તે ભાગો અવિનાશિત રહે છે. લક્ષ્યો સાથે `supportsVideo === true` બ્રિજને બાયપાસ કરે છે. ક્લાયન્ટ વિનંતી અટકાવવાનો સંકેત ડાઉનલોડ, બ્રોકર ક્યૂ, સબપ્રોસેસ અને કેપ્શન કોલ્સમાં પ્રસારિત થાય છે; અટકાવા વિડિઓઓ વચ્ચે અટકે છે અને ક્યારેય કાચા મીડિયા માટે ખૂલે નહીં.

120 સેકન્ડથી વધુના વારસામાં રહેલ વિડિઓ ટાઇમઆઉટ મૂલ્યો બ્રોકર ડેડલાઇન પર ક્લેમ્પ કરવામાં આવે છે; તે મર્યાદા ઉપર નવા સેટિંગ્સ લખવા નકારી દેવામાં આવે છે. `GET /api/modality-bridge/video/runtime` માન્યStamped લૂપબેક સ્થાનિકતા માટે માન્યતા અથવા રનટાઇમ પ્રોબિંગ પહેલાંની જરૂર છે, પછી વ્યવસ્થાપન authની જરૂર છે. તે માત્ર `available`, sanitized FFmpeg/ffprobe સંસ્કરણો, અને જ્યારે રનટાઇમ ઉપલબ્ધ નથી ત્યારે એક નિશ્ચિત કારણ પાછું આપે છે. આંતરિક ઉત્કર્ષ બિંદુ જાહેર અપલોડ API નથી: ક્યૂ સેચરેશન `503` અને `Retry-After` પાછું આપે છે, એક કૉલર ડિસ્કનેક્ટ `499` પાછું આપે છે, અને નિશ્ચિત બ્રોકર ડેડલાઇન `504` પાછું આપે છે. રૂપાંતરિત પ્રતિસાદો કેન્દ્રિય `x-omniroute-modality-bridge` હેડરમાં `video->text;model=<visionModel>;parts=<videos>` ઉમેરે છે વિઝન અથવા ઓડિયો વિભાગોને દૂર કર્યા વિના.

### PII Masker (`piiMasker.ts`)

**બન્ને** તબક્કાઓ પર ચાલે છે.

- **`preCall`** પેઇલોડને ક્લોન કરે છે, `system`, `messages`, `input`, અને `prompt` (સાધારણ સ્ટ્રિંગ આઇટમ્સને સમાવેશ કરે છે) ને ચાલે છે, અને `processPII()` (થી `@/shared/utils/inputSanitizer`) ને સ્ટ્રિંગ `content`/`text` ફીલ્ડ્સ પર લાગુ કરે છે. જ્યારે `PII_REDACTION_ENABLED=true` હોય, ત્યારે શોધાયેલ PII આઉટબાઉન્ડ પેઇલોડમાં છુપાવવામાં આવે છે. આ `INPUT_SANITIZER_MODE` (જે ફક્ત પ્રોમ્પ્ટ-ઇન્જેક્શન નીતિને નિયંત્રિત કરે છે) થી સ્વતંત્ર છે. જ્યારે છુપાવા બંધ હોય, ત્યારે કોલ શોધણી ગણતરીઓને નોંધે છે કન્ટેન્ટને પુનઃલેખિત કર્યા વિના.
- **`postCall`** પ્રતિસાદને ડીપ-ક્લોન કરે છે, `sanitizePIIResponse()` ચલાવે છે અને પ્રતિસાદ-API-આકાર માસ્કર (`maskResponsesOutput` — `output_text` અને `output[].content[].text`ને આવરી લે છે). જો કોઈ છુપાવા થાય છે, તો સુધારેલ પ્રતિસાદ મૂળને બદલે છે.

ગાર્ડરેલ ક્યારેય બ્લોક નથી થતો; તે ફક્ત નોંધ કરે છે (`meta.detections`, `meta.redacted`) અથવા પુનઃલેખિત કરે છે.

### Prompt Injection (`promptInjection.ts`)

વપરાશકર્તા દ્વારા પૂરા પાડવામાં આવેલા સામગ્રીમાં વિરોધી માળખાઓને ઓળખે છે અને રૂપરેખાંકિત નીતિને અમલમાં લાવે છે. વર્તન પર્યાવરણના ચલ અને કન્સ્ટ્રક્ટર વિકલ્પો દ્વારા ચલાવવામાં આવે છે:

| સેટિંગ          | Env var                                                                                               | ડિફોલ્ટ | અસર                                                                                                                                                                                                 |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| સક્રિય          | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | જ્યારે `false`, ગાર્ડરેલ શોર્ટ-સર્કિટ કરે છે.                                                                                                                                                       |
| મોડ             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | ઇન્જેક્શન નીતિ: `block`, `warn`, અથવા `log`. (`redact` પાછા-સંગત માટે સ્વીકારવામાં આવે છે પરંતુ ઇન્જેક્શન ટેક્સ્ટને **કાઢી** નથી; વિનંતી PII પુનરલેખન `PII_REDACTION_ENABLED` દ્વારા નિયંત્રિત છે.) |
| બ્લોક થ્રેશોલ્ડ | `blockThreshold` વિકલ્પ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ઉપનામ `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | બ્લોક કરવા માટેની જરૂરી ન્યૂનતમ ગંભીરતા. ડિફોલ્ટમાં મધ્યમ માત્ર અવલોકન-માત્ર છે.                                                                                                                    |

**મોડ પ્રાધિકરણ** (`getMode`): caller `options.mode` →
`INJECTION_GUARD_MODE` **DB ફીચર-ફ્લેગ ઓવરરાઇડ** (ડેશબોર્ડ → સેટિંગ્સ →
ફીચર ફ્લેગ્સ) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. તેથી, ડેશબોર્ડ ઓવરરાઇડ પર્યાવરણના ચલોથી વધુ શક્તિશાળી છે, તેથી ફીચર ફ્લેગ્સ UI જીવંત ગાર્ડને ચલાવે છે (કોઈ પુનઃપ્રારંભ નથી). DB વાંચન ફેઇલ-સેફ છે:
જો તે ભૂલ કરે છે, તો ગાર્ડ પર્યાવરણ આધારિત વર્તન પર પાછું ફરશે, અને જ્યારે કોઈ ઓવરરાઇડ સેટ નથી ત્યારે વર્તન પર્યાવરણ-માત્ર ઉકેલ સાથે સમાન છે.

ઓળખવા માટેના સ્ત્રોતો:

1. `sanitizeRequest()` from `@/shared/utils/inputSanitizer` (pipelineમાં અન્ય જગ્યાએ ઉપયોગમાં લેવાતા શેર કરેલા ડિટેક્ટર સેટ).
2. બિલ્ટ-ઇન `DEFAULT_GUARD_PATTERNS` (હાલમાં `system_override_inline` અને
   `markdown_system_block`, બંને `high` ગંભીરતા).
3. વૈકલ્પિક `customPatterns` કન્સ્ટ્રક્ટર વિકલ્પો દ્વારા પસાર કરવામાં આવે છે (સ્ટ્રિંગ્સ, regex,
   અથવા `{ name, pattern, severity }` રેકોર્ડ).

જ્યારે `mode === "block"` **અને** ઓછામાં ઓછા એક ઓળખાણ ગંભીરતા થ્રેશોલ્ડને પૂર્ણ કરે છે, ત્યારે `preCall` `{ block: true, message: "વિનંતી નકારી દેવામાં આવી: શંકાસ્પદ સામગ્રી ઓળખાઈ છે" }` પાછું આપે છે. `warn`/`log` મોડમાં ગાર્ડરેલ લોગ કરે છે પરંતુ કોલને મંજૂરી આપે છે. શેર કરેલ હેલ્પર `evaluatePromptInjection()` પણ કૉલર્સ માટે નિકાસ કરવામાં આવે છે જેમને રજિસ્ટ્રીમાં જવા વિના પ્રોમ્પ્ટ્સને મૂલ્યાંકન કરવાની જરૂર છે.

**સ્કેન બાઉન્ડ (v3.8.20):** ડિટેક્ટર ફક્ત **પ્રથમ 16 KB** જોડાયેલા પ્રોમ્પ્ટ ટેક્સ્ટને તપાસે છે — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 બાઇટ) માં
`src/shared/utils/inputSanitizer.ts`. બંને `detectInjection()` અને
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` પેટર્ન લૂપ ચલાવ્યા પહેલા કરે છે. ઇન્જેક્શન ડિરેક્ટિવ્સ ઇનપુટના ટોચના નજીક બેસે છે, તેથી આ મલ્ટી-સો-KB પે લોડ પર regex CPU/GCને મર્યાદિત કરે છે જ્યારે ઓળખાણને નબળું કર્યા વિના (cf.
#3932, #4041).

### ક્રેડેંશિયલ માસ્કર (`credentialMasker.ts`)

**બન્ને** તબક્કાઓ પર ચાલે છે, ડિફોલ્ટ ચેઇનમાં છેલ્લું (પ્રાથમિકતા `95`). આઉટબાઉન્ડ પે લોડ (સંદેશા સામગ્રી, ટૂલ-કોલ દલીલો, ટૂલ પરિણામો) **અને** પ્રદાતા પ્રતિસાદમાંથી જાણીતા API-કી / સિક્રેટ-ટોકન પેટર્નને દૂર કરે છે, જેથી પ્રોમ્પ્ટમાં પેસ્ટ કરેલ ક્રેડેંશિયલ (અથવા ટૂલ પરિણામ દ્વારા પાછું પ્રતિબિંબિત) ઉપરવાળા પ્રદાતા અથવા ક્લાયન્ટને લીક ન થાય.

- **ઓપ્ટ-ઇન માત્ર**, PII પુનરલેખન સાથે સમાન સંકેત (હાર્ડ રૂલ #20-સંલગ્ન):
  જ્યારે સુધી `settings.credentialRedactionEnabled === true` **અથવા**
  `CREDENTIAL_REDACTION_ENABLED=true` નથી, ત્યારે નિષ્ક્રિય. આને બંધ રાખતા, ગાર્ડરેલ એક નોન-ઓપ છે —
  તે ક્યારેય બ્લોક નથી કરે અને ક્યારેય પુનરલેખન નથી કરે.
- `redactCredentials()` સંપૂર્ણ પે લોડ/પ્રતિસાદ વૃક્ષને ચાલે છે (`walkValue()`,
  પ્રોટોટાઇપ-પોલ્યુશન-સેફ, ચક્ર-સેફ `WeakSet` દ્વારા) અને મેળ ખાતા સાથે
  `[REDACTED:<type>]` પ્લેસહોલ્ડર સાથે બદલે છે, ફક્ત તે શાખાઓને ક્લોન કરે છે જે ખરેખર
  બદલાઈ ગઈ છે.
- `CREDENTIAL_PATTERNS` LLM પ્રદાતા કી (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ટોકન (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), ચુકવણી કી (Stripe, Square), ક્લાઉડ
  કી (AWS ઍક્સેસ કી, Twilio, SendGrid, Mailgun), ખાનગી કી / JWTs,
  ક્રેડેંશિયલ ધરાવતી કનેક્શન સ્ટ્રિંગ્સ (`mongodb://user:pass@...`, વગેરે), અને
  સામાન્ય `Authorization`/`x-api-key`/`api-key`/`apikey` હેડર-મૂલ્ય
  પેટર્ન. હેડર-આકારની કી (`authorization`, `x-api-key`, `api-key`,
  `apikey`) ઢાંચાકીય રીતે દૂર કરવામાં આવે છે (માત્ર મૂલ્ય, સ્કીમ પ્રિફિક્સ જેમ કે
  `Bearer `/`Basic ` જાળવવામાં આવે છે) સામાન્ય ટેક્સ્ટ regex દ્વારા નહીં.
- ગાર્ડરેલ ક્યારેય બ્લોક નથી કરે; તે ફક્ત પુનરલેખન કરે છે (`modifiedPayload` /
  `modifiedResponse`) અને નોંધ કરે છે (`meta.credentialsRedacted`, `meta.count`).

પુનરાવર્તન ગાર્ડ: `tests/unit/credential-masker-guardrail.test.ts`.

## મૂળભૂત કરાર (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ચેઇનને તરત જ અટકાવે છે
  message?: string; // અવરોધિત કરતી વખતે દર્શાવવામાં આવે છે
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // વિનંતીને ફરી લખવા માટે preCall દ્વારા પરત કરવામાં આવે છે
  modifiedResponse?: TValue; // પ્રતિસાદને ફરી લખવા માટે postCall દ્વારા પરત કરવામાં આવે છે
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ગાર્ડરેલ `void`, `{}`, અથવા `{ block: false }` પરત કરીને "કોઈ ફેરફાર નહીં"નો સંકેત આપે છે. `modifiedPayload`/`modifiedResponse` પરત કરવાથી ચેઇનમાં આગળના ગાર્ડરેલ્સ તરફ વહેતું મૂલ્ય બદલાઈ જાય છે.
`signal?: AbortSignal` કૉલરની લાઇફસાઇકલને ગાર્ડરેલ્સ સુધી લઈ જાય છે. વિનંતી રદ થવી એ ઇરાદાપૂર્વકનો fail-open અપવાદ છે: મીડિયા બ્રિજ કામ અટકાવે છે અને જે લક્ષ્ય તેને સપોર્ટ કરતું નથી તે જાણીતું હોવા છતાં તેમાં મૂળ મીડિયા પુનઃસ્થાપિત કર્યા વિના ક્લીનઅપ કરે છે.

## રજિસ્ટ્રી (`registry.ts`)

સિંગલટન `guardrailRegistry` નીચેની સુવિધાઓ પ્રદાન કરે છે:

- `register(guardrail)` — ગાર્ડરેલ ઉમેરે છે (અથવા સામાન્યકૃત નામ દ્વારા બદલે છે) અને
  ચઢતા `priority` મુજબ ફરીથી ગોઠવે છે.
- `clear()` / `list()` — વહીવટી સહાયકો.
- `runPreCallHooks(payload, context)` — સક્રિય ગાર્ડરેલ્સ પર ક્રમશઃ ફરે છે, પેલોડને
  `modifiedPayload` મારફતે આગળ ધપાવે છે અને પ્રથમ `block: true` પર અટકે છે.
- `runPostCallHooks(response, context)` — પ્રતિસાદની બાજુએ સમાન પ્રવાહ.
- `resetGuardrailsForTests({ registerDefaults })` — સ્વચ્છ ટેસ્ટ અલગીકરણ માટે સ્ટેટ સાફ કરે છે અને વૈકલ્પિક રીતે
  ડિફૉલ્ટ્સને ફરીથી રજિસ્ટર કરે છે.

બંને રનર્સ `{ blocked, payload|response, results, guardrail?, message? }`
પરત કરે છે, જ્યાં `results` એ `GuardrailExecutionResult` રેકોર્ડ્સની એરે છે, જેમાં
દરેક ગાર્ડરેલ માટેના `blocked`, `skipped`, `modified`, `error`, અને `meta` ફીલ્ડ્સ
સમાવિષ્ટ હોય છે, જે ટ્રેસિંગ માટે ઉપયોગી છે.

### દરેક વિનંતી માટે ગાર્ડરેલ્સ અક્ષમ કરવા

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` વર્તમાન
વિનંતી માટે છોડવામાં આવનાર ગાર્ડરેલ નામોની ડુપ્લિકેટ-રહિત યાદી એકત્રિત કરે છે.
સ્ત્રોતો (બધા વૈકલ્પિક, બધા મર્જ કરવામાં આવે છે):

- `apiKeyInfo.disabledGuardrails`
- વિનંતી બોડીનું `disabledGuardrails` (ટોચના સ્તરે)
- વિનંતી બોડીનું `metadata.disabledGuardrails`
- હેડર `x-omniroute-disabled-guardrails` (અથવા જૂનું
  `x-disabled-guardrails`)

મૂલ્યો સ્ટ્રિંગ્સની એરે અથવા કૉમાથી અલગ કરેલી સ્ટ્રિંગ હોઈ શકે છે; નામોને
લોઅરકેસ kebab-caseમાં સામાન્યકૃત કરવામાં આવે છે (`pii_masker` → `pii-masker`). પરિણામ
`context.disabledGuardrails` મારફતે રજિસ્ટ્રીને આપવામાં આવે છે, જે
મેળ ખાતા ગાર્ડરેલ્સને છોડી દે છે (`results`માં `skipped: true`).

## અમલીકરણ ક્રમ

`src/sse/handlers/chat.ts` અને
`open-sse/handlers/chatCore.ts`માંથી પસાર થતી દરેક વિનંતી માટે:

1. `resolveDisabledGuardrails(...)` API કી, બોડી અને હેડર્સમાંથી સ્કિપ સૂચિ બનાવે છે.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ચડતા પ્રાથમિકતા ક્રમમાં ગાર્ડરેલ્સ ચલાવે છે:
   - અક્ષમ કરેલા ગાર્ડરેલ્સ `skipped` તરીકે નોંધાય છે.
   - દરેક ગાર્ડરેલનું `preCall`, `modifiedPayload` મારફતે પેલોડને ફરી લખી શકે છે.
   - પ્રથમ `block: true` ચેઇનને શોર્ટ-સર્કિટ કરે છે અને હેન્ડલર
     ગાર્ડરેલ અસ્વીકાર પ્રતિસાદ પરત કરે છે.
3. (સંભવિત રીતે ફરી લખાયેલો) પેલોડ કોમ્બો રાઉટિંગ અને અપસ્ટ્રીમ
   ડિસ્પેચમાં જાય છે.
4. પ્રતિસાદ તૈયાર થયા પછી, `guardrailRegistry.runPostCallHooks(...)`
   પ્રતિસાદ પર એ જ ચેઇન ચલાવે છે. અહીં `block: true` અપસ્ટ્રીમ
   પ્રતિસાદને કાઢી નાખે છે.

જે ગાર્ડરેલ્સ અપવાદ ફેંકે છે તે `error: <message>` સાથે નોંધાય છે અને
`logger.warn` મારફતે લૉગ થાય છે, પરંતુ ચેઇન ચાલુ રહે છે — ડિઝાઇન મુજબ ફેઇલ-ઓપન.

## કસ્ટમ ગાર્ડરેલ્સ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

પગલાં:

1. `BaseGuardrail`ને વિસ્તૃત કરતી `src/lib/guardrails/myGuardrail.ts` બનાવો.
2. `preCall` અને/અથવા `postCall` અમલમાં મૂકો.
3. કાં તો ઇમ્પોર્ટ સમયે નોંધણી કરો (`registerDefaultGuardrails`માંથી પુશ કરો) અથવા
   રનટાઇમ પર `guardrailRegistry.register(...)` કૉલ કરો — રજિસ્ટ્રી સમાન સામાન્યકૃત
   નામ ધરાવતા કોઈપણ અગાઉના ગાર્ડરેલને બદલી નાખે છે.
4. `tests/unit/` હેઠળ પરીક્ષણો ઉમેરો (હાલનાં ઉદાહરણો:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## પરીક્ષણ

જાણીતી સ્થિતિથી શરૂઆત કરવા માટે પરીક્ષણો વચ્ચે `resetGuardrailsForTests()`નો ઉપયોગ કરો.
ખાલી રજિસ્ટ્રીથી શરૂઆત કરવા માટે `{ registerDefaults: false }` પાસ કરો અને
માત્ર પરીક્ષણ હેઠળના ગાર્ડરેલ્સની નોંધણી કરો. Vision Bridge ડિપેન્ડન્સી
ઇન્જેક્શન (`deps.getSettings`, `deps.callVisionModel`) સ્વીકારે છે; Audio Bridge
સેટિંગ્સ, ક્ષમતાઓ, STT મોડેલ પસંદગી, ક્રેડેન્શિયલ તપાસો અને ટ્રાન્સક્રિપ્શન માટે
સમકક્ષ સીમ્સ ઉપલબ્ધ કરાવે છે. તેથી પરીક્ષણો DB અથવા નેટવર્ક ઍક્સેસ વિના બંને
પ્રવાહોને ચકાસી શકે છે.

## ઇન્જેક્શન-ગાર્ડ રૂટ કવરેજ અને રેડ-ટીમ (તબક્કો 8 · બ્લૉક D)

ઇન્જેક્શન-ગાર્ડ (`createInjectionGuard` / `withInjectionGuard`) વપરાશકર્તા પ્રોમ્પ્ટ્સ
સ્વીકારતા તમામ રૂટ્સને આવરી લે છે. તે `INJECTION_GUARD_MODE`નું પાલન કરે છે (ડિફૉલ્ટ
`warn` = ફક્ત લૉગ; `block` = HTTP 400 `SECURITY_001` પરત કરે છે).

| પ્રકાર           | રૂટ્સ                                                                                                                                                | ડિફૉલ્ટ મોડ |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| ટેક્સ્ટ (હાલનું) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| જનરેટિવ          | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| ડેટા             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

ટેક્સ્ટ નિષ્કર્ષણ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`ને આવરી લે છે.

**રેડ-ટીમ (દરરોજ રાત્રે, `nightly-llm-security.yml`):** promptfoo ચકાસે છે કે દરેક રૂટ
`INJECTION_GUARD_MODE=block`માં OWASP-LLM કોર્પસને બ્લૉક કરે છે; garak પ્રોબ્સ ચલાવે છે
(સિક્રેટ વિના સ્કિપ કરે છે). સુસંગતતા માટે `moderations`નો સમાવેશ કરવામાં આવ્યો છે —
બ્લૉક-મોડમાં ઑપરેટર્સ `resolveDisabledGuardrails` મારફતે તેને મુક્તિ આપી શકે છે.

રાત્રિકાલીન વર્કફ્લો (`.github/workflows/nightly-llm-security.yml`, cron + મેન્યુઅલ
ડિસ્પેચ)માં બે જૉબ્સ છે:

- **`promptfoo-guard` (બ્લૉકિંગ)** — `INJECTION_GUARD_MODE=block` સાથે
  `promptfoo eval -c promptfooconfig.yaml` ચલાવે છે. દરેક પ્રતિકૂળ કેસ (દા.ત. "અગાઉની
  તમામ સૂચનાઓ અવગણો…", DAN-શૈલીના જેલબ્રેક્સ) ખાતરી કરે છે કે પ્રતિસાદમાં
