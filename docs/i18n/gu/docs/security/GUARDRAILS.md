> **સત્યનો અધિકૃત સ્રોત:** `src/lib/guardrails/`
> **છેલ્લે અપડેટ કરેલું:** 2026-08-29 — v3.8.51 (Video Bridge ટ્રાન્સક્રિપ્ટનું મૂળ કૉલર દ્વારા જાહેર કરવામાં આવે છે,
> હજી સર્વર દ્વારા ચકાસાયેલું નથી — #11661 અનુસાર સ્પષ્ટ કરવામાં આવ્યું)

Guardrails, OmniRoute અને અપસ્ટ્રીમ પ્રદાતાઓ વચ્ચેની સીમા પર સુરક્ષા, નીતિ અને કન્ટેન્ટ રૂપાંતરણો લાગુ કરે છે. દરેક guardrail વિનંતીના payloads (`preCall`) અને અપસ્ટ્રીમ પ્રતિસાદો (`postCall`)નું નિરીક્ષણ કરી શકે છે (અને વૈકલ્પિક રીતે તેમને નકારી, રૂપાંતરિત અથવા ઍનોટેટ કરી શકે છે).

સિસ્ટમ **fail-open** છે: જો કોઈ guardrail કાર્યરત હોય ત્યારે અપવાદ ફેંકે, તો registry ભૂલ નોંધે છે અને વિનંતીને નિષ્ફળ કરવાને બદલે આગામી guardrail સાથે ચાલુ રહે છે. બ્લૉક કરવું હંમેશાં સ્પષ્ટ નિર્ણય (`block: true`) હોય છે, ક્યારેય આકસ્મિક ઘટના નહીં.

## બિલ્ટ-ઇન ગાર્ડરેલ્સ

રજિસ્ટ્રી આયાત પર પ્રાથમિકતા ક્રમમાં છ ગાર્ડરેલ્સને આપોઆપ લોડ કરે છે
(જુઓ `registry.ts` → `registerDefaultGuardrails()`):

| પ્રાથમિકતા | નામ                 | તબક્કા(ઓ)      | ફાઇલ                  |
| ---------- | ------------------- | -------------- | --------------------- |
| `5`        | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`        | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`        | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`       | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`       | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`       | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

નિમ્ન પ્રાથમિકતા નંબર **પ્રથમ** ચાલે છે.

### વિઝન બ્રિજ (`visionBridge.ts`) — મોડાલિટી બ્રિજ PR-1

**ગેર-વિઝન મોડેલ્સ** માટેના છબી ધરાવતી વિનંતીઓને અટકાવે છે અને અથવા તો
વિઝન-ક્ષમ મોડેલ તરફ સમગ્ર વિનંતીને ફરીથી માર્ગદર્શન આપે છે અથવા છબીના
ભાગોને ટેક્સ્ટ વર્ણન સાથે બદલવા માટે એક કન્ફિગરેબલ વિઝન મોડેલનો ઉપયોગ કરે છે
ઉપરાંત કૉલ પહેલાં. આ ટેક્સ્ટ-માત્ર પ્રદાતાઓને મલ્ટીમોડલ પેલોડ્સને પારદર્શક રીતે સંભાળવા દે છે.

પ્રવાહ:

1. જો લક્ષ્ય મોડેલ પહેલેથી જ વિઝનને સપોર્ટ કરે છે તો છોડી દો (જો તે
   ફરજિયાત-બ્રિજ યાદીમાં `isVisionBridgeForcedModel`માં દેખાય તો સિવાય).
2. `extractImageParts(messages)` દ્વારા છબીના ભાગોને કાઢી નાખો
   (`visionBridgeHelpers.ts`), જે **એકીકૃત મીડિયા ડિટેક્ટર** `detectMediaParts()`
   ને `open-sse/utils/mediaParts.ts`માં委托 કરે છે — કોમ્બો સુસંગતતા ફિલ્ટર સાથે શેર કરાયેલ એકમાત્ર સત્યનો સ્ત્રોત.
   કાઢી નાખવું તે ટોપ-લેવલ ભાગો માટે મંજૂર છે જે આકારો
   `replaceImageParts` પાછા સ્પ્લાઇસ કરી શકે છે (કાઢી નાખવું↔બદલવું કરાર): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, અને Responses API `input_image`. નેસ્ટેડ હિટ્સ અને
   સૂચક-માત્ર આકારો કોમ્બો-ફિલ્ટર સામગ્રી છે અને ક્યારેય કાઢી નાંખવામાં આવતી નથી.
   જો કશું મળતું નથી તો છોડી દો.
3. `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`) દ્વારા રનટાઇમ કન્ફિગરેશનને ઉકેલો: નવા `modalityBridge*`
   સેટિંગ્સ કી જીતે છે; વારસાગત `visionBridge*` કી **એક-ચક્ર
   પાછા ફરવા** (રોલબેક વિન્ડો) તરીકે રહે છે. બ્રિજ અક્ષમ હોય ત્યારે કોઈપણ મીડિયા ટ્રાવર્સલ પહેલાં છોડી દો.
4. મોડ પસંદકર્તા (`modalityBridgeVisionMode`, નીચેની કોષ્ટક જુઓ) ફરીથી માર્ગદર્શન
   સામે વર્ણનનો નિર્ણય કરે છે. ફરીથી માર્ગદર્શન `modifiedPayload` સાથે પાછું આપે છે
   જેમાં ફક્ત `model` બદલાયું છે, ઉપરાંત મેટા `{ rerouted, fromModel, toModel, imagesKept }`.
5. વર્ણન માર્ગ: છબીઓને `maxImages` પર મર્યાદિત કરો, કાર્ય-જાણકાર પ્રોમ્પ્ટ બનાવો,
   વર્ણન કેશને સલાહ આપો, વિઝન મોડેલને **સાથે** કૉલ કરો
   (`Promise.allSettled`), અને `[Image N]: <description>` ટેક્સ્ટ ભાગોને તેમના સ્થાનમાં દાખલ કરો. એક નિષ્ફળ વર્ણન `null` આપે છે અને મૂળ છબીનો ભાગ **સંરક્ષિત** રહે છે (#4012) — સિવાય કોમ્બો વર્ણન માર્ગ પર જ્યારે દરેક
   વર્ણન નિષ્ફળ જાય છે, જ્યાં એક પુષ્ટિ કરેલ ગેર-વિઝન ઉપરવાળા એક
   `(unavailable — no vision-capable provider connected)` સ્ટબ મળે છે (#8430).
6. `modifiedPayload` + મેટા (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) પાછું આપો.

#### મોડ પસંદકર્તા (`modalityBridgeVisionMode`)

| મોડ        | ડિફોલ્ટ | વર્તન                                                                                                                                                                                                                                                                                     |
| ---------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | વારસાગત હ્યુરિસ્ટિક, અસ્પષ્ટ (#6640/#7204): ગેર-કોમ્બો/`auto/` મોડેલો શ્રેષ્ઠ વિઝન મોડેલ તરફ ફરીથી માર્ગદર્શન આપે છે જો કે મૂળ મોડેલ પાસે ઉપયોગી પ્રમાણપત્રો હોય (ત્યારે વર્ણન); કોમ્બો લક્ષ્યો હંમેશા વર્ણન કરે છે.                                                                      |
| `describe` |         | હંમેશા વર્ણન કરો — ફરીથી માર્ગદર્શન બ્લોક સંપૂર્ણપણે છોડી દેવામાં આવે છે; વપરાશકર્તાના પસંદ કરેલા મોડેલ હંમેશા જવાબ આપે છે.                                                                                                                                                               |
| `reroute`  |         | ફરજિયાત ફરીથી માર્ગદર્શન: રાખવા-પ્રમાણિત-મોડેલ ગાર્ડને બાયપાસ કરવામાં આવે છે. ફરીથી માર્ગદર્શન-**લક્ષ્ય** પ્રમાણપત્ર ગાર્ડ હજુ પણ લાગુ પડે છે — જ્યારે કોઈ ઉપયોગી વિઝન લક્ષ્ય નથી, ત્યારે વિનંતી વર્ણન તરફ જતી હોય છે જેથી કાચી છબીઓ ક્યારેય ટેક્સ્ટ-માત્ર બેકએન્ડ સુધી ન પહોંચે (#8430). |

ફરજિયાત મોડ્સ **પહેલાં** ઓટો હ્યુરિસ્ટિક ચાલે છે; `auto` વર્તન
પ્રિ-PR-1 ગાર્ડરેલ સાથે બાઇટ-આઈડેન્ટિકલ છે.

#### API-કી વ્યાપકતા (`visionBridgeKeyScope.ts`)

જ્યારે callerની API કી `allowedConnections`, ક્વોટા પૂલ
(`allowedQuotas`) અથવા મોડેલો (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`)ને મર્યાદિત કરે છે, ત્યારે બ્રિજ ફક્ત
ફરીથી માર્ગદર્શન અને વર્ણન મોડેલો પસંદ કરે છે જે કીનો ઉપયોગ કરી શકે છે, કનેક્શન પર જે કીનો ઉપયોગ કરી શકે છે. વર્ણન કૉલ પછી હંમેશા ઓમ્નીરૂટ સ્વયં-લૂપમાં જાય છે
`x-omniroute-self-loop-key-id` હેડર સાથે, તેથી પ્રાપ્ત થતી ચેટ વિનંતી
તે કીનું કનેક્શન અને મોડેલ નીતિ ફરીથી અમલમાં લાવે છે. `enforceApiKeyPolicy()`
તે હેડરને માત્ર સ્વયં-લૂપ બેરર સાથે માન્ય રાખે છે, તેથી તે ફક્ત
ઍક્સેસને સંકોચી શકે છે, અને એક આઈડી જે ઉકેલાતું નથી તે નકારી દેવામાં આવે છે.

જો કી માટે કોઈ વિઝન મોડેલની મંજૂરી નથી, તો વર્ણન માર્ગ બાજુમાં જતો છે અને
વિનંતી બદલાવ વગર પસાર થાય છે, તે જ નિષ્ફળ-ખુલ્લા વર્તન જે એક અક્ષમ
ગાર્ડરેલ તરીકે છે (મેટા `{ skipped: true, reason: "no_permitted_vision_model" }`).
વિનંતીઓ વિના કી, અને આ મર્યાદાઓ વિના કી, અગાઉની જેમ જ વર્તે છે.

#### કાર્ય-જાણકાર વર્ણન પ્રોમ્પ્ટ (`modalityBridgeVisionTaskAware`)

ડિફોલ્ટ **સાચું**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) **છેલ્લા યુઝર સંદેશાનો** (500 અક્ષરો સુધી કાપી) લખાણને આધાર વર્ણન પ્રોમ્પ્ટમાં જોડે છે, વર્ણનને તે તરફ દોરી જાય છે જે યુઝરે વાસ્તવમાં પૂછ્યું હતું (codex-vision-proxy પેટર્ન) અને દૃષ્ટિ મોડલને દૃશ્યમાન લખાણને ટ્રાન્સક્રાઇબ કરવા માટે પૂછે છે. ફ્લેગ બંધ હોય ત્યારે — અથવા કોઈ યુઝર લખાણ ન હોય — આધાર પ્રોમ્પ્ટ અપરિવર્તિત રીતે ઉપયોગમાં લેવામાં આવે છે.

વર્ણન સ્વ-લૂપની પોતાની OpenAI-સંગત વિનંતી (`callVisionModelSingle()` `visionBridgeHelpers.ts` માં) હંમેશા `image_url.detail: "high"` માટે વિનંતી કરે છે — કોઈ શરત વિના, દરેક કોલર/પ્રદાતા માટે, કોઈ ક્લાયન્ટ સંકેત પર ગેટેડ નથી. નીચા-વિગતના નમૂનાઓ OCR ચોકસાઈને ખરાબ કરે છે તે ચોક્કસ લખાણ-ટ્રાન્સક્રિપ્શન કાર્ય માટે જે આ પ્રોમ્પ્ટ માંગે છે, તેથી વર્ણન કોલ હંમેશા ઉચ્ચ વિગતો માટે માંગે છે ભલે મૂળ inbound વિનંતી કઈ વિગતોના સ્તરનો ઉપયોગ કરે છે. આ માત્ર આંતરિક વર્ણન વિનંતી શરીરને અસર કરે છે; તે OmniRoute કેવી રીતે કોલરનો પોતાનો `image_url.detail` પ્રાથમિક વિનંતી પર આગળ વધારવા માટે બદલતું નથી — તે ડિફોલ્ટ અલગ રીતે લાગુ થાય છે, અને માત્ર શોધાયેલ OpenCode ક્લાયન્ટો માટે, `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) માં. વર્ણન સ્વ-લૂપનો Anthropic વાયર-ફોર્મેટ શાખામાં કોઈ `detail` ક્ષેત્ર નથી અને તે બંને ડિફોલ્ટથી અસંવેદનશીલ છે.

#### વર્ણન આઉટપુટ કૅપ (`modalityBridgeVisionMaxChars`)

| કી                             | ડિફોલ્ટ | શ્રેણી             |
| ------------------------------ | ------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`     | `0` અથવા 100–50000 |

`0` (ડિફોલ્ટ)નો અર્થ છે **કોઈ કૅપ નથી** — `callVisionModel()` દ્વારા પાછું મળેલ વર્ણન અપરિવર્તિત રીતે પસાર થાય છે, હાલની વર્તનને જાળવી રાખે છે. 100–50000 શ્રેણીમાં કોઈપણ મૂલ્ય વર્ણનને `…` સોફિક્સ સાથે કાપે છે તે પહેલાં તે `[Image N]: <description>` તરીકે ફરીથી જોડાય છે (`VisionBridgeGuardrail.preCall()` `src/lib/guardrails/visionBridge.ts` માં). આને ઊંચી વિગતોવાળા OCR કાર્યો માટે વધારવું જ્યાં નીચેના મોડલને સંપૂર્ણ ટ્રાન્સક્રિપ્શનની જરૂર છે; ચેટી દૃષ્ટિ મોડલ પર ટોકન ઉપયોગને બાઉન્ડ કરવા માટે તેને ઓછું કરો. ડેશબોર્ડ ક્ષેત્ર Vision ટેબના એડવાન્સ્ડ પેનલમાં રહે છે (`modality-bridge-max-chars` `ModalityBridgeVisionTab.tsx` માં) અને 1 અને 99 વચ્ચેના કોઈપણ મૂલ્યને 100 ની તળિયે કંપ કરે છે જ્યારે સ્પષ્ટ `0` ને અસ્પષ્ટ રાખે છે — `0` પોતાને જ માન્ય Zod મૂલ્ય છે (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), માત્ર "unset" ડિફોલ્ટ નથી.

#### વર્ણન કેશ (`modalityBridge/bridgeCache.ts`)

વર્ણન આઉટપુટ માટે મેમરીમાં LRU + TTL કેશ, શેર કરેલ પ્રક્રિયા-વિસ્તૃત. કી = `sha256(imageRef + composedPrompt + configuredBridgeModel)` સાથે લંબાઈ-પ્રિફિક્સ ફ્રેમિંગ (કોઈ ફીલ્ડ-બાઉન્ડરી ટકરાવા નથી). મોડલ ઘટક એ **કન્ફિગર કરેલ** બ્રિજ મોડલ છે, જે મોડલ વાસ્તવમાં જવાબ આપ્યું — `callVisionModel` આંતરિક રીતે પાછું પડી શકે છે, અને દરેક પ્રયાસ પર કીંગ કરવાથી કેશને તૂટે છે. નિષ્ફળ વર્ણનો કેશ કરવામાં નથી આવતો. સેટિંગ્સ:

| કી                              | ડિફોલ્ટ | શ્રેણી  |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### રિમોટ ઇમેજ નોર્મલાઇઝેશન (સ્વ-લૂપ વર્ણન/base64 ફેચ)

જ્યારે બ્રિજ **રિમોટ** ઇમેજને પોતે ફેચ કરે છે — Anthropic વર્ણન સ્વ-કોલ અને claude-wire-format base64 રૂપાંતરણ (`ensureBase64ImagesForClaudeWire`), બંને `fetchRemoteImageAsDataUri()` માં `visionBridgeHelpers.ts` દ્વારા — પરિણામે મળેલ ડેટા URI `normalizeDataUri()` દ્વારા પસાર થાય છે (`open-sse/utils/imageNormalize.ts`) પહેલાં દૃષ્ટિ-મોડલ વિનંતીમાં એમ્બેડ કરવામાં આવે છે. ઓવરસાઇઝ્ડ ઇમેજોને **2048px લાંબા કિનારે** (જે OpenAI/Anthropic પહેલેથી સર્વર-સાઇડ પર લાગુ કરે છે) પર ઘટાડવામાં આવે છે, જે અપલોડ બાઇટ્સ/લેટન્સીને કાપે છે તે વિના દૃષ્ટિ મોડલ શું જોવે છે તે બદલ્યા વિના. પુનઃમાપન `sharp` નો ઉપયોગ કરે છે, જે ડાયનેમિક આયાત દ્વારા લોડ થાય છે: એક પ્લેટફોર્મ પર જ્યાં તેની નેટિવ બાયનરી લોડ થવામાં નિષ્ફળ જાય છે, `normalizeDataUri()` **ક્યારેય ફેંકતું નથી** — તે મૂળ બાઇટ્સના પાસ થવામાં પાછું પડે છે, તેથી વર્ણન/base64-રૂપાંતરણ માર્ગ હંમેશા કાર્યરત રહે છે. નોન-ઇમેજ બાઇટ્સ (એક ફેચ જે ડીકોડ કરી શકાય તેવી ઇમેજ પાછું ન લાવે) પણ અપરિવર્તિત રીતે પસાર થાય છે. આ નોર્મલાઇઝેશન બ્રિજ દ્વારા તેના પોતાના સ્વ-કોલ માટે ફેચ કરેલ ઇમેજો સુધી મર્યાદિત છે — તે ક્યારેય કોલરનું કાચું પાસ થતું પેઇલોડ પર લાગુ નથી થતું, ઓપ્ટ-ઇન-માત્ર મ્યુટેશન સિદ્ધાંત (હાર્ડ રૂલ #20) સાથે સુસંગત છે.

#### સેટિંગ્સ સ્કીમા + માઇગ્રેશન

નવી `modalityBridge*` કી `updateSettingsSchema` માં Zod-પ્રમાણિત છે (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCache*` ત્રિયો, અને `modalityBridgeAudio*` જૂથ જે ઓડિયો બ્રિજ દ્વારા ઉપયોગમાં લેવાય છે. માઇગ્રેશન `141_modality_bridge_settings.sql` અસ્તિત્વમાં રહેલ વારસાગત `visionBridge*` મૂલ્યોને મેળ ખાતા નવા કી પર નકલ કરે છે (ઇડેમ્પોટન્ટ, ક્યારેય ઓપરેટર-સેટ `modalityBridge*` મૂલ્યને ઓવરરાઇટ નથી કરે); વારસાગત કી એક રીડ ફોલબેક તરીકે એક રિલીઝ ચક્ર માટે સ્વીકૃત રહે છે.

#### પારદર્શિતા હેડર + આંકડા

વર્ણન-પરિવર્તિત પ્રતિસાદો ધરાવે છે `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` (જે `buildModalityBridgeHeader()` માં બનાવવામાં આવે છે `modalityBridge/bridgeStats.ts`, `withModalityBridgeHeader()` માં સ્ટેમ્પ કરવામાં આવે છે `src/sse/handlers/chatHelpers.ts`). ફરીથી માર્ગદર્શિત વિનંતીઓમાં **કોઈ** હેડર નથી — પેઇલોડ અપરિવર્તિત હતું અને મોડલ સ્વાપ પહેલેથી જ પ્રતિસાદના શરીરના `model` ક્ષેત્રમાં દેખાય છે.

`GET /api/modality-bridge/stats` (વ્યવસ્થાપન પ્રાધિકરણ, `GET /api/settings` સાથે સમાન સ્તર) મેમરીમાં પ્રત્યેક મોડાલિટી કાઉન્ટર્સ પાછા આપે છે `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` માટે `vision`, `audio`, અને `video`. `averageLatencyMs` `latencySamples` નો ઉપયોગ કરે છે, બધા પ્રયાસો નહીં, તેના ગુણાંક તરીકે; સમય વિના એક ઓપરેશન શૂન્ય-મિલિસેકન્ડ નમૂનો બનાવતું નથી. `bridged` સફળ રૂપાંતરણો માટે પાછળની સુસંગત ઉપનામ તરીકે રહે છે; નિષ્ફળ પ્રયાસો તેને વધારતા નથી. કાઉન્ટર્સ પ્રક્રિયા પુનઃપ્રારંભ પર ડિઝાઇન દ્વારા પુનઃસેટ થાય છે (ટેલેમેટ્રી, નાણાકીય હિસાબ નહીં).

#### ડેશબોર્ડ રૂપરેખાંકન

વિશિષ્ટ ડેશબોર્ડ પાનું છે `/dashboard/settings/modality-bridge`. તેની URL-સરનામાની `Vision`, `Audio`, અને `Video` ટેબ્સ `tab` મૂલ્ય બદલતા સમયે ક્વેરી પેરામીટર્સ જાળવે છે. Vision ટેબ સક્રિયતા, મોડ, મોડલ પસંદગી (સ્વચાલિત ડિફોલ્ટ સહિત), કાર્ય-જાણકાર પ્રોમ્પ્ટિંગ, અદ્યતન ટાઇમઆઉટ/છબી/વર્ણન-લંબાઈ/કેશ મર્યાદાઓ, રનટાઇમ કાઉન્ટર્સ, અને એક સુરક્ષિત નમૂના વિનંતી પ્રદર્શિત કરે છે. Audio ટેબ પણ જીવંત છે: તે સક્રિયતા, STT-માત્ર મોડલ પિકર સાથે Auto, ટાઇમઆઉટ/મહત્તમ-ક્લિપ મર્યાદાઓ, ઓડિયો કાઉન્ટર્સ, અને એક `input_audio` નમૂના પરીક્ષણ પ્રદર્શિત કરે છે. Video ટેબ કાર્યાત્મક છે: તે FFmpeg/ffprobe રનટાઇમ રાજ્યને રિપોર્ટ કરે છે — ચાર સ્પષ્ટ UI રાજ્યોમાંની એક (`unknown` જ્યારે પ્રોબ ઉડાનમાં છે અથવા પૂર્ણ થઈ શકતું નથી, `restricted` એક નોન-લૂપબેક ડેશબોર્ડ હોસ્ટ પર જ્યાં પ્રોબ ક્લાયન્ટ-સાઇડ પર છોડી દેવામાં આવે છે, `unavailable` એકવાર પ્રોબ કરવામાં આવે છે અને ખોટું હોવાનું પુષ્ટિ કરવામાં આવે છે, અથવા `available` FFmpeg/ffprobe આવૃત્તિઓ સાથે) — સક્રિય/મોડલ/ફ્રેમ/વિડિયો/ટાઇમઆઉટ મર્યાદાઓ જાળવે છે, મોડલ પિકરને દ્રષ્ટિ-ક્ષમ મોડલ્સ સુધી મર્યાદિત કરે છે, અને વિડિયો કાઉન્ટર્સને પ્રદર્શિત કરે છે.

AI સેટિંગ્સ હેઠળનો પૂર્વવર્તી Vision Bridge કાર્ડ નવા પાનાને સુસંગતતા લિંક છે; તે ફોર્મની બીજી નકલ ધરાવતી નથી. મીડિયા પ્રદાતાઓ પણ છબી-થી-ટેક્સ્ટ અને ભાષણ-થી-ટેક્સ્ટ કાર્યપ્રવાહોને સંબંધિત મોડાલિટી બ્રિજ ટેબ્સ સાથે લિંક કરે છે, જે હાલના ભાષણ-થી-ટેક્સ્ટ પ્લેગ્રાઉન્ડને દૂર કર્યા વિના.

**સ્વ-લૂપ પ્રવેશ બાયપાસ:** જ્યારે વર્ણન કોલ ઓમ્નીરૂટના પોતાના `/v1` સ્વ-લૂપ (અસામાન્ય પ્રદાતા મોડલ) મારફતે માર્ગદર્શન કરે છે, ત્યારે ઉપ-વિનંતી `x-omniroute-admission-bypass: internal` મોકલે છે અને ઉકેલાયેલા સ્વ-લૂપ પ્રમાણપત્ર સાથે માન્યતા પ્રાપ્ત થાય છે — સ્થાનિક મોડમાં સ્થાનિક `sk_omniroute` સેન્ટિનલ, અથવા ઓપરેટર-કન્ફિગર કરેલ `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env કી (#1350) જેથી `REQUIRE_API_KEY=true` ડિપ્લોયમેન્ટ્સ વર્ણન કોલ ચલાવી શકે. બાયપાસ માત્ર તે ચોક્કસ પ્રમાણપત્રો માટે માન્ય છે, તેથી બાહ્ય ક્લાયન્ટ header નો ઉપયોગ કરીને પ્રવેશને છોડી શકતા નથી.

પરંપરાગત ડિફોલ્ટ્સ `src/shared/constants/visionBridgeDefaults.ts` માં રહે છે; નવા મોડ/કાર્ય-જાણકાર/કેશ ડિફોલ્ટ્સ અને સેટિંગ્સ રિઝોલ્વર `src/shared/constants/modalityBridgeDefaults.ts` માં રહે છે. ગાર્ડરેલ એક `deps` કન્સ્ટ્રક્ટર વિકલ્પ પ્રદર્શિત કરે છે જેથી પરીક્ષણો નકલી `getSettings` અને `callVisionModel` અમલને દાખલ કરી શકે.

### ઓડિયો બ્રિજ (`audioBridge.ts`) — મોડાલિટી બ્રિજ PR-3

ઓડિયો ધરાવતી ચેટ વિનંતીઓને લક્ષ્ય પર પહોંચતા પહેલા અટકાવે છે જે ઓડિયો ઇનપુટ સ્વીકારવા માટે જાણીતી નથી. તે ક્યારેય ચેટ વિનંતીને ફરીથી માર્ગદર્શન આપતું નથી: ઓડિયો ભાગો મૌજુદ OpenAI-સંગત મલ્ટિપાર્ટ અંતિમ બિંદુ મારફતે લખવામાં આવે છે અને પસંદ કરેલ ચેટ મોડ ટેક્સ્ટ ટ્રાન્સક્રિપ્ટ સાથે ચાલુ રહે છે.

પ્રવાહ:

1. `getResolvedModelCapabilities()` મારફતે `supportsAudio` ઉકેલવું. સ્પષ્ટ પ્રદાતા-રજિસ્ટ્રી મેટાડેટા જીતે છે, પછી સ્થિર મોડલ મેટાડેટા, પછી સમંકિત `modalities_input`. `audio` વિના જાહેર કરેલ ઇનપુટ યાદી `false` છે; કોઈ ક્ષમતા પુરાવા `null` રહે છે. બંને `false` અને `null` સંરક્ષિત બ્રિજને સક્રિય કરે છે, જ્યારે `true` તેને બાયપાસ કરે છે.
2. `modalityBridgeAudio*` સેટિંગ્સ ઉકેલવું અને દરેક સંદેશામાંથી સ્પ્લાઇસેબલ ટોપ-લેવલ ઓડિયો ભાગો કાઢવા માટે શેર કરેલ `detectMediaParts()` ડિટેક્ટરનો ઉપયોગ કરવો. સમર્થિત વાયર આકારો OpenAI `input_audio`, `audio_url`, અને `source.media_type: "audio/*"` છે. નેસ્ટેડ ઓડિયો માર્ગદર્શન માટે ઓળખવામાં આવે છે પરંતુ સ્પ્લાઇસ પાથ દ્વારા દૂર કરવામાં આવતું નથી. કાર્ય `modalityBridgeAudioMaxClips` દ્વારા મર્યાદિત છે; પછીના ભાગો અચૂક રહે છે.
3. એક કન્ફિગર કરેલ `provider/model`ને માન્યતા આપો, અથવા `selectAudioBridgeModel()` ને `AUDIO_TRANSCRIPTION_PROVIDERS` માં સ્થિર કૅટલોગ ક્રમમાં ચાલવા દો અને પ્રથમ મોડલ પસંદ કરો જે ઉપયોગી સક્રિય પ્રદાતા પ્રમાણપત્ર ધરાવે છે.
4. `callAudioTranscription()` base64/data-URI ઓડિયોને મલ્ટિપાર્ટ `file` માં રૂપાંતરિત કરે છે, અથવા જાહેર-માત્ર આઉટબાઉન્ડ ગાર્ડ મારફતે DNS પિનિંગ અને 25 MB મર્યાદા સાથે એક દૂરના `audio_url` ને ડાઉનલોડ કરે છે. તે પછી ફાઇલ અને પસંદ કરેલ મોડલને સ્થાનિક `/v1/audio/transcriptions` સ્વ-લૂપમાં POST કરે છે, જે `resolveSelfLoopBearer()` સાથે માન્યતા પ્રાપ્ત છે. મૌજુદ ટ્રાન્સક્રિપ્શન માર્ગ સામાન્ય પ્રમાણપત્ર શોધ, કૂલડાઉન/દર-મર્યાદા હેન્ડલિંગ, અને પ્રદાતા વિતરણ કરે છે.
5. સફળ કોલ્સ તેમના ભાગોને `[Audio N]: <transcript>` સાથે બદલે છે. કોલ્સ `Promise.allSettled` સાથે ચલાવવામાં આવે છે: એક વ્યક્તિગત નિષ્ફળતા મૂળ ઓડિયો ભાગને જાળવે છે (#4012 કરાર). જો દરેક કોલ નિષ્ફળ જાય અને લક્ષ્યને સાબિત કરવામાં આવે `supportsAudio === false`, તો ભાગો બની જાય `[Audio N]: (unavailable — no STT provider connected)` (#8430 કરાર). અજાણ્યા લક્ષ્ય માટે (`null`), એક તમામ-નિષ્ફળ પરિણામ અચૂક રહે છે. એક સાબિત ટેક્સ્ટ-માત્ર લક્ષ્ય જે કોઈ ઉપયોગી STT પ્રમાણપત્ર ધરાવતું નથી તે સમાન સ્પષ્ટ સ્ટબ પ્રાપ્ત કરે છે વિના નેટવર્ક કોલ જારી કર્યા.

સફળ ટ્રાન્સક્રિપ્ટ્સ પ્રક્રિયા-વિસ્તૃત મોડાલિટી બ્રિજ LRU/TTL કેશનો ઉપયોગ કરે છે. કી ઓડિયો સંદર્ભ, સ્થિર `audio-transcription` ઓપરેશન લેબલ, અને પસંદ કરેલ STT મોડલને જોડે છે; નિષ્ફળતાઓ ક્યારેય કેશ કરવામાં આવતી નથી. ઓડિયો પ્રયાસો શેર કરેલ `bridged`, `cacheHits`, `failures`, અને `lastUsedAt` કાઉન્ટર્સને અપડેટ કરે છે. રૂપાંતરિત પ્રતિસાદો ધરાવે છે `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; અચૂક વિનંતીઓને ઓડિયો બ્રિજ વિભાગ પ્રાપ્ત નથી.

રનટાઇમ સેટિંગ્સ DB-આધારિત અને Zod-માન્યતા પ્રાપ્ત છે:

| કી                            | ડિફોલ્ટ | શ્રેણી           |
| ----------------------------- | ------- | ---------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —                |
| `modalityBridgeAudioModel`    | `""`    | Auto અથવા STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000      |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10             |

સાંજેદાર કેશ `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, અને `modalityBridgeCacheMaxEntries` દ્વારા નિયંત્રિત રહે છે.

### વિડિયો બ્રિજ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ચેટ પૂર્ણતાઓ `messages` અને પ્રતિસાદો API `input` માં ટોચના સ્તરના વિડિયો ભાગોને અવરોધિત કરે છે
જ્યારે કોઈ નિશ્ચિત સ્થાનિક વિડિયો સપોર્ટ સાથેનો લક્ષ્ય કૉલ કરવામાં આવે છે.
સમર્થિત આકારો છે `input_video`, `video_url`, `video_source`, HTTPS URLs,
અને `data:video/*;base64,...` ડેટા URI. ટેક્સ્ટમાં સાદા ફાઇલના નામોને
વિડિયો તરીકે માનવામાં આવતું નથી.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) વિનંતી પસાર કરે છે, ક્ષમતા/નીતિ ચકાસણી, પ્રતિ વિનંતી સંકલન, અને પ્રતિસાદ પેલોડ.
પ્રતિ વિડિયો કાર્ય — પ્રાપ્ત કરવું, સમગ્ર પરિણામ કેશ, ફ્રેમ
ક્રમનું વર્ણન (જે કોઈ પણ કૉલર દ્વારા જાહેર કરેલા ઓડિયો ટ્રાન્સક્રિપ્ટને મિશ્રિત કરે છે), અને પ્રતિ પ્રયાસ
મેટ્રિક્સ/રદ/સફાઈ — `processVideoPart` પાછળ છુપાયેલું છે
`videoBridgePipeline.ts` માં, જે `preCall` ના લૂપમાં પ્રતિ વિડિયો ભાગ માટે એકવાર કૉલ થાય છે.
તે મોડ્યુલ સ્પષ્ટ પોર્ટ સીમાઓને પણ વ્યાખ્યાયિત કરે છે `VideoMediaBrokerPort`
(બાઇટ્સ મેળવવું અને નમૂનાકૃત ફ્રેમ્સ કાઢવું), `VideoAudioTranscriptionPort`
(કૉલર દ્વારા જાહેર કરેલા ઓડિયો ટ્રાન્સક્રિપ્ટને નમૂનાકૃત શીર્ષકો સાથે મિશ્રિત કરવું), અને
`VideoDrilldownPort` (પરંપરાગત કાચા-સ્ટોર આકાર). ઉત્પાદન STT અને ફ્રેમ જાળવણી
વર્ણન પોર્ટની આસપાસ રચાયેલ છે `createVideoSttAdapter` અને
`createVideoDrilldownAdapter`; છેલ્લું શેર કરેલા ઓપેક-હેન્ડલ જીવનચક્રનો ઉપયોગ કરે છે.

જાહેર `/v1` વિનંતી માર્ગ ક્યારેય એક ઉપપ્રક્રિયા આયાત અથવા કૉલ નથી કરે. દૂરના
વિડિયોને 50 MiB મર્યાદા હેઠળ ડાઉનલોડ કરવામાં આવે છે; ઇનલાઇન બેસ64 વિડિયોને
સંરક્ષણાત્મક 36 MiB ડિકોડ કરેલ પ્રતિ વિડિયો મર્યાદા છે જેથી મોડેલ/messages/framing envelope

#### FU-07 ઢાંચાકીય સેગમેન્ટ પુરાવો

`segment_aware` પહેલેથી માન્ય સ્થાનિક વિડિઓ સ્ટ્રીમ પર એક બાઉન્ડેડ પ્રી-એનલિસિસ પાસનો ઉપયોગ કરે છે. ફિક્સ્ડ ફિલ્ટર ચેઇન પ્રથમ 320 પિક્સેલ પહોળાઈ સુધી સ્કેલ કરે છે, દૃશ્ય પરિવર્તનો અને જમણાં સમયગાળા શોધે છે, પછી ધૂંધલાપણું, સરેરાશ લ્યુમા, અને જગ્યા/સમયની માહિતી માટે પ્રતિ સેકન્ડ 1 ફ્રેમ નમૂના લે છે. પાસ 600 બંધારણ નમૂનાઓ, એક FFmpeg/filter થ્રેડ, સમાન `file`-ફક્ત પ્રોટોકોલ અને કન્ટેનર અલોયલિસ્ટ, 1 MiB પ્રક્રિયા-આઉટપુટ બાઉન્ડ, અને બ્રોકરના શેર કરેલા અભિગમ/સમયસીમા અંદર મહત્તમ 30 સેકન્ડ સુધી મર્યાદિત છે. તે ક્યારેય વિનંતીમાંથી આદેશ, ફિલ્ટર, માર્ગ, અથવા URL સ્વીકારતું નથી.

બંધારણ મૂલ્યો નિશ્ચિત નમૂના પુરાવા છે, અર્થપૂર્ણ વિડિઓ સમજણ નથી. તેઓ વિષયો, ક્રિયાઓ, શીર્ષકો, ભાષણ, અથવા વપરાશકર્તા ઇરાદા અનુમાનિત નથી. દૃશ્ય અને જમણાં સીમાઓ વિભાગો બનાવે છે; જમણાં આવરણ, ધૂંધલાપણું, પ્રકાશન, જગ્યા વિગતો, અને સમય પરિવર્તન માત્ર તે કેવી રીતે વર્તમાન 1–16 ફ્રેમ બજેટ ફાળવવામાં આવે છે તે પર અસર કરે છે. સંપૂર્ણ રીતે જમણાં થયેલ વિભાગ એક ફ્રેમ પર મર્યાદિત છે, જ્યારે ન જમણાં થયેલ વિભાગો બાકી બજેટ માટે સ્પર્ધા કરે છે. જ્યારે સીમાઓ ફ્રેમ્સની સંખ્યાને વધુ હોય છે, ત્યારે સમાન સમયરેખા આવરણ જાળવવામાં આવે છે જેથી ઝડપી પ્રારંભિક કટ્સ લાંબા પછાત વિભાગને છુપાવી ન શકે. 1-સેકન્ડના વિશ્લેષણના ઉકેલમાં જમણાં સીમાના અંદર દૃશ્ય સીમાઓ એકત્રિત કરવામાં આવે છે.

ગેરહાજર ફિલ્ટર્સ, ખોટા/ખાલી પુરાવા, ડિટેક્ટર ભૂલ, અથવા બાઉન્ડેડ પ્રી-એનલિસિસ ટાઇમઆઉટ ચોક્કસ સમાન મધ્યબિંદુ નીતિ પર ખૂલે છે. એક કૉલર અભિગમ અથવા બ્રોકર સમયસીમા ખૂલે નહીં: તે ફ્લાઇટમાં રહેલા ઉપપ્રક્રિયાને સમાપ્ત કરે છે, પછીની ફ્રેમ નિષ્કર્ષણને રોકે છે, અને ખાનગી તાત્કાલિક વૃક્ષ `finally` માં દૂર કરવામાં આવે છે.

`scripts/perf/video-bridge-fu07-eval.ts` પોસ્ટ-ડેડુપ શીર્ષક-કૉલ બચત, ઘન-ચલન બજેટ ફાળવણી, ધૂંધલાપણું/પ્રકાશન/SI-TI પુરાવા, લાંબા પછાત સાથે ઝડપી કટ્સ, અને ધીમે-ફેડ ખોટા પોઝિટિવ્સ માટે નિશ્ચિત વાસ્તવિક FFmpeg ફિક્સચર્સ બનાવે છે. તે પ્રી-એનલિસિસ વોલ સમયને નોંધે છે અને જ્યાં `/usr/bin/time` ઉપલબ્ધ છે, ત્યાં બાળક CPU અને પીક RSS. તેની ગુણવત્તા ચકાસણીઓ માત્ર બંધારણ ઓરેકલ છે. વાસ્તવિક શીર્ષક-મોડલ ગુણવત્તા `HOLD` પર રહે છે કારણ કે આ હાર્નેસ પાસે કોઈ અધિકૃત અંતિમ બિંદુ અથવા જમણાં જજ નથી. નાણાકીય બચત પણ `HOLD` પર રહે છે જો કે `--caption-cost-per-call-usd` સ્પષ્ટ સકારાત્મક પ્રતિ-કૉલ અંદાજ પૂરું પાડે છે; સ્ક્રિપ્ટ ક્યારેય કોઈપણ પરિણામ બનાવતી નથી.

દરેક ફ્રેમ 4 MiB સુધી મર્યાદિત છે, તમામ કાચા ફ્રેમ્સ સાથે 23 MiB સુધી, અને સીરિયલાઇઝ્ડ બ્રોકર પ્રતિસાદ 32 MiB સુધી. એક ખાનગી તાત્કાલિક ડિરેક્ટરી `finally` માં દૂર કરવામાં આવે છે. ઓમ્નીરૂટ FFmpeg ને બંડલ નથી કરતી અને કસ્ટમ એક્ઝિક્યુટેબલ માર્ગ સ્વીકારતી નથી. શીર્ષક આપતા પહેલા, બ્રિજ એક સંરક્ષણાત્મક દૃશ્ય ડેડુપ્લિકેશન પાસ લાગુ કરે છે: દરેક JPEG ને 16×16 ગ્રેસ્કેલ બફરમાં ઘટાડવામાં આવે છે અને તે માત્ર છેલ્લી ફ્રેમ સાથે જ તુલના કરવામાં આવે છે. એક ફ્રેમથી વધુની માંગ કરેલી શીર્ષક બજેટ માટે, નિષ્કર્ષણ બાઉન્ડેડ ઉમેદવાર પૂલ પૂરો પાડે છે જે તે બજેટના બે ગણા સુધી છે અને ક્યારેય 16 ફ્રેમ્સથી વધુ નથી. માંગ કરેલ મર્યાદા ડેડુપ્લિકેશન પછી જ લાગુ થાય છે, પ્રથમ અને અંતિમ પસંદ કરેલ ઉમેદવારોને અંતિમ પાતળા દરમિયાન જાળવવામાં આવે છે જ્યારે બજેટ ઓછામાં ઓછા બે હોય. સંસ્કરણવાળા `grayscale-16x16-mean-cells-v2` નીતિ સરેરાશ લ્યુમા ડેલ્ટા અને થંબનેલ સેલ્સના પ્રમાણનો મોટો ઉપયોગ કરે છે જેનું સામાન્ય ડેલ્ટા ઓછામાં ઓછું 0.05 છે. ડુપ્લિકેટ થ્રેશોલ્ડ સ્થિર 0.04 છે, જે આગાહી માટે પસંદ કરવામાં આવી છે, ન કે રનટાઇમ સેટિંગ તરીકે પ્રદર્શિત. આ દ્વિતીય ઉચ્ચ-વિપરીત સંકેત નાના ચળવળ અને દૃશ્ય-ટેક્સ્ટ પરિવર્તનોને જાળવે છે જે માત્ર સરેરાશ તુલનાએ છુપાવી શકે છે. તુલનાકાર અથવા ડિકોડર ભૂલો ખૂલે છે અને આવરણ જાળવે છે. આઉટપુટ મેટાડેટા કાઢેલા ઉમેદવારો, સફળતાપૂર્વક ઉપયોગમાં લેવાયેલા ફ્રેમ્સ, અને દૃશ્ય ડુપ્લિકેટ્સને અલગ કરે છે.

એક સ્પષ્ટ રીતે ચિહ્નિત વિડિઓ ભાગ સમયચિહ્નિત સંપર્ક શીટની માંગ કરી શકે છે. બ્રિજ મહત્તમ 4-કોલમ, 16-ફ્રેમ JPEG ગ્રિડ બનાવે છે. દરેક 512-પિક્સેલ સેલ તેની સ્ત્રોત સમયચિહ્નને ઉચ્ચ-વિપરીત તળિયાના બૅન્ડમાં બર્ન કરે છે, જ્યારે તે જ સમયચિહ્નો ટેક્સ્ટ મેટાડેટામાં નીચેના સંઘટન અને ઓડિટ માટે રહે છે. સંપૂર્ણ JPEG 32 MiB પર મર્યાદિત રહે છે. જો `sharp` ગ્રિડને ડિકોડ અથવા રચવા માટે અસમર્થ હોય, તો બ્રિજ વ્યક્તિગત JPEG ફ્રેમ્સ પર પાછું જાય છે; ક્લાયન્ટ અભિગમ હજુ પણ શીટ ઓપરેશનમાં ફેલાય છે.

પ્રમોશન પુરાવો故意 રીતે કૃત્રિમ રચના માઇક્રોબેંચમાર્કથી અલગ છે. `scripts/perf/video-bridge-contact-sheet-eval.ts` વાસ્તવિક OpenAI-સંગત દૃષ્ટિ મોડલ માટે એક સ્કીમા-સંસ્કરણિત A/B હાર્નેસ વ્યાખ્યાયિત કરે છે. તે પ્રદાતા-અહેવાલિત ટોકન, અંત-થી-અંત વોલ વિલંબ (શીટ રચનાને સમાવેશ કરીને), મોડલ-કૉલ ગણતરી, અને મેનિફેસ્ટ-વ્યાખ્યાયિત તથ્ય જાળવણીને માપે છે. કાચા મોડલ પ્રતિસાદો રિપોર્ટમાં લખવામાં આવતાં નથી; ફક્ત SHA-256 ડિજેસ્ટ અને મેળ ખાતા તથ્ય ID જ રાખવામાં આવે છે. હાર્નેસ કોઈ નેટવર્ક અથવા ચૂકવેલ મોડલ કૉલ નથી કરતી જો કે `--execute-real` પસાર કરવામાં આવે છે અને `--model`, `OMNIROUTE_BASE_URL`, અને `OMNIROUTE_API_KEY` કન્ફિગર કરવામાં આવે છે. તે સ્પષ્ટ વાસ્તવિક ચલાવ્યા વિના, તેની મશીન-વાંચનીય ચુકાદો `HOLD` પર રહે છે; કૃત્રિમ પેલોડ/કૉલ-ગણતરીના માપ જ પ્રમોશન પુરાવો નથી.

અલગ `scripts/perf/video-bridge-promotion-eval.ts` FU-07 અથવા FU-09 અવલોકનોનો ઉપયોગ કરે છે. પ્રમોશન પ્રવેશ માટે તમામ આઠ કૃત્રિમ દ્રષ્ટાંત પ્રકારો અને એક સાફ કરેલ વાસ્તવિક ક્લિપ, દરેક ભૂમિકા અને કેસ માટે ઓછામાં ઓછા ત્રણ માપેલા પુનરાવૃત્તિઓ, તમામ દસ જાહેર કરેલ મેટ્રિક્સ, જમણાં મીડિયા/પ્રોમ્પ્ટ/અપેક્ષિત-તથ્ય/સેટિંગ્સ ડિજેસ્ટ, અનન્ય અવલોકન ID અને માન્ય બીજિત A/B ક્રમની જરૂર છે. અમલની રસીદ કોર્પસ ડિજેસ્ટ, ચોક્કસ ઉમેદવાર SHA અને મોડલ સંસ્કરણને બાંધે છે. ગેરહાજર અથવા અમાન્ય માપો `HOLD` પર રહે છે, જેમાં CPU 30 સેકન્ડથી વધુ, પીક RSS 512 MiB થી વધુ અથવા પ્રી-એનલિસિસ 30 સેકન્ડથી વધુ છે. આ પુરાવો-પ્રવેશ મર્યાદા છે, નવી રનટાઇમ RSS અમલમાં લાવવાની ખાતરી નથી.

FU-07 ને ઓછામાં ઓછા 98% ગુણવત્તા જાળવણી અને p95 વિલંબ 1.2x બેઝલાઇનથી વધુ ન હોવું જોઈએ, ઉપરાંત સમાન સરેરાશ કૅપ્શન કૉલ્સ પર 0.05 સંપૂર્ણ કેસ-સંતુલિત સરેરાશ પુનઃપ્રાપ્તિ સુધારો અથવા ઓછામાં ઓછા 10% ઓછા સરેરાશ પોસ્ટ-ડેડુપ કૅપ્શન કૉલ્સ હોવા જોઈએ. FU-09 ને ઓછામાં ઓછા 0.85 ગુણવત્તા, 95% જાળવણી, 20% p95 વિલંબ ઘટાડો અને 10% ટોકન ઘટાડો જોઈએ. મહત્વપૂર્ણ તથ્ય નુકશાન, ઇન્જેક્શન અનુરૂપતા અથવા ગેરહાજર ઉપયોગ પ્રમોશનને રોકે છે. એક અમલ કંઈપણ પ્રમોટ કરી શકતું નથી: `--previous-report` સમાન નીતિ/મોડલ સંશોધન/ઉમેદવાર/કોર્પસના બે અલગ, નોન-ઓવરલેપિંગ, અનુક્રમણિકા માટેની યોગ્ય અમલની પુષ્ટિ કરે છે. એક નમૂના પ્રયોગ સંપર્ક-શીટ પ્રયોગની પુષ્ટિ કરી શકતો નથી.

સંગ્રહકોએ યાદીમાં પ્રતિસાદોને સ્કોર કરવો જોઈએ અને `responseDigest` સાથે મેટ્રિક્સ અને અવલોકન બાઇન્ડિંગ્સ સાચવવા જોઈએ, ક્યારેય પ્રતિસાદ લખાણ નહીં. ગ્રાહક પણ વારસાગત કાચા અવલોકનો વાંચે છે પરંતુ ક્યારેય તે લખાણને તેની અહેવાલોમાં નકલ નથી કરે. દરેક અવલોકન માટે ચોક્કસપણે `responseDigest` અથવા `rawResponseText` માંથી એક જ સ્વીકારવામાં આવે છે. સંસ્કરણવાળા મંજૂરી યાદી ખાલી રહે છે જેમાં અપરિવર્તિત `hold` ડિફોલ્ટ છે. એક યોગ્ય એન્ટ્રી માટે તેની પુરાવાની સંદર્ભ, નીતિ, મોડલ સંશોધન, ચોક્કસ ઉમેદવાર SHA, મેનિફેસ્ટ ડિજેસ્ટ અને બે અલગ રન ID ની જરૂર છે; વિરુદ્ધ સંદર્ભો નકારી દેવામાં આવે છે. આ મેટાડેટા એક ઓડિટ કરાર છે, જે દર્શાવે છે કે સંદર્ભિત ફાઇલમાં વાસ્તવિક માપણો છે. કોઈપણ એન્ટ્રી ઉમેરવા પહેલાં વાસ્તવિક રસીદો સમીક્ષા કરો. મેનેજમેન્ટ આંકડા અંતિમ બિંદુ અને વિડિઓ ડેશબોર્ડ સંરક્ષિત તૈયારીને પ્રદર્શિત કરે છે. એક રૂપરેખાંકિત મોડલ ઉપનામ જ તેની સંશોધન અથવા ચાલતી ઉમેદવાર SHA સ્થાપિત નથી કરતી, તેથી વર્તમાન ડેશબોર્ડ `HOLD`ને રિપોર્ટ કરે છે અને અન્ય અમલ સંદર્ભમાંથી યોગ્યતા ફરીથી ઉપયોગ કરતી નથી. સ્પષ્ટ પ્રયોગાત્મક પસંદગી પ્રમોશનથી અલગ રહે છે; કોઈ ડિફોલ્ટ આપોઆપ બદલાતું નથી.

કોલર્સે સમર્થિત વિડિઓ ભાગ સાથે વૈકલ્પિક `transcript.cues` એરે જોડવા માટે જ્યારે તેઓ પહેલેથી જ સમન્વિત લખાણ ધરાવે છે ત્યારે કરી શકે છે. દરેક ક્યૂમાં `text`, એક મર્યાદિત `start`/`end` અંતર હોવું જોઈએ જે તપાસવામાં આવેલી અવધિની અંદર હોય, અને એક વ્હાઇટલિસ્ટેડ `source` (`client`, `embedded`, અથવા `audio-bridge`); `confidence` ડિફોલ્ટ તરીકે `1` છે અને `0` અને `1` વચ્ચે રહેવું જોઈએ. ચોક્કસ ડુપ્લિકેટ ક્યૂઝને સમકક્ષ કરવામાં આવે છે. OmniRoute ક્યારેય આ મેટાડેટા પરથી ટ્રાન્સ્ક્રિપ્શન શરૂ કરતું નથી: માન્ય ક્યૂઝને વર્ણવેલ પરિણામમાં સ્ત્રોત, વિશ્વસનીયતા અને અંતર સાથે નકલ કરવામાં આવે છે, અને ફ્રેમ કૅપ્શન સાથે અવિશ્વસનીય અવલોકનો તરીકે રજૂ કરવામાં આવે છે. અમાન્ય, રેન્જની બહાર, અથવા પુરાવા-મુક્ત લખાણને કૅપ્શન પ્રવાહમાં મિશ્રિત કરવામાં બદલે નકારી દેવામાં આવે છે. બંને વિનંતી-શરીર ટ્રાન્સ્ક્રિપ્ટ ચેનલ્સ પુરવઠા પુરાવાને `client` તરીકે સામાન્ય બનાવે છે, જેમાં સ્વયં-દાવો કરેલ `embedded` અથવા `audio-bridge` લેબલ્સનો સમાવેશ થાય છે. ફક્ત સર્વર-માલિક એડેપ્ટર જ આ વિશ્વસનીય લેબલ્સને કોડ-માત્ર `trustedSource` દલીલ દ્વારા સોંપી શકે છે; વિનંતી JSON ક્ષેત્ર તે દલીલ સુધી પહોંચી શકતું નથી. ટ્રાન્સ્ક્રિપ્ટ લખાણ અવિશ્વસનીય મીડિયા-ઉત્પાદિત સામગ્રી રહે છે, તેની પુરાવા પછી પણ, અને ક્યારેય અધિકૃતતા નક્કી કરવી જોઈએ.

એક અદ્યતન કોલર સમાન વિડિઓ માટે `audioTranscript` ટ્રેક પ્રદાન કરી શકે છે; તેને ક્લાયન્ટ-પ્રદાન કરેલ લખાણ તરીકે માનવામાં આવે છે, સર્વર ટ્રાન્સ્ક્રિપ્શનનો પુરાવો નથી. ફ્યુઝન સીમ એક જ ડેડલાઇન અનેabort સંકેત હેઠળ દૃશ્ય અને ઓડિયો અવલોકનો ચલાવે છે, તેમને સામાન્ય સમયરેખા પર ઓર્ડર કરે છે, ચોક્કસ ડુપ્લિકેટ્સને સમકક્ષ કરે છે, અને જ્યારે ફક્ત એક બાજુ સફળ થાય ત્યારે અંશિક પરિણામને રિપોર્ટ કરે છે. અમાન્ય `audioTranscript` તે અંશિક પરિણામમાં ઘટાડે છે - દૃશ્ય વર્ણન જાળવવામાં આવે છે અને ઓડિયો શાખા એક સ્વચ્છ નિષ્ફળતા કોડને નોંધે છે - સમગ્ર વિડિઓને નિષ્ફળ બનાવવાની બદલે. પ્રતિ-શાખા ઉપલબ્ધતા, અંશિક ધ્વજ, અને સ્વચ્છ નિષ્ફળતા કોડ વર્ણવેલ પરિણામમાં, ગાર્ડરેલ મેટાડેટા (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), પરિણામ-કેશ મેટાડેટા, અને બ્રિજ ફ્યુઝન કાઉન્ટર્સમાં જાળવવામાં આવે છે. ડિફોલ્ટ વિડિઓ બ્રિજ પાથ બોલી-થી-લેખનને પ્રેરિત નથી કરતી અથવા બીજું મીડિયા નકલ ડાઉનલોડ કરતી; તે સ્પષ્ટ ટ્રેક વિના, તે માત્ર વિડિઓ જ રહે છે.

**ટ્રાન્સ્ક્રિપ્ટ જાળવણી (#12150 P1).** જ્યારે વિડિઓ બ્રિજ (તે પોતે ઓપ્ટ-ઇન) ટ્રાન્સ્ક્રિપ્ટ ક્યૂને રજૂ કરે છે ત્યારે આ આપોઆપ લાગુ પડે છે - કોઈ અલગ જાળવણી ધ્વજ નથી. જ્યારે એક વિનંતી કોઈપણ ટ્રાન્સ્ક્રિપ્ટ ક્યૂ (એક કોલર-જાહેરાત `transcript` અથવા એક ફ્યુઝ્ડ `audioTranscript`)ને રજૂ કરે છે, ત્યારે ગાર્ડરેલ તેને `videoBridgeObserved` તરીકે માર્ક કરે છે અને વિડિઓ વર્ણનનો એક રેડેક્ટેડ શેડો ઉત્પન્ન કરે છે - એક સમાન રેન્ડરિંગ જેમાં દરેક ક્યૂના મફત-લેખન શરીરને `[redacted-video-transcript]` દ્વારા બદલવામાં આવે છે, જે રચનાત્મક ક્યૂ ક્ષેત્રને સ્ટ્રિંગ એકત્રિત કરવામાં પહેલાં બદલવા દ્વારા બનાવવામાં આવે છે (ક્યારેય સમકક્ષ લખાણને પાર્સ કરીને, તેથી કોઈ ક્યૂ સામગ્રી - વિરોધી અથવા સામાન્ય, જેમાં `]` ધરાવતી બોડીઓ જેમ કે `[inaudible]`/`[music]` - જીવંત રહી શકતી નથી). જાળવવામાં આવેલી કોલ-લોગ વિનંતી શરીર દરેક વિડિઓ-ઉત્પાદિત લખાણના ભાગને તે રેડેક્ટેડ શેડો માટે બદલાવે છે, સામગ્રી સમાનતાના આધારે; `fullText` એન્કર પૂર્ણ થયેલ પૂર્વ-કોલ ગાર્ડરેલ પેઇલોડમાંથી ફરીથી વાંચવામાં આવે છે, તેથી મેચ પછીના ચેઇન ગાર્ડરેલ્સ (PII અને ક્રેડેંશિયલ માસ્કર્સ, પ્રાથમિકતાઓ 10/95) વર્ણન લખાણને સ્થાનમાં ફરીથી લખે છે અને પછી સિસ્ટમ-પ્રોમ્પ્ટ/હેન્ડઓફ/મેમરી ઇન્જેક્શન સંદેશા એરેને પુનઃઆકાર આપે છે. મોડલને ઉપર મોકલવામાં આવેલ શરીર અપરિવર્તિત રહે છે. એક અવલોકિત વિનંતી પણ કોઈ ટકાઉ મેમરીને ભરતી નથી (વિનંતી અને પ્રતિસાદ-ઉત્પાદિત નિષ્કર્ષ બંને છોડી દેવામાં આવે છે), તેથી મોડલની પોતાની પ્રતિસાદ મેમરીમાં ટ્રાન્સ્ક્રિપ્ટ લખાણને પ્રતિબિંબિત કરી શકતી નથી.

**કાચા વિડિઓ ક્ષેત્રો (#12430).** જ્યારે બ્રિજ સક્રિય હોય છે અને સ્થાનિક વિડિઓ સપોર્ટ અજ્ઞાત અથવા ગેરહાજર હોય છે, ત્યારે વ્યાખ્યાયિત `transcript`/`audioTranscript` ક્ષેત્રો પણ `videoBridgeObserved`ને સક્રિય કરે છે, વર્ણન નિષ્ફળતા અથવા `maxVideos` મર્યાદા પછી પણ. `null` અને ખાલી સ્ટ્રિંગ્સ ગણવામાં આવે છે; ગેરહાજર ક્ષેત્રો અને નોન-વિડિઓ મેટાડેટા નથી. જાળવવામાં આવેલી નકલ આ ક્ષેત્રોને રેડેક્ટ કરે છે અથવા વિનંતી છોડી દે છે, અને કેશ/મેમરીને બાયપાસ કરવામાં આવે છે.

આ ફોલબેક પાથ પર, માન્ય કોલર ક્યૂઝ સમર્થિત `text`/`input_text` ભાગોમાં રૂપાંતરિત થાય છે, જે નોનસ્ટાન્ડર્ડ પ્રદાતા ક્ષેત્રો નથી. બંને વિનંતી-પ્રદાન કરેલ ટ્રેક્સ અવિશ્વસનીય `client` અવલોકનો તરીકે રહે છે, જેમાં સ્પષ્ટ ચેતવણી છે કે વિડિયો વર્ણવવામાં આવ્યો નથી અને સમયચિહ્નો મીડિયા સામે ચકાસવામાં આવ્યા નથી. અસ્તિત્વમાં રહેલા 256-ક્યૂ/64-KiB કુલ અને પ્રતિ-ક્યૂ બજેટ બંને ટ્રેક્સ પર લાગુ પડે છે; સમયચિહ્નો બ્રોકરનું 600-સેકન્ડનું છત અને કોઈપણ પ્રદાન કરેલ ફોકસ વિન્ડોમાં ફિટ થવા જોઈએ. અમાન્ય ટ્રેક્સને ફેંકી દેવામાં આવે છે, અનિયંત્રિત ટેક્સ્ટ તરીકે આગળ નહીં વધે; માન્ય ભાઈ હજુ પણ ઉપયોગમાં લેવામાં આવી શકે છે જો તેમની સંયુક્ત બજેટથી વધુ ન થાય. નલ/ખાલી ક્ષેત્રો કોઈ ટેક્સ્ટ ઉમેરતા નથી. આ ફોલબેક દ્વારા કોઈ મીડિયા ફેચ અથવા ટ્રાન્સક્રિપ્શન ઉમેરવામાં આવતું નથી. ટ્રાન્સક્રિપ્ટ વિસ્તરણ ક્ષેત્રો ફોલબેક વિડિયો કેરિયર અને તેના `video_url`/`source` ઑબ્જેક્ટમાંથી દૂર કરવામાં આવે છે. OpenAI વાયર અલોઇસ્ટ કડક રહે છે; અજાણ્યા-સ્થાનિક વિડિયો કેરિયર્સ ઉપલબ્ધ રહે છે અને જાણીતા ટેક્સ્ટ-માત્ર લક્ષ્યો સુરક્ષિત માર્કર્સ રાખે છે. બંધારણબદ્ધ રેડક્શન શેડોઝ જોડાયેલ ટ્રાન્સક્રિપ્ટ ટેક્સ્ટને સુરક્ષિત કરે છે, જ્યારે મૂળ કોલર-માલિક વિનંતી અપરિવર્તિત રહે છે. સ્થાનિક-સમર્થિત લક્ષ્યો અને નિષ્ક્રિય બ્રિજ તેમના અસ્તિત્વમાં રહેલા બાયપાસ વર્તનને જાળવે છે.

વધારાના રાખેલા નકલોએ સમાન અવલોકિત-વિનંતી સંકેતનો ઉપયોગ કર્યો છે. કાચા પ્રી-ગાર્ડરેલ ક્લાયન્ટ-વિનંતી સ્નેપશોટ, મેમરીમાં પેન્ડિંગ વિનંતી, અને વહેલી નકારી લેવામાં આવેલી વિનંતી લોગ બંધારણાત્મક રીતે વિડિયો ભાગોમાં ટ્રાન્સક્રિપ્ટ ક્ષેત્રોને બદલે છે; પાઇપલાઇન તબક્કાઓ અને સંદર્ભ હેન્ડઓફ દ્વારા સંશ્લેષિત સ્ટ્રિંગ પ્રોમ્પ્ટ્સને જાળવેલ-વિનંતી-શરીરમાં રેડેક્ટ કરવામાં આવે છે. જાળવેલ `video_content_removed` માર્કર `previous_response_id` ચાલુ રાખવામાં નિષ્ફળ થાય છે, ટેક્સ્ટને પુનઃનિર્માણ કરતા જે ઇરાદે ફેંકી દેવામાં આવ્યું હતું. જો અવલોકિત વિનંતી તેના પ્રતિ-ભાગ રેડક્શન શેડોને લોગિંગ પહેલાં ગુમાવે છે, અથવા પછીની વિનંતી પરિવર્તનો પછી ઘણા વિડિયો શેડોમાંથી એક પણ મેળ ખાતા નથી, તો જાળવેલ વિનંતી શરીર સંપૂર્ણપણે છોડી દેવામાં આવે છે, ભાગિક રીતે રેડક્ટેડ ટ્રાન્સક્રિપ્ટને જાળવવા બદલે.

અવલોકિત વિનંતી માટે, મોડેલ પ્રતિસાદ ટ્રાન્સક્રિપ્ટના કોઈપણ ભાગને બંધારણબદ્ધ ક્યૂ સીમાની વિના ઉલ્લેખ કરી શકે છે. તેથી, તેની જાળવેલ કોલ-લોગ `responseBody`ને એક છોડી દેવા માટેના માર્કર દ્વારા બદલી દેવામાં આવે છે; વિગતવાર પાઇપલાઇન આર્ટિફેક્ટ (જેમાં અપસ્ટ્રીમ/ક્લાયન્ટ શરીરો અને સ્ટ્રીમ ચંક્સનો સમાવેશ થઈ શકે છે) જાળવવામાં આવતું નથી. અર્થશાસ્ત્ર, આઇડેમ્પોટેન્સી, અને તર્ક-પુનરાવર્તન કેશો તે વિનંતી માટે વાંચન અને લખાણને બાયપાસ કરે છે. પ્રદાતા વિનંતી અને ક્લાયન્ટ-દૃશ્ય પ્રતિસાદ અપરિવર્તિત રહે છે. વિગતવાર આર્ટિફેક્ટ છોડી દેવામાં આવે ત્યારે વહેલી કીપલાઇવ બાઇટ્સ તાત્કાલિક બફરમાંથી કાઢી લેવામાં આવે છે. કિરોની ખોટી ઇવેન્ટસ્ટ્રીમ ચેતવણી Payload બાઇટ ગણતરીને જ અહેવાલ આપે છે, ક્યારેય તેની સામગ્રી અથવા JSON પાર્સરની કાચી ભૂલને નહીં.
આ દાવો નથી કે દરેક અસંબંધિત પ્રદાતા/પ્લગિન નિદાનની સમીક્ષા કરવામાં આવી છે; વ્યાપક જાળવેલ-સિંક સ્વીપ #11658 માં ટ્રેક કરવામાં આવે છે.

આંતરિક `/api/modality-bridge/video/drilldown` જીવનચક્ર એક અલગ, લૂપબેક/ટોકન-પ્રમાણિત કેશ આધારભૂત છે. દરેક ઓપરેશન માટે એક કૅનોનિકલ ઓપેક પ્રિન્સિપલ IDની જરૂર છે. ઉત્પાદન કોલર સક્રિય કરવામાં પહેલાં, તેને પ્રમાણિત ટેનન્ટમાંથી તે ID મેળવવું જોઈએ અને ક્યારેય ક્લાયન્ટ-ચૂંટેલ મૂલ્યને આગળ ન વધારવું જોઈએ. કેશ કી તે પ્રિન્સિપલને કૅનોનિકલ સત્ર અને વિડિયો-સંદર્ભ ID સાથે બાંધે છે, ફક્ત તેમના SHA-256-પ્રાપ્ત કી જ રાખે છે, અને વાંચન અને મિટાવાને સમાન પ્રિન્સિપલ માટે મર્યાદિત કરે છે. કેશમાં દરેક એન્ટ્રી માટે મહત્તમ 16 પ્રાપ્ત JPEG ફ્રેમ્સ હોય છે, તે દસ મિનિટ પછી સમાપ્ત થાય છે, અને મર્યાદિત `start`/`end` વાંચન અથવા સ્પષ્ટ સત્ર મિટાવાને સપોર્ટ કરે છે.

દરેક પ્રિન્સિપલ 16 એન્ટ્રીઓ અને 64 MiB કૅનોનિકલ JPEG ડેટા સુધી મર્યાદિત છે. આ મર્યાદાઓ વૈશ્વિક 64-એન્ટ્રી/256 MiB છતથી સ્વતંત્ર છે: પ્રિન્સિપલ કોટા દબાણ માત્ર તે પ્રિન્સિપલના સૌથી-તાજેતરના ઉપયોગમાં લેવાયેલા એન્ટ્રીઓને દૂર કરે છે, વૈશ્વિક LRU મિટાવા પર વિચાર કરવામાં આવે છે. સમાપ્ત થયેલ એન્ટ્રીઓ કેશ પ્રવૃત્તિ પર પ્રિન્સિપલ અને વૈશ્વિક હિસાબમાંથી દૂર કરવામાં આવે છે, જ્યારે રદ કરવું અને માન્યતા નિષ્ફળતા ભાગીય મર્યાદા બદલાવને પ્રતિબદ્ધ નથી.

કેશ નોન-કૅનોનિકલ બેસ64, વધુ પેડિંગ, નોન-JPEG મીડિયા, ખોટા અથવા કાપેલા JPEG, અને JPEGને નકારી દે છે જે મર્યાદિત સંપૂર્ણ-છબી `sharp` ડિકોડ દરમિયાન ચેતવણી આપે છે. તે દરેક સ્વીકૃત છબીને કૅનોનિકલ JPEG તરીકે પુનઃકોડ કરે છે, કોલર ક્ષેત્રો પર વિશ્વાસ કરવા બદલે ડિકોડ થયેલ બાઇટ્સમાંથી પહોળાઈ અને ઊંચાઈ પ્રાપ્ત કરે છે, અને કોઈપણ ટ્રેલિંગ પોલીગ્લોટ બાઇટ્સને જાળવવા બદલે ફેંકી દે છે. ફક્ત મર્યાદિત કૅનોનિકલ સંકોચિત બફર બંને કોટાઓને ચાર્જ કરવામાં આવે છે. JSON વાયર મર્યાદા 32 MiB ડિકોડ-ઇનપુટ છત માટે બેસ64 ઓવરહેડને સમાવેશ કરે છે. દરેક જાળવેલ વ્યાખ્યાને તેની માન્ય JPEG ફોર્મેટ/રિઝોલ્યુશન, નમૂના નીતિ, વ્યાખ્યાના સંસ્કરણ, સર્જન સમય, સર્વર-ગણિત સામગ્રી હેશ, અને હેશ કરેલ પેરન્ટ સંદર્ભ સાથે જાળવવામાં આવે છે, ઉપરાંત વિશ્વસનીય કોલરનું પેરન્ટ-સામગ્રી હેશ. રદ કરવું અસંબંધિત ડિકોડ/હેશ તબક્કાઓ વચ્ચે ચકાસવામાં આવે છે પહેલાં આટોમિક કેશ કમિટ.

ઉત્પાદન ઉત્પાદક સફળ દૃશ્ય વિશ્લેષણ પછી જ પહેલાથી જ પ્રાપ્ત બ્રોકર ફ્રેમ્સનો પુનઃઉપયોગ કરે છે, બીજું વિડિયો ડાઉનલોડ/નિકાલ વગર. તે ઓપરેટર `modalityBridgeVideoDrilldownEnabled=true`, કડક પ્રતિ-ભાગ `drilldown: true`, અને એક પ્રમાણિત API-કી રેકોર્ડ IDની જરૂર છે. ક્લાયન્ટ-જાહેરાત કરેલ પ્રિન્સિપલ/સત્ર મૂલ્યો ક્યારેય માલિકી સ્થાપિત નથી. આ ત્રણ શરતો વિના તે હેશ, પુનઃમાપે અથવા વધારાના ફ્રેમ્સને જાળવે નહીં. જાળવણી નિષ્ફળતા ઉપયોગી દૃશ્ય પ્રતિસાદને જાળવે છે. સંમતિ પ્રાપ્ત વિનંતીઓ સમગ્ર-વિડિયો પરિણામ કેશને બાયપાસ કરે છે જેથી કેશ કરેલ પરિણામો ક્યારેય હેન્ડલને પુનરાવર્તિત ન કરે.

સફળ JSON અને SSE પ્રતિસાદો બાઉન્ડેડ `x-omniroute-video-drilldown` હેડરમાં વધુમાં વધુ ચાર ઓપેક હેન્ડલ્સને પ્રદર્શિત કરે છે. અધિકૃત બ્રાઉઝર ઓરિજન્સ તે હેડરને વાંચી શકે છે બિન-વિસ્તૃત CORS ઓરિજિન નીતિ વિના. નવા હેન્ડલ્સ `v1.<32-byte random base64url token>` નો ઉપયોગ કરે છે, અને રજિસ્ટ્રી માત્ર તેમના SHA-256 હેશને જ રાખે છે. રીડર/હેડર પાર્સર જૂના 64-હેક્સ ટોકનને પણ સ્વીકારે છે. માન્યતાપત્રિત જાહેર ગ્રાહક છે `GET /api/v1/video-bridge/drilldown?handle=...`, જે સ્વતંત્ર રીતે `modalityBridgeVideoDrilldownRemoteEnabled=true` દ્વારા ગેટેડ છે. સ્પષ્ટ રીતે જાળવવામાં આવેલ ખોટું પ્રવેશને રદ કરે છે જ્યારે જૂની `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` env ફોલબેક સક્રિય હોય છે. ઉત્પાદન જાળવણીમાં સમાન જૂની `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED` ફોલબેક છે. બંને ફોલબેક ડિફોલ્ટ રીતે બંધ છે.

ગ્રાહક માન્યતાપત્રિત કીમાંથી માલિકી મેળવશે, કી નીતિ લાગુ કરશે, અને અજાણ્યા, સમાપ્ત અને અન્ય કી ના હેન્ડલ્સ માટે સમાન 404 પાછું આપે છે. તે `variant=preview|standard|detail` (અધિકતમ JPEG પરિમાણ 320/640/1280, ક્યારેય અપસ્કેલ નહીં), `limit=1..8` (અથવા જૂના `frames` ઉપનામ, ક્યારેય બંને નહીં), શૂન્ય આધારિત `page`, અને વૈકલ્પિક `start`/`end` ફોકસ સેકન્ડ્સને સ્વીકારે છે. પુનરાવૃત્ત પ્રશ્ન કી અને વિરુદ્ધ ફોકસ વિન્ડોઝને નકારી દેવામાં આવે છે. દરેક પાછા મળેલ વૈવિધ્યમાં તેના વાસ્તવિક સામગ્રી અને વાસ્તવિક ઉંચાઈ મેટાડેટાનો હેશ હોય છે, જે જાળવવામાં આવેલા સ્ત્રોત સાથે જોડાયેલ છે. વૈવિધ્ય વાંચન પર આધારિત છે, વધારાના જાળવેલા નકલ તરીકે સંગ્રહિત નથી. JSON પ્રતિસાદ, જેમાં Base64/envelope શામેલ છે, 32 MiB પર મર્યાદિત છે; એક વિશાળ પાનું 413 પાછું આપે છે અને ક્લાયન્ટે ઓછા ફ્રેમ્સની વિનંતી કરવી જોઈએ. વાંચન દરેક પુનઃમાપની આસપાસ રદ કરવાનું ચકાસે છે અને પાછા ફરતા પહેલા હેન્ડલની માન્યતા ફરીથી ચકાસે છે. માલિક દ્વારા `DELETE` આઈડેમ્પોટેન્ટ છે; ડિલીટ અથવા TTL સમાપ્ત થવાથી જાળવવામાં આવેલા સ્ત્રોત અને ઉપયોગની ગણતરી મુક્ત થાય છે.

શેર કરેલ સ્ટોર પ્રક્રિયા-સ્થાનિક છે: હેન્ડલ્સ પુનઃપ્રારંભ પર સમાપ્ત થાય છે અને સ્વતંત્ર OmniRoute પ્રક્રિયાઓ વચ્ચે પરિવહન કરી શકાતી નથી. વ્યવસ્થાપન આંકડાઓ અસરકારક જાળવણી/દૂરની નીતિ અને માત્ર જાળવેલ પ્રવેશો/બાઇટ્સને પ્રદર્શિત કરે છે, ક્યારેય મીડિયા, સંદર્ભો, મુખ્ય ID અથવા હેન્ડલ્સને નહીં. વિડિઓ સેટિંગ્સ પેનલ તે મૂલ્યોને દર્શાવે છે અને બંને સંમતિ સ્વિચને જાળવી શકે છે. આ અમલ દસ્તાવેજીકરણ જીવંત ડિપ્લોયમેન્ટ અથવા પ્રમોશન પુરાવા નથી; વાસ્તવિક-મોડલ સ્વીકૃતિ અલગથી ટ્રેક કરવામાં આવે છે.

ફ્રેમ્સને રૂપરેખાંકિત વિડિઓ મોડ સાથે અનુક્રમણિકા સાથે કૅપ્શન કરવામાં આવે છે. ખાલી વિડિઓ ઓવરરાઇડ વિઝન સેટિંગને વારસામાં લે છે; જો બંને ખાલી હોય, તો વિઝન ઓટો-રૂટર અસરકારક વિઝન-ક્ષમ મોડને પસંદ કરે છે. સફળ કૅપ્શન મૂળ ભાગને સ્થિર `[Video description:` પૂર્વફિકાર સાથે બદલે છે જે ટેક્સ્ટને અવિશ્વસનીય મીડિયા-ઉત્પન્ન અવલોકન તરીકે પણ ચિહ્નિત કરે છે અને નીચેના મોડલને મીડિયા માં મળેલા સૂચનોને અનુસરણ ન કરવા માટે કહે છે. ફ્રેમ-કૅપ્શન કેશ કી JPEG બાઇટ્સ, પ્રોમ્પ્ટ, ટાઈમસ્ટેમ્પ, અને અસરકારક મોડને શામેલ કરે છે; ફક્ત સફળ કૅપ્શન જ કેશ કરવામાં આવે છે. કેશ પ્રવેશો વાસ્તવિક સફળ ઉત્પાદક મોડને જાળવે છે, જેમાં એક ફોલબેક મોડ શામેલ છે; બ્રિજ `mixed` રિપોર્ટ કરે છે જ્યારે વિવિધ ફ્રેમ્સને વિવિધ મોડલ દ્વારા ઉત્પન્ન કરવામાં આવ્યા હતા. કેશ હિટ તે ઉત્પાદક ઓળખને પુનઃઉપયોગ કરે છે તેના બદલે તેને વિનંતી કરેલ રૂટિંગ યોજના તરીકે પુનઃલેબલ કરે છે. સમગ્ર-વિડિઓ પરિણામ કેશ દરેક ઇનપુટ પર કીબદ્ધ છે જે આઉટપુટને બદલે છે — પ્રોમ્પ્ટ, અસરકારક મોડ, નમૂનાકાર નીતિ, ફ્રેમ ગણતરી, અર્થશાસ્ત્ર વિશ્લેષણ મોડ, નોર્મલાઇઝ્ડ ફોકસ હિન્ટનો SHA-256 ફિંગરપ્રિન્ટ, ફોકસ વિન્ડો, `transcript`, `audioTranscript`, અને સંપર્ક-શીટ ધ્વજ — તેથી આમાંથી કોઈપણ પરિમાણ બદલવાથી કેશ મિસ થાય છે, ક્યારેય જૂના પુનઃઉપયોગ નહીં. દૃશ્ય ડેડુપ નીતિ સંસ્કરણ, થ્રેશોલ્ડ, અને મર્યાદિત ઉમેદવાર-ફ્રેમ ગણતરી પણ પરિણામ-કેશ કી અને મેટાડેટામાં સ્પષ્ટ છે; તેથી, નીતિમાં ફેરફાર જૂના સમગ્ર-વિડિઓ વર્ણનને પુનઃઉપયોગ કરી શકતું નથી. પરિણામ-કેશ v4 મેટાડેટા મોડ અને ફિંગરપ્રિન્ટને જાળવે છે, ક્યારેય કાચા વપરાશકર્તા કાર્યને નહીં. ગાર્ડરેલ મેટાડેટા વિનંતી કરેલ અને અસરકારક વિશ્લેષણ મોડ બંનેને રિપોર્ટ કરે છે; ઉપયોગી વપરાશકર્તા ટેક્સ્ટ વિના વિનંતી કરેલ `focused` મોડને અસરકારક રીતે `full` તરીકે રિપોર્ટ કરવામાં આવે છે.

ગાર્ડરેલ દરેક સમર્થિત વિડિઓ ભાગને કાઢી લે છે પરંતુ `modalityBridgeVideoMaxVideos` કરતાં વધુ વર્ણવતું નથી. એક લક્ષ્ય જે સાબિત કરવા માટે `supportsVideo === false` છે, નિષ્ફળ અને ઓવર-લિમિટ વિડિઓઓ સ્પષ્ટ સુરક્ષિત ટેક્સ્ટ માર્કરોમાં ફેરવાય છે જેથી કોઈ કાચા વિડિઓ જીવંત ન રહે. જ્યારે ક્ષમતા અજાણ હોય, ત્યારે તે ભાગો તેમના વિડિઓ કેરિયર જાળવે છે; કોઈપણ ફોલબેક ટ્રાન્સ્ક્રિપ્ટ ઉપરના મર્યાદિત ટેક્સ્ટ રૂપાંતરણને અનુસરે છે. લક્ષ્યો સાથે `supportsVideo === true` બ્રિજને બાયપાસ કરે છે. ક્લાયન્ટ વિનંતી રદ સંકેત ડાઉનલોડ, બ્રોકર ક્યૂ, ઉપપ્રક્રિયાઓ, અને કૅપ્શન કોલ્સમાં પ્રસારિત થાય છે; રદ કરવું વિડિઓઓ વચ્ચે રોકે છે અને ક્યારેય કાચા મીડિયા માટે ખોટું નથી.

રનટાઇમ સેટિંગ્સ DB-બેકડ અને Zod-માન્યતાપત્રિત છે:

| કી                                  | ડિફોલ્ટ     | શ્રેણી / વર્તન                                                                                         |
| ----------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------ |
| `modalityBridgeVideoEnabled`        | `false`     | વૈકલ્પિક રનટાઇમ, ઓપ્ટ-ઇન                                                                               |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` સામાન્ય કૅપ્શન જાળવે છે; `focused` મર્યાદિત, અવિશ્વસનીય છેલ્લી વપરાશકર્તા સંદર્ભનો ઉપયોગ કરે છે |
| `modalityBridgeVideoModel`          | `""`        | વિઝન બ્રિજ મોડને વારસામાં લેવું                                                                        |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                   |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, અથવા પ્રમાણભૂત `segment_aware`; ડિટેક્ટર નિષ્ફળતા `uniform` પર પાછું આવે છે  |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                    |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                         |

Legacy persisted Video timeout values above 120 seconds are clamped to the
broker deadline; new settings writes above that limit are rejected.
`GET /api/modality-bridge/video/runtime` requires trusted stamped loopback
locality before authentication or runtime probing, then requires management
auth. It returns only `available`, sanitized FFmpeg/ffprobe versions, and a fixed
reason when the runtime is unavailable. The internal extraction endpoint is not
a public upload API: queue saturation returns `503` plus `Retry-After`, a caller
disconnect returns `499`, and the fixed broker deadline returns `504`. Converted responses add
`video->text;model=<visionModel>;parts=<videos>` to the central
`x-omniroute-modality-bridge` header without removing Vision or Audio segments.

### PII Masker (`piiMasker.ts`)

**બન્ને** તબક્કાઓ પર ચાલે છે.

- **`preCall`** પેલોડને ક્લોન કરે છે, `system`, `messages`, `input`, અને
  `prompt` (સામાન્ય સ્ટ્રિંગ આઇટમ્સ સહિત) પર ચાલે છે, અને `processPII()` (from
  `@/shared/utils/inputSanitizer`) ને સ્ટ્રિંગ `content`/`text` ફીલ્ડ્સ પર લાગુ કરે છે. જ્યારે
  `PII_REDACTION_ENABLED=true` હોય છે, ત્યારે શોધવામાં આવેલ PII આઉટબાઉન્ડ
  પેલોડમાં છુપાવવામાં આવે છે. આ `INPUT_SANITIZER_MODE` થી સ્વતંત્ર છે (જે ફક્ત
  પ્રોમ્પ્ટ-ઇન્જેક્શન નીતિને નિયંત્રિત કરે છે). જ્યારે છુપાવવું બંધ હોય છે, ત્યારે કોલ રેકોર્ડ્સ શોધ
  ગણનાઓને સામગ્રીને ફરી લખ્યા વિના.
- **`postCall`** પ્રતિસાદને ડીપ-ક્લોન કરે છે, `sanitizePIIResponse()` અને
  Responses-API-આકાર માસ્કર (`maskResponsesOutput` — `output_text` અને `output[].content[].text`ને આવરી લે છે) ચલાવે છે. જો કોઈ છુપાવણું થાય છે, તો
  ફેરફાર કરેલ પ્રતિસાદ મૂળને બદલે છે.

ગાર્ડરેલ ક્યારેય બ્લોક નથી થતો; તે ફક્ત નોંધ કરે છે (`meta.detections`,
`meta.redacted`) અથવા ફરી લખે છે.

### Prompt Injection (`promptInjection.ts`)

વપરાશકર્તા દ્વારા પૂરા પાડવામાં આવેલા સામગ્રીમાં વિરોધી માળખાઓને શોધે છે અને
નિયંત્રિત નીતિને અમલમાં લાવે છે. વર્તન પર્યાવરણના ચલ અને કન્સ્ટ્રક્ટર
વિકલ્પો દ્વારા ચલાવવામાં આવે છે:

| સેટિંગ          | Env var                                                                                               | ડિફોલ્ટ | અસર                                                                                                                                                                                                |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| સક્રિય          | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | જ્યારે `false` હોય છે, ત્યારે ગાર્ડરેલ શોર્ટ-સર્કિટ કરે છે.                                                                                                                                        |
| મોડ             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | ઇન્જેક્શન નીતિ: `block`, `warn`, અથવા `log`. (`redact` પાછા-સંસાધન માટે સ્વીકાર્ય છે પરંતુ ઇન્જેક્શન ટેક્સ્ટને **કાપતું નથી**; PII ફરી લખવાની વિનંતી `PII_REDACTION_ENABLED` દ્વારા નિયંત્રિત છે.) |
| બ્લોક થ્રેશોલ્ડ | `blockThreshold` વિકલ્પ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ઉપનામ `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | બ્લોક કરવા માટેની જરૂરી ન્યૂનતમ ગંભીરતા. મધ્યમ ડિફોલ્ટ પરobserve-માત્ર છે.                                                                                                                         |

**મોડ પ્રાધિકરણ** (`getMode`): caller `options.mode` →
`INJECTION_GUARD_MODE` **DB ફીચર-ફ્લેગ ઓવરરાઇડ** (ડેશબોર્ડ → સેટિંગ્સ →
ફીચર ફ્લેગ્સ) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. ડેશબોર્ડ ઓવરરાઇડ તેથી પર્યાવરણના ચલોથી વધુ જીતે છે, તેથી ફીચર
ફ્લેગ્સ UI જીવંત ગાર્ડને ચલાવે છે (કોઈ પુનઃપ્રારંભ નથી). DB વાંચન ફેઇલ-સેફ છે:
જો તે ભૂલ કરે છે, તો ગાર્ડ પર્યાવરણ આધારિત વર્તન પર પાછું જાય છે, અને જ્યારે કોઈ
ઓવરરાઇડ સેટ નથી ત્યારે વર્તન પર્યાવરણ-માત્ર ઉકેલ સાથે સમાન છે.

   `markdown_system_block`, બન્ને `high` ગંભીરતા).
3. વૈકલ્પિક `customPatterns` કન્સ્ટ્રક્ટર વિકલ્પો દ્વારા પસાર થાય છે (સ્ટ્રિંગ્સ, regex,
   અથવા `{ name, pattern, severity }` રેકોર્ડ).

જ્યારે `mode === "block"` **અને** ઓછામાં ઓછા એક શોધ ગંભીરતા
થ્રેશોલ્ડને પૂર્ણ કરે છે, `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` પાછું આપે છે. `warn`/`log` મોડમાં ગાર્ડરેલ લોગ કરે છે પરંતુ
કોલને મંજૂરી આપે છે. શેર કરેલ હેલ્પર `evaluatePromptInjection()` પણ નિકાસ કરવામાં આવે છે
તેથી કોલર્સને રજિસ્ટ્રીમાં જવા વિના પ્રોમ્પ્ટને મૂલ્યાંકન કરવાની જરૂર છે.

**સ્કેન બાઉન્ડ (v3.8.20):** ડિટેક્ટર ફક્ત **પ્રથમ 16 KB** ના
જોડાયેલા પ્રોમ્પ્ટ ટેક્સ્ટને તપાસે છે — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 બાઇટ) માં
`src/shared/utils/inputSanitizer.ts`. બંને `detectInjection()` અને
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` પેટર્ન લૂપ ચલાવવા પહેલાં કરે છે. ઇન્જેક્શન નિર્દેશો ઇનપુટના ટોચના નજીક બેસે છે, તેથી આ
મલ્ટી-સેંકેડ KB પેલોડ્સ પર regex CPU/GCને કાપે છે વિના શોધને નબળું બનાવે છે (cf.
#3932, #4041).

### Credential Masker (`credentialMasker.ts`)

**બન્ને** તબક્કાઓ પર ચાલે છે, ડિફોલ્ટ ચેઇનમાં છેલ્લું (પ્રાથમિકતા `95`). આઉટબાઉન્ડ પેલોડ (સંદેશા
સામગ્રી, ટૂલ-કોલ દલીલો, ટૂલ પરિણામો) **અને** પ્રદાતા પ્રતિસાદમાંથી જાણીતા API-કી / સિક્રેટ-ટોકન પેટર્નને છુપાવે છે, જેથી પ્રોમ્પ્ટમાં પેસ્ટ કરેલ ક્રેડેન્શિયલ (અથવા ટૂલ પરિણામ દ્વારા પાછું પ્રતિબિંબિત) ઉપરના પ્રદાતા અથવા ક્લાયન્ટને લીક ન થાય.

- **ઓપ્ટ-ઇન માત્ર**, PII રેડક્શન જેવી જ પરંપરા (હાર્ડ નિયમ #20-સંબંધિત):
  `settings.credentialRedactionEnabled === true` **અથવા**
  `CREDENTIAL_REDACTION_ENABLED=true` ના સિવાય નિષ્ક્રિય. જ્યારે તે બંધ હોય છે, ત્યારે ગાર્ડરેલ એક નોન-ઓપ છે —
  તે ક્યારેય બ્લોક નથી કરતી અને ક્યારેય પુનઃલેખિત નથી કરતી.
- `redactCredentials()` સંપૂર્ણ પેલોડ/પ્રતિસાદ વૃક્ષને ચાલે છે (`walkValue()`,
  પ્રોટોટાઇપ-પોલ્યુશન-સુરક્ષિત, ચક્ર-સુરક્ષિત `WeakSet` દ્વારા) અને મેળ ખાતા ભાગોને
  `[REDACTED:<type>]` પ્લેસહોલ્ડર સાથે બદલતી છે, ફક્ત તે શાખાઓને ક્લોન કરતી છે જે વાસ્તવમાં
  બદલાઈ ગઈ છે.
- `CREDENTIAL_PATTERNS` LLM પ્રદાતા કી (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ટોકન (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), ચુકવણી કી (Stripe, Square), ક્લાઉડ
  કી (AWS એક્સેસ કી, Twilio, SendGrid, Mailgun), ખાનગી કી / JWTs,
  ક્રેડેન્શિયલ-ધારક કનેક્શન સ્ટ્રિંગ્સ (`mongodb://user:pass@...`, વગેરે), અને
  એક સામાન્ય `Authorization`/`x-api-key`/`api-key`/`apikey` હેડર-મૂલ્ય
  પેટર્નને આવરી લે છે. હેડર-આકારની કી (`authorization`, `x-api-key`, `api-key`,
  `apikey`) ઢાંચાકીય રીતે રેડેક્ટ કરવામાં આવે છે (મૂલ્ય જ, યોજના પૂર્વફિક્રા જેમ કે
  `Bearer `/`Basic ` જાળવવામાં આવે છે) સામાન્ય ટેક્સ્ટ regex દ્વારા નહીં.
- ગાર્ડરેલ ક્યારેય બ્લોક નથી કરતી; તે ફક્ત પુનઃલેખિત કરે છે (`modifiedPayload` /
  `modifiedResponse`) અને નોંધ કરે છે (`meta.credentialsRedacted`, `meta.count`).

પુનરાવર્તન ગાર્ડ: `tests/unit/credential-masker-guardrail.test.ts`.

## મૂળભૂત કરાર (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ચેઇનને તરત જ અટકાવે છે
  message?: string; // અવરોધિત કરતી વખતે દર્શાવવામાં આવે છે
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // વિનંતીને ફરી લખવા માટે preCall દ્વારા પરત કરવામાં આવે છે
  modifiedResponse?: TValue; // પ્રતિસાદને ફરી લખવા માટે postCall દ્વારા પરત કરવામાં આવે છે
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ગાર્ડરેલ `void`, `{}`, અથવા `{ block: false }` પરત કરીને "કોઈ ફેરફાર નહીં"નો સંકેત આપે છે. `modifiedPayload`/`modifiedResponse` પરત કરવાથી ચેઇનમાં આગળના ગાર્ડરેલ્સ તરફ વહેતું મૂલ્ય બદલાઈ જાય છે.
`signal?: AbortSignal` કૉલરની લાઇફસાઇકલને ગાર્ડરેલ્સ સુધી લઈ જાય છે. વિનંતી રદ થવી એ ઇરાદાપૂર્વકનો fail-open અપવાદ છે: મીડિયા બ્રિજ કામ અટકાવે છે અને જે લક્ષ્ય તેને સપોર્ટ કરતું નથી તે જાણીતું હોવા છતાં તેમાં મૂળ મીડિયા પુનઃસ્થાપિત કર્યા વિના ક્લીનઅપ કરે છે.

## રજિસ્ટ્રી (`registry.ts`)

સિંગલટન `guardrailRegistry` નીચેની સુવિધાઓ પ્રદાન કરે છે:

- `register(guardrail)` — ગાર્ડરેલ ઉમેરે છે (અથવા સામાન્યકૃત નામ દ્વારા બદલે છે) અને
  ચઢતા `priority` મુજબ ફરીથી ગોઠવે છે.
- `clear()` / `list()` — વહીવટી સહાયકો.
- `runPreCallHooks(payload, context)` — સક્રિય ગાર્ડરેલ્સ પર ક્રમશઃ ફરે છે, પેલોડને
  `modifiedPayload` મારફતે આગળ ધપાવે છે અને પ્રથમ `block: true` પર અટકે છે.
- `runPostCallHooks(response, context)` — પ્રતિસાદની બાજુએ સમાન પ્રવાહ.
- `resetGuardrailsForTests({ registerDefaults })` — સ્વચ્છ ટેસ્ટ અલગીકરણ માટે સ્ટેટ સાફ કરે છે અને વૈકલ્પિક રીતે
  ડિફૉલ્ટ્સને ફરીથી રજિસ્ટર કરે છે.

બંને રનર્સ `{ blocked, payload|response, results, guardrail?, message? }`
પરત કરે છે, જ્યાં `results` એ `GuardrailExecutionResult` રેકોર્ડ્સની એરે છે, જેમાં
દરેક ગાર્ડરેલ માટેના `blocked`, `skipped`, `modified`, `error`, અને `meta` ફીલ્ડ્સ
સમાવિષ્ટ હોય છે, જે ટ્રેસિંગ માટે ઉપયોગી છે.

### દરેક વિનંતી માટે ગાર્ડરેલ્સ અક્ષમ કરવા

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` વર્તમાન
વિનંતી માટે છોડવામાં આવનાર ગાર્ડરેલ નામોની ડુપ્લિકેટ-રહિત યાદી એકત્રિત કરે છે.
સ્ત્રોતો (બધા વૈકલ્પિક, બધા મર્જ કરવામાં આવે છે):

- `apiKeyInfo.disabledGuardrails`
- વિનંતી બોડીનું `disabledGuardrails` (ટોચના સ્તરે)
- વિનંતી બોડીનું `metadata.disabledGuardrails`
- હેડર `x-omniroute-disabled-guardrails` (અથવા જૂનું
  `x-disabled-guardrails`)

મૂલ્યો સ્ટ્રિંગ્સની એરે અથવા કૉમાથી અલગ કરેલી સ્ટ્રિંગ હોઈ શકે છે; નામોને
લોઅરકેસ kebab-caseમાં સામાન્યકૃત કરવામાં આવે છે (`pii_masker` → `pii-masker`). પરિણામ
`context.disabledGuardrails` મારફતે રજિસ્ટ્રીને આપવામાં આવે છે, જે
મેળ ખાતા ગાર્ડરેલ્સને છોડી દે છે (`results`માં `skipped: true`).

## અમલીકરણ ક્રમ

`src/sse/handlers/chat.ts` અને
`open-sse/handlers/chatCore.ts`માંથી પસાર થતી દરેક વિનંતી માટે:

1. `resolveDisabledGuardrails(...)` API કી, બોડી અને હેડર્સમાંથી સ્કિપ સૂચિ બનાવે છે.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ચડતા પ્રાથમિકતા ક્રમમાં ગાર્ડરેલ્સ ચલાવે છે:
   - અક્ષમ કરેલા ગાર્ડરેલ્સ `skipped` તરીકે નોંધાય છે.
   - દરેક ગાર્ડરેલનું `preCall`, `modifiedPayload` મારફતે પેલોડને ફરી લખી શકે છે.
   - પ્રથમ `block: true` ચેઇનને શોર્ટ-સર્કિટ કરે છે અને હેન્ડલર
     ગાર્ડરેલ અસ્વીકાર પ્રતિસાદ પરત કરે છે.
3. (સંભવિત રીતે ફરી લખાયેલો) પેલોડ કોમ્બો રાઉટિંગ અને અપસ્ટ્રીમ
   ડિસ્પેચમાં જાય છે.
4. પ્રતિસાદ તૈયાર થયા પછી, `guardrailRegistry.runPostCallHooks(...)`
   પ્રતિસાદ પર એ જ ચેઇન ચલાવે છે. અહીં `block: true` અપસ્ટ્રીમ
   પ્રતિસાદને કાઢી નાખે છે.

જે ગાર્ડરેલ્સ અપવાદ ફેંકે છે તે `error: <message>` સાથે નોંધાય છે અને
`logger.warn` મારફતે લૉગ થાય છે, પરંતુ ચેઇન ચાલુ રહે છે — ડિઝાઇન મુજબ ફેઇલ-ઓપન.

## રૂપરેખાંકન

બિલ્ટ-ઇન ગાર્ડરેલ્સ દ્વારા વાંચવામાં આવતા એન્વાયર્નમેન્ટ વેરિએબલ્સ:

| વેરિએબલ                               | આના દ્વારા વપરાય છે        | અસર                                                                                                             |
| ------------------------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | શોધને સંપૂર્ણપણે અક્ષમ કરવા માટે `false` સેટ કરો.                                                               |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | ઇન્જેક્શન નીતિ: `warn`, `block`, અથવા `log`. લેગસી મૂલ્ય `redact` ઇન્જેક્શન ટેક્સ્ટને ફરીથી લખતું નથી.          |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | ઇન્જેક્શન ગાર્ડ માટેનો મોડ; આ DB ફીચર ફ્લેગ પણ છે, જે એન્વાયર્નમેન્ટ વેરિએબલ્સને **ઓવરરાઇડ** કરે છે (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | `MODE=block` દ્વારા અસ્વીકાર થવા માટેની ન્યૂનતમ ગંભીરતા: `high` (ડિફૉલ્ટ), `medium`, અથવા `low`.                |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD` માટેનો લેગસી ઉપનામ.                                                           |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | જ્યારે `true` હોય, ત્યારે વિનંતીમાં રહેલી PII રિડેક્ટ થાય છે (ઇન્જેક્શન મોડથી સ્વતંત્ર).                        |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ડાઉનસ્ટ્રીમ) | પ્રતિસાદ-બાજુના માસ્કરની વર્તણૂકને નિયંત્રિત કરે છે.                                                            |

Modality Bridge ગાર્ડરેલ્સ એન્વાયર્નમેન્ટ વેરિએબલ્સને બદલે DB-આધારિત સેટિંગ્સ
સ્ટોર (`getSettings()`)માંથી રનટાઇમ રૂપરેખાંકન વાંચે છે. Visionની પ્રાથમિક કીઓ
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, અને
`modalityBridgeCacheMaxEntries` છે. લેગસી
`visionBridge*` કીઓ ફક્ત દસ્તાવેજીકૃત એક-ચક્ર રીડ
ફૉલબૅક તરીકે સ્વીકારવામાં આવે છે; ડૅશબોર્ડ રાઇટ્સ પ્રાથમિક કીઓનો ઉપયોગ કરે છે. ડિફૉલ્ટ્સ અને ફૉલબૅક
રિઝૉલ્વર `src/shared/constants/modalityBridgeDefaults.ts`માં છે, જ્યારે લેગસી
કોન્સ્ટન્ટ્સ `src/shared/constants/visionBridgeDefaults.ts`માં જાળવી રાખવામાં આવ્યા છે.

Audio, `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout`, અને `modalityBridgeAudioMaxClips`, તેમજ શેર કરેલ
`modalityBridgeCache*` સેટિંગ્સનો ઉપયોગ કરે છે. Audio માટે કોઈ લેગસી-કી ફૉલબૅક નથી, કારણ કે આ
કીઓ Modality Bridge સ્કીમા સાથે રજૂ કરવામાં આવી હતી.

Video, `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos`, અને
`modalityBridgeVideoTimeout`, તેમજ શેર કરેલ `modalityBridgeCache*` સેટિંગ્સનો ઉપયોગ કરે છે.
તે ડિફૉલ્ટ રૂપે અક્ષમ છે કારણ કે FFmpeg/ffprobe વૈકલ્પિક ઓપરેશનલ
ડિપેન્ડન્સીઝ છે અને ફ્રેમ કૅપ્શનિંગ લેટન્સી અને મોડેલ ખર્ચ વધારે છે.

## કસ્ટમ ગાર્ડરેલ્સ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

પગલાં:

1. `BaseGuardrail`ને વિસ્તૃત કરતી `src/lib/guardrails/myGuardrail.ts` બનાવો.
2. `preCall` અને/અથવા `postCall` અમલમાં મૂકો.
3. કાં તો ઇમ્પોર્ટ સમયે નોંધણી કરો (`registerDefaultGuardrails`માંથી પુશ કરો) અથવા
   રનટાઇમ પર `guardrailRegistry.register(...)` કૉલ કરો — રજિસ્ટ્રી સમાન સામાન્યકૃત
   નામ ધરાવતા કોઈપણ અગાઉના ગાર્ડરેલને બદલી નાખે છે.
4. `tests/unit/` હેઠળ પરીક્ષણો ઉમેરો (હાલનાં ઉદાહરણો:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## પરીક્ષણ

જાણીતી સ્થિતિથી શરૂઆત કરવા માટે પરીક્ષણો વચ્ચે `resetGuardrailsForTests()`નો ઉપયોગ કરો.
ખાલી રજિસ્ટ્રીથી શરૂઆત કરવા માટે `{ registerDefaults: false }` પાસ કરો અને
માત્ર પરીક્ષણ હેઠળના ગાર્ડરેલ્સની નોંધણી કરો. Vision Bridge ડિપેન્ડન્સી
ઇન્જેક્શન (`deps.getSettings`, `deps.callVisionModel`) સ્વીકારે છે; Audio Bridge
સેટિંગ્સ, ક્ષમતાઓ, STT મોડેલ પસંદગી, ક્રેડેન્શિયલ તપાસો અને ટ્રાન્સક્રિપ્શન માટે
સમકક્ષ સીમ્સ ઉપલબ્ધ કરાવે છે. તેથી પરીક્ષણો DB અથવા નેટવર્ક ઍક્સેસ વિના બંને
પ્રવાહોને ચકાસી શકે છે.

## ઇન્જેક્શન-ગાર્ડ રૂટ કવરેજ અને રેડ-ટીમ (તબક્કો 8 · બ્લૉક D)

ઇન્જેક્શન-ગાર્ડ (`createInjectionGuard` / `withInjectionGuard`) વપરાશકર્તા પ્રોમ્પ્ટ્સ
સ્વીકારતા તમામ રૂટ્સને આવરી લે છે. તે `INJECTION_GUARD_MODE`નું પાલન કરે છે (ડિફૉલ્ટ
`warn` = ફક્ત લૉગ; `block` = HTTP 400 `SECURITY_001` પરત કરે છે).

| પ્રકાર           | રૂટ્સ                                                                                                                                                | ડિફૉલ્ટ મોડ |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| ટેક્સ્ટ (હાલનું) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| જનરેટિવ          | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| ડેટા             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

ટેક્સ્ટ નિષ્કર્ષણ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`ને આવરી લે છે.

**રેડ-ટીમ (દરરોજ રાત્રે, `nightly-llm-security.yml`):** promptfoo ચકાસે છે કે દરેક રૂટ
`INJECTION_GUARD_MODE=block`માં OWASP-LLM કોર્પસને બ્લૉક કરે છે; garak પ્રોબ્સ ચલાવે છે
(સિક્રેટ વિના સ્કિપ કરે છે). સુસંગતતા માટે `moderations`નો સમાવેશ કરવામાં આવ્યો છે —
બ્લૉક-મોડમાં ઑપરેટર્સ `resolveDisabledGuardrails` મારફતે તેને મુક્તિ આપી શકે છે.

રાત્રિકાલીન વર્કફ્લો (`.github/workflows/nightly-llm-security.yml`, cron + મેન્યુઅલ
ડિસ્પેચ)માં બે જૉબ્સ છે:

- **`promptfoo-guard` (બ્લૉકિંગ)** — `INJECTION_GUARD_MODE=block` સાથે
  `promptfoo eval -c promptfooconfig.yaml` ચલાવે છે. દરેક પ્રતિકૂળ કેસ (દા.ત. "અગાઉની
  તમામ સૂચનાઓ અવગણો…", DAN-શૈલીના જેલબ્રેક્સ) ખાતરી કરે છે કે પ્રતિસાદમાં
  `error.code === "SECURITY_001"` હોય, એટલે કે ગાર્ડે વિનંતીને ખરેખર નકારી હતી.
- **`garak` (સલાહકારી)** — સ્થાનિક OmniRoute ઇન્સ્ટન્સ
  (`http://localhost:20128/v1`) સામે garak `--probes promptinject,dan,leakreplay`
  ચલાવે છે. તે પ્રોવાઇડર સિક્રેટ (`PROMPTFOO_PROVIDER_KEY`) પર આધારિત છે; સિક્રેટ
  ન હોય તો સરળતાથી સ્કિપ કરે છે અને તેની પાછળ `|| true` જોડાયેલું છે, તેથી તે CIને
  નિષ્ફળ કર્યા વિના રિપોર્ટ કરે છે.

ગાર્ડ હેલ્પર (`createInjectionGuard` / `withInjectionGuard`)નું કવરેજ પ્રોમ્પ્ટ ધરાવતા
દરેક `/v1` રૂટ સુધી વિસ્તરે છે; પ્રોમ્પ્ટ ટેક્સ્ટને
`src/shared/utils/inputSanitizer.ts`માંના `extractMessageContents()` દ્વારા
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`માંથી
લેવામાં આવે છે.
