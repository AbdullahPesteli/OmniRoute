ガードレールは、OmniRoute とアップストリームプロバイダーの境界で、安全性、ポリシー、およびコンテンツ変換を適用します。各ガードレールは、リクエストペイロード（`preCall`）とアップストリームレスポンス（`postCall`）を検査し、必要に応じて拒否、変換、または注釈付けできます。

システムは **フェイルオープン** です。ガードレールの実行中に例外が発生した場合、レジストリはエラーを記録し、リクエストを失敗させるのではなく、次のガードレールの処理を続行します。ブロックは常に明示的な判断（`block: true`）であり、偶発的に発生することはありません。

## ビルトインガードレール

レジストリは、インポート時に優先順位順に6つのガードレールを自動ロードします
（`registry.ts` → `registerDefaultGuardrails()`を参照）：

| 優先順位 | 名前                | ステージ(s)    | ファイル              |
| -------- | ------------------- | -------------- | --------------------- |
| `5`      | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`      | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`      | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`     | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`     | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`     | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

優先順位が低い番号が**最初**に実行されます。

### ビジョンブリッジ (`visionBridge.ts`) — モダリティブリッジ PR-1

**非ビジョンモデル**を対象とした画像を含むリクエストを傍受し、
リクエスト全体をビジョン対応モデルにリルートするか、画像部分を
構成可能なビジョンモデルによって生成されたテキスト記述に置き換えます。
これにより、テキストのみのプロバイダーがマルチモーダルペイロードを
透過的に処理できるようになります。

フロー：

1. 対象モデルがすでにビジョンをサポートしている場合はスキップします
   （強制ブリッジリスト `isVisionBridgeForcedModel` に表示されていない限り）。
2. `extractImageParts(messages)` を介して画像部分を抽出します
   （`visionBridgeHelpers.ts`）、これは **統合メディア
   ディテクター** `detectMediaParts()` に委任されます
   `open-sse/utils/mediaParts.ts` で — コンボ互換フィルターと共有される
   真実の唯一のソースです。抽出は、`replaceImageParts` が戻せる
   形状のトップレベル部分に許可されています（抽出↔置換契約）：OpenAI
   `image_url`、Anthropic base64 `source.type:"base64"`、Anthropic URL
   `source.type:"url"`、および Responses API `input_image`。ネストされたヒットと
   インジケーターのみの形状はコンボフィルターの素材であり、決して抽出されません。
   見つからなかった場合はスキップします。
3. `resolveVisionBridgeRuntimeSettings()`
   （`src/shared/constants/modalityBridgeDefaults.ts`）を介してランタイム設定を解決します：
   新しい `modalityBridge*` 設定キーが勝ち、レガシー `visionBridge*` キーは
   **1サイクルのフォールバック**（ロールバックウィンドウ）として残ります。
   ブリッジが無効な場合は、メディアトラバーサルの前にスキップします。
4. モードセレクター（`modalityBridgeVisionMode`、下の表を参照）が
   リルートと記述を決定します。リルートは `modifiedPayload` を返し、
   `model` のみが交換され、メタ `{ rerouted, fromModel, toModel, imagesKept }` が追加されます。
5. 記述パス：画像を `maxImages` で制限し、タスク対応のプロンプトを構成し、
   記述キャッシュを参照し、ビジョンモデルを**並行して**呼び出します
   （`Promise.allSettled`）、そしてその場所に `[Image N]: <description>` テキスト部分を
   注入します。記述に失敗した場合は `null` が返され、元の画像部分は
   **保持されます** (#4012) — ただし、すべての記述が失敗した場合のコンボ記述パスでは、
   確認された非ビジョンの上流が `(unavailable — no vision-capable provider connected)` スタブを受け取ります (#8430)。
6. `modifiedPayload` + メタ（`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`）を返します。

#### モードセレクター (`modalityBridgeVisionMode`)

| モード     | デフォルト | 挙動                                                                                                                                                                                                                                                                           |
| ---------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auto`     | ✔          | レガシーヒューリスティック、変更なし (#6640/#7204)：非コンボ/`auto/` モデルは、元のモデルが使用可能な資格情報を持っていない限り、最良のビジョンモデルにリルートされます（その場合は記述）；コンボターゲットは常に記述します。                                                  |
| `describe` |            | 常に記述 — リルートブロックは完全にスキップされます；ユーザーが選択したモデルが常に応答します。                                                                                                                                                                                |
| `reroute`  |            | 強制リルート：資格情報を持つモデルのガードがバイパスされます。リルート-**ターゲット**資格情報ガードは依然として適用されます — 使用可能なビジョンタゲットが存在しない場合、リクエストは記述に落ち、未加工の画像がテキストのみのバックエンドに到達することはありません (#8430)。 |

強制モードは、**自動ヒューリスティックが実行される前に**ショートサーキットします；`auto` の動作は
PR-1ガードレールの前とバイト同一です。

#### APIキーのスコープ (`visionBridgeKeyScope.ts`)

呼び出し元のAPIキーが `allowedConnections`、クォータプール
（`allowedQuotas`）またはモデル（`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`）を制限している場合、
ブリッジはキーが使用できるリルートおよび記述モデルのみを選択し、キーが使用できる接続でのみ動作します。
その後、記述呼び出しは常に `x-omniroute-self-loop-key-id` ヘッダーを持つ
OmniRoute自己ループを通過するため、受信したチャットリクエストは再度そのキーの接続とモデルポリシーを強制します。
`enforceApiKeyPolicy()` は、そのヘッダーを自己ループベアラーと一緒にのみ尊重するため、
アクセスを狭めることしかできず、解決できないIDは拒否されます。

キーに許可されたビジョンモデルがない場合、記述パスは脇に退き、
リクエストは変更されずに通過し、無効なガードレールと同じフェイルオープンの動作をします
（メタ `{ skipped: true, reason: "no_permitted_vision_model" }`）。
キーなしのリクエスト、およびこれらの制限のないキーは、以前とまったく同じように動作します。

#### タスク対応の記述プロンプト (`modalityBridgeVisionTaskAware`)

デフォルトは **true** です。 `composeVisionPrompt()` (`visionBridgeHelpers.ts`) は
**最後のユーザーメッセージ** のテキスト（500文字に切り詰められたもの）を基本の
説明プロンプトに追加し、ユーザーが実際に求めた内容（codex-vision-proxyパターン）に
説明を導き、視覚モデルに可視テキストの転写を依頼します。フラグがオフの場合、または
ユーザーのテキストがない場合は、基本プロンプトが変更されずに使用されます。

説明の自己ループのOpenAI互換リクエスト（`callVisionModelSingle()`
`visionBridgeHelpers.ts`内）は、常に `image_url.detail: "high"` を要求します —
無条件で、すべての呼び出し元/プロバイダーに対して、クライアントのシグナルに基づいて
制限されることはありません。低詳細のサンプリングは、まさにこのプロンプトが求める
テキスト転写タスクのOCR精度を低下させるため、説明呼び出し自体は元の受信リクエストが
使用した詳細レベルに関係なく、常に高詳細を要求します。これは内部の説明リクエストボディにのみ影響し、OmniRouteが呼び出し元の `image_url.detail` を
主要リクエストで転送する方法には変更を加えません — そのデフォルトは別に適用され、
検出されたOpenCodeクライアントに対してのみ、`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) で行われます。
説明の自己ループのAnthropicワイヤーフォーマットブランチには `detail` フィールドがなく、
どちらのデフォルトにも影響されません。

#### 説明出力制限 (`modalityBridgeVisionMaxChars`)

| キー                           | デフォルト | 範囲                 |
| ------------------------------ | ---------- | -------------------- |
| `modalityBridgeVisionMaxChars` | `0`        | `0` または 100–50000 |

`0`（デフォルト）は **制限なし** を意味します — `callVisionModel()` によって返される
説明は変更されずに通過し、既存の動作を保持します。100–50000の範囲内の任意の値は、
説明を `…` サフィックスで切り詰めてから `[Image N]: <description>` として
再結合されます（`VisionBridgeGuardrail.preCall()` は `src/lib/guardrails/visionBridge.ts` 内）。
これは、下流モデルが完全な転写を必要とする詳細重視のOCRタスクに対して引き上げ、
おしゃべりな視覚モデルのトークン使用を制限するために引き下げます。
ダッシュボードフィールドは、Visionタブの高度なパネルに存在し
（`modality-bridge-max-chars` は `ModalityBridgeVisionTab.tsx` 内）、
1から99の間の任意の値を100のフロアまで制限し、明示的な `0` はそのままにします —
`0` は独自の有効なZod値です
（`z.union([z.literal(0), z.number().int().min(100).max(50000)])`）、単なる
「未設定」デフォルトではありません。

#### 説明キャッシュ (`modalityBridge/bridgeCache.ts`)

説明出力のためのメモリ内LRU + TTLキャッシュで、プロセス全体で共有されます。
キー = `sha256(imageRef + composedPrompt + configuredBridgeModel)` で
長さプレフィックスフレーミング（フィールド境界の衝突なし）。モデルコンポーネントは
**設定された** ブリッジモデルであり、実際に応答したモデルではありません —
`callVisionModel` は内部でフォールバックする可能性があり、試行ごとにキーを付けると
キャッシュが断片化されます。失敗した説明は決してキャッシュされません。設定：

| キー                            | デフォルト | 範囲    |
| ------------------------------- | ---------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`     | —       |
| `modalityBridgeCacheTtlMinutes` | `60`       | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`      | 10–5000 |

#### リモート画像の正規化（自己ループ説明/base64取得）

ブリッジが **リモート** 画像を自ら取得する場合 — Anthropicの説明自己呼び出しと
claude-wire-formatのbase64変換（`ensureBase64ImagesForClaudeWire`）、両方とも
`fetchRemoteImageAsDataUri()` によって `visionBridgeHelpers.ts` 内で行われます —
結果として得られるデータURIは `normalizeDataUri()`
（`open-sse/utils/imageNormalize.ts`）を通過してから視覚モデルリクエストに埋め込まれます。
オーバーサイズの画像は **2048pxの長辺** にリサイズされます（OpenAI/Anthropicが
すでにサーバー側で適用しているリサイズ制限に一致）、これによりアップロードバイト/レイテンシが削減され、
視覚モデルが見るものは変わりません。リサイズには `sharp` が使用され、動的インポートを介して読み込まれます：
そのネイティブバイナリが読み込まれないプラットフォームでは、`normalizeDataUri()` は **決して例外を投げません** —
元のバイトのパススルーにフォールバックするため、説明/base64変換パスは常に機能し続けます。
非画像バイト（デコード可能な画像を返さなかった取得）もそのまま通過します。この正規化は
ブリッジが自己呼び出しのために取得する画像に限定されており、呼び出し元の生のパススルーペイロードには
適用されず、オプトインのみの変異原則（ハードルール #20）に一貫しています。

#### 設定スキーマ + マイグレーション

新しい `modalityBridge*` キーは `updateSettingsSchema`
（`src/shared/validation/settingsSchemas.ts`）でZodによって検証されます：
`modalityBridgeVisionEnabled`、`modalityBridgeVisionMode`、`modalityBridgeVisionModel`、
`modalityBridgeVisionTaskAware`、`modalityBridgeVisionPrompt`、
`modalityBridgeVisionTimeout`、`modalityBridgeVisionMaxImages`、
`modalityBridgeVisionMaxChars`、`modalityBridgeCache*` トリオ、および
Audio Bridgeによって使用される `modalityBridgeAudio*` グループ。
マイグレーション `141_modality_bridge_settings.sql` は、既存のレガシー
`visionBridge*` 値を一致する新しいキーにコピーします（冪等性があり、オペレーター設定の
`modalityBridge*` 値を上書きすることはありません）；レガシーキーは
1回のリリースサイクルの間、読み取りフォールバックとして受け入れられ続けます。

#### トランスペアレンシーヘッダー + スタッツ

説明変換されたレスポンスは
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
（`modalityBridge/bridgeStats.ts` 内の `buildModalityBridgeHeader()` によって構築され、
`src/sse/handlers/chatHelpers.ts` 内の `withModalityBridgeHeader()` によってスタンプされます）。
再ルーティングされたリクエストには **ヘッダーがありません** — ペイロードは変更されておらず、
モデルのスワップはすでにレスポンスボディの `model` フィールドに表示されています。

`GET /api/modality-bridge/stats` (管理認証、`GET /api/settings` と同じ階層) は、`vision`、`audio`、および `video` の各モダリティごとのメモリ内カウンター `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` を返します。`averageLatencyMs` は、すべての試行ではなく `latencySamples` を分母として使用します。タイミングのない操作は、ゼロミリ秒のサンプルを作成しません。`bridged` は成功した変換のための後方互換性のあるエイリアスとして残り、失敗した試行はこれを増加させません。カウンターは設計上、プロセス再起動時にリセットされます（テレメトリ、会計ではありません）。

#### ダッシュボード設定

専用のダッシュボードページは `/dashboard/settings/modality-bridge` です。そのURLアドレス可能な `Vision`、`Audio`、および `Video` タブは、`tab` 値を切り替える際にクエリパラメータを保持します。Vision タブでは、機能の有効化、モード、モデル選択（自動デフォルトを含む）、タスク認識プロンプト、高度なタイムアウト/画像/説明長/キャッシュ制限、ランタイムカウンター、および保護されたサンプルリクエストが公開されています。Audio タブもライブで、機能の有効化、STT専用モデルピッカー（Auto、タイムアウト/最大クリップ制限）、オーディオカウンター、および `input_audio` サンプルテストを公開しています。Video タブは機能しており、FFmpeg/ffprobe のランタイム状態を報告します — プローブが飛行中または完了できなかった場合は `unknown`、プローブがクライアント側でスキップされた非ループバックダッシュボードホストでは `restricted`、プローブが確認されて欠落している場合は `unavailable`、または FFmpeg/ffprobe バージョンがある場合は `available` です — モデル/フレーム/ビデオ/タイムアウト制限を保持し、モデルピッカーを視覚対応モデルにフィルタリングし、ビデオカウンターを公開します。

AI 設定の下にある以前の Vision Bridge カードは新しいページへの互換性リンクであり、フォームの二重コピーを所有しなくなりました。メディアプロバイダーは、既存の Speech-to-Text プレイグラウンドを削除することなく、Image-to-Text および Speech-to-Text ワークフローを対応する Modality Bridge タブにリンクします。

**自己ループ入場バイパス:** describe コールが OmniRoute の独自の `/v1` 自己ループ（非標準プロバイダモデル）を通過する場合、サブリクエストは `x-omniroute-admission-bypass: internal` を送信し、解決された自己ループ資格情報で認証されます — ローカルモードの `sk_omniroute` センティネル、またはオペレーターが設定した `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` 環境キー (#1350) により、`REQUIRE_API_KEY=true` のデプロイメントでも describe コールを実行できます。このバイパスは、正確な資格情報に対してのみ尊重されるため、外部クライアントはヘッダーを使用して入場をスキップすることはできません。

レガシーデフォルトは `src/shared/constants/visionBridgeDefaults.ts` に存在します。新しいモード/タスク認識/キャッシュデフォルトと設定リゾルバは `src/shared/constants/modalityBridgeDefaults.ts` に存在します。ガードレールは、テストが偽の `getSettings` および `callVisionModel` 実装を注入できるように `deps` コンストラクタオプションを公開します。

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

オーディオを含むチャットリクエストが、オーディオ入力を受け入れることが知られていないターゲットに到達する前にインターセプトします。チャットリクエストを再ルーティングすることは決してありません：オーディオ部分は既存の OpenAI 互換のマルチパートエンドポイントを通じて転写され、選択されたチャットモデルはテキストの転写を続行します。

フロー：

1. `getResolvedModelCapabilities()` を通じて `supportsAudio` を解決します。明示的なプロバイダレジストリメタデータが優先され、次に静的モデルメタデータ、次に同期された `modalities_input` です。`audio` を含まない宣言された入力リストは `false` です。能力の証拠がない場合は `null` です。`false` と `null` の両方が保守的なブリッジをアクティブにし、`true` はそれをバイパスします。
2. `modalityBridgeAudio*` 設定を解決し、共有の `detectMediaParts()` デテクタを通じて各メッセージからスプライス可能なトップレベルのオーディオ部分を抽出します。サポートされるワイヤー形状は OpenAI の `input_audio`、`audio_url`、および `source.media_type: "audio/*"` です。ネストされたオーディオはルーティングのために検出されますが、スプライスパスによって削除されることはありません。作業は `modalityBridgeAudioMaxClips` によって制限され、後の部分はそのまま残ります。
3. 設定された `provider/model` を尊重するか、`selectAudioBridgeModel()` に `AUDIO_TRANSCRIPTION_PROVIDERS` を安定したカタログ順に歩かせ、使用可能なアクティブプロバイダ資格情報を持つ最初のモデルを選択させます。
4. `callAudioTranscription()` は base64/data-URI オーディオをマルチパート `file` に変換するか、DNS ピンニングと 25 MB の制限を持つ公開専用のアウトバウンドガードを通じてリモート `audio_url` をダウンロードします。その後、ファイルと選択されたモデルをローカルの `/v1/audio/transcriptions` 自己ループに POST し、`resolveSelfLoopBearer()` で認証されます。既存の転写ルートは通常の資格情報の検索、クールダウン/レート制限の処理、およびプロバイダのディスパッチを行います。
5. 成功したコールは、その部分を `[Audio N]: <transcript>` に置き換えます。コールは `Promise.allSettled` で実行されます：個々の失敗は元のオーディオ部分を保持します (#4012 契約)。すべてのコールが失敗し、ターゲットが `supportsAudio === false` であることが証明された場合、部分は `[Audio N]: (unavailable — no STT provider connected)` になります (#8430 契約)。未知のターゲット（`null`）の場合、すべての失敗結果はそのまま残ります。使用可能な STT 資格情報を持たない証明されたテキスト専用ターゲットは、ネットワークコールを発行することなく同じ明示的なスタブを受け取ります。

成功した転写は、プロセス全体の Modality Bridge LRU/TTL キャッシュを使用します。キーはオーディオ参照、安定した `audio-transcription` 操作ラベル、および選択された STT モデルを組み合わせたものです。失敗は決してキャッシュされません。オーディオ試行は共有の `bridged`、`cacheHits`、`failures`、および `lastUsedAt` カウンターを更新します。変換されたレスポンスは `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` を持ち、変更されていないリクエストは Audio Bridge セグメントを受け取りません。

ランタイム設定は DB バックアップされ、Zod によって検証されます：

| キー                          | デフォルト | 範囲               |
| ----------------------------- | ---------- | ------------------ |
| `modalityBridgeAudioEnabled`  | `true`     | —                  |
| `modalityBridgeAudioModel`    | `""`       | Auto または STT ID |
| `modalityBridgeAudioTimeout`  | `60000`    | 1000–300000        |
| `modalityBridgeAudioMaxClips` | `3`        | 1–10               |

共有キャッシュは `modalityBridgeCacheEnabled`、`modalityBridgeCacheTtlMinutes`、および `modalityBridgeCacheMaxEntries` によって制御されます。

### ビデオブリッジ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ターゲットが知られていないネイティブビデオサポートを持つ場合に呼び出される前に、チャットコンプリーションの `messages` とレスポンスAPIの `input` で最上位のビデオ部分をインターセプトします。サポートされている形状は `input_video`、`video_url`、`video_source`、HTTPS URL、および `data:video/*;base64,...` データURIです。テキスト内のプレーンファイル名はビデオとして扱われません。

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) はリクエストのトラバーサル、能力/ポリシーチェック、リクエストごとの集約、およびレスポンスペイロードを管理します。ビデオごとの作業 — 取得、全結果キャッシュ、フレームシーケンスの記述（呼び出し元が宣言した音声トランスクリプトを融合する）、および試行ごとのメトリクス/中止/クリーンアップ — は `processVideoPart` に隠されており、`preCall` のループ内でビデオ部分ごとに一度呼び出されます。このモジュールは、バイトを取得しサンプリングされたフレームを抽出する `VideoMediaBrokerPort`、呼び出し元が宣言した音声トランスクリプトをサンプリングされたキャプションと融合する `VideoAudioTranscriptionPort`、およびレガシーの生ストア形状である `VideoDrilldownPort` の明示的なポート境界も定義しています。プロダクションSTTとフレーム保持は、`createVideoSttAdapter` と `createVideoDrilldownAdapter` を通じて記述ポートの周りに構成されます。後者は共有の不透明ハンドルライフサイクルを使用します。

公開の `/v1` リクエストパスは、サブプロセスをインポートまたは呼び出すことはありません。リモートビデオは50 MiBの制限内でダウンロードされます。インラインのbase64ビデオは、モデル/メッセージ/フレーミングエンベロープが公開のJSONリクエスト受け入れ制限の50 MiB内に留まるように、保守的な36 MiBのデコード済みビデオキャップを持っています。インラインの長さとデコードサイズの推定は、割り当ての前にチェックされます。最初のリモートURLとすべてのリダイレクトにはHTTPSが必要で、既存の公開専用のアウトバウンドガードとDNSピンニングを使用します。そのバイトは、正確な内部 `POST /api/modality-bridge/video/extract` ブローカー境界を越えます。このルートは `LOCAL_ONLY` かつ `SPAWN_CAPABLE` であり、プロセスごとに認証された信頼できるループバックリクエストのみを受け入れ、URL、ファイルシステムパス、実行可能ファイル、または引数リストは決して受け入れません。APIボディサイズパイプラインとハンドラーのインクリメンタルボディリーダーは、独立して50 MiBのブローカー入力キャップを強制します。その制限付きキューは、一度に1つの抽出を実行し、4つの保留中のジョブを許可し、保留中の入力を100 MiBに制限します。

ブローカー内で、`ffprobe` はプライベートローカルファイルを読み取ります。固定フォーマットのホワイトリストは、プレイリストおよびマニフェストフォーマットを除外します。許可されたMOVファミリーコンテナについては、外部MOVデータ参照はデフォルトで無効になっており、固定コマンドはそれらにオプトインしません。`ffprobe` と `ffmpeg` は、`file` のみのプロトコルホワイトリスト、1つのスレッド、固定引数配列、シェルなし、`PATH` から解決された実行可能ファイルを使用します。添付された画像カバーのストリームは再生可能な候補ではありません。すべての再生可能なストリームは制限を満たす必要があり、明示的なデフォルトストリームが決定論的に最低インデックスのフォールバックの前に優先されます。ビデオは600秒、各次元で8192ピクセル、33554432ソースピクセルに制限されています。FFmpegは1〜16の中間JPEGフレームをサンプリングし、長辺を最大1024ピクセルにスケールダウンし、小さい入力をアップスケーリングせず、URLを受け取ることはありません。サンプリングはデフォルトで `uniform` です。オプションの `scene_aware` および実験的な `segment_aware` ポリシーは、すでに検証されたローカルストリームに対して追加の固定FFmpegパスを実行し、制限された `showinfo` シーンタイムスタンプを選択し、検出器の失敗、タイムアウト、形式が不正な出力、または空の候補セットに対して決定論的に同じ均一な中間点にフォールバックします。セグメント認識モードは、検証されたシーン間隔に比例して中間サンプルを割り当てます。セグメント認識の証拠とフォールバック動作は以下に詳述されています。厳格な16フレームのキャップは、すべてのポリシーで選択後に適用されます。シーン認識リクエストが1フレームの予算しかない場合、アクティブなフルビデオまたはフォーカスウィンドウの均一な中間点を使用し、`policyEffective: uniform` を報告します：単一の選択されたシーンフレームは、両方の時間的端を保持することはできません。呼び出し元はオプションで有限のフォーカスウィンドウ（`start`/`end` 秒）を提供できます；境界はメディアの持続時間にクランプされ、逆または非有限のウィンドウは拒否され、すべてのサンプリングポリシーは正規化された間隔内でのみ実行されます。結果のウィンドウはサンプリングメタデータおよび信頼できない説明プレフィックスに含まれ、下流のモデルがフルタイムラインから焦点を当てた抜粋を区別できるようにします。

セマンティックキャプションフォーカスは、別の明示的な設定です。デフォルトの `full` 分析モードは、既存のフレームプロンプトを保持し、リクエストテキストをキャプションモデルに転送することはありません。`focused` モードでは、ブリッジは同じチャットまたはレスポンスコンテナから最新の非空のユーザー作成 `text`/`input_text` のみを読み取り、それをNFCに正規化し、制御文字とホワイトスペースを圧縮し、500のUnicodeコードポイントに制限します。空の結果は正確な `full` プロンプトにフォールバックします。使用可能なヒントは、専用の信頼できないユーザーコンテキストブロック内でJSONとしてシリアライズされ、観察可能な詳細を優先することしかできず、メディア内で可視または可聴の指示に従うことに対する別の警告を上書きすることはできません。テキストフォーカスは `start`/`end` を推測したり、時間的サンプラーを変更したりすることはありません。

#### FU-07 構造的セグメント証拠

`segment_aware` は、すでに検証されたローカルビデオストリームに対して、1回の制限された事前分析パスを使用します。固定フィルターチェーンは、まず最大320ピクセル幅にスケーリングし、シーンの変化やフリーズ間隔を検出し、次に1秒ごとにぼかし、平均輝度、空間/時間情報のためにサンプリングします。このパスは、600の構造サンプル、1つのFFmpeg/フィルタースレッド、同じ`file`専用プロトコルとコンテナのホワイトリスト、1 MiBのプロセス出力制限、ブローカーの共有中止/期限内で最大30秒に制限されています。リクエストからコマンド、フィルター、パス、またはURLを受け入れることはありません。

構造的値は決定論的サンプリング証拠であり、意味的なビデオ理解ではありません。彼らは主題、行動、キャプション、スピーチ、またはユーザーの意図を推測しません。シーンとフリーズの境界はセグメントを形成し、フリーズカバレッジ、ぼかし、露出、空間的詳細、および時間的変化は、既存の1〜16フレームの予算がどのように配分されるかにのみ影響します。完全にフリーズしたセグメントは1フレームに制限され、非フリーズセグメントは残りの予算を競います。境界がフレームを上回る場合、均一なタイムラインカバレッジが保持されるため、迅速な早期カットは長いトレーリングセグメントを隠すことができません。フリーズ境界の1秒の分析解像度内のシーン境界は統合されます。

フィルターの欠如、形式が不正な/空の証拠、検出器エラー、または制限された事前分析タイムアウトは、正確な均一中点ポリシーにオープンに失敗します。呼び出し元の中止またはブローカーの期限はオープンに失敗することはなく、進行中のサブプロセスを終了し、後のフレーム抽出を防ぎ、プライベートな一時ツリーは`finally`で削除されます。

`scripts/perf/video-bridge-fu07-eval.ts` は、重複排除後のキャプションコールの節約、密な動きの予算配分、ぼかし/露出/SI-TI証拠、長い尾を持つ迅速なカット、徐々にフェードする偽陽性のための決定論的なリアルFFmpegフィクスチャを生成します。事前分析の壁時間を記録し、`/usr/bin/time` が利用可能な場合は、子CPUとピークRSSを記録します。その品質チェックは構造的オラクルのみです。リアルキャプションモデルの品質は`HOLD`のままであり、このハーネスには認可されたエンドポイントやフリーズした審査員がいないためです。金銭的な節約も、`--caption-cost-per-call-usd` が明示的なポジティブなコールごとの見積もりを提供しない限り、`HOLD`のままです。このスクリプトは、いずれの結果も作り出すことはありません。

各フレームは4 MiBに制限され、すべての生フレームは合計23 MiBに制限され、シリアライズされたブローカーの応答は32 MiBに制限されます。プライベートな一時ディレクトリは`finally`で削除されます。OmniRouteはFFmpegをバンドルせず、カスタム実行可能パスを受け入れません。キャプション付けの前に、ブリッジは保守的な視覚的重複排除パスを適用します：各JPEGは16×16のグレースケールバッファに減少し、保持された最後のフレームとのみ比較されます。1フレームを超えるキャプション予算が要求される場合、抽出はその予算の最大2倍の制限された候補プールを提供し、16フレームを超えることはありません。要求された上限は重複排除の後にのみ適用され、最初と最後に選択された候補は、予算が少なくとも2のときに最終的なスリム化中に保持されます。バージョン管理された`grayscale-16x16-mean-cells-v2`ポリシーは、平均輝度デルタと、正規化されたデルタが少なくとも0.05のサムネイルセルの比率の大きい方を使用します。重複の閾値は、予測可能性のために選ばれた定数0.04です。これはランタイム設定として公開されていません。この二次的な高コントラスト信号は、平均のみの比較が隠す可能性のある小さな動きや可視テキストの変化を保持します。コンパレータやデコーダのエラーはオープンに失敗し、カバレッジを保持します。出力メタデータは、抽出された候補、成功したフレーム、および削除された視覚的重複を分離します。

明示的にマークされたビデオ部分は、タイムスタンプ付きのコンタクトシートを要求することができます。ブリッジは最大4列、16フレームのJPEGグリッドを構築します。各512ピクセルのセルは、そのソースのタイムスタンプを高コントラストの下部バンドに焼き付け、同じタイムスタンプは下流の関連付けと監査のためにテキストメタデータに残ります。完全なJPEGは32 MiBに制限されます。`sharp` がグリッドをデコードまたは構成できない場合、ブリッジは個々のJPEGフレームにフォールバックします。クライアントの中止は、シート操作を通じて依然として伝播します。

プロモーション証拠は、合成構成マイクロベンチマークとは意図的に分離されています。`scripts/perf/video-bridge-contact-sheet-eval.ts` は、リアルなOpenAI互換のビジョンモデルのためのスキーマバージョン管理されたA/Bハーネスを定義します。プロバイダーが報告したトークン、エンドツーエンドの壁のレイテンシ（シート構成を含む）、モデルコールのカウント、およびマニフェストで定義された事実の保持を測定します。生のモデル応答はレポートに書き込まれず、SHA-256ダイジェストと一致した事実IDのみが保持されます。このハーネスは、`--execute-real` が渡され、`--model`、`OMNIROUTE_BASE_URL`、および `OMNIROUTE_API_KEY` が設定されていない限り、ネットワークや有料モデルコールを行いません。その明示的なリアルランがない限り、その機械可読の判決は`HOLD`のままです。合成ペイロード/コールカウントの測定のみはプロモーション証拠ではありません。

別の`scripts/perf/video-bridge-promotion-eval.ts` は、FU-07またはFU-09の観察を消費します。プロモーションの受け入れには、すべての8つの合成シナリオタイプと、少なくとも3回測定された繰り返し、すべての10の宣言されたメトリック、フリーズしたメディア/プロンプト/期待される事実/設定のダイジェスト、ユニークな観察ID、および検証されたシードA/B順序が必要です。実行レシートはコーパスのダイジェスト、正確な候補SHA、およびモデルのリビジョンを結びつけます。欠落または無効な測定は`HOLD`のままであり、CPUが30秒を超える場合、ピークRSSが512 MiBを超える場合、または事前分析が30秒を超える場合も含まれます。これらは証拠受け入れの上限であり、新しいランタイムRSSの強制保証ではありません。

FU-07は、少なくとも98％の品質保持と、p95レイテンシがベースラインの1.2倍を超えないことを要求します。さらに、同等の平均キャプション呼び出しにおいて、0.05の絶対ケースバランス平均リコールの改善、または平均ポストデデュープキャプション呼び出しが少なくとも10％減少する必要があります。FU-09は、少なくとも0.85の品質、95％の保持、20％のp95レイテンシ削減、および10％のトークン削減を要求します。重要な事実の喪失、注入コンプライアンス、または使用の欠如は昇進を妨げます。一度の実行では何も昇進できません：`--previous-report`は、同じポリシー/モデルの改訂/候補/コーパスの2つの異なる、重複しない、連続して適格な実行を確認します。サンプリング実験は、コンタクトシート実験を確認できません。

コレクターは、メモリ内で応答をスコアリングし、`responseDigest`とメトリクスおよび観察バインディングを保存し、応答テキストは保存しません。コンシューマは、レガシーの生の観察を読み取りますが、そのテキストをレポートにコピーすることはありません。各観察に対して、`responseDigest`または`rawResponseText`のいずれかが受け入れられます。バージョン管理された許可リストは空のままで、変更不可能な`hold`がデフォルトです。適格なエントリには、その証拠参照、ポリシー、モデルの改訂、正確な候補SHA、マニフェストダイジェスト、および2つの異なる実行IDが必要です。矛盾するコンテキストは拒否されます。これらのメタデータは監査契約であり、参照されたファイルが真の測定値を含む証拠ではありません。エントリを追加する前に、実際のレシートを確認してください。管理統計エンドポイントとビデオダッシュボードは保守的な準備状況を公開します。構成されたモデルエイリアスだけでは、その改訂や実行中の候補SHAを確立することはできないため、現在のダッシュボードは他の実行コンテキストからの適格性を再利用するのではなく、`HOLD`を報告します。明示的な実験選択は昇進とは別に保持され、デフォルトは自動的に変更されません。

呼び出し元は、すでに整列されたテキストを持っている場合、サポートされているビデオ部分にオプションの`transcript.cues`配列を添付できます。各キューは、`text`、プローブされた期間内の有限な`start`/`end`間隔、およびホワイトリストに登録された`source`（`client`、`embedded`、または`audio-bridge`）を持つ必要があります。`confidence`はデフォルトで`1`であり、`0`と`1`の間に留まる必要があります。正確な重複キューは統合されます。OmniRouteはこのメタデータからの転写を開始しません：検証されたキューは、ソース、信頼度、および間隔とともに記述された結果にコピーされ、フレームキャプションとともに信頼できない観察として表示されます。無効、範囲外、または出所のないテキストは、キャプションストリームに混入するのではなく拒否されます。両方のリクエストボディトランスクリプトチャネルは、自己主張された`embedded`または`audio-bridge`ラベルを含む`client`に供給された出所を正規化します。信頼できるラベルをコード専用の`trustedSource`引数を通じて割り当てることができるのは、サーバー所有のアダプターのみです；リクエストJSONフィールドはその引数に到達できません。トランスクリプトテキストは、出所に関係なく信頼できないメディア由来のコンテンツであり、決して認証を決定してはなりません。

高度な呼び出し元は、同じビデオのために`audioTranscript`トラックを提供できます；これはサーバーの転写の証拠ではなく、クライアント提供のテキストとして扱われます。フュージョンシームは、視覚および音声の観察を1つの締切と中止信号の下で実行し、共通のタイムラインで順序付け、正確な重複を統合し、片方だけが成功した場合に部分的な結果を報告します。無効な`audioTranscript`はその部分的な結果に劣化します — 視覚的な説明は保持され、音声ブランチはサニタイズされた失敗コードを記録します — 全体のビデオが失敗するのではなく。各ブランチの可用性、部分フラグ、およびサニタイズされた失敗コードは、記述された結果、ガードレイルメタデータ（`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`）、結果キャッシュメタデータ、およびブリッジフュージョンカウンターに保持されます。デフォルトのビデオブリッジパスは、音声からテキストへの変換を呼び出したり、2番目のメディアコピーをダウンロードしたりしません；その明示的なトラックがない限り、ビデオのみのままです。

**トランスクリプト保持 (#12150 P1)。** これは、ビデオブリッジ（オプトイン自体）がトランスクリプトキューをレンダリングするたびに自動的に適用されます — 別の保持フラグはありません。リクエストが任意のトランスクリプトキュー（呼び出し元が宣言した`transcript`または融合された`audioTranscript`）をレンダリングすると、ガードレイルはそれを`videoBridgeObserved`としてマークし、ビデオ説明の赤acted影を生成します — 各キューの自由テキストボディが`[redacted-video-transcript]`に置き換えられた同一のレンダリングで、文字列が組み立てられる前に構造化されたキューフィールドを置き換えることによって構築されます（平坦化されたテキストを解析することによってではなく、したがってキューの内容 — 敵対的または通常の、`[inaudible]`や`[music]`のように`]`を含むボディを含む — は生き残ることができません）。保持されたコールログリクエストボディは、各ビデオ由来のテキスト部分をその赤acted影に置き換え、内容の等価性で一致します；`fullText`アンカーは、完了した事前コールガードレイルペイロードから再読み込みされるため、後のチェーンガードレイル（PIIおよび資格情報マスキング、優先度10/95）が説明テキストをその場で書き換え、システムプロンプト/ハンドオフ/メモリ注入がメッセージ配列を再形成した後でも、一致が成功します。モデルに送信されるボディは変更されません。観察されたリクエストは、耐久性のあるメモリをも生成しないため（リクエストおよび応答由来の抽出はスキップされます）、モデル自身の応答はトランスクリプトテキストをメモリにエコーすることはできません。

**生のビデオフィールド (#12430)。** ブリッジが有効で、ネイティブビデオサポートが不明または存在しない場合、定義された`transcript`/`audioTranscript`フィールドは、説明の失敗や`maxVideos`制限の後でも`videoBridgeObserved`を有効にします。`null`および空の文字列もカウントされます；欠落フィールドおよび非ビデオメタデータはカウントされません。保持されたコピーはこれらのフィールドを赤actedするか、リクエストを省略し、キャッシュ/メモリはバイパスされます。

そのフォールバックパスでは、有効な呼び出しキューは非標準プロバイダーフィールドではなく、サポートされている `text`/`input_text` 部分になります。リクエスト提供のトラックは、明示的な警告とともに、ビデオが説明されておらず、タイムスタンプがメディアに対して検証されていないことを示す信頼できない `client` 観測として残ります。既存の 256 キュー/64-KiB の合計および各キューの予算は、2 つのトラック全体に適用されます。タイムスタンプはブローカーの 600 秒の上限と、提供されたフォーカスウィンドウに収まる必要があります。無効なトラックは破棄され、任意のテキストとして転送されることはありません。有効な兄弟トラックは、結合された予算が超過しない限り使用可能です。ヌル/空のフィールドはテキストを追加しません。このフォールバックによってメディアの取得や文字起こしは追加されません。文字起こし拡張フィールドは、フォールバックビデオキャリアおよびその `video_url`/`source` オブジェクトから削除されます。OpenAI のワイヤー許可リストは厳格に保たれ、未知のネイティブビデオキャリアは引き続き利用可能で、既知のテキスト専用ターゲットは安全なマーカーを保持します。構造化されたレダクションシャドウは、追加された文字起こしテキストを保護し、元の呼び出し元のリクエストは変更されません。ネイティブサポートされたターゲットと無効なブリッジは、既存のバイパス動作を維持します。

追加の保持されたコピーは、同じ観測リクエスト信号を使用します。生のプレガードレールクライアントリクエストスナップショット、メモリ内の保留中のリクエスト、および早期拒否リクエストログは、ビデオ部分の文字起こしフィールドを構造的に置き換えます。パイプラインステージおよびコンテキストハンドオフによって合成された文字列プロンプトは、保持されたリクエストボディのシンクでレダクションされます。保持された `video_content_removed` マーカーは、`previous_response_id` の継続を失敗させ、意図的に破棄されたテキストを再構築することはありません。観測されたリクエストがログ記録前にそのパートごとのレダクションシャドウを失った場合、または後のリクエスト変異後に複数のビデオシャドウのいずれかが一致しない場合、保持されたリクエストボディは部分的にレダクションされた文字起こしを保持するのではなく、完全に省略されます。

観測されたリクエストに対して、モデルの応答は構造化されたキュー境界なしに文字起こしの任意の部分を引用することがあります。そのため、保持されたコールログの `responseBody` は省略マーカーによって置き換えられます。詳細なパイプラインアーティファクト（上流/クライアントボディやストリームチャンクを含む可能性があります）は保持されません。セマンティック、冪等性、および推論リプレイキャッシュは、そのリクエストの読み取りおよび書き込みをバイパスします。プロバイダリクエストとクライアント可視の応答は変更されません。詳細なアーティファクトが省略されると、早期のキープアライブバイトは一時バッファから排出されます。Kiro の不正な EventStream 警告は、ペイロードバイト数のみを報告し、その内容や JSON パーサーの生のエラーは決して報告しません。これは、すべての無関係なプロバイダー/プラグイン診断が監査されたことを主張するものではありません。より広範な保持されたシンクスイープは #11658 で追跡されています。

内部の `/api/modality-bridge/video/drilldown` ライフサイクルは、別のループバック/トークン認証されたキャッシュ基盤です。すべての操作には、標準的な不透明なプリンシパル ID が必要です。プロダクション呼び出し元が有効化される前に、その ID を認証されたテナントから導出し、クライアントが選択した値を転送してはなりません。キャッシュキーは、そのプリンシパルを標準のセッションおよびビデオ参照 ID にバインドし、SHA-256 から導出されたキーのみを保存し、読み取りおよび削除のスコープを同じプリンシパルに制限します。キャッシュは、エントリごとに最大 16 の導出 JPEG フレームを保存し、10 分後に期限切れになり、制限された `start`/`end` 読み取りまたは明示的なセッション削除をサポートします。

各プリンシパルは、16 エントリおよび 64 MiB の標準 JPEG データに制限されています。これらの制限は、グローバルな 64 エントリ/256 MiB の上限とは独立しています。プリンシパルのクォータ圧力は、そのプリンシパルの最も最近使用されていないエントリのみを追い出し、グローバル LRU 追い出しが考慮される前に行われます。期限切れのエントリは、キャッシュアクティビティに基づいてプリンシパルおよびグローバルの会計から掃除され、キャンセルおよび検証失敗は部分的な置き換えをコミットしません。

キャッシュは、非標準の Base64、過剰なパディング、非 JPEG メディア、形式が不正または切り捨てられた JPEG、制限されたフルイメージ `sharp` デコード中に警告を生成する JPEG を拒否します。受け入れられた各画像は標準 JPEG として再エンコードされ、呼び出し元フィールドを信頼するのではなく、デコードされたバイトから幅と高さを導出し、トレーリングポリグロットバイトは保持するのではなく破棄されます。制限された標準圧縮バッファのみが両方のクォータに請求されます。JSON ワイヤー制限には、32 MiB のデコード入力上限に対する Base64 オーバーヘッドが含まれます。すべての保存された導出は、その検証された JPEG 形式/解像度、サンプリングポリシー、導出バージョン、作成時間、サーバー計算されたコンテンツハッシュ、およびハッシュ化された親参照に加えて、信頼できる呼び出し元の親コンテンツハッシュを記録します。キャンセルは、原子的なキャッシュコミットの前に非同期デコード/ハッシュフェーズ間でチェックされます。

プロダクションプロデューサーは、成功した視覚分析の後にのみ、すでに導出されたブローカーフレームを再利用し、2 回目のビデオダウンロード/抽出は行いません。これは、オペレーター `modalityBridgeVideoDrilldownEnabled=true`、厳格なパートごとの `drilldown: true`、および認証された API キーのレコード ID を必要とします。クライアントが宣言したプリンシパル/セッション値は、所有権を確立することはありません。これらの 3 つの条件がすべて満たされない限り、追加のフレームをハッシュ、リサイズ、または保持することはありません。保持失敗は、使用可能な視覚応答を保持します。同意されたリクエストは、全ビデオ結果キャッシュをバイパスするため、キャッシュされた結果は決してハンドルをリプレイしません。

成功したJSONおよびSSEレスポンスは、最大で4つの不透明ハンドルを制限された`x-omniroute-video-drilldown`ヘッダーに公開します。認可されたブラウザのオリジンは、そのヘッダーをCORSオリジンポリシーを広げることなく読み取ることができます。新しいハンドルは`v1.<32-byte random base64url token>`を使用し、レジストリはそのSHA-256ハッシュのみを保持します。リーダー/ヘッダーパーサーは、レガシーの64-16進トークンも受け入れます。認証された公開コンシューマは`GET /api/v1/video-bridge/drilldown?handle=...`であり、`modalityBridgeVideoDrilldownRemoteEnabled=true`によって独立して制御されます。明示的に永続化されたfalseは、レガシーの`OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED`環境フォールバックが有効になっている場合でもアクセスを取り消します。プロダクションの保持には、類似のレガシー`OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED`フォールバックがあります。両方のフォールバックはデフォルトでオフです。

コンシューマは認証されたキーから所有権を導出し、キーのポリシーを適用し、未知、期限切れ、または他のキーのハンドルに対して同じ404を返します。`variant=preview|standard|detail`（最大JPEG寸法320/640/1280、決してアップスケールしない）、`limit=1..8`（またはレガシーの`frames`エイリアス、両方は決して使用しない）、ゼロベースの`page`、およびオプションの`start`/`end`フォーカス秒を受け入れます。重複したクエリキーと逆フォーカスウィンドウは拒否されます。返される各バリアントには、その実際のコンテンツと実際の解像度メタデータのハッシュが含まれ、保持されたソースにリンクされています。バリアントは読み取り時に導出され、追加の保持されたコピーとして保存されることはありません。JSONレスポンス（Base64/エンベロープを含む）は32 MiBに制限されており、サイズが大きすぎるページは413を返し、クライアントはより少ないフレームを要求する必要があります。読み取りは各リサイズの周りでキャンセルを確認し、返す前にハンドルの有効性を再確認します。所有者による`DELETE`は冪等です。削除またはTTLの期限切れは、保持されたソースと使用会計を解放します。

共有ストアはプロセスローカルであり、ハンドルは再起動時に期限切れになり、独立したOmniRouteプロセス間で転送することはできません。管理統計は、効果的な保持/リモートポリシーと集計された保持エントリ/バイトのみを公開し、メディア、参照、主要ID、またはハンドルは決して公開しません。ビデオ設定パネルはこれらの値を表示し、両方の同意スイッチを永続化できます。この実装ドキュメントは、ライブデプロイメントやプロモーションの証拠ではありません。実際のモデルの受け入れは別途追跡されます。

フレームは、構成されたビデオモデルで順次キャプションされます。空のビデオオーバーライドはビジョン設定を継承します。両方が空の場合、ビジョンオートルーターは効果的なビジョン対応モデルを選択します。成功したキャプションは、元の部分を安定した`[Video description:`プレフィックスで置き換え、テキストを信頼できないメディア由来の観察としてマークし、下流のモデルにメディア内で見つかった指示に従わないように指示します。フレームキャプションキャッシュキーには、JPEGバイト、プロンプト、タイムスタンプ、および効果的なモデルが含まれ、成功したキャプションのみがキャッシュされます。キャッシュエントリは、実際の成功したプロデューサーモデルを保持し、フォールバックモデルを含みます。ブリッジは、異なるフレームが異なるモデルによって生成された場合に`mixed`を報告します。キャッシュヒットは、そのプロデューサーのアイデンティティを再利用し、要求されたルーティングプランとして再ラベル付けすることはありません。全ビデオ結果キャッシュは、出力を変更するすべての入力 — プロンプト、効果的なモデル、サンプリングポリシー、フレーム数、セマンティック分析モード、正規化されたフォーカスヒントのSHA-256フィンガープリント、フォーカスウィンドウ、`transcript`、`audioTranscript`、およびコンタクトシートフラグ — に基づいてキー付けされているため、これらの次元のいずれかを変更するとキャッシュミスとなり、決して古い再利用にはなりません。視覚的重複排除ポリシーのバージョン、しきい値、および制限された候補フレーム数も結果キャッシュキーとメタデータに明示的に含まれているため、ポリシーの変更は古い全ビデオの説明を再利用することはできません。結果キャッシュv4メタデータは、モードとフィンガープリントを保持し、ユーザーの生のタスクは決して保持しません。ガードレイルメタデータは、要求された分析モードと効果的な分析モードの両方を報告します。使用可能なユーザーテキストがない要求された`focused`モードは、実際には`full`として報告されます。

ガードレイルは、サポートされているすべてのビデオ部分を抽出しますが、`modalityBridgeVideoMaxVideos`を超えることはありません。`supportsVideo === false`であることが証明されたターゲットに対しては、失敗したビデオと制限を超えたビデオは明示的な安全テキストマーカーとなり、生のビデオは生き残りません。能力が不明な場合、これらの部分はそのビデオキャリアを保持します。いかなるフォールバックトランスクリプトも、上記の制限されたテキスト変換に従います。`supportsVideo === true`のターゲットはブリッジをバイパスします。クライアントリクエストの中止信号は、ダウンロード、ブローカーキュー、サブプロセス、およびキャプション呼び出しを通じて伝播します。中止はビデオ間で停止し、生のメディアに対してオープンに失敗することはありません。

ランタイム設定はDBバックアップされ、Zodで検証されています：

| キー                                | デフォルト  | 範囲 / 挙動                                                                                                           |
| ----------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | オプションのランタイム、オプトイン                                                                                    |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full`は一般的なキャプションを保持します。`focused`は制限された、信頼できない最新のユーザーコンテキストを使用します。 |
| `modalityBridgeVideoModel`          | `""`        | ビジョンブリッジモデルを継承します                                                                                    |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                                  |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`、`scene_aware`、または比例的な`segment_aware`。検出器の失敗は`uniform`にフォールバックします。              |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                                   |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                                        |

レガシーの永続化されたビデオタイムアウト値が120秒を超える場合、ブローカーの期限に制限されます。その制限を超える新しい設定の書き込みは拒否されます。`GET /api/modality-bridge/video/runtime`は、認証またはランタイムプロービングの前に信頼されたスタンプ付きループバックローカリティを必要とし、その後に管理者認証が必要です。これは、ランタイムが利用できない場合にのみ、`available`、サニタイズされたFFmpeg/ffprobeバージョン、および固定の理由を返します。内部抽出エンドポイントは公開アップロードAPIではありません：キューの飽和は`503`と`Retry-After`を返し、呼び出し元の切断は`499`を返し、固定のブローカー期限は`504`を返します。変換されたレスポンスは、中央の`x-omniroute-modality-bridge`ヘッダーに`video->text;model=<visionModel>;parts=<videos>`を追加し、VisionまたはAudioセグメントを削除しません。

### PII マスカー (`piiMasker.ts`)

**両方の**ステージで実行されます。

- **`preCall`**はペイロードをクローンし、`system`、`messages`、`input`、および`prompt`（プレーン文字列アイテムを含む）を歩き、`@/shared/utils/inputSanitizer`からの`processPII()`を文字列`content`/`text`フィールドに適用します。`PII_REDACTION_ENABLED=true`のとき、検出されたPIIはアウトバウンドペイロードで赤外線処理されます。これは`INPUT_SANITIZER_MODE`（プロンプトインジェクションポリシーのみを制御）とは独立しています。赤外線処理がオフの場合、呼び出しはコンテンツを書き換えずに検出カウントを記録します。
- **`postCall`**はレスポンスをディープクローンし、`sanitizePIIResponse()`とレスポンスAPI形状マスカー（`maskResponsesOutput` — `output_text`および`output[].content[].text`をカバー）を実行します。赤外線処理が発生した場合、修正されたレスポンスが元のものに置き換えられます。

ガードレールは決してブロックせず、注釈（`meta.detections`、`meta.redacted`）または書き換えを行います。

### プロンプトインジェクション (`promptInjection.ts`)

ユーザー提供のコンテンツ内の敵対的構造を検出し、設定されたポリシーを強制します。動作は環境変数とコンストラクタオプションによって駆動されます：

| 設定         | 環境変数                                                                                                      | デフォルト | 効果                                                                                                                                                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 有効         | `INPUT_SANITIZER_ENABLED`                                                                                     | `true`     | `false`の場合、ガードレールはショートサーキットします。                                                                                                                                                                  |
| モード       | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                               | `warn`     | インジェクションポリシー：`block`、`warn`、または`log`。(`redact`は後方互換性のために受け入れられますが、インジェクションテキストを削除しません；リクエストPIIの書き換えは`PII_REDACTION_ENABLED`によって制御されます。) |
| ブロック閾値 | `blockThreshold`オプション / `INPUT_SANITIZER_BLOCK_THRESHOLD`（エイリアス`INJECTION_GUARD_BLOCK_THRESHOLD`） | `high`     | ブロックするために必要な最小の重大度。デフォルトでは中程度は観察のみです。                                                                                                                                               |

**モードの優先順位**（`getMode`）：呼び出し元の`options.mode` → `INJECTION_GUARD_MODE` **DBフィーチャーフラグオーバーライド**（ダッシュボード → 設定 → フィーチャーフラグ） → `INJECTION_GUARD_MODE`環境 → `INPUT_SANITIZER_MODE`環境 → `warn`。ダッシュボードのオーバーライドは環境変数よりも優先されるため、フィーチャーフラグUIが実行中のガードをライブで制御します（再起動不要）。DBの読み取りはフェイルセーフです：エラーが発生した場合、ガードは環境ベースの動作にフォールバックし、オーバーライドが設定されていない場合の動作は環境のみの解決と同じです。

検出ソース：

1. `@/shared/utils/inputSanitizer`からの`sanitizeRequest()`（パイプラインの他の場所で使用される共有デテクタセット）。
2. ビルトインの`DEFAULT_GUARD_PATTERNS`（現在は`system_override_inline`と`markdown_system_block`、どちらも`high`重大度）。
3. コンストラクタオプションを介して渡されるオプションの`customPatterns`（文字列、正規表現、または`{ name, pattern, severity }`レコード）。

`mode === "block"` **かつ**少なくとも1つの検出が重大度閾値を満たす場合、`preCall`は`{ block: true, message: "リクエストが拒否されました：疑わしいコンテンツが検出されました" }`を返します。`warn`/`log`モードでは、ガードレールはログを記録しますが、呼び出しを許可します。共有ヘルパー`evaluatePromptInjection()`も、レジストリを通らずにプロンプトを評価する必要がある呼び出し元のためにエクスポートされています。

**スキャンバウンド（v3.8.20）：** デテクタは結合されたプロンプトテキストの**最初の16 KB**のみを検査します — `MAX_INJECTION_SCAN_BYTES = 16 * 1024`（16,384バイト）`src/shared/utils/inputSanitizer.ts`にあります。`detectInjection()`と`evaluatePromptInjection()`は、パターンループを実行する前に`slice(0, MAX_INJECTION_SCAN_BYTES)`を行います。インジェクション指令は入力の上部近くに位置するため、これは検出を弱めることなく、数百KBのペイロードに対する正規表現のCPU/GCを制限します（cf. #3932, #4041）。

### クレデンシャルマスカー (`credentialMasker.ts`)

**両方の**ステージで実行され、デフォルトチェーンの最後（優先度`95`）です。アウトバウンドペイロード（メッセージコンテンツ、ツール呼び出し引数、ツール結果）**および**プロバイダーのレスポンスから、よく知られたAPIキー/シークレットトークンパターンを赤外線処理します。これにより、プロンプトに貼り付けられたクレデンシャル（またはツール結果によってエコーされたもの）が上流のプロバイダーやクライアントに漏れないようにします。

- **オプトインのみ**、PIIの非表示と同じ規則（ハードルール#20隣接）：
  `settings.credentialRedactionEnabled === true` **または**
  `CREDENTIAL_REDACTION_ENABLED=true` の場合にのみ有効。無効にすると、ガードレールは何もしません —
  ブロックも書き換えも行いません。
- `redactCredentials()` は、全ペイロード/レスポンスツリーを走査します（`walkValue()`、
  プロトタイプ汚染に対して安全、`WeakSet`を介してサイクルに対して安全）、
  一致する部分を `[REDACTED:<type>]` プレースホルダーに置き換え、
  実際に変更されたブランチのみをクローンします。
- `CREDENTIAL_PATTERNS` は、LLMプロバイダーキー（OpenAI、OpenAI-proj、
  Anthropic、Google、Hugging Face、Replicate）、VCS/SaaSトークン（GitHub、Slack、
  Linear、Notion、npm、Postman、Discord）、支払いキー（Stripe、Square）、クラウド
  キー（AWSアクセスキー、Twilio、SendGrid、Mailgun）、プライベートキー / JWT、
  認証情報を含む接続文字列（`mongodb://user:pass@...` など）、および
  一般的な `Authorization`/`x-api-key`/`api-key`/`apikey` ヘッダー値
  パターンをカバーします。ヘッダー形式のキー（`authorization`、`x-api-key`、`api-key`、
  `apikey`）は、一般的なテキスト正規表現を介してではなく、構造的に（値のみ、スキームプレフィックス
  `Bearer `/`Basic ` は保持）非表示にされます。
- ガードレールは決してブロックしません；それは書き換え（`modifiedPayload` /
  `modifiedResponse`）と注釈（`meta.credentialsRedacted`、`meta.count`）のみを行います。

回帰ガード： `tests/unit/credential-masker-guardrail.test.ts`。

## 基底コントラクト (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true の場合、チェーンを即座に終了する
  message?: string; // ブロック時に通知される
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // リクエストを書き換えるために preCall から返される
  modifiedResponse?: TValue; // レスポンスを書き換えるために postCall から返される
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ガードレールは、`void`、`{}`、または `{ block: false }` のいずれかを返すことで「変更なし」を示します。`modifiedPayload`/`modifiedResponse` を返すと、チェーンを通って後続のガードレールに渡される値が置き換えられます。
`signal?: AbortSignal` は、呼び出し元のライフサイクルをガードレールに引き継ぎます。リクエストの中断は、意図的なフェイルオープンの例外です。メディアブリッジは処理を停止してクリーンアップを行い、未加工のメディアをサポートしないことが判明しているターゲットに、そのメディアを復元することはありません。

## レジストリ (`registry.ts`)

シングルトンの `guardrailRegistry` は、以下を公開します。

- `register(guardrail)` — ガードレールを追加（または正規化された名前に基づいて置換）し、`priority` の昇順で再ソートします。
- `clear()` / `list()` — 管理用のヘルパーです。
- `runPreCallHooks(payload, context)` — 有効なガードレールを反復処理し、`modifiedPayload` を介してペイロードを順次引き渡し、最初の `block: true` で停止します。
- `runPostCallHooks(response, context)` — レスポンス側で同じ処理を行います。
- `resetGuardrailsForTests({ registerDefaults })` — 状態をクリアし、必要に応じてデフォルトを再登録することで、テストをクリーンに分離します。

どちらのランナーも `{ blocked, payload|response, results, guardrail?, message? }` を返します。ここで `results` は、ガードレールごとの `blocked`、`skipped`、`modified`、`error`、`meta` フィールドを含む `GuardrailExecutionResult` レコードの配列であり、トレースに役立ちます。

### リクエストごとのガードレールの無効化

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` は、現在のリクエストでスキップすべきガードレール名を重複のないリストとして集約します。情報源は以下のとおりです（すべて任意であり、すべてマージされます）。

- `apiKeyInfo.disabledGuardrails`
- リクエスト本文の `disabledGuardrails`（トップレベル）
- リクエスト本文の `metadata.disabledGuardrails`
- ヘッダー `x-omniroute-disabled-guardrails`（またはレガシーの `x-disabled-guardrails`）

値には文字列の配列またはカンマ区切りの文字列を指定できます。名前は小文字のケバブケースに正規化されます（`pii_masker` → `pii-masker`）。結果は `context.disabledGuardrails` を介してレジストリに渡され、レジストリは一致するガードレールをスキップします（`results` 内で `skipped: true`）。

## 実行順序

`src/sse/handlers/chat.ts` および
`open-sse/handlers/chatCore.ts` を通過する各リクエストについて:

1. `resolveDisabledGuardrails(...)` は、API キー、ボディ、
   ヘッダーからスキップリストを構築します。
2. `guardrailRegistry.runPreCallHooks(body, ctx)` は、優先度の昇順で
   ガードレールを実行します:
   - 無効化されたガードレールは `skipped` として記録されます。
   - 各ガードレールの `preCall` は、`modifiedPayload` を介してペイロードを書き換える場合があります。
   - 最初の `block: true` によってチェーンが短絡され、ハンドラーは
     ガードレールによる拒否レスポンスを返します。
3. （書き換えられている可能性のある）ペイロードは、コンボルーティングとアップストリームへの
   ディスパッチに渡されます。
4. レスポンスの構築後、`guardrailRegistry.runPostCallHooks(...)`
   はレスポンスに対して同じチェーンを実行します。ここで `block: true` になると、アップストリームの
   レスポンスは破棄されます。

例外をスローしたガードレールは `error: <message>` として記録され、
`logger.warn` を介してログに記録されますが、チェーンは継続します。これは意図的なフェイルオープン設計です。

## 設定

組み込みガードレールが読み取る環境変数:

| 変数                                  | 使用元                           | 効果                                                                                                                          |
| ------------------------------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`               | 検出を完全に無効化するには `false` に設定します。                                                                             |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`               | インジェクションポリシー: `warn`、`block`、または `log`。従来の値 `redact` ではインジェクションテキストは書き換えられません。 |
| `INJECTION_GUARD_MODE`                | `prompt-injection`               | インジェクションガードのモード。環境変数を**上書きする** DB 機能フラグでもあります（DB > ENV）。                              |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`               | `MODE=block` が拒否する最小重大度: `high`（デフォルト）、`medium`、または `low`。                                             |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`               | `INPUT_SANITIZER_BLOCK_THRESHOLD` の従来のエイリアス。                                                                        |
| `PII_REDACTION_ENABLED`               | `pii-masker`                     | `true` の場合、リクエスト内の PII が秘匿化されます（インジェクションモードとは独立）。                                        |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker`（ダウンストリーム） | レスポンス側のマスカーの動作を制御します。                                                                                    |

Modality Bridge ガードレールは、環境変数ではなく、DB を基盤とする設定
ストア（`getSettings()`）からランタイム設定を読み取ります。Vision の主要キーは
`modalityBridgeVisionEnabled`、`modalityBridgeVisionMode`、
`modalityBridgeVisionModel`、`modalityBridgeVisionTaskAware`、
`modalityBridgeVisionPrompt`、`modalityBridgeVisionTimeout`、
`modalityBridgeVisionMaxImages`、`modalityBridgeVisionMaxChars`、
`modalityBridgeCacheEnabled`、`modalityBridgeCacheTtlMinutes`、および
`modalityBridgeCacheMaxEntries` です。従来の
`visionBridge*` キーは、文書化されている 1 サイクル限りの読み取り
フォールバックとしてのみ受け入れられます。ダッシュボードからの書き込みには主要キーが使用されます。デフォルト値とフォールバック
リゾルバーは `src/shared/constants/modalityBridgeDefaults.ts` にあり、従来の
定数は `src/shared/constants/visionBridgeDefaults.ts` に保持されています。

Audio は `modalityBridgeAudioEnabled`、`modalityBridgeAudioModel`、
`modalityBridgeAudioTimeout`、`modalityBridgeAudioMaxClips`、および共有の
`modalityBridgeCache*` 設定を使用します。これらのキーは Modality Bridge スキーマとともに
導入されたため、Audio には従来キーへのフォールバックはありません。

Video は `modalityBridgeVideoEnabled`、`modalityBridgeVideoAnalysisMode`、
`modalityBridgeVideoModel`、
`modalityBridgeVideoFrameCount`、`modalityBridgeVideoSamplingPolicy`、
`modalityBridgeVideoMaxVideos`、および
`modalityBridgeVideoTimeout` と、共有の `modalityBridgeCache*` 設定を使用します。
FFmpeg/ffprobe は任意の運用依存関係であり、
フレームのキャプション生成によってレイテンシとモデルコストが増加するため、デフォルトでは無効になっています。

## カスタムガードレール

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

手順:

1. `BaseGuardrail` を継承する `src/lib/guardrails/myGuardrail.ts` を作成します。
2. `preCall` および/または `postCall` を実装します。
3. インポート時に登録する（`registerDefaultGuardrails` から追加する）か、
   実行時に `guardrailRegistry.register(...)` を呼び出します。レジストリは、
   正規化された名前が同じ既存のガードレールを置き換えます。
4. `tests/unit/` 配下にテストを追加します（既存の例:
   `tests/unit/guardrails-registry.test.ts`、
   `tests/unit/prompt-injection-guard.test.ts`、
   `tests/unit/guardrails/visionBridge.test.ts`）。

## テスト

テスト間では `resetGuardrailsForTests()` を使用し、既知の状態から開始します。
空のレジストリから開始し、テスト対象のガードレールのみを登録するには、
`{ registerDefaults: false }` を渡します。Vision Bridge は依存性注入
（`deps.getSettings`、`deps.callVisionModel`）を受け付けます。Audio Bridge も、
設定、ケイパビリティ、STT モデル選択、認証情報チェック、文字起こしについて
同等の差し替えポイントを公開しています。そのため、テストでは DB や
ネットワークにアクセスせずに、両方のフローを実行できます。

## インジェクションガードのルートカバレッジとレッドチーム（フェーズ 8 · ブロック D）

インジェクションガード（`createInjectionGuard` / `withInjectionGuard`）は、ユーザープロンプトを
受け付けるすべてのルートを対象とします。`INJECTION_GUARD_MODE` に従って動作します（デフォルトの
`warn` = ログのみ、`block` = HTTP 400 `SECURITY_001` を返します）。

| 種類             | ルート                                                                                                                                               | デフォルトモード |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| テキスト（既存） | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn             |
| 生成系           | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn             |
| データ           | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn             |

テキスト抽出（`extractMessageContents`）は、`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` を対象とします。

**レッドチーム（夜間実行、`nightly-llm-security.yml`）:** promptfoo は、
`INJECTION_GUARD_MODE=block` で各ルートが OWASP-LLM コーパスをブロックすることを検証します。
garak はプローブを実行します（シークレットがない場合はスキップします）。
一貫性を保つため、`moderations` も対象に含まれています。ブロックモードの運用者は、
`resolveDisabledGuardrails` を使用してこれを除外できます。

夜間ワークフロー（`.github/workflows/nightly-llm-security.yml`、cron + 手動
ディスパッチ）には、次の 2 つのジョブがあります:

- **`promptfoo-guard`（ブロッキング）** — `INJECTION_GUARD_MODE=block` を指定して
  `promptfoo eval -c promptfooconfig.yaml` を実行します。各敵対的ケース（例:
  「以前の指示をすべて無視せよ…」、DAN 形式のジェイルブレイク）では、
  レスポンスに `error.code === "SECURITY_001"` が含まれること、つまりガードが
  実際にリクエストを拒否したことを検証します。
- **`garak`（参考情報）** — ローカルの OmniRoute インスタンス
  （`http://localhost:20128/v1`）に対して、garak
  `--probes promptinject,dan,leakreplay` を実行します。プロバイダーシークレット
  （`PROMPTFOO_PROVIDER_KEY`）の存在を条件とし、シークレットがない場合は問題なく
  スキップされます。また、末尾に `|| true` が付いているため、CI を失敗させずに
  結果を報告します。

ガードヘルパー（`createInjectionGuard` / `withInjectionGuard`）のカバレッジは、
プロンプトを受け取るすべての `/v1` ルートに及びます。プロンプトテキストは、
`src/shared/utils/inputSanitizer.ts` 内の `extractMessageContents()` によって、
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` から
抽出されます。
