> **Последнее обновление:** 2026-08-29 — v3.8.51 (Происхождение стенограммы Video Bridge объявляется вызывающей стороной,
> еще не проверено сервером — уточнено согласно #11661)

Защитные механизмы (guardrails) обеспечивают безопасность, соблюдение политик и преобразования контента на границе между OmniRoute и вышестоящими провайдерами. Каждый защитный механизм может проверять (и опционально отклонять, преобразовывать или аннотировать) полезные данные запросов (`preCall`) и ответы вышестоящих систем (`postCall`).

Система является **открытой при сбое (fail-open)**: если защитный механизм выдает ошибку во время выполнения, реестр записывает ошибку и продолжает работу со следующим защитным механизмом, вместо того чтобы отклонять запрос. Блокировка — это явное решение (`block: true`), а не случайность.

## Встроенные Ограничения

Реестр автоматически загружает шесть ограничений в порядке приоритета при импорте
(см. `registry.ts` → `registerDefaultGuardrails()`):

| Приоритет | Название            | Этап(ы)        | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |

### Vision Bridge (`visionBridge.ts`) — Мост Модальностей PR-1

Перехватывает запросы с изображениями, направленные на **немодальные модели**, и либо
перенаправляет весь запрос на модель, способную обрабатывать визуальные данные, либо заменяет части изображения текстовыми описаниями, созданными настраиваемой визуальной моделью, перед вызовом вверх по потоку. Это позволяет поставщикам, работающим только с текстом, прозрачно обрабатывать мультимодальные данные.

Поток:

1. Пропустить, если целевая модель уже поддерживает визуальные данные (если только она не указана в
   списке принудительных мостов `isVisionBridgeForcedModel`).
2. Извлечь части изображения с помощью `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), который делегирует задачу **унифицированному медиадетектору**
   `detectMediaParts()` в `open-sse/utils/mediaParts.ts` — единственному источнику правды, общему с фильтром совместимости.
   Извлечение разрешено только для верхних частей форматов,
   которые `replaceImageParts` может вставить обратно (контракт extract↔replace): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, и Responses API `input_image`. Вложенные попадания и
   формы только для индикаторов являются материалом для комбинированного фильтра и никогда не извлекаются.
   Пропустить, если ничего не найдено.
3. Разрешить настройки времени выполнения с помощью `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): новые ключи настроек `modalityBridge*`
   имеют приоритет; устаревшие ключи `visionBridge*` остаются **однократным
   резервным вариантом** (окно отката). Пропустить перед любым обходом медиа, когда
   мост отключен.
4. Выбор режима (`modalityBridgeVisionMode`, см. таблицу ниже) решает
   перенаправление или описание. Перенаправление возвращает `modifiedPayload` с замененным только `model`,
   плюс мета `{ rerouted, fromModel, toModel, imagesKept }`.
5. Путь описания: ограничить изображения до `maxImages`, составить задачу-осознанный запрос,
   проконсультироваться с кэшем описаний, вызвать визуальную модель **параллельно**
   (`Promise.allSettled`), и вставить текстовые части `[Image N]: <description>` на их место. Неудачное описание возвращает `null`, и оригинальная часть изображения
   **сохраняется** (#4012) — за исключением комбинированного пути описания, когда каждое
   описание не удалось, где подтвержденный не-визуальный источник получает
   `(unavailable — no vision-capable provider connected)` заглушку вместо этого (#8430).
6. Вернуть `modifiedPayload` + мета (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Выбор режима (`modalityBridgeVisionMode`)

| Режим      | По умолчанию | Поведение                                                                                                                                                                                                                                                                                                               |
| ---------- | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔            | Устаревшая эвристика, не тронутый (#6640/#7204): немодальные/`auto/` модели перенаправляют на лучшую визуальную модель, если у оригинальной модели нет используемых учетных данных (тогда описание); цели комбинирования всегда описываются.                                                                            |
| `describe` |              | Всегда описывать — блок перенаправления полностью пропускается; выбранная пользователем модель всегда отвечает.                                                                                                                                                                                                         |
| `reroute`  |              | Принудительное перенаправление: охрана модели с сохраненными учетными данными обходится. Охрана учетных данных для **цели** перенаправления все еще применяется — когда нет доступной визуальной цели, запрос переходит к описанию, так что необработанные изображения никогда не достигают текстового бэкенда (#8430). |

Принудительные режимы срабатывают **до** выполнения автоэвристики; поведение `auto`
идентично байт-коду предшествующего ограничения PR-1.

#### Область действия API-ключа (`visionBridgeKeyScope.ts`)

Когда API-ключ вызывающего ограничивает `allowedConnections`, пул квот
(`allowedQuotas`) или модели (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), мост выбирает только
перенаправляемые и описываемые модели, которые ключ может использовать, на соединениях, которые ключ может
использовать. Вызов описания всегда проходит через самопетлю OmniRoute с
заголовком `x-omniroute-self-loop-key-id`, так что получающий запрос чата
снова применяет политику соединения и модели этого ключа. `enforceApiKeyPolicy()`
уважает этот заголовок только вместе с носителем самопетли, так что он может только
сузить доступ, и идентификатор, который не разрешается, отклоняется.

Если для ключа не разрешена визуальная модель, путь описания отступает, и
запрос проходит без изменений, такое же поведение fail-open, как у отключенного
ограничения (мета `{ skipped: true, reason: "no_permitted_vision_model" }`).
Запросы без ключа и ключи без этих ограничений ведут себя точно так же, как и раньше.

#### Запрос на описание с учетом задачи (`modalityBridgeVisionTaskAware`)

По умолчанию **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) добавляет
текст **последнего сообщения пользователя** (усеченный до 500 символов) к базовому
запросу описания, направляя описание к тому, что на самом деле спросил пользователь
(шаблон codex-vision-proxy) и прося модель зрения транскрибировать видимый
текст. Если флаг выключен — или нет текста пользователя — используется неизмененный
базовый запрос.

Запрос самого цикла описания, совместимый с OpenAI (`callVisionModelSingle()`
в `visionBridgeHelpers.ts`), всегда запрашивает `image_url.detail: "high"` —
без условий, для каждого вызывающего/поставщика, не завися от какого-либо сигнала
клиента. Сэмплирование с низким разрешением ухудшает точность OCR для именно той
задачи транскрипции текста, которую запрашивает этот запрос, поэтому вызов
описания всегда запрашивает высокое разрешение, независимо от того, какой уровень
разрешения использовался в исходном входном запросе. Это влияет только на тело
внутреннего запроса описания; это не изменяет то, как OmniRoute передает
собственное `image_url.detail` вызывающего в основном запросе — этот параметр
применяется отдельно и только для обнаруженных клиентов OpenCode в
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Ветвь
формата wire-format Anthropic цикла описания не имеет поля `detail` и не
подвержена ни одному из значений по умолчанию.

#### Ограничение на выходные данные описания (`modalityBridgeVisionMaxChars`)

| Ключ                           | По умолчанию | Диапазон          |
| ------------------------------ | ------------ | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` или 100–50000 |

`0` (по умолчанию) означает **без ограничения** — описание, возвращаемое
`callVisionModel()`, передается без изменений, сохраняя существующее
поведение. Любое значение в диапазоне 100–50000 усечет описание с
суффиксом `…` перед тем, как оно будет вставлено обратно как
`[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` в `src/lib/guardrails/visionBridge.ts`).
Увеличьте это значение для задач OCR с большим количеством деталей, где
модель на выходе нуждается в полной транскрипции; уменьшите его, чтобы
ограничить использование токенов на разговорчивых моделях зрения.
Поле панели управления находится на вкладке Vision в расширенной панели
(`modality-bridge-max-chars` в `ModalityBridgeVisionTab.tsx`) и ограничивает
любое значение между 1 и 99 до нижнего предела 100, оставляя явное значение `0`
нетронутым — `0` является допустимым значением Zod само по себе
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто
"неустановленным" значением по умолчанию.

#### Кэш описания (`modalityBridge/bridgeCache.ts`)

Кэш LRU + TTL в памяти для выходных данных описания, общий для всего процесса.
Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` с
длина-префиксным фреймингом (без коллизий границ полей). Компонент модели —
это **сконфигурированная** модель моста, а не модель, которая на самом деле ответила —
`callVisionModel` может внутренне использовать резервные варианты, и ключевание
по каждой попытке фрагментировало бы кэш. Неудачные описания никогда не кэшируются. Настройки:

| Ключ                            | По умолчанию | Диапазон |
| ------------------------------- | ------------ | -------- |
| `modalityBridgeCacheEnabled`    | `true`       | —        |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000  |

#### Нормализация удаленного изображения (самоцикл описания/получение base64)

Когда мост сам получает **удаленное** изображение — самообращение описания
Anthropic и преобразование base64 формата claude-wire
(`ensureBase64ImagesForClaudeWire`), оба через
`fetchRemoteImageAsDataUri()` в `visionBridgeHelpers.ts` — полученный URI данных
проходит через `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) перед тем, как быть встроенным в запрос
модели зрения. Изображения, превышающие размер, уменьшаются до **2048px по длинной стороне**
(соответствует ограничению изменения размера, которое OpenAI/Anthropic уже
применяют на стороне сервера), что сокращает объем загружаемых байтов/задержку
без изменения того, что видит модель зрения. Изменение размера использует `sharp`,
загружаемый через динамический импорт: на платформе, где его нативный
бинарный файл не удается загрузить, `normalizeDataUri()` **никогда не выбрасывает**
исключение — он возвращается к передаче оригинальных байтов, так что путь
описания/преобразования base64 всегда продолжает работать. Небайтовые данные
(запрос, который не вернул декодируемое изображение) также передаются без изменений.
Эта нормализация ограничена изображениями, которые мост получает для своего
самообращения — она никогда не применяется к необработанному полезному
нагрузке вызывающего, что соответствует принципу мутации только по запросу
(Жесткое правило #20).

#### Схема настроек + миграция

Новые ключи `modalityBridge*` проверяются с помощью Zod в `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, трио `modalityBridgeCache*` и группа
`modalityBridgeAudio*`, используемая Audio Bridge. Миграция
`141_modality_bridge_settings.sql` копирует существующие устаревшие
значения `visionBridge*` в соответствующие новые ключи (идемпотентно, никогда не
перезаписывает установленное оператором значение `modalityBridge*`); устаревшие
ключи остаются принятыми в качестве резервного варианта чтения на один цикл
выпуска.

#### Заголовок прозрачности + статистика

Ответы, преобразованные с помощью описания, содержат
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(созданный `buildModalityBridgeHeader()` в `modalityBridge/bridgeStats.ts`,
отмеченный `withModalityBridgeHeader()` в `src/sse/handlers/chatHelpers.ts`).
Перенаправленные запросы не получают **никакого** заголовка — полезная нагрузка
осталась нетронутой, и замена модели уже видна в поле `model` тела ответа.

`GET /api/modality-bridge/stats` (управленческая аутентификация, тот же уровень, что и
`GET /api/settings`) возвращает счетчики в памяти по каждой модальности
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` и
`video`. `averageLatencyMs` использует `latencySamples`, а не все попытки, в качестве
знаменателя; операция без времени не создает образец с нулевой миллисекундой.
`bridged` остается обратнос совместимым псевдонимом для успешных
конверсий; неудачные попытки не увеличивают его.
Счетчики сбрасываются при перезапуске процесса по замыслу
(телеметрия, а не учет).

#### Конфигурация панели управления

Специальная страница панели управления находится по адресу
`/dashboard/settings/modality-bridge`. Ее URL-адресуемые вкладки `Vision`, `Audio`
и `Video` сохраняют параметры запроса при переключении значения `tab`.
Вкладка Vision предоставляет возможность включения, режим, выбор модели (включая автоматический
по умолчанию), осведомленное о задаче побуждение, расширенные ограничения по времени/изображению/длине описания/кэшу,
время выполнения
счетчики и защищенный запрос образца. Вкладка Audio также активна: она предоставляет
возможность включения, выбор модели только для STT с Auto, ограничения по времени/максимальной длительности клипа, аудио
счетчики и тест образца `input_audio`. Вкладка Video функциональна: она сообщает
о состоянии выполнения FFmpeg/ffprobe — одно из четырех явных состояний UI (`unknown`, пока
проба в пути или не может завершиться, `restricted` на хосте панели управления, не поддерживающем обратную связь, где проба пропускается на стороне клиента, `unavailable`, как только проба завершена и подтверждено отсутствие, или `available` с версиями FFmpeg/ffprobe) — сохраняет
ограничения включения/модели/кадра/видео/времени, фильтрует выбор модели для моделей, способных к визуализации,
и предоставляет аудио счетчики.

Бывшая карточка Vision Bridge в настройках ИИ является ссылкой на
новую страницу; она больше не содержит вторую копию формы. Поставщики медиа также
ссылаются на рабочие процессы Image-to-Text и Speech-to-Text в соответствующие вкладки Modality
Bridge, не удаляя существующую площадку Speech-to-Text.

**Обход допуска самопетли:** когда вызов describe проходит через
собственную самопетлю OmniRoute `/v1` (нестандартная модель провайдера), подзапрос отправляет
`x-omniroute-admission-bypass: internal` и аутентифицируется с разрешенной
учетной записью самопетли — локальным `sk_omniroute` в локальном режиме или
настроенным оператором `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env ключом (#1350), так что
развертывания с `REQUIRE_API_KEY=true` все еще могут выполнять вызов describe. Обход
признается только для этих точных учетных данных, поэтому внешние клиенты не могут использовать
заголовок для пропуска допуска.

Устаревшие значения по умолчанию находятся в `src/shared/constants/visionBridgeDefaults.ts`; новые значения по умолчанию для режима/задачи/кэша и разрешитель настроек находятся в
`src/shared/constants/modalityBridgeDefaults.ts`. Ограничение предоставляет
опцию конструктора `deps`, чтобы тесты могли внедрять поддельные реализации `getSettings` и
`callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехватывает запросы чата с аудио до того, как они достигнут цели, которая не
известна как принимающая аудиовход. Он никогда не перенаправляет запрос чата: аудиочасти
транскрибируются через существующую совместимую с OpenAI многокомпонентную конечную точку, и
выбранная модель чата продолжает с текстовыми транскрипциями.

Поток:

1. Разрешите `supportsAudio` через `getResolvedModelCapabilities()`. Явные
   метаданные реестра провайдеров имеют приоритет, затем статические метаданные модели, затем синхронизированные
   `modalities_input`. Объявленный список входов без `audio` равен `false`; отсутствие
   доказательств возможности остается `null`. И `false`, и `null` активируют
   консервативный мост, в то время как `true` обходит его.
2. Разрешите настройки `modalityBridgeAudio*` и извлеките сплайсируемые верхнеуровневые
   аудиочасти из каждого сообщения через общий детектор `detectMediaParts()`.
   Поддерживаемые формы проводов — это OpenAI `input_audio`, `audio_url` и
   `source.media_type: "audio/*"`. Вложенное аудио обнаруживается для маршрутизации, но не
   удаляется сплайс-путем. Работа ограничена `modalityBridgeAudioMaxClips`;
   последующие части остаются нетронутыми.
3. Уважайте настроенный `provider/model`, или позвольте `selectAudioBridgeModel()` пройти
   по `AUDIO_TRANSCRIPTION_PROVIDERS` в стабильном порядке каталога и выбрать первую
   модель с используемой активной учетной записью провайдера.
4. `callAudioTranscription()` преобразует аудио в формате base64/data-URI в многокомпонентный
   `file`, или загружает удаленный `audio_url` через только публичный исходящий
   защитник с привязкой DNS и ограничением в 25 МБ. Затем он отправляет файл и выбранную
   модель на локальную самопетлю `/v1/audio/transcriptions`, аутентифицированную с
   `resolveSelfLoopBearer()`. Существующий маршрут транскрипции выполняет обычный
   поиск учетных данных, обработку времени ожидания/лимитов и распределение провайдеров.
5. Успешные вызовы заменяют свои части на `[Audio N]: <transcript>`. Вызовы
   выполняются с `Promise.allSettled`: индивидуальная ошибка сохраняет оригинальную
   аудиочасть (#4012 контракт). Если каждый вызов завершается неудачей и цель оказывается
   `supportsAudio === false`, части становятся
   `[Audio N]: (недоступно — нет подключенного STT провайдера)` (#8430 контракт). Для
   неизвестной цели (`null`) результат с полными неудачами остается нетронутым. Доказанная
   цель только для текста без используемой учетной записи STT получает тот же явный
   заглушку без выполнения сетевого вызова.

Успешные транскрипции используют кэш LRU/TTL Modality Bridge на уровне процесса. Ключ
сочетает аудиоссылку, стабильную метку операции `audio-transcription` и выбранную модель STT; неудачи никогда не кэшируются. Попытки аудио обновляют
общие счетчики `bridged`, `cacheHits`, `failures` и `lastUsedAt`.
Преобразованные ответы содержат
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; нетронутые
запросы не получают сегмент Audio Bridge.

Настройки времени выполнения поддерживаются базой данных и проверяются с помощью Zod:

| Ключ                          | По умолчанию | Диапазон        |
| ----------------------------- | ------------ | --------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —               |
| `modalityBridgeAudioModel`    | `""`         | Auto или STT ID |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10            |

Общий кэш остается под контролем `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` и `modalityBridgeCacheMaxEntries`.

### Видеомост (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехватывает верхнеуровневые видео-части в Chat Completions `messages` и Responses
API `input` перед вызовом целевого элемента, у которого нет известной нативной поддержки видео.
Поддерживаемые форматы: `input_video`, `video_url`, `video_source`, HTTPS URL,
и `data:video/*;base64,...` data URI. Обычные имена файлов в тексте не рассматриваются
как видео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) отвечает за прохождение запроса, проверку
возможностей/политики, агрегацию по запросу и полезную нагрузку ответа.
Работа с видео — получение, кэширование всего результата, описание последовательности кадров
(которая объединяет любой аудиотронскрипт, объявленный вызывающим), и метрики/отмена/очистка
по каждой попытке — скрыта за `processVideoPart` в
`videoBridgePipeline.ts`, вызываемой один раз для каждой видео-части внутри цикла `preCall`.
Этот модуль также определяет явные границы портов `VideoMediaBrokerPort`
(получение байтов и извлечение выборочных кадров), `VideoAudioTranscriptionPort`
(объединение аудиотронскрипта, объявленного вызывающим, с выборочными подписями), и
`VideoDrilldownPort` (формат устаревшего сырого хранилища). Производственные STT и удержание кадров
составляются вокруг описывающего порта через `createVideoSttAdapter` и
`createVideoDrilldownAdapter`; последний использует общий жизненный цикл непрозрачной ручки.

Общий путь запроса `/v1` никогда не импортирует и не вызывает подсистему. Удаленные
видео загружаются с ограничением в 50 МиБ; встроенные base64 видео имеют
консервативный предел в 36 МиБ декодированного размера на видео, чтобы модель/сообщения/обрамление
могли оставаться внутри предела допуска JSON-запроса в 50 МиБ. Длина встроенных
и оценки декодированного размера проверяются перед выделением. HTTPS
требуется для начального удаленного URL и каждого перенаправления, используя существующий
только для публичного доступа защитный механизм с привязкой DNS. Затем байты пересекают
точную внутреннюю границу брокера `POST /api/modality-bridge/video/extract`. Этот маршрут является
как `LOCAL_ONLY`, так и `SPAWN_CAPABLE`, принимает только аутентифицированный запрос
в рамках процесса, доверенный обратный запрос, и никогда не принимает URL, путь к файловой системе,
исполняемый файл или список аргументов. Конвейер размера тела API и инкрементальный
чтение тела обработчика независимо обеспечивают предел входных данных брокера в 50 МиБ. Его ограниченная очередь
обрабатывает одно извлечение за раз, допускает четыре ожидающих задания и ограничивает ожидающий ввод до
100 МиБ.

Внутри брокера `ffprobe` читает частный локальный файл; фиксированный формат
включает в себя список разрешенных форматов, исключая плейлисты и манифесты. Для разрешенных контейнеров
семейства MOV внешние ссылки на данные MOV по умолчанию отключены, и фиксированная команда
не включает их. Как `ffprobe`, так и `ffmpeg` используют
только протокол `file`, один поток, фиксированные массивы аргументов, без оболочки,
и исполняемые файлы, разрешенные из `PATH`. Потоки с обложками прикрепленных изображений не
являются играбельными кандидатами. Все играбельные потоки должны удовлетворять ограничениям, и
явный поток по умолчанию предпочтителен перед детерминированным резервным вариантом с наименьшим индексом.
Видео ограничены 600 секундами, 8192 пикселями по размеру и
33,554,432 исходными пикселями. FFmpeg выбирает 1–16 промежуточных JPEG кадров, уменьшает
длинную сторону до максимум 1024 пикселей без увеличения меньших входов и
никогда не получает URL. Выборка по умолчанию является `uniform`. Опциональные
политики `scene_aware` и экспериментальная `segment_aware` выполняют один дополнительный
фиксированный проход FFmpeg по уже проверенному локальному потоку, выбирают ограниченные
временные метки сцен `showinfo`, и детерминированно возвращаются к тем же
однородным промежуточным точкам при сбое детектора, тайм-ауте, неправильно сформированном выводе или пустом
наборе кандидатов. Режим, учитывающий сегменты, выделяет промежуточные образцы пропорционально
проверенным временным интервалам сцен; доказательства, учитывающие сегменты, и поведение резервного копирования
подробно описаны ниже. Жесткий предел в 16 кадров применяется
после выбора в каждой политике. Когда запрос с учетом сцены имеет только
один кадр в бюджете, он использует однородную промежуточную точку активного полного видео или окна фокуса
и сообщает `policyEffective: uniform`: один выбранный кадр сцены
не может сохранить оба временных конца. Вызывающий может опционально предоставить
конечное окно фокуса (`start`/`end` секунды); границы ограничиваются длительностью медиа,
обратные или бесконечные окна отклоняются, и все политики выборки выполняются только внутри
нормализованного интервала. Результирующее окно включается в метаданные выборки и в ненадежный префикс описания,
чтобы последующие модели могли различать фокусированный фрагмент от полной временной линии.

Фокус семантических подписей является отдельной, явной настройкой. Режим анализа по умолчанию `full`
сохраняет существующий кадровый запрос и никогда не передает текст запроса модели подписей. В режиме `focused`
мост читает только последний непустой текст/ввод текста, созданный пользователем, из того же контейнера Chat или Responses,
нормализует его до NFC, сворачивает управляющие символы и пробелы,
и ограничивает его до 500 кодовых точек Unicode. Пустой результат возвращается к
точному запросу `full`. Полезная подсказка сериализуется как JSON в выделенном
блоке ненадежного пользовательского контекста и может только приоритизировать наблюдаемые детали; она
не может переопределить отдельное предупреждение против следования инструкциям, видимым
или слышимым в медиа. Текстовый фокус никогда не подразумевает `start`/`end` или не изменяет
временной выборщик.

#### Доказательства структурного сегмента FU-07

`segment_aware` использует один ограниченный предварительный анализ уже проверенного локального видеопотока. Фиксированная цепочка фильтров сначала масштабирует до максимум 320 пикселей в ширину, обнаруживает изменения сцены и замороженные интервалы, затем выбирает 1 кадр в секунду для размытия, среднего значения яркости и пространственной/временной информации. Проход ограничен 600 структурными образцами, одним потоком FFmpeg/filter, тем же протоколом и контейнерными белыми списками только для `file`, ограничением на выходные данные процесса в 1 МБ и максимум 30 секундами внутри общего прерывания/срока брокера. Он никогда не принимает команду, фильтр, путь или URL из запроса.

Структурные значения являются детерминированными доказательствами выборки, а не семантическим пониманием видео. Они не делают выводы о субъектах, действиях, подписях, речи или намерениях пользователя. Границы сцен и заморозки формируют сегменты; покрытие заморозки, размытие, экспозиция, пространственные детали и временные изменения лишь влияют на то, как распределяется существующий бюджет в 1–16 кадров. Полностью замороженный сегмент ограничен одним кадром, в то время как незамороженные сегменты конкурируют за оставшийся бюджет. Когда границы превышают количество кадров, сохраняется равномерное покрытие временной шкалы, чтобы быстрые ранние обрезки не могли скрыть длинный хвостовой сегмент. Границы сцен внутри разрешения анализа в 1 секунду границы заморозки объединяются.

Отсутствие фильтров, неправильно сформированные/пустые доказательства, ошибка детектора или ограниченное время предварительного анализа приводят к открытию в точной равномерной средней политике. Прерывание вызывающего или срок брокера не приводит к открытию: оно завершает текущий подпроцесс, предотвращает последующую выборку кадров, и временное дерево удаляется в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` генерирует детерминированные реальные фикстуры FFmpeg для экономии на вызовах подписей после дедупликации, распределения бюджета плотного движения, доказательств размытия/экспозиции/SI-TI, быстрых обрезок с длинным хвостом и ложных срабатываний при постепенном затухании. Он записывает время стенда анализа и, где доступно `/usr/bin/time`, использование CPU и пиковую RSS. Его проверки качества являются только структурными оракулами. Реальное качество модели подписей остается `HOLD`, потому что этот хранилище не имеет авторизованной конечной точки или замороженного судьи. Денежные сбережения также остаются `HOLD`, если `--caption-cost-per-call-usd` не предоставляет явную положительную оценку за вызов; скрипт никогда не фабрикует ни один из результатов.

Каждый кадр ограничен 4 МБ, все необработанные кадры вместе — 23 МБ, а сериализованный ответ брокера — 32 МБ. Временная директория удаляется в `finally`. OmniRoute не включает FFmpeg и не принимает пользовательский путь к исполняемому файлу. Перед подписыванием мост применяет консервативный проход визуальной дедупликации: каждый JPEG уменьшается до 16×16 градаций серого и сравнивается только с последним сохраненным кадром. Для запрашиваемого бюджета подписей выше одного кадра выборка предоставляет ограниченный пул кандидатов до двухкратного бюджета и никогда более 16 кадров. Запрашиваемый предел применяется только после дедупликации, при этом первые и последние выбранные кандидаты сохраняются во время окончательной тонкой настройки, когда бюджет составляет как минимум два. Версионированная политика `grayscale-16x16-mean-cells-v2` использует большее из среднего дельта яркости и соотношения ячеек миниатюр, чья нормализованная дельта составляет как минимум 0.05. Порог дубликатов составляет постоянное значение 0.04, выбранное для предсказуемости, а не выставленное в качестве параметра времени выполнения. Этот вторичный высококонтрастный сигнал сохраняет небольшие движения и изменения видимого текста, которые могут скрыть сравнение только по среднему значению. Ошибки компаратора или декодера открываются и сохраняют покрытие. Метаданные вывода разделяют извлеченные кандидаты, успешно использованные кадры и визуальные дубликаты, которые были отброшены.

Явно помеченная часть видео может запросить временную контактную таблицу. Мост строит максимум 4-колоночную, 16-кадровую сетку JPEG. Каждая ячейка размером 512 пикселей встраивает свой временной штамп в высококонтрастную нижнюю полосу, в то время как те же временные штампы остаются в текстовых метаданных для последующей ассоциации и аудита. Полный JPEG остается ограниченным 32 МБ. Если `sharp` не может декодировать или составить сетку, мост возвращается к отдельным кадрам JPEG; прерывание клиента все равно распространяется через операцию таблицы.

Доказательства продвижения намеренно отделены от синтетического микробенчмарка композиции. `scripts/perf/video-bridge-contact-sheet-eval.ts` определяет схему с версией A/B для реальных моделей зрения, совместимых с OpenAI. Он измеряет токены, сообщаемые поставщиком, задержку от начала до конца (включая составление таблицы), количество вызовов модели и сохранение фактов, определенных в манифесте. Сырые ответы модели не записываются в отчет; сохраняются только дайджесты SHA-256 и совпадающие идентификаторы фактов. Хранилище не делает сетевых или платных вызовов модели, если не передан `--execute-real` и не настроены `--model`, `OMNIROUTE_BASE_URL` и `OMNIROUTE_API_KEY`. Без этого явного реального запуска его читаемое машиной решение остается `HOLD`; измерения синтетической нагрузки/количества вызовов сами по себе не являются доказательством продвижения.

Отдельный `scripts/perf/video-bridge-promotion-eval.ts` обрабатывает наблюдения FU-07 или FU-09. Для допуска к продвижению требуется все восемь типов синтетических сценариев плюс очищенный реальный клип, как минимум три измеренные репетиции на роль и случай, все десять объявленных метрик, дайджесты замороженных медиа/подсказок/ожидаемых фактов/настроек, уникальные идентификаторы наблюдений и проверенный посев A/B порядок. Квитанция выполнения связывает дайджест корпуса, точный SHA кандидата и ревизию модели. Отсутствующие или недействительные измерения остаются `HOLD`, включая CPU выше 30 с, пиковую RSS выше 512 МБ или предварительный анализ выше 30 с. Это пределы допуска доказательств, а не новая гарантия соблюдения RSS во время выполнения.

FU-07 требует как минимум 98% сохранения качества и p95 задержки не более 1.2x
базового уровня, плюс либо 0.05 абсолютное улучшение сбалансированного среднего
вызова по отзывам при эквивалентных средних вызовах подписей, либо как минимум
10% меньше средних вызовов подписей после дедупликации. FU-09 требует как минимум
0.85 качества, 95% сохранения, 20% уменьшения задержки p95 и 10% уменьшения токенов.
Потеря критических фактов, несоответствие требованиям или отсутствие использования
предотвращает продвижение. Один запуск не может продвигать ничего:
`--previous-report` подтверждает два различных, неперекрывающихся, последовательно
допустимых запуска одного и того же политика/модель/ревизия/кандидат/корпус.
Эксперимент выборки не может подтвердить эксперимент контактной таблицы.

Сборщики должны оценивать ответы в памяти и сохранять `responseDigest` плюс
метрики и привязки наблюдений, никогда не текст ответа. Потребитель также читает
наследственные необработанные наблюдения, но никогда не копирует этот текст в свои
отчеты. Для каждого наблюдения принимается ровно одно из `responseDigest` или
`rawResponseText`. Версионированный белый список остается пустым с неизменяемым
значением по умолчанию `hold`. Допустимая запись требует ссылки на доказательства,
политики, ревизии модели, точного SHA кандидата, дайджеста манифеста и двух
различных идентификаторов запусков; конфликтующие контексты отклоняются. Эти
метаданные являются контрактом аудита, а не доказательством того, что
ссылающийся файл содержит подлинные измерения. Просмотрите фактические квитанции
прежде чем добавлять любую запись. Конечная точка статистики управления и
панель управления видео показывают консервативную готовность. Настроенное
псевдоним модели само по себе не устанавливает ее ревизию или
SHA текущего кандидата, поэтому текущая панель управления сообщает `HOLD`,
а не повторно использует допустимость из другого контекста выполнения. Явный
экспериментальный выбор остается отдельным от продвижения; никакое значение по
умолчанию не изменяется автоматически.

Вызывающие функции могут прикрепить необязательный массив `transcript.cues` к
поддерживаемой части видео, когда они уже имеют выровненный текст. Каждый
сигнал должен содержать `text`, конечный интервал `start`/`end` внутри
измеряемой продолжительности и разрешенный `source` (`client`, `embedded` или
`audio-bridge`); `confidence` по умолчанию равен `1` и должен оставаться
между `0` и `1`. Точные дубликаты сигналов объединяются. OmniRoute никогда не
начинает транскрипцию с этих метаданных: проверенные сигналы копируются в
описанный результат с источником, уверенностью и интервалом и отображаются как
недоверенные наблюдения наряду с подписями кадров. Неверный, вне диапазона или
без происхождения текст отклоняется, а не смешивается в поток подписей. Оба
канала транскрипции в теле запроса нормализуют предоставленное происхождение
до `client`, включая самопровозглашенные метки `embedded` или `audio-bridge`.
Только адаптер, принадлежащий серверу, может назначить эти доверенные метки
через аргумент только для кода `trustedSource`; поле JSON запроса не может
достигнуть этого аргумента. Текст транскрипции остается недоверенным
медиа-производным контентом, независимо от его происхождения, и никогда не
должен определять авторизацию.

Расширенный вызывающий может предоставить трек `audioTranscript` для того же
видео; он рассматривается как текст, предоставленный клиентом, а не доказательство
транскрипции сервера. Шов слияния запускает визуальные и аудио наблюдения
под одним сроком и сигналом прерывания, упорядочивает их на общей временной
линии, объединяет точные дубликаты и сообщает частичный результат, когда
успешна только одна сторона. Неверный `audioTranscript` ухудшается до этого
частичного результата — визуальное описание сохраняется, а аудио ветвь
регистрирует очищенный код ошибки — вместо того чтобы завершить все видео.
Доступность по ветвям, частичный флаг и очищенные коды ошибок сохраняются в
описанном результате, в метаданных защитных барьеров (`audioFusionRuns`/
`audioFusionPartials`/`audioFusionFailureCodes`), в метаданных кэша результата и
в счетчиках слияния моста. Путь по умолчанию Video Bridge не вызывает
преобразование речи в текст или загрузку второй копии медиа; без этого
явного трека он остается только видео.

**Сохранение транскрипции (#12150 P1).** Это применяется автоматически
всякий раз, когда Video Bridge (сам по себе по желанию) отображает сигнал
транскрипции — отдельного флага сохранения нет. Когда запрос отображает любой
сигнал транскрипции (объявленный вызывающим `transcript` или слитый
`audioTranscript`), защитный барьер помечает его как `videoBridgeObserved`
и создает редактированную тень описания видео — идентичное отображение, в
котором тело свободного текста каждого сигнала заменяется на
`[redacted-video-transcript]`, созданное путем замены структурированного
поля сигнала перед сборкой строки (никогда не путем разбора
упрощенного текста, так что никакое содержание сигнала — враждебное или
обычное, включая тела, содержащие `]`, такие как `[inaudible]`/`[music]`,
не может выжить). Сохраненный журнал вызовов меняет каждую часть текста,
произведенного видео, на эту редактированную тень, сопоставленную по
равенству содержания; якорь `fullText` считывается заново из завершенной
нагрузки защитного барьера перед вызовом, так что совпадение все еще
успешно после последующих защитных барьеров (маскировщики PII и
учетных данных, приоритеты 10/95) переписывают текст описания на месте и
после системного запроса/передачи/введения памяти изменяют массив сообщений.
Тело, отправленное вверх к модели, остается неизменным. Наблюдаемый запрос
также не заполняет долговременную память (как извлечение, основанное на
запросе, так и ответе, пропускаются), так что ответ модели не может
отразить текст транскрипции в памяти.

**Поля необработанного видео (#12430).** Когда мост включен, а нативная
поддержка видео неизвестна или отсутствует, определенные поля `transcript`/
`audioTranscript` также активируют `videoBridgeObserved`, даже после
неудачи описания или предела `maxVideos`. `null` и пустые строки
учитываются; отсутствующие поля и не-видео метаданные не учитываются.
Сохраненные копии редактируют эти поля или пропускают запрос, а кэши/
память обходятся. Нагрузка поставщика остается неизменной.

Дополнительные сохраненные копии используют тот же сигнал наблюдаемого запроса. Сырой снимок клиентского запроса до установки ограничений, ожидающий запрос в памяти и журнал ранее отклоненных запросов структурно заменяют поля транскрипта в частях видео; строковые подсказки, синтезированные этапами конвейера и передачей контекста, редактируются на уровне сохраненного тела запроса. Сохраненный маркер `video_content_removed` делает продолжение `previous_response_id` закрытым, а не восстанавливает текст, который был намеренно отброшен. Если наблюдаемый запрос теряет свою тень редактирования на уровне частей до записи в журнал, или даже одна из нескольких теней видео не совпадает после последующих мутаций запроса, сохраненное тело запроса полностью опускается вместо того, чтобы сохранять частично отредактированный транскрипт.

Для наблюдаемого запроса ответ модели может цитировать любую часть транскрипта без структурной границы подсказки. Поэтому его сохраненный журнал вызовов `responseBody` заменяется маркером пропуска; детальный артефакт конвейера (который может включать тела upstream/клиента и фрагменты потока) не сохраняется. Кэши семантики, идемпотентности и воспроизведения рассуждений обходят чтения и записи для этого запроса. Запрос провайдера и видимый клиенту ответ остаются без изменений. Ранние байты keepalive отводятся из временного буфера, когда детальный артефакт опускается. Предупреждение Kiro о неправильно сформированном EventStream сообщает только о количестве байтов полезной нагрузки, никогда о ее содержимом или сырой ошибке парсера JSON. Это не утверждает, что каждый несвязанный диагностический инструмент провайдера/плагина был проверен; более широкий обзор сохраненного слива отслеживается в #11658.

Внутренний жизненный цикл `/api/modality-bridge/video/drilldown` является отдельным кэш-субстратом с обратной связью/аутентификацией токенов. Каждая операция также требует канонического непрозрачного идентификатора принципала. Прежде чем производственный вызов будет разрешен, он должен получить этот идентификатор от аутентифицированного арендатора и никогда не должен пересылать выбранное клиентом значение. Ключи кэша связывают этого принципала с каноническими идентификаторами сессии и видео, хранят только их ключи, полученные из SHA-256, и ограничивают как чтения, так и удаление тем же принципалом. Кэш хранит не более 16 производных JPEG-кадров на запись, истекает через десять минут и поддерживает ограниченные чтения `start`/`end` или явное удаление сессии.

Каждый принципал ограничен 16 записями и 64 МиБ канонических JPEG-данных. Эти ограничения независимы от глобального потолка в 64 записи/256 МиБ: давление квоты принципала исключает только наименее используемые записи этого принципала, прежде чем будет рассмотрено глобальное удаление LRU. Истекшие записи удаляются как из учета принципала, так и из глобального учета при активности кэша, в то время как отмена и ошибка проверки не фиксируют частичную замену.

Кэш отклоняет неканонический Base64, избыточное заполнение, не-JPEG медиа, неправильно сформированные или усеченные JPEG и JPEG, которые вызывают предупреждение во время ограниченного полного декодирования изображения `sharp`. Он перекодирует каждое принятое изображение в канонический JPEG, получает ширину и высоту из декодированных байтов, вместо того чтобы доверять полям вызова, и отбрасывает любые завершающие полиглотные байты вместо того, чтобы сохранять их. Только ограниченный канонический сжатый буфер учитывается по обеим квотам. Лимит JSON по проводам включает накладные расходы Base64 для потолка декодированного ввода в 32 МиБ. Каждое сохраненное производное записывает свой проверенный формат/разрешение JPEG, политику выборки, версию производного, время создания, хэш содержимого, вычисленный сервером, и хэш родительской ссылки, а также хэш родительского содержимого доверенного вызова. Отмена проверяется между асинхронными фазами декодирования/хеширования перед атомарным коммитом кэша.

Производственный производитель повторно использует уже полученные кадры брокера только после успешного визуального анализа, без второго скачивания/извлечения видео. Он требует оператора `modalityBridgeVideoDrilldownEnabled=true`, строгого по частям `drilldown: true` и аутентифицированного идентификатора записи API-ключа. Объявленные клиентом значения принципала/сессии никогда не устанавливают право собственности. Без всех трех условий он не хеширует, не изменяет размер и не сохраняет дополнительные кадры. Неудача сохранения сохраняет используемый визуальный ответ. Запрошенные запросы обходят кэш результатов всего видео, поэтому кэшированные результаты никогда не воспроизводят обработчики.

Успешные ответы JSON и SSE раскрывают не более четырех непрозрачных обработчиков в ограниченном заголовке `x-omniroute-video-drilldown`. Авторизованные источники браузера могут читать этот заголовок, не расширяя политику CORS для источников. Новые обработчики используют `v1.<32-byte random base64url token>`, а реестр сохраняет только их хэши SHA-256. Читатель/парсер заголовков также принимает устаревшие 64-шестнадцатеричные токены. Аутентифицированный публичный потребитель — это `GET /api/v1/video-bridge/drilldown?handle=...`, независимо контролируемый `modalityBridgeVideoDrilldownRemoteEnabled=true`. Явное сохраненное ложное значение отменяет доступ, даже когда включен устаревший резервный вариант `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED`. Производственное сохранение имеет аналогичный устаревший резервный вариант `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED`. Оба резервных варианта по умолчанию выключены.

Потребитель получает право собственности от аутентифицированного ключа, применяет политику ключа и возвращает тот же 404 для неизвестных, истекших и других обработчиков ключей. Он принимает `variant=preview|standard|detail` (максимальное измерение JPEG 320/640/1280, никогда не увеличивается), `limit=1..8` (или устаревший псевдоним `frames`, никогда не оба), нулевой индекс `page` и необязательные секунды фокуса `start`/`end`. Дублирующие ключи запроса и перевернутые окна фокуса отклоняются. Каждый возвращаемый вариант имеет хэш своего фактического содержимого и метаданные фактического разрешения, связанные с сохраненным источником. Варианты производятся при чтении, а не хранятся как дополнительные сохраненные копии. Ответ JSON, включая Base64/конверт, ограничен 32 МиБ; слишком большой запрос возвращает 413, и клиент должен запросить меньше кадров. Чтения проверяют отмену вокруг каждого изменения размера и повторно проверяют действительность обработчика перед возвратом. `DELETE` владельцем является идемпотентным; удаление или истечение TTL освобождает сохраненный источник и учет использования.

Общий магазин локален для процесса: дескрипторы истекают при перезапуске и не могут быть переданы между независимыми процессами OmniRoute. Статистика управления показывает эффективную политику удержания/удаления и агрегирует только удерживаемые записи/байты, никогда не включая медиа, ссылки, идентификаторы принципалов или дескрипторы. Панель настроек видео отображает эти значения и может сохранять оба переключателя согласия. Эта документация по реализации не является доказательством развертывания или продвижения в реальной модели; принятие реальной модели отслеживается отдельно.

Кадры подписываются последовательно с использованием настроенной модели видео. Пустое переопределение видео наследует настройку Vision; если оба пустые, авто-маршрутизатор Vision выбирает эффективную модель, способную к визуализации. Успешные подписи заменяют оригинальную часть на стабильный префикс `[Video description:` , который также помечает текст как недоверяемое наблюдение, полученное из медиа, и сообщает последующим моделям не следовать инструкциям, найденным в медиа. Ключи кэша подписей кадров включают байты JPEG, подсказку, временную метку и эффективную модель; кэшируются только успешные подписи. Записи кэша сохраняют фактическую успешную модель производителя, включая резервную модель; мост сообщает `mixed`, когда разные кадры были произведены разными моделями. Попадание в кэш повторно использует эту идентичность производителя вместо того, чтобы переименовывать ее в запрашиваемый план маршрутизации. Кэш результатов всего видео ключируется на каждом входе, который изменяет выход — подсказка, эффективная модель, политика выборки, количество кадров, режим семантического анализа, SHA-256 отпечаток нормализованного подсказки фокуса, окно фокуса, `transcript`, `audioTranscript` и флаг контактной таблицы — поэтому изменение любого из этих параметров приводит к промаху кэша, никогда не к устаревшему повторному использованию. Версия политики визуального дедуплицирования, порог и ограниченное количество кандидатов на кадры также явно указаны в ключе кэша результатов и метаданных; следовательно, изменение политики не может повторно использовать устаревшее описание всего видео. Метаданные кэша результатов v4 сохраняют режим и отпечаток, никогда не сохраняя сырую задачу пользователя. Метаданные защитного барьера сообщают как запрашиваемые, так и эффективные режимы анализа; запрашиваемый режим `focused` без доступного текста пользователя сообщается как эффективно `full`.

Защитный барьер извлекает каждую поддерживаемую часть видео, но не описывает более чем `modalityBridgeVideoMaxVideos`. Для цели, доказанной как `supportsVideo === false`, неудачные и превышающие лимит видео становятся явными безопасными текстовыми маркерами, так что сырое видео не сохраняется. Когда возможности неизвестны, эти части остаются нетронутыми. Цели с `supportsVideo === true` обходят мост. Сигнал прерывания клиентского запроса распространяется через загрузку, очередь брокера, подпроцессы и вызовы подписей; прерывания останавливаются между видео и никогда не допускают открытого доступа к сырому медиа.

Настройки времени выполнения поддерживаются базой данных и проверяются с помощью Zod:

| Ключ                                | Значение по умолчанию | Диапазон / поведение                                                                                             |
| ----------------------------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`               | Необязательное время выполнения, по желанию                                                                      |
| `modalityBridgeVideoAnalysisMode`   | `"full"`              | `full` сохраняет общие подписи; `focused` использует ограниченный, недоверенный контекст последнего пользователя |
| `modalityBridgeVideoModel`          | `""`                  | Унаследовать модель Vision Bridge                                                                                |
| `modalityBridgeVideoFrameCount`     | `8`                   | 1–16                                                                                                             |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`           | `uniform`, `scene_aware` или пропорциональный `segment_aware`; сбой детектора возвращается к `uniform`           |
| `modalityBridgeVideoMaxVideos`      | `1`                   | 1–4                                                                                                              |
| `modalityBridgeVideoTimeout`        | `120000`              | 1000–120000 мс                                                                                                   |

Устаревшие сохраненные значения времени ожидания видео выше 120 секунд ограничиваются сроком брокера; новые записи настроек выше этого предела отклоняются. `GET /api/modality-bridge/video/runtime` требует доверенной локальности петли перед аутентификацией или проверкой времени выполнения, затем требует управления аутентификацией. Он возвращает только `available`, очищенные версии FFmpeg/ffprobe и фиксированную причину, когда время выполнения недоступно. Внутренний конечный пункт извлечения не является общедоступным API загрузки: насыщение очереди возвращает `503` плюс `Retry-After`, отключение вызывающего возвращает `499`, а фиксированный срок брокера возвращает `504`. Преобразованные ответы добавляют `video->text;model=<visionModel>;parts=<videos>` в центральный заголовок `x-omniroute-modality-bridge` без удаления сегментов Vision или Audio.

### Маска PII (`piiMasker.ts`)

Работает на **обоих** этапах.

- **`preCall`** клонирует полезную нагрузку, проходит по `system`, `messages`, `input` и `prompt` (включая простые строковые элементы) и применяет `processPII()` (из `@/shared/utils/inputSanitizer`) к строковым полям `content`/`text`. Когда `PII_REDACTION_ENABLED=true`, обнаруженные PII удаляются в исходящей полезной нагрузке. Это независимо от `INPUT_SANITIZER_MODE` (который контролирует только политику инъекции подсказок). Когда редактирование отключено, вызов фиксирует количество обнаружений без переписывания содержимого.
- **`postCall`** глубоко клонирует ответ, запускает `sanitizePIIResponse()` плюс маску формы API Ответов (`maskResponsesOutput` — охватывает `output_text` и `output[].content[].text`). Если происходит любое редактирование, измененный ответ заменяет оригинал.

Защитный барьер никогда не блокирует; он только аннотирует (`meta.detections`, `meta.redacted`) или переписывает.

### Инъекция подсказок (`promptInjection.ts`)

Обнаруживает враждебные структуры в пользовательском контенте и применяет
настроенную политику. Поведение определяется переменными окружения и параметрами конструктора:

| Настройка        | Переменная окружения                                                                                     | По умолчанию | Эффект                                                                                                                                                                                                  |
| ---------------- | -------------------------------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Включено         | `INPUT_SANITIZER_ENABLED`                                                                                | `true`       | Когда `false`, защитная система прекращает работу.                                                                                                                                                      |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                          | `warn`       | Политика инъекций: `block`, `warn` или `log`. (`redact` принимается для обратной совместимости, но **не** удаляет текст инъекции; запрос на редактирование PII контролируется `PII_REDACTION_ENABLED`.) |
| Порог блокировки | `blockThreshold` опция / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдоним `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | Минимальная серьезность, необходимая для блокировки. Средний уровень по умолчанию является только для наблюдения.                                                                                       |

**Приоритет режима** (`getMode`): параметры вызова `options.mode` →
`INJECTION_GUARD_MODE` **переопределение флага функции БД** (Панель управления → Настройки →
Флаги функций) → `INJECTION_GUARD_MODE` переменная окружения → `INPUT_SANITIZER_MODE` переменная окружения →
`warn`. Переопределение панели управления, таким образом, имеет приоритет над переменными окружения, поэтому интерфейс флагов функций управляет работой защитной системы в реальном времени (без перезапуска). Чтение из БД безопасно:
если возникает ошибка, защитная система возвращается к поведению на основе переменных окружения, и когда переопределение не установлено, поведение идентично разрешению только на основе переменных окружения.

Источники обнаружения:

1. `sanitizeRequest()` из `@/shared/utils/inputSanitizer` (общий детектор,
   используемый в других местах в конвейере).
2. Встроенные `DEFAULT_GUARD_PATTERNS` (в настоящее время `system_override_inline` и
   `markdown_system_block`, оба с серьезностью `high`).
3. Необязательные `customPatterns`, переданные через параметры конструктора (строки, регулярные выражения,
   или `{ name, pattern, severity }` записи).

Когда `mode === "block"` **и** по крайней мере одно обнаружение соответствует порогу
серьезности, `preCall` возвращает `{ block: true, message: "Запрос отклонен:
обнаружен подозрительный контент" }`. В режимах `warn`/`log` защитная система ведет журнал, но
разрешает вызов. Общий помощник `evaluatePromptInjection()` также экспортируется
для вызывающих, которым нужно оценить подсказки без обращения к реестру.

**Граница сканирования (v3.8.20):** детектор проверяет только **первые 16 КБ**
объединенного текста подсказки — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байта) в
`src/shared/utils/inputSanitizer.ts`. Как `detectInjection()`, так и
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском
цикла шаблонов. Директивы инъекции находятся в верхней части ввода, поэтому это
ограничивает использование ЦП/GC регулярных выражений на многокилобайтовых полезных нагрузках без ослабления обнаружения (сравните
#3932, #4041).

### Маскировщик учетных данных (`credentialMasker.ts`)

Работает на **обоих** этапах, последний в цепочке по умолчанию (приоритет `95`). Удаляет
известные шаблоны API-ключей / секретных токенов из исходящей полезной нагрузки (содержимое сообщения, аргументы вызова инструмента, результаты инструмента) **и** ответа провайдера, так что
учетные данные, вставленные в подсказку (или возвращенные результатом инструмента), не утечет
к upstream провайдеру или обратно к клиенту.

- **Только по желанию**, та же конвенция, что и для редактирования PII (Жесткое правило #20-соседнее):
  отключено, если `settings.credentialRedactionEnabled === true` **или**
  `CREDENTIAL_REDACTION_ENABLED=true`. При отключении защитная система не выполняет никаких действий —
  она никогда не блокирует и никогда не переписывает.
- `redactCredentials()` проходит по всему дереву полезной нагрузки/ответа (`walkValue()`,
  безопасно от загрязнения прототипа, безопасно от циклов через `WeakSet`) и заменяет совпадения на
  заполнитель `[REDACTED:<type>]`, клонируя только те ветви, которые действительно
  изменились.
- `CREDENTIAL_PATTERNS` охватывает ключи провайдеров LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токены VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платежные ключи (Stripe, Square), облачные
  ключи (AWS access key, Twilio, SendGrid, Mailgun), закрытые ключи / JWT,
  строки подключения с учетными данными (`mongodb://user:pass@...` и т.д.), и
  общий шаблон заголовка `Authorization`/`x-api-key`/`api-key`/`apikey`. Ключи в форме заголовка (`authorization`, `x-api-key`, `api-key`,
  `apikey`) маскируются структурно (только значение, префикс схемы, такой как
  `Bearer `/`Basic ` сохраняется) вместо использования общего текстового регулярного выражения.
- Защитная система никогда не блокирует; она только переписывает (`modifiedPayload` /
  `modifiedResponse`) и аннотирует (`meta.credentialsRedacted`, `meta.count`).

Регрессионная защита: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовый контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true прерывает цепочку
  message?: string; // выводится при блокировке
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // возвращается preCall для изменения запроса
  modifiedResponse?: TValue; // возвращается postCall для изменения ответа
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Гардуар сигнализирует о "без изменений", возвращая либо `void`, `{}`, или
`{ block: false }`. Возвращение `modifiedPayload`/`modifiedResponse` заменяет
значение, проходящее через цепочку для последующих гардуаров.
`signal?: AbortSignal` переносит жизненный цикл вызывающего в гардуары. Прерывание запроса — это преднамеренное исключение fail-open: медиаперекрытия прекращают работу и очищаются, не восстанавливая необработанные медиа в целевой объект, который, как известно, не поддерживает это.

## Реестр (`registry.ts`)

Синглтон `guardrailRegistry` предоставляет:

- `register(guardrail)` — добавляет (или заменяет по нормализованному имени) защитный механизм и
  повторно сортирует по возрастанию `priority`.
- `clear()` / `list()` — вспомогательные функции администрирования.
- `runPreCallHooks(payload, context)` — итерирует активные защитные механизмы, пропускает
  полезную нагрузку через `modifiedPayload` и останавливается на первом `block: true`.
- `runPostCallHooks(response, context)` — тот же поток на стороне ответа.
- `resetGuardrailsForTests({ registerDefaults })` — очищает состояние и опционально
  повторно регистрирует значения по умолчанию для чистой изоляции тестов.

Оба запускатора возвращают `{ blocked, payload|response, results, guardrail?, message? }`,
где `results` — это массив записей `GuardrailExecutionResult`, которые включают
поля `blocked`, `skipped`, `modified`, `error` и `meta` для каждого защитного механизма,
полезные для трассировки.

### Отключение защитных механизмов для каждого запроса

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегирует
дедуплицированный список имен защитных механизмов, которые должны быть пропущены для текущего
запроса. Источники (все опциональные, все объединенные):

- `apiKeyInfo.disabledGuardrails`
- Тело запроса `disabledGuardrails` (верхний уровень)
- Тело запроса `metadata.disabledGuardrails`
- Заголовок `x-omniroute-disabled-guardrails` (или устаревший
  `x-disabled-guardrails`)

Значения могут быть массивами строк или строкой, разделенной запятыми; имена
нормализуются в нижний регистр kebab-case (`pii_masker` → `pii-masker`). Результат
передается через `context.disabledGuardrails` в реестр, который пропускает
соответствующие защитные механизмы (`skipped: true` в `results`).

## Порядок выполнения

Для каждого запроса, проходящего через `src/sse/handlers/chat.ts` и
`open-sse/handlers/chatCore.ts`:

1.  `resolveDisabledGuardrails(...)` формирует список исключений из ключа API, тела запроса
    и заголовков.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` запускает защитные механизмы в порядке
    возрастания приоритета:
    - Отключенные защитные механизмы записываются как `skipped`.
    - Метод `preCall` каждого защитного механизма может переписывать полезную нагрузку через `modifiedPayload`.
    - Первый `block: true` прерывает цепочку, и обработчик возвращает
      ответ об отклонении защитным механизмом.
3.  (Потенциально переписанная) полезная нагрузка поступает в комбинированную маршрутизацию и
    диспетчеризацию вышестоящему сервису.
4.  После сборки ответа `guardrailRegistry.runPostCallHooks(...)`
    запускает ту же цепочку для ответа. `block: true` здесь отбрасывает
    ответ вышестоящего сервиса.

Защитные механизмы, которые выбрасывают исключения, записываются с `error: <message>` и
логируются через `logger.warn`, но цепочка продолжается — по замыслу, система
открыта к сбоям.

## Конфигурация

Переменные окружения, считываемые встроенными защитными механизмами:

| Переменная                            | Используется                  | Эффект                                                                                                                 |
| :------------------------------------ | :---------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`            | Установите `false`, чтобы полностью отключить обнаружение.                                                             |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`            | Политика инъекций: `warn`, `block` или `log`. Устаревшее значение `redact` не переписывает текст инъекции.             |
| `INJECTION_GUARD_MODE`                | `prompt-injection`            | Режим для защиты от инъекций; также флаг функции БД, который **переопределяет** переменные окружения (БД > ОКРУЖЕНИЕ). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`            | Минимальная серьезность, при которой `MODE=block` отклоняет: `high` (по умолчанию), `medium` или `low`.                |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`            | Устаревший псевдоним для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                            |
| `PII_REDACTION_ENABLED`               | `pii-masker`                  | Если `true`, PII запроса скрывается (независимо от режима инъекции).                                                   |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ниже по потоку) | Управляет поведением маскировщика на стороне ответа.                                                                   |

Защитные механизмы Modality Bridge считывают конфигурацию времени выполнения из хранилища настроек,
поддерживаемого БД (`getSettings()`), а не из переменных окружения. Основные ключи Vision:
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и
`modalityBridgeCacheMaxEntries`. Устаревшие ключи
`visionBridge*` принимаются только в качестве документированного одноциклового
резервного чтения; записи с панели управления используют основные ключи. Значения по умолчанию и
резервный резолвер находятся в `src/shared/constants/modalityBridgeDefaults.ts`,
при этом устаревшие константы сохранены в `src/shared/constants/visionBridgeDefaults.ts`.

Аудио использует `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` и `modalityBridgeAudioMaxClips`, а также общие
настройки `modalityBridgeCache*`. У Аудио нет резервного варианта для устаревших ключей,
поскольку эти ключи были введены со схемой Modality Bridge.

Видео использует `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` и
`modalityBridgeVideoTimeout`, а также общие настройки `modalityBridgeCache*`.
По умолчанию оно отключено, поскольку FFmpeg/ffprobe являются необязательными
операционными зависимостями, а создание подписей к кадрам увеличивает задержку и
стоимость модели.

## Пользовательские Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Шаги:

1.  Создайте `src/lib/guardrails/myGuardrail.ts`, расширяющий `BaseGuardrail`.
2.  Реализуйте `preCall` и/или `postCall`.
3.  Либо зарегистрируйте во время импорта (push из `registerDefaultGuardrails`), либо
    вызовите `guardrailRegistry.register(...)` во время выполнения — реестр заменяет
    любой предыдущий guardrail с тем же нормализованным именем.
4.  Добавьте тесты в `tests/unit/` (существующие примеры:
    `tests/unit/guardrails-registry.test.ts`,
    `tests/unit/prompt-injection-guard.test.ts`,
    `tests/unit/guardrails/visionBridge.test.ts`).

## Тестирование

Используйте `resetGuardrailsForTests()` между тестами, чтобы начать с известного состояния.
Передайте `{ registerDefaults: false }`, чтобы начать с пустого реестра и
зарегистрировать только тестируемые guardrails. Vision Bridge принимает внедрение зависимостей
(`deps.getSettings`, `deps.callVisionModel`); Audio Bridge предоставляет эквивалентные точки расширения
для настроек, возможностей, выбора модели STT, проверки учетных данных и транскрипции.
Таким образом, тесты могут проверять оба потока без доступа к БД или сети.

## Покрытие маршрутов защитой от инъекций и red-team (Фаза 8 · Блок D)

Защита от инъекций (`createInjectionGuard` / `withInjectionGuard`) охватывает все маршруты,
которые принимают пользовательские промпты. Она учитывает `INJECTION_GUARD_MODE` (по умолчанию `warn` = только логирование;
`block` = возвращает HTTP 400 `SECURITY_001`).

| Тип                  | Маршруты                                                                                                                                             | Режим по умолчанию |
| :------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------- |
| Текст (существующий) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn               |
| Генеративный         | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn               |
| Данные               | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn               |

Извлечение текста (`extractMessageContents`) охватывает `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team (ночной, `nightly-llm-security.yml`):** promptfoo проверяет, что каждый маршрут блокирует
корпус OWASP-LLM в режиме `INJECTION_GUARD_MODE=block`; garak запускает зонды (пропускает без секрета).
`moderations` включен для согласованности — операторы в режиме блокировки могут исключить его через
`resolveDisabledGuardrails`.

Ночной рабочий процесс (`.github/workflows/nightly-llm-security.yml`, cron + ручной
запуск) состоит из двух задач:

- **`promptfoo-guard` (блокирующий)** — запускает `promptfoo eval -c promptfooconfig.yaml`
  с `INJECTION_GUARD_MODE=block`. Каждый adversarial-кейс (например, "игнорировать все
  предыдущие инструкции...", джейлбрейки в стиле DAN) подтверждает, что ответ содержит
  `error.code === "SECURITY_001"`, то есть защита фактически отклонила запрос.
- **`garak` (консультативный)** — запускает garak `--probes promptinject,dan,leakreplay`
  против локального экземпляра OmniRoute (`http://localhost:20128/v1`). Ограничен
  секретом провайдера (`PROMPTFOO_PROVIDER_KEY`); корректно пропускается и имеет суффикс
  `|| true`, поэтому он сообщает о результатах, не приводя к сбою CI.

Покрытие вспомогательной функции защиты (`createInjectionGuard` / `withInjectionGuard`)
охватывает каждый маршрут `/v1`, содержащий промпты; текст промпта извлекается из
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` с помощью
`extractMessageContents()` в `src/shared/utils/inputSanitizer.ts`.
