> **مستند ماخذ:** `src/lib/guardrails/`
> **آخری تازہ کاری:** 2026-08-29 — v3.8.51 (Video Bridge ٹرانسکرپٹ کا ماخذ کالر کی جانب سے بیان کیا جاتا ہے،
> ابھی سرور سے تصدیق شدہ نہیں — #11661 کے مطابق وضاحت کی گئی)

Guardrails، OmniRoute اور اپ اسٹریم فراہم کنندگان کے درمیان حد پر حفاظت، پالیسی، اور مواد کی تبدیلیوں کو نافذ کرتے ہیں۔ ہر guardrail درخواست کے پے لوڈز (`preCall`) اور
اپ اسٹریم جوابات (`postCall`) کا معائنہ کر سکتا ہے (اور اختیاری طور پر انہیں مسترد، تبدیل، یا تشریح شدہ کر سکتا ہے)۔

سسٹم **fail-open** ہے: اگر عمل درآمد کے دوران کوئی guardrail استثنا پیدا کرے، تو رجسٹری
خرابی ریکارڈ کرتی ہے اور درخواست کو ناکام کرنے کے بجائے اگلے guardrail کے ساتھ جاری رہتی ہے۔
بلاک کرنا ایک واضح فیصلہ (`block: true`) ہے، کبھی بھی اتفاقی نتیجہ نہیں۔

## بلٹ ان گارڈریل

رجسٹری خود بخود چھ گارڈریل کو ترجیحی ترتیب میں لوڈ کرتی ہے جب درآمد کیا جاتا ہے
(دیکھیں `registry.ts` → `registerDefaultGuardrails()`):

| ترجیح | نام                 | مرحلہ(ات)      | فائل                  |
| ----- | ------------------- | -------------- | --------------------- |
| `5`   | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`   | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`   | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`  | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`  | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`  | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

کم ترجیحی نمبر **پہلے** چلتے ہیں۔

### وژن برج (`visionBridge.ts`) — موڈالیٹی برج PR-1

تصویر رکھنے والی درخواستوں کو **غیر وژن ماڈلز** کی طرف نشانہ بناتے ہوئے روکتا ہے اور یا تو
پورے درخواست کو ایک وژن قابل ماڈل کی طرف موڑ دیتا ہے یا تصویر
کے حصوں کو ایک قابل ترتیب وژن ماڈل کی طرف سے تیار کردہ متنی وضاحتوں سے بدل دیتا ہے
اوپر کی کال سے پہلے۔ یہ ٹیکسٹ صرف فراہم کرنے والوں کو شفاف طور پر
ملٹی موڈل پیلوڈز کو سنبھالنے کی اجازت دیتا ہے۔

پروسیس:

1. چھوڑ دیں اگر ہدف ماڈل پہلے ہی وژن کی حمایت کرتا ہے (جب تک کہ یہ
   فورسڈ برج کی فہرست `isVisionBridgeForcedModel` میں ظاہر نہ ہو)۔
2. تصویر کے حصے نکالیں `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`)، جو **متحدہ میڈیا
   ڈیٹیکٹر** `detectMediaParts()` کو `open-sse/utils/mediaParts.ts` میں منتقل کرتا ہے — یہ
   سچائی کا واحد ماخذ ہے جو کمبو مطابقت فلٹر کے ساتھ مشترک ہے۔
   نکالنا صرف اوپر کی سطح کے حصوں تک محدود ہے جنہیں
   `replaceImageParts` دوبارہ شامل کر سکتا ہے (نکالنے↔بدلنے کا معاہدہ): OpenAI
   `image_url`، Anthropic base64 `source.type:"base64"`، Anthropic URL
   `source.type:"url"`، اور Responses API `input_image`۔ نیسٹڈ ہٹس اور
   صرف اشارے والے اشکال کمبو فلٹر مواد ہیں اور کبھی بھی نہیں نکالی جاتی ہیں۔
   چھوڑ دیں اگر کچھ نہیں ملا۔
3. رن ٹائم کنفیگ کو حل کریں `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): نئے `modalityBridge*`
   سیٹنگز کی چابیاں جیتتی ہیں؛ وراثتی `visionBridge*` چابیاں ایک **ایک سائیکل
   فال بیک** (ریورس ونڈو) رہتی ہیں۔ جب پل غیر فعال ہو تو کسی بھی میڈیا کی گزرگاہ سے پہلے چھوڑ دیں۔
4. موڈ سلیکٹر (`modalityBridgeVisionMode`، نیچے جدول دیکھیں) فیصلہ کرتا ہے
   موڑنے بمقابلہ وضاحت۔ موڑنے سے `modifiedPayload` واپس آتا ہے جس میں صرف `model`
   تبدیل کیا گیا ہے، ساتھ ہی میٹا `{ rerouted, fromModel, toModel, imagesKept }`۔
5. وضاحت کا راستہ: تصاویر کو `maxImages` پر محدود کریں، کام سے آگاہ کرنے والا پرامپٹ بنائیں،
   وضاحت کی کیش سے مشورہ کریں، وژن ماڈل کو **پیرالل** میں کال کریں
   (`Promise.allSettled`)، اور `[Image N]: <description>` متنی حصے کو ان کی جگہ میں شامل کریں۔ ناکام وضاحت `null` دیتی ہے اور اصل تصویر کا حصہ **محفوظ** رہتا ہے (#4012) — سوائے کمبو وضاحت کے راستے کے جب ہر
   وضاحت ناکام ہو جاتی ہے، جہاں ایک تصدیق شدہ غیر وژن اوپر کی طرف
   `(unavailable — no vision-capable provider connected)` اسٹب ملتا ہے (#8430)۔
6. واپس کریں `modifiedPayload` + میٹا (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`)۔

#### موڈ سلیکٹر (`modalityBridgeVisionMode`)

| موڈ        | ڈیفالٹ | رویہ                                                                                                                                                                                                                                                            |
| ---------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔      | وراثتی ہیوریسٹک، بغیر تبدیلی (#6640/#7204): غیر کمبو/`auto/` ماڈلز بہترین وژن ماڈل کی طرف موڑ دیتے ہیں جب تک کہ اصل ماڈل کے پاس قابل استعمال اسناد نہ ہوں (پھر وضاحت کریں)؛ کمبو کے ہدف ہمیشہ وضاحت کرتے ہیں۔                                                   |
| `describe` |        | ہمیشہ وضاحت کریں — موڑنے کا بلاک مکمل طور پر چھوڑ دیا جاتا ہے؛ صارف کا منتخب کردہ ماڈل ہمیشہ جواب دیتا ہے۔                                                                                                                                                      |
| `reroute`  |        | زبردستی موڑنا: رکھیں-اسناد ماڈل گارڈ کو نظر انداز کیا جاتا ہے۔ موڑنے-**ہدف** کی اسناد گارڈ اب بھی لاگو ہوتی ہے — جب کوئی قابل استعمال وژن ہدف موجود نہ ہو تو درخواست وضاحت کی طرف گزر جاتی ہے تاکہ خام تصاویر کبھی بھی ٹیکسٹ صرف بیک اینڈ تک نہ پہنچیں (#8430)۔ |

مجبوری موڈز **پہلے** خودکار ہیوریسٹک چلنے سے پہلے مختصر سرکٹ کرتے ہیں؛ `auto` کا رویہ
پری-PR-1 گارڈریل کے ساتھ بائٹ میں ایک جیسا ہے۔

#### API-key دائرہ (`visionBridgeKeyScope.ts`)

جب کال کرنے والے کی API کلید `allowedConnections`، کوٹہ پولز
(`allowedQuotas`) یا ماڈلز (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) کو محدود کرتی ہے، تو پل صرف
موڑنے اور وضاحت کرنے والے ماڈلز کو منتخب کرتا ہے جنہیں کلید استعمال کر سکتی ہے، ان کنکشنز پر جنہیں کلید استعمال کر سکتی ہے۔ وضاحت کی کال پھر ہمیشہ OmniRoute خود لوپ کے ذریعے جاتی ہے جس میں
`x-omniroute-self-loop-key-id` ہیڈر ہوتا ہے، لہذا وصول کرنے والی چیٹ درخواست
اس کلید کے کنکشن اور ماڈل کی پالیسی کو دوبارہ نافذ کرتی ہے۔ `enforceApiKeyPolicy()`
صرف اس ہیڈر کو خود لوپ بیئرر کے ساتھ مل کر عزت دیتا ہے، لہذا یہ صرف
رسائی کو محدود کر سکتا ہے، اور ایک ID جو حل نہیں ہوتی ہے اسے مسترد کر دیا جاتا ہے۔

اگر کلید کے لیے کوئی وژن ماڈل کی اجازت نہیں ہے، تو وضاحت کا راستہ ایک طرف ہٹ جاتا ہے اور
درخواست بغیر تبدیلی کے گزر جاتی ہے، وہی ناکام-کھلا رویہ جیسے ایک غیر فعال
گارڈریل (میٹا `{ skipped: true, reason: "no_permitted_vision_model" }`)۔
بغیر کلید کی درخواستیں، اور ان کلیدوں کے بغیر جو ان پابندیوں کے بغیر ہیں، بالکل پہلے کی طرح برتاؤ کرتی ہیں۔

#### کام سے آگاہ وضاحت پرامپٹ (`modalityBridgeVisionTaskAware`)

ڈیفالٹ **true**۔ `composeVisionPrompt()` (`visionBridgeHelpers.ts`) **آخری صارف کے پیغام** کا متن (500 حروف تک محدود) بنیادی بیان کرنے والے پرامپٹ میں شامل کرتا ہے، جس سے وضاحت اس چیز کی طرف مڑ جاتی ہے جو صارف نے واقعی پوچھا (codex-vision-proxy پیٹرن) اور بصری ماڈل سے مرئی متن کی نقل کرنے کی درخواست کرتا ہے۔ جب یہ پرچم بند ہو — یا کوئی صارف کا متن نہ ہو — تو بنیادی پرامپٹ بغیر کسی تبدیلی کے استعمال ہوتا ہے۔

بیان کرنے والے خود لوپ کی اپنی OpenAI-ہم آہنگ درخواست (`callVisionModelSingle()` `visionBridgeHelpers.ts` میں) ہمیشہ `image_url.detail: "high"` کی درخواست کرتی ہے — بغیر کسی شرط کے، ہر کالر/فراہم کنندہ کے لیے، کسی بھی کلائنٹ سگنل پر نہیں۔ کم تفصیل کے نمونے OCR کی درستگی کو خراب کرتے ہیں بالکل اسی متن کی نقل کے کام کے لیے جس کی اس پرامپٹ میں درخواست کی گئی ہے، لہذا بیان کرنے والی کال ہمیشہ اعلی تفصیل کی درخواست کرتی ہے چاہے اصل آنے والی درخواست میں کس تفصیل کی سطح کا استعمال کیا گیا ہو۔ یہ صرف اندرونی بیان کرنے والی درخواست کے جسم کو متاثر کرتا ہے؛ یہ OmniRoute کے ذریعے کالر کے اپنے `image_url.detail` کو بنیادی درخواست پر آگے بڑھانے کے طریقے کو تبدیل نہیں کرتا — یہ ڈیفالٹ علیحدہ طور پر لاگو ہوتا ہے، اور صرف دریافت شدہ OpenCode کلائنٹس کے لیے، `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) میں۔ بیان کرنے والے خود لوپ کی Anthropic وائر-فارمیٹ شاخ میں کوئی `detail` فیلڈ نہیں ہے اور یہ کسی بھی ڈیفالٹ سے متاثر نہیں ہوتی۔

#### بیان کرنے والے آؤٹ پٹ کی حد (`modalityBridgeVisionMaxChars`)

| کلید                           | ڈیفالٹ | رینج             |
| ------------------------------ | ------ | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`    | `0` یا 100–50000 |

`0` (ڈیفالٹ) کا مطلب ہے **کوئی حد نہیں** — `callVisionModel()` کی طرف سے واپس کردہ وضاحت بغیر کسی تبدیلی کے گزر جاتی ہے، موجودہ رویے کو برقرار رکھتے ہوئے۔ 100–50000 کی رینج میں کوئی بھی قیمت وضاحت کو `…` لاحقہ کے ساتھ ٹرم کرتی ہے اس سے پہلے کہ اسے `[Image N]: <description>` کے طور پر دوبارہ جوڑا جائے (`VisionBridgeGuardrail.preCall()` `src/lib/guardrails/visionBridge.ts` میں)۔ اس کو تفصیل سے بھرپور OCR کے کاموں کے لیے بڑھائیں جہاں نیچے کی ماڈل کو مکمل نقل کی ضرورت ہوتی ہے؛ اسے چیٹ کرنے والے بصری ماڈلز پر ٹوکن کے استعمال کو محدود کرنے کے لیے کم کریں۔ ڈیش بورڈ کا میدان بصری ٹیب کے ایڈوانسڈ پینل پر موجود ہے (`modality-bridge-max-chars` `ModalityBridgeVisionTab.tsx` میں) اور کسی بھی قیمت کو 1 اور 99 کے درمیان 100 کی بنیاد تک محدود کرتا ہے جبکہ واضح `0` کو بغیر کسی تبدیلی کے چھوڑ دیتا ہے — `0` اپنے حق میں ایک درست Zod قیمت ہے (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`)، صرف "غیر سیٹ" ڈیفالٹ نہیں۔

#### بیان کرنے والا کیش (`modalityBridge/bridgeCache.ts`)

بیان کرنے والے آؤٹ پٹس کے لیے میموری میں LRU + TTL کیش، مشترکہ عمل کے وسیع۔ کلید = `sha256(imageRef + composedPrompt + configuredBridgeModel)` لمبائی-پری فریم کے ساتھ (کوئی فیلڈ-سرحدی تصادم نہیں)۔ ماڈل جزو **کنفیگر کردہ** پل ماڈل ہے، نہ کہ وہ ماڈل جو واقعی جواب دیتا ہے — `callVisionModel` اندرونی طور پر واپس جا سکتا ہے، اور ہر کوشش کے لیے کلید بنانا کیش کو ٹکڑے ٹکڑے کر دے گا۔ ناکام بیان کبھی بھی کیش نہیں ہوتے۔ ترتیبات:

| کلید                            | ڈیفالٹ | رینج    |
| ------------------------------- | ------ | ------- |
| `modalityBridgeCacheEnabled`    | `true` | —       |
| `modalityBridgeCacheTtlMinutes` | `60`   | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`  | 10–5000 |

#### دور دراز کی تصویر کی معمولی شکل (خود لوپ بیان/base64 fetch)

جب پل خود ایک **دور دراز** تصویر حاصل کرتا ہے — Anthropic بیان خود کال اور claude-wire-format base64 تبدیلی (`ensureBase64ImagesForClaudeWire`)، دونوں `fetchRemoteImageAsDataUri()` میں `visionBridgeHelpers.ts` کے ذریعے — نتیجے میں حاصل کردہ ڈیٹا URI `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) کے ذریعے گزر جاتا ہے اس سے پہلے کہ اسے بصری ماڈل کی درخواست میں شامل کیا جائے۔ زیادہ سائز کی تصاویر کو **2048px لمبی کنارے** پر کم کیا جاتا ہے (جو OpenAI/Anthropic پہلے ہی سرور سائیڈ پر لاگو کرتے ہیں)، جو اپ لوڈ بائٹس/لیٹنسی کو کم کرتا ہے بغیر اس کے کہ بصری ماڈل کو کیا نظر آتا ہے۔ دوبارہ سائز دینے کے لیے `sharp` کا استعمال کیا جاتا ہے، جو متحرک درآمد کے ذریعے لوڈ ہوتا ہے: ایک پلیٹ فارم پر جہاں اس کا مقامی بائنری لوڈ ہونے میں ناکام رہتا ہے، `normalizeDataUri()` **کبھی بھی پھینکتا نہیں** — یہ اصل بائٹس کے پاس تھرو پر واپس آتا ہے، لہذا بیان کرنے والا/base64-تبدیلی کا راستہ ہمیشہ کام کرتا رہتا ہے۔ غیر تصویری بائٹس (ایک fetch جو قابل ترجمہ تصویر واپس نہیں کرتا) بھی بغیر کسی تبدیلی کے گزر جاتے ہیں۔ یہ معمولی شکل ان تصاویر تک محدود ہے جو پل اپنی خود کال کے لیے حاصل کرتا ہے — یہ کبھی بھی کالر کے خام پاس تھرو پیلوڈ پر لاگو نہیں ہوتی، جو کہ صرف آپٹ ان تبدیلی کے اصول (Hard Rule #20) کے ساتھ ہم آہنگ ہے۔

#### ترتیبات کا خاکہ + ہجرت

نئے `modalityBridge*` کلیدیں `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts` میں) میں Zod کی توثیق کی گئی ہیں: `modalityBridgeVisionEnabled`، `modalityBridgeVisionMode`، `modalityBridgeVisionModel`، `modalityBridgeVisionTaskAware`، `modalityBridgeVisionPrompt`، `modalityBridgeVisionTimeout`، `modalityBridgeVisionMaxImages`، `modalityBridgeVisionMaxChars`، `modalityBridgeCache*` کا تین گنا، اور `modalityBridgeAudio*` گروپ جو آڈیو پل کے ذریعہ استعمال ہوتا ہے۔ ہجرت `141_modality_bridge_settings.sql` موجودہ وراثتی `visionBridge*` قیمتوں کو نئے متناسب کلیدوں میں کاپی کرتی ہے (idempotent، کبھی بھی ایک آپریٹر سیٹ `modalityBridge*` قیمت کو اوور رائٹ نہیں کرتی)؛ وراثتی کلیدیں ایک ریڈ فال بیک کے طور پر ایک ریلیز سائیکل کے لیے قبول کی جاتی رہتی ہیں۔

#### شفافیت ہیڈر + اعداد و شمار

بیان کردہ تبدیل شدہ جوابات میں `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` ہوتا ہے (جو `buildModalityBridgeHeader()` میں `modalityBridge/bridgeStats.ts` میں بنایا گیا ہے، `withModalityBridgeHeader()` میں `src/sse/handlers/chatHelpers.ts` میں مہر لگا ہوا ہے)۔ دوبارہ روٹ کی گئی درخواستوں میں **کوئی** ہیڈر نہیں ہوتا — پیلوڈ بغیر کسی تبدیلی کے تھا اور ماڈل کا تبادلہ پہلے ہی جواب کے جسم کے `model` فیلڈ میں نظر آتا ہے۔

`GET /api/modality-bridge/stats` (انتظامی توثیق، اسی سطح پر جیسے
`GET /api/settings`) میموری میں ہر موڈالٹی کے لئے کاؤنٹرز واپس کرتا ہے
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` کے لئے `vision`, `audio`, اور
`video`۔ `averageLatencyMs` `latencySamples` کا استعمال کرتا ہے، تمام کوششوں کا نہیں،
جیسا کہ اس کا مخرج؛ ایک آپریشن جس میں وقت نہیں ہوتا ایک صفر ملی سیکنڈ
نمونہ نہیں بناتا۔ `bridged` کامیاب تبدیلیوں کے لئے پیچھے کی طرف ہم آہنگ نام رہتا ہے؛ ناکام کوششیں اسے بڑھاتی نہیں ہیں۔
کاؤنٹرز ڈیزائن کے مطابق پروسیس دوبارہ شروع ہونے پر ری سیٹ ہوتے ہیں
(ٹیلی میٹری، اکاؤنٹنگ نہیں)۔

#### ڈیش بورڈ کی تشکیل

مخصوص ڈیش بورڈ صفحہ ہے
`/dashboard/settings/modality-bridge`۔ اس کا URL پتہ لگانے کے قابل `Vision`, `Audio`,
اور `Video` ٹیبز سوال کے پیرامیٹرز کو برقرار رکھتے ہیں جبکہ `tab` کی قیمت کو تبدیل کرتے ہیں۔
Vision ٹیب فعال کرنے، موڈ، ماڈل کے انتخاب (خودکار
ڈیفالٹ سمیت)، کام سے آگاہ پرامپٹنگ، جدید ٹائم آؤٹ/تصویر/تفصیل کی لمبائی/کیچ
حدود، رن ٹائم
کاؤنٹرز، اور ایک محفوظ نمونہ درخواست کو ظاہر کرتا ہے۔ Audio ٹیب بھی زندہ ہے: یہ
فعال کرنے، STT-صرف ماڈل چننے والے کے ساتھ خودکار، ٹائم آؤٹ/زیادہ سے زیادہ کلپ کی حدود، آڈیو
کاؤنٹرز، اور ایک `input_audio` نمونہ ٹیسٹ کو ظاہر کرتا ہے۔ Video ٹیب فعال ہے: یہ رپورٹ کرتا ہے
FFmpeg/ffprobe رن ٹائم کی حالت — چار واضح UI حالتوں میں سے ایک (`unknown` جب
پروب پرواز میں ہے یا مکمل نہیں ہو سکا، `restricted` ایک غیر لوپ بیک
ڈیش بورڈ میزبان پر جہاں پروب کلائنٹ سائیڈ پر چھوڑ دیا جاتا ہے، `unavailable` جب پروب کیا جاتا ہے
اور تصدیق شدہ غائب، یا `available` FFmpeg/ffprobe ورژن کے ساتھ) — برقرار رکھتا ہے
enable/model/frame/video/timeout کی حدود، ماڈل چننے والے کو وژن کے قابل
ماڈلز تک محدود کرتا ہے، اور ویڈیو کاؤنٹرز کو ظاہر کرتا ہے۔

AI سیٹنگز کے تحت سابقہ Vision Bridge کارڈ ایک ہم آہنگی کا لنک ہے
نئے صفحے کے لئے؛ یہ اب فارم کی دوسری کاپی کا مالک نہیں ہے۔ میڈیا فراہم کرنے والے بھی
تصویر سے متن اور تقریر سے متن کے ورک فلو کو متعلقہ موڈالٹی
Bridge ٹیبز سے جوڑتے ہیں بغیر موجودہ تقریر سے متن کے کھیل کے میدان کو ہٹائے۔

**سیلف لوپ داخلے کی بائی پاس:** جب بیان کرنے کی کال OmniRoute کے
اپنے `/v1` سیلف لوپ (غیر معیاری فراہم کنندہ ماڈل) کے ذریعے روٹ ہوتی ہے، تو ذیلی درخواست بھیجتی ہے
`x-omniroute-admission-bypass: internal` اور حل شدہ
سیلف لوپ اسناد کے ساتھ توثیق کی جاتی ہے — مقامی `sk_omniroute` سینٹینل مقامی موڈ میں، یا
آپریٹر کی تشکیل کردہ `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env کلید (#1350) تاکہ
`REQUIRE_API_KEY=true` تعیناتیاں اب بھی بیان کرنے کی کال چلا سکیں۔ یہ بائی پاس
صرف ان مخصوص اسناد کے لئے تسلیم کیا جاتا ہے، لہذا بیرونی کلائنٹس ہیڈر کا استعمال
کر کے داخلے کو چھوڑ نہیں سکتے۔

وراثتی ڈیفالٹس `src/shared/constants/visionBridgeDefaults.ts` میں موجود ہیں؛
نئے موڈ/کام سے آگاہ/کیچ ڈیفالٹس اور سیٹنگز ریزولور `src/shared/constants/modalityBridgeDefaults.ts` میں موجود ہیں۔ گارڈریل ایک
`deps` کنسٹرکٹر آپشن کو ظاہر کرتا ہے تاکہ ٹیسٹ جعلی `getSettings` اور
`callVisionModel` کے نفاذ کو داخل کر سکیں۔

### آڈیو برج (`audioBridge.ts`) — موڈالٹی برج PR-3

آڈیو رکھنے والی چیٹ درخواستوں کو ہدف پر پہنچنے سے پہلے روکتا ہے جو
آڈیو ان پٹ قبول کرنے کے لئے جانا جاتا نہیں ہے۔ یہ کبھی بھی چیٹ درخواست کو دوبارہ روٹ نہیں کرتا: آڈیو حصے
موجودہ OpenAI-ہم آہنگ ملٹی پارٹ اینڈ پوائنٹ کے ذریعے نقل کیے جاتے ہیں اور منتخب کردہ چیٹ ماڈل
متن کی نقل کے ساتھ جاری رہتا ہے۔

پروسیس:

1. `supportsAudio` کو `getResolvedModelCapabilities()` کے ذریعے حل کریں۔ واضح
   فراہم کنندہ-رجسٹری میٹا ڈیٹا جیتتا ہے، پھر سٹیٹک ماڈل میٹا ڈیٹا، پھر ہم آہنگ
   `modalities_input`۔ بغیر `audio` کے ایک اعلان کردہ ان پٹ کی فہرست `false` ہے؛ کوئی
   صلاحیت کا ثبوت `null` رہتا ہے۔ دونوں `false` اور `null` محتاط برج کو فعال کرتے ہیں، جبکہ `true` اسے بائی پاس کرتا ہے۔
2. `modalityBridgeAudio*` سیٹنگز کو حل کریں اور ہر پیغام سے اسپلیسیبل ٹاپ لیول
   آڈیو حصے نکالیں `detectMediaParts()` مشترکہ
   ڈیٹیکٹر کے ذریعے۔ سپورٹ کردہ وائر شکلیں OpenAI `input_audio`, `audio_url`, اور
   `source.media_type: "audio/*"` ہیں۔ نیسٹڈ آڈیو روٹنگ کے لئے پتہ لگایا جاتا ہے لیکن
   اسپلیس راستے سے ہٹا نہیں جاتا۔ کام `modalityBridgeAudioMaxClips` سے محدود ہے؛
   بعد کے حصے بغیر تبدیلی رہتے ہیں۔
3. ایک تشکیل شدہ `provider/model` کی عزت کریں، یا `selectAudioBridgeModel()` کو چلنے دیں
   `AUDIO_TRANSCRIPTION_PROVIDERS` کو مستحکم کیٹلاگ کے ترتیب میں چلنے دیں اور پہلے
   ماڈل کو منتخب کریں جس کے پاس قابل استعمال فعال فراہم کنندہ کی اسناد ہوں۔
4. `callAudioTranscription()` base64/data-URI آڈیو کو ایک ملٹی پارٹ
   `file` میں تبدیل کرتا ہے، یا عوامی صرف آؤٹ باؤنڈ
   گارڈ کے ذریعے DNS پننگ اور 25 MB کی حد کے ساتھ ایک دور دراز `audio_url` ڈاؤن لوڈ کرتا ہے۔ پھر یہ فائل اور منتخب
   ماڈل کو مقامی `/v1/audio/transcriptions` سیلف لوپ پر POST کرتا ہے، جس کی توثیق
   `resolveSelfLoopBearer()` کے ساتھ کی جاتی ہے۔ موجودہ نقل کا راستہ معمول کے
   اسناد کی تلاش، کول ڈاؤن/ریٹ-حد کی ہینڈلنگ، اور فراہم کنندہ کی تقسیم کرتا ہے۔
5. کامیاب کالیں اپنے حصے کو `[Audio N]: <transcript>` سے تبدیل کرتی ہیں۔ کالیں
   `Promise.allSettled` کے ساتھ چلتی ہیں: ایک انفرادی ناکامی اس اصل
   آڈیو حصے کو محفوظ رکھتی ہے (#4012 معاہدہ)۔ اگر ہر کال ناکام ہو جاتی ہے اور ہدف ثابت ہوتا ہے
   `supportsAudio === false`، تو حصے بن جاتے ہیں
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 معاہدہ)۔ ایک نامعلوم ہدف (`null`) کے لئے، ایک تمام ناکامی کا نتیجہ بغیر تبدیلی رہتا ہے۔ ایک ثابت شدہ
   متن-صرف ہدف جس کے پاس کوئی قابل استعمال STT اسناد نہیں ہے وہ اسی واضح
   اسٹب کو حاصل کرتا ہے بغیر نیٹ ورک کال جاری کیے۔

کامیاب نقلیں پروسیس کی سطح پر موڈالٹی برج LRU/TTL کیش کا استعمال کرتی ہیں۔ کلید آڈیو حوالہ، مستحکم `audio-transcription` آپریشن
لیبل، اور منتخب STT ماڈل کو ملا کر بنتی ہے؛ ناکامیاں کبھی بھی کیش نہیں کی جاتیں۔ آڈیو کوششیں مشترکہ `bridged`, `cacheHits`, `failures`, اور `lastUsedAt` کاؤنٹرز کو اپ ڈیٹ کرتی ہیں۔
تبدیل شدہ جوابات لے کر آتے ہیں
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`؛ بغیر تبدیلی کی درخواستیں آڈیو برج کے حصے کو نہیں حاصل کرتی ہیں۔

رن ٹائم سیٹنگز DB سے منسلک ہیں اور Zod کی توثیق شدہ ہیں:

| کلید                          | ڈیفالٹ  | رینج             |
| ----------------------------- | ------- | ---------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —                |
| `modalityBridgeAudioModel`    | `""`    | خودکار یا STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000      |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10             |

شیئرڈ کیش `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, اور `modalityBridgeCacheMaxEntries` کے ذریعے کنٹرول کیا جاتا ہے۔

### ویڈیو برج (`videoBridge.ts`, `videoBridgePipeline.ts`)

چیٹ کمپلیشنز `messages` اور جوابات API `input` میں ہدف سے پہلے اعلیٰ سطح کے ویڈیو حصوں کو روکتا ہے جس کے پاس معلوم مقامی ویڈیو سپورٹ نہیں ہے۔ سپورٹ کردہ شکلیں `input_video`, `video_url`, `video_source`, HTTPS URLs,
اور `data:video/*;base64,...` ڈیٹا URI ہیں۔ ٹیکسٹ میں سادہ فائل کے نام کو ویڈیو کے طور پر نہیں لیا جاتا۔

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) درخواست کی عبور، قابلیت/پالیسی چیک، فی درخواست جمع کرنا، اور جواب کا پیلوڈ سنبھالتا ہے۔ فی ویڈیو کام — حصول، مکمل نتیجہ کیش، ایک فریم کی ترتیب کی وضاحت (جو کسی بھی کالر کے اعلان کردہ آڈیو ٹرانسکرپٹ کو ضم کرتا ہے)، اور فی کوشش میٹرکس/منسوخی/صفائی — `processVideoPart` کے پیچھے چھپا ہوا ہے جو `videoBridgePipeline.ts` میں ہے، جو `preCall` کے لوپ کے اندر ہر ویڈیو حصے کے لیے ایک بار کال کیا جاتا ہے۔ یہ ماڈیول واضح پورٹ کی سرحدیں بھی متعین کرتا ہے `VideoMediaBrokerPort`
(بائٹس حاصل کرنا اور نمونہ شدہ فریم نکالنا)، `VideoAudioTranscriptionPort`
(کالر کے اعلان کردہ آڈیو ٹرانسکرپٹ کو نمونہ شدہ کیپشنز کے ساتھ ضم کرنا)، اور
`VideoDrilldownPort` (ماضی کی خام اسٹور شکل)۔ پروڈکشن STT اور فریم برقرار رکھنے
کی وضاحت کرنے والے پورٹ کے گرد `createVideoSttAdapter` اور
`createVideoDrilldownAdapter` کے ذریعے کی گئی ہے؛ آخری مشترکہ غیر شفاف ہینڈل کی زندگی کے چکر کا استعمال کرتا ہے۔

عوامی `/v1` درخواست کا راستہ کبھی بھی کسی ذیلی عمل کو درآمد یا متحرک نہیں کرتا۔ دور دراز ویڈیوز 50 MiB کی حد کے تحت ڈاؤن لوڈ کی جاتی ہیں؛ ان لائن بیس64 ویڈیوز میں ایک محتاط 36 MiB کی ڈی کوڈ شدہ فی ویڈیو کیپ ہے تاکہ ماڈل/پیغامات/فریمنگ لفافہ عوامی JSON درخواست کی داخلہ حد 50 MiB کے اندر رہ سکے۔ ان لائن لمبائی اور ڈی کوڈ شدہ سائز کے تخمینے مختص کرنے سے پہلے چیک کیے جاتے ہیں۔ HTTPS ابتدائی دور دراز URL اور ہر ری ڈائریکٹ پر درکار ہے، موجودہ عوامی صرف آؤٹ باؤنڈ گارڈ کے ساتھ DNS پننگ کا استعمال کرتے ہوئے۔ بائٹس پھر بالکل اندرونی
`POST /api/modality-bridge/video/extract` بروکر کی سرحد کو عبور کرتے ہیں۔ یہ راستہ دونوں
`LOCAL_ONLY` اور `SPAWN_CAPABLE` ہے، صرف فی عمل کی تصدیق شدہ،
معتبر لوپ بیک درخواست کو قبول کرتا ہے، اور کبھی بھی URL، فائل سسٹم کا راستہ، قابل عمل،
یا دلیل کی فہرست کو قبول نہیں کرتا۔ API باڈی سائز پائپ لائن اور ہینڈلر کا انکریمنٹل باڈی
ریڈر آزادانہ طور پر 50 MiB بروکر ان پٹ کیپ کو نافذ کرتا ہے۔ اس کی حد بند قطار ایک وقت میں ایک نکاسی کو چلاتی ہے، چار زیر التواء ملازمتوں کی اجازت دیتی ہے، اور زیر التواء ان پٹ کو 100 MiB پر کیپ کرتی ہے۔

بروکر کے اندر، `ffprobe` ایک نجی مقامی فائل کو پڑھتا ہے؛ مقررہ شکل
کی اجازت کی فہرست پلے لسٹ اور مینیفیسٹ فارمیٹس کو خارج کرتی ہے۔ اجازت یافتہ MOV-خاندان
کے کنٹینرز کے لیے، بیرونی MOV ڈیٹا حوالہ جات بطور ڈیفالٹ غیر فعال رہتے ہیں، اور مقررہ کمانڈ ان میں شامل نہیں ہوتی۔ دونوں `ffprobe` اور `ffmpeg` استعمال کرتے ہیں
`file`-صرف پروٹوکول وائٹ لسٹ، ایک دھاگہ، مقررہ دلیل کی صفیں، کوئی شیل،
اور `PATH` سے حل شدہ قابل عمل۔ منسلک تصویر کے کور اسٹریمز قابل کھیل امیدوار نہیں ہیں۔ تمام قابل کھیل اسٹریمز کو حدود کو پورا کرنا چاہیے، اور ایک واضح ڈیفالٹ اسٹریم کو ترجیح دی جاتی ہے اس سے پہلے کہ متعین کم از کم انڈیکس کی فالس بیک۔ ویڈیوز کی لمبائی 600 سیکنڈ، 8,192 پکسلز فی جہت، اور
33,554,432 ماخذ پکسلز تک محدود ہیں۔ FFmpeg 1–16 درمیانی JPEG فریموں کا نمونہ لیتا ہے، طویل کنارے کو زیادہ سے زیادہ 1,024 پکسلز تک کم کرتا ہے بغیر چھوٹے ان پٹ کو اپ اسکیل کیے، اور کبھی بھی URL نہیں لیتا۔ نمونہ لینا بطور ڈیفالٹ `uniform` ہے۔ اختیاری
`scene_aware` اور تجرباتی `segment_aware` پالیسیاں پہلے سے تصدیق شدہ مقامی اسٹریم پر ایک اضافی مقررہ FFmpeg پاس انجام دیتی ہیں، محدود `showinfo` منظر کے وقت کی مہریں منتخب کرتی ہیں، اور متعین ناکامی، وقت ختم ہونے، خراب آؤٹ پٹ، یا خالی امیدوار سیٹ پر متعین طور پر اسی
یونیفارم درمیانی نقطوں پر واپس آتی ہیں۔ سیگمنٹ-آویر موڈ تصدیق شدہ منظر کے وقفوں کے تناسب سے درمیانی نمونہ مختص کرتا ہے؛ سیگمنٹ-آویر ثبوت اور فالس بیک رویے کی تفصیلات نیچے دی گئی ہیں۔ سخت 16-فریم کیپ ہر پالیسی میں انتخاب کے بعد لاگو ہوتی ہے۔ جب ایک منظر-آویر درخواست کے پاس صرف ایک فریم کا بجٹ ہوتا ہے، تو یہ فعال مکمل ویڈیو یا توجہ کی ونڈو کے یونیفارم درمیانی نقطے کا استعمال کرتی ہے اور `policyEffective: uniform` کی رپورٹ کرتی ہے: ایک منتخب منظر کا فریم دونوں وقتی انتہاؤں کو محفوظ نہیں رکھ سکتا۔ ایک کالر اختیاری طور پر ایک محدود توجہ کی ونڈو (`start`/`end` سیکنڈ) فراہم کر سکتا ہے؛ حدود میڈیا کی مدت پر لگائی جاتی ہیں، الٹی یا غیر محدود ونڈوز کو مسترد کیا جاتا ہے، اور تمام نمونہ لینے کی پالیسیاں صرف معیاری وقفے کے اندر انجام دی جاتی ہیں۔ نتیجے میں آنے والی ونڈو نمونہ لینے کے میٹا ڈیٹا اور غیر معتبر وضاحت کے پیشگی میں شامل کی جاتی ہے تاکہ نیچے کی طرف ماڈلز ایک توجہ دی گئی اقتباس کو مکمل ٹائم لائن سے ممتاز کر سکیں۔

سمیٹک کیپشن توجہ ایک علیحدہ، واضح سیٹنگ ہے۔ ڈیفالٹ `full`
تجزیاتی موڈ موجودہ فریم پرامپٹ کو محفوظ رکھتا ہے اور کبھی بھی درخواست کے متن کو کیپشن ماڈل کو آگے نہیں بڑھاتا۔ `focused` موڈ میں، برج صرف تازہ ترین غیر خالی صارف کے تخلیق کردہ `text`/`input_text` کو اسی چیٹ یا جوابات کے کنٹینر سے پڑھتا ہے، اسے NFC میں معیاری بناتا ہے، کنٹرول کرداروں اور خالی جگہوں کو کم کرتا ہے،
اور اسے 500 Unicode کوڈ پوائنٹس تک محدود کرتا ہے۔ ایک خالی نتیجہ بالکل `full` پرامپٹ پر واپس آتا ہے۔ ایک قابل استعمال اشارہ ایک مخصوص غیر معتبر صارف کے سیاق و سباق کے بلاک میں JSON کے طور پر سیریلائز کیا جاتا ہے اور صرف قابل مشاہدہ تفصیلات کو ترجیح دے سکتا ہے؛ یہ میڈیا میں نظر آنے یا سننے میں ہدایات کی پیروی کے خلاف علیحدہ انتباہ کو ختم نہیں کر سکتا۔ متنی توجہ کبھی بھی `start`/`end` کا استنباط نہیں کرتی یا وقتی نمونہ لینے والے کو تبدیل نہیں کرتی۔

#### FU-07 ساختی سیگمنٹ ثبوت

`segment_aware` پہلے سے تصدیق شدہ مقامی ویڈیو اسٹریم پر ایک محدود پیش تجزیاتی پاس استعمال کرتا ہے۔ مقررہ فلٹر چین پہلے زیادہ سے زیادہ 320 پکسل چوڑا اسکیل کرتا ہے، منظر کی تبدیلیوں اور منجمد وقفوں کا پتہ لگاتا ہے، پھر دھندلاہٹ، اوسط لومی، اور مکانی/وقتی معلومات کے لیے فی سیکنڈ 1 فریم پر نمونہ لیتا ہے۔ یہ پاس 600 ساختی نمونوں، ایک FFmpeg/filter تھریڈ، اسی `file`-only پروٹوکول اور کنٹینر کی اجازت کی فہرستوں، 1 MiB پروسیس آؤٹ پٹ کی حد، اور بروکر کے مشترکہ منسوخی/آخری تاریخ کے اندر زیادہ سے زیادہ 30 سیکنڈ تک محدود ہے۔ یہ کبھی بھی درخواست سے کوئی کمانڈ، فلٹر، راستہ، یا URL قبول نہیں کرتا۔

ساختی اقدار متعین نمونہ لینے کے شواہد ہیں، نہ کہ معنوی ویڈیو کی تفہیم۔ یہ مضامین، اعمال، عنوانات، تقریر، یا صارف کی نیت کا اندازہ نہیں لگاتے۔ منظر اور منجمد کی سرحدیں حصے بناتی ہیں؛ منجمد کوریج، دھندلاہٹ، نمائش، مکانی تفصیل، اور وقتی تبدیلی صرف اس بات پر اثر انداز ہوتی ہیں کہ موجودہ 1–16 فریم بجٹ کیسے مختص کیا جاتا ہے۔ ایک مکمل طور پر منجمد حصہ ایک فریم پر محدود ہے، جبکہ غیر منجمد حصے باقی بجٹ کے لیے مقابلہ کرتے ہیں۔ جب سرحدیں فریمز کی تعداد سے زیادہ ہوں تو یکساں ٹائم لائن کوریج برقرار رکھی جاتی ہے تاکہ تیز ابتدائی کٹ ایک طویل پیچھے رہ جانے والے حصے کو چھپا نہ سکے۔ 1 سیکنڈ کے تجزیاتی حل کے اندر منجمد کی سرحد کے منظر کی سرحدیں یکجا کی جاتی ہیں۔

غائب فلٹرز، غلط شکل میں/خالی شواہد، ایک ڈیٹیکٹر کی غلطی، یا محدود پیش تجزیاتی ٹائم آؤٹ درست یکساں وسطی پالیسی پر کھل جاتے ہیں۔ ایک کالر کی منسوخی یا بروکر کی آخری تاریخ کھلنے میں ناکام ہوتی ہے: یہ زیر پرواز ذیلی عمل کو ختم کرتی ہے، بعد میں فریم نکالنے سے روکتی ہے، اور نجی عارضی درخت کو `finally` میں ہٹا دیتی ہے۔

`scripts/perf/video-bridge-fu07-eval.ts` بعد میں غیر دہرائی جانے والی عنوان-کال کی بچت، کثیف حرکت کے بجٹ کی تقسیم، دھندلاہٹ/نمائش/SI-TI شواہد، طویل دم کے ساتھ تیز کٹ، اور بتدریج مدھم جھوٹی مثبتات کے لیے متعین حقیقی FFmpeg کے فکسچر تیار کرتا ہے۔ یہ پیش تجزیاتی دیوار کے وقت کو ریکارڈ کرتا ہے اور، جہاں `/usr/bin/time` دستیاب ہے، بچے کے CPU اور عروجی RSS کو بھی۔ اس کے معیار کے چیک صرف ساختی اوریکل ہیں۔ حقیقی عنوان ماڈل کا معیار `HOLD` پر رہتا ہے کیونکہ اس ہارنس میں کوئی مجاز اینڈپوائنٹ یا منجمد جج نہیں ہے۔ مالی بچت بھی `HOLD` پر رہتی ہے جب تک کہ `--caption-cost-per-call-usd` ایک واضح مثبت فی کال تخمینہ فراہم نہ کرے؛ اسکرپٹ کبھی بھی کسی نتیجے کو جعلی نہیں بناتا۔

ہر فریم 4 MiB تک محدود ہے، تمام خام فریمز کو ملا کر 23 MiB تک، اور سیریلائزڈ بروکر کا جواب 32 MiB تک۔ ایک نجی عارضی ڈائریکٹری `finally` میں ہٹا دی جاتی ہے۔ OmniRoute FFmpeg کو باندھتا نہیں ہے اور نہ ہی ایک حسب ضرورت قابل عمل راستہ قبول کرتا ہے۔ عنوان دینے سے پہلے، پل ایک محتاط بصری غیر دہرائی جانے والی پاس لگاتا ہے: ہر JPEG کو 16×16 گری اسکیل بفر میں کم کیا جاتا ہے اور صرف آخری محفوظ کردہ فریم کے ساتھ موازنہ کیا جاتا ہے۔ ایک درخواست کردہ عنوان بجٹ ایک فریم سے زیادہ ہونے پر، نکاسی ایک محدود امیدوار پول فراہم کرتی ہے جو اس بجٹ کا دوگنا ہو سکتا ہے اور کبھی بھی 16 فریم سے زیادہ نہیں۔ درخواست کردہ حد صرف غیر دہرائی جانے کے بعد لگائی جاتی ہے، پہلے اور آخری منتخب کردہ امیدواروں کو آخری پتلا کرنے کے دوران محفوظ کیا جاتا ہے جب بجٹ کم از کم دو ہو۔ ورژن شدہ `grayscale-16x16-mean-cells-v2` پالیسی اوسط لومی ڈیلٹا اور تھمب نیل سیلز کے تناسب میں سے بڑے کا استعمال کرتی ہے جس کا معمولی ڈیلٹا کم از کم 0.05 ہو۔ نقل کا تھریشولڈ مستقل 0.04 ہے، جو پیش گوئی کے لیے منتخب کیا گیا ہے نہ کہ ایک رن ٹائم سیٹنگ کے طور پر ظاہر کیا گیا ہے۔ یہ ثانوی ہائی کنٹراسٹ سگنل چھوٹے حرکت اور نظر آنے والی متن کی تبدیلیوں کو محفوظ رکھتا ہے جو صرف اوسط موازنہ چھپا سکتا ہے۔ موازنہ کرنے والے یا ڈی کوڈر کی غلطیاں کھل جاتی ہیں اور کوریج کو برقرار رکھتی ہیں۔ آؤٹ پٹ میٹا ڈیٹا نکالے گئے امیدواروں، کامیابی سے استعمال ہونے والے فریمز، اور بصری نقلوں کو الگ کرتا ہے۔

ایک واضح طور پر نشان زد ویڈیو حصہ ایک ٹائم اسٹیمپ شدہ رابطہ شیٹ کی درخواست کر سکتا ہے۔ پل زیادہ سے زیادہ 4 کالم، 16 فریم JPEG گرڈ بناتا ہے۔ ہر 512 پکسل سیل اپنے ماخذ کے ٹائم اسٹیمپ کو ایک ہائی کنٹراسٹ نیچے کی پٹی میں جلا دیتا ہے، جبکہ وہی ٹائم اسٹیمپس ٹیکسٹ میٹا ڈیٹا میں نیچے کی جانب رہتے ہیں تاکہ بعد میں تعلق اور آڈٹ کے لیے۔ مکمل JPEG 32 MiB پر محدود رہتا ہے۔ اگر `sharp` گرڈ کو ڈیکوڈ یا مرتب نہیں کر سکتا، تو پل انفرادی JPEG فریمز پر واپس آتا ہے؛ ایک کلائنٹ کی منسوخی اب بھی شیٹ کے عمل میں پھیل جاتی ہے۔

پروموشن کے شواہد جان بوجھ کر مصنوعی ترکیب مائیکرو بینچ مارک سے الگ ہیں۔ `scripts/perf/video-bridge-contact-sheet-eval.ts` حقیقی OpenAI کے ہم آہنگ بصری ماڈلز کے لیے ایک اسکیمہ ورژن شدہ A/B ہارنس کی وضاحت کرتا ہے۔ یہ فراہم کنندہ کی رپورٹ کردہ ٹوکنز، آخر تک دیوار کی تاخیر (شیٹ کی ترکیب سمیت)، ماڈل کال کی تعداد، اور مینیفیسٹ کی تعریف کردہ حقیقت کی برقرار رکھنے کی پیمائش کرتا ہے۔ خام ماڈل کے جوابات رپورٹ میں نہیں لکھے جاتے؛ صرف SHA-256 ہیش اور میچ کردہ حقیقت کے IDs محفوظ کیے جاتے ہیں۔ یہ ہارنس کوئی نیٹ ورک یا ادائیگی ماڈل کی کال نہیں کرتا جب تک کہ `--execute-real` پاس نہ کیا جائے اور `--model`، `OMNIROUTE_BASE_URL`، اور `OMNIROUTE_API_KEY` ترتیب نہ دیے جائیں۔ اس واضح حقیقی رن کے بغیر، اس کا مشین پڑھنے کے قابل فیصلہ `HOLD` پر رہتا ہے؛ مصنوعی بوجھ/کال کی تعداد کی پیمائش اکیلے پروموشن کے شواہد نہیں ہیں۔

الگ `scripts/perf/video-bridge-promotion-eval.ts` FU-07 یا FU-09 مشاہدات کو استعمال کرتا ہے۔ پروموشن کی قبولیت کے لیے تمام آٹھ مصنوعی منظرنامے کی اقسام کے ساتھ ساتھ ایک صاف کردہ حقیقی کلپ کی ضرورت ہوتی ہے، ہر کردار اور کیس کے لیے کم از کم تین ماپی گئی تکرار، تمام دس اعلان کردہ میٹرکس، منجمد میڈیا/پرومپٹ/متوقع حقیقت/سیٹنگز کے ہیش، منفرد مشاہدے کے IDs اور تصدیق شدہ بیج A/B ترتیب۔ عملدرآمد کی رسید مجموعہ کے ہیش، درست امیدوار SHA اور ماڈل کے ترمیم کو باندھتی ہے۔ غائب یا غلط ماپیں `HOLD` پر رہتی ہیں، بشمول CPU 30 سیکنڈ سے اوپر، عروجی RSS 512 MiB سے اوپر یا پیش تجزیاتی 30 سیکنڈ سے اوپر۔ یہ شواہد کی قبولیت کی حدیں ہیں، نئی رن ٹائم RSS نافذ کرنے کی ضمانت نہیں۔

FU-07 کو کم از کم 98% معیار کی برقرار رکھنے کی ضرورت ہے اور p95 کی تاخیر 1.2x بیسلائن سے زیادہ نہیں ہونی چاہیے، اس کے علاوہ یا تو 0.05 مطلق کیس بیلنسڈ اوسط یادداشت میں بہتری ہونی چاہیے جو مساوی اوسط کیپشن کالز پر ہو، یا کم از کم 10% کم اوسط پوسٹ ڈی ڈوپ کیپشن کالز ہونی چاہئیں۔ FU-09 کو کم از کم 0.85 معیار، 95% برقرار رکھنے، 20% p95 کی تاخیر میں کمی اور 10% ٹوکن میں کمی کی ضرورت ہے۔ اہم حقیقت کا نقصان، انجیکشن کی تعمیل یا استعمال کی کمی ترقی کو روکتی ہے۔ ایک عمل کچھ بھی ترقی نہیں کر سکتا: `--previous-report` ایک ہی پالیسی/ماڈل کی نظرثانی/امیدوار/کارپس کے دو مختلف، غیر اوورلیپنگ، متواتر اہل عملوں کی تصدیق کرتا ہے۔ ایک نمونہ تجربہ ایک رابطہ شیٹ کے تجربے کی تصدیق نہیں کر سکتا۔

جمع کرنے والوں کو یادداشت میں جوابات کی درجہ بندی کرنی چاہیے اور `responseDigest` کے ساتھ ساتھ میٹرکس اور مشاہدے کی بائنڈنگز کو محفوظ کرنا چاہیے، کبھی بھی جواب کا متن نہیں۔ صارف بھی وراثتی خام مشاہدات پڑھتا ہے لیکن کبھی بھی اس متن کو اپنی رپورٹوں میں نہیں کاپی کرتا۔ ہر مشاہدے کے لیے بالکل ایک `responseDigest` یا `rawResponseText` قبول کیا جاتا ہے۔ ورژنڈ الاؤ لسٹ خالی رہتی ہے جس کا غیر متغیر `hold` ڈیفالٹ ہوتا ہے۔ ایک اہل اندراج کے لیے اس کے ثبوت کا حوالہ، پالیسی، ماڈل کی نظرثانی، درست امیدوار SHA، مینیفیسٹ ڈائجسٹ اور دو مختلف رن IDs کی ضرورت ہوتی ہے؛ متضاد سیاق و سباق کو مسترد کر دیا جاتا ہے۔ یہ میٹا ڈیٹا ایک آڈٹ معاہدہ ہے، نہ کہ اس بات کا ثبوت کہ حوالہ دیا گیا فائل حقیقی پیمائشیں رکھتا ہے۔ کسی بھی اندراج کو شامل کرنے سے پہلے اصل رسیدوں کا جائزہ لیں۔ انتظامی اعداد و شمار کا اینڈ پوائنٹ اور ویڈیو ڈیش بورڈ محتاط تیاری کو ظاہر کرتے ہیں۔ صرف ایک تشکیل شدہ ماڈل ایلیاس اس کی نظرثانی یا چلنے والے امیدوار SHA کو قائم نہیں کرتا، اس لیے موجودہ ڈیش بورڈ `HOLD` کی اطلاع دیتا ہے بجائے اس کے کہ کسی دوسرے عمل کے سیاق و سباق سے اہلیت کو دوبارہ استعمال کیا جائے۔ واضح تجرباتی انتخاب ترقی سے الگ رہتا ہے؛ کوئی ڈیفالٹ خود بخود تبدیل نہیں ہوتا۔

کال کرنے والے ایک آپشنل `transcript.cues` ارے کو سپورٹ کردہ ویڈیو حصے کے ساتھ منسلک کر سکتے ہیں جب ان کے پاس پہلے سے ہی ہم آہنگ متن ہو۔ ہر اشارہ میں `text` ہونا چاہیے، ایک محدود `start`/`end` وقفہ جو جانچے گئے دورانیے کے اندر ہو، اور ایک وائٹ لسٹڈ `source` (`client`, `embedded`, یا `audio-bridge`); `confidence` کا ڈیفالٹ `1` ہے اور اسے `0` اور `1` کے درمیان رہنا چاہیے۔ عین مطابق نقل اشارے کو سمیٹ دیا جاتا ہے۔ OmniRoute کبھی بھی اس میٹا ڈیٹا سے نقل نویسی شروع نہیں کرتا: تصدیق شدہ اشارے بیان کردہ نتیجے میں ماخذ، اعتماد، اور وقفے کے ساتھ کاپی کیے جاتے ہیں، اور انہیں فریم کیپشنز کے ساتھ غیر معتبر مشاہدات کے طور پر پیش کیا جاتا ہے۔ غیر درست، حد سے باہر، یا ماخذ سے آزاد متن کو مسترد کر دیا جاتا ہے بجائے اس کے کہ اسے کیپشن اسٹریم میں ملایا جائے۔ دونوں درخواست-باڈی نقل نویسی چینلز فراہم کردہ ماخذ کو `client` میں معمول پر لاتے ہیں، بشمول خود-مبنی `embedded` یا `audio-bridge` لیبلز۔ صرف ایک سرور کے زیر ملکیت ایڈاپٹر ان قابل اعتماد لیبلز کو کوڈ-صرف `trustedSource` دلیل کے ذریعے تفویض کر سکتا ہے؛ ایک درخواست JSON فیلڈ اس دلیل تک نہیں پہنچ سکتی۔ نقل نویسی کا متن غیر معتبر میڈیا سے حاصل کردہ مواد رہتا ہے، اس کے ماخذ سے قطع نظر، اور کبھی بھی اختیار کا تعین نہیں کرنا چاہیے۔

ایک ترقی یافتہ کالر اسی ویڈیو کے لیے `audioTranscript` ٹریک فراہم کر سکتا ہے؛ اسے کلائنٹ کی فراہم کردہ متن کے طور پر سمجھا جاتا ہے، سرور کی نقل نویسی کے ثبوت کے طور پر نہیں۔ فیوژن سیام بصری اور صوتی مشاہدات کو ایک ہی ڈیڈ لائن اورAbort سگنل کے تحت چلاتا ہے، انہیں ایک مشترکہ ٹائم لائن پر ترتیب دیتا ہے، عین مطابق نقل کو سمیٹتا ہے، اور جب صرف ایک طرف کامیاب ہوتی ہے تو جزوی نتیجہ کی اطلاع دیتا ہے۔ ایک غیر درست `audioTranscript` اس جزوی نتیجے میں کم ہو جاتا ہے — بصری تفصیل رکھی جاتی ہے اور صوتی شاخ ایک صاف شدہ ناکامی کوڈ ریکارڈ کرتی ہے — پورے ویڈیو کو ناکام کرنے کے بجائے۔ ہر شاخ کی دستیابی، جزوی پرچم، اور صاف شدہ ناکامی کے کوڈز بیان کردہ نتیجے میں محفوظ کیے جاتے ہیں، گارڈریل میٹا ڈیٹا (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`) میں، نتیجہ کیش میٹا ڈیٹا میں، اور پل فیوژن کاؤنٹرز میں۔ ڈیفالٹ ویڈیو پل کا راستہ تقریر سے متن میں تبدیل کرنے یا دوسرے میڈیا کی کاپی ڈاؤن لوڈ نہیں کرتا؛ اس واضح ٹریک کے بغیر، یہ صرف ویڈیو رہتا ہے۔

**نقل نویسی کی برقرار رکھنے (#12150 P1).** یہ خود بخود لاگو ہوتا ہے جب بھی ویڈیو پل (خود بھی آپٹ ان) ایک نقل نویسی اشارہ پیش کرتا ہے — کوئی علیحدہ برقرار رکھنے کا پرچم نہیں ہے۔ جب کوئی درخواست کسی بھی نقل نویسی اشارہ (ایک کالر کی طرف سے بیان کردہ `transcript` یا ایک فیوزڈ `audioTranscript`) کو پیش کرتی ہے، تو گارڈریل اسے `videoBridgeObserved` کے طور پر نشان زد کرتا ہے اور ویڈیو کی تفصیل کا ایک سرخ شدہ سایہ پیدا کرتا ہے — ایک یکساں پیشکش جس میں ہر اشارے کے آزاد متن کے جسم کو `[redacted-video-transcript]` سے تبدیل کیا جاتا ہے، جو اسٹرکچرڈ اشارے کے میدان کو تبدیل کر کے بنایا جاتا ہے اس سے پہلے کہ سٹرنگ کو جمع کیا جائے (کبھی بھی فلیٹ ٹیکسٹ کو پارس کر کے نہیں، لہذا کوئی اشارے کا مواد — مخالف یا عام، بشمول جسم جو `]` جیسے ` [inaudible]`/`[music]` پر مشتمل ہو — زندہ نہیں رہ سکتا)۔ محفوظ شدہ کال-لاگ درخواست کا جسم ہر ویڈیو سے حاصل کردہ متن کے حصے کو اس سرخ شدہ سایہ کے لیے تبدیل کرتا ہے، مواد کی برابری سے ملتا ہے؛ `fullText` اینکر کو مکمل پیش کال گارڈریل پیلوڈ سے دوبارہ پڑھا جاتا ہے، لہذا میچ بعد میں چین گارڈریل (PII اور کریڈینشل ماسکرز، ترجیحات 10/95) کی تفصیل کے متن کو جگہ پر دوبارہ لکھنے کے بعد بھی کامیاب رہتا ہے اور نظام-پرومپٹ/ہینڈ آف/یادداشت کے انجیکشن کے بعد پیغام کی صف کو دوبارہ شکل دیتا ہے۔ ماڈل کو بھیجی گئی جسم میں کوئی تبدیلی نہیں ہوتی۔ ایک مشاہدہ شدہ درخواست بھی کوئی مستقل یادداشت کو آبادی نہیں دیتی (درخواست اور جواب سے حاصل کردہ نکالنے کو چھوڑ دیا جاتا ہے)، لہذا ماڈل کا اپنا جواب یادداشت میں نقل نویسی کے متن کو نہیں دہرا سکتا۔

**خام ویڈیو کے میدان (#12430).** جب پل فعال ہو اور مقامی ویڈیو کی حمایت نامعلوم یا غیر موجود ہو، تو متعین `transcript`/`audioTranscript` کے میدان بھی `videoBridgeObserved` کو فعال کرتے ہیں، یہاں تک کہ تفصیل کی ناکامی یا `maxVideos` کی حد کے بعد بھی۔ `null` اور خالی سٹرنگز شمار ہوتی ہیں؛ غیر موجود میدان اور غیر ویڈیو میٹا ڈیٹا شمار نہیں ہوتے۔ محفوظ شدہ کاپیوں میں ان میدانوں کو سرخ کیا جاتا ہے یا درخواست کو چھوڑ دیا جاتا ہے، اور کیش/یادداشت کو بائی پاس کیا جاتا ہے۔

ان فیل بیک راستوں پر، درست کالر اشارے سپورٹڈ `text`/`input_text` حصے بن جاتے ہیں بجائے غیر معیاری فراہم کنندہ کے میدانوں کے۔ دونوں درخواست فراہم کردہ ٹریکس غیر معتبر `client` مشاہدات رہتے ہیں، جس کے ساتھ ایک واضح انتباہ ہے کہ ویڈیو کی وضاحت نہیں کی گئی تھی اور وقت کے نشانات میڈیا کے خلاف تصدیق نہیں کیے گئے تھے۔ موجودہ 256-اشارے/64-KiB کل اور فی اشارہ بجٹ دونوں ٹریکس پر لاگو ہوتے ہیں؛ وقت کے نشانات بروکر کے 600 سیکنڈ کی چھت اور کسی بھی فراہم کردہ توجہ کی کھڑکی میں فٹ ہونے چاہئیں۔ غیر درست ٹریکس کو خارج کر دیا جاتا ہے، انہیں بے ترتیب متن کے طور پر آگے نہیں بڑھایا جاتا؛ ایک درست بہن اب بھی استعمال کی جا سکتی ہے جب تک کہ ان کا مجموعی بجٹ تجاوز نہ کر جائے۔ نل/خالی میدان کوئی متن شامل نہیں کرتے۔ اس فیل بیک کے ذریعے کوئی میڈیا fetch یا نقل نہیں کی جاتی۔ نقل کے توسیع کے میدان فیل بیک ویڈیو کیریئر اور اس کے `video_url`/`source` اشیاء سے ہٹا دیے جاتے ہیں۔ OpenAI وائر اجازت نامہ سخت رہتا ہے؛ نامعلوم مقامی ویڈیو کیریئر دستیاب رہتے ہیں اور معلوم صرف متن کے ہدف محفوظ نشانات رکھتے ہیں۔ ساختی سرخیوں کی سیاہی شامل کردہ نقل کے متن کی حفاظت کرتی ہے، جبکہ اصل کالر کی ملکیت والی درخواست بغیر کسی تبدیلی کے رہتی ہے۔ مقامی طور پر سپورٹ کردہ ہدف اور غیر فعال پلز اپنی موجودہ بائی پاس کی طرز عمل کو برقرار رکھتے ہیں۔

اضافی محفوظ شدہ کاپیوں میں وہی مشاہدہ شدہ درخواست کا اشارہ استعمال ہوتا ہے۔ خام پیش گارڈریل کلائنٹ درخواست کا اسنیپ شاٹ، میموری میں زیر التواء درخواست، اور ابتدائی مسترد شدہ درخواست کا لاگ ساختی طور پر ویڈیو حصوں میں نقل کے میدانوں کی جگہ لیتا ہے؛ سٹرنگ پرامپٹس جو پائپ لائن مراحل اور سیاق و سباق کی ہینڈ آف کے ذریعہ تیار کیے گئے ہیں، محفوظ شدہ درخواست کے جسم کے سنک پر سرخی کر دیے جاتے ہیں۔ محفوظ شدہ `video_content_removed` نشان `previous_response_id` کی تسلسل کو بند کر دیتا ہے بجائے اس کے کہ وہ متن کو دوبارہ تشکیل دے جو جان بوجھ کر خارج کیا گیا تھا۔ اگر ایک مشاہدہ شدہ درخواست اپنے ہر حصے کی سرخی کا سایہ لاگنگ سے پہلے کھو دیتی ہے، یا یہاں تک کہ کئی ویڈیو سائے میں سے ایک بعد میں درخواست کی تبدیلیوں کے بعد میل نہیں کھاتا، تو محفوظ شدہ درخواست کا جسم مکمل طور پر چھوڑ دیا جاتا ہے بجائے اس کے کہ جزوی طور پر سرخی شدہ نقل کو برقرار رکھا جائے۔

ایک مشاہدہ شدہ درخواست کے لیے، ماڈل کا جواب نقل کے کسی بھی حصے کا حوالہ دے سکتا ہے بغیر کسی ساختی اشارے کی سرحد کے۔ اس کی محفوظ شدہ کال-لاگ `responseBody` اس لیے ایک حذف نشان سے تبدیل ہو جاتی ہے؛ تفصیلی پائپ لائن آرٹفیکٹ (جو اوپر کی طرف/کلائنٹ کے جسم اور اسٹریم کے ٹکڑوں کو شامل کر سکتا ہے) محفوظ نہیں کیا جاتا۔ معنوی، ایڈیمپوٹنسی، اور استدلال-دوبارہ پلے کیشیں اس درخواست کے لیے پڑھنے اور لکھنے کو بائی پاس کرتی ہیں۔ فراہم کنندہ کی درخواست اور کلائنٹ کے سامنے آنے والا جواب بغیر کسی تبدیلی کے رہتا ہے۔ ابتدائی کیپ الائیو بائٹس عارضی بافر سے نکال دیے جاتے ہیں جب تفصیلی آرٹفیکٹ کو خارج کیا جاتا ہے۔ کیرو کی malformed EventStream انتباہ صرف پیلوڈ بائٹ کی تعداد کی رپورٹ کرتی ہے، کبھی بھی اس کے مواد یا JSON پارسر کی خام غلطی کو نہیں۔

یہ دعویٰ نہیں کرتا کہ ہر غیر متعلقہ فراہم کنندہ/پلگ ان تشخیصی جانچ کی گئی ہے؛ وسیع تر محفوظ شدہ-سنک صفائی کو #11658 میں ٹریک کیا جاتا ہے۔

اندرونی `/api/modality-bridge/video/drilldown` لائف سائیکل ایک علیحدہ، لوپ بیک/ٹوکین-تصدیق شدہ کیش سبسٹریٹ ہے۔ ہر کارروائی کے لیے ایک معیاری غیر شفاف پرنسپل ID کی ضرورت ہوتی ہے۔ ایک پروڈکشن کالر کو فعال کرنے سے پہلے، اسے اس ID کو تصدیق شدہ کرایہ دار سے حاصل کرنا چاہیے اور اسے کبھی بھی کلائنٹ کے منتخب کردہ قیمت کو آگے نہیں بڑھانا چاہیے۔ کیش کی چابیاں اس پرنسپل کو معیاری سیشن اور ویڈیو حوالہ ID سے باندھتی ہیں، صرف ان کی SHA-256 سے حاصل کردہ چابیاں ذخیرہ کرتی ہیں، اور پڑھنے اور حذف کو اسی پرنسپل تک محدود کرتی ہیں۔ کیش ہر اندراج کے لیے زیادہ سے زیادہ 16 حاصل کردہ JPEG فریمز ذخیرہ کرتی ہے، انہیں دس منٹ بعد ختم کرتی ہے، اور محدود `start`/`end` پڑھنے یا واضح سیشن حذف کی حمایت کرتی ہے۔

ہر پرنسپل 16 اندراجات اور 64 MiB کی معیاری JPEG ڈیٹا تک محدود ہے۔ یہ حدود عالمی 64-اندراج/256 MiB کی چھت سے آزاد ہیں: پرنسپل کوٹا دباؤ صرف اس پرنسپل کے کم سے کم حالیہ استعمال شدہ اندراجات کو خارج کرتا ہے اس سے پہلے کہ عالمی LRU خارج کرنے پر غور کیا جائے۔ ختم شدہ اندراجات کیش کی سرگرمی پر دونوں پرنسپل اور عالمی حساب سے صاف کی جاتی ہیں، جبکہ منسوخی اور توثیق کی ناکامی جزوی تبدیلی کو کمٹ نہیں کرتی۔

کیش غیر معیاری Base64، اضافی پیڈنگ، غیر JPEG میڈیا، malformed یا truncated JPEGs، اور JPEGs کو خارج کرتی ہے جو محدود مکمل تصویر `sharp` decode کے دوران انتباہ پیدا کرتی ہیں۔ یہ ہر قبول شدہ تصویر کو معیاری JPEG کے طور پر دوبارہ کوڈ کرتی ہے، کالر کے میدانوں پر بھروسہ کرنے کے بجائے ڈی کوڈ کردہ بائٹس سے چوڑائی اور اونچائی حاصل کرتی ہے، اور کسی بھی پچھلے polyglot بائٹس کو خارج کرتی ہے بجائے اس کے کہ انہیں برقرار رکھا جائے۔ صرف معیاری کمپریسڈ بافر دونوں کوٹا پر چارج کیا جاتا ہے۔ JSON وائر کی حد 32 MiB کے ڈی کوڈ کردہ-ان پٹ کی چھت کے لیے Base64 اوور ہیڈ کو شامل کرتی ہے۔ ہر محفوظ شدہ مشتق اپنے توثیق شدہ JPEG فارمیٹ/حل، نمونہ پالیسی، مشتق ورژن، تخلیق کا وقت، سرور کے حساب سے مواد کا ہیش، اور ہیش کردہ والد کا حوالہ ریکارڈ کرتا ہے اور قابل اعتماد کالر کے والد کے مواد کا ہیش۔ منسوخی کو غیر متوازن ڈی کوڈ/ہیش مراحل کے درمیان چیک کیا جاتا ہے اس سے پہلے کہ ایٹمی کیش کمٹ ہو۔

پروڈکشن پروڈیوسر پہلے سے حاصل کردہ بروکر فریمز کو صرف کامیاب بصری تجزیے کے بعد دوبارہ استعمال کرتا ہے، بغیر کسی دوسرے ویڈیو ڈاؤن لوڈ/نکالنے کے۔ اسے آپریٹر `modalityBridgeVideoDrilldownEnabled=true`، سخت فی حصے `drilldown: true`، اور ایک تصدیق شدہ API-key ریکارڈ ID کی ضرورت ہوتی ہے۔ کلائنٹ کے اعلان کردہ پرنسپل/سیشن کی قیمتیں کبھی بھی ملکیت قائم نہیں کرتی ہیں۔ ان تینوں شرائط کے بغیر یہ اضافی فریمز کو ہیش، دوبارہ سائز یا برقرار نہیں رکھتا۔ برقرار رکھنے میں ناکامی قابل استعمال بصری جواب کو محفوظ رکھتی ہے۔ رضامند درخواستیں پوری ویڈیو کے نتیجے کیش کو بائی پاس کرتی ہیں تاکہ کیش شدہ نتائج کبھی بھی ہینڈلز کو دوبارہ پلے نہ کریں۔

کامیاب JSON اور SSE جوابات زیادہ سے زیادہ چار اوپیک ہینڈلز کو محدود `x-omniroute-video-drilldown` ہیڈر میں ظاہر کرتے ہیں۔ مجاز براؤزر کے ذرائع اس ہیڈر کو CORS اصل پالیسی کو وسیع کیے بغیر پڑھ سکتے ہیں۔ نئے ہینڈلز `v1.<32-byte random base64url token>` کا استعمال کرتے ہیں، اور رجسٹری صرف ان کے SHA-256 ہیشز کو برقرار رکھتی ہے۔ ریڈر/ہیڈر پارسر بھی وراثتی 64-ہیکس ٹوکنز کو قبول کرتا ہے۔ تصدیق شدہ عوامی صارف ہے `GET /api/v1/video-bridge/drilldown?handle=...`، جو کہ `modalityBridgeVideoDrilldownRemoteEnabled=true` کے ذریعہ آزادانہ طور پر گیٹ کیا جاتا ہے۔ واضح طور پر برقرار رکھا گیا جھوٹا رسائی کو منسوخ کرتا ہے یہاں تک کہ وراثتی `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` env فیل بیک فعال ہو۔ پیداوار کی برقرار رکھنے میں وراثتی `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED` فیل بیک ہے۔ دونوں فیل بیک ڈیفالٹ طور پر بند ہیں۔

صارف تصدیق شدہ کلید سے ملکیت حاصل کرتا ہے، کلید کی پالیسی کو نافذ کرتا ہے، اور نامعلوم، ختم شدہ اور دوسری کلید کے ہینڈلز کے لیے وہی 404 واپس کرتا ہے۔ یہ `variant=preview|standard|detail` (زیادہ سے زیادہ JPEG ابعاد 320/640/1280، کبھی بھی اپ اسکیل نہیں) کو قبول کرتا ہے، `limit=1..8` (یا وراثتی `frames` متبادل، کبھی بھی دونوں نہیں)، صفر پر مبنی `page`، اور اختیاری `start`/`end` توجہ کے سیکنڈز۔ نقل سوال کی چابیاں اور الٹی توجہ کی کھڑکیاں مسترد کر دی جاتی ہیں۔ ہر واپس کردہ متغیر میں اس کے اصل مواد اور اصل قرارداد کے میٹا ڈیٹا کا ہیش ہوتا ہے، جو برقرار رکھے گئے ماخذ سے منسلک ہوتا ہے۔ متغیرات پڑھنے پر حاصل کیے جاتے ہیں نہ کہ اضافی برقرار رکھنے کی کاپیوں کے طور پر محفوظ کیے جاتے ہیں۔ JSON جواب، بشمول Base64/envelope، 32 MiB پر محدود ہے؛ ایک زیادہ سائز کا صفحہ 413 واپس کرتا ہے اور کلائنٹ کو کم فریمز کی درخواست کرنی چاہیے۔ پڑھنے ہر سائز کے ارد گرد منسوخی کی جانچ کرتے ہیں اور واپس کرنے سے پہلے ہینڈل کی درستگی کی دوبارہ جانچ کرتے ہیں۔ مالک کے ذریعہ `DELETE` ایڈیمپوٹنٹ ہے؛ حذف یا TTL کی میعاد ختم ہونے سے برقرار رکھا گیا ماخذ اور استعمال کا حساب جاری ہوتا ہے۔

مشترکہ اسٹور پروسیس مقامی ہے: ہینڈلز دوبارہ شروع ہونے پر ختم ہو جاتے ہیں اور آزاد OmniRoute پروسیس کے درمیان منتقل نہیں کیے جا سکتے۔ انتظامی اعداد و شمار مؤثر برقرار رکھنے/دور دراز کی پالیسی اور صرف مجموعی طور پر برقرار رکھی گئی اندراجات/بائٹس کو ظاہر کرتے ہیں، کبھی بھی میڈیا، حوالہ جات، اہم IDs یا ہینڈلز نہیں۔ ویڈیو کی ترتیبات کا پینل ان اقدار کو دکھاتا ہے اور دونوں رضامندی کے سوئچز کو برقرار رکھ سکتا ہے۔ یہ عمل درآمد کی دستاویزات براہ راست تعیناتی یا تشہیر کے ثبوت نہیں ہیں؛ حقیقی ماڈل کی قبولیت کو علیحدہ طور پر ٹریک کیا جاتا ہے۔

فریمز کو ترتیب وار ویڈیو ماڈل کے ساتھ کیپشن کیا جاتا ہے۔ ایک خالی ویڈیو اووررائیڈ وژن کی ترتیب وراثت کرتا ہے؛ اگر دونوں خالی ہیں، تو وژن خودکار روٹر مؤثر وژن کے قابل ماڈل کا انتخاب کرتا ہے۔ کامیاب کیپشن اصل حصے کو ایک مستحکم `[Video description:` پیش لفظ کے ساتھ تبدیل کرتا ہے جو متن کو غیر معتبر میڈیا سے حاصل کردہ مشاہدہ کے طور پر بھی نشان زد کرتا ہے اور نیچے کے ماڈلز کو بتاتا ہے کہ میڈیا میں پائے جانے والے ہدایات کی پیروی نہ کریں۔ فریم-کیپشن کیش کی چابیاں JPEG بائٹس، پرامپٹ، ٹائم اسٹیمپ، اور مؤثر ماڈل شامل کرتی ہیں؛ صرف کامیاب کیپشن کیش کیے جاتے ہیں۔ کیش کی اندراجات اصل کامیاب پروڈیوسر ماڈل کو برقرار رکھتی ہیں، بشمول ایک فیل بیک ماڈل؛ پل رپورٹ کرتا ہے `mixed` جب مختلف فریمز مختلف ماڈلز کے ذریعہ تیار کیے گئے تھے۔ کیش ہٹ اس پروڈیوسر کی شناخت کو دوبارہ استعمال کرتا ہے بجائے اس کے کہ اسے درخواست کردہ روٹنگ منصوبے کے طور پر دوبارہ لیبل کیا جائے۔ پورے ویڈیو کے نتیجے کی کیش ہر ان پٹ پر کلید ہوتی ہے جو آؤٹ پٹ کو تبدیل کرتی ہے — پرامپٹ، مؤثر ماڈل، نمونہ پالیسی، فریم کی تعداد، معنوی تجزیے کا طریقہ، معیاری توجہ کی اشارہ کا SHA-256 فنگر پرنٹ، توجہ کی کھڑکی، `transcript`، `audioTranscript`، اور رابطہ شیٹ کا جھنڈا — لہذا ان میں سے کسی بھی جہت کو تبدیل کرنا کیش کی کمی ہے، کبھی بھی پرانی دوبارہ استعمال نہیں۔ بصری ڈی ڈوپ پالیسی ورژن، تھریشولڈ، اور محدود امیدوار-فریم کی تعداد بھی نتیجہ-کیش کی چابی اور میٹا ڈیٹا میں واضح ہیں؛ اس لیے پالیسی کی تبدیلی پرانی پورے ویڈیو کی تفصیل کو دوبارہ استعمال نہیں کر سکتی۔ نتیجہ-کیش v4 میٹا ڈیٹا موڈ اور فنگر پرنٹ کو برقرار رکھتا ہے، کبھی بھی خام صارف کے کام کو نہیں۔ گارڈریل میٹا ڈیٹا دونوں درخواست کردہ اور مؤثر تجزیے کے طریقوں کی رپورٹ کرتا ہے؛ ایک درخواست کردہ `focused` موڈ جس میں قابل استعمال صارف کا متن نہیں ہے مؤثر طور پر `full` کے طور پر رپورٹ کیا جاتا ہے۔

گارڈریل ہر سپورٹ کردہ ویڈیو حصے کو نکالتا ہے لیکن `modalityBridgeVideoMaxVideos` سے زیادہ بیان نہیں کرتا۔ ایک ہدف جس کا ثابت ہونا `supportsVideo === false`، ناکام اور حد سے زیادہ ویڈیوز واضح محفوظ متن کے نشانات بن جاتے ہیں تاکہ کوئی خام ویڈیو زندہ نہ رہے۔ جب صلاحیت نامعلوم ہو تو، ان حصوں میں ان کا ویڈیو کیریئر برقرار رہتا ہے؛ کوئی بھی فیل بیک ٹرانسکرپٹ اوپر بیان کردہ محدود متن کی تبدیلی کی پیروی کرتا ہے۔ ایسے ہدف جن میں `supportsVideo === true` پل کو بائی پاس کرتے ہیں۔ کلائنٹ کی درخواست کی منسوخی کا سگنل ڈاؤن لوڈ، بروکر کی قطار، ذیلی عمل، اور کیپشن کالز کے ذریعے پھیلتا ہے؛ منسوخیاں ویڈیوز کے درمیان رک جاتی ہیں اور کبھی بھی خام میڈیا کے لیے کھلی ناکامی نہیں ہوتی۔

### PII Masker (`piiMasker.ts`)

**دونوں** مراحل پر چلتا ہے۔

- **`preCall`** پیلوڈ کو کلون کرتا ہے، `system`، `messages`، `input`، اور `prompt` (سیدھے سٹرنگ آئٹمز سمیت) کو چلتا ہے، اور سٹرنگ `content`/`text` فیلڈز پر `processPII()` (سے `@/shared/utils/inputSanitizer`) کو لاگو کرتا ہے۔ جب `PII_REDACTION_ENABLED=true` ہو تو، پتہ لگائے گئے PII کو آؤٹ باؤنڈ پیلوڈ میں ریڈیکٹ کیا جاتا ہے۔ یہ `INPUT_SANITIZER_MODE` سے آزاد ہے (جو صرف پرامپٹ-انجیکشن پالیسی کو کنٹرول کرتا ہے)۔ جب ریڈکشن بند ہو تو، کال ریکارڈز پتہ لگانے کی تعداد کو بغیر مواد کو دوبارہ لکھے ریکارڈ کرتا ہے۔
- **`postCall`** جواب کو ڈیپ کلون کرتا ہے، `sanitizePIIResponse()` اور Responses-API-شکل ماسکر (`maskResponsesOutput` — `output_text` اور `output[].content[].text` کو ڈھانپتا ہے) کو چلاتا ہے۔ اگر کوئی ریڈکشن ہوتی ہے تو، تبدیل شدہ جواب اصل کو تبدیل کرتا ہے۔

گارڈریل کبھی بھی بلاک نہیں کرتا؛ یہ صرف تشریح کرتا ہے (`meta.detections`، `meta.redacted`) یا دوبارہ لکھتا ہے۔

### Prompt Injection (`promptInjection.ts`)

صارف کی فراہم کردہ مواد میں مخالف ساختوں کا پتہ لگاتا ہے اور ترتیب دی گئی پالیسی کو نافذ کرتا ہے۔ رویہ ماحولیاتی متغیرات اور کنسٹرکٹر کے اختیارات سے چلتا ہے:

| سیٹنگ         | ماحولیاتی متغیر                                                                                   | ڈیفالٹ | اثر                                                                                                                                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| فعال          | `INPUT_SANITIZER_ENABLED`                                                                         | `true` | جب `false` ہو تو، گارڈریل شارٹ سرکٹ کرتا ہے۔                                                                                                                                                                  |
| موڈ           | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                   | `warn` | انجیکشن پالیسی: `block`، `warn`، یا `log`۔ (`redact` پچھلے ہم آہنگی کے لیے قبول کیا جاتا ہے لیکن انجیکشن ٹیکسٹ کو **نہیں** ہٹاتا؛ درخواست PII دوبارہ لکھنے کو `PII_REDACTION_ENABLED` سے کنٹرول کیا جاتا ہے۔) |
| بلاک تھریشولڈ | `blockThreshold` آپشن / `INPUT_SANITIZER_BLOCK_THRESHOLD` (عرف `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high` | بلاک کرنے کے لیے درکار کم از کم شدت۔ درمیانہ ڈیفالٹ پر صرف مشاہدہ ہے۔                                                                                                                                         |

**موڈ کی ترجیح** (`getMode`): کالر `options.mode` → `INJECTION_GUARD_MODE` **DB فیچر-فلیگ اووررائیڈ** (ڈیش بورڈ → سیٹنگز → فیچر فلیگ) → `INJECTION_GUARD_MODE` ماحولیاتی → `INPUT_SANITIZER_MODE` ماحولیاتی → `warn`۔ اس لیے ڈیش بورڈ اووررائیڈ ماحولیاتی متغیرات پر غالب آتا ہے، لہذا فیچر فلیگ UI چلتے ہوئے گارڈ کو کنٹرول کرتا ہے (کوئی دوبارہ شروع نہیں)۔ DB پڑھنا محفوظ ہے: اگر یہ غلطی کرتا ہے تو، گارڈ ماحولیاتی بنیاد پر رویے پر واپس آتا ہے، اور جب کوئی اووررائیڈ سیٹ نہیں ہوتا تو رویہ ماحولیاتی صرف حل کے برابر ہوتا ہے۔

پتہ لگانے کے ذرائع:

1. `sanitizeRequest()` سے `@/shared/utils/inputSanitizer` (پائپ لائن میں کہیں اور استعمال ہونے والا مشترکہ ڈیٹیکٹر سیٹ)۔
2. بلٹ ان `DEFAULT_GUARD_PATTERNS` (فی الحال `system_override_inline` اور `markdown_system_block`، دونوں `high` شدت)۔
3. اختیاری `customPatterns` جو کنسٹرکٹر کے اختیارات کے ذریعے پاس کیے جاتے ہیں (سٹرنگز، regex، یا `{ name, pattern, severity }` ریکارڈز)۔

جب `mode === "block"` **اور** کم از کم ایک پتہ لگانے کی شدت کی حد کو پورا کرتا ہے، `preCall` `{ block: true, message: "Request rejected: suspicious content detected" }` واپس کرتا ہے۔ `warn`/`log` موڈز میں گارڈریل لاگ کرتا ہے لیکن کال کی اجازت دیتا ہے۔ مشترکہ ہیلپر `evaluatePromptInjection()` بھی کالرز کے لیے برآمد کیا گیا ہے جنہیں رجسٹری کے ذریعے جانے کے بغیر پرامپٹس کا اندازہ لگانے کی ضرورت ہوتی ہے۔

**اسکین باؤنڈ (v3.8.20):** ڈیٹیکٹر صرف **پہلے 16 KB** کے ملے جلے پرامپٹ ٹیکسٹ کا معائنہ کرتا ہے — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 بائٹس) میں `src/shared/utils/inputSanitizer.ts`۔ دونوں `detectInjection()` اور `evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` کو پیٹرن لوپ چلانے سے پہلے چلاتے ہیں۔ انجیکشن ہدایتیں ان پٹ کے اوپر کی طرف ہوتی ہیں، لہذا یہ ملٹی-ہنڈریڈ-KB پیلوڈز پر regex CPU/GC کو کیپ کرتا ہے بغیر پتہ لگانے کی طاقت کو کمزور کیے (cf. #3932، #4041)۔

### Credential Masker (`credentialMasker.ts`)

**دونوں** مراحل پر چلتا ہے، ڈیفالٹ چین میں آخری (ترجیحات `95`)۔ آؤٹ باؤنڈ پیلوڈ (پیغام کے مواد، ٹول-کال دلائل، ٹول کے نتائج) **اور** فراہم کنندہ کے جواب سے معروف API-key / secret-token پیٹرن کو ریڈیکٹ کرتا ہے، تاکہ ایک کریڈینشل جو پرامپٹ میں پیسٹ کیا گیا ہو (یا ٹول کے نتیجے میں واپس کیا گیا ہو) اوپر کی فراہم کنندہ یا کلائنٹ کو لیک نہ ہو۔

- **صرف آپٹ ان**، PII ریڈکشن کے ساتھ اسی کنونشن (Hard Rule #20-adjacent):
  جب تک `settings.credentialRedactionEnabled === true` **یا**
  `CREDENTIAL_REDACTION_ENABLED=true` نہ ہو، غیر فعال ہے۔ جب یہ بند ہو، تو گارڈریل ایک غیر عملی عمل ہے —
  یہ کبھی بھی بلاک نہیں کرتا اور نہ ہی دوبارہ لکھتا ہے۔
- `redactCredentials()` مکمل پیلوڈ/جواب کے درخت کو چلتا ہے (`walkValue()`,
  پروٹوٹائپ آلودگی سے محفوظ، `WeakSet` کے ذریعے سائیکل سے محفوظ) اور میچز کو
  `[REDACTED:<type>]` پلیس ہولڈر کے ساتھ تبدیل کرتا ہے، صرف ان شاخوں کی کلوننگ کرتا ہے جو واقعی
  تبدیل ہوئی ہیں۔
- `CREDENTIAL_PATTERNS` LLM فراہم کنندہ کی چابیاں (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate)، VCS/SaaS ٹوکن (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord)، ادائیگی کی چابیاں (Stripe, Square)، کلاؤڈ
  چابیاں (AWS access key, Twilio, SendGrid, Mailgun)، نجی چابیاں / JWTs،
  کریڈینشل رکھنے والی کنکشن سٹرنگز (`mongodb://user:pass@...`، وغیرہ)، اور
  ایک عمومی `Authorization`/`x-api-key`/`api-key`/`apikey` ہیڈر-ویلیو
  پیٹرن۔ ہیڈر کی شکل کی چابیاں (`authorization`, `x-api-key`, `api-key`,
  `apikey`) ساختی طور پر ریڈیکٹ کی جاتی ہیں (صرف ویلیو، اسکیم کا پیش لفظ جیسے
  `Bearer `/`Basic ` محفوظ) بجائے عمومی ٹیکسٹ ریگیکس کے۔
- گارڈریل کبھی بھی بلاک نہیں کرتا؛ یہ صرف دوبارہ لکھتا ہے (`modifiedPayload` /
  `modifiedResponse`) اور تشریح کرتا ہے (`meta.credentialsRedacted`, `meta.count`)۔

ریگریشن گارڈ: `tests/unit/credential-masker-guardrail.test.ts`۔

## بنیادی کنٹریکٹ (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true چین کو فوری طور پر روک دیتا ہے
  message?: string; // بلاک ہونے پر ظاہر کیا جاتا ہے
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // درخواست کو دوبارہ لکھنے کے لیے preCall کے ذریعے واپس کیا جاتا ہے
  modifiedResponse?: TValue; // جواب کو دوبارہ لکھنے کے لیے postCall کے ذریعے واپس کیا جاتا ہے
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ایک گارڈ ریل `void`، `{}`، یا `{ block: false }` واپس کرکے "کوئی تبدیلی نہیں" کا اشارہ دیتی ہے۔ `modifiedPayload`/`modifiedResponse` واپس کرنے سے چین میں آگے آنے والی گارڈ ریلز تک پہنچنے والی قدر تبدیل ہو جاتی ہے۔
`signal?: AbortSignal` کالر کے لائف سائیکل کو گارڈ ریلز تک پہنچاتا ہے۔ درخواست کا منسوخ ہونا دانستہ fail-open استثنا ہے: میڈیا برجز کام روک دیتے ہیں اور صفائی کرتے ہیں، مگر خام میڈیا کو ایسے ہدف کے لیے بحال نہیں کرتے جس کے بارے میں معلوم ہو کہ وہ اسے سپورٹ نہیں کرتا۔

## رجسٹری (`registry.ts`)

سنگلٹن `guardrailRegistry` درج ذیل سہولیات فراہم کرتی ہے:

- `register(guardrail)` — ایک گارڈ ریل شامل کرتی ہے (یا نارملائزڈ نام کے لحاظ سے تبدیل کرتی ہے) اور
  صعودی `priority` کے مطابق دوبارہ ترتیب دیتی ہے۔
- `clear()` / `list()` — انتظامی معاون فنکشنز۔
- `runPreCallHooks(payload, context)` — فعال گارڈ ریلز پر تکرار کرتی ہے، پے لوڈ کو
  `modifiedPayload` کے ذریعے آگے بڑھاتی ہے، اور پہلے `block: true` پر رک جاتی ہے۔
- `runPostCallHooks(response, context)` — جواب کی جانب بھی یہی بہاؤ استعمال کرتی ہے۔
- `resetGuardrailsForTests({ registerDefaults })` — حالت صاف کرتی ہے اور صاف ستھری ٹیسٹ علیحدگی کے لیے، اختیاری طور پر
  ڈیفالٹس کو دوبارہ رجسٹر کرتی ہے۔

دونوں رنرز `{ blocked, payload|response, results, guardrail?, message? }`
واپس کرتے ہیں، جہاں `results`، `GuardrailExecutionResult` ریکارڈز کی ایک ارے ہے جس میں
ہر گارڈ ریل کے `blocked`، `skipped`، `modified`، `error`، اور `meta` فیلڈز شامل ہوتے ہیں،
جو ٹریسنگ کے لیے مفید ہیں۔

### ہر درخواست کے لیے گارڈ ریلز کو غیر فعال کرنا

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` گارڈ ریل ناموں کی ایک
نقل سے پاک فہرست یکجا کرتا ہے جنہیں موجودہ درخواست کے لیے چھوڑ دینا چاہیے۔
ذرائع (سب اختیاری، سب ضم کیے جاتے ہیں):

- `apiKeyInfo.disabledGuardrails`
- درخواست کی باڈی کا `disabledGuardrails` (اعلیٰ سطح پر)
- درخواست کی باڈی کا `metadata.disabledGuardrails`
- ہیڈر `x-omniroute-disabled-guardrails` (یا قدیمی
  `x-disabled-guardrails`)

اقدار اسٹرنگز کی ارے یا کوما سے جدا کی گئی اسٹرنگ ہو سکتی ہیں؛ ناموں کو
لوئرکیس kebab-case میں نارملائز کیا جاتا ہے (`pii_masker` → `pii-masker`)۔ نتیجہ
`context.disabledGuardrails` کے ذریعے رجسٹری کو دیا جاتا ہے، جو مماثل
گارڈ ریلز کو چھوڑ دیتی ہے (`results` میں `skipped: true`)۔

## عمل درآمد کی ترتیب

`src/sse/handlers/chat.ts` اور `open-sse/handlers/chatCore.ts` سے گزرنے والی ہر درخواست کے لیے:

1. `resolveDisabledGuardrails(...)`، API کلید، باڈی، اور ہیڈرز سے نظر انداز کیے جانے والے عناصر کی فہرست بناتا ہے۔
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ترجیح کی صعودی ترتیب میں گارڈ ریلز چلاتا ہے:
   - غیر فعال گارڈ ریلز کو `skipped` کے طور پر ریکارڈ کیا جاتا ہے۔
   - ہر گارڈ ریل کا `preCall`، `modifiedPayload` کے ذریعے پے لوڈ دوبارہ لکھ سکتا ہے۔
   - پہلا `block: true` سلسلے کو فوری طور پر روک دیتا ہے اور ہینڈلر گارڈ ریل کی جانب سے مسترد کیے جانے کا جواب واپس کرتا ہے۔
3. (ممکنہ طور پر دوبارہ لکھا گیا) پے لوڈ کومبو روٹنگ اور اپ اسٹریم ڈسپیچ میں جاتا ہے۔
4. جواب تیار ہونے کے بعد، `guardrailRegistry.runPostCallHooks(...)` جواب پر یہی سلسلہ چلاتا ہے۔ یہاں `block: true` اپ اسٹریم جواب کو خارج کر دیتا ہے۔

خرابی پیدا کرنے والی گارڈ ریلز کو `error: <message>` کے ساتھ ریکارڈ کیا جاتا ہے اور `logger.warn` کے ذریعے لاگ کیا جاتا ہے، لیکن سلسلہ جاری رہتا ہے — یہ ڈیزائن کے لحاظ سے فیل-اوپن ہے۔

## حسبِ ضرورت Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

مراحل:

1. `BaseGuardrail` کو توسیع دیتے ہوئے `src/lib/guardrails/myGuardrail.ts` بنائیں۔
2. `preCall` اور/یا `postCall` نافذ کریں۔
3. یا تو import کے وقت رجسٹر کریں (`registerDefaultGuardrails` سے push کریں) یا
   runtime پر `guardrailRegistry.register(...)` کو کال کریں — registry اسی normalized نام والے
   کسی بھی سابقہ guardrail کو بدل دیتی ہے۔
4. `tests/unit/` کے تحت ٹیسٹ شامل کریں (موجودہ مثالیں:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)۔

## Injection-guard route coverage اور red-team (مرحلہ 8 · بلاک D)

injection-guard (`createInjectionGuard` / `withInjectionGuard`) ان تمام routes کا احاطہ کرتا ہے
جو user prompts قبول کرتے ہیں۔ یہ `INJECTION_GUARD_MODE` کا احترام کرتا ہے (default `warn` = صرف log؛
`block` = HTTP 400 `SECURITY_001` واپس کرتا ہے)۔

| قسم          | Routes                                                                                                                                               | Default mode |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| متن (موجودہ) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn         |
| تخلیقی       | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn         |
| ڈیٹا         | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn         |

متن اخذ کرنا (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` کا احاطہ کرتا ہے۔

**Red-team (ہر شب، `nightly-llm-security.yml`):** promptfoo تصدیق کرتا ہے کہ ہر route
`INJECTION_GUARD_MODE=block` میں OWASP-LLM corpus کو block کرتا ہے؛ garak probes چلاتا ہے (secret نہ ہونے پر چھوڑ دیتا ہے)۔
`moderations` کو یکسانیت کے لیے شامل کیا گیا ہے — block-mode میں operators اسے
`resolveDisabledGuardrails` کے ذریعے مستثنیٰ کر سکتے ہیں۔

ہر شب چلنے والے workflow (`.github/workflows/nightly-llm-security.yml`، cron + دستی
dispatch) میں دو jobs ہیں:

- **`promptfoo-guard` (blocking)** — `INJECTION_GUARD_MODE=block` کے ساتھ
  `promptfoo eval -c promptfooconfig.yaml` چلاتا ہے۔ ہر مخالفانہ case (مثلاً "ignore all
  previous instructions…"، DAN-style jailbreaks) تصدیق کرتا ہے کہ response میں
  `error.code === "SECURITY_001"` موجود ہے، یعنی guard نے واقعی request مسترد کی۔
- **`garak` (مشاورتی)** — مقامی OmniRoute instance (`http://localhost:20128/v1`) کے خلاف
