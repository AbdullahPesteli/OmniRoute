> **مستند ماخذ:** `src/lib/guardrails/`
> **آخری تازہ کاری:** 2026-08-29 — v3.8.51 (Video Bridge ٹرانسکرپٹ کا ماخذ کالر کی جانب سے بیان کیا جاتا ہے،
> ابھی سرور سے تصدیق شدہ نہیں — #11661 کے مطابق وضاحت کی گئی)

Guardrails، OmniRoute اور اپ اسٹریم فراہم کنندگان کے درمیان حد پر حفاظت، پالیسی، اور مواد کی تبدیلیوں کو نافذ کرتے ہیں۔ ہر guardrail درخواست کے پے لوڈز (`preCall`) اور
اپ اسٹریم جوابات (`postCall`) کا معائنہ کر سکتا ہے (اور اختیاری طور پر انہیں مسترد، تبدیل، یا تشریح شدہ کر سکتا ہے)۔

سسٹم **fail-open** ہے: اگر عمل درآمد کے دوران کوئی guardrail استثنا پیدا کرے، تو رجسٹری
خرابی ریکارڈ کرتی ہے اور درخواست کو ناکام کرنے کے بجائے اگلے guardrail کے ساتھ جاری رہتی ہے۔
بلاک کرنا ایک واضح فیصلہ (`block: true`) ہے، کبھی بھی اتفاقی نتیجہ نہیں۔

## بلٹ ان گارڈ ریلز

رجسٹری خود بخود چھ گارڈ ریلز کو ترجیحی ترتیب میں لوڈ کرتی ہے جب درآمد کی جاتی ہے
(دیکھیں `registry.ts` → `registerDefaultGuardrails()`):

| ترجیح | نام                 | مرحلہ(ات)      | فائل                  |
| ----- | ------------------- | -------------- | --------------------- |
| `5`   | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`   | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`   | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`  | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`  | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`  | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

کم ترجیحی نمبر **پہلے** چلتے ہیں۔

### وژن برج (`visionBridge.ts`) — موڈالٹی برج PR-1

تصویر رکھنے والی درخواستوں کو **غیر وژن ماڈلز** کی طرف نشانہ بناتے ہوئے روکتا ہے اور یا تو
پورے درخواست کو ایک وژن قابل ماڈل کی طرف موڑ دیتا ہے یا تصویر
کے حصوں کو ایک قابل ترتیب وژن ماڈل کی طرف سے تیار کردہ متنی وضاحتوں سے بدل دیتا ہے
اوپر کی کال سے پہلے۔ یہ ٹیکسٹ صرف فراہم کرنے والوں کو شفاف طور پر
ملٹی موڈل پیلوڈز کو سنبھالنے کی اجازت دیتا ہے۔

پروسیس:

1. چھوڑ دیں اگر ہدف ماڈل پہلے ہی وژن کی حمایت کرتا ہے (جب تک کہ یہ
   زبردستی برج کی فہرست `isVisionBridgeForcedModel` میں ظاہر نہ ہو)۔
2. تصویر کے حصے نکالیں `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`)، جو **متحدہ میڈیا
   ڈیٹیکٹر** `detectMediaParts()` کو `open-sse/utils/mediaParts.ts` میں منتقل کرتا ہے — یہ
   واحد سچائی کا ماخذ ہے جو کمبو مطابقت کے فلٹر کے ساتھ مشترک ہے۔
   نکالنا صرف اوپر کی سطح کے حصوں تک محدود ہے جنہیں
   `replaceImageParts` دوبارہ جوڑ سکتا ہے (نکالنا↔بدلنے کا معاہدہ): OpenAI
   `image_url`، Anthropic base64 `source.type:"base64"`، Anthropic URL
   `source.type:"url"`، اور Responses API `input_image`۔ نیسٹڈ ہٹس اور
   صرف اشارے والے حصے کمبو فلٹر مواد ہیں اور کبھی بھی نہیں نکالے جاتے۔
   چھوڑ دیں اگر کچھ نہیں ملا۔
3. رن ٹائم کنفیگ کو حل کریں `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): نئے `modalityBridge*`
   سیٹنگز کی چابیاں جیتتی ہیں؛ وراثتی `visionBridge*` چابیاں ایک **ایک سائیکل
   فیل بیک** (واپسی کی ونڈو) رہتی ہیں۔ جب پل غیر فعال ہو تو کسی بھی میڈیا کی گزرگاہ سے پہلے چھوڑ دیں۔
4. موڈ منتخب کرنے والا (`modalityBridgeVisionMode`، نیچے جدول دیکھیں) فیصلہ کرتا ہے
   موڑنے یا وضاحت کرنے کے درمیان۔ موڑنے سے `modifiedPayload` واپس آتا ہے جس میں صرف `model`
   تبدیل ہوتا ہے، ساتھ ہی میٹا `{ rerouted, fromModel, toModel, imagesKept }`۔
5. وضاحت کا راستہ: تصاویر کو `maxImages` پر محدود کریں، کام سے آگاہ کرنے والا پرامپٹ بنائیں،
   وضاحت کی کیش سے مشورہ کریں، وژن ماڈل کو **پیرالل** میں کال کریں
   (`Promise.allSettled`)، اور `[Image N]: <description>` متنی حصے کو ان کی جگہ میں شامل کریں۔ ناکام وضاحت `null` دیتی ہے اور اصل تصویر کا حصہ **محفوظ** رہتا ہے (#4012) — سوائے کمبو وضاحت کے راستے کے جب ہر
   وضاحت ناکام ہو جاتی ہے، جہاں ایک تصدیق شدہ غیر وژن اوپر کی طرف
   `(unavailable — no vision-capable provider connected)` اسٹب ملتا ہے (#8430)۔
6. واپس کریں `modifiedPayload` + میٹا (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`)۔

#### موڈ منتخب کرنے والا (`modalityBridgeVisionMode`)

| موڈ        | ڈیفالٹ | رویہ                                                                                                                                                                                                                                                           |
| ---------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔      | وراثتی ہیورسٹک، بغیر تبدیلی (#6640/#7204): غیر کمبو/`auto/` ماڈلز بہترین وژن ماڈل کی طرف موڑ دیتے ہیں جب تک کہ اصل ماڈل کے پاس قابل استعمال اسناد نہ ہوں (پھر وضاحت کریں)؛ کمبو ہدف ہمیشہ وضاحت کرتا ہے۔                                                       |
| `describe` |        | ہمیشہ وضاحت کریں — موڑنے کا بلاک مکمل طور پر چھوڑ دیا جاتا ہے؛ صارف کا منتخب کردہ ماڈل ہمیشہ جواب دیتا ہے۔                                                                                                                                                     |
| `reroute`  |        | زبردستی موڑنا: محفوظ کردہ ماڈل گارڈ کو نظر انداز کیا جاتا ہے۔ موڑنے کا **ہدف** اسناد گارڈ اب بھی لاگو ہوتا ہے — جب کوئی قابل استعمال وژن ہدف موجود نہ ہو تو درخواست وضاحت کی طرف گزر جاتی ہے تاکہ خام تصاویر کبھی بھی ٹیکسٹ صرف بیک اینڈ تک نہ پہنچیں (#8430)۔ |

زبردستی موڈ خودکار ہیورسٹک چلنے سے **پہلے** مختصر ہوتے ہیں؛ `auto` کا رویہ
پری-PR-1 گارڈ ریل کے ساتھ بائٹ میں ایک جیسا ہے۔

#### API-key دائرہ (`visionBridgeKeyScope.ts`)

جب کال کرنے والے کی API کلید `allowedConnections`، کوٹہ پولز
(`allowedQuotas`) یا ماڈلز (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) کو محدود کرتی ہے، تو پل صرف
موڑنے اور وضاحت کرنے والے ماڈلز کو منتخب کرتا ہے جنہیں کلید استعمال کر سکتی ہے، ان کنکشنز پر جنہیں کلید استعمال کر سکتی ہے۔ وضاحت کی کال پھر ہمیشہ `x-omniroute-self-loop-key-id` ہیڈر کے ساتھ OmniRoute خود لوپ کے ذریعے جاتی ہے، لہذا وصول کرنے والی چیٹ درخواست
اس کلید کے کنکشن اور ماڈل کی پالیسی کو دوبارہ نافذ کرتی ہے۔ `enforceApiKeyPolicy()`
صرف اس ہیڈر کو خود لوپ بیئرر کے ساتھ مل کر عزت دیتا ہے، لہذا یہ صرف
رسائی کو محدود کر سکتا ہے، اور ایک ID جو حل نہیں ہوتی اسے مسترد کر دیا جاتا ہے۔

اگر کلید کے لیے کوئی وژن ماڈل کی اجازت نہیں ہے، تو وضاحت کا راستہ کنارے پر چلا جاتا ہے اور
درخواست بغیر تبدیلی کے گزر جاتی ہے، وہی ناکام کھلا رویہ جیسے ایک غیر فعال
گارڈ ریل (میٹا `{ skipped: true, reason: "no_permitted_vision_model" }`)۔
بغیر کلید کی درخواستیں، اور ان کلیدوں کے بغیر جو ان پابندیوں کے بغیر ہیں، بالکل پہلے کی طرح برتاؤ کرتی ہیں۔

#### کام سے آگاہ وضاحت پرامپٹ (`modalityBridgeVisionTaskAware`)

ڈیفالٹ **true**۔ `composeVisionPrompt()` (`visionBridgeHelpers.ts`) آخری صارف کے پیغام کا متن (500 حروف تک محدود) بنیادی بیان کرنے والے پرامپٹ میں شامل کرتا ہے، بیان کو اس چیز کی طرف مائل کرتا ہے جو صارف نے واقعی پوچھا (codex-vision-proxy پیٹرن) اور بصری ماڈل سے نظر آنے والے متن کی نقل کرنے کی درخواست کرتا ہے۔ جب یہ پرچم بند ہو — یا کوئی صارف کا متن نہ ہو — تو بنیادی پرامپٹ بغیر کسی تبدیلی کے استعمال کیا جاتا ہے۔

بیان کرنے والے خود لوپ کی اپنی OpenAI-compatible درخواست (`callVisionModelSingle()` `visionBridgeHelpers.ts` میں) ہمیشہ `image_url.detail: "high"` کی درخواست کرتی ہے — بغیر کسی شرط کے، ہر کالر/فراہم کنندہ کے لیے، کسی بھی کلائنٹ سگنل پر نہیں۔ کم تفصیل کے نمونے OCR کی درستگی کو خراب کرتے ہیں بالکل اسی متن کی نقل کرنے کے کام کے لیے جس کی اس پرامپٹ میں درخواست کی گئی ہے، لہذا بیان کرنے والی کال ہمیشہ اعلی تفصیل کی درخواست کرتی ہے چاہے اصل آنے والی درخواست نے کس تفصیل کی سطح کا استعمال کیا ہو۔ یہ صرف اندرونی بیان کرنے والی درخواست کے جسم کو متاثر کرتا ہے؛ یہ OmniRoute کے ذریعے کالر کے اپنے `image_url.detail` کو بنیادی درخواست پر آگے بڑھانے کے طریقے کو نہیں بدلتا — یہ ڈیفالٹ علیحدہ طور پر لاگو ہوتا ہے، اور صرف دریافت شدہ OpenCode کلائنٹس کے لیے، `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) میں۔ بیان کرنے والے خود لوپ کی Anthropic وائر-فارمیٹ شاخ میں کوئی `detail` فیلڈ نہیں ہے اور یہ کسی بھی ڈیفالٹ سے متاثر نہیں ہوتی۔

#### بیان کرنے والے آؤٹ پٹ کی حد (`modalityBridgeVisionMaxChars`)

| کلید                           | ڈیفالٹ | رینج             |
| ------------------------------ | ------ | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`    | `0` یا 100–50000 |

`0` (ڈیفالٹ) کا مطلب ہے **کوئی حد نہیں** — `callVisionModel()` کی طرف سے واپس کردہ بیان بغیر کسی تبدیلی کے گزر جاتا ہے، موجودہ رویے کو برقرار رکھتے ہوئے۔ 100–50000 کی رینج میں کوئی بھی قیمت بیان کو `…` لاحقہ کے ساتھ کاٹ دیتی ہے اس سے پہلے کہ اسے `[Image N]: <description>` کے طور پر دوبارہ شامل کیا جائے (`VisionBridgeGuardrail.preCall()` `src/lib/guardrails/visionBridge.ts` میں)۔ اس کو تفصیل سے بھرپور OCR کے کاموں کے لیے بڑھائیں جہاں نیچے کے ماڈل کو مکمل نقل کی ضرورت ہوتی ہے؛ اسے چٹ چیٹ بصری ماڈلز پر ٹوکن کے استعمال کو محدود کرنے کے لیے کم کریں۔ ڈیش بورڈ کا میدان بصری ٹیب کے ایڈوانسڈ پینل پر موجود ہے (`modality-bridge-max-chars` `ModalityBridgeVisionTab.tsx` میں) اور کسی بھی قیمت کو 1 اور 99 کے درمیان 100 کی بنیاد تک محدود کرتا ہے جبکہ واضح `0` کو بغیر کسی تبدیلی کے چھوڑ دیتا ہے — `0` اپنے حق میں ایک درست Zod قیمت ہے (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`)، صرف "unset" ڈیفالٹ نہیں۔

#### بیان کرنے والا کیش (`modalityBridge/bridgeCache.ts`)

بیان کرنے والے آؤٹ پٹس کے لیے میموری میں LRU + TTL کیش، مشترکہ عمل کے وسیع۔ کلید = `sha256(imageRef + composedPrompt + configuredBridgeModel)` لمبائی-پری فریم کے ساتھ (کوئی فیلڈ-سرحدی ٹکراؤ نہیں)۔ ماڈل جزو **کنفیگر کردہ** پل ماڈل ہے، نہ کہ وہ ماڈل جو واقعی جواب دیتا ہے — `callVisionModel` اندرونی طور پر پیچھے ہٹ سکتا ہے، اور ہر کوشش کے لیے کلید بنانا کیش کو ٹکڑوں میں تقسیم کر دے گا۔ ناکام بیان کبھی بھی کیش نہیں کیے جاتے۔ ترتیبات:

| کلید                            | ڈیفالٹ | رینج    |
| ------------------------------- | ------ | ------- |
| `modalityBridgeCacheEnabled`    | `true` | —       |
| `modalityBridgeCacheTtlMinutes` | `60`   | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`  | 10–5000 |

#### دور دراز کی تصویر کی معمولی شکل (خود لوپ بیان/base64 fetch)

جب پل خود ایک **دور دراز** تصویر حاصل کرتا ہے — Anthropic بیان خود کال اور claude-wire-format base64 تبدیلی (`ensureBase64ImagesForClaudeWire`)، دونوں `fetchRemoteImageAsDataUri()` میں `visionBridgeHelpers.ts` کے ذریعے — نتیجے میں حاصل کردہ ڈیٹا URI کو `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) کے ذریعے گزرنے دیا جاتا ہے اس سے پہلے کہ اسے بصری ماڈل کی درخواست میں شامل کیا جائے۔ زیادہ سائز کی تصاویر کو **2048px لمبی کنارے** پر کم کیا جاتا ہے (جو OpenAI/Anthropic پہلے ہی سرور سائیڈ پر لاگو کرتے ہیں)، جو اپ لوڈ کے بائٹس/لیٹنسی کو کم کرتا ہے بغیر اس کے کہ بصری ماڈل کو کیا نظر آتا ہے۔ دوبارہ سائز دینے کے لیے `sharp` کا استعمال کیا جاتا ہے، جو متحرک درآمد کے ذریعے لوڈ ہوتا ہے: ایک پلیٹ فارم پر جہاں اس کا مقامی بائنری لوڈ ہونے میں ناکام رہتا ہے، `normalizeDataUri()` **کبھی بھی پھینکتا نہیں** — یہ اصل بائٹس کے پاس تھرو پر واپس آتا ہے، لہذا بیان/base64 تبدیلی کا راستہ ہمیشہ کام کرتا رہتا ہے۔ غیر تصویری بائٹس (ایک fetch جو قابل پڑھنے والی تصویر واپس نہیں کرتا) بھی بغیر کسی تبدیلی کے گزر جاتے ہیں۔ یہ معمولی شکل صرف ان تصاویر تک محدود ہے جو پل اپنی خود کال کے لیے حاصل کرتا ہے — یہ کبھی بھی کالر کے خام پاس تھرو پیلوڈ پر لاگو نہیں ہوتی، جو کہ صرف آپٹ ان تبدیلی کے اصول (Hard Rule #20) کے ساتھ ہم آہنگ ہے۔

#### ترتیبات کا خاکہ + ہجرت

نئے `modalityBridge*` کلیدیں `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts` میں) میں Zod کی توثیق کی گئی ہیں: `modalityBridgeVisionEnabled`، `modalityBridgeVisionMode`، `modalityBridgeVisionModel`، `modalityBridgeVisionTaskAware`، `modalityBridgeVisionPrompt`، `modalityBridgeVisionTimeout`، `modalityBridgeVisionMaxImages`، `modalityBridgeVisionMaxChars`، `modalityBridgeCache*` کا تینوں، اور `modalityBridgeAudio*` گروپ جو آڈیو پل کے ذریعہ استعمال ہوتا ہے۔ ہجرت `141_modality_bridge_settings.sql` موجودہ وراثتی `visionBridge*` قیمتوں کو نئے ملتے جلتے کلیدوں میں کاپی کرتی ہے (idempotent، کبھی بھی ایک آپریٹر سیٹ `modalityBridge*` قیمت کو اوور رائٹ نہیں کرتی)؛ وراثتی کلیدیں ایک ریڈ فال بیک کے طور پر ایک ریلیز سائیکل کے لیے قبول کی جاتی رہتی ہیں۔

#### شفافیت ہیڈر + اعداد و شمار

بیان کردہ تبدیل شدہ جوابات میں شامل ہوتا ہے `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` (جو `buildModalityBridgeHeader()` میں بنایا گیا ہے `modalityBridge/bridgeStats.ts` میں، `withModalityBridgeHeader()` کے ذریعے مہر بند کیا گیا ہے `src/sse/handlers/chatHelpers.ts` میں)۔ دوبارہ روٹ کی گئی درخواستوں میں **کوئی** ہیڈر نہیں ہوتا — پیلوڈ بغیر کسی تبدیلی کے تھا اور ماڈل کا تبادلہ پہلے ہی جواب کے جسم کے `model` فیلڈ میں نظر آتا ہے۔

`GET /api/modality-bridge/stats` (انتظامی تصدیق، اسی سطح پر جیسے
`GET /api/settings`) میموری میں ہر موڈالٹی کے لئے کاؤنٹرز واپس کرتا ہے
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` کے لئے `vision`, `audio`, اور
`video`. `averageLatencyMs` `latencySamples` کا استعمال کرتا ہے، تمام کوششوں کا نہیں،
جیسا کہ اس کا مخرج؛ ایک آپریشن بغیر وقت کے صفر ملی سیکنڈ کا نمونہ نہیں بناتا۔
`bridged` کامیاب تبدیلیوں کے لئے پیچھے کی طرف ہم آہنگ متبادل رہتا ہے؛ ناکام کوششیں
اسے بڑھاتی نہیں ہیں۔
کاؤنٹرز عمل دوبارہ شروع ہونے پر ڈیزائن کے مطابق ری سیٹ ہوتے ہیں
(ٹیلی میٹری، حساب نہیں)۔

#### ڈیش بورڈ کی تشکیل

مخصوص ڈیش بورڈ صفحہ ہے
`/dashboard/settings/modality-bridge`. اس کا URL-پتہ `Vision`, `Audio`,
اور `Video` ٹیبز کو `tab` کی قیمت تبدیل کرتے وقت کوئری پیرامیٹرز کو محفوظ رکھتا ہے۔
ویژن ٹیب فعال کرنے، موڈ، ماڈل کے انتخاب (خودکار
ڈیفالٹ سمیت)، کام سے آگاہ پرامپٹنگ، جدید ٹائم آؤٹ/تصویر/تفصیل کی لمبائی/کیچ
حدود، رن ٹائم
کاؤنٹرز، اور ایک محفوظ نمونہ درخواست کو ظاہر کرتا ہے۔ آڈیو ٹیب بھی زندہ ہے: یہ
فعال کرنے، STT-صرف ماڈل چننے والے کے ساتھ خودکار، ٹائم آؤٹ/زیادہ سے زیادہ کلپ کی حدود، آڈیو
کاؤنٹرز، اور ایک `input_audio` نمونہ ٹیسٹ کو ظاہر کرتا ہے۔ ویڈیو ٹیب فعال ہے: یہ
FFmpeg/ffprobe رن ٹائم حالت کی رپورٹ کرتا ہے — چار واضح UI حالتوں میں سے ایک
(`unknown` جب پروب پرواز میں ہے یا مکمل نہیں ہو سکا، `restricted` ایک غیر لوپ بیک
ڈیش بورڈ میزبان پر جہاں پروب کلائنٹ سائیڈ پر چھوڑ دیا گیا ہے، `unavailable` جب پروب کیا
گیا اور غائب ہونے کی تصدیق کی گئی، یا `available` FFmpeg/ffprobe ورژن کے ساتھ) —
فعال/ماڈل/فریم/ویڈیو/ٹائم آؤٹ کی حدود کو برقرار رکھتا ہے، ماڈل چننے والے کو بصری
قابل ماڈلز تک محدود کرتا ہے، اور ویڈیو کاؤنٹرز کو ظاہر کرتا ہے۔

AI سیٹنگز کے تحت سابقہ ویژن برج کارڈ ایک ہم آہنگی کا لنک ہے
نئے صفحے کے لئے؛ یہ اب فارم کی دوسری کاپی کا مالک نہیں ہے۔ میڈیا فراہم کنندگان بھی
تصویر سے متن اور تقریر سے متن کے ورک فلو کو متعلقہ موڈالٹی
برج ٹیبز سے جوڑتے ہیں بغیر موجودہ تقریر سے متن کے کھیل کے میدان کو ہٹائے۔

**خود لوپ داخلہ بائی پاس:** جب بیان کال OmniRoute کے اپنے `/v1` خود لوپ کے ذریعے
روٹ کرتی ہے (غیر معیاری فراہم کنندہ ماڈل)، ذیلی درخواست بھیجتی ہے
`x-omniroute-admission-bypass: internal` اور حل شدہ
خود لوپ سند کے ساتھ تصدیق کی جاتی ہے — مقامی `sk_omniroute` سینٹینل مقامی موڈ میں، یا
آپریٹر کی تشکیل کردہ `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env کلید (#1350) تاکہ
`REQUIRE_API_KEY=true` تعیناتیاں اب بھی بیان کال چلا سکیں۔ یہ بائی پاس
صرف ان مخصوص اسناد کے لئے تسلیم کیا جاتا ہے، لہذا بیرونی کلائنٹس ہیڈر کا استعمال
کر کے داخلے کو چھوڑ نہیں سکتے۔

وراثتی ڈیفالٹس `src/shared/constants/visionBridgeDefaults.ts` میں موجود ہیں؛
نئے موڈ/کام سے آگاہ/کیچ ڈیفالٹس اور سیٹنگز ریزولور
`src/shared/constants/modalityBridgeDefaults.ts` میں موجود ہیں۔ گارڈریل ایک
`deps` کنسٹرکٹر آپشن کو ظاہر کرتا ہے تاکہ ٹیسٹ جعلی `getSettings` اور
`callVisionModel` کے نفاذ کو داخل کر سکیں۔

### آڈیو برج (`audioBridge.ts`) — موڈالٹی برج PR-3

آڈیو رکھنے والی چیٹ درخواستوں کو اس ہدف سے پہلے روک دیتا ہے جو
آڈیو ان پٹ قبول کرنے کے لئے جانا نہیں جاتا۔ یہ کبھی بھی چیٹ درخواست کو دوبارہ روٹ نہیں کرتا: آڈیو کے حصے
موجودہ OpenAI-ہم آہنگ ملٹی پارٹ اینڈ پوائنٹ کے ذریعے نقل کیے جاتے ہیں اور
چنا ہوا چیٹ ماڈل متن کی نقل کے ساتھ جاری رہتا ہے۔

پروسیس:

1. `supportsAudio` کو `getResolvedModelCapabilities()` کے ذریعے حل کریں۔ واضح
   فراہم کنندہ-رجسٹری میٹا ڈیٹا جیتتا ہے، پھر سٹیٹک ماڈل میٹا ڈیٹا، پھر ہم آہنگ
   `modalities_input`. ایک اعلان کردہ ان پٹ فہرست بغیر `audio` کے `false` ہے؛ کوئی
   صلاحیت کا ثبوت `null` رہتا ہے۔ دونوں `false` اور `null` محتاط برج کو فعال کرتے ہیں،
   جبکہ `true` اسے بائی پاس کرتا ہے۔
2. `modalityBridgeAudio*` سیٹنگز کو حل کریں اور ہر پیغام سے اسپلیسیبل ٹاپ لیول
   آڈیو حصے نکالیں مشترکہ `detectMediaParts()`
   ڈیٹیکٹر کے ذریعے۔ سپورٹ شدہ وائر شکلیں OpenAI `input_audio`, `audio_url`, اور
   `source.media_type: "audio/*"` ہیں۔ نیسٹڈ آڈیو روٹنگ کے لئے پتہ لگایا جاتا ہے لیکن
   اسپلیس راستے کے ذریعے ہٹایا نہیں جاتا۔ کام `modalityBridgeAudioMaxClips` سے محدود ہے؛
   بعد کے حصے بغیر تبدیلی کے رہتے ہیں۔
3. ایک تشکیل شدہ `provider/model` کی عزت کریں، یا `selectAudioBridgeModel()` کو
   مستحکم کیٹلاگ ترتیب میں `AUDIO_TRANSCRIPTION_PROVIDERS` کو چلنے دیں اور پہلے
   ماڈل کا انتخاب کریں جس کے پاس قابل استعمال فعال فراہم کنندہ سند ہو۔
4. `callAudioTranscription()` base64/data-URI آڈیو کو ایک ملٹی پارٹ
   `file` میں تبدیل کرتا ہے، یا عوامی صرف آؤٹ باؤنڈ
   گارڈ کے ذریعے DNS پننگ اور 25 MB کی حد کے ساتھ ایک دور دراز `audio_url` ڈاؤن لوڈ کرتا ہے۔
   پھر یہ فائل اور منتخب ماڈل کو مقامی `/v1/audio/transcriptions` خود لوپ پر POST کرتا ہے،
   جو `resolveSelfLoopBearer()` کے ساتھ تصدیق شدہ ہے۔ موجودہ نقل کا راستہ معمول کے
   سند کی تلاش، کول ڈاؤن/ریٹ-حد کی ہینڈلنگ، اور فراہم کنندہ کی تقسیم کرتا ہے۔
5. کامیاب کالز اپنے حصے کو `[Audio N]: <transcript>` سے تبدیل کرتی ہیں۔ کالز
   `Promise.allSettled` کے ساتھ چلتی ہیں: ایک انفرادی ناکامی اصل
   آڈیو حصے کو محفوظ رکھتی ہے (#4012 معاہدہ)۔ اگر ہر کال ناکام ہو جاتی ہے اور ہدف ثابت
   `supportsAudio === false` ہے، تو حصے بن جاتے ہیں
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 معاہدہ)۔ ایک نامعلوم ہدف
   (`null`) کے لئے، ایک مکمل ناکامی کا نتیجہ بغیر تبدیلی کے رہتا ہے۔ ایک ثابت
   ٹیکسٹ-صرف ہدف جس کے پاس کوئی قابل استعمال STT سند نہیں ہے وہ اسی واضح
   اسٹب کو وصول کرتا ہے بغیر نیٹ ورک کال جاری کیے۔

کامیاب نقلیں پروسیس-وائیڈ موڈالٹی برج LRU/TTL کیش کا استعمال کرتی ہیں۔ کلید
آڈیو حوالہ، مستحکم `audio-transcription` آپریشن لیبل، اور منتخب STT ماڈل کو ملا کر بنتی ہے؛ ناکامیاں کبھی بھی کیش نہیں کی جاتیں۔ آڈیو کی کوششیں مشترکہ `bridged`, `cacheHits`, `failures`, اور `lastUsedAt` کاؤنٹرز کو اپ ڈیٹ کرتی ہیں۔
تبدیل شدہ جوابات لے کر آتے ہیں
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`؛ بغیر تبدیلی کے
درخواستیں آڈیو برج کے حصے کو نہیں پاتی ہیں۔

رن ٹائم سیٹنگز DB-بیکڈ اور Zod-ویلیڈیٹڈ ہیں:

| کلید                          | ڈیفالٹ  | رینج           |
| ----------------------------- | ------- | -------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —              |
| `modalityBridgeAudioModel`    | `""`    | Auto یا STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000    |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10           |

شیئر کردہ کیش `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, اور `modalityBridgeCacheMaxEntries` کے ذریعے کنٹرول کیا جاتا ہے۔

چیٹ مکملات `messages` اور جوابات API `input` میں ہدف سے پہلے اعلیٰ سطح کے ویڈیو حصوں کو روکتا ہے جس کے بارے میں معلوم نہیں ہے کہ اس میں مقامی ویڈیو سپورٹ ہے۔ سپورٹ کردہ شکلیں `input_video`, `video_url`, `video_source`, HTTPS URLs,
اور `data:video/*;base64,...` ڈیٹا URI ہیں۔ متن میں سادہ فائل کے نام کو ویڈیو کے طور پر نہیں سمجھا جاتا۔

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) درخواست کی گزرگاہ، صلاحیت/پالیسی کی جانچ، فی درخواست جمع کرنا، اور جواب کا مواد سنبھالتا ہے۔ فی ویڈیو کام — حصول، مکمل نتیجہ کی کیش، ایک فریم کی ترتیب کی وضاحت کرنا (جو کسی بھی کالر کے اعلان کردہ آڈیو نقل کو ضم کرتا ہے)، اور فی کوشش میٹرکس/منسوخی/صفائی — `processVideoPart` کے پیچھے چھپا ہوا ہے جو `videoBridgePipeline.ts` میں ہے، جو `preCall` کے لوپ کے اندر ہر ویڈیو حصے کے لیے ایک بار کال کیا جاتا ہے۔ یہ ماڈیول واضح پورٹ کی سرحدیں بھی متعین کرتا ہے `VideoMediaBrokerPort`
(بائٹس حاصل کرنا اور نمونہ شدہ فریم نکالنا)، `VideoAudioTranscriptionPort`
(کالر کے اعلان کردہ آڈیو نقل کو نمونہ شدہ کیپشنز کے ساتھ ضم کرنا)، اور
`VideoDrilldownPort` (ورثے کی خام اسٹور شکل)۔ پیداوار STT اور فریم کی برقرار رکھنے کی تشکیل بیان کرنے والے پورٹ کے گرد `createVideoSttAdapter` اور
`createVideoDrilldownAdapter` کے ذریعے کی گئی ہے؛ آخری مشترکہ غیر شفاف ہینڈل کی زندگی کے چکر کا استعمال کرتا ہے۔

عوامی `/v1` درخواست کا راستہ کبھی بھی کسی ذیلی عمل کو درآمد یا متحرک نہیں کرتا۔ دور دراز ویڈیوز 50 MiB کی حد کے تحت ڈاؤن لوڈ کی جاتی ہیں؛ ان لائن بیس64 ویڈیوز کے پاس ایک محتاط 36 MiB کی ڈی کوڈ شدہ فی ویڈیو کیپ ہے تاکہ ماڈل/پیغامات/فریمنگ لفافہ عوامی JSON درخواست کی داخلے کی حد 50 MiB کے اندر رہ سکے۔ مختصر لمبائی اور ڈی کوڈ شدہ سائز کے تخمینے مختص کرنے سے پہلے چیک کیے جاتے ہیں۔ HTTPS ابتدائی دور دراز URL اور ہر ری ڈائریکٹ پر درکار ہے، موجودہ عوامی صرف آؤٹ باؤنڈ گارڈ کے ساتھ DNS پننگ کا استعمال کرتے ہوئے۔ بائٹس پھر بالکل اندرونی `POST /api/modality-bridge/video/extract` بروکر کی سرحد عبور کرتے ہیں۔ یہ راستہ `LOCAL_ONLY` اور `SPAWN_CAPABLE` دونوں ہے، صرف فی عمل کی تصدیق شدہ، قابل اعتماد لوپ بیک درخواست کو قبول کرتا ہے، اور کبھی بھی URL، فائل سسٹم کا راستہ، قابل عمل، یا دلیل کی فہرست کو قبول نہیں کرتا۔ API جسم کے سائز کی پائپ لائن اور ہینڈلر کے انکریمنٹل باڈی ریڈر آزادانہ طور پر 50 MiB بروکر کی ان پٹ کیپ کو نافذ کرتے ہیں۔ اس کی محدود قطار ایک بار میں ایک نکاسی کو چلاتی ہے، چار زیر التوا ملازمتوں کی اجازت دیتی ہے، اور زیر التوا ان پٹ کو 100 MiB پر محدود کرتی ہے۔

بروکر کے اندر، `ffprobe` ایک نجی مقامی فائل کو پڑھتا ہے؛ مقررہ شکل کی اجازت کی فہرست پلے لسٹ اور مینیفیسٹ کی شکلوں کو خارج کرتی ہے۔ اجازت یافتہ MOV-خاندان کے کنٹینرز کے لیے، بیرونی MOV ڈیٹا کے حوالہ جات بطور ڈیفالٹ غیر فعال رہتے ہیں، اور مقررہ کمانڈ ان میں شامل ہونے کا انتخاب نہیں کرتی۔ دونوں `ffprobe` اور `ffmpeg` `file`-صرف پروٹوکول کی اجازت کی فہرست، ایک دھاگہ، مقررہ دلیل کے ارے، کوئی شیل، اور `PATH` سے حل شدہ قابل عمل استعمال کرتے ہیں۔ منسلک تصویر کے کور اسٹریم قابل پلے امیدوار نہیں ہیں۔ تمام قابل پلے اسٹریمز کو حدود کو پورا کرنا چاہیے، اور ایک واضح ڈیفالٹ اسٹریم کو ترجیح دی جاتی ہے اس سے پہلے کہ متعین کم از کم انڈیکس کی فالس بیک ہو۔ ویڈیوز 600 سیکنڈ، 8,192 پکسلز فی جہت، اور 33,554,432 ماخذ پکسلز تک محدود ہیں۔ FFmpeg 1–16 درمیانی JPEG فریمز کا نمونہ لیتا ہے، طویل کنارے کو زیادہ سے زیادہ 1,024 پکسلز تک کم کرتا ہے بغیر چھوٹے ان پٹ کو اپ اسکیل کیے، اور کبھی بھی URL وصول نہیں کرتا۔ نمونہ لینا بطور ڈیفالٹ `uniform` ہے۔ اختیاری `scene_aware` اور تجرباتی `segment_aware` پالیسیاں پہلے سے تصدیق شدہ مقامی اسٹریم پر ایک اضافی مقررہ FFmpeg پاس کرتی ہیں، محدود `showinfo` منظر کے وقت کی مہریں منتخب کرتی ہیں، اور متعین ناکامی، وقت ختم ہونے، غلط شکل کے آؤٹ پٹ، یا خالی امیدوار سیٹ پر متعین طور پر اسی یکساں درمیانی نکات پر واپس آتی ہیں۔ سیگمنٹ-آگاہ موڈ تصدیق شدہ منظر کے وقفوں کے تناسب سے درمیانی نمونہ مختص کرتا ہے؛ سیگمنٹ-آگاہ ثبوت اور فالس بیک کے رویے کی تفصیلات نیچے دی گئی ہیں۔ سخت 16-فریم کیپ ہر پالیسی میں انتخاب کے بعد لاگو ہوتی ہے۔ جب ایک منظر-آگاہ درخواست کے پاس صرف ایک فریم کا بجٹ ہوتا ہے، تو یہ فعال مکمل ویڈیو یا توجہ کے ونڈو کے یکساں درمیانی نقطے کا استعمال کرتی ہے اور `policyEffective: uniform` کی رپورٹ کرتی ہے: ایک منتخب منظر کے فریم دونوں وقتی سرے کو محفوظ نہیں رکھ سکتا۔ ایک کالر اختیاری طور پر ایک محدود توجہ کے ونڈو (`start`/`end` سیکنڈ) فراہم کر سکتا ہے؛ حدود میڈیا کی مدت پر لگائی جاتی ہیں، الٹی یا غیر محدود ونڈوز کو مسترد کیا جاتا ہے، اور تمام نمونہ لینے کی پالیسیاں صرف معیاری وقفے کے اندر انجام دی جاتی ہیں۔ نتیجے میں آنے والا ونڈو نمونہ لینے کے میٹا ڈیٹا میں اور غیر معتبر وضاحت کے پیشگی میں شامل کیا جاتا ہے تاکہ نیچے کے ماڈل ایک توجہ مرکوز اقتباس کو مکمل ٹائم لائن سے ممتاز کر سکیں۔

سمیٹک کیپشن توجہ ایک علیحدہ، واضح سیٹنگ ہے۔ ڈیفالٹ `full`
تجزیاتی موڈ موجودہ فریم کے اشارے کو محفوظ رکھتا ہے اور کبھی بھی درخواست کے متن کو کیپشن ماڈل کو آگے نہیں بڑھاتا۔ `focused` موڈ میں، برج صرف تازہ ترین غیر خالی صارف کے تخلیق کردہ `text`/`input_text` کو اسی چیٹ یا جوابات کے کنٹینر سے پڑھتا ہے، اسے NFC میں معیاری بناتا ہے، کنٹرول کرداروں اور سفید جگہ کو کم کرتا ہے، اور اسے 500 Unicode کوڈ پوائنٹس تک محدود کرتا ہے۔ ایک خالی نتیجہ بالکل `full` اشارے پر واپس آتا ہے۔ ایک قابل استعمال اشارہ ایک مخصوص غیر معتبر صارف کے سیاق و سباق کے بلاک میں JSON کے طور پر سیریلائز کیا جاتا ہے اور صرف قابل مشاہدہ تفصیلات کو ترجیح دے سکتا ہے؛ یہ میڈیا میں نظر آنے یا سننے میں ہدایات کی پیروی کرنے کے خلاف علیحدہ انتباہ کو ختم نہیں کر سکتا۔ متنی توجہ کبھی بھی `start`/`end` کا اندازہ نہیں لگاتی یا وقتی نمونہ لینے والے کو تبدیل نہیں کرتی۔

#### FU-07 ساختی سیگمنٹ ثبوت

`segment_aware` پہلے سے تصدیق شدہ مقامی ویڈیو اسٹریم پر ایک محدود پیش تجزیاتی پاس استعمال کرتا ہے۔ مقررہ فلٹر چین پہلے زیادہ سے زیادہ 320 پکسل چوڑا اسکیل کرتا ہے، منظر کی تبدیلیوں اور منجمد وقفوں کا پتہ لگاتا ہے، پھر دھندلاہٹ، اوسط لُما، اور مکانی/وقتی معلومات کے لیے فی سیکنڈ 1 فریم کا نمونہ لیتا ہے۔ یہ پاس 600 ساختی نمونوں، ایک FFmpeg/filter تھریڈ، اسی `file`-only پروٹوکول اور کنٹینر کی اجازت کی فہرستوں، 1 MiB پروسیس-آؤٹ پٹ کی حد، اور بروکر کے مشترکہ منسوخی/آخری تاریخ کے اندر زیادہ سے زیادہ 30 سیکنڈ تک محدود ہے۔ یہ کبھی بھی درخواست سے کوئی کمانڈ، فلٹر، راستہ، یا URL قبول نہیں کرتا۔

ساختی اقدار متعین نمونہ لینے کے شواہد ہیں، نہ کہ معنوی ویڈیو کی تفہیم۔ یہ مضامین، اعمال، عنوانات، تقریر، یا صارف کی نیت کا اندازہ نہیں لگاتے۔ منظر اور منجمد کی سرحدیں حصے بناتی ہیں؛ منجمد کوریج، دھندلاہٹ، نمائش، مکانی تفصیل، اور وقتی تبدیلی صرف اس بات پر اثر انداز ہوتی ہیں کہ موجودہ 1–16 فریم کا بجٹ کیسے مختص کیا جاتا ہے۔ ایک مکمل طور پر منجمد حصہ ایک فریم پر محدود ہے، جبکہ غیر منجمد حصے باقی بجٹ کے لیے مقابلہ کرتے ہیں۔ جب سرحدیں فریمز کی تعداد سے زیادہ ہوں تو یکساں ٹائم لائن کوریج برقرار رکھی جاتی ہے تاکہ تیز ابتدائی کٹ ایک طویل پیچھے رہ جانے والے حصے کو چھپا نہ سکے۔ ایک منجمد سرحد کے 1 سیکنڈ کے تجزیاتی حل کے اندر منظر کی سرحدیں یکجا کی جاتی ہیں۔

غائب فلٹرز، غلط شکل میں/خالی شواہد، ایک ڈیٹیکٹر کی غلطی، یا محدود پیش تجزیاتی ٹائم آؤٹ درست یکساں وسطی پالیسی پر کھل جاتے ہیں۔ ایک کالر کی منسوخی یا بروکر کی آخری تاریخ کھلنے میں ناکام ہوتی ہے: یہ زیر پرواز ذیلی عمل کو ختم کرتی ہے، بعد میں فریم نکالنے سے روکتی ہے، اور نجی عارضی درخت کو `finally` میں ہٹا دیتی ہے۔

`scripts/perf/video-bridge-fu07-eval.ts` پوسٹ-ڈیڈوپ عنوان-کال کی بچت، کثیف-حرکت بجٹ کی مختص، دھندلاہٹ/نمائش/SI-TI شواہد، طویل دم کے ساتھ تیز کٹ، اور بتدریج مدھم جھوٹی مثبتات کے لیے متعین حقیقی FFmpeg کے فکسچر تیار کرتا ہے۔ یہ پیش تجزیاتی دیوار کے وقت کو ریکارڈ کرتا ہے اور، جہاں `/usr/bin/time` دستیاب ہے، بچے کے CPU اور عروجی RSS کو بھی۔ اس کے معیار کے چیک صرف ساختی اوریکل ہیں۔ حقیقی عنوان-ماڈل کا معیار `HOLD` پر رہتا ہے کیونکہ اس ہارنس کے پاس کوئی مجاز اینڈپوائنٹ یا منجمد جج نہیں ہے۔ مالی بچت بھی `HOLD` پر رہتی ہے جب تک کہ `--caption-cost-per-call-usd` ایک واضح مثبت فی کال تخمینہ فراہم نہ کرے؛ اسکرپٹ کبھی بھی کسی نتیجے کو جعلی نہیں بناتا۔

ہر فریم 4 MiB تک محدود ہے، تمام خام فریمز کو ملا کر 23 MiB تک، اور سیریلائزڈ بروکر کا جواب 32 MiB تک۔ ایک نجی عارضی ڈائریکٹری `finally` میں ہٹا دی جاتی ہے۔ OmniRoute FFmpeg کو باندھتا نہیں ہے اور نہ ہی ایک حسب ضرورت قابل عمل راستہ قبول کرتا ہے۔ عنوان دینے سے پہلے، پل ایک محتاط بصری ڈیڈوپلیکیشن پاس لگاتا ہے: ہر JPEG کو 16×16 گری اسکیل بفر میں کم کیا جاتا ہے اور صرف آخری محفوظ فریم کے ساتھ موازنہ کیا جاتا ہے۔ ایک درخواست کردہ عنوان بجٹ ایک فریم سے زیادہ ہونے پر، نکاسی ایک محدود امیدوار پول فراہم کرتی ہے جو اس بجٹ سے دوگنا تک ہو سکتی ہے اور کبھی بھی 16 فریم سے زیادہ نہیں۔ درخواست کردہ حد صرف ڈیڈوپلیکیشن کے بعد لاگو کی جاتی ہے، پہلے اور آخری منتخب امیدواروں کو آخری پتلا کرنے کے دوران محفوظ کیا جاتا ہے جب بجٹ کم از کم دو ہو۔ ورژن شدہ `grayscale-16x16-mean-cells-v2` پالیسی اوسط لُما ڈیلٹا اور تھمب نیل سیلز کے تناسب میں سے بڑے کا استعمال کرتی ہے جن کا معمولی ڈیلٹا کم از کم 0.05 ہے۔ نقل کا تھریشولڈ مستقل 0.04 ہے، جو پیش گوئی کے لیے منتخب کیا گیا ہے نہ کہ ایک رن ٹائم سیٹنگ کے طور پر ظاہر کیا گیا ہے۔ یہ ثانوی ہائی-کنٹراسٹ سگنل چھوٹے حرکت اور نظر آنے والے متن کی تبدیلیوں کو محفوظ رکھتا ہے جو صرف اوسط موازنہ چھپا سکتا ہے۔ موازنہ کرنے والے یا ڈیکوڈر کی غلطیاں کھل جاتی ہیں اور کوریج کو برقرار رکھتی ہیں۔ آؤٹ پٹ میٹاڈیٹا نکالے گئے امیدواروں، کامیابی سے استعمال ہونے والے فریمز، اور بصری نقلوں کو الگ کرتا ہے۔

ایک واضح طور پر نشان زدہ ویڈیو حصہ ایک ٹائم اسٹیمپ شدہ رابطہ شیٹ کی درخواست کر سکتا ہے۔ پل زیادہ سے زیادہ 4 کالم، 16 فریم JPEG گرڈ بناتا ہے۔ ہر 512 پکسل سیل اپنے ماخذ کے ٹائم اسٹیمپ کو ایک ہائی-کنٹراسٹ نیچے کی پٹی میں جلا دیتا ہے، جبکہ وہی ٹائم اسٹیمپس ٹیکسٹ میٹاڈیٹا میں نیچے کی جانب تعلق اور آڈٹ کے لیے رہتے ہیں۔ مکمل JPEG 32 MiB پر محدود رہتا ہے۔ اگر `sharp` گرڈ کو ڈیکوڈ یا ترتیب نہیں دے سکتا تو پل انفرادی JPEG فریمز پر واپس آتا ہے؛ ایک کلائنٹ کی منسوخی پھر بھی شیٹ کے عمل کے ذریعے پھیلتی ہے۔

پروموشن کے شواہد جان بوجھ کر مصنوعی ترکیب مائیکرو بینچ مارک سے الگ ہیں۔ `scripts/perf/video-bridge-contact-sheet-eval.ts` حقیقی OpenAI-ہم آہنگ بصری ماڈلز کے لیے ایک اسکیمہ-ورژنڈ A/B ہارنس کی وضاحت کرتا ہے۔ یہ فراہم کنندہ کی رپورٹ کردہ ٹوکنز، آخر تک دیوار کی تاخیر (شیٹ کی ترکیب سمیت)، ماڈل-کال کی تعداد، اور مینیفیسٹ کی تعریف کردہ حقیقت کی برقرار رکھنے کی پیمائش کرتا ہے۔ خام ماڈل کے جوابات رپورٹ میں نہیں لکھے جاتے؛ صرف SHA-256 ڈائجسٹ اور میچ کردہ حقیقت کے IDs محفوظ کیے جاتے ہیں۔ یہ ہارنس کوئی نیٹ ورک یا ادائیگی ماڈل کی کال نہیں کرتا جب تک کہ `--execute-real` پاس نہ کیا جائے اور `--model`، `OMNIROUTE_BASE_URL`، اور `OMNIROUTE_API_KEY` ترتیب نہ دیے جائیں۔ اس واضح حقیقی رن کے بغیر، اس کا مشین-پڑھنے والا فیصلہ `HOLD` پر رہتا ہے؛ مصنوعی پے لوڈ/کال-شمار کی پیمائش اکیلے پروموشن کے شواہد نہیں ہیں۔

الگ `scripts/perf/video-bridge-promotion-eval.ts` FU-07 یا FU-09 مشاہدات کو استعمال کرتا ہے۔ پروموشن کی قبولیت کے لیے تمام آٹھ مصنوعی منظرنامے کی اقسام کے ساتھ ساتھ ایک صاف شدہ حقیقی کلپ کی ضرورت ہوتی ہے، ہر کردار اور کیس کے لیے کم از کم تین ماپی گئی تکرار، تمام دس اعلان کردہ میٹرکس، منجمد میڈیا/پرومپٹ/متوقع حقیقت/ترتیب کے ڈائجسٹ، منفرد مشاہدے کے IDs اور تصدیق شدہ بیجڈ A/B ترتیب۔ عمل درآمد کی رسید مجموعہ کے ڈائجسٹ، درست امیدوار SHA اور ماڈل کی ترمیم کو باندھتی ہے۔ غائب یا غلط ماپیں `HOLD` پر رہتی ہیں، بشمول CPU 30 سیکنڈ سے زیادہ، عروجی RSS 512 MiB سے زیادہ یا پیش تجزیاتی 30 سیکنڈ سے زیادہ۔ یہ شواہد-قبولیت کی حدود ہیں، نہ کہ ایک نئی رن ٹائم RSS نافذ کرنے کی ضمانت۔

FU-07 کو کم از کم 98% معیار کی برقرار رکھنے اور p95 کی تاخیر کو 1.2x بیس لائن سے زیادہ نہیں ہونا چاہیے، اس کے علاوہ یا تو 0.05 کی مطلق کیس بیلنسڈ اوسط یاد دہانی میں بہتری ہونی چاہیے جو مساوی اوسط کیپشن کالز پر ہو، یا کم از کم 10% کم اوسط پوسٹ-ڈی ڈوپ کیپشن کالز ہونی چاہئیں۔ FU-09 کو کم از کم 0.85 معیار، 95% برقرار رکھنے، 20% p95 کی تاخیر میں کمی اور 10% ٹوکن میں کمی کی ضرورت ہے۔ اہم حقیقت کا نقصان، انجیکشن کی تعمیل یا استعمال کی کمی ترقی کو روکتی ہے۔ ایک عمل کسی چیز کو ترقی نہیں دے سکتا: `--previous-report` اسی پالیسی/ماڈل کی نظرثانی/امیدوار/کارپس کے دو مختلف، غیر اوورلیپنگ، تسلسل سے اہل عملوں کی تصدیق کرتا ہے۔ ایک نمونہ تجربہ ایک رابطہ شیٹ کے تجربے کی تصدیق نہیں کر سکتا۔

جمع کرنے والوں کو یادداشت میں جوابات کی درجہ بندی کرنی چاہیے اور `responseDigest` کے ساتھ ساتھ میٹرکس اور مشاہدے کی بائنڈنگز کو محفوظ کرنا چاہیے، کبھی بھی جواب کا متن نہیں۔ صارف بھی وراثتی خام مشاہدات کو پڑھتا ہے لیکن کبھی بھی اس متن کو اپنی رپورٹوں میں نقل نہیں کرتا۔ ہر مشاہدے کے لیے بالکل ایک `responseDigest` یا `rawResponseText` قبول کیا جاتا ہے۔ ورژنڈ الاؤ لسٹ خالی رہتا ہے جس میں ایک ناقابل تبدیلی `hold` ڈیفالٹ ہوتا ہے۔ ایک اہل اندراج کے لیے اس کے ثبوت کا حوالہ، پالیسی، ماڈل کی نظرثانی، درست امیدوار SHA، مینیفیسٹ ڈائجسٹ اور دو مختلف رن IDs کی ضرورت ہوتی ہے؛ متضاد سیاق و سباق کو مسترد کر دیا جاتا ہے۔ یہ میٹا ڈیٹا ایک آڈٹ معاہدہ ہے، یہ ثابت نہیں کہ حوالہ دیا گیا فائل حقیقی پیمائشات پر مشتمل ہے۔ کسی بھی اندراج کو شامل کرنے سے پہلے حقیقی رسیدوں کا جائزہ لیں۔ انتظامی اعداد و شمار کا اینڈ پوائنٹ اور ویڈیو ڈیش بورڈ محتاط تیاری کو ظاہر کرتے ہیں۔ ایک ترتیب دی گئی ماڈل ایلیاس اکیلا اس کی نظرثانی یا چلنے والے امیدوار SHA کو قائم نہیں کرتا، لہذا موجودہ ڈیش بورڈ `HOLD` کی رپورٹ کرتا ہے بجائے اس کے کہ کسی دوسرے عمل کے سیاق و سباق سے اہلیت کو دوبارہ استعمال کرے۔ واضح تجرباتی انتخاب ترقی سے الگ رہتا ہے؛ کوئی ڈیفالٹ خود بخود تبدیل نہیں ہوتا۔

کال کرنے والے ایک آپشنل `transcript.cues` ارے کو ایک سپورٹ شدہ ویڈیو حصے سے منسلک کر سکتے ہیں جب ان کے پاس پہلے سے ہی ہم آہنگ متن موجود ہو۔ ہر اشارہ میں `text`، ایک محدود `start`/`end` وقفہ ہونا چاہیے جو جانچے گئے دورانیے کے اندر ہو، اور ایک وائٹ لسٹڈ `source` (`client`, `embedded`, یا `audio-bridge`); `confidence` کا ڈیفالٹ `1` ہے اور اسے `0` اور `1` کے درمیان رہنا چاہیے۔ بالکل ایک جیسے اشارے کو سمیٹا جاتا ہے۔ OmniRoute کبھی بھی اس میٹا ڈیٹا سے نقل نویسی شروع نہیں کرتا: تصدیق شدہ اشارے بیان کردہ نتیجے میں ماخذ، اعتماد، اور وقفے کے ساتھ کاپی کیے جاتے ہیں، اور انہیں فریم کیپشنز کے ساتھ غیر معتبر مشاہدات کے طور پر پیش کیا جاتا ہے۔ غیر درست، حد سے باہر، یا ماخذ سے آزاد متن کو مسترد کر دیا جاتا ہے بجائے اس کے کہ اسے کیپشن اسٹریم میں ملایا جائے۔ دونوں درخواست-باڈی نقل نویسی چینلز فراہم کردہ ماخذ کو `client` میں معمول پر لاتے ہیں، بشمول خود-مؤکد `embedded` یا `audio-bridge` لیبلز۔ صرف ایک سرور کے زیر ملکیت ایڈاپٹر ان قابل اعتماد لیبلز کو کوڈ-صرف `trustedSource` دلیل کے ذریعے تفویض کر سکتا ہے؛ ایک درخواست JSON فیلڈ اس دلیل تک نہیں پہنچ سکتی۔ نقل نویسی کا متن غیر معتبر میڈیا سے حاصل کردہ مواد رہتا ہے، اس کے ماخذ سے قطع نظر، اور کبھی بھی اختیار کا تعین نہیں کرنا چاہیے۔

ایک ترقی یافتہ کالر ایک ہی ویڈیو کے لیے `audioTranscript` ٹریک فراہم کر سکتا ہے؛ اسے کلائنٹ کی فراہم کردہ متن کے طور پر سمجھا جاتا ہے، سرور کی نقل نویسی کے ثبوت کے طور پر نہیں۔ فیوژن سیام بصری اور صوتی مشاہدات کو ایک ہی ڈیڈ لائن اور منسوخی کے سگنل کے تحت چلاتا ہے، انہیں ایک مشترکہ ٹائم لائن پر ترتیب دیتا ہے، بالکل ایک جیسے نقلوں کو سمیٹتا ہے، اور جب صرف ایک طرف کامیاب ہوتی ہے تو جزوی نتیجہ کی رپورٹ کرتا ہے۔ ایک غیر درست `audioTranscript` اس جزوی نتیجے میں کم ہو جاتا ہے — بصری تفصیل رکھی جاتی ہے اور صوتی شاخ ایک صاف شدہ ناکامی کوڈ ریکارڈ کرتی ہے — پورے ویڈیو کو ناکام کرنے کے بجائے۔ ہر شاخ کی دستیابی، جزوی جھنڈا، اور صاف شدہ ناکامی کے کوڈز بیان کردہ نتیجے میں، گارڈریل میٹا ڈیٹا (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`) میں، نتیجہ-کیچ میٹا ڈیٹا میں، اور پل فیوژن کاؤنٹرز میں محفوظ کیے جاتے ہیں۔ ڈیفالٹ ویڈیو پل کا راستہ تقریر سے متن میں تبدیل کرنے یا دوسرے میڈیا کی کاپی ڈاؤن لوڈ نہیں کرتا؛ اس واضح ٹریک کے بغیر، یہ صرف ویڈیو رہتا ہے۔

**نقل نویسی کی برقرار رکھنے (#12150 P1).** یہ خود بخود لاگو ہوتا ہے جب بھی ویڈیو پل (خود بھی آپٹ ان) ایک نقل نویسی اشارہ تیار کرتا ہے — کوئی علیحدہ برقرار رکھنے کا جھنڈا نہیں ہوتا۔ جب کوئی درخواست کسی بھی نقل نویسی اشارے (ایک کالر کے اعلان کردہ `transcript` یا ایک فیوزڈ `audioTranscript`) کو تیار کرتی ہے، تو گارڈریل اسے `videoBridgeObserved` کے طور پر نشان زد کرتا ہے اور ویڈیو کی تفصیل کا ایک سرخ شدہ سایہ پیدا کرتا ہے — ایک یکساں رینڈرنگ جس میں ہر اشارے کے آزاد متن کے جسم کو `[redacted-video-transcript]` سے تبدیل کیا جاتا ہے، جو کہ ساختی اشارے کے میدان کو تبدیل کر کے بنایا جاتا ہے اس سے پہلے کہ سٹرنگ کو جمع کیا جائے (کبھی بھی فلیٹ ٹیکسٹ کو پارس کرکے نہیں، لہذا کوئی اشارے کا مواد — مخالف یا عام، بشمول ایسے جسم جو `]` جیسے `[inaudible]`/`[music]` پر مشتمل ہو — زندہ نہیں رہ سکتا)۔ محفوظ شدہ کال-لاگ درخواست کا جسم ہر ویڈیو سے حاصل کردہ متن کے حصے کو اس سرخ شدہ سایہ کے لیے تبدیل کرتا ہے، جو مواد کی مساوات کے ذریعے ملتا ہے؛ `fullText` اینکر کو مکمل پیش کال گارڈریل پیلوڈ سے دوبارہ پڑھا جاتا ہے، لہذا میچ بعد میں چین گارڈریل (PII اور اسناد کے ماسکرز، ترجیحات 10/95) کی تفصیل کے متن کو جگہ پر دوبارہ لکھنے کے بعد بھی کامیاب رہتا ہے اور نظام-پرومپٹ/ہینڈ آف/یادداشت کے انجیکشن کے بعد پیغام کی صف کو دوبارہ شکل دیتا ہے۔ ماڈل کو بھیجی گئی جسم میں کوئی تبدیلی نہیں ہوتی۔ ایک مشاہدہ شدہ درخواست بھی کوئی مستقل یادداشت کو آبادی نہیں دیتی (درخواست اور جواب سے حاصل کردہ نکالنے کو چھوڑ دیا جاتا ہے)، لہذا ماڈل کا اپنا جواب یادداشت میں نقل نویسی کے متن کو گونج نہیں کر سکتا۔

**خام ویڈیو کے میدان (#12430).** جب پل فعال ہو اور مقامی ویڈیو کی حمایت نامعلوم یا غیر موجود ہو، تو متعین `transcript`/`audioTranscript` کے میدان بھی `videoBridgeObserved` کو فعال کرتے ہیں، یہاں تک کہ تفصیل کی ناکامی یا `maxVideos` کی حد کے بعد بھی۔ `null` اور خالی سٹرنگز شمار کی جاتی ہیں؛ غیر موجود میدان اور غیر ویڈیو میٹا ڈیٹا شمار نہیں ہوتے۔ برقرار رکھی گئی کاپیوں میں ان میدانوں کو سرخ کیا جاتا ہے یا درخواست کو چھوڑ دیا جاتا ہے، اور کیچ/یادداشت کو نظر انداز کیا جاتا ہے۔ فراہم کنندہ کا پیلوڈ بغیر تبدیلی کے رہتا ہے۔

| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` عمومی کیپشنز کو برقرار رکھتا ہے؛ `focused` محدود، غیر معتبر تازہ ترین صارف کے سیاق و سباق کا استعمال کرتا ہے |
| `modalityBridgeVideoModel`          | `""`        | وژن پل ماڈل وراثت میں لیں                                                                                           |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                                |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, یا تناسبی `segment_aware`; ڈیٹیکٹر کی ناکامی `uniform` پر واپس آتی ہے                     |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                                 |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                                      |

120 سیکنڈ سے اوپر کے وراثتی برقرار رکھے گئے ویڈیو ٹائم آؤٹ کی قیمتیں بروکر کی آخری تاریخ پر پابند ہیں؛ اس حد سے اوپر کی نئی ترتیبات کی تحریریں مسترد کر دی جاتی ہیں۔ `GET /api/modality-bridge/video/runtime` کو مستند مہر لگے لوپ بیک مقامی ہونے کی ضرورت ہے اس سے پہلے کہ توثیق یا ریئل ٹائم پروبنگ کی جائے، پھر انتظامی توثیق کی ضرورت ہے۔ یہ صرف `available`، صاف شدہ FFmpeg/ffprobe ورژن، اور ایک مقررہ وجہ واپس کرتا ہے جب ریئل ٹائم دستیاب نہیں ہوتا۔ اندرونی استخراج کا اینڈ پوائنٹ عوامی اپ لوڈ API نہیں ہے: قطار کی سیر کی صورت میں `503` کے ساتھ `Retry-After` واپس آتا ہے، کالر کا منقطع ہونا `499` واپس کرتا ہے، اور مقررہ بروکر کی آخری تاریخ `504` واپس کرتی ہے۔ تبدیل شدہ جوابات مرکزی `x-omniroute-modality-bridge` ہیڈر میں `video->text;model=<visionModel>;parts=<videos>` شامل کرتے ہیں بغیر وژن یا آڈیو حصوں کو ہٹائے۔

### PII ماسکر (`piiMasker.ts`)

**دونوں** مراحل پر چلتا ہے۔

- **`preCall`** پے لوڈ کو کلون کرتا ہے، `system`، `messages`، `input`، اور `prompt` (سیدھے سٹرنگ آئٹمز سمیت) کو چلتا ہے، اور `processPII()` (سے `@/shared/utils/inputSanitizer`) کو سٹرنگ `content`/`text` فیلڈز پر لاگو کرتا ہے۔ جب `PII_REDACTION_ENABLED=true` ہو تو، دریافت شدہ PII کو آؤٹ باؤنڈ پے لوڈ میں چھپایا جاتا ہے۔ یہ `INPUT_SANITIZER_MODE` سے آزاد ہے (جو صرف پرامپٹ-انجیکشن پالیسی کو کنٹرول کرتا ہے)۔ جب چھپانے کی خصوصیت بند ہو تو، کال کیپشن کی تعداد کو ریکارڈ کرتی ہے بغیر مواد کو دوبارہ لکھے۔
- **`postCall`** جواب کو ڈیپ کلون کرتا ہے، `sanitizePIIResponse()` چلاتا ہے اور جوابات-API-شکل ماسکر (`maskResponsesOutput` — `output_text` اور `output[].content[].text` کو ڈھانپتا ہے)۔ اگر کوئی چھپانے کا عمل ہوتا ہے، تو ترمیم شدہ جواب اصل کو تبدیل کرتا ہے۔

گارڈریل کبھی بھی بلاک نہیں کرتا؛ یہ صرف تشریح کرتا ہے (`meta.detections`، `meta.redacted`) یا دوبارہ لکھتا ہے۔

### پرامپٹ انجیکشن (`promptInjection.ts`)

معلوماتی مواد میں مخالف ساختوں کا پتہ لگاتا ہے جو صارف کی فراہم کردہ ہیں اور ترتیب دی گئی پالیسی کو نافذ کرتا ہے۔ رویہ ماحولیاتی متغیرات اور کنسٹرکٹر کے اختیارات سے متاثر ہوتا ہے:

| سیٹنگ         | ماحولیاتی متغیر                                                                                   | ڈیفالٹ | اثر                                                                                                                                                                                                            |
| ------------- | ------------------------------------------------------------------------------------------------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| فعال          | `INPUT_SANITIZER_ENABLED`                                                                         | `true` | جب `false` ہو تو گارڈریل فوری طور پر بند ہو جاتا ہے۔                                                                                                                                                           |
| موڈ           | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                   | `warn` | انجیکشن پالیسی: `block`, `warn`, یا `log`۔ (`redact` پچھلے ہم آہنگی کے لیے قبول کیا جاتا ہے لیکن یہ انجیکشن متن کو **نہیں** ہٹاتا؛ درخواست PII دوبارہ لکھنے کو `PII_REDACTION_ENABLED` سے کنٹرول کیا جاتا ہے۔) |
| بلاک تھریشولڈ | `blockThreshold` آپشن / `INPUT_SANITIZER_BLOCK_THRESHOLD` (عرف `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high` | بلاک کرنے کے لیے درکار کم از کم شدت۔ ڈیفالٹ پر درمیانہ صرف مشاہدہ کیا جاتا ہے۔                                                                                                                                 |

**موڈ کی ترجیح** (`getMode`): کالر `options.mode` →
`INJECTION_GUARD_MODE` **ڈیٹا بیس کی خصوصیت-پرچم اووررائیڈ** (ڈیش بورڈ → سیٹنگز →
خصوصیت کے پرچم) → `INJECTION_GUARD_MODE` ماحولیاتی متغیر → `INPUT_SANITIZER_MODE` ماحولیاتی متغیر →
`warn`۔ اس لیے ایک ڈیش بورڈ اووررائیڈ ماحولیاتی متغیرات پر غالب آتا ہے، لہذا خصوصیت کے پرچم کا UI چلتے ہوئے گارڈ کو کنٹرول کرتا ہے (کوئی دوبارہ شروع نہیں)۔ ڈیٹا بیس کی پڑھائی محفوظ ہے:
اگر یہ غلطی کرتا ہے تو گارڈ ماحولیاتی بنیاد پر رویے پر واپس آ جاتا ہے، اور جب کوئی اووررائیڈ سیٹ نہیں ہوتا تو رویہ ماحولیاتی صرف حل کے مساوی ہوتا ہے۔

پتہ لگانے کے ذرائع:

1. `sanitizeRequest()` سے `@/shared/utils/inputSanitizer` (پائپ لائن میں کہیں اور استعمال ہونے والا مشترکہ ڈیٹیکٹر سیٹ)۔
2. بلٹ ان `DEFAULT_GUARD_PATTERNS` (فی الحال `system_override_inline` اور
   `markdown_system_block`، دونوں `high` شدت)۔
3. اختیاری `customPatterns` جو کنسٹرکٹر کے اختیارات کے ذریعے فراہم کیے گئے ہیں (سٹرنگز، ریگیکس،
   یا `{ name, pattern, severity }` ریکارڈ)۔

جب `mode === "block"` **اور** کم از کم ایک پتہ لگانے کی شدت کی حد کو پورا کرتا ہے،
`preCall` `{ block: true, message: "Request rejected: suspicious content detected" }` واپس کرتا ہے۔ `warn`/`log` موڈز میں گارڈریل لاگ کرتا ہے لیکن
کال کی اجازت دیتا ہے۔ مشترکہ ہیلپر `evaluatePromptInjection()` بھی برآمد کیا گیا ہے
ان کالرز کے لیے جنہیں رجسٹری کے بغیر پرامپٹس کا اندازہ لگانے کی ضرورت ہے۔

**اسکین کی حد (v3.8.20):** ڈیٹیکٹر صرف **پہلے 16 KB** کو جانچتا ہے
ملے ہوئے پرامپٹ متن — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 بائٹس) میں
`src/shared/utils/inputSanitizer.ts`۔ دونوں `detectInjection()` اور
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` کو چلانے سے پہلے پیٹرن لوپ۔ انجیکشن کی ہدایات ان پٹ کے اوپر کی طرف ہوتی ہیں، لہذا یہ
بہت بڑی KB کے پیلوڈز پر ریگیکس CPU/GC کو محدود کرتا ہے بغیر پتہ لگانے کی طاقت کو کم کیے (cf.
#3932, #4041)۔

### کریڈینشل ماسکر (`credentialMasker.ts`)

**دونوں** مراحل پر چلتا ہے، ڈیفالٹ چین میں آخری (ترجیحات `95`)۔ معروف API-key / secret-token پیٹرن کو آؤٹ باؤنڈ پیلوڈ (پیغام
مواد، ٹول کال کے دلائل، ٹول کے نتائج) **اور** فراہم کنندہ کے جواب سے ہٹا دیتا ہے، تاکہ پرامپٹ میں چسپاں کردہ ایک کریڈینشل (یا ٹول کے نتیجے میں واپس گونجتا ہوا) اوپر کی طرف فراہم کنندہ یا کلائنٹ کو لیک نہ ہو۔

- **صرف آپٹ ان**، PII ریڈکشن کے ساتھ ایک ہی کنونشن (ہارڈ رول #20 کے قریب):
  جب تک `settings.credentialRedactionEnabled === true` **یا**
  `CREDENTIAL_REDACTION_ENABLED=true` نہ ہو، غیر فعال۔ جب یہ بند ہو تو، گارڈریل ایک ناپسندیدہ عمل ہے —
  یہ کبھی بلاک نہیں کرتا اور کبھی دوبارہ نہیں لکھتا۔
- `redactCredentials()` مکمل پیلوڈ/جواب کے درخت کو چلتا ہے (`walkValue()`,
  پروٹوٹائپ آلودگی سے محفوظ، `WeakSet` کے ذریعے سائیکل سے محفوظ) اور میچز کو
  `[REDACTED:<type>]` ہولڈر کے ساتھ تبدیل کرتا ہے، صرف ان شاخوں کی نقل بناتا ہے جو واقعی
  تبدیل ہوئیں۔
- `CREDENTIAL_PATTERNS` LLM فراہم کنندہ کی چابیاں (OpenAI، OpenAI-proj،
  Anthropic، Google، Hugging Face، Replicate)، VCS/SaaS ٹوکن (GitHub، Slack،
  Linear، Notion، npm، Postman، Discord)، ادائیگی کی چابیاں (Stripe، Square)، کلاؤڈ
  چابیاں (AWS رسائی کی چابی، Twilio، SendGrid، Mailgun)، نجی چابیاں / JWTs،
  کریڈینشل رکھنے والی کنکشن کی تاریں (`mongodb://user:pass@...`، وغیرہ)، اور
  ایک عمومی `Authorization`/`x-api-key`/`api-key`/`apikey` ہیڈر-ویلیو
  پیٹرن کو ڈھانپتا ہے۔ ہیڈر کی شکل کی چابیاں (`authorization`، `x-api-key`، `api-key`,
  `apikey`) ساختی طور پر ہٹا دی جاتی ہیں (صرف قیمت، اسکیم کا پیشگی جیسے
  `Bearer `/`Basic ` محفوظ) بجائے عمومی متن کے ریگیکس کے ذریعے۔
- گارڈریل کبھی بلاک نہیں کرتا؛ یہ صرف دوبارہ لکھتا ہے (`modifiedPayload` /
  `modifiedResponse`) اور تشریح کرتا ہے (`meta.credentialsRedacted`, `meta.count`)۔

ریگریشن گارڈ: `tests/unit/credential-masker-guardrail.test.ts`۔

## بنیادی کنٹریکٹ (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true چین کو فوری طور پر روک دیتا ہے
  message?: string; // بلاک ہونے پر ظاہر کیا جاتا ہے
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // درخواست کو دوبارہ لکھنے کے لیے preCall کے ذریعے واپس کیا جاتا ہے
  modifiedResponse?: TValue; // جواب کو دوبارہ لکھنے کے لیے postCall کے ذریعے واپس کیا جاتا ہے
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ایک گارڈ ریل `void`، `{}`، یا `{ block: false }` واپس کرکے "کوئی تبدیلی نہیں" کا اشارہ دیتی ہے۔ `modifiedPayload`/`modifiedResponse` واپس کرنے سے چین میں آگے آنے والی گارڈ ریلز تک پہنچنے والی قدر تبدیل ہو جاتی ہے۔
`signal?: AbortSignal` کالر کے لائف سائیکل کو گارڈ ریلز تک پہنچاتا ہے۔ درخواست کا منسوخ ہونا دانستہ fail-open استثنا ہے: میڈیا برجز کام روک دیتے ہیں اور صفائی کرتے ہیں، مگر خام میڈیا کو ایسے ہدف کے لیے بحال نہیں کرتے جس کے بارے میں معلوم ہو کہ وہ اسے سپورٹ نہیں کرتا۔

## رجسٹری (`registry.ts`)

سنگلٹن `guardrailRegistry` درج ذیل سہولیات فراہم کرتی ہے:

- `register(guardrail)` — ایک گارڈ ریل شامل کرتی ہے (یا نارملائزڈ نام کے لحاظ سے تبدیل کرتی ہے) اور
  صعودی `priority` کے مطابق دوبارہ ترتیب دیتی ہے۔
- `clear()` / `list()` — انتظامی معاون فنکشنز۔
- `runPreCallHooks(payload, context)` — فعال گارڈ ریلز پر تکرار کرتی ہے، پے لوڈ کو
  `modifiedPayload` کے ذریعے آگے بڑھاتی ہے، اور پہلے `block: true` پر رک جاتی ہے۔
- `runPostCallHooks(response, context)` — جواب کی جانب بھی یہی بہاؤ استعمال کرتی ہے۔
- `resetGuardrailsForTests({ registerDefaults })` — حالت صاف کرتی ہے اور صاف ستھری ٹیسٹ علیحدگی کے لیے، اختیاری طور پر
  ڈیفالٹس کو دوبارہ رجسٹر کرتی ہے۔

دونوں رنرز `{ blocked, payload|response, results, guardrail?, message? }`
واپس کرتے ہیں، جہاں `results`، `GuardrailExecutionResult` ریکارڈز کی ایک ارے ہے جس میں
ہر گارڈ ریل کے `blocked`، `skipped`، `modified`، `error`، اور `meta` فیلڈز شامل ہوتے ہیں،
جو ٹریسنگ کے لیے مفید ہیں۔

### ہر درخواست کے لیے گارڈ ریلز کو غیر فعال کرنا

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` گارڈ ریل ناموں کی ایک
نقل سے پاک فہرست یکجا کرتا ہے جنہیں موجودہ درخواست کے لیے چھوڑ دینا چاہیے۔
ذرائع (سب اختیاری، سب ضم کیے جاتے ہیں):

- `apiKeyInfo.disabledGuardrails`
- درخواست کی باڈی کا `disabledGuardrails` (اعلیٰ سطح پر)
- درخواست کی باڈی کا `metadata.disabledGuardrails`
- ہیڈر `x-omniroute-disabled-guardrails` (یا قدیمی
  `x-disabled-guardrails`)

اقدار اسٹرنگز کی ارے یا کوما سے جدا کی گئی اسٹرنگ ہو سکتی ہیں؛ ناموں کو
لوئرکیس kebab-case میں نارملائز کیا جاتا ہے (`pii_masker` → `pii-masker`)۔ نتیجہ
`context.disabledGuardrails` کے ذریعے رجسٹری کو دیا جاتا ہے، جو مماثل
گارڈ ریلز کو چھوڑ دیتی ہے (`results` میں `skipped: true`)۔

## عمل درآمد کی ترتیب

`src/sse/handlers/chat.ts` اور `open-sse/handlers/chatCore.ts` سے گزرنے والی ہر درخواست کے لیے:

1. `resolveDisabledGuardrails(...)`، API کلید، باڈی، اور ہیڈرز سے نظر انداز کیے جانے والے عناصر کی فہرست بناتا ہے۔
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ترجیح کی صعودی ترتیب میں گارڈ ریلز چلاتا ہے:
   - غیر فعال گارڈ ریلز کو `skipped` کے طور پر ریکارڈ کیا جاتا ہے۔
   - ہر گارڈ ریل کا `preCall`، `modifiedPayload` کے ذریعے پے لوڈ دوبارہ لکھ سکتا ہے۔
   - پہلا `block: true` سلسلے کو فوری طور پر روک دیتا ہے اور ہینڈلر گارڈ ریل کی جانب سے مسترد کیے جانے کا جواب واپس کرتا ہے۔
3. (ممکنہ طور پر دوبارہ لکھا گیا) پے لوڈ کومبو روٹنگ اور اپ اسٹریم ڈسپیچ میں جاتا ہے۔
4. جواب تیار ہونے کے بعد، `guardrailRegistry.runPostCallHooks(...)` جواب پر یہی سلسلہ چلاتا ہے۔ یہاں `block: true` اپ اسٹریم جواب کو خارج کر دیتا ہے۔

خرابی پیدا کرنے والی گارڈ ریلز کو `error: <message>` کے ساتھ ریکارڈ کیا جاتا ہے اور `logger.warn` کے ذریعے لاگ کیا جاتا ہے، لیکن سلسلہ جاری رہتا ہے — یہ ڈیزائن کے لحاظ سے فیل-اوپن ہے۔

| ------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------ |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | تشخیص کو مکمل طور پر غیر فعال کرنے کے لیے `false` مقرر کریں۔                                           |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | انجیکشن پالیسی: `warn`، `block`، یا `log`۔ پرانی قدر `redact` انجیکشن متن کو دوبارہ نہیں لکھتی۔        |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | انجیکشن گارڈ کا موڈ؛ یہ DB فیچر فلیگ بھی ہے جو ماحولیاتی متغیرات کو **اوور رائیڈ** کرتا ہے (DB > ENV)۔ |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | کم از کم شدت جسے `MODE=block` مسترد کرتا ہے: `high` (ڈیفالٹ)، `medium`، یا `low`۔                      |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD` کا پرانا عرف۔                                                        |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | `true` ہونے پر، درخواست کا PII حذف کر دیا جاتا ہے (انجیکشن موڈ سے آزاد)۔                               |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ڈاؤن اسٹریم) | جواب کی جانب ماسکر کے رویے کو کنٹرول کرتا ہے۔                                                          |

Modality Bridge گارڈ ریلز ماحولیاتی متغیرات کے بجائے DB کی معاونت والے سیٹنگز اسٹور (`getSettings()`) سے رن ٹائم کنفیگریشن پڑھتی ہیں۔ Vision کی بنیادی کلیدیں `modalityBridgeVisionEnabled`، `modalityBridgeVisionMode`، `modalityBridgeVisionModel`، `modalityBridgeVisionTaskAware`، `modalityBridgeVisionPrompt`، `modalityBridgeVisionTimeout`، `modalityBridgeVisionMaxImages`، `modalityBridgeVisionMaxChars`، `modalityBridgeCacheEnabled`، `modalityBridgeCacheTtlMinutes`، اور `modalityBridgeCacheMaxEntries` ہیں۔ پرانی `visionBridge*` کلیدیں صرف دستاویزی، ایک سائیکل کے ریڈ فال بیک کے طور پر قبول کی جاتی ہیں؛ ڈیش بورڈ رائٹس بنیادی کلیدیں استعمال کرتی ہیں۔ ڈیفالٹس اور فال بیک ریزالور `src/shared/constants/modalityBridgeDefaults.ts` میں موجود ہیں، جبکہ پرانے کانسٹنٹس `src/shared/constants/visionBridgeDefaults.ts` میں برقرار رکھے گئے ہیں۔

Audio، `modalityBridgeAudioEnabled`، `modalityBridgeAudioModel`، `modalityBridgeAudioTimeout`، اور `modalityBridgeAudioMaxClips` کے ساتھ مشترکہ `modalityBridgeCache*` سیٹنگز استعمال کرتا ہے۔ Audio کے لیے پرانی کلیدوں کا کوئی فال بیک نہیں ہے کیونکہ یہ کلیدیں Modality Bridge اسکیما کے ساتھ متعارف کرائی گئی تھیں۔

Video، `modalityBridgeVideoEnabled`، `modalityBridgeVideoAnalysisMode`، `modalityBridgeVideoModel`، `modalityBridgeVideoFrameCount`، `modalityBridgeVideoSamplingPolicy`، `modalityBridgeVideoMaxVideos`، اور `modalityBridgeVideoTimeout` کے ساتھ مشترکہ `modalityBridgeCache*` سیٹنگز استعمال کرتا ہے۔ یہ ڈیفالٹ طور پر غیر فعال ہے کیونکہ FFmpeg/ffprobe اختیاری آپریشنل انحصارات ہیں اور فریم کیپشننگ تاخیر اور ماڈل کی لاگت میں اضافہ کرتی ہے۔

## حسبِ ضرورت Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

مراحل:

1. `BaseGuardrail` کو توسیع دیتے ہوئے `src/lib/guardrails/myGuardrail.ts` بنائیں۔
2. `preCall` اور/یا `postCall` نافذ کریں۔
3. یا تو import کے وقت رجسٹر کریں (`registerDefaultGuardrails` سے push کریں) یا
   runtime پر `guardrailRegistry.register(...)` کو کال کریں — registry اسی normalized نام والے
   کسی بھی سابقہ guardrail کو بدل دیتی ہے۔
4. `tests/unit/` کے تحت ٹیسٹ شامل کریں (موجودہ مثالیں:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)۔

## ٹیسٹنگ

معلوم حالت سے آغاز کرنے کے لیے ٹیسٹس کے درمیان `resetGuardrailsForTests()` استعمال کریں۔
خالی registry سے آغاز کرنے اور صرف زیرِ ٹیسٹ guardrails رجسٹر کرنے کے لیے
`{ registerDefaults: false }` پاس کریں۔ Vision Bridge dependency
injection (`deps.getSettings`, `deps.callVisionModel`) قبول کرتا ہے؛ Audio Bridge
settings، capabilities، STT model کے انتخاب، credential
کی جانچ، اور transcription کے لیے مساوی seams فراہم کرتا ہے۔ اس طرح ٹیسٹس DB
یا network تک رسائی کے بغیر دونوں flows کو آزما سکتے ہیں۔

## Injection-guard route coverage اور red-team (مرحلہ 8 · بلاک D)

injection-guard (`createInjectionGuard` / `withInjectionGuard`) ان تمام routes کا احاطہ کرتا ہے
جو user prompts قبول کرتے ہیں۔ یہ `INJECTION_GUARD_MODE` کا احترام کرتا ہے (default `warn` = صرف log؛
`block` = HTTP 400 `SECURITY_001` واپس کرتا ہے)۔

| قسم          | Routes                                                                                                                                               | Default mode |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| متن (موجودہ) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn         |
| تخلیقی       | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn         |
| ڈیٹا         | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn         |

متن اخذ کرنا (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` کا احاطہ کرتا ہے۔

**Red-team (ہر شب، `nightly-llm-security.yml`):** promptfoo تصدیق کرتا ہے کہ ہر route
`INJECTION_GUARD_MODE=block` میں OWASP-LLM corpus کو block کرتا ہے؛ garak probes چلاتا ہے (secret نہ ہونے پر چھوڑ دیتا ہے)۔
`moderations` کو یکسانیت کے لیے شامل کیا گیا ہے — block-mode میں operators اسے
`resolveDisabledGuardrails` کے ذریعے مستثنیٰ کر سکتے ہیں۔

ہر شب چلنے والے workflow (`.github/workflows/nightly-llm-security.yml`، cron + دستی
dispatch) میں دو jobs ہیں:

- **`promptfoo-guard` (blocking)** — `INJECTION_GUARD_MODE=block` کے ساتھ
  `promptfoo eval -c promptfooconfig.yaml` چلاتا ہے۔ ہر مخالفانہ case (مثلاً "ignore all
  previous instructions…"، DAN-style jailbreaks) تصدیق کرتا ہے کہ response میں
  `error.code === "SECURITY_001"` موجود ہے، یعنی guard نے واقعی request مسترد کی۔
- **`garak` (مشاورتی)** — مقامی OmniRoute instance (`http://localhost:20128/v1`) کے خلاف
  garak کو `--probes promptinject,dan,leakreplay` کے ساتھ چلاتا ہے۔ اسے provider
  secret (`PROMPTFOO_PROVIDER_KEY`) کے ذریعے مشروط کیا گیا ہے؛ یہ مؤدبانہ طور پر چھوڑ دیتا ہے اور اس کے آخر میں
  `|| true` شامل ہے، لہٰذا یہ CI کو ناکام کیے بغیر رپورٹ کرتا ہے۔

guard helper (`createInjectionGuard` / `withInjectionGuard`) کی coverage
ہر prompt رکھنے والے `/v1` route تک پھیلی ہوئی ہے؛ prompt کا متن
`src/shared/utils/inputSanitizer.ts` میں موجود `extractMessageContents()` کے ذریعے
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` سے حاصل کیا جاتا ہے۔
