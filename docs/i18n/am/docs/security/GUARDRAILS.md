> እስካሁን በሰርቨሩ አልተረጋገጠም — በ#11661 መሠረት ግልጽ ተደርጓል)

Guardrails በOmniRoute እና በላይኛ ደረጃ አቅራቢዎች መካከል ባለው ወሰን ላይ
ደኅንነትን፣ ፖሊሲን እና የይዘት ለውጦችን ያስፈጽማሉ። እያንዳንዱ guardrail
የጥያቄ payload-ዎችን (`preCall`) እና የላይኛ ደረጃ ምላሾችን (`postCall`)
መመርመር (እንዲሁም እንደአማራጭ ውድቅ ማድረግ፣ መለወጥ ወይም ማብራሪያ መጨመር) ይችላል።

ስርዓቱ **fail-open** ነው፦ guardrail በሚፈጸምበት ጊዜ exception ካስነሳ፣ registryው
ጥያቄውን ከማሳካት ይልቅ ስህተቱን መዝግቦ ወደሚቀጥለው guardrail
ይቀጥላል። ማገድ ግልጽ ውሳኔ (`block: true`) እንጂ በአጋጣሚ የሚከሰት አይደለም።

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

የምስል ያሉበትን ጥያቄዎች ወደ **vision ያልሆኑ ሞዴሎች** ሲሄዱ ይቆራረጣል እና
ጥያቄውን በሙሉ ወደ vision መቻል ያለው ሞዴል ወይም የምስል ክፍሎቹን በተለይ በተወሰነ የvision ሞዴል የተፈጥሮ የጽሑፍ መግለጫ በመቀየር ከመላው ጥያቄ በፊት ይቀየራል። ይህ ለጽሑፍ-ብቻ አቅራቢዎች በቀላሉ የተያያዙ የተዘራሪ መልእክቶችን እንዲያከናውኑ ያደርጋል።

የሂደት ደረጃዎች፦

1. የተመረጠው ሞዴል አስቀድሞ vision የሚያቀርብ ከሆነ ይዝለው (ከሆነም በተግባር በ `isVisionBridgeForcedModel` የተወሰኑ ሞዴሎች ውስጥ ካልተገኘ ብቻ)።
2. የምስል ክፍሎችን በ `extractImageParts(messages)` ይውጡ
   (`visionBridgeHelpers.ts`), ይህም ለ **unified media detector** `detectMediaParts()` በ `open-sse/utils/mediaParts.ts` ይሰጣል — የእውነት አንደኛ ምንጭ ለ combo compatibility filter የተጋራ።
   መውጣት በ አንደኛ ደረጃ የ `replaceImageParts` የሚቀይሩበት ቅርጸ-ተከታታይ ብቻ ይፈቀዳል (የመውጣት↔መቀየር ውል): OpenAI `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL `source.type:"url"`, እና Responses API `input_image`። የተያዙ እና የምልክት-ብቻ ቅርጸ-ተከታታይ combo-filter ናቸው እና በፍጹም አይወጡም። ምንም ካልተገኘ ይዝለው።
3. የruntime ቅንብርን በ `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`) ይወስኑ፡ አዲሱ `modalityBridge*`
   ቅንብሮች ይቆጠራሉ፤ አሮጌ `visionBridge*` ቅንብሮች አንድ-ዙር የመመለሻ መንገድ ናቸው። በማንኛውም የሚዲያ መተንተኛ በፊት በተሰናከለ ጊዜ ይዝለው።
4. የmode selector (`modalityBridgeVisionMode`, ከታች ያለውን ሰንጠረዥ ይመልከቱ) የreroute እና የdescribe መንገድ ይወስናል። የreroute መንገድ `modifiedPayload` በ `model` ብቻ የተቀየረ ይመልሳል፣ ከሚከተሉት መታወቂያዎች ጋር `{ rerouted, fromModel, toModel, imagesKept }`።
5. የdescribe መንገድ፡ ምስሎችን በ `maxImages` ይገደቡ፣ በተግባር የተለያዩ ጥያቄዎች የሚሆኑ መግለጫዎችን ያዘጋጁ፣ የdescribe cache ይመልከቱ፣ የvision ሞዴልን **በተያያዥ** ይጥሩ (`Promise.allSettled`)፣ እና `[Image N]: <description>` የጽሑፍ ክፍሎችን በቦታቸው ይጨምሩ። የdescribe ውድቀት `null` ይመልሳል እና የመጀመሪያው የምስል ክፍል **ይጠበቃል** (#4012) — ከሆነም በcombo describe መንገድ ሁሉም describe ካልተሳኩ፣ ለተረጋጋ የvision ያልሆነ አቅራቢ የሚሄድ የተዘጋጀ `(unavailable — no vision-capable provider connected)` ይሆናል (#8430)።
6. `modifiedPayload` + meta (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) ይመልሳል።

#### የAPI-key ክልል (`visionBridgeKeyScope.ts`)

የጠራቂው API key `allowedConnections`, እንዲሁም የአቅርቦት ህዋሶች
(`allowedQuotas`) ወይም ሞዴሎች (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) ካሉበት፣ ብሪጅ የreroute እና የdescribe ሞዴሎችን በkey የሚጠቀሙበት መዳረሻ ብቻ ይምረጣል። የdescribe ጥሪ ሁልጊዜ OmniRoute self-loop በ `x-omniroute-self-loop-key-id` ራስጌ ይሄዳል፣ ስለዚህ የሚቀበለው የchat ጥያቄ የዚያ key መዳረሻ እና የሞዴል ፖሊሲ ይተገበራል። `enforceApiKeyPolicy()` ያ ራስጌ ብቻ ከself-loop bearer ጋር ብቻ ይከተላል፣ ስለዚህ የመዳረሻ ክልልን ማጣራት ብቻ ይችላል፣ እና ያልተወሰነ id ይተወዋል።

ለkey ምንም የvision ሞዴል ካልተፈቀደ፣ የdescribe መንገድ ይዝለዋል እና ጥያቄው በማይቀየር መልኩ ይሄዳል፣ ከተሰናከለ መከላከያ ጋር ተመሳሳይ የfail-open ባህሪ (meta `{ skipped: true, reason: "no_permitted_vision_model" }`)። ያልተያዙ key ያላቸው ጥያቄዎች እና ያልተያዙ እንደ ቀድሞው ይሄዳሉ።

#### በተግባር የሚቀየሩ የdescribe ጥያቄዎች (`modalityBridgeVisionTaskAware`)

ነባሪው **እውነት** ነው። `composeVisionPrompt()` (`visionBridgeHelpers.ts`) የ**መጨረሻውን የተጠቃሚ መልእክት** ጽሑፍ (እስከ 500 ቁምፊ የተቆረጸ) ወደ መሠረታዊው የመግለጫ ማነቃቂያ ይጨምራል፣ መግለጫውን ወደ ተጠቃሚው በእውነት የጠየቀው ነገር እንዲመራ ይረዳል (codex-vision-proxy አባል እንደሆነ) እና ከታይ የሚታዩ ጽሑፎችን እንዲተረጉም ከvision model ይጠይቃል። ባንዱ ባለበት — ወይም የተጠቃሚ ጽሑፍ ባለመኖሩ — መሠረታዊው ማነቃቂያ ያልተለወጠ ተጠቅመዋል።

የመግለጫ ራሱ የራሱን OpenAI-ተስማሚ ጥያቄ (`callVisionModelSingle()` በ`visionBridgeHelpers.ts` ውስጥ) ሁልጊዜ `image_url.detail: "high"` ይጠይቃል — ያለ ማንኛውም የደንበኛ ምልክት፣ ለሁሉም ጠራቢ/አቅራቢ፣ ያለ መደበኛ መደበኛ አይደለም። ዝቅተኛ ዝርዝር የሆነ ምርጫ ለዚህ ማነቃቂያ የሚጠየቀውን የጽሑፍ ትርጉም OCR ትክክለኛነት ያበላሽቃል፣ ስለዚህ የመግለጫ ጥሪው ራሱ ሁልጊዜ ከመጀመሪያው ጥያቄ የተጠቀሰው የዝርዝር ደረጃ ምንም እንኳን ከሆነ ከፍተኛ ዝርዝር ይጠይቃል። ይህ የውስጥ የመግለጫ ጥያቄ አካልን ብቻ ይነካል፤ የOmniRoute የጠራቢውን የ`image_url.detail` በዋናው ጥያቄ ላይ እንዴት እንደሚያስተላልፍ አይቀየምም — ያ ነባሪ በተለየ ሁኔታ ይተገበራል፣ እና ለተገኙ የOpenCode ደንበኞች ብቻ በ`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) ውስጥ ይተገበራል። የAnthropic wire-format ቅርንጫፍ የመግለጫ ራሱ የ`detail` መስክ የለውም እና በሁለቱም ነባሪዎች አይተገናኝም።

#### የመግለጫ ውጤት ገደብ (`modalityBridgeVisionMaxChars`)

| ቁልፍ                            | ነባሪ | ክልል               |
| ------------------------------ | --- | ----------------- |
| `modalityBridgeVisionMaxChars` | `0` | `0` ወይም 100–50000 |

`0` (ነባሪ) ማለት **ገደብ የለም** ማለት ነው — በ`callVisionModel()` የተመለሰው መግለጫ ያልተለወጠ ይወሰዳል፣ ያለውን ባህሪ ይጠብቃል። በ100–50000 ክልል ውስጥ ማንኛውም ዋጋ መግለጫውን በ`…` ቅጥ ከመመለሱ በፊት ይቆረጣል። ከዚያም `[Image N]: <description>` እንደሚሆን ይደጋገማል (`VisionBridgeGuardrail.preCall()` በ`src/lib/guardrails/visionBridge.ts` ውስጥ)። ለዝርዝር የሆኑ OCR ስራዎች የታችኛው ሞዴል ሙሉ ትርጉም እንዲያገኝ ይህን ያስጨምሩ፤ ለብዙ ቃላት የሚያወጡ የvision model የቶክን አጠቃቀምን ለመገደብ ያንሱት። የdashboard መስኩ በVision tab የበለፀገው ፓነል ላይ ይገኛል (`modality-bridge-max-chars` በ`ModalityBridgeVisionTab.tsx`) እና ማንኛውንም ዋጋ በ1 እና 99 መካከል ወደ 100 ያደርሳል፣ ግን ግልጽ `0` አልተቀየረም — `0` ራሱ ትክክለኛ የZod ዋጋ ነው (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), ብቻ አይደለም "unset" ነባሪ እንደሆነ።

#### የመግለጫ ካሽ (`modalityBridge/bridgeCache.ts`)

በመታሰቢያ ውስጥ የሚገኝ የLRU + TTL ካሽ ለመግለጫ ውጤቶች፣ በመስመር ላይ ሁሉም ሂደት የተጋራ።

#### የሩቅ ምስል መደበኛ ማድረግ (self-loop describe/base64 fetch)

bridge ራሱ **ሩቅ** ምስል ሲያመጣ — የAnthropic መግለጫ ራሱን ጥሪ እና የclaude-wire-format base64 ለውጥ (`ensureBase64ImagesForClaudeWire`), ሁለቱም በ`fetchRemoteImageAsDataUri()` በ`visionBridgeHelpers.ts` — የተገኘው data URI በ`normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) ይደርሳል ከመግለጫ ሞዴል ጥያቄ በፊት። ከመጠኑ በላይ ያሉ ምስሎች ወደ **2048px ረዥም ጠረፍ** ይቀነሳሉ (OpenAI/Anthropic በአገልጋይ የሚያደርጉትን የመጠን ገደብ ይዛመዳል)፣ ይህም የመጫኛ ባይቶችን/የመድረሻ ጊዜን ያቆራረጣል ያለ ሞዴሉ የሚያየውን ማሻሻል ሳይደርስ። የመቀነሻው መሳሪያ `sharp` ነው፣ በdynamic import የተጫነ። በመድረሻ ላይ የተፈጠረ የnative binary ማያገለግል ከሆነ፣ `normalizeDataUri()` **በፍጹም አይጣልም** — ወደ መጀመሪያው ባይት ይመለሳል፣ ስለዚህ የመግለጫ/የbase64-ለውጥ መንገድ ሁልጊዜ ይሰራል። የምስል ያልሆኑ ባይቶች (የተመጣ የማይታወቅ ምስል ከተመለሰ) እንዲሁም ያልተቀየሩ ይወሰዳሉ። ይህ መደበኛ ማድረግ ለbridge ራሱ ሲያመጣ ምስሎች ብቻ ይተገበራል — በፍጹም የጠራቢው የተላከው የraw passthrough መጫኛ አይተገበርበትም፣ ከተመለከተው የሚቀየር ብቻ የሚሆነው መስፈርት (Hard Rule #20) ጋር ተመሳሳይ ነው።

የVision ትር እንዲከፈት የሚያደርጉት እንቅስቃሴ፣ ዘዴ፣ የሞዴል ምርጫ (ከአውቶማቲክ ነባሪው ጋር)፣ ተግባራዊ ምክር፣ የላቀ ጊዜ ገደብ/ምስል/መግለጫ-ርዝመት/ካሽ ገደቦች፣ የሂደት ቆጣሪዎች፣ እና የተጠበቀ የናሙና ጥያቄ ናቸው። የAudio ትርም በቀጥታ ነው፡፡ እንቅስቃሴ፣ የSTT-ብቻ ሞዴል መምረጫ ከAuto ጋር፣ የጊዜ/ከፍተኛ-ክሊፕ ገደቦች፣ የኦዲዮ ቆጣሪዎች፣ እና `input_audio` የናሙና ሙከራ ይገልጻል። የVideo ትር ደግሞ ተግባራዊ ነው፡፡ የFFmpeg/ffprobe የሂደት ሁኔታን ይዘውበታል — አራት ግልጽ UI ሁኔታዎች መካከል (`unknown` በፕሮብ ሂደት ላይ ወይም ሲያልቅ ሳይችል፣ `restricted` በተለመዱ ያልሆኑ የዳሽቦርድ አስተናጋጆች ላይ ፕሮብ በአካባቢ ሲይዘው፣ `unavailable` ከተፈተነ በኋላ እና ከጎደለ፣ ወይም `available` ከFFmpeg/ffprobe እትም ጋር) — እንቅስቃሴ/ሞዴል/ፍሬም/ቪዲዮ/ጊዜ ገደቦችን ይዞ ይቆያል፣ የሞዴል መምረጫውን ወደ የvision ችሎታ ያላቸው ሞዴሎች ይገልፃል፣ የቪዲዮ ቆጣሪዎችንም ይገልጻል።

የቀድሞው Vision Bridge ካርድ በAI ቅንብሮች ስር ወደ አዲሱ ገጽ የሚወስደው የተስማሚ አገናኝ ነው፤ የቅጂ ቅጥ ቅጽ አይይዝም። የሚዲያ አቅራቢዎችም የምስል-ወደ-ጽሑፍ እና የንግግር-ወደ-ጽሑፍ ሂደቶችን ወደ ተመሳሳይ Modality Bridge ትሮች ይገናኛሉ ነገር ግን የነበረውን Speech-to-Text playground አያስወግዱም።

**የራስ-ሊዩፕ መግቢያ መዝለል:** የdescribe ጥያቄ በOmniRoute የራሱ `/v1` ሊዩፕ ሲያልፍ (ያልተለመደ አቅራቢ ሞዴል), ንዑስ-ጥያቄው
`x-omniroute-admission-bypass: internal` ይልካል እና በተወሰነው ራስ-ሊዩፕ ማረጋገጫ ይማረካል — በአካባቢ ዘዴ የአካባቢው `sk_omniroute` ሰንተኔል፣ ወይም በኦፕሬተር የተዘጋጀው `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` የአካባቢ ቁልፍ (#1350) ስለዚህ
`REQUIRE_API_KEY=true` የተቀመጡ ዲፕሎይመንቶች የdescribe ጥያቄውን ማስኬድ ይችላሉ። መዝለሉ ለእነዚህ ትክክለኛ ማረጋገጫዎች ብቻ ይከበራል፣ ስለዚህ የውጭ አቅራቢዎች አይችሉ header በመጠቀም መግቢያ ማስወገድ።

የቀድሞው ነባሪዎች በ `src/shared/constants/visionBridgeDefaults.ts` ውስጥ ይኖራሉ፤ አዲሱ ዘዴ/ተግባር-የሚያውቅ/ካሽ ነባሪዎችና የቅንብር መወሰኛው በ
`src/shared/constants/modalityBridgeDefaults.ts` ውስጥ ይኖራሉ። የጥበቃ መስመሩ የ `deps` ኮንስትራክተር አማራጭ ያሳያል ስለዚህ ፈተናዎች የሐሰት `getSettings` እና
`callVisionModel` አስፈጻሚዎችን ማስገባት ይችላሉ።

### የኦዲዮ ብሪጅ (`audioBridge.ts`) — Modality Bridge PR-3

የኦዲዮ ይዞ የቻት ጥያቄዎችን ከታደለ ኦዲዮ ግቤት የማይችል መዳረሻ ሲደርሱ በፊት ይቆራረጣል። ቻት ጥያቄውን በፍጹም አይቀይርም፤ የኦዲዮ ክፍሎች በአሁኑ የOpenAI ተስማሚ የተዋሃዱ መግቢያ አካባቢ ይተረጉማሉ እና የተመረጠው የቻት ሞዴል በጽሑፍ ትርጉሞች ይቀጥላል።

የሂደት ደረጃዎች፦

1. `supportsAudio` በ `getResolvedModelCapabilities()` ይታወቃል። ግልጽ የአቅራቢ-ሪጀስትሪ መታወቂያ ይቆጣጠራል፣ ከዚያ የቆራጭ ሞዴል መታወቂያ፣ ከዚያም የተዛመዱ `modalities_input`። የተገለጸ የግቤት ዝርዝር ኦዲዮ ካልያዘ የ `false` ነው፤ የችሎታ ማስረጃ ካልተገኘ `null` ይቆያል። `false` እና `null` ሁለቱም የጥንቃቄ ብሪጅን ያንቀሳቅሳሉ፣ ነገር ግን `true` ይዘው ይዞ ይቀራል።
2. የ `modalityBridgeAudio*` ቅንብሮችን ያውቁ እና ከእያንዳንዱ መልእክት የሚቀይሩ የኦዲዮ ክፍሎችን በ `detectMediaParts()` የተጋራ መቆጣጠሪያ ይሰብስባሉ። የተደጋጋሚ የመስመር ቅርጸቶች OpenAI `input_audio`, `audio_url`, እና `source.media_type: "audio/*"` ናቸው። የተያያዘ ኦዲዮ ለመመራት ይታወቃል ነገር ግን በsplice መንገድ አይወገድም። ስራው በ `modalityBridgeAudioMaxClips` ይገደባል፤ ከዚያ በኋላ ክፍሎች አይታገዱም።
3. የተዘጋጀ `provider/model` አክብሮ ወይም `selectAudioBridgeModel()` በተረጋጋ ካታሎግ ቅደም ተከተል `AUDIO_TRANSCRIPTION_PROVIDERS` ይመራ እና በተገቢው የአቅራቢ ማረጋገጫ የሚሰራ የመጀመሪያውን ሞዴል ይምረጣል።
4. `callAudioTranscription()` የbase64/data-URI ኦዲዮን ወደ multipart
   `file` ይቀይራል፣ ወይም የሩቅ `audio_url` በየህዝብ ብቻ የወጣ ጠባቂ ከDNS ጠባቂ ጋር እና 25 MB ገደብ ይወርዳል። ከዚያ ፋይሉን እና የተመረጠውን ሞዴል ወደ አካባቢ `/v1/audio/transcriptions` ራስ-ሊዩፕ በPOST ይላካል፣ በ `resolveSelfLoopBearer()` የተማረከ ማረጋገጫ ጋር። ያለው transcription መንገድ መደበኛ የማረጋገጫ ፍለጋ፣ የቀዝቃዛ/የደረሰኝ አያያዝ፣ እና የአቅራቢ መላኪያ ይሰጣል።
5. የተሳኩ ጥያቄዎች ክፍሎቻቸውን `[Audio N]: <transcript>` ይለዋዋጣሉ። ጥያቄዎች `Promise.allSettled` ጋር ይሄዳሉ፡፡ የተናቀ አንዱ የመጀመሪያውን ኦዲዮ ክፍል ያቆያል (#4012 ውል)። ሁሉም ጥያቄዎች ካልተሳኩ እና መዳረሻው `supportsAudio === false` ተረጋግጧል ከሆነ፣ ክፍሎቹ
   `[Audio N]: (unavailable — no STT provider connected)` ይሆናሉ (#8430 ውል)። ለያልታወቀ መዳረሻ (`null`) ሁሉም ውድቅ ከሆነ አይታገዱም። የተረጋገጠ ጽሑፍ-ብቻ መዳረሻ የሚገባው የSTT ማረጋገጫ ካልተገኘ እንደዚሁ ግልጽ አቃላዊ ስብ ያገኛል ነገር ግን የኔትዎርክ ጥያቄ አይወጣም።

የተሳኩ ትርጉሞች በፕሮሴስ ውስጥ የሚኖሩ የModality Bridge LRU/TTL ካሽ ይጠቀማሉ።
ቁልፉ የኦዲዮ ማግኛ፣ የተረጋጋ `audio-transcription` ኦፕሬሽን መለያ፣ እና የተመረጠው STT ሞዴል ይዋሃዳል፤ ውድቅ የሆኑ አይቀመጡም። የኦዲዮ ሙከራዎች የተጋራውን `bridged`, `cacheHits`, `failures`, እና `lastUsedAt` ቆጣሪዎች ያዘምናሉ።
የተቀየሩ ምላሾች
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ይይዛሉ፤ ያልተቀየሩ ጥያቄዎች የኦዲዮ ብሪጅ ክፍል አይይዙም።

የሂደት ቅንብሮች በዳታቤዝ የተደገፉ ናቸው እና በZod የተረጋገጡ ናቸው፦

### ቪዲዮ ብሪጅ (`videoBridge.ts`, `videoBridgePipeline.ts`)

በChat Completions `messages` እና Responses API `input` ውስጥ ወደ አንድ ዓላማ ያልታወቀ የቪዲዮ የተፈጥሮ ድጋፍ ከሌለው በፊት ከፍተኛ ደረጃ የቪዲዮ ክፍሎችን ይቆርጣል። የተደገፉ ቅርፀቶች `input_video`, `video_url`, `video_source`, የHTTPS URLs, እና `data:video/*;base64,...` የውሂብ URIዎች ናቸው። በጽሑፍ ውስጥ የተጻፉ የፋይል ስሞች እንደ ቪዲዮ አይቆጠሩም።

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) የጥያቄ ጉዞ, የችሎታ/ፖሊሲ ምርመራ, በጥያቄ ላይ የሚደረግ ማጠናከሪያ, እና የምላሽ ጭነትን ይቆጣጠራል። በቪዲዮ ላይ የሚደረግ ስራ — መያዝ, ሙሉ-ውጤት ካሽ, የፍሬም ቅደም ተከተል መግለጫ (ይህም የተጠሪው የኦዲዮ ትርጉምን ያጣምራል), እና በሙከራ ላይ የሚደረጉ ሜትሪክስ/ማቋረጫ/ማጽዳት — በ`processVideoPart` ውስጥ ተደብቆ አለ በ`videoBridgePipeline.ts`, በ`preCall` ሒደት ውስጥ በቪዲዮ ክፍል ላይ አንድ ጊዜ ይጠራል። ይህ ሞጁል እንዲሁም ግልጽ የፖርት ድንበሮችን ይገልጻል — `VideoMediaBrokerPort` (ባይቶችን መያዝ እና የተመረጡ ፍሬሞችን መውጣት), `VideoAudioTranscriptionPort` (የተጠሪው የኦዲዮ ትርጉምን ከተመረጡ ካፕሽኖች ጋር መዋሃድ), እና `VideoDrilldownPort` (የታዋቂ የቀድሞ የውሂብ ቅርፀት)። የምርት STT እና የፍሬም ማስቀመጫ በ`createVideoSttAdapter` እና `createVideoDrilldownAdapter` በመካከል በመግለጫ ፖርት ዙሪያ ይደርሳሉ፤ ከዚህ ውስጥ ከሆነው የተጋራ የውስጥ ድምብ አንደበት የህይወት ዑደትን ይጠቀማል።

የውጭ `/v1` የጥያቄ መንገድ ፕሮሴስ ወይም ንዑስ ፕሮሴስ በፍጥነት አይጠራም። የውጭ ቪዲዮዎች ከ50 MiB ገደብ በታች ይወርዳሉ፤ የበይነ መረብ base64 ቪዲዮዎች በቪዲዮ ላይ የተወሰነ 36 MiB የተቀናጀ ገደብ አላቸው ስለዚህ ሞዴሉ/መልእክቶች/የመስተንግዶ አቅጣጫ በውጭ JSON የጥያቄ መግቢያ ገደብ ውስጥ እንዲቆይ ይደረጋል። የበይነ መረብ ርዝመት እና የተቀናጀ መጠን ከመመደብ በፊት ይምረመራሉ። በመጀመሪያው የውጭ URL እና በሁሉም እንደገና መምሪያ ላይ HTTPS ያስፈልጋል፣ ይህም በአሁኑ የውጭ ብቻ የሆነ የውጭ መውጫ ጠባቂ ከDNS ፒኒንግ ጋር ተጠቃሚ ነው። ባይቶቹ በትክክል የውስጥ `POST /api/modality-bridge/video/extract` የባንክ ድንበርን ይሻገራሉ። ይህ መንገድ `LOCAL_ONLY` እና `SPAWN_CAPABLE` ነው፣ በፕሮሴስ ላይ የተሟሟ የተማከረ የሎፕባክ ጥያቄ ብቻ ይቀበላል፣ እና በፍጥነት URL, የፋይል መንገድ, አከናውንያ, ወይም የአርግዩመንት ዝርዝር አይቀበልም። የAPI አካል-መጠን ቻንክ እና የአንቀጽ የአካል አንቀጽ አንቀጽ አንዱ በትክክል የ50 MiB የባንክ ግብዓት ገደብን ይጠብቃሉ። የተወሰነው ተራ አንድ ማውጫ በአንድ ጊዜ አንድ ማውጫ ያስፈጽማል፣ አራት በመጠባበቅ ላይ ያሉ ስራዎችን ይፈቅዳል፣ እና በመጠባበቅ ላይ ያለውን ግብዓት በ100 MiB ይገደባል።

በባንክ ውስጥ, `ffprobe` የግል የአካባቢ ፋይል ይነባል፤ የተወሰኑ ቅርፀቶች የፕሌይሊስት እና የማኒፌስት ቅርፀቶችን ያስወግዳል። ለተፈቀደው MOV-ቤተሰብ ኮንቴነሮች፣ የውጭ MOV ውሂብ ማጣቀሻዎች በነባር ተሰናክለዋል፣ እና የተወሰነው ትእዛዝ አይቀርበውም። `ffprobe` እና `ffmpeg` የ`file`-ብቻ ፕሮቶኮል ነጻ ዝርዝር, አንድ ክፍል, የተወሰኑ አርግዩመንት ዝርዝሮች, ምንም shell የለም, እና ከ`PATH` የተወሰኑ አከናውንያዎችን ይጠቀማሉ። የተያያዙ ምስል ካቨር ስትሪሞች አይጫወቱም። ሁሉም የሚጫወቱ ስትሪሞች ወሰኖቹን ማሟሟ አለባቸው፣ እና ግልጽ ነባር ስትሪም ከተወሰነው ዝርዝር በፊት ይመረጣል። ቪዲዮዎች እስከ 600 ሰከንድ, 8,192 ፒክስል በአንዱ አቅጣጫ, እና 33,554,432 የምንጭ ፒክስሎች ይገደባሉ። FFmpeg 1–16 የመካከለኛ የJPEG ፍሬሞችን ይወስዳል፣ ረጅም ጠረጴዛውን እስከ 1,024 ፒክስል ያደቅ ይቆረጣል አነስተኛ ግብዓት አይደግፍም፣ እና URL በፍጥነት አይቀበልም። ምርጫው `uniform` በነባር ነው። አማራጭ `scene_aware` እና የሙከራ `segment_aware` ፖሊሲዎች በተሟሟ የተወሰነ የFFmpeg ሂደት በቀድሞው የተሟሟ የአካባቢ ስትሪም ላይ ይሰራሉ፣ የተወሰኑ የ`showinfo` ሲን ጊዜ ማስታወቂያዎችን ይምረጣሉ፣ እና በመታወቂያ አልተሳካም, ጊዜ አልቆ, የተበላሸ ውጤት, ወይም ባዶ እቃ ላይ በትክክል ወደ ተመሳሳይ የuniform መካከለኛዎች ይመለሳሉ። የsegment-aware ዘዴ የመካከለኛ ምርጫዎችን በተሟሟ የሆኑ የሲን ክፍሎች ርዝመት መጠን ያደርጋል፤ የsegment-aware ማስረጃ እና የመመለሻ ባህሪ በታች በዝርዝር ተገልጿል። የጠንካራ 16-ፍሬም ገደብ በሁሉም ፖሊሲ ምርጫ በኋላ ይተገበራል። ሲን-አዋቂ ጥያቄ አንድ ፍሬም ብቻ ካለው በመጠን ሲኖረው፣ የuniform መካከለኛ የሙሉ ቪዲዮ ወይም የተመረጠ መስክ መካከለኛ ይጠቀማል እና `policyEffective: uniform` ይዘው ይገልጻሉ፤ አንድ የተመረጠ ሲን ፍሬም ሁለቱንም የጊዜ መጨረሻዎች ማስቀመጥ አይችልም። ተጠሪው በአማራጭ መልኩ የተወሰነ የትንታኔ መስክ (`start`/`end` ሰከንዶች) ሊያቀርብ ይችላል፤ ወሰኖቹ ወደ የሚዲያው ቆይታ ይቀናጃሉ፣ የተቀየሩ ወይም ያልተወሰኑ መስኮች ይተወዳሉ፣ እና ሁሉም የምርጫ ፖሊሲዎች በተንቀሳቃሽ ክፍል ውስጥ ብቻ ይፈጸማሉ። የተወሰነው መስክ በምርጫ ሜታዳታ እና በያልታመነ መግለጫ ቅድመ አስተያየት ውስጥ ይካተታል ስለዚህ በኋላ ሞዴሎች የተመረጠ ክፍል ከሙሉ የጊዜ መስመር ውስጥ የተለየ መሆኑን ሊለዩ ይችላሉ።

የሴማንቲክ ካፕሽን ትንታኔ በተለየ ቅንብር ነው። ነባር `full` የትንታኔ ሞዴ አሁኑን ያለውን የፍሬም ፕሮምፕት ያቆያል እና የጥያቄ ጽሑፍን ወደ ካፕሽን ሞዴል አይልከውም። በ`focused` ሞዴ፣ ብሪጁ ከተመሳሳይ Chat ወይም Responses ኮንቴነር የተጠቃሚውን የቅርብ ያለውን ባዶ ያልሆነ `text`/`input_text` ብቻ ይያዛል፣ ወደ NFC ይኖርማላል፣ የመቆጣጠሪያ ቁልፎችን እና ነጠላ ክፍተቶችን ይቀንሳል፣ እና እስከ 500 ዩኒኮድ ኮድ ነጥቦች ይገደባል። ባዶ ውጤት በትክክል ወደ `full` ፕሮምፕት ይመለሳል። የሚጠቀም ምክር እንደ JSON በተለየ ያልታመነ የተጠቃሚ-ኮንቴክስት ቦታ ውስጥ ይቀመጣል እና በተመረጡ ዝርዝሮች ላይ ብቻ ሊሰራ ይችላል፤ በሚዲያው ውስጥ የሚታዩ መመሪያዎችን መከተል ላይ የተለየ ማስጠንቀቂያ ማሻሻያ አይችልም። የጽሑፍ ትንታኔ በፍጥነት `start`/`end` አይገምትም ወይም የጊዜ ምርጫውን አይቀይርም።

አስጠሪዎች ቀድሞ የተዛመደ ጽሑፍ ካላቸው በተደጋጋሚ የቪዲዮ ክፍል ላይ አማራጭ `transcript.cues` ዝርዝር ማካተት ይችላሉ። እያንዳንዱ cue የጽሑፍ፣ በተወሰነ ውስጥ የሚገኝ የ`start`/`end` ክፍተት እና በነባሪ ዝርዝር የተፈቀደ `source` (`client`, `embedded`, ወይም `audio-bridge`) መያዝ አለበት፤ `confidence` ነባሪው 1 ነው እና በ0 እና 1 መካከል መቆየት አለበት። ትክክለኛ የተደጋጋሚ cue ይዋሃዳሉ። OmniRoute ከዚህ መረጃ መሰንዘሪያ መጀመር አይችልም፡ የተረጋገጡ cue በተገለጸው ውጤት ውስጥ ከsource፣ confidence እና ክፍተት ጋር ይቀዳሉ፣ እና ከframe caption ጋር እንደማይታመኑ ምርመራዎች ይታያሉ። የተሳሳተ፣ ከክልሉ ውጭ ወይም የማይታወቀው ጽሑፍ ይተወዋል እና በcaption ወንድም ውስጥ አይቀላቀልም። የrequest-body transcript ቻናሎች የተሰጠውን provenance ወደ `client` ያካትታሉ፣ ራሳቸው የተጠቀሱ `embedded` ወይም `audio-bridge` መለያዎችን ጨምሮ። የአገልጋይ ባለቤት adapter ብቻ እነዚህን የታመኑ መለያዎች በኮድ-ብቻ `trustedSource` አርጉመንት ማስያዝ ይችላል፤ የrequest JSON መስክ ወደዚያ አይደርም። የtranscript ጽሑፍ የማይታመን ከሚዲያ የተገኘ ይቆያል፣ ከprovenance ጋር ቢሆንም፣ እና ማንኛውም የፈቃድ መወሰን አይችልም።

የሚያውቁ አስጠሪዎች ለተመሳሳይ ቪዲዮ `audioTranscript` ትራክ ማቅረብ ይችላሉ፤ እንደ ደንበኛ የተሰጠ ጽሑፍ ይቆጠራል፣ የአገልጋይ ትርጉም ማረጋገጫ አይደለም። የfusion seam የራሱን የራዕይና የድምፅ ምርመራዎች በአንድ የጊዜ ገደብና የማቋረጫ ምልክት ይያዛል፣ በአንድ የጊዜ መስመር ላይ ያደርጋል፣ ትክክለኛ የተደጋጋሚዎችን ይዋሃዳል፣ እና አንዱ ብቻ ሲሳካ ከአንዱ በኋላ የተሳካ የከፊል ውጤት ይወጣል። የተሳሳተ `audioTranscript` ወደዚያ የከፊል ውጤት ይወርዳል — የራዕይ መግለጫ ይቀመጣል እና የድምፅ ቅርንጫፍ የተጠበቀ የአሳያ አደጋ ኮድ ይመዝገባል — ከቪዲዮው ሁሉ መሳካት ይበልጣል። የቅርንጫፍ አገናኝነት፣ የከፊል ምልክት፣ እና የተጠበቁ የአደጋ ኮዶች በተገለጸው ውጤት፣ በguardrail መረጃዎች (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), በresult-cache መረጃዎች እና በbridge fusion ቆጣሪዎች ይጠበቃሉ። የተሰጠው የVideo Bridge መንገድ የንግግር-ወደ-ጽሑፍ አይጠራም ወይም ሁለተኛ የሚዲያ ቅጂ አይወስድም፤ ያ ትራክ በግልጽ ሁኔታ ካልተሰጠ ቪዲዮ ብቻ ይቆያል።

**የTranscript ግብረ-መልስ (#12150 P1).** ይህ በራሱ ሲሆን ሁሉ ጊዜ የVideo Bridge (ራሱ በምርጫ ላይ) የtranscript cue ሲያቀርብ በራሱ ይተገበራል — የተለየ retention flag የለም። ማንኛውም ጥያቄ የtranscript cue ሲያቀርብ (የአስጠሪው የተገለጸ `transcript` ### የPII መደበቂያ (`piiMasker.ts`)

በ**ሁለቱም** ደረጃዎች ላይ ይሰራል።

- **`preCall`** የተላከውን መጠየቂያ ይቅዳል፣ `system`፣ `messages`፣ `input` እና
  `prompt` (ቀላል የstring እቃዎችን ጨምሮ) ይመላለሳል፣ እና `processPII()` (ከ
  `@/shared/utils/inputSanitizer`) በstring `content`/`text` መስኮች ላይ ይተግባራል። ሲሆን
  `PII_REDACTION_ENABLED=true` ከሆነ፣ የተገኙ የPII መረጃዎች በወጪ መጠየቂያ ይደበቃሉ። ይህ ከ
  `INPUT_SANITIZER_MODE` በተለየ ነው (ይህ ብቻ የprompt-injection ፖሊሲን ይቆጣጠራል)። የመደበቂያው ሲታገድ፣ ጥምረቱ የተገኙትን ብዛት ይመዝግባል ይሁን እንጂ ይዘቱን አይቀይርም።
- **`postCall`** ምላሹን በጥልቅ ይቅዳል፣ `sanitizePIIResponse()` እና
  የResponses-API-ቅርጸት መደበቂያ (`maskResponsesOutput` — `output_text` እና `output[].content[].text` ይሸፍናል) ይሰራል። ማንኛውም መደበቂያ ከተፈጸመ፣ የተቀየረው ምላሽ የመጀመሪያውን ይተካል።

መከላከያው በፍጹም አይከልከልም፤ ማስታወቂያ ብቻ ይጨምራል (`meta.detections`,
`meta.redacted`) ወይም ይቀይራል።

### የPrompt Injection (`promptInjection.ts`)

በተጠቃሚ የቀረበ ይዘት ውስጥ የጠላት መዋቅሮችን ይያዣል እና የተቀመጠውን ፖሊሲ ይተግባራል። ባህሪው በenvironment variables እና በconstructor options ይመራል፦

| ቅንብር       | Env var                                                                                               | ነባር    | ተፅዕኖ                                                                                                                                           |
| ---------- | ----------------------------------------------------------------------------------------------------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| ተችሏል       | `INPUT_SANITIZER_ENABLED`                                                                             | `true` | ሲሆን `false` መከላከያው በፍጹም ይቋረጣል።                                                                                                                 |
| ዘዴ         | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn` | የInjection ፖሊሲ፡ `block`, `warn`, ወይም `log`። (`redact` ለቅድሚያ ተስማሚ ነው ነገር ግን የinjection ጽሑፍ አይወግድም፤ የPII መደበቂያ በ`PII_REDACTION_ENABLED` ይቆጣጠራል።) |
| የመከልከያ መጠን | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high` | ለመከልከል የሚያስፈልገው ዝቅተኛ ከፍተኛነት። አካባቢው በነባሩ ላይ ማስተዋወቅ ብቻ ነው።                                                                                       |

**የዘዴ ቅደም ተከተል** (`getMode`): የጠራው `options.mode` →
`INJECTION_GUARD_MODE` **የDB feature-flag override** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`። ስለዚህ የdashboard override በenv vars ላይ ይቆያል፣ ስለዚህ የFeature Flags UI በቀጥታ የሚሰራውን መከላከያ ይቆጣጠራል (እንደገና ሳይጀምር)። የDB ንባብ የተያያዘ ነው፤ ስለዚህ ሲስተር መከላከያው ወደ env-based ባህሪ ይመለሳል፣ እና ምንም የoverride ካልተቀመጠ ባህሪው ከenv ብቻ ጋር አንድ ነው።

የመያዣ ምንጮች፦

1. `sanitizeRequest()` ከ `@/shared/utils/inputSanitizer` (በሌሎች ቦታዎች የሚጠቀሙት የተጋራ መያዣ ስብስብ)።
2. የተገናኘ `DEFAULT_GUARD_PATTERNS` (አሁን `system_override_inline` እና
   `markdown_system_block`, ሁለቱም `high` ከፍተኛነት)።
3. በተፈጥሮ በconstructor options የተሰጡ `customPatterns` (strings, regex,
   ወይም `{ name, pattern, severity }` መዝገቦች)።

`mode === "block"` **እና** ቢያንስ አንድ መያዣ ወደ መከልከያ መጠን ከደረሰ፣ `preCall` ይመልሳል `{ block: true, message: "Request rejected: suspicious content detected" }`። በ`warn`/`log` ዘዴዎች መከላከያው ይመዝግባል ነገር ግን ጥሪውን ይፈቅዳል። የተጋራው helper `evaluatePromptInjection()` እንዲሁም ለተጠቃሚዎች ያስመውዛል በመዝገቡ ውስጥ ሳይገቡ የprompt ማረጋገጫ ከፈለጉ።

**የመቃኘት ገደብ (v3.8.20):** መያዣው የprompt ጽሑፍን **የመጀመሪያውን 16 KB** ብቻ ይመለከታል — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 bytes) በ`src/shared/utils/inputSanitizer.ts` ውስጥ። `detectInjection()` እና
`evaluatePromptInjection()` ሁለቱም `slice(0, MAX_INJECTION_SCAN_BYTES)` ከመስመሩ በፊት ይሰራሉ። የinjection መመሪያዎች በግብዣ ላይ ቅርብ ስለሆኑ፣ ይህ በብዙ መቶ-KB መጠየቂያዎች ላይ የregex CPU/GC ይገድባል ያነሳል ነገር ግን መያዣውን አያሳነስም (cf.
#3932, #4041).

### የማስረጃ መደበቂያ (`credentialMasker.ts`)

በ**ሁለቱም** ደረጃዎች ላይ ይሰራል፣ በነባር ሰንሰለቱ መጨረሻ (priority `95`)። የታወቀ የAPI-key / secret-token መያዣዎችን ከወጪ መጠየቂያ (የመልእክት ይዘት፣ የመሣሪያ ጥሪ አርግሞች፣ የመሣሪያ ውጤቶች) **እና** ከአቅራቢው ምላሽ ይደበቃል፣ ስለዚህ የማስረጃ ቁልፍ በprompt ውስጥ ቢገባ (ወይም በመሣሪያ ውጤት ቢመለስ) ወደ አቅራቢው ወይም ወደ ተጠቃሚው አይፈለግም።

- **በራስ ፈቃድ ብቻ**፣ ከ PII መጠበቂያ ጋር ተመሳሳይ ልምድ (ጠንካራ ደንብ #20-ቅርብ):
  እስከማይነቃነቅ `settings.credentialRedactionEnabled === true` **ወይም**
  `CREDENTIAL_REDACTION_ENABLED=true` አይሰራም። ከተጠፋ በኋላ፣ መከላከያው ምንም አይሰራም —
  በፍጹም አይከለከልም እና አይቀይርም።
- `redactCredentials()` የተላከውን/የተመለሰውን መልእክት ዛፍ በሙሉ ይመራል (`walkValue()`,
  ከ prototype-pollution የተጠበቀ፣ ከ cycle የተጠበቀ በ `WeakSet`) እና የተዛመዱትን ክፍሎች በ `[REDACTED:<type>]` ቦታ ይቀይራል፣ በእውነቱ የተቀየሩትን ቅርንጫፎች ብቻ ይቅዳል።
- `CREDENTIAL_PATTERNS` የ LLM አቅራቢዎችን ቁልፎች (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), የ VCS/SaaS ቶክኖች (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), የክፍያ ቁልፎች (Stripe, Square), የደመና ቁልፎች (AWS access key, Twilio, SendGrid, Mailgun), የግል ቁልፎች / JWTs,
  የማስተላለፊያ ሐረጎች ውስጥ የሚያከብሩ መረጃዎች (`mongodb://user:pass@...`, ወዘተ), እና
  አጠቃላይ `Authorization`/`x-api-key`/`api-key`/`apikey` አሰጣጥ-እሴት
  አቀማመጦችን ይሸፍናል። የ header ቅርጸ-ቁልፎች (`authorization`, `x-api-key`, `api-key`,
  `apikey`) በመዋቅሩ (እሴቱ ብቻ፣ የ scheme ቅድመ-ቃል እንደ
  `Bearer `/`Basic ` የተጠበቀ) ይሸፍናሉ እንጂ በአጠቃላይ የጽሑፍ regex አይሆንም።
- መከላከያው በፍጹም አይከለከልም፤ የሚያደርገው ብቻ (`modifiedPayload` /
  `modifiedResponse`) ነው እና ይገልጻል (`meta.credentialsRedacted`, `meta.count`)።

የተደጋጋሚ መከላከያ፡ `tests/unit/credential-masker-guardrail.test.ts`።

## መሠረታዊ ውል (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ሰንሰለቱን ወዲያውኑ ያቋርጣል
  message?: string; // ሲታገድ ይታያል
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ጥያቄውን እንደገና ለመጻፍ በ-preCall ይመለሳል
  modifiedResponse?: TValue; // ምላሹን እንደገና ለመጻፍ በ-postCall ይመለሳል
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

አንድ guardrail `void`፣ `{}` ወይም `{ block: false }` በመመለስ "ለውጥ የለም" የሚል ምልክት ይሰጣል። `modifiedPayload`/`modifiedResponse` መመለስ በሰንሰለቱ ውስጥ ወደ ታችኛዎቹ guardrails የሚተላለፈውን እሴት ይተካል።
`signal?: AbortSignal` የጠሪውን የሕይወት ዑደት ወደ guardrails ያስተላልፋል። የጥያቄ ማቋረጥ ሆን ተብሎ የተደረገው ክፍት-በመተው የሚሳካ ልዩ ሁኔታ ነው፦ የሚዲያ ማገናኛዎች ሥራቸውን ያቆማሉ እና ያጸዳሉ፤ ጥሬ ሚዲያን እንደማይደግፈው ወደሚታወቅ ዒላማ ግን አይመልሱም።

## መዝገብ (`registry.ts`)

ብቸኛው `guardrailRegistry` የሚከተሉትን ያቀርባል፦

- `register(guardrail)` — guardrail ያክላል (ወይም በመደበኛ የስም ቅርጹ መሠረት ይተካል)፣ ከዚያም በ`priority` ከዝቅተኛ ወደ ከፍተኛ እንደገና ይደረድራል።
- `clear()` / `list()` — የአስተዳደር ረዳት መሣሪያዎች።
- `runPreCallHooks(payload, context)` — ንቁ guardrailsን በየተራ ያካሂዳል፣ payloadን በ`modifiedPayload` በኩል ያስተላልፋል፣ እና በመጀመሪያው `block: true` ላይ ያቆማል።
- `runPostCallHooks(response, context)` — በምላሹ በኩል ተመሳሳይ ፍሰትን ይከተላል።
- `resetGuardrailsForTests({ registerDefaults })` — ለንጹሕ የሙከራ ማግለል ሁኔታውን ያጸዳል፣ እና እንደ አማራጭ ነባሪዎቹን እንደገና ይመዘግባል።

ሁለቱም አስኪያጆች `{ blocked, payload|response, results, guardrail?, message? }` ይመልሳሉ፤ በዚህ ውስጥ `results` ለእያንዳንዱ guardrail `blocked`፣ `skipped`፣ `modified`፣ `error` እና `meta` መስኮችን የሚያካትቱ የ`GuardrailExecutionResult` መዝገቦች ድርድር ሲሆን፣ ለክትትል ጠቃሚ ነው።

### Guardrailsን በእያንዳንዱ ጥያቄ ማሰናከል

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` ለአሁኑ ጥያቄ መዝለል ያለባቸውን የguardrail ስሞች ድግግሞሽ የተወገደለት ዝርዝር ያሰባስባል። ምንጮቹ (ሁሉም አማራጭ፣ ሁሉም የሚዋሃዱ)፦

- `apiKeyInfo.disabledGuardrails`
- የጥያቄ አካል `disabledGuardrails` (ከፍተኛ ደረጃ)
- የጥያቄ አካል `metadata.disabledGuardrails`
- ራስጌ `x-omniroute-disabled-guardrails` (ወይም የቀድሞው
  `x-disabled-guardrails`)

እሴቶቹ የሕብረቁምፊዎች ድርድር ወይም በኮማ የተለየ ሕብረቁምፊ ሊሆኑ ይችላሉ፤ ስሞች ወደ ትንሽ ፊደል kebab-case (`pii_masker` → `pii-masker`) ይደበኛሉ። ውጤቱ በ`context.disabledGuardrails` በኩል ወደ መዝገቡ ይተላለፋል፤ መዝገቡም ተዛማጅ guardrailsን ይዘላል (`skipped: true` በ`results` ውስጥ)።

## የአፈጻጸም ቅደም ተከተል

በ`src/sse/handlers/chat.ts` እና
`open-sse/handlers/chatCore.ts` በኩል ለሚያልፍ ለእያንዳንዱ ጥያቄ፦

1. `resolveDisabledGuardrails(...)` ከAPI ቁልፍ፣ ከbody እና
   ከheaders የመዝለያ ዝርዝሩን ይገነባል።
2. `guardrailRegistry.runPreCallHooks(body, ctx)` guardrailsን በቅድሚያ
   ደረጃቸው ከዝቅተኛ ወደ ከፍተኛ ቅደም ተከተል ያስኬዳል፦
   - የተሰናከሉ guardrails እንደ `skipped` ይመዘገባሉ።
   - የእያንዳንዱ guardrail `preCall` በ`modifiedPayload` አማካኝነት payloadን እንደገና ሊጽፍ ይችላል።
   - የመጀመሪያው `block: true` ሰንሰለቱን ወዲያውኑ ያቋርጣል፣ እና handlerው
     የguardrail ውድቅ ማድረጊያ ምላሽ ይመልሳል።
3. (ሊሻሻል የሚችለው) payload ወደ combo routing እና upstream
   dispatch ይገባል።
4. ምላሹ ከተዋቀረ በኋላ፣ `guardrailRegistry.runPostCallHooks(...)`
   በምላሹ ላይ ያንኑ ሰንሰለት ያስኬዳል። እዚህ ያለ `block: true` የupstream
   ምላሹን ይጥላል።

ስህተት የሚያስነሱ guardrails በ`error: <message>` ይመዘገባሉ፣ እንዲሁም በ
`logger.warn` በኩል log ይደረጋሉ፤ ነገር ግን ሰንሰለቱ ይቀጥላል — ይህ በንድፍ fail-open ነው።

## ብጁ መከላከያዎች

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ደረጃዎች፦

1. `BaseGuardrail`ን የሚወርስ `src/lib/guardrails/myGuardrail.ts` ይፍጠሩ።
2. `preCall` እና/ወይም `postCall`ን ይተግብሩ።
3. በመጫን ጊዜ ይመዝግቡ (`registerDefaultGuardrails` ውስጥ ያክሉ) ወይም
   በአሂድ ጊዜ `guardrailRegistry.register(...)`ን ይጥሩ — መዝገቡ ተመሳሳይ መደበኛ የተደረገ ስም ያለውን
   ቀደምት መከላከያ ይተካል።
4. ሙከራዎችን በ`tests/unit/` ስር ያክሉ (ያሉ ምሳሌዎች፦
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)።
